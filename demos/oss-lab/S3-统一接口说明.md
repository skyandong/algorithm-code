# S3 统一接口说明（oss-lab 改造核心思路）

> 本文档解释 `oss-lab` 从阿里云专有 SDK 迁移到 `aws-sdk-go-v2` 的 S3 接口后，
> 「S3 代码」到底是什么、为什么能做到「本地 MinIO / 生产阿里云 OSS 只改配置不改动业务代码」。
> 阅读对象：想理解架构选型、或后续要把对象存储接入自己项目的同学。

---

## 1. "S3" 是什么

**S3 = Amazon Simple Storage Service**，亚马逊 2006 年推出的对象存储服务。
它的接口设计得太成功了，以至于业界形成了一个共识：**「兼容 S3 协议」≈ 对象存储的通用语言**。

于是下面这一长串存储服务，都「能听懂 S3 的指令」：

- 本地 / 自建：MinIO、SeaweedFS、Ceph RGW、Garage、RustFS
- 公有云：阿里云 OSS（S3 兼容模式）、腾讯云 COS、AWS S3、华为云 OBS、Google Cloud Storage（互操作模式）……

**打个比方**：S3 协议就像 **USB 接口标准**。你的 U 盘（业务代码）只要做成 USB 口，
插到任何带 USB 的电脑（存储后端）上都能用——不管那台电脑是戴尔、联想还是苹果。

---

## 2. "S3 代码" 指什么

就是**用实现了 S3 协议的 SDK 写出来的代码**。在本项目中，具体指 `aws-sdk-go-v2` 的 `s3` 包。
代码里全是基于 S3 标准协议的「通用指令」：

```go
// 上传一个对象 —— 任何 S3 兼容存储都认这个
s3Client.PutObject(ctx, &s3.PutObjectInput{
    Bucket: aws.String("oss-lab"),
    Key:    aws.String("demo/hello.txt"),
    Body:   strings.NewReader("..."),
})

// 列举 / 下载 / 生成签名 URL —— 都是 S3 标准 API
s3Client.ListObjectsV2(ctx, &s3.ListObjectsV2Input{...})
s3Client.GetObject(ctx, &s3.GetObjectInput{...})
s3Client.PresignGetObject(ctx, &s3.GetObjectInput{...})  // 签名 URL
```

### 切换的「魔法」

关键在 `storage/client.go` 里那一句——**只改端点地址，同一个 `PutObject` 调用就从一个存储跳到另一个存储**：

```go
cfg.BaseEndpoint = aws.String("http://127.0.0.1:9000")                 // 本地 MinIO
// cfg.BaseEndpoint = aws.String("https://s3.oss-cn-hangzhou.aliyuncs.com")  // 生产阿里云 OSS
```

因为两边说的都是 S3 这门「通用语言」，所以业务层对「背后到底是哪家存储」完全无感知。

## 3. "非 S3 代码" 长什么样，为什么切不动

改造前的 `oss-lab` 用的是阿里云**专有 SDK** `aliyun-oss-go-sdk`，它有一套独家 API：

```go
// 阿里云独有，MinIO 根本不认识这些函数
bucket.SignURL("hello.txt", oss.HTTPGet, 600)
bucket.PutObject("key", reader, oss.ContentType("image/png"))
```

这套 API 在 S3 协议里**没有对应物**。一旦你的代码调用了 `bucket.SignURL()`，
就等于给 U 盘焊死了一个「苹果专属接口」——插不进任何非苹果电脑。

**这就是改造前「这套代码切不到 MinIO」的根因**：不是配置问题，是 SDK 选型锁死在了阿里云。

---

## 4. 专有 SDK vs S3 统一接口 对比

| 维度 | 专有 SDK 写法（旧） | S3 统一接口写法（新） |
|---|---|---|
| 上传对象 | `bucket.PutObject(...)` | `s3Client.PutObject(...)` |
| 签名 URL | `bucket.SignURL(...)`（独家 API） | `s3Client.PresignGetObject(...)` |
| 列举对象 | `bucket.ListObjects(...)` | `s3Client.ListObjectsV2(...)` |
| 切换后端 | **重写代码**（不同 SDK 不同 API） | **改 `BaseEndpoint` 一个变量** |
| 本地能跑吗 | ❌ 必须真实阿里云账号 | ✅ 本地 MinIO / SeaweedFS 即可 |
| 生态通用性 | 仅限该厂商 | 全行业 S3 兼容服务通用 |

**一句话总结**：S3 代码 = 用业界通用协议写的存储操作代码；
它让「测试环境用本地存储、生产切阿里云 OSS」从「重写一遍」降级成了「改几行配置」。

## 5. 改造中踩过的坑（统一 S3 接口的通用陷阱）

这些坑在「任意 S3 兼容存储」上都可能遇到，已固化进 `storage/config.go` 与客户端实现：

### 5.1 寻址风格 `UsePathStyle`
- MinIO / 本地部署：用 **path-style** `http://127.0.0.1:9000/mybucket/key` → `UsePathStyle=true`
- 阿里云 OSS：**只支持 virtual-hosted style** `https://mybucket.s3.oss-cn-hangzhou.aliyuncs.com/key`，
  path-style 请求会被直接拒绝 → `UsePathStyle=false`

### 5.2 Endpoint 端点不能混用
- S3 SDK 用：`s3.oss-cn-hangzhou.aliyuncs.com`（注意带 `s3.` 前缀）
- 专有 SDK 用：`oss-cn-hangzhou.aliyuncs.com`（**不带 `s3.`**）
- 两者**不能互换**，混用会连错服务。

### 5.3 绕开 `aws-chunked` 分块传输
阿里云 OSS 不支持 chunked encoding。Go SDK v2 的 `manager.Uploader` 在传 ≥5MB 文件时会
**自动启用 chunked**，直接报 `InvalidArgument: aws-chunked encoding is not supported`。
→ 本项目**刻意不用 `manager.Uploader`**，分片逻辑手写，跨后端通用。

### 5.4 关闭默认 CRC32 校验
新版 aws-sdk-go-v2 默认给所有 `PutObject` 加 `x-amz-checksum-crc32` 头，
部分第三方存储不识别。
→ 在 `storage/config.go` 中设置 `RequestChecksumCalculation = when_no_retry`、
`ResponseChecksumValidation = when_no_retry` 关闭自动校验。

### 5.5 并发分片必须按 part number 升序合并
`CompleteMultipartUpload` 要求 parts **严格按 PartNumber 升序**。
并发上传时用 `append` 收集分片会导致顺序错乱 → OSS/MinIO 均报 `InvalidPartOrder`。
→ 改用「按分片号索引写入」的数组，天然有序。这 bug 在 OSS 上同样会触发，已根治。

### 5.6 ETag 不一致
- OSS 的 PUT 上传 ETag 是**大写**，S3 是**小写**
- **分片上传的 ETag 算法两端完全不同**
- 若用 ETag 做缓存/完整性校验：忽略大小写，且分片场景**不能跨服务比对**。

### 5.7 阿里云新政策（2025-03-20 起）
新开通 OSS 用户，中国内地 Bucket 无法通过默认外网域名调用上传/下载等数据类 API，
必须走 **CNAME 自定义域名**（HTTPS 还需配 SSL 证书）。

## 6. 本地怎么跑（开箱即用）

```bash
cd oss-lab
docker compose up -d            # 用本地缓存的 MinIO 起 S3 兼容存储（端口 9000）
go run .                       # 自动建桶，跑全套演示（上传/下载/列举/签名URL/分片/...）

# 切生产：只改环境变量，代码一行不动
export STORAGE_BACKEND=aliyun STORAGE_REGION=cn-hangzhou \
       STORAGE_ACCESS_KEY=<RAM子账号AK> STORAGE_SECRET_KEY=<SK> STORAGE_BUCKET=<你的bucket>
```

> 注：本机 Docker Hub 直连超时，但 `docker.m.daocloud.io` 镜像源可达，已用缓存的 MinIO 镜像；
> SeaweedFS 镜像拉不下来，故本地用 MinIO（它才是 S3 协议事实标准，对「能否平滑切 OSS」最有代表性）。
> 关于 MinIO 自身进入维护模式 / 归档的现状，见仓库对话记录，不影响本地开发使用。

## 7. 一句话回顾

| 概念 | 含义 |
|---|---|
| S3 协议 | 对象存储的「通用语言」（类比 USB 接口标准） |
| S3 代码 | 用 `aws-sdk-go-v2` 等 S3 SDK 写、可被任何兼容存储执行的存储操作代码 |
| 专有 SDK | 厂商独家 API（如 `aliyun-oss-go-sdk`），锁定单一云，无法切换 |
| 统一接口的价值 | 本地 MinIO ↔ 生产阿里云 OSS，只改 `BaseEndpoint`，业务零改动 |
