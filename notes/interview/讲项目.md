# 讲项目：把学习仓库讲成工程能力

> **核心认知：** 面试官问"讲讲你的项目"，考察的不是项目本身多牛，是**你有没有工程思维**——能不能讲清"为什么这么做"（决策过程）、"踩了什么坑"（真实经历感）、"和生产差距在哪"（清醒认知）。本篇把本仓库的素材（gRPC 服务、kitex、tracing、Kafka 笔记、一致性哈希等）重组为 STAR 叙事，每个素材配"面试官视角的追问预演"。两条铁律：**没有真实数据时用诚实的压测表达法，绝不编造线上数据**；**被质疑"这是学习项目"时，展示 trade-off 思考与对生产差距的认知，恰恰是加分项**。

## 1. STAR 模板：四段式叙事结构

```text
S - Situation（业务背景）: 一两句话。不是公司简介, 是"这个系统面临的约束"
T - Task（职责边界）:     说清"我负责什么、不负责什么"——边界感是成熟度信号
A - Action（技术决策）:   重点, 70% 的篇幅。讲"有几个选项、各有什么代价、我选了什么、为什么"
R - Result（量化收益）:   数字。没有线上数据就给压测数据（§3 话术）
```

**三个最常见的结构错误**：

- **流水账**（"我先做了 A，然后做了 B，然后 C……"）：没有决策只有工序。正确写法是每个技术点都过一遍"选项-取舍-结论"。
- **技术堆砌**（"用了 gRPC、etcd、Kafka、istio……"）：名词轰炸等于自曝"不懂为什么用"。每个组件都要能回答"不用它会怎样"。
- **模糊的我们**（"我们做了……"）：面试官无法区分你的贡献。说"我负责 X 模块，我的方案是……，团队采纳因为……"。

**A 段的黄金句式**：

> "当时有两个方案：X 简单但【代价】；Y 复杂但【收益】。我评估了【约束：延迟预算/团队熟悉度/迭代速度】，选了 X，规避代价的手段是【补丁】。事后看如果【条件】变了我会换 Y。"

## 2. 素材重组：本仓库讲成项目的方法

本仓库是学习仓库，但**素材的技术密度是真实项目级的**——关键是讲法：把"学习了 X"重构为"为了解决 Y 问题，实现了 X 并验证了 Z"。

### 素材一：微服务通信与错误治理（rpc/）

**STAR 范例**：

```text
S: 我在搭建一套 Go 微服务的通信层, 需要覆盖同步调用、流式传输、错误语义三类场景。
T: 我负责服务端与客户端的全部实现——不是调框架, 是把治理语义在框架层落地。
A: 四种通信模式（unary/服务端流/客户端流/双向流）各自验证了适用场景——
   比如"客户端流"对应批量上传、"双向流"对应 IM 长连接。
   错误治理是重点: 错误不是返回 error 就完了, 我用 status.WithDetails
   携带结构化错误信息（错误码/重试建议/trace 关联）,
   让调用方能程序化地区分"可重试的瞬时错误"和"不可重试的参数错误"——
   这是熔断/重试策略的输入, 错误不结构化, 治理就是空中楼阁。
   拦截器做了一元+流式两套（日志与 metadata 透传）,
   TLS 用正规写法（信任池+ServerName 校验）而非 InsecureSkipVerify。
R: 四种模式+7 个客户端场景端到端跑通; deadline 700ms 全链路取消验证了
   超时控制的真实传播（client 到 server 的 context 联动）。
```

**追问预演**：

1. *"为什么 gRPC 不用 HTTP？"* → 二进制协议（同语义体积 1/3~1/5）、强类型契约（proto 即文档即代码）、双向流（HTTP/1.1 做不了）、生态（拦截器/deadline 传播是内建语义，HTTP 要自己造）。反问自己：内部服务间调用才值得 gRPC，对外 API 仍是 HTTP/JSON 友好。
2. *"WithDetails 和自己定义错误码字段有什么区别？"* → 语义是同一个（结构化错误负载）；WithDetails 的优势是走标准 any 通道、多语言 SDK 可解析、不污染正常响应的 message 字段。讲出"我知道它只是标准化的载体"比背 API 值钱。
3. *"deadline 是怎么传播的？"* → context 截止时间随 RPC metadata 传递，每跳重新计算剩余时间——所以我能在客户端断言"700ms 后服务端一定停了工作"。这是 `notes/golang/10` 的 context 传播在 RPC 层的实例。

### 素材二：可观测性建设（demos/tracing）

```text
S: 微服务化后, 一次请求穿透多个进程, 排障时"不知道该在哪台机器看日志"。
T: 我负责引入 OpenTelemetry 并把 trace 语义跑通到最小可用。
A: 选 OTel 而非 Jaeger 私有 SDK 的原因: 统一模型（一套 SDK 导出任意后端）
   + collector 中间层（尾部采样/批量/换后端不改应用代码）。
   埋点的关键是 span 边界: 每个 RPC/DB 调用一个 span, trace_id 全链路透传。
   采样策略我验证了头部采样的局限——错误请求可能恰好没被采到,
   这让我理解了尾部采样（按结果保留错误/慢样本）存在的理由。
R: 端到端 demo 跑通调用树组装, 能从"哪一段 span 耗时异常"直接定位慢点。
```

**追问预演**：

1. *"span 上报会不会影响业务延迟？"* → 必须异步（攒 batch+后台发），同步上报等于给每个请求加一跳网络——我能讲出这个反讽是因为实现时踩过。
2. *"采样率怎么定？"* → 从"出事时需要几条慢 trace 定位"倒推——头部 1% 保底 + 尾部捞错误。纯头部采样在低流量服务上几乎采不到东西。
3. *"metrics 和 tracing 的分工？"* → metrics 是告警来源（便宜、聚合、持续），tracing 是显微镜（采样、因果链）。漏斗关系不是三选一（`notes/microservice/05`）。

### 素材三：异步解耦与削峰（notes/akafka + system-design/02）

```text
S: 秒杀类瞬时写洪峰（100 万 QPS 量级）远超 DB 容量（单机 MySQL 写 ~2k QPS）。
T: 设计写路径的削峰架构并验证"不超卖"的正确性闭环。
A: 六层漏斗: 静态化→nginx 限流→验证码→Redis 预扣（原子 DECR, <0 回滚）
   →MQ 异步落库→MySQL 条件更新（UPDATE...WHERE n>0）兜底。
   核心认知是"性能靠 Redis, 正确性靠 DB": Redis 挡掉 99.9% 无效写,
   DB 的条件更新是最终裁判（行锁串行化+持久化事务）,
   中间用 at-least-once+消费端幂等填缝（订单唯一索引挡重复消息）。
R: 内存模拟验证: 10 万并发请求、1000 库存, 订单恰好 1000, 0 超卖 0 少卖,
   Redis/DB/订单三方对账一致（experiments/02 可复跑）。
```

**追问预演**：

1. *"Redis 挂了怎么办？"* → 降级纯 DB 条件更新+限流到 2k QPS——慢但正确；这就是"每层都要有失败预案"的意思。
2. *"为什么不用分布式锁防超卖？"* → 锁把并发变串行，吞吐死在锁上；条件更新本质是"乐观的原子 CAS"，DB 行锁只在冲突瞬间持有。锁是手段不是目的（`notes/redis/08`）。
3. *"MQ 消息丢了怎么办？"* → ack 机制+重试+死信；更重要的是消费幂等——at-least-once 下重复不可避免，把去重做在消费端（唯一索引/去重表）。

### 素材四：基础设施组件（engineering/consistenthash）

```text
S: 分片场景（缓存/存储路由）需要"增删节点时数据迁移量最小"的哈希算法。
T: 从零实现一致性哈希并量化验证它的性质。
A: 实现时踩了一个真实的坑: fnv32a 对 "node-0"/"node-1" 这类相似短串极度聚集
   ——5 个节点挤在 1.5% 的环长上, 负载完全不均。
   排查后换成 md5 取前 4 字节（ketama 同款）, 分布恢复均匀。
   这个坑教会我: 一致性哈希的"均匀性"依赖哈希函数的质量, 不是算法本身保证的。
R: 虚拟节点 150/物理节点时, 5→6 节点扩容只迁移 ~17% 的 key（理论值 1/6≈16.7%）,
   与理论吻合（README 有数据锚点表）。
```

**追问预演**：

1. *"为什么需要虚拟节点？"* → 少量物理节点时环上分布天然不均；虚拟节点把"均匀性"从概率事件变成大数定律。顺带引出热点 key 的治理同构（`notes/system-design/08`）。
2. *"和普通 hash 取模比，迁移量差多少？"* → 取模 `hash%N` 在 N 变化时几乎全量重分布（~100%）；一致性哈希只迁移受影响弧段（~1/N）——17% vs 100% 就是选它的全部理由。
3. *"哪里会真的用到？"* → Redis 客户端分片、分库分表路由、负载均衡（ketama 一致性哈希最早就是 memcached 客户端方案）。

## 3. 量化话术库：没有真实数据的诚实表达法

**铁律：绝不编造线上数据。** 面试官一句"这个 QPS 是怎么测的"就能让编造崩盘，且性质是诚信问题。诚实的表达法：

| 场景 | ✗ 危险话术 | ✓ 诚实话术 |
|---|---|---|
| 压测数据 | "系统支撑 10 万 QPS" | "**压测环境下**单机达到 X QPS（4C8G/docker/关闭了 Y），瓶颈在 Z" |
| 优化收益 | "P99 从 500ms 降到 50ms" | "压测中把【具体改动】后，P99 从 X 到 Y——**因为消除了【具体瓶颈】**" |
| 规模表述 | "服务几千万用户" | "我的实验按【千万级 DAU 假设】做了容量推演，推导链是……" |
| 学习项目 | "线上跑了一年" | "这是我的工程训练仓库，但每个组件都有**可复跑的验证实验**和理论对齐的锚点数据" |

**话术的核心心法**：**把"数据"换成"推导过程"**——"压测环境下 X，瓶颈在 Y，如果上生产我会先解决 Z"展示的是工程师的完整性，比一个来路不明的数字可信十倍。**说清楚前提的数据才叫数据**。

## 4. 高频追问应对：包括"这是学习项目"

**Q："这些是学习项目吧？有生产环境经验吗？"**（必考，不要慌）

回答框架——**承认 + 重构 + 反客为主**：

```text
承认（不辩解）: "对, 这是我的工程训练仓库, 我刻意把它做成了可验证的形态。"
重构（学习 ≠ 玩具）: "每个模块我做到了三件事:
    ① 技术决策讲得出取舍——为什么 gRPC 不用 HTTP、为什么条件更新不用分布式锁;
    ② 关键性质可复跑验证——秒杀 10 万并发 0 超卖、一致性哈希迁移量对齐理论值;
    ③ 认知覆盖生产差距——我知道我的内存模拟里缺了什么:
       真实 Redis 的网络往返、DB 的 fsync 延迟分布、MQ 的 rebalance 抖动。"
反客为主: "所以我来贵司最想补的就是'真实流量的分布长什么样'——
        这也是学习仓库给不了我的东西。"
```

**为什么这样答有效**：面试官质疑的本质是"你会不会只有理论"。上述回答直接展示了三样生产工程师的品质：决策意识、验证习惯、对未知的清醒认知。**把质疑变成展示 trade-off 思考的舞台**。

**其他高频追问的应对要点**：

- *"这个方案最大的缺陷是什么？"* —— 每个素材准备一个真实的坑（fnv32a 聚集、头部采样漏错误、时序实验的输出不稳定），真实的坑比完美的方案更可信。
- *"如果重做你会改什么？"* —— 准备具体改进（"我会先补 CI 和 benchmark 再堆功能——现在全仓 0 个 Benchmark 是我最后悔的"），展示迭代意识。
- *"和团队怎么协作的？"* —— 学习仓库没有团队协作，诚实说"单人项目，所以我刻意用 README+自测清单+规格书做自我约束，这培养了我对'文档是协作基础设施'的理解"——把缺陷转成方法论。

## 5. 反问环节清单：10 个有水平的问题

反问是最后一道加分题——问得好说明你懂工程现实，问"加班多吗"等于放弃。

**技术债与质量**：

1. "团队现在最大的技术债是什么？有没有专门的时间（如 20% 工程效率时间）去还？"
2. "线上事故的复盘文化是怎样的—— blameless 还是追责？最近一次事故改出了什么？"
3. "CI/CD 的覆盖情况？从 merge 到生产的平均耗时和回滚时长是多久？"

**架构与演进**：

4. "服务现在的规模（服务数/QPS 量级）？接下来一年架构上最可能的大动作是什么？"
5. "微服务治理用的是 SDK 还是 sidecar 路线？当时为什么这么选？"

**工程文化**：

6. "on-call 轮值是怎样的？新人多久参与 on-call？"
7. "代码 review 的标准严格吗？新人有 mentor 机制吗？"
8. "技术方案的决策流程——谁拍板？一线工程师能发起架构变更吗？"

**个人成长**：

9. "这个岗位前三个月，什么样算'做成功了'？有什么可量化的期望？"
10. "团队里做得最好的工程师，强在哪里？"（既是信号也是学习路径）

**使用策略**：挑 2~3 个真想知道的，结合面试中听到的信息现场追问（"刚才您提到治理用自研框架，那多语言服务怎么接？"）——**反问的最好状态是对话，不是清单**。

## 6. 60 秒项目自我介绍口述脚本

> 以下为模板——【】里按你的真实侧重点替换，语速 220 字/分钟，全长 ~230 字。

"我的主要项目是一套 Go 后端的工程能力体系，核心是**微服务通信和稳定性治理**。

通信层我基于 gRPC 落地了四种流模式，重点做了**结构化错误**——错误信息带错误码和重试建议，让调用方能程序化地区分瞬时错误和参数错误，这是后续重试与熔断策略的输入；拦截器、metadata 透传、TLS 校验都是按生产写法实现的。

稳定性方面我完整实现了**熔断器三态机**——closed 统计错误率、open 快速失败、half-open 探活恢复——以及注册发现和配置热更新，配置用 atomic 快照整体替换，保证并发读者永远看到完整版本。

验证方式上，每个组件都配了**可复跑的实验**：比如秒杀闭环用十万并发模拟验证了零超卖，一致性哈希的迁移量和理论值对齐。

这套东西让我对'每个技术选型的 trade-off'都有第一手的认知——比如我踩过 fnv32a 在一致性哈希上极度聚集的坑，换成 ketama 同款的 md5 才恢复均匀。这也是我想来真实业务环境验证这些认知的原因。"

**节奏要点**：三个技术点（通信/稳定性/验证）各 15 秒，一个真实的坑收尾——**坑是可信度的锚**。
