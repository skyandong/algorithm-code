# nginx 核心架构与配置

> **核心认知：nginx 是"一个 master + N 个 worker"的事件驱动模型。master 只管管理（读配置、绑端口、fork worker、热重载），worker 才干活，一个 worker 用 epoll 跑几万个连接。
> 和 Redis 一样是"单线程 + 事件循环"思想，但 worker 数量 = CPU 核数，吃满多核。一切性能配置都围绕这个模型展开。**

---

## 为什么是 master-worker 模型

```
                    ┌─ worker 1 ── epoll 事件循环 ── 几千连接
master（root 启动） ──┼─ worker 2 ── epoll 事件循环 ── 几千连接
  读配置 / 绑 80/443  ├─ worker 3 ── ...
  fork worker        └─ worker 4 ── ...
  热重载 / 优雅退出
```

| 角色 | 职责 | 权限 |
|------|------|------|
| master | 读配置、绑定特权端口（80/443）、管理 worker、处理 SIGHUP 热重载 | root |
| worker | 事件循环处理连接：解析请求 → 反代/静态 → 回包 | 普通用户（user 指令指定） |

**WHY 这样分：**
- 特权端口 <1024 只有 root 能绑 → master 用 root 绑，worker 降权干活，被攻破也拿不到 root
- worker 挂了 master 立刻拉起新的 → 天然的进程级看护
- 热重载时 master fork 新 worker 用新配置，旧 worker 处理完存量请求再退 → **不停机换配置**（`nginx -s reload`）

对应实验：`experiments/` 起服务后 `ps -ef | grep nginx`，观察 1 master + N worker。

---

## 事件驱动：worker 为什么能扛几万连接

一个 worker ≠ 一个连接一个线程（那是 Apache prefork 的老路）。worker 内部是 epoll 事件循环：

```
worker 事件循环:
  for {
      events = epoll_wait(...)        // 谁就绪处理谁
      for e in events {
          e.handle()                   // 读请求头 / 转发 / 写回包
      }
  }
```

- 连接只是 fd，挂到 epoll 上，不占线程栈内存
- **CPU 密集的操作只有"解析请求头"和"拷贝数据"**，单核就能跑满
- 对应配置 `worker_processes auto;`（= 核数）、`worker_connections 10240;`（单 worker 最大连接数）
- 理论最大并发 = worker_processes × worker_connections（反代场景每个请求占 client + upstream 两个连接槽，纯反代时实际约减半，是粗略近似值）

## 配置文件结构：块状继承

```nginx
# 全局块：worker 进程数、错误日志、pid 路径
worker_processes auto;
error_log logs/error.log warn;

events {
    worker_connections 10240;        # 每个 worker 的最大连接数
    use kqueue;                      # macOS 用 kqueue，Linux 用 epoll（auto 即可）
}

http {
    # http 块：所有七层相关的公共配置
    include       mime.types;
    log_format  main  '$remote_addr - $request_time $upstream_response_time '
                      '$upstream_addr "$request" $status';
    access_log  logs/access.log  main;

    upstream backend {               # 上游（02 篇详讲）
        server 127.0.0.1:8081;
        server 127.0.0.1:8082;
    }

    server {                         # 虚拟主机（一个 IP:Port 一组）
        listen 8080;
        server_name localhost;

        location / {                 # 路由规则，按优先级匹配（见下）
            proxy_pass http://backend;
        }
    }
}
```

**继承规则：由外向内，内层没写就继承外层，写了就覆盖。** `root`、`index`、`proxy_set_header` 都遵循这条。

## location 匹配：优先级是必考点

五种语法，**优先级从高到低**：

| 优先级 | 语法 | 含义 | 示例 |
|--------|------|------|------|
| 1 | `location = /exact` | 精确匹配，命中即停 | `= /login` |
| 2 | `location ^~ /static/` | 前缀匹配，**命中后不再查正则** | `^~ /images/` |
| 3 | `location ~ \.php$` | 正则（区分大小写），按文件顺序取第一个命中 | `~ \.(png\|jpg)$` |
| 3 | `location ~* \.PNG$` | 正则（不区分大小写） | `~* \.(gif)$` |
| 4 | `location /prefix` | 普通前缀匹配，取最长 | `/api/` |

匹配流程：先在**所有前缀匹配里选最长**的记住 → 如果它带 `^~` 或是 `=`，直接用 → 否则按顺序查正则，命中正则就用正则的 → 都没命中才用记住的前缀。

**WHY `^~` 存在**：`/images/xxx.png` 想走静态文件，但会被 `~ \.php$` 之类的正则劫走，`^~` 就是"选完前缀后跳过正则检查"的开关。

对应实验：`experiments/01_location_match.go` 对同一组路径验证优先级。

## 常用核心指令速查

| 指令 | 作用 | 备注 |
|------|------|------|
| `worker_processes auto` | worker 数 = CPU 核数 | 别手写 4，核数变了配置就错了 |
| `worker_connections` | 单 worker 最大连接 | × worker 数 = 总并发上限 |
| `root / path;` | 静态文件根目录 | 拼接 URI；`alias` 是替换 location 部分 |
| `return 200 "text";` | 直接返回，不再往下走 | 实验和健康检查常用 |
| `rewrite ^/old/(.*)$ /new/$1 last;` | 重写 URI | `last` 重新匹配 location，`break` 停止，`redirect` 回 302 |
| `try_files $uri $uri/ /index.html;` | 依序找文件 | 前端 SPA 部署标配：找不到回落 index.html |
| `add_header X-Debug $uri;` | 加响应头 | 调试 location 命中情况的野路子 |

## 日志：排障的生命线

```nginx
log_format main '$remote_addr [$time_local] "$request" $status '
                '$request_time $upstream_response_time $upstream_addr';
```

- `$request_time`：nginx 收到请求到回完包的总耗时
- `$upstream_response_time`：后端处理耗时
- **两者差值大 = 慢在 nginx 层（网络传输/缓冲/限流排队）**，这是排障第一判断依据
- `$upstream_addr` 记录实际打到的后端，配合负载均衡排查 502

对应实验：`experiments/main.go` 运行后看 `conf/logs/access.log`。

## 热重载与平滑升级（必考）

```bash
nginx -t                # 测试配置语法（改完必做）
nginx -s reload         # 热重载：master 收 SIGHUP
```

reload 过程：
1. master 用新配置 fork 一批新 worker
2. 旧 worker 收到信号，**处理完存量连接**再退出（非暴力杀）
3. 全程监听 socket 不关闭 → 不丢请求

对应实验：跑着实验脚本时 `nginx -s reload`，观察请求无一失败。
