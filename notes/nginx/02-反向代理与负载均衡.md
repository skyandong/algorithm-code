# 反向代理与负载均衡

> **核心认知：nginx 反代的本质是"把客户端连接上的请求解析出来，用一条新的连接发给上游"。
> 所以有两条独立的长连接：client↔nginx、nginx↔upstream，两头都要配 keepalive，少一条都会性能腰斩。
> 反代后后端看到的不再是真实客户端 IP/协议，全靠 proxy_set_header 透传。**

---

## 反向代理在干什么

```
client ──HTTP──▶ nginx ──HTTP──▶ upstream(后端)
        ①收到完整请求头      ②新建/复用连接转发
client ◀──HTTP── nginx ◀──HTTP── upstream
        ④原样回给客户端      ③收到响应流式回传
```

- nginx 是**完整代理**：请求头解析完再转发，不是四层透传（四层是 stream 块的事）
- 响应是**流式转发**：后端边吐 nginx 边吐，不落盘（除非开 buffering 且包大）
- 客户端永远不知道后端存在，`proxy_pass` 指向谁客户端说了不算 → 这就是"反向"

## proxy_pass 的 4 种写法（必考坑点）

```nginx
location /api/ {
    # ① 带 URI：替换 location 前缀。/api/user → /user
    proxy_pass http://backend/;

    # ② 不带 URI：原样拼接。/api/user → /api/user
    proxy_pass http://backend;

    # ③ 带变量：精确控制
    proxy_pass http://backend$new_uri;

    # ④ 指向 upstream 名字：② 的行为，且能用负载均衡/keepalive
    proxy_pass http://backend;
}
```

**最高频的坑：①和②差一个斜杠，路径就变了。** 记忆口诀：**带 URI 就"吃掉" location 前缀，不带就原样传**。

## upstream：负载均衡四策略

```nginx
upstream backend {
    least_conn;                          # 策略指令（不写 = 轮询）
    server 127.0.0.1:8081 weight=2 max_fails=3 fail_timeout=10s;
    server 127.0.0.1:8082;
    server 127.0.0.1:8083 backup;        # 备机，全挂才用
    server 127.0.0.1:8084 down;          # 摘除，配合发布
    keepalive 32;                        # 与上游的长连接池！
}
```

| 策略 | 配置 | 适用 |
|------|------|------|
| 轮询（默认） | 不写 | 后端性能相近 |
| 权重 | `weight=2` | 机器配置不均 |
| ip_hash | `ip_hash;` | 会话粘性（同一 IP 固定打同一后端） |
| least_conn | `least_conn;` | 请求耗时不均，把新请求给最闲的 |
| 一致性哈希 | hash 模块 | 缓存命中场景（衔接 engineering/consistenthash） |

- `max_fails=3 fail_timeout=10s`：10 秒内失败 3 次就摘除 10 秒 —— **被动健康检查**
- `ip_hash` 的局限：NAT 后大量用户同一出口 IP 会倾斜；有 session 的场景更该用 Redis 存会话（衔接 notes/redis 08）

对应实验：`experiments/03_loadbalance.go` 打 10 发看轮询分布。

## 透传头：后端的"用户视角"全靠它

反代后后端 `$remote_addr` 是 nginx 的 IP，`$scheme` 是 http。真实信息必须手动带过去：

```nginx
location / {
    proxy_pass http://backend;
    proxy_set_header Host              $host;        # 后端拿到原始域名
    proxy_set_header X-Real-IP         $remote_addr; # 真实客户端 IP
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for; # IP 链路（可伪造，最左不可信）
    proxy_set_header X-Forwarded-Proto $scheme;      # 原始协议：https 场景的关键！
}
```

**X-Forwarded-Proto 是本模块的设计基线（TLS 终止在 nginx，见 04 篇）：**
客户端走 HTTPS，nginx 解密后用 HTTP 转发，后端代码里**零 TLS**；后端想知道"用户原始是 https 吗"，只看这个头。

**X-Forwarded-For 为什么要防伪造**：`$proxy_add_x_forwarded_for` 是"追加"不是"覆盖"，客户端可以自带一个假的 XFF 头，nginx 会追加在假值后面。可信做法：**从右往左数，取第一个可信代理写入的 IP**，或者边缘直接 `proxy_set_header X-Forwarded-For $remote_addr;` 重置。

对应实验：`experiments/02_proxy_headers.go` 对比直连后端 vs 走 nginx 的头部差异。

## keepalive：两头都要开（性能铁律）

```nginx
upstream backend {
    keepalive 32;                 # nginx→上游：连接池 32 条
}
server {
    location / {
        proxy_http_version 1.1;   # 默认 1.0，1.1 才支持长连接
        proxy_set_header Connection "";   # 清掉 close，才能复用
        proxy_pass http://backend;
    }
}
```

- 不开 keepalive：每请求一次 TCP 三次握手 + TIME_WAIT 堆积，QPS 高时端口耗尽
- `Connection ""` 必须清：nginx 默认给上游发 `Connection: close`，不清等于没开
- client→nginx 侧默认 `keepalive_timeout 75s`（03 篇安全清单收紧到 65s），一般不用动

对应实验：`experiments/06_performance.go` 压测对比开关 keepalive 的耗时差。

## 502/504 排障对照表（高频面试）

| 状态码 | 含义 | 常见原因 |
|--------|------|----------|
| 502 Bad Gateway | 上游返回了无效响应 | 后端挂了 / 端口没监听 / 后端回包不合法 |
| 504 Gateway Timeout | 上游超时 | 后端处理慢，超 `proxy_read_timeout`（默认 60s） |
| 503 | 限流触发 | `limit_req`/`limit_conn` 打满（本仓库实验故意用它）；后端全挂是 502（`no live upstreams`） |

排查口诀：**先看 `$upstream_addr` 确认打到谁，再看 `$request_time` 和 `$upstream_response_time` 的差值定位慢在哪一层。**
