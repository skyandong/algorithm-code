# 场景题专题

> **面试场景题的答法套路：先问清约束（流量级、机器数、是否已有组件）→ 给出分层方案（接入层/应用层/存储层）→ 说清关键取舍。以下题目的答案都建立在前 5 篇的原理上，遇到变体不要背答案，推。**

---

## 场景一：前端 SPA + 多个后端服务的统一入口

**题目：一个域名下同时有前端页面、/api 接口、/ws WebSocket，怎么部署？**

```nginx
upstream api_backend { server 127.0.0.1:8081; server 127.0.0.1:8082; keepalive 32; }

server {
    listen 8443 ssl;
    # 静态资源：直接 nginx 出，不碰后端（动静分离）
    location / {
        root /var/www/dist;
        try_files $uri $uri/ /index.html;   # SPA 路由刷新 404 的解法
    }
    # API：反代 + 负载均衡
    location /api/ {
        proxy_pass http://api_backend;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    # WebSocket：升级头必须透传
    location /ws/ {
        proxy_pass http://api_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";    # 这里不能清空！
        proxy_read_timeout 3600s;                 # 长连接别被 60s 默认掐了
    }
}
```

**考点**：`try_files` 回落、WebSocket 的 `Upgrade` 头、动静分离减轻后端压力。注意 `Connection "upgrade"` 是 02 篇"清空 Connection"的唯一例外。

## 场景二：发布不停机（灰度/蓝绿）

**题目：v2 版本上线，怎么让 10% 流量先打到 v2？**

```nginx
upstream backend {
    server 127.0.0.1:8081 weight=9;   # v1
    server 127.0.0.1:8083 weight=1;   # v2 灰度
}
# 按 cookie 灰度（指定测试用户）
map $cookie_gray $pool {
    "beta"  backend_gray;
    default backend_main;
}
```

- 权重 = 数量级灰度；map + cookie = 定向灰度；`server ... down` = 摘流量
- **配合 reload 的零丢包**：新 worker 上线收新流量，旧 worker 处理完存量再退（01 篇）
- 真正的蓝绿是两套 upstream + 切换入口；金丝雀是权重渐进

## 场景三：秒杀入口怎么挡住流量（综合题）

**题目：秒杀开始 QPS 预计 10 万，后端只能扛 1 万，接入层怎么配？**

```
10万 QPS 进入
  │
  ├─ ① nginx limit_req：单 IP 5r/s + burst —— 挡脚本/单人刷（IP 维度拦）
  ├─ ② 静态化：秒杀页静态资源全 CDN/nginx 出，动态只剩下单接口
  ├─ ③ nginx 层排队：limit_req 不加 nodelay → 多余请求排队而不是打死后端
  └─ ④ 后端 Redis 预扣库存（notes/redis 场景题）：1 万 QPS 进来后快速失败
```

答题主线：**限流不是让请求成功，是让后端在能力范围内工作，多余流量尽快、便宜地失败。** nginx 挡的是最贵的（进程、goroutine、数据库连接）。

## 场景四：为什么加了 nginx 就慢了 / 502 变多

**题目：上了 nginx 之后接口偶尔 502，直连后端没问题，怎么查？**

按 05 篇手册推：
1. access log 看 `$upstream_addr` 有没有多值 → 有 = nginx 重试过，后端偶发失败
2. `proxy_next_upstream` 默认对 error/timeout 换一台重试，但**已发送到上游的非幂等请求（POST 等）默认不重试**——nginx 的默认保护；显式配 `non_idempotent` 才会让 POST 也重试 = **幂等炸弹**（重复下单）
3. 修复：默认不配 `non_idempotent`（或 `proxy_next_upstream error timeout;` 显式收窄），要求重试安全的场景才放开；POST 重试需求 → 后端做幂等（幂等键）
4. 高并发偶发 502：查 worker_connections / 文件描述符 / 上游 keepalive 没开导致 TIME_WAIT 堆积

**这题的核心是把"偶现"翻译成"并发边界条件"**：直连测试=单连接，上 nginx=连接复用+重试+并发放大，问题只在并发形态下暴露。

## 场景五：内网多级代理，后端怎么拿到真实 IP

```
client(1.2.3.4) → CDN(104.x) → nginx(10.0.0.1) → backend
XFF 到后端 = "1.2.3.4, 104.x"    （nginx 追加自己的 $remote_addr）
```

- XFF 最左可伪造（客户端自己带假头）；正确读法：**从右往左跳过可信代理，第一个非可信 IP 就是真实的**
- nginx 侧用 `set_real_ip_from` + `real_ip_header X-Forwarded-For` 从 CDN 头里还原真实 IP（realip 模块）
- 自己做边缘时干脆重置：`proxy_set_header X-Forwarded-For $remote_addr;`
