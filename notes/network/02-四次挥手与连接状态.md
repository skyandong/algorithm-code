# 四次挥手与连接状态机

> **核心认知：** TCP 是全双工，两个方向**独立关闭**，所以拆连接要四次。一个方向关完还能继续收——这就是「半关闭」，也是 CLOSE_WAIT 堆积这类事故的语义根源：FIN 只代表对方不发了，不代表你该退出了。

---

## 1. 状态机全景

```
                         ┌──────────┐
                         │  CLOSED  │
                         └────┬─────┘
              被动打开/主动打开  │
              ┌───────────────┴───────────────┐
       ┌──────▼──────┐                  ┌──────▼───────┐
       │  LISTEN     │                  │  SYN_SENT    │
       └──────┬──────┘                  └──────┬───────┘
              │ 收 SYN                          │ 收 SYN+ACK
              │ 发 SYN+ACK                      │ 发 ACK
       ┌──────▼──────┐                  ┌──────▼───────┐
       │  SYN_RCVD   │                  │  ESTABLISHED │◀──┐
       └──────┬──────┘                  └───┬──────┬───┘   │
              │ 收 ACK                      │      │       │ 收/发数据
              └────────────────────────────▶│      │       │
                                             │      │       │
                       主动关闭(发 FIN)       │      │ 被动关闭(收 FIN)
                    ┌────────────────────────┘      └──────────────┐
             ┌──────▼──────┐                              ┌────────▼─────┐
             │ FIN_WAIT_1  │                              │  CLOSE_WAIT  │
             └──┬───────┬──┘                              └──────┬───────┘
        收 ACK │       │ 同时收到对方 FIN                        │ 应用 close()
             ┌──▼────┐│ (同时关闭)                               │
             │FIN_WAIT││                                 ┌───────▼──────┐
             │  _2    │└──────────────┐                  │   LAST_ACK   │
             └──┬─────┘        ┌──────▼──────┐           └──────┬───────┘
      收对方FIN │              │  CLOSING    │                  │ 收 ACK
             ┌──▼─────┐        └──────┬──────┘                  │
             │TIME_WAIT│◀──────────────┘                         │
             └──┬─────┘                                          │
       2MSL 超时│                                                │
             ┌──▼──────────────────────────────────────────────▼──┐
             │                     CLOSED                         │
             └────────────────────────────────────────────────────┘
```

**只有两方都发过 FIN 且都被 ACK，连接才真正消失。** 记住四个「谁的」：

| 状态 | 谁在等 | 等什么 |
|------|-------|--------|
| FIN_WAIT_1 | 主动关闭方 | 自己的 FIN 被确认 |
| FIN_WAIT_2 | 主动关闭方 | 对方也发 FIN（**可能等很久，甚至永远**） |
| CLOSE_WAIT | 被动关闭方 | **自己的应用调 close()** —— 卡在这里 100% 是代码问题 |
| TIME_WAIT | 主动关闭方 | 2MSL 计时到期 |

## 2. 为什么四次而不是三次

因为 FIN 只关一个方向。对方收到 FIN 时，它可能**还有数据没发完**——它先回 ACK（"我知道你不发了"），把剩下的数据发完，再发自己的 FIN。这两步不能合并。

只有在「对方也没有数据要发」时，ACK 和 FIN 才会合并成一包——这就是抓包里看到"三次挥手"的原因，不是协议变了。

**半关闭的价值**：`shutdown(SHUT_WR)` 后仍能收。典型场景是客户端说"我请求发完了"（`CloseWrite`），然后等服务器把响应流式吐完再关。HTTP/1.1 的老式 "Connection: close" 响应就靠这个：服务器读完请求后关自己的写方向，客户端读到 EOF 才知道响应结束。

## 3. TIME_WAIT：为什么必须存在，为什么要 2MSL

两个作用，缺一不可：

1. **保证最后的 ACK 能到达**。主动关闭方发完最后一个 ACK 就进入 TIME_WAIT，如果这个 ACK 丢了，对方会重传 FIN，此时连接还在，能再回一次 ACK。要是直接 CLOSED，对方重传的 FIN 会收到 RST，对方看到的是"连接被异常重置"。
2. **让旧连接的残余报文在网络中死掉**。MSL 是一个报文的最长存活时间，往返 2MSL 后，这个四元组上的旧包一定已过期。否则新连接可能收到上一条连接迟到的数据——序号恰好对得上，就直接把脏数据交给应用。

**TIME_WAIT 只出现在主动关闭方。** 谁先 close 谁背锅，这条决定了很多架构选择：

- 短连接 + 高 QPS 的服务端如果主动关，会攒出海量 TIME_WAIT（每条占一个四元组 60 秒），端口耗尽后连不上上游。
- 解决方向：**让客户端主动关**（HTTP 场景里服务端用 keep-alive 不主动关）、扩大端口范围 `ip_local_port_range`、`tcp_tw_reuse=1`（只对主动发起的连接生效，且需要时间戳开启）。
- `tcp_tw_recycle` 已被删除（Linux 4.12），NAT 环境下它会误杀正常连接——面试问"为什么删"就是答这个。

## 4. CLOSE_WAIT 堆积：最常见的事故形态

现象：`ss -tan state close-wait | wc -l` 持续上涨，进程 fd 数逼近 `ulimit -n`，最终 `too many open files`。

机制：对方已经 FIN（它不再发了），内核把连接置为 CLOSE_WAIT 并**等你 close**。你不 close，这个 fd 就永远占着。所以：

> **CLOSE_WAIT 只增不减 = 应用漏了 Close。** TIME_WAIT 多不一定是故障（正常现象），CLOSE_WAIT 多一定是 bug。

三个典型漏点：

```go
// 1. 错误分支提前 return，defer 没写
resp, err := http.Get(url)
if err != nil { return err }        // resp 为 nil，但下面漏 close
defer resp.Body.Close()

// 2. 只 close 了 Body 外层，没读干 Body
resp, _ := http.Get(url)
defer resp.Body.Close()
// 没 io.Copy(io.Discard, resp.Body)：连接无法复用，且可能挂住

// 3. 自己 Listen 的服务，处理 goroutine panic 后没 close
go func(c net.Conn) {
    defer c.Close()   // 这行漏掉就是 CLOSE_WAIT 制造机
    handle(c)
}(conn)
```

## 5. RST：连接被强拆的所有理由

RST 不是异常，是内核的"立刻终止"手段。触发它的典型场景：

| 场景 | 说明 |
|------|------|
| 连不存在的端口 | 内核直接回 RST，应用侧表现为 `connection refused` |
| `SO_LINGER` 设 0 后 close | close 时直接发 RST，丢弃发送缓冲——**用它可以让关闭"不排队"**，但对方看到的是异常断开 |
| 全连接队列溢出 + `tcp_abort_on_overflow=1` | 回 RST，客户端立刻失败 |
| 收到不属于任何连接的数据 | 回 RST 让对方别发了（TIME_WAIT 的作用就是减少这种误伤） |
| 半关闭后继续往里写 | 对方已 FIN 且应用已关，写数据会招来 RST |

**`Connection reset by peer` 的归因顺序**：先看是不是自己 close 得太早（有未读完的响应），再看对端是不是被重启/OOM 杀掉（对端进程消失，内核替它回 RST），最后才怀疑中间设备。

## 6. 观测命令与判读

```bash
# 各状态连接数分布（最常用）
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c | sort -rn

# 只看某个状态的明细，含队列
ss -tan state time-wait | head
ss -lnt                                  # 监听队列：Recv-Q 未 accept，Send-Q backlog

# TIME_WAIT 的来源：本地端口在左侧说明本机是主动关闭方
ss -tan state time-wait | awk '{print $3}' | cut -d: -f1 | sort | uniq -c | sort -rn | head

# 内核层面的累计计数
netstat -s | grep -E 'segments retransmit|reset|overflow'
```

判读要点：

- **TIME_WAIT 集中在少数几个本地端口** → 这些是服务端主动关的监听端口（短连接服务），要么改 keep-alive，要么接受它。
- **TIME_WAIT 分散在大量临时端口** → 本机作为客户端高频短连接，检查连接池是否真的复用。
- `FIN_WAIT_2` 长期存在 → 对方不 close；可能是对端应用没关，也可能是对端进程崩了但内核还留着（等超时 `tcp_fin_timeout`）。

## 7. 记忆锚点（面试 30 秒版）

> "TCP 全双工，两个方向独立关闭，所以四次：FIN → ACK → FIN → ACK。主动关闭方最后进 TIME_WAIT 等 2MSL，一是保证 ACK 到了（否则对方重传 FIN 没人应），二是让旧连接的残余包在网络里死透，不污染同四元组的新连接。被动关闭方卡在 CLOSE_WAIT 说明应用没 close——那是代码 bug，不是网络问题。"
