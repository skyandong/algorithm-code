# 排查实战：三段定位法

> **核心认知：** 一次 HTTP 请求的耗时可以**无侵入地切开**：DNS 解析、TCP 建连、TLS 握手、首字节、内容传输。先定位到段，再进那一段内部找原因——不要一上来就 `tcpdump` 抓全流量，那是在用最贵的工具做最粗的排除。

---

## 1. 把耗时切成五段

```
发起请求 ──┬─ DNS 解析 ──┬─ TCP 建连 ──┬─ TLS 握手 ──┬─ 首字节(TTFB) ──┬─ 内容传输
           │            │            │            │                │
        time_         time_        time_        time_            time_
        namelookup    connect      appconnect   starttransfer    total
```

`curl` 一行命令就能拿到这五段（`appconnect` 对纯 HTTP 为 0）：

```bash
curl -o /dev/null -sS -w '
dns       : %{time_namelookup}s
connect   : %{time_connect}s
tls       : %{time_appconnect}s
ttfb      : %{time_starttransfer}s
total     : %{time_total}s
http      : %{http_code}  版本 %{http_version}  复用 %{num_connects}
' https://api.example.com/health
```

> `num_connects` 是**本次新建连接数**：0 表示走了连接复用。查"为什么慢"时先看这个，很多时候慢就是因为在反复建连。

各段对应的病因，这张表要能背下来：

| 段耗时高 | 先查 | 典型原因 |
|---------|------|---------|
| dns | `dig`、`/etc/resolv.conf`、`nscd` | DNS 服务器慢、走了 IPv6 先解析失败再回退、`search` 域拼错导致多次查询 |
| connect | `mtr`、`ss -s`、防火墙 | SYN 被丢（防火墙 DROP）、回程路由不通、服务端 accept 队列满 |
| tls | `openssl s_client -connect host:443` | 证书链下载慢（缺中间证书）、OCSP 阻塞、RSA 握手 CPU 打满 |
| ttfb | 服务端链路追踪、后端依赖耗时 | 业务慢、下游依赖慢、连接池耗尽、锁等待、GC 停顿 |
| total − ttfb | `ss -ti` 的 cwnd/retrans | 带宽不足、窗口太小（BDP 不够）、丢包重传 |

**口诀：`connect` 段的问题一定在网络/内核，`ttfb` 段的问题一定在应用。** 这两段之外的部分通常不需要应用开发介入。

---

## 2. 第二段内部：建连失败怎么分

```bash
# 1. 端口通不通（最快的一刀）
nc -zv -w 2 api.example.com 443

# 2. 卡在哪一跳
mtr -rw -c 20 api.example.com

# 3. 是拒绝还是静默丢弃
#    refused  = 对端回 RST：进程没起 / 端口错 / 队列满且开了 abort_on_overflow
#    timeout  = 包被丢：防火墙 DROP / 路由黑洞 / 中间设备
```

服务端视角看是不是**自己的**问题：

```bash
ss -lnt                    # Recv-Q 顶到 Send-Q = 全连接队列满，应用 accept 慢
netstat -s | grep -iE 'overflow|SYNs to LISTEN'
ss -s                      # 各状态连接总数，TIME_WAIT/CLOSE_WAIT 一眼看到
```

`Recv-Q ≈ Send-Q` 且持续增长，直接去查应用为什么 accept 慢（通常是处理逻辑阻塞在 accept 循环里，或单线程）。

## 3. 第四段内部：TTFB 高的归因

TTFB 高但服务端"看起来正常"，按这个顺序查：

1. **是不是每次都新建连接**（`num_connects` > 0 且频繁）→ 连接池配置太小 / body 没读干导致复用失效 / 中间设备掐 keep-alive。
2. **是不是只有部分实例慢**（看监控分实例）→ 单机问题：GC、锁、磁盘、个别下游。
3. **是不是下游依赖慢**（看链路追踪里最深的 span）→ 这类问题在自己代码里查不出来，必须靠 trace。
4. **是不是排队**（连接池等待、线程池满、DB 连接数打满）→ 看 P99 与 QPS 的关系：QPS 涨、P99 涨、CPU 不涨，多半是排队。
5. **CPU 打满**别急着归因"计算密集"：先看是不是 GC（`GOGC`/`GOMEMLIMIT`）、是不是大量小对象分配、是不是锁竞争（`mutex profile`）。

**一个反直觉但高频的结论**：TTFB 抖动 + 平均 QPS 不高时，先看 `GOGC` 与容器内存限制——Go 在接近内存上限时 GC 会变得激进，表现为延迟毛刺而非 OOM。

## 4. 第五段内部：传输慢

```bash
ss -ti dst 10.0.0.1            # 看每条连接：rtt、cwnd、retrans、发送队列
```

判读：

- `cwnd` 长期很小（十几个 MSS 以下）且 `retrans` 在涨 → 丢包导致窗口爬不起来，查链路。
- `rtt` 波动大（`rtt` 与 `rttvar` 同时高）→ 队列堆积（bufferbloat），查是不是缓冲过大或有人跑满带宽。
- `send-q` 持续不为 0 → 对端收得慢（rwnd 限制），是**接收方应用**的问题，不是网络。

吞吐上限的粗算公式（先算再测，能省一半时间）：

```
吞吐 ≈ min(rwnd, cwnd) / RTT
```

100ms RTT、64KB 窗口 → 上限约 5 Mbps。这种链路上加带宽毫无意义，要调窗口（window scale）或换拥塞控制。

## 5. 抓包的时机与方式

**只在网络层析完毕、怀疑"包本身"时才抓**：

```bash
# 只抓握手阶段，别抓业务流量
tcpdump -i any -nn -c 50 'tcp port 443 and (tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0)'

# 看重传与重复 ACK
tcpdump -i any -nn 'tcp port 443' -w /tmp/x.pcap    # 再拖进 Wireshark 看 Expert Info
```

Wireshark 里最该看的三个过滤：`tcp.analysis.retransmission`（重传）、`tcp.analysis.zero_window`（接收方缓冲满）、`tcp.flags.reset == 1`（被 RST）。**这三个基本覆盖了"网络层到底有没有问题"。**

## 6. 速查：症状 → 第一动作

| 症状 | 第一动作 |
|------|---------|
| 偶发 `connection reset by peer` | 查自己是否 close 太早 / 对端是否重启（`ss -s` 里 RST 计数） |
| 大量 TIME_WAIT | 确认谁是主动关闭方；高频短连接改长连接池 |
| 大量 CLOSE_WAIT | 应用漏 close，直接查代码（`ss -tanp` 看是哪个进程） |
| `too many open files` | `ulimit -n` 与 fd 泄漏（`ls /proc/<pid>/fd \| wc -l`） |
| 连接数上不去 | backlog、`somaxconn`、端口范围 `ip_local_port_range` |
| 吞吐只有理论值的零头 | 算 BDP，看窗口是不是瓶颈 |
| 延迟毛刺、平均正常 | 看 P99 分实例、看 GC/队列，别先怀疑网络 |

---

## 7. 记忆锚点（面试 30 秒版）

> "排查先从 curl -w 把一次请求切成 DNS、建连、TLS、TTFB、传输五段，先定位段再进段。建连段的问题看 mtr 和防火墙，refused 是内核拒绝、timeout 是包被丢；TTFB 段一定是应用问题，按连接复用→实例差异→下游依赖→排队→GC 的顺序查；传输段算 BDP，看 ss -ti 的 cwnd 和重传。抓包是最后手段，不是第一步。"
