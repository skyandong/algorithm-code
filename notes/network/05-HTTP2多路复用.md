# HTTP/2：二进制分帧与多路复用

> **核心认知：** HTTP/2 没有改语义（方法、状态码、头字段全一样），改的是**传输层**：把"一条连接上串行排队"换成"一条连接上并行交错的多路帧流"。它解决的是 HTTP 层队头阻塞；TCP 层的队头阻塞它一点没碰——那要等 HTTP/3。

---

## 1. 二进制分帧层

HTTP/1.1 的报文是文本，靠空行和长度界定；HTTP/2 把一切切成**帧**，每帧 9 字节头：

```
┌──────────────┬────────────┬───────────┬──────────┬─────────────────┐
│ Length(24)   │ Type(8)    │ Flags(8)  │ R(1)+   │ Stream ID(31)   │
│ 载荷长度      │ 帧类型      │ 标志位     │ 保留位   │ 属于哪条流       │
└──────────────┴────────────┴───────────┴──────────┴─────────────────┘
```

| 帧类型 | 作用 |
|--------|------|
| HEADERS | 请求/响应的头（可带 CONTINUATION） |
| DATA | body 片段 |
| SETTINGS | 连接级参数协商（`MAX_CONCURRENT_STREAMS`、`INITIAL_WINDOW_SIZE`、头表大小） |
| WINDOW_UPDATE | 流控窗口增量 |
| RST_STREAM | **取消单条流**——1.1 里这是做不到的 |
| PING / GOAWAY | 探活 / 优雅关连接（告知"别再开新流了"） |

**为什么改二进制**：文本解析要处理不定长、空白、大小写，易错且效率低；二进制定长头可以直接跳读。这个改动的真正价值在于**让"交错"成为可能**——文本报文没法在中间切开插别的报文，帧可以。

## 2. 多路复用：一条连接，多个流

```
HTTP/1.1（6 条连接）
conn1 [req A ................ resp A]
conn2 [req B ....... resp B]
conn3 [req C ................... resp C]
        ↑ 每条连接各自握手 + 慢启动，互不干扰但也互不共享

HTTP/2（1 条连接）
conn1 [HDR stream1][HDR stream3][DATA stream1][HDR stream5][DATA stream3][DATA stream5]
        ↑ 帧交错发送，流之间互不阻塞
```

规则：

- 客户端发起的流用**奇数** ID，服务端（推送）用偶数；ID 单调递增，不复用。
- 每个流是独立的请求/响应，有自己的状态机（idle → open → half-closed → closed）。
- 取消一个请求 = 发 `RST_STREAM`，不影响同连接上其他流——这是 1.1 时代做不到的（1.1 取消只能关整条连接）。
- 一条连接通常**每个域名一条**，多域名同 IP 且证书覆盖时可复用（连接合并，connection coalescing）。

**收益的本质**：把"6 条连接各自冷启动"换成"1 条连接始终处于拥塞窗口已爬升的状态"。跨地域高延迟场景收益最大——省掉的是握手和慢启动的 RTT。

---

## 3. 头部压缩：HPACK

HTTP/2 的请求头动辄几百字节（Cookie/UA 尤其大），而 body 往往很小。不压缩头，多路复用省下的就全吐回去了。

HPACK 三招：

1. **静态表**：61 个常见头（`:method: GET`、`:status: 200`、`content-type` 等）编成 1 字节索引。
2. **动态表**：本次连接里出现过的头加入表，后续只发索引号。**连接级共享**，所以复用得越久越省。
3. **哈夫曼编码**：字面量再压一道。

**为什么不用 gzip**——这是个高频追问，答案是安全问题：压缩算法基于"用短码表示高频串"，攻击者可以把自己的输入和敏感数据（如 Cookie）混在一起压缩，通过观察密文长度逐字节猜出敏感内容（CRIME/BREACH）。HPACK 通过**限制动态表内容和索引语义**规避了这类跨域泄漏，同时保持高效。

**HPACK 的副作用**：动态表必须**按序**解码（后面的头引用前面的表项），所以头块之间有轻微串行性。HTTP/3 的 QPACK 用"独立的编码器/解码器流 + 显式确认"把这个残余也去掉了。

## 4. 两级流控

HTTP/2 有两层窗口，都靠 `WINDOW_UPDATE` 增量补充：

| 级别 | 控制什么 | 初始值 |
|------|---------|--------|
| 连接级 | 整个连接上未被消费的字节数 | 65535 |
| 流级 | 单条流未被消费的字节数 | `SETTINGS_INITIAL_WINDOW_SIZE`，默认 65535 |

**为什么要两级**：只有连接级，一个大响应的流会占满连接窗口，把小请求饿死；只有流级，恶意客户端可以开大量流绕过总量限制。

工程含义：下载大文件时如果只调大了流级窗口没调连接级，吞吐仍然卡在连接窗口上——这是 Go 里被问过多次的"HTTP/2 大文件慢"的成因之一。

---

## 5. 它没解决什么

**TCP 层队头阻塞依然存在**：所有流共用一个 TCP 连接，一个包丢了，内核必须等它重传才把后续字节交给 HTTP/2 层——即使那些字节属于别的流且已经到达。

```
TCP 层：[流1的数据][✗丢了][流3的数据][流5的数据]...
                     ↑ 内核缓冲区有空洞，应用层只能等到补齐
```

丢包率低时影响不大（1% 丢包下，一个 100KB 的窗口里被卡住的概率已经不低）；一旦链路质量差（移动网络、跨国），HTTP/2 的多路复用反而会**放大**伤害——1.1 时 6 条连接里丢包只影响其中 1 条，2.0 的全部押在 1 条上。这就是 HTTP/3 的直接动机。

**服务端推送（PUSH_PROMISE）失败了**：服务器猜不准客户端要不要、缓存里有没有，推了就是浪费带宽；Chrome 从 106 版起移除。现在只有 `103 Early Hints` 还在发挥"提前给提示"的作用。

---

## 6. 落地要点

- **明文 h2c 很少用**：浏览器只支持 TLS 上的 h2（ALPN 协商 `h2`），内网 gRPC 才大量用 h2c。
- **连接数骤降的副作用**：1.1 时代一个域名 6 条连接，2.0 变 1 条——**任何单连接上的 head-of-line 都会被放大**，负载均衡也变成"连接级"而非"请求级"（长连接导致流量分布不均，需要 L7 代理按流分派）。
- **Go 侧**：`http.Server` 只要挂了 TLS 就自动支持 h2（ALPN）；客户端 `Transport` 默认 `ForceAttemptHTTP2`。想看协议版本用 `resp.Proto`。

---

## 7. 记忆锚点（面试 30 秒版）

> "HTTP/2 用二进制分帧把一条连接切成多条流交错发送，解决了 1.1 的 HTTP 层队头阻塞，一条连接替代 6 条，省掉握手和慢启动；头用 HPACK 压（静态表 + 连接级动态表 + 哈夫曼），不用 gzip 是因为 BREACH 那类压缩侧信道。代价是流控变两级、以及最关键的——TCP 层队头阻塞还在，丢一个包全部流都等，这正是 HTTP/3 要解决的。"
