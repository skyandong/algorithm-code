# HTTP/3 与 QUIC

> **核心认知：** HTTP/3 = HTTP over QUIC，而 QUIC = **跑在 UDP 上的传输层**（自带可靠传输 + TLS 1.3 + 多路复用）。它不是在 TCP 上打补丁，而是把传输层从内核搬到用户态重写——因为 TCP 已经被中间设备和内核实现"冻结"了，想改协议头只能换协议。

---

## 1. 三层抽象与协议栈

```
HTTP/1.1          HTTP/2            HTTP/3
   │                 │                 │
   └── TCP ──────────┘                 │
       (内核)                          │
                                   QUIC（用户态）
                                       ├── 流多路复用
                                       ├── 可靠传输 + 拥塞控制
                                       ├── TLS 1.3 内建
                                       └── 连接迁移（Connection ID）
                                          └── UDP（内核只做无连接转发）
```

关键判断：**QUIC 不是"可靠 UDP"这么简单**，它把三个原本分层的东西合成一个：传输（TCP 的活）、加密（TLS 的活）、多路复用（HTTP/2 的活）。所以它必须重新实现 TCP 的可靠传输与拥塞控制，也必须重新实现 HTTP/2 的流控。

---

## 2. 三个核心卖点

### 卖点一：彻底消灭跨流队头阻塞

QUIC 的每条流有**独立的字节序与重传**。丢包只阻塞丢包所在的那条流。

```
TCP（HTTP/2 之上）：[流1][流3✗丢][流5][流1]  ← 内核按字节序，后面的都要等
QUIC：             流1 自己的序号空间    → 丢包只影响流1
                   流3 自己的序号空间    → 流3的后续照常交付
                   流5 自己的序号空间
```

这不是"优化"，是架构性差异：TCP 的可靠传输是**连接级整体有序**，QUIC 把它下放到**流级**。

### 卖点二：握手合并，1-RTT 甚至 0-RTT

- TCP + TLS 1.3：TCP 握手 1-RTT + TLS 握手 1-RTT = **2-RTT** 才发首个请求。
- QUIC：传输参数与 TLS 1.3 密钥交换在同一个往返里完成 = **1-RTT**；恢复连接（有 PSK）时 **0-RTT**，第一个包就能带数据。

0-RTT 的代价与 TLS 1.3 完全一样：**可重放**。所以只能用于幂等请求（GET），POST 必须等握手完成——否则攻击者重放一个"下单"包就能重复下单。

### 卖点三：连接迁移

TCP 连接由**四元组**（源 IP/端口 + 目的 IP/端口）标识。手机从 WiFi 切到 4G，源 IP 变了 → TCP 连接必然断，要重连重握手。

QUIC 用**Connection ID** 标识连接，与 IP/端口解耦。路径变了就重新探测路径（换 IP 继续用原连接），只要 Connection ID 对得上，会话状态全保留。

```
手机：WiFi(192.168.1.7) ──┐
                          ├─ 同一个 ConnectionID=0x9f2a → 服务端无缝续上
      4G(10.20.3.44) ─────┘
```

## 3. 为什么必须基于 UDP

这是面试最爱追问的一题。三个理由，从强到弱：

1. **中间设备让 TCP 头不可扩展**。NAT、防火墙、负载均衡、DPI 设备都深度解析 TCP 头，遇到不认识的选项/标志位就直接丢弃或改写。想给 TCP 加个新字段，等于要升级全球中间设备——这就是"协议僵化"（protocol ossification）。
2. **内核实现让迭代周期以年计**。改 Linux 的 TCP 拥塞控制要进内核、要等发行版；QUIC 在用户态，跟着应用发版就能改算法、加特性（这正是 BBR 在 QUIC 里能快速落地的原因）。
3. **UDP 是唯一"没人管"的传输层**。中间设备对 UDP 基本只做转发，不解析载荷，天然给了 QUIC 自由空间。

**换来的代价（必须能说出来）**：

| 代价 | 说明 |
|------|------|
| 被限速/被墙 | 部分网络对 UDP 限流甚至封禁（历史上 QUIC 常被当 P2P 误伤），只能回退 TCP |
| CPU 开销高 | 加解密、拥塞控制在用户态；UDP 缺少 TCP 那样的内核分段卸载优化，小包多时更明显 |
| 可观测性差 | tcpdump 抓到的是加密载荷，中间设备看不到序号/重传信息；排障要依赖 QUIC 自身日志与 qlog |
| 生态 | 需要客户端库、服务端、负载均衡（L4 要能按 Connection ID 亲和）全部支持 |

## 4. HTTP/3 相对 HTTP/2 的其他改动

- **QPACK 替代 HPACK**：动态表不再隐式同步，改用两条单向流分别传输"表更新指令"和"确认"，需要引用未确认表项时用字面量兜底——消除了头部压缩带来的跨流阻塞。
- **流 ID 与优先级**：沿用 HTTP/2 的流语义，优先级机制被简化（Extensible Prioritization）。
- **发现机制**：首次仍走 TCP（HTTP/1.1 或 2），服务端通过响应头 `Alt-Svc: h3=":443"; ma=86400` 告知"我也支持 h3"，客户端下次才切换；`HTTPS` 类型 DNS 记录（SVCB/HTTPS RR）可让客户端首次就直连 h3。

**注意**：HTTP/3 不改语义层。方法、状态码、Header 字段语义全部与 1.1/2 一致——改的只有传输。所以"HTTP/3 有什么新方法"这种问题，答案是"没有"。

---

## 5. 什么时候值得上

| 场景 | 收益 |
|------|------|
| 移动端 / 弱网 / 跨国 | 大。丢包与网络切换是常态，跨流队头阻塞与连接迁移直接命中痛点 |
| 首屏加载 | 中。省 1-RTT，且多资源并发不再受单连接拖累 |
| 内网低延迟短连接 | 小。RTT 本来就低，UDP 的 CPU 代价反而更显眼 |
| 已有成熟 TCP 优化链路（同机房） | 很小，还可能因为 UDP 限速变差 |

落地判断依据是**丢包率和 RTT**，不是"新就好"。

---

## 6. 记忆锚点（面试 30 秒版）

> "HTTP/3 是 HTTP over QUIC。QUIC 跑在 UDP 上，把可靠传输、TLS 1.3、多路复用合并成一层：每条流独立重传所以没有 TCP 层队头阻塞；握手和密钥交换合并成 1-RTT，恢复可 0-RTT；用 Connection ID 而不是四元组标识连接，所以换网不断线。选 UDP 是因为 TCP 头被中间设备和内核实现冻住了，改不动。"

## 实验

`go run ./experiments/ quic` 用最小实现演示 QUIC 的两个关键设计（不需要引入第三方库）：

- **四元组标识 vs Connection ID 标识**：客户端换一个本地端口（模拟 WiFi→4G）后继续发数据

  - 按 Connection ID 查找会话：命中，无缝续上
- 观察"路径变了但会话没变"这一点，正是连接迁移的全部含义
