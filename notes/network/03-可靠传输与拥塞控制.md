# 可靠传输与拥塞控制

> **核心认知：** TCP 靠四件事把不可靠的 IP 变成可靠字节流——**重传**补丢失、**序号**排顺序、**窗口**控节奏、**拥塞控制**探容量。前三个是"我说了算"，最后一个只能靠猜：网络有多少余量，TCP 看不见，只能用丢包/延迟当信号去试。

---

## 1. 重传：超时与快速，两套机制

### 超时重传的 RTO 怎么算

RTO 不能拍脑袋，它来自对 RTT 的在线估计（RFC 6298）：

```
SRTT   = (1 - α) * SRTT + α * RTT          α = 1/8
RTTVAR = (1 - β) * RTTVAR + β * |SRTT - RTT|   β = 1/4
RTO    = SRTT + 4 * RTTVAR
```

两条纪律：

- **Karn 算法**：被重传过的报文，其 ACK 无法区分是哪个副本的（重传歧义），**不参与 RTT 采样**。
- **RTO 指数退避**：每次超时翻倍，Linux 有下限 200ms、上限 120s（`tcp_rto_min/max`）。所以"链路断了"表现为越等越久。

### 快速重传：不等超时

收到 **3 个重复 ACK**（同序号，说明后面有包到了但缺口没补上）就立刻重传缺口，不等 RTO 到期。这是绝大多数丢包的恢复路径——超时重传是最后的兜底。

```
发送 1 2 3 4 5，2 丢了
接收方：1 → ACK 2；3 → ACK 2（重复）；4 → ACK 2（重复）；5 → ACK 2（重复，第3个）
发送方：收到 3 个重复 ACK → 立即重传 2
```

**SACK**（选择性确认）让接收方告诉发送方"我收到了哪些不连续的块"，避免发送方逐个试。没有 SACK 时，一个包丢了，后面全收到，发送方也只能重传一整个窗口——这是老版本 TCP 在长肥管道上慢的根因之一。

### 重传的观测

```bash
ss -ti                          # 看每条连接的：rtt、cwnd、retrans、重传次数
netstat -s | grep -i retrans    # 全局累计重传段数
```

`ss -ti` 里 `retrans:0/3` 表示当前重传计数 0、历史累计 3。**生产上看重传率**：重传段数 / 总发送段数，超过 1% 就该查链路了。

## 2. 流控与拥塞控制：两个窗口，别答混

| | 流量控制（rwnd） | 拥塞控制（cwnd） |
|---|---|---|
| 谁决定 | **接收方**告诉发送方"我还剩多少缓冲" | **发送方**自己推测"网络还能塞多少" |
| 依据 | 接收窗口字段 / 窗口缩放 | 丢包与延迟（或带宽估计） |
| 目的 | 别把接收方撑爆 | 别把网络压垮 |
| 失效表现 | 发送方写阻塞（对端不读） | 重传、吞吐上不去 |

**实际发送窗口 = min(rwnd, cwnd)**，所以这两个问题的表现可以很像，但归因完全不同：一个是**对端应用不读**，一个是**链路有损**。

## 3. 拥塞控制四阶段（经典 Reno 视角）

```
 cwnd
   │                        ╭──── 超时/丢包 ────╮
   │            ssthresh ───╯                   ╰── 回慢启动
   │         ╭──────────────●─────────●
   │        ╱ 拥塞避免(线性)  ╲ 快恢复(线性)
   │       ╱                   ╲
   │      ╱ 慢启动(指数)
   │     ╱
   └────┴────────────────────────────────────────▶ 时间
```

| 阶段 | 规则 | 触发 |
|------|------|------|
| 慢启动 | 每收到一个 ACK，cwnd 翻倍（指数增长） | 连接开始 / 超时后重置 |
| 拥塞避免 | 每 RTT cwnd 加 1 个 MSS（线性增长） | cwnd ≥ ssthresh |
| 快重传 | 3 个重复 ACK 立即重传 | 丢包但后续包在到达 |
| 快恢复 | ssthresh = cwnd/2，cwnd = ssthresh + 3MSS，然后线性 | 快重传之后 |

**超时 vs 快重传的惩罚不同**：超时意味着"网络可能严重拥塞或对端消失"，cwnd 直接回到 1；快重传说明"只是零星丢包"，只砍半。这个区别是面试官爱追问的点。

「慢启动」这个名字是历史包袱——它一点都不慢，是**指数**增长。

## 4. 现代算法：CUBIC 与 BBR

**CUBIC**（Linux 默认）：cwnd 随时间的**三次函数**增长，与 RTT 解耦。Reno 的线性增长在长 RTT 链路上恢复太慢，CUBIC 在高带宽长距离（长肥管道）上快得多，且更稳定。

**BBR**（Google）：彻底换思路——不把丢包当拥塞信号，而是**估计瓶颈带宽和最小 RTT**，把发送速率控制在 `带宽 × 最小RTT` 附近，并在探测周期里主动试探更高带宽。

| | 判据 | 优点 | 代价 |
|---|---|---|---|
| CUBIC | 丢包 = 拥塞 | 部署广、与其他流公平 | 在有缓存的链路上把 buffer 填满（bufferbloat），延迟升高 |
| BBR | 带宽 × 延迟建模 | 高丢包链路吞吐好、排队延迟低 | 与 CUBIC 共存时不公平（抢带宽），小缓冲链路可能表现差 |

面试问"BBR 为什么快"，答案是：**它不把丢包当拥塞**，因此不会因为 0.1% 的随机丢包就把窗口砍半。

## 5. Nagle 与延迟 ACK：40ms 毛刺的经典组合

两个各自合理的优化，凑一起出问题：

- **Nagle 算法**：有小包未确认时，后续小数据先攒着，等 ACK 或攒够一个 MSS 再发——减少小包数量。
- **延迟 ACK**：接收方不立刻回 ACK，等 40ms（Linux 上限约 40ms，通常有数据捎带就立刻回）——减少纯 ACK 包。

组合效果：发送方等 ACK 才发下一小包，接收方等 40ms 才发 ACK → **每轮 40ms 的停顿**。表现是"小请求慢、大请求不慢"，非常反直觉。

解法：`TCP_NODELAY` 关掉 Nagle（Go 里 `net.Dialer` 默认就设了 `TCP_NODELAY`，这是 Go 相对 C 的一个体贴之处，也是 Go 写 RPC 客户端不用操心这个的原因）。

## 6. 带宽时延积：为什么"加带宽不加吞吐"

```
BDP = 带宽 × RTT
    = 100 Mbps × 100 ms = 12.5 MB ≈ 8500 个 1460 字节的段
```

BDP 是"管道里能同时飞多少数据"。若接收窗口或 cwnd 小于 BDP，链路的理论带宽永远用不满——**这就是跨国专线加带宽却不提速的原因**：瓶颈在窗口，不在管道。破解靠 window scale（rwnd 放大）与更好的拥塞控制（cwnd 爬升更快）。

反过来，`min(rwnd, cwnd) < BDP` 时，吞吐 ≈ `窗口 / RTT`。这条公式是排查"吞吐上不去"的第一把尺。

## 7. 记忆锚点（面试 30 秒版）

> "TCP 可靠性靠序号 + 重传：超时重传用 RTO = SRTT + 4×RTTVAR 自适应，3 个重复 ACK 触发快速重传；重传过的包不参与 RTT 采样（Karn）。发送窗口取 min(接收窗口, 拥塞窗口)——前者是接收方怕被撑爆，后者是发送方怕压垮网络。拥塞控制慢启动指数、拥塞避免线性，丢包砍半（快恢复），超时回 1。Nagle 配延迟 ACK 会造 40ms 毛刺，Go 默认开 TCP_NODELAY。"

## 实验

`go run ./experiments/ congestion` 用本地回环观察窗口限制：

- 接收端不读、发送端小缓冲 + 大块写：写调用被**阻塞**——这是 rwnd 耗尽，不是丢包
- 对比接收端持续读的场景：同样的数据量，写不再阻塞

这说明"写阻塞"和"网络丢包"是两种完全不同的现象，排查时别混。
