# 性能优化与生产实践

> **核心认知：ES 的性能问题 90% 可以归结为两类——写入量超出 Segment 刷新能力，或查询时扫描了太多不必要的数据。优化方向是：减少无效 Segment、利用 Filter 缓存、避免深分页、做好冷热分层。**

---

## 写入优化

### Bulk API

单条写入每次都要解析 HTTP 请求、路由文档、写 Translog，开销大。Bulk 把多条操作打包一次提交：

```json
POST /_bulk
{ "index": { "_index": "orders", "_id": "1" } }
{ "user_id": 1, "amount": 100 }
{ "index": { "_index": "orders", "_id": "2" } }
{ "user_id": 2, "amount": 200 }
```

**单批次建议 5~15 MB**，不是越大越好——太大会导致 GC 压力和超时。可以用 bulk 的响应时间自动调整批次大小（响应 < 200ms 增大，> 500ms 减小）。

### 调大 refresh_interval

```json
PUT /orders/_settings
{ "refresh_interval": "30s" }
```

每次 Refresh 会生成一个新 Segment，频繁 Refresh 导致小 Segment 过多，查询时合并开销大。批量导入时可以设为 `-1`（禁用），导完再恢复。

### 临时关闭副本

```json
PUT /orders/_settings
{ "number_of_replicas": 0 }
```

副本写入是同步的，关闭后写入只需写主分片，速度大幅提升。导完数据再恢复副本数。

### 使用自动生成 ID

```json
POST /orders/_doc   // ← 不指定 ID，ES 自动生成
{ "user_id": 1 }
```

指定 ID 时，ES 需要先查这个 ID 是否存在（GET + 可能的版本冲突检查），自动生成跳过这一步。

## 查询优化

### 利用 Filter 缓存

ES 对 Filter Context 的查询结果（Bitset：哪些文档匹配）做 Segment 级别的缓存。

```
第一次查询 { "filter": { "term": { "status": "published" } } }
  → 计算每个 Segment 的 Bitset，存入内存缓存

第二次相同查询
  → 直接读缓存，跳过计算
```

缓存的 key 是 filter 子句的 JSON，所以同样的 filter 条件才能命中缓存。动态 filter（如每次传不同时间戳）无法命中缓存。

### 避免深分页

见 [04-分片与写入流程.md](04-分片与写入流程.md)。用 `search_after + PIT` 替代 `from + size`。

### 避免 Wildcard / Script 查询

```json
// 慢：通配符查询，无法利用倒排索引，需要扫描所有词项
{ "wildcard": { "url": "*example.com*" } }

// 慢：Script 查询，每个文档都要执行脚本
{ "script": { "script": "doc['price'].value > params.min_price" } }
```

能用 `term`/`range`/`prefix` 的就不要用 `wildcard`/`script`。

### 聚合用 doc_values

`doc_values` 是列式存储（类似数据库的列存），专门为排序和聚合优化，默认对 `keyword`/`numeric`/`date` 开启。

不需要聚合/排序的字段关闭 `doc_values` 节省磁盘：

```json
{ "user_id": { "type": "keyword", "doc_values": false } }
```

### 禁用不需要的功能

```json
{
  "mappings": {
    "properties": {
      "content": {
        "type": "text",
        "_source": { "enabled": false },    // 不需要返回原始文档时关闭（节省存储）
        "norms": false,                      // 不需要评分归一化时关闭（节省内存）
        "index": false                       // 只存储不需要搜索的字段
      }
    }
  }
}
```

## 容量规划与架构

### JVM Heap 设置

```
规则：
1. 堆设为机器内存的 50%，剩余给 OS File Cache
2. 单节点堆最大 32 GB（超过 32GB，JVM 指针压缩失效，反而更慢）
3. 每 GB 堆对应约 20 个分片

示例：64 GB 机器 → 堆设为 32 GB，OS Cache 32 GB，最多约 640 个分片
```

**为什么留一半给 OS Cache：**
Lucene 的 Segment 文件通过 OS File Cache 缓存（mmap），热数据 Segment 常驻内存后读操作不需要磁盘 IO，性能极高。

### 冷热分离（Hot-Warm-Cold 架构）

```
Hot 节点：SSD + 大内存，存最近 7 天数据（高频读写）
Warm 节点：HDD，存 7~90 天数据（低频读）
Cold 节点：低配 HDD，存 90 天以上数据（极低频或只备份）
Frozen 节点：数据存对象存储（S3），只在查询时加载
```

配合 **ILM（Index Lifecycle Management）** 自动流转：

```json
// 策略示例
{
  "policy": {
    "phases": {
      "hot":   { "actions": { "rollover": { "max_size": "50gb" } } },
      "warm":  { "min_age": "7d",  "actions": { "shrink": { "number_of_shards": 1 }, "forcemerge": { "max_num_segments": 1 } } },
      "cold":  { "min_age": "30d", "actions": { "freeze": {} } },
      "delete":{ "min_age": "90d", "actions": { "delete": {} } }
    }
  }
}
```

### Index Rollover（索引滚动）

日志类场景不要把所有数据写一个索引，按时间/大小 rollover 成多个索引，配合别名使用：

```
orders-2024-01, orders-2024-02, ... → 别名 orders（指向最新的写索引）
```

好处：单个索引不会无限增长；老索引可以 shrink（减少分片）、forcemerge（合并 Segment 到 1 个）、冷冻（只保留内存索引结构，Segment 换出到磁盘）。

## ES 与 MySQL 的对比与协作

| 维度 | MySQL | Elasticsearch |
|------|-------|---------------|
| 定位 | 事务型，强一致，关系型 | 搜索/分析型，近实时，文档型 |
| 查询能力 | 精确查询、联表、事务 | 全文检索、聚合分析、模糊查询 |
| 一致性 | ACID，强一致 | 近实时，最终一致 |
| 扩展性 | 垂直扩展为主，分库分表复杂 | 天然水平扩展 |
| 适用场景 | 下单、支付、用户信息 | 商品搜索、日志分析、数据报表 |

**典型架构：MySQL 主存储 + Canal 同步 ES 做搜索**

```
业务写入 MySQL（事务保障）
    ↓
Canal 订阅 MySQL Binlog
    ↓
解析变更事件，写入 ES
    ↓
搜索请求查 ES，精确查询走 MySQL
```

延迟：Canal 同步通常在秒级，ES 再 Refresh 1 秒，总延迟 2~3 秒内可接受。
