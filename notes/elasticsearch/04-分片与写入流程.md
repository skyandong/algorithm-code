# 分片与写入流程

> **核心认知：分片数量是 ES 最重要的容量规划决策，创建后不可改（只能 reindex）。写入流程是 NRT（近实时）的本质所在——数据不是写完就能搜索的，中间有 Refresh 和 Flush 两道关卡。**

---

## 分片（Shard）

### 分片的本质

每个分片是一个独立的 Lucene 实例，有完整的倒排索引。一个 ES 索引 = N 个分片，分布在集群的不同节点上。

```
Index: orders (5 个主分片，1 个副本)

Node-1: P0, P2, R1, R3
Node-2: P1, P3, R0, R2
Node-3: P4, R4

P = Primary Shard，R = Replica Shard
同一分片的 P 和 R 不在同一节点（防止单点故障）
```

### 主分片 vs 副本分片

| | Primary Shard | Replica Shard |
|--|--------------|---------------|
| 读写 | 写入必须先写主分片，主分片再同步到副本 | 只读（可承担搜索请求） |
| 数量 | **创建索引时确定，之后不可改** | 可以随时动态调整 |
| 高可用 | 主分片挂了，副本升为主分片 | 主分片压力大时，副本分担搜索流量 |

**为什么主分片数不可改：**

文档路由公式固定：`shard = hash(doc_id) % number_of_primary_shards`

改了分片数，所有文档的路由结果都变了，整个索引需要完全重建。

### 分片数量设计

**太少的问题：**
- 无法水平扩展，单分片数据量大，查询慢
- 单分片超过 50GB 后性能明显下降

**太多的问题：**
- 每个分片是独立 Lucene 实例，占用文件句柄、内存
- 查询时协调节点要合并所有分片结果，分片越多开销越大
- 一个节点分片过多，JVM 堆压力大（每个分片 Segment 数据结构都在堆内）

**经验值：**
- 单分片建议 20~50 GB
- 分片数 ≈ 数据总量 / 30 GB
- 节点堆内存每 GB 对应约 20 个分片（1 GB 堆 → 最多 20 个分片）

## 写入流程（NRT 的来源）

### 完整链路

```
客户端写请求
    ↓
协调节点（接收请求）
    ↓ hash(doc_id) % shards → 找到对应主分片节点
主分片节点
    ↓ 写入 Memory Buffer（内存）
    ↓ 写入 Translog（磁盘，顺序写，类似 WAL）
    ↓ 同步到副本分片（replica）
    ↓ 返回成功（此时数据在 Buffer 里，还不能搜索）
```

### Refresh（缓冲区 → 文件系统缓存）

```
Memory Buffer → [Refresh，默认每 1 秒] → Segment（文件系统缓存 OS Cache）
                                                    ↓
                                            数据此时可被搜索（NRT）
                                            但 Segment 还未 fsync 到磁盘
                                            节点宕机数据丢失依赖 Translog 恢复
```

**这就是"近实时"（NRT）的来源：写入后最多 1 秒才可搜索，不是实时。**

### Flush（文件系统缓存 → 磁盘）

```
触发条件：Translog 大小超过 512MB 或 30 分钟未 Flush

Flush 过程：
  1. 执行一次 Refresh（Buffer → Segment）
  2. 将所有 Segment fsync 到磁盘
  3. 清空 Translog，生成新的 Translog
```

### Translog 的作用

类似 MySQL 的 Redo Log，节点宕机时用于数据恢复：

```
宕机场景：
  - Segment 未 Flush 到磁盘 → 依赖 Translog 重放写操作
  - Translog 未落盘 → 数据丢失

translog.durability 参数：
  - request（默认）：每次写请求都 fsync Translog，最安全，性能较差
  - async：按 sync_interval（默认 5s）异步刷盘，性能好，但宕机可能丢 5 秒数据
```

### 关键参数

| 参数 | 默认值 | 作用 |
|------|--------|------|
| `refresh_interval` | `1s` | 调大（如 `30s`）可减少 Segment 生成，提高写入吞吐 |
| `translog.durability` | `request` | `async` 可提高写入性能，接受少量数据丢失 |
| `translog.sync_interval` | `5s` | `async` 模式下的刷盘间隔 |
| `number_of_replicas` | `1` | 批量写入时临时设为 `0`，写完再恢复，显著提升写速度 |

## 查询流程（分散-收集）

```
客户端搜索请求
    ↓
协调节点
    ↓ 广播到所有相关分片（或其副本）
各分片并行搜索
    ↓ 每个分片返回 top-N 的 doc_id + _score（不含完整文档）
协调节点
    ↓ 合并所有分片结果，全局排序取 top-N
    ↓ 用 doc_id 回各分片拿完整文档（MGET）
    ↓ 返回客户端
```

**这就是深分页为什么代价高：**

`from=9990, size=10`：每个分片返回 10000 条，协调节点合并 N×10000 条，排序后取 10 条。分片越多，内存压力越大。（`from + size` 不能超过默认的 `index.max_result_window=10000`，否则直接报 "Result window is too large"，要翻更深的页需先调大该参数）

## 深分页问题

| 方案 | 原理 | 适用场景 | 限制 |
|------|------|---------|------|
| `from + size` | 每个分片取 from+size 条，协调节点合并 | 页数少（< 1000 页） | 深分页内存爆炸，默认 max 10000 |
| `search_after` | 基于上一页最后一条记录的排序值继续查，无需跳页 | 实时翻页（瀑布流、cursor 翻页） | 不能跳页，只能顺序翻 |
| `Scroll API` | 生成快照，保存查询上下文，每次取一批 | 全量数据导出 | 快照不实时，不适合用户翻页；scroll 上下文占 JVM 内存 |
| `PIT + search_after` | Point In Time，7.10+ 推荐；保存查询时刻的索引快照，配合 search_after 翻页 | 实时翻页的最优方案 | 需要 7.10+ |

**search_after 示例：**

```json
// 第一页
{
  "size": 10,
  "sort": [{ "created_at": "desc" }, { "_id": "asc" }],
  "query": { "match_all": {} }
}
// 返回最后一条: created_at=1700000000, _id="abc"

// 第二页（传入上一页最后一条的排序值）
{
  "size": 10,
  "sort": [{ "created_at": "desc" }, { "_id": "asc" }],
  "search_after": [1700000000, "abc"],
  "query": { "match_all": {} }
}
```

排序字段必须包含唯一值（如 `_id`）作为 tiebreaker，否则数据可能漏或重。
