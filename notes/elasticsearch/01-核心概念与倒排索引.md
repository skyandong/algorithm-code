# 核心概念与倒排索引

> **核心认知：ES 的一切设计都源于一个出发点——全文检索要在海量文本中快速找到包含某个词的所有文档。**
>
> 传统数据库是"文档 → 词"的正排索引，只能逐行扫描；ES 反过来建"词 → 文档"的倒排索引，查询时直接定位，不需要扫描。
> - **倒排索引**：词频查询从 O(N) 降到 O(log N)
> - **FST 压缩 Term Index**：词典可以全部常驻内存，定位词项不需要磁盘 IO
> - **分片**：把一个大索引拆成多个 Lucene 实例，天然水平扩展
> - **Near Real-Time（NRT）**：写入先进内存 Buffer，1 秒 Refresh 一次，不追求实时但也不慢
>
> 理解这条线，ES 的 Mapping/Analyzer/Shard 设计都能推导出来。

## 核心概念速览

| 概念 | 对应 MySQL | 说明 |
|------|-----------|------|
| Index（索引） | Table | 同类文档的集合 |
| Document（文档） | Row | 一条 JSON 数据 |
| Mapping | 表结构 | 定义字段类型、分词器等 |
| Shard（分片） | 分表 | 索引的水平拆分，每个分片是一个独立的 Lucene 实例 |
| Replica（副本） | 从库 | 分片的拷贝，提供高可用和读扩展 |
| Segment | 数据文件 | 分片内部不可变的存储单元，查询需合并多个 Segment 结果 |
| Node（节点） | 数据库实例 | 集群中的一台机器 |
| Cluster（集群） | 集群 | 多个节点组成，Master 负责元数据，Data 负责数据 |

> Type 字段已废弃：7.x 默认 `_doc`，8.x 彻底移除。

## 倒排索引

### 正排 vs 倒排

```
正排索引（MySQL 全表扫描）：
  文档1: "I love Elasticsearch"
  文档2: "I love Kafka"
  查询 "Elasticsearch"：遍历所有文档，检查是否包含 → O(N)

倒排索引（ES）：
  love          → [doc1, doc2]
  Elasticsearch → [doc1]
  Kafka         → [doc2]
  查询 "Elasticsearch"：直接查词典，O(log N) 定位，读 Posting List → O(1) 级别
```

### 三件套结构

```
Term Index（FST，常驻内存）
   ↓ 定位到前缀，找到 Term Dictionary 中的位置
Term Dictionary（磁盘，有序）
   ↓ 二分查找目标词项，找到 Posting List 的起始位置
Posting List（磁盘）
   → [doc_id=1, tf=2, pos=[3,7]], [doc_id=5, tf=1, pos=[2]], ...
```

| 组件 | 存储位置 | 作用 |
|------|---------|------|
| Term Index | 内存（FST 压缩，很小） | 词典的索引，快速定位 Term Dictionary 中的位置 |
| Term Dictionary | 磁盘（有序） | 所有词项的有序列表，支持二分查找 |
| Posting List | 磁盘 | 词项出现的文档 ID、词频、位置信息 |

**为什么 FST 能放内存：**

FST（Finite State Transducer）是一种有向无环图，对有序字符串做前缀/后缀共享压缩。
百万词项的 Term Dictionary 可能有几百 MB，FST 压缩后只需几十 MB，全量常驻内存。

```
词典：[and, apple, application, apply]
FST：a-p-p → 分叉 → l-e → output: offset_of_apple
                    ↓
                    i-c-a-t-i-o-n → output: offset_of_application
                    ↓
                    y → output: offset_of_apply
共享了 "app" 前缀，大幅压缩空间。
```

### Posting List 的压缩（Frame Of Reference）

Posting List 存储的是文档 ID 列表，原始数据可能是 `[1, 3, 5, 100, 200]`。

ES 用**增量编码**：存差值 `[1, 2, 2, 95, 100]`，数值更小，用变长编码（VInt）后占用字节更少。

再按 128 个 ID 为一块，对每块用最小公共位数压缩（Frame Of Reference），大幅减少磁盘空间。

## Segment 与不可变性

**Segment 是 Lucene 的基本存储单元，一旦写入就不可修改。**

| 操作 | 实现方式 |
|------|---------|
| 新增文档 | 写入新 Segment |
| 删除文档 | 用 `.liv`（live docs）位图标记存活文档，查询时过滤已删文档，不真正删除（Lucene 8.0 / ES 7.x 起取代旧版 `.del` 文件） |
| 更新文档 | 先标记旧 Segment 中的旧版本为删除，再写入新 Segment |

**不可变的好处：**
- 并发读无需加锁，多线程安全读
- 可以直接 OS 文件缓存，无需担心脏读

**不可变的代价：**
- 删除/更新不能原地修改，删除标记会堆积
- 随时间推移 Segment 越来越多，每次查询需要合并多个 Segment 结果

**Segment 合并（Merge）：**
后台定期将多个小 Segment 合并成大 Segment，同时真正清除已标记删除的文档，释放空间。

## 节点角色

| 角色 | 职责 |
|------|------|
| Master 节点 | 管理集群元数据（索引增删、分片分配）；不负责数据读写；轻量，需要高可用 |
| Data 节点 | 存储数据，执行 CRUD 和搜索；重 CPU/内存/磁盘 |
| Coordinating 节点 | 接收请求，分发到对应分片，汇总结果；每个节点默认都有此能力 |
| Ingest 节点 | 写入前的数据预处理（Pipeline）|

生产集群一般专门配置 3 个 Master-eligible 节点（其中一个是 Active Master），防止脑裂。
