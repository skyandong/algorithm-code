# 指标体系与数据模型：为什么 Prometheus 只存数字

> **核心认知：** 指标系统是**在采集端就完成聚合**的系统——你的服务进程里只维护几百个 `float64` 计数器，Prometheus 来问一句"现在多少"，你回一串文本。**没有事件、没有明细、没有单条请求**，这是它便宜到可以常开的根本原因，也是它"能报警但说不出为什么"的根本原因（答案在 05 篇的漏斗里：明细归 logging 和 tracing 管）。理解这一点，下面所有设计选择（为什么只有四种类型、为什么怕高基数、为什么 pull 而不是 push）都能顺着推出来。

前置知识：[05-可观测性](05-可观测性.md)（三支柱漏斗）、`notes/golang/07`（原子操作——埋点就是原子加）。

## 1. 时序数据模型：一个四元组

一条样本（sample）就是四元组：

```text
指标名 + 标签集 + 时间戳 + 数值
http_requests_total{method="POST",route="/pay",status="500"}  1752123456789  3521
```

**指标名**回答"量的什么"，**标签集**回答"哪一类"，两者合起来唯一确定一条**时间序列（time series）**。

**WHY 标签而不是"名字里拼维度"**：`http_requests_post_pay_500_total` 这种把维度塞进名字的做法，查询端只能靠正则去拆——**不可聚合、不可下钻**。标签是结构化的维度，于是 `sum by (route)` 一句话就能聚合出每个路由的量，而这正是排查时最常问的。

**时间戳的归属**：Prometheus 是 pull 模型，**时间戳由服务端在抓取时打**，不是应用上报时打。这个细节决定了为什么它容忍不了 Pushgateway 乱用（见 08 篇）——上报端带时间戳会破坏"同一时刻的全局快照"语义。

**series 是存储与成本的基本单位**：一条 series 在内存里就是一个常驻对象 + 一串压缩后的样本点。**指标系统的所有成本问题，本质都是 series 数量问题**，不是样本点数量问题。

## 2. 四类指标与选型

只有四种，不是偷懒，是够用了——**任何你想监控的东西都能归到这四类的某一类**：

| 类型 | 语义 | 单调 | 典型 | 反例（误用） |
|---|---|---|---|---|
| **Counter** | 累计量，只增（重启归零） | 是 | 请求总数、错误总数、字节数 | 用 Counter 记"当前在线数"（那是 Gauge） |
| **Gauge** | 瞬时值，可增可减 | 否 | 内存占用、队列深度、连接池使用率、goroutine 数 | 用 Gauge 记 QPS（丢失率，见下） |
| **Histogram** | 分桶计数 + 总和 | 是（各桶） | 请求延迟分布、响应体大小 | 分桶边界拍脑袋设成线性 |
| **Summary** | 客户端算好的分位数 | 是 | 同上（但**不能聚合**） | 多实例场景用 Summary 算全局 P99 |

**Counter 的"只增"是刻意的**：单看 `http_requests_total = 3521` 毫无意义，**有意义的是它在一段时间内的增量**——这正是 `rate()` 做的事。Counter 归零（进程重启）由 `rate()` 自动处理（见 09 篇），所以你永远不要自己维护"每秒请求数"这个 Gauge。

**WHY 不用 Gauge 记 QPS**：Gauge 是瞬时采样，抓取间隔之间的抖动全丢了；Counter 的增量是**区间内的真实总量**，除以区间长度才是准确速率。**记速率用 Counter + rate，记余量用 Gauge**——这是埋点的第一条纪律。

**Histogram 的真实长相**（三个 series 家族，不是一个）：

```text
http_request_duration_seconds_bucket{le="0.1"}   240   # 累计: <=0.1s 的有 240 个
http_request_duration_seconds_bucket{le="0.5"}   980
http_request_duration_seconds_bucket{le="+Inf"} 1000   # 必须有, 等于总数
http_request_duration_seconds_sum                183.4 # 总和, 用来算平均值
http_request_duration_seconds_count              1000  # 总数
```

注意 `le` 桶是**累计**的（后面的桶包含前面的），且 `+Inf` 桶 == `count`。这个"累计"约定是 `histogram_quantile` 能工作的前提。

## 3. 分位数：Histogram 与 Summary 的分水岭

**这是面试区分度最高的一题。**

| | Histogram | Summary |
|---|---|---|
| 算分位数的位置 | **服务端查询时**（PromQL） | **客户端进程内**（上报前） |
| 桶/分位数配置 | 桶边界采集前定死 | 分位数采集前定死（如 0.5/0.9/0.99） |
| 跨实例聚合 | **可以**（各实例桶相加再算） | **不行**（分位数不可加） |
| 精度 | 受桶宽限制，有误差 | 客户端精确，但有滑动窗口误差 |
| 成本 | 桶数 × series | 分位数个数 × series（通常更省） |

**WHY 分位数不可加**：两个实例的 P99 都是 100ms，**整体的 P99 不是 100ms**——整体分布是两个分布的并集，分位数只能在整体分布上重新算。这是统计学常识，也是 Summary 的死穴。而 Histogram 的**桶是可加的**（A 实例 <=0.1s 有 240 个 + B 实例 <=0.1s 有 300 个 = 整体 540 个），桶加完之后在服务端重新算分位数就对了。

**所以默认选 Histogram**，只有两种情况用 Summary：①单机/单实例场景，不需要聚合；②你对分位数精度要求极高且桶边界无法预判。

**`histogram_quantile` 的线性插值**（手算 P99 是经典 killer 题）：

```text
桶: le=0.1→240,  le=0.5→980,  le=1.0→1000,  总数=1000
求 P99 → 第 990 个样本落在哪个桶？
  累计: 240 < 990 <= 980? 否;  980 < 990 <= 1000 → 落在 (0.5, 1.0] 桶
  桶内排名: 990 - 980 = 10;   桶内样本数: 1000 - 980 = 20
  线性插值: 0.5 + (10/20) × (1.0 - 0.5) = 0.75s
```

注意这是**假设桶内均匀分布**的近似——**桶越粗，误差越大**。所以桶边界要贴着你的 SLO 设（SLO 是 200ms 就在 0.1/0.2/0.3 附近加密），而不是 0.1/0.2/.../10 均匀铺开。实验 `08_histogram` 里手写了这个算法并演示了粗桶造成的误差。

## 4. 基数：指标的头号杀手

**基数 = series 总数**。它的增长是**乘法**：

```text
series 数 = 指标种类 × 各标签取值数的乘积 × 实例数

http_requests_total{method, route, status, user_id}
  method 5 × route 200 × status 10 × user_id 100万  × 实例 100  → 直接爆炸
```

**为什么爆炸是灾难性的**：一条 series 在 Prometheus 内存里约 3KB（head block 里的索引 + 样本缓冲）。1000 万 series ≈ 30GB 内存，查询时倒排索引遍历也全废。**高基数不是"慢一点"，是打挂整个监控系统**。

**高基数的典型来源**（埋点时看见就绕开）：
- **用户 ID / 订单号 / 请求 ID** —— 绝对禁忌，这不是维度这是明细，明细归 logging 管
- **URL 路径未归一化** —— `/user/123` 和 `/user/456` 变成两条 series；必须写成 `/user/{id}`
- **错误码无收敛** —— 下游返回任意 message，直接塞进 label
- **客户端 IP / UA** —— 同上

**唯一的例外**：错误详情这种"高基数但有排障价值"的信息，**用 exemplar 挂在样本上（trace_id），不要做成 label**——这是指标联动链路的正道（见 09、11 篇）。

**治理手段**：`metric_relabel_configs` 在抓取时丢弃标签；客户端侧限制 label 值域（枚举而非自由文本）；给 series 总数设告警（`prometheus_tsdb_head_series`）。

## 5. 命名规范

约定大于配置，这套命名让陌生人也能读懂你的面板：

```text
① 格式:  <namespace>_<subject>_<suffix>_<unit>
   http_request_duration_seconds / redis_connected_clients / process_resident_memory_bytes

② 单位必须是基本单位: 秒(不是毫秒)、字节(不是 MB)、比率用 0~1(不是百分比)
   → 否则 Grafana 面板和 PromQL 里到处是乘除换算, 迟早算错

③ Counter 必须以 _total 结尾; 单位是秒的以 _seconds 结尾
   → 这不是洁癖: Prometheus 的某些函数(如 rate)会据此做单位推断与校验

④ 不要用保留字: rate / sum / quantile / le / job / instance
```

**`job` 和 `instance` 是 Prometheus 自动加的**：`job` = 抓取配置里的任务名（如 `pay-service`），`instance` = 目标地址（`10.0.0.1:8080`）。**这两个标签你不用自己埋，也不该覆盖**——它们是服务发现和聚合下钻的基础维度。

## 6. 暴露格式：一行文本就够了

Prometheus 抓一次 `/metrics` 拿到的就是纯文本（text exposition format），没有 protobuf、没有二进制：

```text
# HELP http_requests_total 请求总数
# TYPE http_requests_total counter
http_requests_total{method="POST",route="/pay",status="200"} 3481
http_requests_total{method="POST",route="/pay",status="500"} 40
# HELP http_request_duration_seconds 请求延迟
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.1"} 240
http_request_duration_seconds_bucket{le="+Inf"} 1000
http_request_duration_seconds_sum 183.4
http_request_duration_seconds_count 1000
# HELP goroutines 当前 goroutine 数
# TYPE goroutines gauge
goroutines 57
```

**WHY 纯文本**：curl 就能调试（排障时这是救命的）、gzip 后体积很小、无版本兼容地狱、任何语言都能生成。**监控系统里最正确的取舍之一就是"文本协议 + 拉模型"带来的极端可调试性**。

三条硬约束：①同一指标的 `# TYPE` 只能出现一次；②label 顺序不影响 identity 但输出要稳定（否则 diff 噪音）；③`+Inf` 桶必须有。

## 7. 面试高频

**Q1：四类指标的区别？什么场景用哪个？**
Counter 累计只增（QPS 用 rate 算）、Gauge 瞬时可增可减（余量类）、Histogram 分桶（延迟分布，可聚合）、Summary 客户端算分位（不可聚合）。记速率一律 Counter+rate，记余量一律 Gauge。

**Q2：Histogram 和 Summary 怎么选？为什么默认 Histogram？**
因为**分位数不可加，桶可加**。多实例场景下 Summary 的各实例分位数无法合成全局分位数；Histogram 各实例的桶直接相加，服务端再 `histogram_quantile` 重新算，才是正确的全局分位数。

**Q3：手算 P99（给桶数据）？**
找第 99 百分位样本落在哪个桶（累计计数首次 >= 目标排名），在桶内线性插值：`桶下界 + (桶内排名/桶内样本数) × 桶宽`。桶越粗误差越大，所以桶边界要贴 SLO 设。

**Q4：什么是高基数？危害和规避？**
series 数 = 各标签取值数的乘积，用户 ID/URL 路径/错误 message 这种高维值进 label 会让 series 爆炸（千万级 series ≈ 数十 GB 内存 + 查询全废）。规避：路径归一化成 `/user/{id}`、label 值域收敛为枚举、抓取时 `metric_relabel_configs` 丢弃、明细信息走 exemplar 挂 trace_id 而不是做成 label。

**Q5：为什么不用 Gauge 记 QPS？**
Gauge 是瞬时采样，抓取间隔内的抖动全丢；Counter 的增量是区间内真实总量，`rate()` 除以区间长度才是准确速率，且能自动处理进程重启导致的归零。

**Q6：指标命名的约定？**
`<namespace>_<subject>_<suffix>_<unit>`，单位用基本单位（秒/字节/0~1 比率），Counter 以 `_total` 结尾。`job`/`instance` 由 Prometheus 自动注入，不要自己埋。

**Q7：为什么 exposition 用纯文本？**
curl 可直调（排障救命）、gzip 后极小、无版本兼容问题、跨语言零成本。可调试性优先于那点序列化效率。
