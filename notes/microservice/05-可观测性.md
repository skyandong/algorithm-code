# 可观测性：metrics、logging、tracing 三支柱

> **核心认知：** 单体时代 debug 靠断点和单机日志；微服务时代一次请求穿透 10 个进程，**你根本不知道该在哪台机器上打断点**——这就是"看不见"问题，也是可观测性存在的理由。三支柱分工记住一句话：**metrics 告诉你"哪里不对劲"（聚合数字，便宜、持续、告警的来源），tracing 告诉你"哪一段不对劲"（跨服务因果链，采样、排障的显微镜），logging 告诉你"为什么不对劲"（离散事件明细，按需检索）**。三者是漏斗关系：告警（metrics）→ 定位（tracing）→ 取证（logging），而不是三选一。串联三者的钥匙是 **trace_id 全链路透传**——一次请求一个 ID，从网关带到最深的 DB 调用，日志和 span 靠它聚拢——`demos/tracing` 里有现成的 OpenTelemetry 端到端 demo 可以跑。

前置知识：SRE 黄金指标与告警哲学、`demos/tracing`（OpenTelemetry 现成实验）、`notes/golang/10`（context 传递）。

## 1. 三支柱的分工与漏斗关系

| | metrics | logging | tracing |
|---|---|---|---|
| 数据形态 | 时序数字（QPS=3521） | 离散事件行 | span 树（带因果的区间） |
| 回答 | 系统整体健康吗？哪里在报警？ | 那一刻发生了什么？ | 请求慢在哪一段？链路怎么走的？ |
| 成本 | **极低**（聚合后只有数字） | 高（全量存文本） | 中高（采样+关联存储） |
| 查询模式 | 时间窗口聚合 | 关键字检索 | trace_id 聚拢 |
| 典型栈 | Prometheus + Grafana | ELK/Loki | Jaeger/Tempo |

**漏斗关系**（这是把三支柱讲出层次的钥匙）：

```text
告警: metrics 的 P99 延迟超阈值 → "支付服务慢了"     （知道哪里, 不知道为什么）
定位: 取当时几个慢 trace → "db.query span 占了 900ms"（知道哪一段）
取证: 用 trace_id 检索日志 → "锁等待 timeout"        （知道为什么）
```

**WHY 不全量上最贵的**：logging 全量+tracing 全采的成本是天文数字（大厂一天几十 TB 日志）。三支柱的成本设计天然就是漏斗——便宜的常开，贵的采样，**按需逐层放大分辨率**。

## 2. 四个黄金指标

Google SRE 的四个信号，一切服务监控的起点（问"这个服务健康吗"先看这四个）：

| 指标 | 定义 | 例子 | 回答 |
|---|---|---|---|
| **延迟** | 处理耗时分布（**必须看分位数**） | P50=12ms, P99=850ms | 慢不慢？对谁慢？ |
| **流量** | 请求量 | 3500 QPS | 压力多大？ |
| **错误** | 错误率（5xx/超时/业务错） | 0.7% | 坏没坏？ |
| **饱和度** | 资源占用（CPU/内存/连接池/队列深度） | 连接池 98% | 还能扛多久？ |

**WHY P99 而不是平均值**：均值是"1 个富人和 100 个穷人平均都是中产"的把戏——尾部用户的体验被均值掩盖。P99 慢往往意味着**一种特定请求模式**出了问题（大 key、锁竞争、慢查询），而均值正常。SLO 的标准写法就是分位数目标（"99% 的请求 < 200ms"）。

**饱和度是先行指标**：延迟涨之前饱和度先涨（连接池 90% → 排队开始 → 延迟上升 → 错误）。**告警配在饱和度和错误率上，延迟是结果**——等到 P99 告警，用户已经在受苦了。

**USE 法与 RED 法**（扩展记忆）：资源视角 USE（Utilization/Saturation/Errors——机器、连接池、磁盘）；服务视角 RED（Rate/Errors/Duration——黄金指标的服务版）。一台服务同时挂两组仪表：RED 看服务表现，USE 看资源余量。

## 3. trace 上下文透传：span 组装原理

tracing 的全部魔法就一句话：**每个请求带一个 trace_id，每个处理段生成一个 span_id，两者随 context 全链路透传，最后按 trace_id 聚拢成树**。

```text
网关:     开新 trace (trace_id=T, span_id=S1)        请求头: traceparent: T-S1
  ├─ 调 order-svc: 传 T, 开 span S2（parent=S1）      请求头: traceparent: T-S2
  │    ├─ 调 db:    开 span S3（parent=S2, 记录 SQL+耗时）
  │    └─ 调 redis: 开 span S4（parent=S2, 记录 key+耗时）
  └─ 调 user-svc:   开 span S5（parent=S1）
                    ……所有 span 异步上报 → 后端按 T 组装成树
```

**透传的载体**（进程内 & 跨进程）：

```go
// 进程内: context.Context 携带（notes/golang/10 的 context 就是干这个的）
ctx = trace.ContextWithSpan(ctx, span)   // 每层中间件/函数自然向下传

// 跨进程: 协议头序列化（W3C Trace Context 标准）
// HTTP:  traceparent: 00-{trace-id}-{parent-span-id}-{flags}
// gRPC:  metadata 里的同名字段
```

**span 的最小要素**：trace_id（同请求全部相同）、span_id（每段唯一）、parent_span_id（树形来源）、name（干了什么）、start/end（耗时）、attributes（结构化标注：SQL 语句、HTTP 状态码）——**树形结构来自 parent 指针，聚拢靠 trace_id**，就这么多，没有更多了。

**WHY 异步上报**：span 上报（走网络到 collector）绝不能阻塞业务请求——进程内攒 batch，后台 goroutine 定期发。可观测性组件自己变成延迟来源是莫大的讽刺（`notes/nginx/01` 的 access log 异步写入同理）。

## 4. 采样策略：头部与尾部

全量 trace 贵，采样是必然。两种策略的分水岭在于**"决定采不采的时点"：

**头部采样**（Head-based，入口决定）：

```text
网关按概率（如 1%）决定采这条 trace → 采: 全链路所有 span 都带标记 → 全部上报
                                        不采: 全链路都不采
优: 一致性好（要么全有要么全无）、实现简单、可提前丢弃（省 CPU）
劣: 慢请求/错误请求可能没被采到——你最想看的那条 trace 恰好没采
```

**尾部采样**（Tail-based，出口决定）：

```text
全链路 span 先缓存在 collector → 请求完成后按结果决定:
  慢于 1s 的 / 有错误的 → 全保留;   正常的 → 采 0.1%
优: **错误和慢请求 100% 保留**（排障价值最高的样本）
劣: 要缓存全量 trace 等结束（内存/存储成本）、实现复杂
```

**生产组合拳**：头部采样保底（1% 常规样本）+ 尾部采样捞重点（错误/慢全留）。**采样率和保留策略是成本与排障能力的直接兑换**——先想清楚"出事时我需要多少条慢 trace 才能定位"，再定采样率。

## 5. OpenTelemetry 统一模型

历史上 metrics/tracing/logging 各有标准（Prometheus/Jaeger/OpenTracing...），**OpenTelemetry（OTel）统一了前两者**（logs 正在并入）：一套 SDK、一套语义约定、一套 collector，导出到任意后端（Prometheus/Jaeger/Tempo/商业栈）。

```text
应用（OTel SDK 埋点）→ OTel Collector（接收/处理/导出的中间层）→ 任意后端
```

**collector 独立成层的 WHY**：①应用与后端解耦（换 Jaeger 为 Tempo 不改应用代码）；②**尾部采样在 collector 做**（应用只管全量发，采样决策集中）；③批量/重试/加密统一处理。这个"代理层"和 04 篇网关的思路同构——**把横切关注点从应用剥离到基础设施**。

语义约定（semantic conventions）的价值：`http.status_code`、`db.statement` 这些 span 属性名全球统一——跨语言跨公司的 trace 才能被同一套面板理解。

**Go 接入**：`demos/tracing` 是现成的 otel 端到端 demo（HTTP 服务 + client 埋点 + 控制台 exporter），跑一遍比读十篇文档直观。

## 6. 面试高频

**Q1：metrics/logging/tracing 的区别和关系？**
metrics 是聚合数字（便宜常开，告警来源）；logging 是离散事件（按需检索取证）；tracing 是跨服务因果链（采样，定位慢段）。漏斗关系：告警（metrics）→ 定位（tracing）→ 取证（logging），分辨率逐层放大，成本逐层升高。

**Q2：四个黄金指标？**
延迟（看 P99 分位数不是均值）、流量（QPS）、错误率、饱和度（CPU/连接池/队列深度）。饱和度是先行指标——告警配在饱和度上，延迟是结果，等 P99 告警用户已在受苦。

**Q3：trace_id 怎么全链路透传？**
进程内 context.Context 携带，跨进程走协议头（W3C traceparent：HTTP header/gRPC metadata）。每段处理生成 span（trace_id+span_id+parent_id+耗时+属性），异步上报后按 trace_id 聚拢成树。树形来自 parent 指针。

**Q4：头部采样和尾部采样的区别？**
头部：入口按概率决定，全链路一致、实现简单，但错误/慢请求可能漏采。尾部：等请求结束按结果决定，错误和慢 100% 保留（排障价值最高），但要全量缓存。生产组合：头部 1% 保底 + 尾部捞错误和慢。

**Q5：为什么 P99 而不是平均延迟？**
均值掩盖尾部——P99 慢通常是特定请求模式（大 key/锁/慢查询），均值正常不代表人人正常。SLO 用分位数定义（"99% 请求 <200ms"）。

**Q6：OTel 的架构为什么要有独立 collector？**
①应用与后端解耦（换后端不改代码）；②尾部采样集中在 collector 做（应用全量发）；③批量/重试统一处理。把横切关注点从应用剥离——与网关收敛治理逻辑同构。

**Q7：span 上报为什么必须异步？**
上报走网络，同步发等于给每个请求加一跳网络延迟——可观测组件自己变成延迟来源是讽刺。进程内攒 batch + 后台 goroutine 定期发，和 nginx access log 异步落盘同理。
