# 监控场景题与排障手册：从告警到根因

> **核心认知：** 面试官问监控，很少问"Prometheus 怎么配"，更多问"**线上报警了你怎么查**"。这类题的区分度不在于背了多少指标名，而在于**有没有一套固定的下钻顺序**——有顺序的人 3 分钟定位，没顺序的人对着看板乱点。下面这套 SOP 是通用的：**先确认影响面（是不是真在影响用户）→ 再定性（延迟/错误/饱和哪一类）→ 再分层（依赖链上哪一层）→ 最后才看资源（CPU/内存/GC 是结果不是原因）**。注意最后一步的顺序——**直接跳到 CPU 是新手最典型的错误，因为 CPU 高几乎总是症状**。

前置知识：[05](05-可观测性.md)（四黄金信号）、[09](09-PromQL实战.md)、[10](10-告警与Alertmanager.md)。

## 1. 排障 SOP：四步下钻

```text
① 影响面: 谁在受影响？多少用户？哪个功能？持续多久？
   查询: 错误率、QPS 是否下降（掉了 = 请求打不进来, 更严重）、P99
   ↓
② 定性: 是"慢"还是"错"还是"堵"？
   延迟涨 → 慢;  错误率涨 → 错;  饱和度先涨后延迟涨 → 堵
   ↓
③ 分层: 依赖链上哪一层？（自己的服务 → 下游 RPC → 缓存 → DB → 中间件）
   查询: 各依赖的错误率与延迟, 找第一个异常的下游
   ↓
④ 定位: 到了具体一层, 才看资源（CPU/内存/GC/慢查询/锁）
   工具: metrics 定性 → trace 定段 → 日志取证（05 篇漏斗）
```

**WHY 必须先看影响面**：告警可能是误报（监控系统自己抖动、阈值设错）。**先确认"用户是不是真的在受影响"再动手**，能省掉大量无效排查，也决定了要不要升级事故等级。

**WHY 资源放最后**：CPU 高、内存高、GC 频繁**几乎都是结果**。看到 CPU 90% 就去看火焰图，是"从症状往回猜原因"；而按 SOP 走到第 ③ 步时，你通常已经知道是哪个下游慢了——**那时候 CPU 高是意料之中的，不需要查**。

**变更关联（第 0 步）**：**任何排障开始前，先看最近有没有发版、配置变更、流量突增、定时任务**。生产故障里相当大比例与变更直接相关——这一步的成本是 10 秒，收益极高。

## 2. 场景：CPU 飙到 90%

**问法**："线上 CPU 突然 90%，你怎么查？"

```text
① 先看影响面: QPS 掉了没？错误率涨了没？P99 涨了没？
   → 如果一切正常, 只是 CPU 高: 这是 ticket 不是 page（10 篇: 基于原因不告警）
   → 如果 QPS 掉了: CPU 已经饱和, 请求处理不过来, 紧急

② 定性是什么在吃 CPU:
   用户态高(us) → 业务代码: 死循环、热路径重复编译正则、序列化、加密、JSON 大对象
   内核态高(sy) → 系统调用多: 大量小 I/O、上下文切换、频繁分配导致页错误
   iowait 高    → 磁盘/网络 IO 阻塞, CPU 在等（真凶是 IO 不是 CPU）
   steal 高     → 宿主机超卖（云上独有, 你的代码没问题）

③ 分层: 是不是下游变慢导致的？
   下游慢 → 请求堆积 → 线程/协程数暴涨 → 上下文切换爆炸 → CPU 高
   **这种情况根因在下游, 优化自己的 CPU 毫无用处**

④ 定位（Go 特有）:
   go_goroutines 是否暴涨  → 协程泄漏导致调度开销
   go_gc_duration_seconds  → GC 频繁（分配速率高）
   pprof 抓 30s CPU profile → 看火焰图里最宽的那一帧
```

**标准答案的关键动作**：**先看是不是死循环/重复编译正则这类"计算型"问题，再看是不是请求堆积这类"容量型"问题**——两者的处置完全相反（前者要改代码，后者要扩容或限流）。

**Go 特有的坑**：热路径里**重复编译正则**（Go 的 regexp 是 RE2 引擎，线性时间、免疫回溯型指数爆炸，但 Compile 本身远贵于 Match，每次请求 Compile 就是纯浪费——`demos/pprof-lab` 有实测：Compile 占该调用 75% 耗时）和 `for` 循环里拼接大字符串，是 CPU 打满的两个高频元凶；而 **goroutine 泄漏**（`notes/golang`）则是通过调度开销间接打满 CPU 的。

## 3. 场景：P99 延迟毛刺，P50 正常

**问法**："P99 突然从 200ms 涨到 2s，但 P50 完全正常，什么原因？"

**P50 正常 + P99 异常 = 只有一小部分请求变慢**，这是最强的定性信号。按可能性排序：

| 可能原因 | 特征 | 验证 |
|---|---|---|
| **GC 暂停** | 毛刺周期性、与流量无关 | 把 `go_gc_duration_seconds` 和 P99 画同一块板看是否对齐 |
| **大 key / 慢查询** | 与特定参数相关 | 按路由拆 P99，看是不是集中在某个接口 |
| **缓存击穿** | 命中率同时下跌 | 看缓存命中率曲线是否同步掉 |
| **锁竞争** | 与并发量正相关 | pprof 看 `sync.Mutex` 阻塞时间（block profile） |
| **下游毛刺** | 只有调某个下游的接口慢 | 分别看各下游的 P99 |
| **分页/限流排队** | 队列深度同时涨 | 看饱和度指标（05 篇：饱和度是先行指标） |

**第一步永远是拆分维度**：`histogram_quantile(0.99, sum(rate(..._bucket[5m])) by (le, route))` 按路由拆——**如果集中在一个路由，直接排除全局原因（GC、CPU），问题就在那个路由的业务逻辑或它依赖的下游**。

**第二步是对比 P50/P90/P99 三条线**（11 篇）：三线一起涨 = 系统性问题；只有 P99 涨 = 特定请求模式。

**为什么不能用平均延迟排查**：均值会被大量正常请求稀释，P99 涨 10 倍时均值可能只涨 5%——**用均值看不出这个故障**。

## 4. 场景：内存/goroutine 持续上涨

**问法**："服务内存一直在涨，重启就好，怎么查？"

```text
① 先区分"泄漏"和"缓存增长":
   内存涨但 GC 后能回落 → 正常（缓存还没到上限）
   内存涨且 GC 后不回落, 涨到 OOM → 泄漏

② Go 服务看 goroutine 数（最快的一步）:
   go_goroutines 持续上涨 → 协程泄漏:
     常见原因: channel 没人读（写端阻塞）、context 没取消、HTTP 连接池没关、
               ticker 没 Stop、无限增长的 goroutine 里等着一个永远不来的事件
   验证: pprof 的 goroutine profile 看堆积在哪个函数

③ 堆内存泄漏:
   pprof heap profile 的 inuse_space, 对比两个时间点做 diff
   常见原因: 全局 map 只加不删、slice 引用大数组的一部分（整个数组不释放）、
             缓存没有淘汰策略或上限
```

**为什么 goroutine 泄漏在 Go 里特别常见**：协程太便宜了，随手 `go func()` 就开，而**"随手开的协程没人负责它的退出"**——这就是 `notes/golang` 里"goroutine 裸奔"反模式在监控上的表现。**监控抓手就是 `go_goroutines` 这条线，它持续上涨 = 一定有协程没退出**。

**slice 截取导致的大内存不释放**（Go 经典坑，`notes/golang/01` 讲过）：`bigSlice[:10]` 仍持有整个底层数组，把它存进长期存活的结构 = 泄漏。解法：`append([]T{}, bigSlice[:10]...)` 拷贝一份。

## 5. 场景：消费积压与容量规划

**问法**："Kafka 消费 lag 一直在涨，怎么办？" / "大促前怎么做容量规划？"

**lag 上涨的三类原因与处置**（联动 `notes/akafka`）：

```text
① 生产能力突增（流量涨了） → 扩容消费者 / 提高并发
② 单条消费变慢（下游慢了） → 先修下游, 扩容只是掩盖（消费能力不变, 扩了也会再积压）
③ 消费者频繁 rebalance → 看是不是处理时间超过 max.poll.interval（调大或减批次）
```

**判断是哪种**：看**消费速率**（`rate(消费总数[5m])`）而不是 lag 本身——消费速率没变而生产涨了 = ①；消费速率掉了 = ② 或 ③。

**容量规划三步**（链路 `notes/system-design`）：

```text
① 定 SLO: "99% 请求 < 200ms" —— 先有目标才谈容量
② 压测找单机水位: 单机在不同 QPS 下的 P99 与饱和度曲线, 找"P99 开始陡升"的拐点
   **拐点才是容量上限, 不是 CPU 到 100% 那一点**
③ 留余量: 按峰值 QPS × (1 + 冗余) 反推机器数, 并留 30~50% 应对单机故障
```

**WHY 用拐点而不是资源打满作为上限**：排队论——接近饱和时延迟是**指数上升**的。CPU 70% 时 P99 可能已经翻倍了。**容量规划的本质是"在延迟不可接受之前留够余量"**，这也是饱和度（先行指标）比使用率重要的原因（11 篇 USE）。

## 6. 设计题：从零设计一套监控

**问法**："给一个新业务从零设计监控，你怎么设计？"

按四层答（这就是本模块 07~13 篇的骨架）：

```text
① 采集层: 自己的服务直埋（12 篇: 中间件埋 RED + 运行时指标）
          第三方系统用 Exporter（13 篇: MySQL/Redis/Kafka/node）
          外部可用性用 blackbox 探测（证书/DNS/连通性）
② 存储与查询层: Prometheus 拉 + 本地 TSDB 15 天
                长期/多集群走 remote_write 到 Thanos/VictoriaMetrics（08 篇）
③ 告警层: Prometheus rules（基于症状: 错误率/P99）+ Alertmanager（分组/抑制/静默）
          分级: page 用电话, warning 进群, 每条 page 必须带 runbook（10 篇）
④ 展示层: Grafana, 每个服务一块 RED 看板 + 依赖中间件各自看板, 用变量模板化（11 篇）
⑤ 三支柱打通: metrics 报警 → exemplar 点进 trace → trace_id 查日志（05/12 篇）
```

**必须主动提到的三件事**（不说会显得没做过）：
- **基数控制**：label 值域收敛、路径归一化、监控 `prometheus_tsdb_head_series`
- **告警噪声治理**：基于症状而非原因、加 `for`、定期复盘删告警
- **监控系统自身的高可用**：Prometheus 自己也要被监控（`up`、双活部署），**监控系统的故障不能让整个业务变成瞎子**

## 7. 面试高频

**Q1：线上告警了，你的排查顺序是什么？**
四步：①影响面（是不是真在影响用户、多少用户）——同时也排掉误报；②定性（慢/错/堵）；③分层（依赖链上哪一层，找第一个异常的下游）；④定位（到了具体一层才看 CPU/内存/GC）。**第 0 步是看最近有没有变更**（发版、配置、定时任务、流量突增）。资源放最后是因为它几乎总是结果。

**Q2：CPU 飙高怎么查？**
先区分"计算型"和"容量型"：计算型（死循环、重复编译正则、序列化）要改代码；容量型（下游慢导致请求堆积、协程暴涨、上下文切换爆炸）要扩容或限流，优化自己的 CPU 没用。Go 特有关注 goroutine 数和 GC 暂停，最后用 pprof CPU profile 看火焰图最宽的一帧。还要看 `iowait`/`steal`——真凶可能不是 CPU。

**Q3：P99 涨了但 P50 正常，什么原因？**
说明只有一小部分请求变慢。按可能性排：GC 暂停（周期性，与 P99 曲线对齐）、大 key/慢查询（集中在某个路由）、缓存击穿（命中率同步掉）、锁竞争（与并发正相关）、下游毛刺（只有调该下游的接口慢）。第一步永远是按路由拆 P99——集中在某个路由就排除全局原因。

**Q4：内存一直涨重启就好，怎么查？**
Go 服务先看 `go_goroutines`——持续上涨就是协程泄漏（channel 没人读、context 没取消、ticker 没 Stop）。堆泄漏用 pprof heap profile 两个时间点 diff。经典坑是 slice 截取仍持有整个底层数组，存进长期结构就是泄漏。

**Q5：Kafka lag 一直涨怎么办？**
先判断是"生产能力涨了"还是"消费能力掉了"——看消费速率而不是 lag。生产涨了就扩容消费者；消费速率掉了要先修下游（扩容只是掩盖）；还要排查是不是 rebalance（处理时间超过 max.poll.interval）。

**Q6：怎么做容量规划？**
三步：定 SLO（99% < 200ms）→ 压测找单机 P99 开始陡升的拐点（**不是 CPU 打满那点**，接近饱和时延迟指数上升）→ 按峰值反推机器数并留 30~50% 冗余应对单机故障。

**Q7：从零给业务设计监控怎么答？**
四层：采集（自研服务直埋 + 第三方 Exporter + blackbox 外部探测）、存储查询（Prometheus + 长期走 remote_write）、告警（基于症状 + Alertmanager 分组抑制静默 + 分级带 runbook）、展示（Grafana RED 看板 + 变量模板）。必须主动提：基数控制、告警噪声治理、监控系统自身的高可用与双活。

**Q8：为什么不能直接从 CPU 高开始查？**
因为 CPU 高几乎总是症状而非原因——下游慢导致请求堆积、协程暴涨导致调度开销、GC 频繁，全都会表现为 CPU 高。从 CPU 入手是"从症状往回猜原因"；按 SOP 先定性分层，走到出问题的那一层时 CPU 高是意料之中的，根本不需要单独查。
