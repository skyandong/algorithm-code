# 微服务治理面试一口答清单

> 从 01~14 篇笔记提炼的「张口就来」清单：被问到要能不带停顿直接说出来。
> 对应章节：`01-注册与发现` ~ `06-服务网格intro`（治理件）、`07~14`（可观测性的指标支柱，含排障），
> 实验代码在 `experiments/`，可一键起的真实栈在 `monitoring/`。
>
> **记忆主线：** 网络成了函数调用，凭空多出五类问题——找不到（注册）、改不动（配置）、连不稳（熔断限流）、看不见（可观测）、说不清（网关）。每个治理件都是对其中一个的应对。

---

## 一、注册与发现（01）

### 1. 注册中心是 CP 还是 AP？
理论张力：名单一致性（给错=打死亡实例）vs 可用性（挂了=全网失联）。etcd 走 CP（Raft），consul 走 AP（gossip），nacos 可切换。祛魅：调用方有本地名单缓存，注册中心短暂不可用只损失变更感知——实践差距小于理论，选型看生态。

### 2. 怎么发现实例死了？
心跳+TTL（TTL≥3×间隔）消极发现；摘除后订阅推送收敛。进程活着≠能服务——健康检查探针（/healthz 验依赖）是第二层。收敛窗口的兜底在调用方：重试+快速失败。

### 3. 优雅下线怎么做？
四步：主动反注册（不等 TTL）→ 探针置不健康拒新 → drain 在途请求 → 退出。上线对称：readiness 通过再注册（或低权重预热）。原则：名单和真相别打架。

## 二、配置中心（02）

### 4. 热更新链路？
watch（长轮询/gRPC stream）→ 校验（失败拒用+告警）→ atomic.Pointer 整体换快照。读者无锁 Load，单请求开头取一次快照全程自洽。

### 5. 为什么 atomic.Pointer 不用 mutex？
读路径无锁（每请求都读的热路径）；快照语义保证完整版本；杜绝"锁内逐字段改"的中间态。配置即值，更新即换快照。

### 6. 配置推送秒级新旧并存怎么办？
先问代价：阈值/开关不一致代价为零，接受。要全网同步（协议升级）用版本号协商。客户端随机延迟应用消解更新风暴（同构 TTL 抖动）。

### 7. 敏感配置？
信封加密：KMS 管数据密钥（慢路径一次），密钥内存解密（快路径常驻）。控制台脱敏，读取按服务隔离。AK 轮换=KMS 禁旧+推新密文。

## 三、熔断降级限流（03）

### 8. 三板斧的区别？
限流保自己（入口拒绝）、熔断保下游（调用方快速失败）、降级保核心（扔次要功能）。熔断在调用方因为下游故障时连拒绝都做不到；重试在故障期是乘法器，熔断切断乘法。

### 9. 熔断器原理？
三态机：closed 统计错误率 → 超阈值转 open 全拒 → 冷却期后 half-open 探活 → 成功恢复。参数：错误率 50%（防背景错误率误触发）、最小样本 20、冷却期 30s。进 open 重置窗口防卡死。

### 10. 漏桶 vs 令牌桶？
漏桶看出口（流出恒速不许突发，保护下游节奏）；令牌桶看入口（平均恒速允许突发，保护自己容量）。nginx limit_req 的 rate+burst+nodelay 是带突发的漏桶变体。

### 11. 滑动窗口实现？
环形桶：60 格每秒滚动，每桶记(总数,错误数)，查询求和——秒级粒度换性能。fixed window 的边界突刺（2 倍瞬时）是它存在的理由。

### 12. 单机限流 vs 分布式限流？
默认单机令牌桶×实例数（简单无依赖）；精确配额（计费）才 Redis+Lua 集中限流。先问配额精度值多少钱。

### 13. 降级方案？
分级预案（L1 关非核心写 → L4 拒服务保数据）提前演练；自动降级配熔断（兜底值），手动降级靠配置开关；每项要能答"数据怎么补"。

## 四、网关（04）

### 14. 网关/BFF/LB 区别？
智能递增：LB 只转发；网关七层+业务元数据（路由/鉴权/限流/灰度）；BFF 面向前端聚合（防腐层，隔离前端易变性）。

### 15. 网关内部结构？
一张路由表（注册中心动态解析实例）+ 一条中间件链（accessLog→trace→限流→鉴权→路由→转发）。限流在鉴权前：先做便宜的拒绝；日志最外层：被拒流量也要可观测。

### 16. 灰度怎么做？
路由表多版本：header（白名单）/uid 取模（抽样）/地域。护栏：规则热更、新旧指标对比、一键回退权重。分流 key 要粘性——同用户恒定同版本，这是和负载均衡随机分流的本质区别。

## 五、可观测性（05）

### 17. 三支柱关系？
metrics（聚合数字，便宜常开，告警）→ tracing（因果链，采样，定位）→ logging（明细，按需，取证）。漏斗：分辨率逐层放大，成本逐层升高。

### 18. 四个黄金指标？
延迟（P99 不是均值）、流量、错误率、饱和度（连接池/队列）。饱和度是先行指标——告警配在饱和度上，等延迟告警用户已在受苦。

### 19. trace_id 透传？
进程内 context.Context，跨进程 W3C traceparent（HTTP header/gRPC metadata）。span=trace_id+span_id+parent_id+耗时+属性，按 trace_id 聚拢建树。上报必须异步。

### 20. 头部 vs 尾部采样？
头部：入口按概率，全链路一致但错误/慢可能漏采；尾部：出口按结果，错误慢 100% 保留但要全量缓存。生产组合：头部 1% 保底+尾部捞错慢。

## 六、服务网格（06）

### 21. 网格解决什么？
把治理逻辑从 SDK 搬到 sidecar（envoy），应用零改造。解决 SDK 三税：多语言重写、升级推动全量发版、治理侵入业务进程。

### 22. istio 架构？
istiod 控制面（Pilot 下发规则/Citadel 签证书）+ envoy 数据面（每 Pod 一个执行）。xDS 下发——控制面/数据面分离，策略热更不发版。

### 23. SDK vs sidecar 怎么选？
三税成立（语言≥3、服务数百+、治理高频演进）→ sidecar 兑现收益；延迟极敏感（两跳硬伤）或要方法级业务治理 → SDK。中间解：薄 SDK+策略外移（国内大厂主流）。规模不够，网格是纯成本。

### 24. sidecar 模式还有哪？
日志 DaemonSet、Dapr、分库分表 proxy——"横切能力做成邻居进程"是云原生基础设施设计单元。

## 七、监控与可观测性落地（07~14）

### 25. 指标四类怎么选？
Counter 累计只增（记速率用 rate 算）、Gauge 瞬时可增可减（余量）、Histogram 分桶（延迟分布，**可聚合**）、Summary 客户端算分位（**不可聚合**）。铁律：**记速率用 Counter+rate，记余量用 Gauge**——Gauge 是瞬时采样，抓取间隔间的抖动全丢。

### 26. Histogram 和 Summary 怎么选？
默认 Histogram。因为**分位数不可加、桶可加**：多实例下各实例的 P99 无法合成全局 P99，但各实例的桶直接相加后服务端再 `histogram_quantile` 就能算对。Summary 只在单实例、不聚合、且要精确分位时用。

### 27. 手算 P99（给桶数据）？
找第 99 百分位样本落在哪个累计桶（首个 count ≥ rank 的桶），桶内线性插值：`桶下界 + 桶宽 × (桶内排名/桶内样本数)`。**桶越粗误差越大，所以桶边界要贴 SLO 设**，不是函数不准。

### 28. 什么是高基数？怎么治？
series 数 = 各 label 取值数的乘积。user_id/URL 路径/错误 message 这种无限增长的维度进 label，series 会爆炸（千万级 ≈ 数十 GB 内存 + 查询全废）。治理：路径归一成 `/user/{id}`、label 值域收敛为枚举、抓取侧 `metric_relabel_configs` 丢弃、明细走 exemplar 挂 trace_id 而不是做成 label。

### 29. Prometheus 为什么用 pull 而不是 push？
三件事：①抓取失败即存活判定（`up=0` 是最基础的告警，push 模式要另建探活）；②目标发现集中在监控侧（扩缩容时应用不用知道监控在哪）；③`curl /metrics` 就能排障。代价是抓不到短命任务，所以 Pushgateway 只作为批任务的特例补丁。

### 30. TSDB 怎么组织的？
写入先进内存 head block 并追写 WAL（防崩），每 2 小时落盘成不可变 block（自带倒排索引，时间戳 delta-of-delta 压缩），后台 compaction 合并。保留期默认 15 天，长期存储靠 remote_write 到 Thanos/VictoriaMetrics。

### 31. rate 和 irate 的区别？
rate 用窗口内所有样本做拟合，平滑抗抖，是告警/面板的默认；irate 只取最后两个样本，能看毛刺但图会锯齿、会让阈值附近告警反复翻转。**窗口必须 ≥ 4×scrape_interval**（15s 抓取配 `[1m]` 起）。

### 32. Counter 重启归零，QPS 会算成负数吗？
不会。rate 检测到后值小于前值即判定重置，把重置后段当作从 0 开始单独算增量。**应用侧永远不用处理重启归零**——这是 Counter 语义 + rate 的分工。

### 33. 多实例全局 P99 的 PromQL？
`histogram_quantile(0.99, sum(rate(..._bucket[5m])) by (le))`。两个要点：**必须保留 `le`**（函数靠它算）、**必须先把各实例桶 sum 起来**（桶可加）。`rate(sum(x))` 是错的——区间选择器只能贴原始选择器。

### 34. 告警基于症状还是原因？
面向值班（page）的基于症状（错误率、P99——用户正在受影响），基于原因的（CPU/磁盘）降级 ticket 或看板。例外是"即将耗尽"类预测告警（`predict_linear` 算磁盘 4 小时后满）。原因：一次根因会让几十个原因指标异常，按原因告警会制造噪声并掩盖根因。

### 35. 为什么告警要加 for？
让告警必须持续满足条件才从 Pending 转 Firing，消解瞬时抖动（GC 停顿、发版重启、网络抖动）。取值 ≈ 可接受的告警延迟：核心 2~5m，非核心 15m。

### 36. Alertmanager 的分组/抑制/静默？
分组：按 label 把一次故障的几十条告警合并成一条（`group_wait` 先攒 30s）；抑制：配置里的长期规则，critical 静默同 job 的 warning；静默：运维临时按 label 屏蔽（有过期）。三者一起把"通知数量"与"故障规模"解耦。

### 37. 线上报警了怎么查？
四步：①影响面（是不是真在影响用户，同时排除误报）；②定性（慢/错/堵）；③分层（依赖链上哪一层，找第一个异常的下游）；④定位（到了具体一层才看 CPU/内存/GC）。第 0 步先看有没有变更（发版/配置/定时任务）。**资源放最后——CPU 高几乎总是症状。**

### 38. 从零设计监控怎么答？
四层：采集（自研直埋 + 第三方 Exporter + blackbox 外部探测）→ 存储查询（Prometheus + remote_write 长期）→ 告警（基于症状 + Alertmanager 分组抑制 + 分级带 runbook）→ 展示（Grafana RED 看板 + 变量模板化）。必须主动提三件事：基数控制、告警噪声治理、监控系统自身的高可用双活。

## 考前 60 秒主线串讲

微服务的代价是**网络成了函数调用**，治理件应对五类新问题。

**找不到**→注册中心：心跳+TTL 摘死实例，探针摘僵尸（进程活着≠能服务），名单滞后是常态、兜底在调用方；优雅上下线四步——先摘流量再停进程。

**改不动**→配置中心：watch→校验→**atomic 换快照**，永不逐字段热改；灰度+一键回滚复用更新链路。

**连不稳**→三板斧：限流保自己、熔断保下游（重试是乘法器，熔断切断它）、降级保核心（分级预案+数据补偿）。熔断器三态机——closed 统计、open 拒绝、half-open 探活，错误率 50%+最小样本 20 防误触发。

**说不清**→网关：路由表+中间件链（限流在鉴权前——先做便宜的拒绝）；灰度用 uid 取模保粘性，发版变成路由权重调整。

**看不见**→三支柱漏斗：metrics 报警（四黄金指标，P99 不用均值）→ tracing 定位（trace_id 透传+parent 建树）→ logging 取证；尾部采样保错误样本。

**指标支柱落地**→一条链：埋点（中间件埋 RED，热路径 O(1) 无锁、label 收敛防高基数）→ 抓取（pull 模型，`up=0` 白送存活判定）→ 存储（head+WAL+block，15 天）→ 查询（Counter 先 rate 再 sum，多实例 P99 靠 `by (le)` 加桶）→ 告警（基于症状 + for 抗抖 + Alertmanager 分组抑制，50 条收敛 1 条）→ 展示（RED 四行看板，P50/P90/P99 三线叠加定性）→ 排障（影响面→定性→分层→资源放最后）。

最后是**居住形态**：治理逻辑住 SDK（进程内、零延迟、三税）还是 sidecar（进程外、两跳、语言无关）——规模和语言多样性决定答案，没有银弹。
