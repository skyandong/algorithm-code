# 注册与发现：从心跳到优雅上下线

> **核心认知：** 微服务的全部代价源于一句话——**网络成了函数调用**。单体的函数调用不会失败（进程内跳转），微服务的"函数调用"横跨网络，于是凭空多出五类问题：**找不到**（实例 IP 随时变，谁来告诉我对方在哪）、**改不动**（配置散落各实例）、**连不稳**（网络抖动被放大成雪崩）、**看不见**（调用链穿透 N 个进程）、**说不清**（路由规则谁来执行）。本模块六篇就是这五个问题的逐个击破，第一篇解决"找不到"：**注册中心 = 一张实时的"服务名 → 健康实例列表"映射表**。实现的核心不是存数据（一张表谁都会存），是**语义选择**：etcd 走 Raft 强一致（`notes/distributed/02`）——宁可注册不可用也不给错名单；consul/nacos 走 AP——先答再收敛。以及最容易被轻视、却制造了最多生产事故的一环：**优雅上下线**——先摘流量再停进程，做反了就是"发布即 502"。

前置知识：Raft 共识（`notes/distributed/02`）、φ-accrual 故障检测（`notes/distributed/07`）、lease 租约（`notes/distributed/04`）。

## 1. 服务模型：注册中心管什么

**服务定义四要素**：

```text
服务名:  "order-service"            —— 逻辑标识, 调用方用的 key
实例:    10.1.2.3:8080, 10.1.2.4:8080 —— 物理地址, 随时增减
元数据:  {version: "v2.1", weight: 100, zone: "hz-1"} —— 灰度/路由的输入
健康状态: healthy / unhealthy / suspect
```

**注册中心的数据本质**：一个"名字 → 实例列表"的**高频变更的、需要全网一致可见的**映射。注意两个定语——高频变更（发布/扩缩容/宕机，每天成百上千次）和全网一致（调用方的名单错一个，请求就打到死实例上）。这两个定语的张力（变更快 vs 一致难）就是选型的核心矛盾。

## 2. 心跳与 TTL：剔除一个死实例

实例不会主动说"我死了"（宕机就是失联，没有遗言）——只能靠**消极发现**：

```text
注册:   实例启动 → PUT /services/order/10.1.2.3:8080 (带 TTL=15s)
心跳:   实例每 5s 续约一次（刷新 TTL）
剔除:   超过 TTL 未续约 → 注册中心删 key → 订阅者收到变更通知
```

**WHY TTL 是心跳间隔的 3 倍**：覆盖"一次心跳丢失"（网络抖动）+ GC 停顿（`notes/distributed/07` 的"慢和死不可分"）。取太短误杀率高（发布时实例重启慢一点就被摘），太长则死实例在调用方名单里多活一会儿（请求失败率上升）。

**注册 vs 第三方健康检查**：自注册+心跳只证明"进程活着"，不证明"能服务"（死锁、连接池耗尽、依赖的 DB 挂了——进程活着但请求必败）。生产配置**健康检查探针**（HTTP /healthz 检查依赖），注册中心按探针结果标记 healthy/unhealthy——心跳管进程死活，探针管服务死活，两层缺一不可。

**摘除的级联**：实例被摘 → 调用方名单收敛。收敛期间打到死实例的请求怎么办？调用方要配**重试 + 失败实例快速熔断**（03 篇的客户端熔断）——**注册中心的名单永远是"略滞后于真相"的缓存**，这个滞后窗口的兜底在调用方，不在注册中心。

## 3. 三种实现对照：etcd / consul / nacos

| | etcd | consul | nacos |
|---|---|---|---|
| 一致性 | **CP**（Raft 强一致） | **AP**（gossip 最终一致） | AP/CP 可切换（临时实例 AP，持久实例 CP） |
| 健康检查 | TTL lease | 丰富（HTTP/TCP/script/间隔可调） | 心跳 + 主动探活双模式 |
| 数据模型 | 通用 KV（lease+watch） | 原生服务模型（KV 是辅助） | 原生服务模型 + 配置中心二合一 |
| 生态 | K8s 御用（事实标准） | HashiCorp 系（多语言友好） | 国内系（Dubbo/Spring Cloud Alibaba） |
| 典型用户 | K8s Pod 发现 | 中立云厂商 | 阿里系开源 |

**WHY etcd 是 CP**：注册信息是"correctness 数据"——给错名单（两个版本的世界里实例列表不同）比短暂不可用更糟？**反过来想也成立**（consul 的立场）：注册中心整体不可用 = 全网服务互相找不到 = 更大的灾难。**两边的哲学**：

```text
CP（etcd）: 名单必须一致——宁可注册失败让实例起不来（部署期发现问题）
           副作用: 网络分区时少数派侧无法注册/续约 → 被摘除
AP（consul）: 名单必须可得——先答（可能旧）再收敛
           副作用: 分区两侧各有一份不同的名单（最终一致, notes/distributed/01）
```

**实践中更普遍的共识**：注册中心短暂不可用**没那么致命**——调用方本地有名单缓存，注册中心挂 5 分钟，已运行的服务照样互相调用（只是感知不到变更）。所以"AP vs CP"在注册场景的实际差距比理论小，**选型更多看生态**（K8s 选 etcd 事实标准、Spring Cloud Alibaba 选 nacos）。能讲出这一层的"祛魅"，比背 CP/AP 表格值钱。

## 4. 客户端发现 vs 服务端发现

**客户端发现**（调用方自己查名单、自己负载均衡）：

```text
调用方 → 本地缓存名单（订阅注册中心推送）→ 选一个实例直连
```

优点：少一跳（无中间层延迟）、客户端可做精细策略（同 zone 优先、灰度元数据路由）。
缺点：**每门语言都要实现一遍 SDK**（名单缓存/健康剔除/负载均衡/重试），升级治理逻辑=全量升级所有服务——**多语言场景是灾难**。

**服务端发现**（网关/sidecar 代劳）：

```text
调用方 → LB/网关/sidecar → 查名单选实例转发
```

优点：治理逻辑集中一处，语言无关。
缺点：多一跳延迟；网关本身要高可用（它成了新的单点层）。

**sidecar 是两者的混合赢家**（06 篇展开）：把"客户端 SDK"做成独立进程部署在应用旁边——逻辑上仍是客户端发现（精细策略），物理上语言无关（应用只管发本地请求）。**这就是服务网格的注册发现观**。

## 5. 优雅上下线：发布事故的根源

**错误顺序**（每次发布一波 502 的经典事故链）：

```text
杀进程 → 连接被 RST → 在途请求全部失败
       → 注册中心还要等 TTL 超时才摘除 → 新请求继续打进来 → 失败
       → 调用方名单收敛完才正常 → 全程可能 30s+ 的错误窗口
```

**正确顺序**（先摘流量，再停进程）：

```text
① 反注册: 主动 DELETE 注册记录（不等 TTL 超时——TTL 是为"死给你看"兜底的, 不是正常退出用的）
② 拒新: 健康检查改为"不健康"（LB/网关探到后摘除）或返回 503
③ 等旧: 等 SIGTERM 后的在途请求 drain（HTTP: 等连接空闲; gRPC: GRACEFUL_STOP）
④ 停进程
```

**扩容的对称问题**：新实例**注册了但还没就绪**（JVM 预热、缓存冷启动）——流量立刻打满会超时。解法：** readiness 探针通过后才允许注册**（先 ready 再 register），或注册后低权重预热（权重从 0 滑升到 100）。**上线要"预热后接入"，下线要"摘除后退出"——两个方向都是"别让名单和真相打架"**。

Go 实现要点（`notes/golang/10` 的 context 取消传播配合）：

```go
// http.Server 的优雅退出
srv := &http.Server{Addr: ":8080", Handler: h}
go func() { _ = srv.ListenAndServe() }()
<-sigCh                        // 收到 SIGTERM
deregister()                   // ① 先摘流量
ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
_ = srv.Shutdown(ctx)          // ③ 等在途请求 drain（最多 30s）
                                // ④ Shutdown 返回后进程退出
```

## 6. 面试高频

**Q1：注册中心是 CP 还是 AP？**
先讲张力：名单一致性（给错=打死亡实例）vs 可用性（整体不可用=全网失联）。etcd 走 CP（Raft），consul 走 AP（gossip），nacos 可切换。再讲祛魅：调用方有本地缓存，注册中心短暂不可用不致命，所以实践差距小于理论——选型主要看生态。

**Q2：怎么发现实例死了？**
消极发现：心跳+TTL（TTL≥3×间隔，覆盖抖动和 GC）；摘除后订阅推送收敛。进程活着≠能服务，还要健康检查探针（/healthz 验依赖）。收敛窗口的兜底在调用方：重试+快速失败。

**Q3：心跳和健康检查有什么区别？**
心跳证明"进程在"（续约），探针证明"能服务"（HTTP 检查 DB/下游依赖）。死锁/连接池耗尽类故障心跳正常但探针必挂——生产两层都要，只有心跳会漏掉"活着的僵尸"。

**Q4：客户端发现和服务端发现怎么选？**
客户端：少一跳、策略精细，但每门语言一套 SDK，升级=全量升级。服务端（网关）：语言无关、集中治理，但多一跳+网关要高可用。多语言+治理复杂度高→网关或 sidecar（把客户端 SDK 下沉成独立进程，06 篇）。

**Q5：怎么做优雅上下线？**
下线四步：主动反注册（不等 TTL）→ 探针置不健康拒新 → drain 在途请求 → 退出。上线对称：readiness 通过后再注册（或低权重预热）。核心原则：**名单和真相别打架**——TTL 摘除是给宕机兜底的，不是给正常发布用的。

**Q6：注册中心挂了服务还能调用吗？**
能（一段时间）。调用方缓存名单本地续用，已建立的服务间调用不受影响——只损失"变更感知"（扩缩容/故障摘除）。这也是注册中心选型不必过度纠结 CP/AP 的原因。缓存名单要有 TTL 和刷新兜底，防止永久使用脏名单。
