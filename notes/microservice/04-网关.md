# 网关：路由、中间件链与灰度

> **核心认知：** 网关是微服务的"**前台**"——所有外部流量从这个单一入口进来，它把"每个服务都要做一遍的事"（路由、鉴权、限流、协议转换、灰度）收敛到一处做一次。理解网关的关键是三个层次的正确定位：**LB**（四层/七层转发，不懂业务）、**网关**（七层+业务感知：路由表、鉴权、灰度）、**BFF**（面向前端的聚合层，懂业务组合）——很多人混着用这三个词，其实它们是"智能程度"递增的三层。网关内部的核心结构只有两个：**一张路由表**（host/path → 服务名，配合注册中心动态解析）和**一条中间件链**（`notes/design-pattern/03` 的装饰器/责任链直接落地——鉴权、限流、日志、trace 都是链上的一个环节）。灰度路由是网关最有面试价值的部分：**按 header/uid 百分比分流**，它是"发布安全"的最后一道基础设施。

前置知识：装饰器与责任链（`notes/design-pattern/03`）、nginx 反代与负载均衡（`notes/nginx/02`）、注册发现（本模块 `01`）、限流（本模块 `03`）。

## 1. 网关 vs BFF vs LB：三层定位

```text
外部流量
   │
   ▼
┌──────────┐  LVS/nginx: 四层/七层转发
│   LB     │  只认 IP:port 和域名, 不懂业务
└────┬─────┘
     ▼
┌──────────┐  APISIX/Kong/Higress: 七层 + 业务元数据
│   网关    │  路由表 / 鉴权 / 限流 / 协议转换 / 灰度
└────┬─────┘
     ▼
┌──────────┐  Backend For Frontend: 面向前端形态的聚合层
│   BFF    │  App 页面要 5 个服务的数据, BFF 一次聚齐（GraphQL/RPC fan-out）
└──────────┘
```

**三层的分工**：LB 管"转发效率"（C/DPDK 级性能，`notes/nginx/02` 的负载均衡策略在这一层）；网关管"流量治理"（路由+策略）；BFF 管"业务聚合"（为 App/Web/小程序 各做一层，隔离前端变化对后端微服务的冲击——**防腐层**思想，`notes/design-pattern/01`）。

**WHY 需要 BFF**：没有 BFF，App 的一个页面改版要 5 个微服务配合改接口；有了 BFF，前端只跟 BFF 对话，微服务保持纯粹的业务原子性——**把"面向前端的易变性"圈在 BFF 一层**。代价：BFF 自己成了需要维护的代码——小团队直接网关+前端调微服务，别为了架构而架构。

## 2. 路由表：从 URL 到实例

网关最核心的数据结构：

```text
路由表（静态配置 + 注册中心动态解析）:
  host: api.example.com
    /order/*    → order-service   （从注册中心拉实例列表, 客户端发现）
    /pay/*      → pay-service
    /user/*     → user-service

匹配优先级（与 nginx location 同构, notes/nginx/02）:
  精确 > 最长前缀 > 正则; 匹配到服务名后做负载均衡选实例
```

**路由表的两个来源**：静态声明（网关配置/CRD——K8s Ingress 就是声明式路由）+ 动态服务发现（`notes/microservice/01` 的名单订阅——路由表里的"服务名"运行时解析为实例列表）。**路由表的热更新**直接复用 02 篇配置中心的模式：watch → 校验 → atomic 换快照——路由表就是一类特殊的"动态配置"。

**协议转换**是路由的衍生能力：外部 HTTP/WebSocket → 内部 gRPC（网关做 HTTP→gRPC 的映射，google.grpc-gateway/envoy 都内置）——**对外一个协议，对内一个协议**，内外解耦。

## 3. 中间件链：网关的骨架

网关的处理流程是一条链（`notes/design-pattern/03` 的责任链模式实战）：

```go
// Handler 链: 每个中间件包裹下一层 —— 装饰器模式的函数化写法
type Handler func(ctx context.Context, req *Request) *Response

func Chain(hs ...Middleware) Handler { // middleware: func(next Handler) Handler
    // 从后往前包裹, 形成洋葱圈
}

// 生产链顺序（顺序是刻意的）:
accessLog → trace → rateLimit → auth → route → proxy
//   │          │        │         │       │       │
//   记进入      埋trace   先限流    再鉴权   最后才   转发到上游
//   (含退出)   (全链路)  (省鉴权    (没被限  解析路由  (连接池+超时+重试)
//             的起点)   的CPU)    流的才配
```

**WHY 顺序是"限流在鉴权前"**：鉴权要查 token/调 Redis（有成本），恶意流量连鉴权的 CPU 都不该消耗——**先做便宜的拒绝，再做贵的校验**。反例顺序（先鉴权后限流）会被无 token 的洪水打到鉴权层自身。同理：accessLog 最外层（记录被拒绝的请求，否则限流拦掉的流量成为监控盲区）。

**中间件链的变体**：洋葱圈（请求/响应两侧都能处理——日志记耗时）vs 直线管道（只有请求侧——更简单）。Go 标准库 `http.Handler` 的 `func(http.Handler) http.Handler` 签名就是函数化装饰器——`notes/design-pattern/03` 的理论在标准库里的直接回响。

## 4. 灰度路由：按 header/uid 分流

灰度 = **新版本只放一部分流量进来，观察没问题再放大**：

```text
策略类型:
  按 header:     x-canary: true        → 走新版本（内部员工/白名单先吃自己的狗粮）
  按 uid 取模:   uid % 100 < 5         → 5% 用户走新版本（真随机抽样）
  按地域/渠道:    region=cn-north       → 华北机房先上新（爆炸半径可控）
  按 cookie:     会员用户 → 新版本      （业务维度切流）

路由表扩展:
  /order/*  → order-service  (stable, 权重 95)
            → order-service-v2 (canary, 匹配 uid%100<5 → 权重 5)
```

**灰度的护栏**（缺一不可）：
1. **匹配规则可热更**——切流 5%→50% 不能发版（02 篇配置中心的动态配置）；
2. **可观测对比**——新旧版本的错误率/P99/QPS 并排监控（05 篇可观测的黄金指标），没有对比面板的灰度是盲飞；
3. **一键回退**——规则回退到 0% 权重（秒级），比回滚代码（分钟级）快一个量级。

**WHY uid 取模而不是纯随机**：同一个用户要**始终**落在同一版本——否则他的两次请求分属新旧版本，看到跳变的 UI/数据不一致，比全量上新还糟。**灰度分流的 key 要"粘性"**（uid/userId/deviceId），这是和负载均衡随机分流（`notes/nginx/02` 的 random/round-robin）的本质区别。

**发布即灰度**：成熟的发布流程全靠灰度托底——蓝绿、金丝雀、A/B 本质都是"路由表权重/规则的操盘"：**基础设施把"发版"从高危动作变成路由权重调整**，这是网关送给工程效率最大的礼物。

## 5. 网关自身的高可用

网关是所有流量的入口——**它的可用性 = 全站可用性**：

```text
① 网关无状态化: 路由表/规则全来自配置中心和注册中心（01/02 篇的产物）
   → 网关实例随意横扩, 挂了任何一台 DNS/LB 自动剔除
② 多实例 + LB 前置: LVS/nginx 做四层负载, 网关集群 N 台
③ 依赖降级: 注册中心挂 → 用本地缓存的路由名单继续转发（01 篇 Q6 同款结论）
   配置中心挂 → 当前配置快照继续生效
④ 兜底路径: 网关整体挂 → nginx 直连一组"保底服务列表"（静态配置的终极降级）
```

**性能账**：网关一跳引入 ~1ms 延迟（解析+转发），换来的是鉴权限流灰度的集中治理——这笔账几乎总是划算的；真正贵的是"每个服务自己做一遍这些事"的维护成本和漏配风险。

## 6. 面试高频

**Q1：网关和 LB 和 BFF 的区别？**
三层智能递增：LB 只转发不懂业务（nginx/LVS）；网关七层+业务元数据（路由/鉴权/限流/灰度）；BFF 面向前端做业务聚合（隔离前端的易变性，防腐层）。小团队网关+直连微服务即可，BFF 是前端形态多了之后的产物。

**Q2：网关内部结构怎么设计？**
一张路由表（host/path→服务名，注册中心动态解析实例）+ 一条中间件链（accessLog→trace→限流→鉴权→路由→转发，函数化装饰器）。链的顺序有讲究：限流在鉴权前（先做便宜的拒绝），日志最外层（被拒流量也要可观测）。

**Q3：灰度发布怎么做的？**
路由表支持多版本：按 header（白名单）、uid 取模（5% 抽样）、地域渠道分流。护栏三件套：规则热更（配置中心）、新旧版本指标对比面板、一键回退权重。分流的 key 要粘性（同用户恒定同版本），否则体验跳变。

**Q4：为什么灰度分流用 uid 取模不用随机？**
灰度要求同一用户始终同一版本（一致性体验），uid 取模天然粘性；负载均衡的随机/轮询不要求粘性（无状态请求），这是两者本质区别。

**Q5：网关怎么保证高可用？**
无状态化（路由/规则全部外置到配置+注册中心）+ 多实例前置 LB + 依赖降级（注册中心挂用本地缓存名单继续转发）+ 极端兜底（静态保底服务列表）。网关可用性=全站可用性，这层的投入最值。

**Q6：网关层限流和应用层限流的分工？**
网关管总量（全局 QPS、按维度的粗粒度——nginx limit_req 的应用层版）；应用层管细粒度（按用户/按接口/按业务对象），两者配合。网关限流拦洪水，应用限流保护自己的容量预算（03 篇）。
