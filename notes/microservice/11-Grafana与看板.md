# Grafana 与看板：把数字摆成一眼能读懂的图

> **核心认知：** Grafana **不存任何数据**，它只是 PromQL 的一层展示与排版工具——换掉它 Prometheus 毫无损失。所以看板设计的全部功夫不在"怎么配 Grafana"，而在"**一个值班的人半夜打开这块板，能不能在 30 秒内判断出系统是否健康、哪里不对**"。据此推出的纪律是：**一屏一屏地组织（总览 → 下钻），每块板只回答一个问题，图的标题要能自解释，单位要标对**。一块需要人读图例猜含义的看板，等于没有看板。

前置知识：[09](09-PromQL实战.md)（面板就是 PromQL 的可视化）、[05](05-可观测性.md)（四个黄金信号、RED/USE）。

## 1. Grafana 在数据链路里的位置

```text
Prometheus (存 + 算)  ──HTTP PromQL──→  Grafana (查 + 画)
        ↑                                      │
    抓取目标                              也可以查 Loki(日志)/Tempo(链路)
```

**三层解耦**（这决定了它能同时画多个数据源）：存储归 Prometheus、日志归 Loki、链路归 Tempo，**Grafana 只是统一的前端**。这也是它能做"从指标面板点进对应 trace"的基础——**三支柱在展示层汇合**（05 篇的漏斗，在 Grafana 上被揉成一个界面）。

** provisioning（配置即代码）**：看板 JSON 要进 Git，用 `provisioning/dashboards/` 目录挂载，而不是在 UI 上手动点——**不然一次误删就再也找不回来**，也没法做 code review。

## 2. 面板类型怎么选

| 面板 | 适合 | 不适合 |
|---|---|---|
| **Time series**（折线） | 一切随时间变化的量：QPS、延迟、错误率、CPU | 无 |
| **Stat**（大数字） | "当前值"：当前 QPS、当前在线数、SLO 达成率 | 看趋势 |
| **Gauge**（仪表） | 有明确上界的比率：连接池使用率 80%、磁盘 62% | 无上界的量（QPS 没有"满"的概念） |
| **Bar gauge** | 多个对象的比率对比：各实例 CPU | 时间序列 |
| **Heatmap**（热力图） | **延迟分布随时间的变化**（比 P99 一条线信息量大得多） | 简单趋势 |
| **Table** | 多维度对比、TopN（配合 `topk`） | 趋势 |
| **Logs panel** | 直接嵌 Loki 日志（与指标同屏） | — |

**Heatmap 是被低估的面板**：P99 是一条线，你只知道"最慢的 1% 在 850ms"；热力图能看到**分布是不是双峰的**（一部分请求 10ms，一部分 500ms）——**双峰意味着有两种请求模式**，这是 P99 单值完全看不出来的，而它恰恰指向根因（缓存命中 vs 未命中、大 key vs 小 key）。

**单位必须标对**（Unit 字段）：延迟用 `seconds`、字节用 `bytes`、比率用 `percentunit`（0~1）不是 `percent`（0~100）。**标错了图上会显示成"0.01s"或"1000%"，而值班的人会照着错的值做判断**。

## 3. 变量：一块板覆盖所有服务与实例

变量就是**把 PromQL 里的常量换成下拉框**：

```promql
# 定义变量: $job  (Query 类型: label_values(job))
# 定义变量: $instance (依赖 $job: label_values(up{job="$job"}, instance))

# 面板查询里引用:
sum(rate(http_requests_total{job="$job",instance=~"$instance"}[5m])) by (route)
```

**WHY 变量是看板设计的核心**：没有变量，100 个服务要建 100 块板；有了变量，一块板覆盖全部，且** onboarding 新服务时零配置**（只要它在被抓取，下拉框里就自动出现了）。

**`interval` 变量**：把 `$__rate_interval` 用在查询里（`rate(x[$__rate_interval])`），Grafana 会根据图的像素宽度自动选一个合适的窗口——**比手写 `[5m]` 更稳**，因为窄图用小窗口、长周期图用大窗口，避免"看 7 天趋势时窗口太小导致图糊成一片"。

## 4. RED 看板：服务的标准布局

RED = Rate / Errors / Duration，[05 篇](05-可观测性.md)四个黄金信号的服务视角版。**一块服务看板的标准三行**：

```text
┌─────────────────────────────────────────────────────┐
│ 第一行（总览 Stat）: QPS | 错误率 | P99  | SLO 达成  │  ← 一眼判断健康
├─────────────────────────────────────────────────────┤
│ 第二行: QPS 折线（按 route 拆）  │ 错误率折线        │  ← 什么时候开始的
├─────────────────────────────────────────────────────┤
│ 第三行: 延迟热力图  │ P50/P90/P99 三线叠加          │  ← 慢在哪类请求
├─────────────────────────────────────────────────────┤
│ 第四行: 饱和度——连接池 / goroutine 数 / 队列深度    │  ← 还能扛多久
└─────────────────────────────────────────────────────┘
```

**第一行为什么是 Stat 而不是折线**：值班的人第一眼要的是"现在好不好"，不是"过去 6 小时的形状"。**Stat 配阈值染色**（绿色正常、黄色警告、红色超标）让判断变成扫一眼。

**P50/P90/P99 三线叠加**（而不是只画 P99）：如果三条线**一起涨**，是系统性变慢（下游慢了、资源不够）；如果**只有 P99 涨**，是特定请求模式出问题（大 key、锁竞争、慢查询）。**这个对比是最快的定性判断**，比任何单值都有用。

**饱和度放最后但最有价值**：05 篇强调过它是先行指标——连接池爬到 90% 时延迟还没涨，这是你唯一的干预窗口。

## 5. USE 看板：资源的标准布局

USE = Utilization / Saturation / Errors，资源视角（机器、连接池、磁盘、线程池）：

| | 含义 | 例子 |
|---|---|---|
| **U** 使用率 | 资源忙的时间占比 | CPU 使用率、连接池占用率 |
| **S** 饱和度 | 排队程度（**比使用率更早报警**） | 运行队列长度、连接池等待数、磁盘 IO 队列 |
| **E** 错误 | 错误事件数 | 磁盘错误、网卡丢包、连接被拒 |

**WHY 饱和度往往比使用率重要**：CPU 90% 但运行队列为 0，说明干得动；CPU 60% 但运行队列常年 8，说明**已经排队了**。使用率是"资源多忙"，饱和度是"有没有人在等"——**后者才直接影响延迟**。

**Go 运行时的 USE**（Go 服务特有的饱和度）：goroutine 数量（`go_goroutines`）、GC 暂停（`go_gc_duration_seconds`）、堆占用（`go_memstats_heap_inuse_bytes`）——**goroutine 数持续上涨 = 协程泄漏，这是 Go 服务最常见的死法之一**（`notes/golang` 里讲过的 goroutine 裸奔问题，在这里有了监控抓手）。

## 6. 四个高频坑

**① 图例爆炸**：`sum by (route)` 有 200 个路由 → 图例 200 条，图没法看。解决：`topk(5, ...)` 只显示 Top5 + 一条 `Other`。

**② 忘记 rate**：直接画 `http_requests_total` → 一条永远上涨的斜线，毫无信息。**Counter 必须先 `rate`**。

**③ 窗口与看板时间范围不匹配**：看 7 天趋势却用 `[5m]` → 图糊成一片噪声。用 `$__rate_interval` 让 Grafana 自适应。

**④ 平均值陷阱**：延迟用 `avg` 而不是分位数 → 均值正常但用户投诉慢。09 篇讲过：**均值掩盖尾部**。

## 7. Grafana 告警 vs Prometheus 告警

Grafana 自己也能配告警（在面板上定义阈值、由 Grafana 定期求值并通知）。**怎么选**：

| | Prometheus + Alertmanager | Grafana Alerting |
|---|---|---|
| 数据来源 | 只能 Prometheus | **任意数据源**（含 Loki、MySQL） |
| 分组/抑制/静默 | Alertmanager 完整能力 | Grafana 自己的 notification policy（能力接近） |
| 与代码关系 | YAML 进 Git，CI 校验 | 也能导出 JSON 进 Git |

**实践建议**：**Prometheus 生态内的告警仍用 Prometheus rules**（与采集同源、延迟低、语义清晰）；**跨数据源的（如"日志里出现某错误且量 > N"）用 Grafana**。不要两边都配同一条告警——会双重通知。

## 8. 面试高频

**Q1：Grafana 存数据吗？它在链路里的位置？**
不存，只查 PromQL 并画图。存储归 Prometheus、日志归 Loki、链路归 Tempo，Grafana 是统一前端——这也是三支柱能在同一个界面汇合的原因（从指标面板点进对应 trace）。

**Q2：服务看板怎么设计？**
RED 三行 + 饱和度：第一行 Stat 总览（QPS/错误率/P99/SLO，配阈值染色，一眼判断健康）；第二行 QPS 与错误率折线（什么时候开始的）；第三行延迟热力图 + P50/P90/P99 三线叠加（慢在哪类请求）；第四行饱和度（还能扛多久）。用变量 `$job`/`$instance` 让一块板覆盖所有服务。

**Q3：P50/P90/P99 三条线一起画的价值？**
定性判断：三线一起涨 = 系统性变慢（下游慢、资源不足）；只有 P99 涨 = 特定请求模式出问题（大 key、锁竞争、慢查询）。比任何单值都快。

**Q4：RED 和 USE 的区别？**
RED 是服务视角（Rate/Errors/Duration，用户感受到的）；USE 是资源视角（Utilization/Saturation/Errors，机器/连接池/磁盘的余量）。一台服务挂两组仪表——RED 看表现，USE 看余量。饱和度是先行指标，使用率是"多忙"，饱和度是"有没有人在等"，后者才直接影响延迟。

**Q5：`$__rate_interval` 是什么，为什么用它？**
Grafana 根据图的像素宽度和时间范围自动计算合适的 rate 窗口。用它替代手写 `[5m]`，避免"看 7 天趋势却用 5m 窗口导致图糊成噪声"。

**Q6：看板图例爆炸怎么办？**
用 `topk(5, ...)` 只显示 Top5 并把其余归为 Other；或提高聚合层级（按服务而不是按路由）。

**Q7：看板要不要进 Git？**
要。用 `provisioning/dashboards/` 目录挂载 JSON，而不是在 UI 上手动点——否则误删找不回来，也无法 code review。

**Q8：热力图什么时候比折线好？**
看延迟分布随时间的变化时。P99 是单值，看不出分布形态；热力图能看出**双峰**（部分 10ms 部分 500ms），双峰意味着存在两种请求模式，直接指向根因（缓存命中/未命中、大 key/小 key）。
