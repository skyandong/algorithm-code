# 服务网格 Intro：sidecar 把治理下沉

> **核心认知：** 服务网格回答的问题是：**治理逻辑（注册发现/熔断/重试/加密）到底应该住在哪？** 上一代答案：住在每个服务的 SDK 里（Java 的 Dubbo/Spring Cloud 全家桶）——代价是**每门语言重写一遍、每次升级推动全公司改依赖发版**，治理能力越强，SDK 越重，枷锁越紧。sidecar 的答案优雅而暴力：**把 SDK 拆出来做成独立进程（envoy），部署在每个应用旁边，应用只跟 localhost 的 sidecar 说话**——治理从"代码依赖"变成"基础设施"。一句话理解 istio：**envoy 做数据面（每台机器上的代理），istiod 做控制面（下发路由/规则给所有 envoy）**——控制面/数据面分离，和 04 篇网关"路由表与转发分离"、02 篇"配置与生效分离"是同一个架构母题的第三次出现。但要清楚代价：**每个请求多两跳 sidecar、每 Pod 多一个容器的资源、排障多一层盒子**——服务网格不是"更高级"，是"用运行时成本换工程组织成本"，SDK 用得挺爽的团队上网格纯属自虐。

前置知识：本模块 `01`（客户端/服务端发现）、`02`（配置下发与热更）、`03`（熔断限流）、`04`（网关）、`05`（可观测）——**本篇是前五篇的"居住形态重组"，没有新概念**。

## 1. SDK 模式的困境：为什么治理逻辑住进代码里是枷锁

前五篇的所有治理能力（发现/熔断/限流/灰度/trace），传统实现都是**业务进程内的库**：

```text
业务进程 = 业务代码 + 治理 SDK（服务发现客户端 + 熔断器 + 负载均衡器 + trace 埋点）
```

三个逐渐恶化的代价：

**① 多语言税**：治理 SDK 是语言绑定的——Java 有 Dubbo 全家桶，Go 要重写一遍（kitex 能做到的事 Java 生态早有了），Python/Rust/Node 每门都要养一套。**公司语言越多，SDK 模式的税越重**。

**② 升级税**：熔断器修个 bug，全公司几百个服务都要升依赖、回归、发版——发版是高危动作（`notes/microservice/01` 的优雅上下线），**治理能力的迭代速度被业务发版节奏锁死**。某个关键漏洞要求两周内全量升级时，SDK 模式直接变成事故。

**③ 侵入税**：SDK 的线程模型/内存模型渗入业务进程（重试逻辑改写语义、超时传染、字节码增强的玄学），业务工程师要懂治理细节才能排障——**关注点没分离，只是物理上在同一个 jar 里**。

**WHY 这些税在大厂变得不可忍受**：服务数过千、语言超过三种、治理策略每周都在演进——三个税相乘，基础设施团队不堪重负，才有了"把治理搬出进程"的动机。**小规模团队根本感受不到这个痛，也就不需要网格**。

## 2. sidecar 做了什么：iptables 劫持与 localhost

sidecar 模式把治理 SDK 拆成独立进程：

```text
┌────────────── Pod ──────────────┐    ┌────────────── Pod ──────────────┐
│  ┌────────┐      ┌────────────┐  │    │  ┌────────┐      ┌────────────┐  │
│  │ 业务容器 │ ───▶ │ sidecar    │ ──────▶ │ 业务容器 │ ◀─── │ sidecar    │  │
│  │ (零治理  │ 请求 │ (envoy)    │  │    │  │  代码)   │      │ (envoy)    │  │
│  │  代码)   │      │ 发现/熔断/  │  │    │  └────────┘      │ LB/重试/   │  │
│  └────────┘      │ trace/mTLS │  │    │                  └────────────┘  │
│                  └────────────┘  │    └──────────────────────────────────┘
└──────────────────────────────────┘
     业务只连 localhost; 出网流量被 sidecar 拦截代理
```

**流量的两条路**：
- **显式代理**：业务把出网地址写成 `localhost:15001`（sidecar 监听）——业务代码"知道" sidecar 存在；
- **透明劫持**（istio 默认）：iptables 规则把 Pod 的全部出网流量改道到 sidecar——**业务代码完全无感知**（连"我在网格里"都不知道，存量服务零改造接入）。

**mTLS 的免费午餐**：sidecar 之间的流量自动双向 TLS（证书轮换由控制面托管）——**业务代码零加解密逻辑，全链路加密白送**。这与 `notes/nginx/04` 的"TLS 终止在边缘"是同一哲学的推进：nginx 把 TLS 从 web 应用剥离，sidecar 把 mTLS 从**所有**服务剥离——**加解密是基础设施的事，业务只管明文**。

**同一思想的其他应用**（sidecar 是个通用模式，不只是网格）：DaemonSet 日志收集（每个节点旁挂个日志 agent）、Dapr（能力 sidecar）——**"把横切能力做成邻居进程"** 是云原生时代的基础设施设计单元。

## 3. istio 架构：控制面与数据面

```text
┌─────────────────── 控制面 istiod ───────────────────┐
│  Pilot:   路由规则/灰度策略 → 下发给所有 envoy        │
│  Citadel: 证书签发/轮换（mTLS 的 CA）                │
│  Galley:  配置校验                                    │
└──────────────────┬───────────────────────────────────┘
                   │ xDS 协议（配置下发, watch 语义）
     ┌─────────────┼─────────────┐
     ▼             ▼             ▼
  envoyPod-1    envoyPod-2    envoyPod-3   ← 数据面: 每实例一个, 只管执行
```

**控制面/数据面分离**——这个母题在本模块出现第三次：

| 篇 | 控制面 | 数据面 |
|---|---|---|
| 02 配置中心 | 配置中心（watch 推送） | 实例的 atomic 快照 |
| 04 网关 | 路由表（配置中心/注册中心） | 网关转发引擎 |
| 06 网格 | istiod（xDS 下发规则） | 每个 envoy（执行路由/熔断/mTLS） |

**分离的通用收益**：①执行面无状态可任意扩缩（envoy 挂了随 Pod 重建）；②**策略变更只改控制面**（灰度规则热更，业务零发版）；③执行与决策解耦，各自独立演进。**xDS 下发的就是 04 篇那张路由表 + 03 篇的熔断参数**——网格没有发明新治理能力，只是把这些能力的"居住地"换了。

**排障视角的代价**：以前查一个调用失败看两方服务日志；现在要查 sidecar 版本、envoy 配置 dump、istiod 下发记录、xDS 是否一致——**故障域多了一层，排障心智负担真实增加**。这不是免费的架构，是换来的。

## 4. SDK vs sidecar：完整 trade-off 表

| 维度 | SDK 模式（kitex/Dubbo/gRPC 拦截器） | sidecar 模式（envoy/istio） |
|---|---|---|
| 多语言 | 每语言一套 SDK（N 份维护成本） | **一份基础设施，语言无关** |
| 升级 | 全公司发版跟进 | **重启/滚动 sidecar 即可** |
| 侵入性 | 业务进程内（线程/内存/语义渗入） | **进程外，零改造接入**（iptables 透明劫持） |
| 延迟 | **进程内调用，零额外跳** | 每请求 **+2 跳**（client/server 各一 sidecar, ~1-2ms） |
| 资源 | 无额外进程 | 每 Pod **+一个容器**（内存/CPU 开销, 通常 0.1~0.5 核） |
| 功能粒度 | **可深入业务语义**（按方法重试、业务感知的降级） | 请求级别（L7 元数据, 深度业务逻辑够不着） |
| 排障 | 一处看代码 | 多一层盒子（envoy 配置/版本/xDS） |
| 成熟案例 | 字节 kitex、阿里 Dubbo | Google/IBM/爱奇艺等中大厂 |

**决策树**（把 trade-off 收敛成选择）：

```text
语言数 ≥ 3？                 → sidecar 的多语言税优势成立
服务数几百+、治理策略高频演进？ → SDK 升级税不可忍受
延迟极度敏感（P99 <10ms 预算紧）？ → 两跳 sidecar 是硬伤, 慎重
业务需要方法级/语义级治理？     → SDK 粒度不可替代
→ 中间地带现实解: SDK 做薄（只留连接管理与拦截器）, 治理策略尽量外移
```

**国内现状参考**：大厂多为"厚 SDK + 控制面"路线（kitex + 字节自研控制面，把 SDK 升级税用内部基建消化），istio 全面铺开的以中大厂和多云环境为主——**sidecar 的收益要用规模和语言多样性来兑现，规模不够就是纯成本**。

## 5. 与前五篇的对照表

| 治理能力 | 住 SDK 时的位置 | 住网格时的位置 |
|---|---|---|
| 服务发现（01） | 客户端名单缓存+LB | envoy 的 cluster/endpoint（xDS 下发） |
| 配置热更（02） | 配置 SDK + atomic 快照 | 策略下发走 istiod（xDS）, 应用配置仍走配置中心 |
| 熔断限流（03） | 进程内熔断器+令牌桶 | envoy 的 outlier detection / local rate limit |
| 网关灰度（04） | 网关的路由表 | VirtualService 路由规则（网格内每跳都能灰度, 粒度更细） |
| 可观测（05） | OTel SDK 埋点 | envoy 自动生成 span/metrics（业务仍需自定义属性） |

**读法**：网格把 01/03/04 的"传输层治理"整体搬走；02 和 05 是**部分搬走**（应用级配置和业务语义的 trace 属性仍需 SDK）。**这就是"服务网格 intro"的准确边界：它重组了前五篇的居住形态，没有取代业务逻辑里的任何判断**。

## 6. 面试高频

**Q1：服务网格是什么？解决什么问题？**
把治理逻辑（发现/熔断/重试/mTLS）从业务进程的 SDK 搬到旁路进程（sidecar/envoy），应用零改造。解决 SDK 模式三税：多语言重写、升级推动全量发版、治理逻辑侵入业务进程。本质是"治理能力的基础设施化"。

**Q2：sidecar 怎么拦截流量的？**
透明劫持：iptables 规则把 Pod 出网流量改道到 sidecar 端口，业务无感知（存量零改造）；或显式代理（业务连 localhost）。sidecar 间自动 mTLS，业务代码零加解密。

**Q3：istio 架构？**
控制面 istiod（Pilot 下发路由/熔断规则，Citinel 签发证书）+ 数据面 envoy（每 Pod 一个，执行转发）。xDS 协议下发配置——控制面/数据面分离，执行无状态、策略热更不发版。

**Q4：SDK 和 sidecar 怎么选？**
看三税是否成立：语言≥3、服务数百+、治理高频演进——成立则 sidecar 兑现收益；延迟极敏感（两跳 sidecar 是硬伤）或需要方法级业务语义治理则 SDK 不可替代。中间解：薄 SDK + 策略外移（国内大厂主流）。规模不够，网格就是纯成本。

**Q5：服务网格的性能代价？**
每请求多两跳（client/server sidecar 各一跳，1-2ms 级）+ 每 Pod 一个容器的资源开销（0.1~0.5 核）+ 排障多一层盒子。用运行时成本换工程组织成本——延迟预算紧的系统要慎重。

**Q6：sidecar 模式还在哪些地方出现？**
日志收集 DaemonSet（节点旁挂 agent）、Dapr（能力 sidecar）、云数据库 proxy（分库分表代理）——"横切能力做成邻居进程"是云原生基础设施的设计单元，网格只是它最重的应用。
