# Go 服务埋点实战：埋点是热路径代码

> **核心认知：** 埋点代码运行在**每个请求的关键路径上**，是全世界执行次数最多的代码之一。这决定了它的两条铁律：①**成本必须是 O(1) 且无锁**（一次 `atomic.AddUint64`，绝不能是加锁、I/O、字符串拼接、map 增删）；②**绝不能影响业务**（panic 要吞掉，异常要兜底，监控把服务搞挂是不可饶恕的）。理解这一点，你就能自己判断一个埋点方案的好坏——**凡是让请求路径上多一次内存分配、多一次锁、多一次字符串拼接的设计，都是错的**。

前置知识：[07](07-指标体系与数据模型.md)（四类指标、基数）、`notes/golang/07`（sync/atomic）、`notes/golang/09`（内存与 GC）。

## 1. 埋在哪：中间件是唯一正解

**HTTP 服务的 RED 指标一律在中间件里埋，业务代码零感知**：

```go
func MetricsMiddleware(reg *registry, next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        rec := &statusRecorder{ResponseWriter: w, status: 200}
        next.ServeHTTP(rec, r)                       // 业务代码干净
        d := time.Since(start).Seconds()
        route := routePattern(r)                     // 必须是 /user/{id} 不是 /user/123
        reg.requests.With(route, r.Method, itoa(rec.status)).Inc()
        reg.duration.With(route).Observe(d)
    })
}
```

**WHY 中间件而不是散在业务代码里**：①**不遗漏**——新增接口自动被覆盖，靠人记得在每个 handler 里写埋点一定会漏；②**不改业务**——业务代码里混埋点是典型的横切关注点污染（04 篇网关的同一个原则）；③**统一语义**——延迟的起止时刻、状态码的判定口径全服务一致。

**业务指标才在业务代码里埋**（下单量、支付金额、缓存命中率），且同样遵守 O(1) 纪律。

**`/metrics` 端点单独开端口还是复用？** 生产建议**复用业务端口但路径隔离**（`/metrics`），并在网关/安全组层禁止外部访问。理由是省一个端口和一套生命周期管理；反方观点（独立管理端口 `127.0.0.1:9090`）在需要严格网络隔离时更干净——**取舍看你的网络策略，不是技术优劣**。

## 2. RED 三件套的最小实现

不用 client_golang，一个最小实现就是这些（完整版见 `experiments/10_middleware.go`）：

```go
// Counter: 只增, 用 atomic.AddUint64
type counter struct{ v uint64 }
func (c *counter) Inc() { atomic.AddUint64(&c.v, 1) }
func (c *counter) Get() float64 {
    return math.Float64frombits(atomic.LoadUint64(&c.v))  // 注意: 这是 float64 位模式的原子读
}

// Gauge: 可增可减, 同样原子
type gauge struct{ bits uint64 }
func (g *gauge) Set(f float64) { atomic.StoreUint64(&g.bits, math.Float64bits(f)) }
func (g *gauge) Add(f float64) { /* CAS 循环 */ }

// Histogram: 分桶 + sum + count
type histogram struct {
    counts []uint64   // len(buckets), 累计桶
    sumBits uint64
    count   uint64
}
func (h *histogram) Observe(v float64) {
    for i, ub := range h.buckets {          // 找第一个 >= v 的桶, 之后全部 +1（累计语义）
        if v <= ub { atomic.AddUint64(&h.counts[i], 1) }
    }
    atomicAddFloat(&h.sumBits, v)
    atomic.AddUint64(&h.count, 1)
}
```

**四个必须做对的细节**：

1. **Histogram 桶是累计的**：`Observe(0.3)` 要让所有 `le >= 0.3` 的桶都 +1，不是只给命中的那个桶 +1。
2. **`+Inf` 桶必须有**：它恒等于 `count`。
3. **`Observe` 里不能有分配**：预分配桶数组，传入的 label 值要复用（见第 6 节）。
4. **`Collect()` 时做快照，不是实时引用**：抓取时把每个计数器的当前值读出来组成快照再序列化——**否则输出过程中值还在变，同一份输出里 `sum` 和 `count` 不一致**。

## 3. 并发安全：为什么必须是原子操作

**每秒几万次的计数器，用 mutex 会怎样**：锁竞争 → goroutine 排队 → P99 延迟上升 → 监控系统成了延迟来源。所以：

| 场景 | 做法 |
|---|---|
| Counter / Gauge（数值） | `atomic.AddUint64` / CAS 循环 |
| Histogram 各桶 | 每个桶一个 `atomic.AddUint64`（桶之间不需要一致） |
| **label 组合的查找** | **sync.Map 或 map+RWMutex，但必须只在首次出现时写一次，之后走无锁读** |

**label 查找的性能关键**：`With(route, method, status)` 每次请求都要根据三个字符串找到对应的 series 对象。如果每次都加锁查 map，热路径上就多了一把全局锁。

**正确做法（两级缓存）**：

```go
// 热路径: 先无锁读 atomic.Pointer 指向的只读快照
// 冷路径: 未命中才加锁创建, 然后整体换快照（02 篇配置中心的同款思路）
if c := atomic.LoadPointer(&m.series); c != nil {
    if s, ok := (*snapshot)[key]; ok { return s }   // 99.99% 的请求走这里
}
return m.getOrCreate(key)   // 首次出现才加锁
```

**这是 02 篇 atomic.Pointer 换快照思路的又一次复用**——写少读多的热数据结构，一律"无锁读 + 整体换快照"。

## 4. 运行时指标：Go 服务的自带仪表

用 `runtime` 包零成本拿到（**不需要额外埋点，开箱即用**）：

| 指标 | 来源 | 看什么 |
|---|---|---|
| `go_goroutines` | `runtime.NumGoroutine()` | **持续上涨 = 协程泄漏**（Go 服务最常见的死法） |
| `go_memstats_heap_inuse_bytes` | `runtime.ReadMemStats` | 堆占用；**与 `heap_idle` 对比看是否该还内存给 OS** |
| `go_gc_duration_seconds` | `memstats.PauseTotalNs` 增量 | GC 暂停；**P99 延迟毛刺的常见元凶** |
| `go_threads` | `runtime/pprof.Lookup("threadcreate")` | 线程数暴涨 = 系统调用阻塞 |

**GC 暂停与 P99 毛刺的关系**（Go 特有、面试常考）：Go 的 GC 暂停是亚毫秒级的，但如果**分配速率极高**（每秒几百 MB），GC 会更频繁、单次暂停变长，表现为 P99 延迟周期性毛刺。**判断方法**：把 `go_gc_duration_seconds` 和 P99 延迟画在同一块板上，看毛刺是否对齐。

**MemStats 的坑**：`runtime.ReadMemStats()` 会 **STW（stop-the-world）**——**不要在每次抓取之外频繁调用**。抓取一次几十微秒可以接受，放进请求路径是灾难。

## 5. 业务埋点：label 的纪律

```go
// ✗ 灾难: 用户 ID 进 label → series 爆炸（07 篇第 4 节）
ordersTotal.With("user_id", userID).Inc()

// ✓ 正确: 只用低基数枚举维度
ordersTotal.With("channel", ch, "pay_type", pt).Inc()

// ✓ 明细走日志/链路: trace_id 挂到 exemplar, 不是 label
```

**label 取值数上限的经验值**：单个 label 的取值数控制在**几十以内**（status、method、route 模式、env、region）。**任何取值数可能随时间无限增长的字段（ID、路径参数、错误 message、IP），一律不能做 label。**

**路径归一化是必做项**：`/user/123` 和 `/user/456` 必须归一成 `/user/{id}`。框架层做（gin/hertz 的 `ctx.FullPath()` 直接给路由模板），**不要自己字符串切割**。

## 6. 性能红线与避坑

| 坑 | 后果 | 做法 |
|---|---|---|
| 埋点里做字符串拼接/格式化 | 每次请求一次分配 → GC 压力 | label 值用常量或从路由模板取 |
| 埋点里加锁 | 锁竞争 → P99 上升 | 原子操作 + 无锁快照 |
| 埋点里做 I/O / 远程上报 | 请求被拖慢 | 只写内存，等 Prometheus 来拉（pull 的好处） |
| 埋点 panic 未兜底 | **监控把业务打挂** | `defer recover()`，监控失败只记日志不影响业务 |
| 每次请求都 `new` series 对象 | 内存泄漏 + GC | `getOrCreate` 缓存，series 集合有界 |
| 高基数 label | 打挂 Prometheus | 值域收敛为枚举 |

**一条总原则**：**埋点失败永远不该影响业务请求**。计数器加不上去，最多是监控数据少一点；把请求打挂，是监控系统造的孽。

## 7. 与 trace 联动：exemplar

**问题**：指标告诉你"P99 是 850ms"，但**是哪些请求慢**？指标里没有明细（它只有数字）。

**解法是 exemplar**：在 Histogram 的某个桶上挂一个 `trace_id`（一小段附加数据），Grafana 上点这个点就能直接跳到对应的 trace。

```text
http_request_duration_seconds_bucket{le="1.0"} 1000 # {trace_id="a1b2c3"} 0.85
                                                    ↑ exemplar: 一个样本 + 一个 trace_id
```

**WHY 这比"把 trace_id 做成 label"好一万倍**：trace_id 做成 label 会让 series 数等于请求数（高基数灾难，07 篇第 4 节）；exemplar 是**挂在样本上的附加信息，不产生新的 series**——**既拿到了下钻能力，又不付出基数代价**。

**这就是三支柱在指标侧的汇合点**：metrics 报警 → 点 exemplar → tracing 定位 → 用 trace_id 查 logging 取证（05 篇的漏斗，链路在这一步被打通）。

## 8. 面试高频

**Q1：Go 服务怎么接 Prometheus？**
HTTP 中间件里埋 RED（不需要业务代码参与），另起 `/metrics` 端点输出文本。计数器用 `atomic` 无锁累加（热路径不能加锁），`Collect()` 时做快照再序列化保证 sum/count 一致。运行时指标用 `runtime` 包零成本拿（goroutine 数、GC 暂停、堆占用）。

**Q2：为什么埋点必须用原子操作而不是 mutex？**
埋点在每个请求的关键路径上，每秒几万次；加锁会造成锁竞争、goroutine 排队、P99 上升——监控组件自己变成延迟来源。label 查找则走"atomic.Pointer 只读快照 + 未命中才加锁创建"，与配置中心换快照同款思路。

**Q3：Go 服务最该监控的运行时指标？**
`go_goroutines`（持续上涨 = 协程泄漏，Go 服务最常见死法）、`go_gc_duration_seconds`（GC 暂停，P99 毛刺元凶——与 P99 画同一块板看是否对齐）、堆占用。注意 `runtime.ReadMemStats()` 会 STW，只能在抓取时调用，不能进请求路径。

**Q4：埋点有哪些性能红线？**
六条：不做字符串拼接/格式化（避免分配）、不加锁（用 atomic）、不做 I/O（pull 模式只写内存）、必须 recover 兜底（监控绝不能打挂业务）、series 对象要缓存复用（有界）、label 值域收敛为枚举（防高基数）。

**Q5：为什么 label 不能用 user_id / 请求路径参数？**
series 数 = 各 label 取值数的乘积，user_id 这种无限增长的维度会让 series 爆炸（千万级 series ≈ 数十 GB 内存 + 查询全废）。路径必须归一成 `/user/{id}`（用框架给的路由模板），错误 message、IP 同理不能用。

**Q6：指标怎么和链路打通？**
用 exemplar：在 Histogram 桶样本上挂 trace_id，Grafana 点一下直接跳到对应 trace。不能把 trace_id 做成 label（会制造高基数灾难）——exemplar 是挂在样本上的附加数据，不产生新 series。这正是三支柱的汇合点：metrics 报警 → exemplar → tracing 定位 → trace_id 查日志取证。

**Q7：/metrics 端点要不要单独端口？**
生产常见做法是复用业务端口做路径隔离（`/metrics`）并在网关/安全组禁止外部访问，省一套生命周期管理；需要严格网络隔离时用独立管理端口绑 `127.0.0.1`。取舍看网络策略，不是技术优劣。

**Q8：Collect 时为什么要做快照？**
抓取过程中业务仍在跑，如果边读边输出，同一份输出里 `_sum` 和 `_count` 可能来自不同时刻，算出的平均延迟是错的。先读一遍所有值组成快照，再序列化。
