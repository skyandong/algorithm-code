# 熔断降级限流：稳定性的三板斧

> **核心认知：** 三个词经常被混着说，定位完全不同：**限流保自己**（入口处控制并发，宁可拒绝也不排队——队列才是真正的杀手）；**熔断保下游**（下游故障时快速失败，别拿重试把濒死的下游打死——"重试风暴"是无数雪崩的第一因）；**降级保核心**（资源不够时扔掉次要功能，有损服务好过全站不可用）。本篇的重头戏是**熔断器三态机**：closed（正常放行，统计错误率）→ open（错误率超阈值，直接拒绝一切请求）→ half-open（放一个探活请求试探下游复活没有）——它是 `notes/design-pattern/04` 状态机的教科书应用：**转移表 + 纯函数判定，状态机本身不执行任何副作用**。配上限流算法四件套（计数器/滑动窗口/漏桶/令牌桶），这一篇就是微服务稳定性的全部家当。

前置知识：状态机模式（`notes/design-pattern/04`）、环形计数器（`engineering/ringcounter`）、nginx 限流三件套（`notes/nginx/03`）、雪崩与重试（`notes/system-design/08` §2.3）。

## 1. 三板斧的定位区分

```text
                    请求 → [限流] → 业务逻辑 → 调下游 → [熔断(客户端侧, 针对下游)]
                              │                       │
                     超量直接拒绝              下游故障快速失败
                     （保自己不被压垮）        （保下游不被打死）
                              │
                    资源不够 → [降级] 扔次要功能（推荐位返回兜底数据）
                              （保核心链路存活）
```

| | 保护对象 | 触发条件 | 动作 | 生效位置 |
|---|---|---|---|---|
| 限流 | **自己** | 并发/QPS 超容量 | 拒绝（429）或排队 | 入口/网关 |
| 熔断 | **下游** | 错误率/慢调用率超阈值 | 快速失败，定期探活 | 调用方（客户端侧） |
| 降级 | **核心链路** | 资源紧张/依赖故障 | 有损服务（兜底值/砍功能） | 业务层 |

**WHY 熔断发生在"调用方"而不是"被调方"**：下游已经故障了，它自己没能力拒绝你（进程僵死时连 RST 都发不出）；只有**调用方**能单方面停止施压。这是"谁造成压力谁负责停止"的分布式伦理。

**重试风暴**（熔断存在的核心理由）：下游超时 → 调用方重试 3 次 → 下游收到的请求量×4 → 更慢 → 更多超时 → 更多重试……**重试在故障场景下是乘法器，熔断就是切断这个乘法的闸**。配套纪律：重试要有**预算**（总重试次数上限）+ 退避（exponential backoff + jitter，和 08 篇 TTL 抖动同构）。

## 2. 熔断器三态机：完整实现规格

```text
        ┌─────────┐ 错误率 ≥ 阈值(如50%) 且 请求数 ≥ 最小样本(如20) ┌─────────┐
        │ CLOSED  │ ────────────────────────────────────────────▶│  OPEN   │
        │ 正常放行 │                                                │ 全部拒绝 │
        └─────────┘ ◀───────────────────────────── 探活成功 ──────└─────────┘
            ▲          half-open 放行 N 个探活请求                    │ 冷却期
            │          全部/多数成功 → 恢复 CLOSED                    │ 到达(如30s)
            │          失败 → 回 OPEN（重置冷却期）                   ▼
            │                                             ┌─────────────┐
            └─────────────────────────────────────────────│  HALF-OPEN  │
                 探活请求失败                               │  限流探活    │
                                                          └─────────────┘
```

**状态机实现的纪律**（`notes/design-pattern/04` 的三要素）：

**① 转移表驱动，不写 if-else 面条**：

```go
// 状态转移: (当前状态, 事件) → 目标状态 —— 纯函数, 无副作用
func next(s state, e event) state {
    switch s {
    case closed:
        if e == errRateExceeded { return open }
    case open:
        if e == cooldownElapsed { return halfOpen }
    case halfOpen:
        if e == probeSucceeded { return closed }
        if e == probeFailed    { return open }
    }
    return s // 默认: 状态不变
}
```

**② 副作用与转移分离**：状态机只回答"该不该变"，放行/拒绝/统计由外层执行——状态机保持纯函数，可单测穷举（3 状态×4 事件=12 个 case 全覆盖）。

**③ 关键参数与语义**：

| 参数 | 典型值 | WHY |
|---|---|---|
| 错误率阈值 | 50% | 不是 1%——网络抖动的背景错误率就有 1~5%, 太灵敏会频繁误熔断 |
| 最小样本数 | 20 | 2 个请求错 1 个=50% 错误率? 样本不足不判定, 防小流量误触发 |
| 冷却期 | 30s | 探活频率的倒数——太短则故障期每 30s 放一批炮灰, 太长则恢复慢 |
| half-open 放行数 | 1~N | 放少量探活请求, 全部成功才恢复——防"一波恢复假象" |

**计数器重置的坑**：进入 open 时要**重置滑动窗口**——否则恢复后残留的高错误率样本立刻再次触发熔断（熔断器"卡死"的常见 bug）。

## 3. 滑动窗口：错误率统计的底座

错误率 = 窗口内失败数 / 窗口内总数。窗口怎么选：

```text
固定窗口计数器: 每分钟一个桶, 边界突变（59s 失败 + 61s 失败 = 两个窗口各 50%? ）
               —— 便宜但边界粗糙, notes/nginx/03 的 limit_req 就是这个
滑动窗口:      最近 N 秒的连续视图, 无边界问题
               实现: 环形桶（engineering/ringcounter 同款!）
               每秒一格 × 60 格 = 最近 60s; 查询 = 60 格求和
```

**环形桶实现**（复用 `engineering/ringcounter` 的结构）：

```go
// 60 个桶, 每秒滚动一格; 每桶记 (总数, 错误数)
type slidingWindow struct {
    buckets []bucket // ring
    cursor  int      // 当前秒对应的桶
}
// 写入: 找到当前桶 → total++ / err++（按结果）
// 查询: 遍历 60 格求和 → 错误率 = Σerr/Σtotal
// 滚动: 每秒 cursor+1, 路过的桶清零（新的一秒从零开始）
```

**WHY 不用精确的环形时间线**（每个请求带时间戳、查询时过滤）：请求量 10 万/s 时每次查询要过滤 60 万时间戳——**近似换性能**，秒级桶的粒度对 50% 阈值的判定完全够用。又是那句话：**先问精度需求，再选实现**。

并发注意：桶的 total/err 计数用 atomic 或每请求加锁——统计路径不能成为新的瓶颈（理想是 lock-free 计数 + 定期快照读取）。

## 4. 限流算法四件套

| 算法 | 原理 | 优点 | 缺点 | 典型实现 |
|---|---|---|---|---|
| **固定计数器** | 每分钟一个计数器，超了拒绝 | 最简单 | **边界突刺**：59.9s 和 60.1s 各放满额度=2 倍瞬时流量 | 简单后台任务 |
| **滑动窗口** | 最近 N 秒计数（环形桶） | 消除边界 | 内存与精度 trade-off | 03 篇熔断统计同款 |
| **漏桶** | 恒定速率流出，超容量丢弃/排队 | **绝对平滑**的输出速率 | 无法应对合理突发；排队引入延迟 | nginx `limit_req`（无 burst 时） |
| **令牌桶** | 恒速放令牌入桶，请求取令牌，桶满暂存 | **允许突发**（攒的令牌一次用掉）, 主流 | 突发仍可能压垮下游（burst 要配） | Guava RateLimiter、Go `golang.org/x/time/rate` |

**漏桶 vs 令牌桶**（高频考点，一句话记忆）：**漏桶看出口（流出恒定，不许突发），令牌桶看入口（放行可突发，平均恒定）**。

```text
漏桶:   ▓▓▓▓│≈≈≈≈≈│ → 恒速流出     —— 保护"下游的处理节奏"（如调用脆弱的三方接口）
令牌桶: ≈≈≈≈│桶(攒令牌)│ → 有令牌就走 —— 保护"自己的平均容量"（允许短时突发）
```

**和 nginx 限流的对应**（`notes/nginx/03` 的应用层版）：`limit_req rate=100r/s burst=50 nodelay` 本质是**带突发容量的漏桶**——rate 是流出速率，burst 是桶的容量，nodelay 让桶内请求立即处理（行为上像令牌桶）。**网关层限流（nginx）管总量，应用层限流（令牌桶）管细粒度（按用户/按接口）**——两层各司其职。

**分布式限流**：单机限流在多实例下配额要除以实例数（不准，实例数变动就要改配置）；集中式（Redis+Lua 原子扣减）准确但引入网络依赖和单点。实践主流：**单机令牌桶×实例数近似**（简单、无依赖、够用），精确配额场景（如按商户计费）才上 Redis 集中限流。

## 5. 降级：有损服务的艺术

降级 = **主动扔掉次要功能，把资源让给核心链路**：

```text
自动降级（熔断的配套动作）: 下游故障时返回兜底值
    推荐位 → 返回缓存的昨日热门（而非空白）
    风控接口超时 → 放行小额订单（业务风险换可用性, 需业务拍板）
手动降级（运营开关）: 大促前主动关闭"猜你喜欢"、评价区、导出功能
    —— 配置中心的热更新开关（02 篇）就是为这个场景生的
```

**降级的分级预案**（提前演练，不是事发即兴）：

```text
L1 关闭非核心写: 评价/收藏/积分 —— 用户几乎无感
L2 关闭非核心读: 推荐流降级为热门列表 —— 可感知可用
L3 只读模式:     停写保读 —— 电商可以逛不能下单
L4 拒绝服务:     保住账户和支付数据 —— 壮士断腕
```

**WHY 有损优于全站不可用**：可用性的数学（`notes/distributed/01`）：99.9% 的系统=年停机 8.7h；一次全站雪崩一小时就烧光全年预算。降级本质是**预算内可控的损失**换**系统整体存活**——"为了不沉，先扔货物"。

**降级的数据补偿**：被降级丢掉的数据（评价/积分）要**可补偿**——降级期间写 MQ 延迟处理或事后对账补录。降级方案设计时就要回答"恢复后怎么补"，答不出补法的降级是数据丢失。

## 6. 面试高频

**Q1：限流、熔断、降级的区别？**
限流保自己（入口超量拒绝）、熔断保下游（调用方快速失败防重试风暴）、降级保核心（扔次要功能换存活）。三者常联动：熔断触发时自动降级（返回兜底值），大促前手动降级配合限流保核心。

**Q2：讲一下熔断器原理。**
三态机：closed 统计错误率（滑动窗口+最小样本数）→ 超阈值转 open 全拒 → 冷却期后 half-open 放探活请求 → 成功恢复 closed、失败回 open。关键参数：错误率阈值 50%（防背景错误率误触发）、最小样本 20（防小流量误判）、冷却期 30s（探活频率）。进入 open 要重置窗口，否则恢复后残留样本导致卡死。

**Q3：为什么熔断在调用方实现？**
下游故障时连拒绝的能力都没有（进程僵死），只有调用方能单方面停止施压。重试在故障期是乘法器（下游超时→重试 3 次→流量×4→更慢→更多重试），熔断是切断这个乘法的闸。

**Q4：漏桶和令牌桶的区别？**
漏桶看出口：流出恒速不许突发——保护下游节奏（脆弱三方接口）；令牌桶看入口：平均恒速允许突发（攒的令牌一次用）——保护自己的容量。nginx limit_req 的 rate+burst+nodelay 是带突发容量的漏桶变体。

**Q5：滑动窗口怎么实现？**
环形桶：60 格每秒滚动一格，每桶记(总数,错误数)，查询=求和。秒级粒度换性能（不过滤每请求时间戳）——和 engineering/ringcounter 同构。fixed window 的边界突刺（2 倍瞬时流量）是它的存在理由。

**Q6：单机限流和分布式限流怎么选？**
默认单机令牌桶×实例数（简单无依赖，近似够用）；精确配额（计费/商户限额）才上 Redis+Lua 集中限流——准确但引入网络依赖和中心点。先问"配额精度值多少钱"再选架构。

**Q7：降级方案怎么设计？**
分级预案（L1 关非核心写→L4 拒绝服务保数据）提前演练；自动降级配熔断（兜底值返回），手动降级靠配置中心开关（热更新）；每个降级项要能回答"数据怎么补偿"（MQ 延迟处理/对账补录）——答不出补法的降级是数据丢失。
