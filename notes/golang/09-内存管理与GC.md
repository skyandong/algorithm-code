# 内存管理与 GC

> **核心认知：** Go 的内存管理是三级流水线：编译器用逃逸分析决定对象进栈还是进堆，堆内走 TCMalloc 思想的三层分配器（mcache 无锁 → mcentral 加锁 → mheap 页堆），垃圾由并发三色标记 + 混合写屏障的 GC 回收。写 Go 代码的性能直觉基本可以浓缩成一句话：**少分配（复用/预分配/消灭逃逸），分配也走小对象快路径**；内存问题排查的两大抓手是 `-gcflags="-m"`（为什么分配在堆）和 `GODEBUG=gctrace=1`（GC 到底慢在哪）。

本文按 Go 1.26 语义说明；版本分界处单独标注。

---

## 1. 逃逸分析：栈还是堆，编译期就定了

栈分配几乎免费（移动栈指针），堆分配要过分配器、将来还要 GC 扫描。编译器对每个变量做逃逸分析：**能否证明它的生命周期不超出当前栈帧**。证明不了 → 堆。

实战命令：

```bash
go build -gcflags="-m" ./experiments/          # 查看逃逸判定
go build -gcflags="-m -l" ./experiments/       # -l 禁用内联，判定更稳定
```

输出示例（节选自本篇实验代码的实际输出）：

```text
experiments/09_gc_memory.go:65:2:  moved to heap: x                # return &x
experiments/09_gc_memory.go:72:9:  func literal escapes to heap     # 闭包捕获
experiments/09_gc_memory.go:77:11: make([]int, n) escapes to heap   # 动态长度
experiments/09_gc_memory.go:47:26: 1024 escapes to heap            # interface 装箱
experiments/09_gc_memory.go:92:11: make([]int, 4) does not escape   # 栈上
```

常见逃逸场景：

| 场景 | 判定 | WHY |
| --- | --- | --- |
| 返回局部变量指针 `return &x` | 逃逸 | 栈帧销毁后 x 还要被使用 |
| 闭包捕获 `x` 并返回 | 逃逸 | x 的生命周期随闭包延长 |
| `make([]T, n)`，n 是变量 | 逃逸 | 编译期不知道大小，栈上无法预留 |
| 发送指针到 channel | 逃逸 | 接收方在另一个 goroutine |
| `fmt.Println(x)` 等 interface 参数 | 装箱逃逸 | 值要转成 `any` 存到堆上的接口对象 |
| 在函数内用完的固定大小对象 | 栈 | 生命周期封闭在栈帧内 |
| 传值拷贝且不外泄 | 栈 | 拷贝本身在栈上发生 |

两个容易忽略的细节：

- interface 参数是否逃逸，取决于**被调用方是否泄漏该参数**：`func f(v any) int { return v.(int) }` 的 `v` 不泄漏 → 调用方传 1024 不逃逸；`fmt` 系列（`Println`/`Sprintf` 等）的参数是 leaking param → 装箱逃逸。本篇实验代码特意把参数存进全局变量来演示泄漏路径。另外 0~255 的小整数有 runtime 静态缓存（`staticuint64s`），运行时不新分配——但逃逸分析照样报 escapes；
- `escape` 不一定是坏事。栈空间有限（goroutine 栈要增长就要拷贝），把热点路径之外的大对象留在堆上、让代码保持简单，常常是正确的取舍。**只优化 profiling 证明热的路径**。

## 2. 分配器：mcache → mcentral → mheap（TCMalloc 思想）

堆对象按大小走不同路径：

```text
对象大小分类（sizeclass，约 67 档：8B、16B、24B…32KB）
  │
  ├─ < 16B 且不含指针 ──→ tiny allocator（多个微小对象合并进一个 16B 块）
  ├─ 16B ~ 32KB ────────→ sizeclass 路径
  └─ > 32KB（大对象）────→ 直接从 mheap 分配整页

sizeclass 路径的三级结构：

G 申请 64B
  │
  ▼
mcache（P 本地，无锁）────── 命中 → 返回（绝大多数分配止步于此）
  │ 本地对应 span 无空闲位
  ▼
mcentral（按 sizeclass 全局，加锁）── 从 mheap 批量拿一个 span 补给 mcache
  │ 也没有
  ▼
mheap（全局页堆，8KB 页）────── 向 OS 申请/复用内存（arena 管理）
```

WHY 这样分层（TCMalloc 的核心思想）：

- mcache 绑定 P（见笔记 05），本 P 的分配**零锁零竞争**——Go 高并发分配快的根源；
- mcentral 按 sizeclass 拆分，锁竞争被 67 把锁分摊，而不是一把全局锁；
- span（连续页 + 空闲位图）作为 mcache↔mcentral↔mheap 的流转单位，补货是批量的，摊薄加锁成本。

实战认知：并发分配很重时，最优解往往不是研究 sizeclass 对齐，而是**减少分配次数**（见 §6 sync.Pool）。

## 3. 栈内存：2KB 起步，按需翻倍

- 初始 2KB（Go 1.4 起），`go func(){}` 的固定成本极低；
- 栈不够用时 `morestack`：分配一块 **2 倍大小的新栈 → 拷贝内容 → 重定向指向旧栈的指针**（Go 1.3 起的连续栈；更早的分段栈有"热分裂"问题——刚好在边界反复调用会反复扩缩）；
- 收缩：GC 周期中检查各 G，**用量低于总量的 1/4 时减半**，下限 2KB；正在系统调用中的 G 不收缩（栈可能正被 M 使用，不能移动）。

```go
// 递归深度大 → 栈增长多次 → 每次都是"分配新栈+拷贝"
func deep(n int) int {
	if n == 0 { return 0 }
	var buf [4096]byte // 占住栈空间
	buf[0] = byte(n)
	return int(buf[0]) + deep(n-1)
}
// 首次触底后栈固定在最大值；goroutine 空闲时由 GC 收缩回去
```

## 4. GC：三色标记 + 混合写屏障

### 4.1 三色抽象

| 颜色 | 含义 |
| --- | --- |
| 白 | 未被扫描；标记结束后仍为白 → 垃圾 |
| 灰 | 自己已标记，但引用的子对象还没扫完 |
| 黑 | 自己和子对象都已扫完 |

标记从根（全局变量、各 goroutine 栈）出发，把可达对象逐步染黑；并发标记期间用户代码还在改指针，靠写屏障维持不变式：

- **强三色不变式**：黑对象不能指向白对象；
- **弱三色不变式**：黑可以指白，但该白必须有别的灰路径可达（不会被漏标）。

漏标 = 存活对象被当垃圾回收（不可接受的内存错误）；多标 = 浮动垃圾（下一轮再收，可接受）。

### 4.2 为什么需要写屏障：两种破坏

```text
① 插入破坏（黑→白建新边，白对象没被扫到）
   黑A.s = 白C     A 已扫完不会再扫，C 若无灰引用 → 被误回收

② 删除破坏（灰→白的边被切断）
   灰B.f = nil      B 的扫描可能拿不到 C，若 C 只被 B 引用 → 误回收
```

- Dijkstra 插入屏障（Go 1.5~1.7）：写入指针时把**新目标**置灰。只做堆，**栈上的写不做屏障**（太热）→ 栈要标黑，代价是标记结束前要 STW 重新扫描所有栈，STW 高达 10~100ms 级。
- Go 1.8 起混合屏障（Yuasa 删除 + Dijkstra 插入）：**堆上每次写指针，旧值和新值都置灰**；栈视为黑、全程免重扫。STW 只剩两个极短窗口（标记开始：开写屏障 + 扫 root；标记结束：收尾 + 关屏障 + 触发 sweep 与栈收缩），典型 **几十~几百 µs，一般 < 1ms**。

### 4.3 一轮 GC 的结构

```text
1. Sweep termination（STW，极短）  结束上轮残余清扫
2. Mark phase（并发）              写屏障开启；后台标记工人（默认 ~25% CPU）+ mutator assist（分配太快的 G 被罚去做标记）
3. Mark termination（STW，极短）   关屏障、算存活堆、触发 sweep 与栈收缩
4. Sweep phase（并发）             按需惰性清扫
```

并发标记期间新分配的对象直接"出生即灰"，不会被漏标；分配速率过高时 GC 用 **assist** 反向施压——分配越狠的 G 被拉去干标记活越多，这也是 GC 慢时吞吐下降的机制。

### 4.4 Go 1.26：Green Tea GC 默认启用

Go 1.25 以 `GOEXPERIMENT=greenteagc` 试用，1.26 转正。**仍是三色并发标记-清除，变的是标记的组织方式**：从逐对象指针追逐（cache 不友好）改为按 8KiB span 页为单位批量扫描（页级广度优先 + 每对象 2bit 元数据），顺序访存让预取器生效；新 CPU 上再用 SIMD 扫页元数据。实测 GC 开销降 10%~40%。退出开关 `GOEXPERIMENT=nogreenteagc`（预计 1.27 移除）。对业务代码零感知——但面试里"Go 1.26 的 GC 变化"是高频新题。

## 5. GOGC 与 GOMEMLIMIT

**GOGC（默认 100）**：相对上一轮标记后的存活堆，允许再增长的比例：

```text
目标堆 = 存活堆 × (1 + GOGC/100)（另计非堆开销修正；有 4MB 最小目标）
```

| 存活堆 | GOGC | 下轮触发点 |
| --- | --- | --- |
| 128MB | 100 | ~256MB |
| 128MB | 400 | ~640MB |
| 128MB | 50 | ~192MB |
| 128MB | off | 永不触发（兜底见下） |

GC 实际触发条件：堆到目标 / 距上轮满 2 分钟（sysmon 强制）/ `runtime.GC()` 手动 / 达到 GOMEMLIMIT。

**GOMEMLIMIT（Go 1.19+）**：runtime 管理总内存（堆 + 栈 + 元数据等）的**软上限**。接近时 GC 提频——本质是"用 CPU 换内存"；若存活集真超限则陷入 thrashing（GC 跑满 CPU）。内置保护：GC 总 CPU 有上限（50%），宁可软限被突破也不会硬死锁，真正的硬顶交给 OOM killer。注意它**不含** cgo 分配、mmap 的文件缓冲等 runtime 之外的内存。

调参取舍（面试高频）：

| 调整 | 收益 | 代价 |
| --- | --- | --- |
| GOGC 调大（200/400/off） | GC 次数少、吞吐高 | 堆峰值高、内存占用大 |
| GOGC 调小（50） | 堆紧凑、省内存 | GC 频繁、CPU 被 GC/assist 吃掉 |
| GOGC 大 + GOMEMLIMIT 兜底 | 吞吐与内存上限兼得 | 软限附近时延迟抖动 |

容器实践常见组合：`GOGC=off GOMEMLIMIT=<limit×80%>`——平时不主动 GC，逼近内存上限才收。

## 6. sync.Pool：每轮 GC 都清空，为什么还值得用

结构：**每个 P 一份本地池**（Get/Put 无锁）+ 全局共享 + Go 1.13 起的 victim 二级缓存（GC 时 primary 整体降级为 victim，下一轮才真正丢弃——相当于清空被摊到两轮，缓解"GC 一过全 miss"的抖动）。

```go
var bufPool = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func render(w io.Writer, data []byte) error {
	buf := bufPool.Get().(*bytes.Buffer)
	defer func() {
		buf.Reset() // 复用前清状态，防止脏数据/引用泄漏到下次使用
		bufPool.Put(buf)
	}()
	buf.Write(data)
	_, err := w.Write(buf.Bytes())
	return err
}
```

WHY 每轮清空还能显著减压：

1. 清空是"不再白送"，不是"立即回收"——本轮内 Get/Put 照常命中；
2. 真正的收益在**分配速率**：高 churn 对象（每请求一个 buffer）从百万次分配降到接近零，GC 触发频率（由分配驱动，见 §5）和标记量双降；
3. 反面教材：往池里塞超大 buffer 会抬高内存驻留，命中越久驻留越久——池大小的上界要想清楚。

清理时机选 GC 的 WHY：池对象常驻等于人为抬高"存活堆"（见 §5 公式），会造成 GC 更频繁；两级 victim 是"复用率 vs 堆目标"的折中。

## 7. GC 慢的三个定位方向

先拿数据：`GODEBUG=gctrace=1 ./app`（对延迟敏感时可只看趋势，不常驻）：

```text
gc 12 @6.234s 3%: 0.058+1.2+0.031 ms clock, 0.46+0.35/2.3/0+0.25 ms cpu,
   47->48->24 MB, 48 MB goal, 0 MB stacks, 0 MB globals, 8 P
```

解读：第 12 轮 @6.234s；GC 累计占 3% CPU；STW 开始 0.058ms + 并发标记 1.2ms + STW 结束 0.031ms；堆 47MB→48MB，标记后存活 24MB，目标 48MB。

三个方向：

| 方向 | gctrace 特征 | 定位手段 | 解法 |
| --- | --- | --- | --- |
| **分配速率高** | GC 轮次密、每轮 heap 涨得快 | `pprof` 的 `alloc_space` 看分配热点 | sync.Pool / 预分配 / 消灭逃逸 / 减少中间对象 |
| **存活对象多** | live（第三个 MB 数）大且不降 | `inuse_space`、前后两份 heap diff、`runtime.NumGoroutine` | 查泄漏：全局 map 只增不减、goroutine 泄漏持有引用、`time.After` 未清理 |
| **标记耗时高** | 并发标记段（中段 ms）长 | `pprof` 看指针密集结构、`gcMarkTermination` 耗时 | 降低指针密度：用索引/slice 替代指针图、值类型数组、拆分大对象 |

注意 STW（前后两段）> 1ms 才值得怀疑（通常 µs 级）；中段长是标记扫描问题；轮次密是分配问题——**先分类，再动手**。

## 8. 面试常见追问速查

| 追问 | 要点 |
| --- | --- |
| GC 触发条件？ | 堆目标 / 2 分钟强制 / `runtime.GC()` / GOMEMLIMIT（§5） |
| 写屏障为什么不上栈？ | 栈写太热；代价是标记开始时把所有栈标黑 + 栈上对象需要保守处理。混合屏障让栈全程免屏障（§4.2） |
| GOGC 调大/调小的取舍？ | 吞吐 vs 堆峰值（§5 表） |
| GOGC=off 会 OOM 吗？ | 不会立刻——GOMEMLIMIT 可兜底；两者都没设才看 OOM killer |
| new 和 make 的区别？ | new(T) 分配并返回 *T（零值）；make 只用于 slice/map/channel，返回初始化后的 T |
| 怎么证明某个对象分配在堆？ | `-gcflags="-m"`；配合 `pprof` alloc_space 看实际流量 |
| `sync.Pool` 什么时候清？ | 每轮 GC（1.13 起经 victim 缓冲一轮，§6） |
| Go 1.26 GC 有什么新东西？ | Green Tea 默认：8KiB 页批量扫描 + SIMD，开销降 10~40%（§4.4） |
