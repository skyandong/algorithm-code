# 内存管理与 GC

> **核心认知：** Go 的内存管理是三级流水线——**逃逸分析**决定对象进栈还是进堆，堆内走三层分配器，垃圾由并发三色标记加混合写屏障回收。性能直觉可以浓缩成一句话：**少分配**（复用、预分配、消灭逃逸）。

本文基于 Go 1.26 的实际行为编写。

## 1. 逃逸分析：栈还是堆，编译期就定了

栈分配几乎免费（移动栈指针），堆分配要过分配器、将来还要 GC 扫描。编译器对每个变量做逃逸分析：**能否证明它的生命周期不超出当前栈帧**。证明不了 → 堆。

实战命令：

```bash
go test -gcflags="-m" -run '^$' ./experiments/      # 查看逃逸判定（只编译，不跑用例）
go test -gcflags="-m -l" -run '^$' ./experiments/   # -l 禁用内联，判定更稳定
```

输出示例（只挑实现部分的记录；断言消息字符串自身的装箱记录已略去）：

```text
experiments/08_gc_memory_test.go:27:2:  moved to heap: x              # return &x
experiments/08_gc_memory_test.go:34:9:  func literal escapes to heap  # 闭包捕获
experiments/08_gc_memory_test.go:39:11: make([]int, n) escapes to heap # 动态长度
experiments/08_gc_memory_test.go:44:25: leaking param: v              # interface 参数外泄
experiments/08_gc_memory_test.go:54:11: make([]int, 4) does not escape # 栈上
```

常见逃逸场景：

| 场景 | 判定 | WHY |
| --- | --- | --- |
| 返回局部变量指针 `return &x` | 逃逸 | 栈帧销毁后 x 还要被使用 |
| 闭包捕获 `x` 并返回 | 逃逸 | x 的生命周期随闭包延长 |
| `make([]T, n)`，n 是变量 | 逃逸 | 编译期不知道大小，栈上无法预留 |
| 发送指针到 channel | 逃逸 | 接收方在另一个 goroutine |
| `fmt.Println(x)` 等 interface 参数 | 装箱逃逸 | 值要转成 `any` 存到堆上的接口对象 |
| 在函数内用完的固定大小对象 | 栈 | 生命周期封闭在栈帧内 |
| 传值拷贝且不外泄 | 栈 | 拷贝本身在栈上发生 |

两个容易忽略的细节：

- interface 参数是否逃逸，取决于**被调用方是否泄漏该参数**：`func f(v any) int { return v.(int) }` 的 `v` 不泄漏 → 调用方传 1024 不逃逸；`fmt` 系列（`Println`/`Sprintf` 等）的参数是 leaking param → 装箱逃逸。本篇实验代码特意把参数存进全局变量来演示泄漏路径。另外 0~255 的小整数有 runtime 静态缓存（`staticuint64s`），运行时不新分配——但逃逸分析照样报 escapes；
- `escape` 不一定是坏事。栈空间有限（goroutine 栈要增长就要拷贝），把热点路径之外的大对象留在堆上、让代码保持简单，常常是正确的取舍。**只优化 profiling 证明热的路径**。

## 2. 分配器：mcache → mcentral → mheap（TCMalloc 思想）

堆对象按大小分流（sizeclass：把尺寸切成若干固定档位）：

```text
对象大小
  │
  ├─ 极小的无指针对象 ───→ tiny allocator（多个微小对象合并进同一块）
  ├─ 一般小对象 ─────────→ sizeclass 档位路径
  └─ 超出档位上限的大对象 → 直接从 mheap 按页分配

sizeclass 路径的三级结构：

G 申请一个小对象
  │
  ▼
mcache（P 本地，无锁）────── 命中 → 返回（绝大多数分配止步于此）
  │ 本地对应 span 无空闲位
  ▼
mcentral（按 sizeclass 全局，加锁）── 从 mheap 批量拿一个 span 补给 mcache
  │ 也没有
  ▼
mheap（全局页堆）────────────── 向 OS 申请/复用内存（arena 管理）
```

WHY 这样分层（TCMalloc 的核心思想）：

- mcache 绑定 P（见笔记 05），本 P 的分配**零锁零竞争**——Go 高并发分配快的根源；
- mcentral 按 sizeclass 档位拆分，锁竞争被分摊到多把锁，而不是一把全局锁；
- span（连续页 + 空闲位图）作为 mcache↔mcentral↔mheap 的流转单位，补货是批量的，摊薄加锁成本。

实战认知：并发分配很重时，最优解往往不是研究 sizeclass 对齐，而是**减少分配次数**（见第 6 节 sync.Pool）。

## 3. 栈内存：初始很小，按需增长

- 初始栈只有 KB 级，`go func(){}` 的固定成本极低；
- 栈不够用时 `morestack`：分配一块 **更大的新栈 → 拷贝内容 → 重定向指向旧栈的指针**（"连续栈"方案）；
- 收缩：GC 周期中检查各 G，**用量远低于容量时缩容**（有下限）；正在系统调用中的 G 不收缩（栈可能正被 M 使用，不能移动）。

```go
// 递归深度大 → 栈增长多次 → 每次都是"分配新栈+拷贝"
func deep(n int) int {
	if n == 0 { return 0 }
	var buf [4096]byte // 占住栈空间
	buf[0] = byte(n)
	return int(buf[0]) + deep(n-1)
}
// 首次触底后栈固定在最大值；goroutine 空闲时由 GC 收缩回去
```

## 4. GC：三色标记 + 混合写屏障

### 4.1 三色抽象

| 颜色 | 含义 |
| --- | --- |
| 白 | 未被扫描；标记结束后仍为白 → 垃圾 |
| 灰 | 自己已标记，但引用的子对象还没扫完 |
| 黑 | 自己和子对象都已扫完 |

标记从根（全局变量、各 goroutine 栈）出发，把可达对象逐步染黑；并发标记期间用户代码还在改指针，靠写屏障维持不变式：

- **强三色不变式**：黑对象不能指向白对象；
- **弱三色不变式**：黑可以指白，但该白必须有别的灰路径可达（不会被漏标）。

漏标 = 存活对象被当垃圾回收（不可接受的内存错误）；多标 = 浮动垃圾（下一轮再收，可接受）。

### 4.2 为什么需要写屏障：两种破坏

```text
① 插入破坏（黑→白建新边，白对象没被扫到）
   黑A.s = 白C     A 已扫完不会再扫，C 若无灰引用 → 被误回收

② 删除破坏（灰→白的边被切断）
   灰B.f = nil      B 的扫描可能拿不到 C，若 C 只被 B 引用 → 误回收
```

- 只做插入屏障（Dijkstra）：写入指针时把**新目标**置灰。只做堆，**栈上的写不做屏障**（太热）→ 栈要标黑，代价是标记结束前要 STW 重新扫描所有栈，STW 会明显变长。
- 当前：混合屏障（Yuasa 删除 + Dijkstra 插入）：**堆上每次写指针，旧值和新值都置灰**；栈视为黑、全程免重扫。STW 只剩两个极短窗口（标记开始：开写屏障 + 扫 root；标记结束：收尾 + 关屏障 + 触发 sweep 与栈收缩），典型在 **µs 量级**。

### 4.3 一轮 GC 的结构

```text
1. Sweep termination（STW，极短）  结束上轮残余清扫
2. Mark phase（并发）              写屏障开启；后台标记工人（占一部分 CPU）+ mutator assist（分配太快的 G 被罚去做标记）
3. Mark termination（STW，极短）   关屏障、算存活堆、触发 sweep 与栈收缩
4. Sweep phase（并发）             按需惰性清扫
```

并发标记期间新分配的对象直接"出生即灰"，不会被漏标；分配速率过高时 GC 用 **assist** 反向施压——分配越狠的 G 被拉去干标记活越多，这也是 GC 慢时吞吐下降的机制。

### 4.4 Green Tea GC（当前默认）

**它仍然是三色并发标记-清除，变的是标记的组织方式——按 span 页批量扫**：标记按页做广度优先，每个对象只留少量元数据，顺序访存让 CPU 预取器能生效；在新 CPU 上还会用 SIMD 扫页元数据。访存变友好之后，GC 开销明显下降。这层实现有退出开关 `GOEXPERIMENT=nogreenteagc`，但对业务代码零感知。

## 5. GOGC 与 GOMEMLIMIT

**GOGC（默认 100）**：相对上一轮标记后的存活堆，允许再增长的比例：

```text
目标堆 = 存活堆 × (1 + GOGC/100)（另计非堆开销修正；另有过小的兜底下限）
```

| 存活堆 | GOGC | 下轮触发点 |
| --- | --- | --- |
| 128MB | 100 | ~256MB |
| 128MB | 400 | ~640MB |
| 128MB | 50 | ~192MB |
| 128MB | off | 永不触发（兜底见下） |

GC 实际触发条件：堆到目标 / 长期没触发时由 sysmon 兜底强制 / `runtime.GC()` 手动 / 达到 GOMEMLIMIT。

**GOMEMLIMIT**：runtime 管理总内存（堆 + 栈 + 元数据等）的**软上限**。接近时 GC 提频——本质是"用 CPU 换内存"；若存活集真超限则陷入 thrashing（GC 跑满 CPU）。内置保护：GC 占用的 CPU 有上限，宁可软限被突破也不会硬死锁，真正的硬顶交给 OOM killer。注意它**不含** cgo 分配、mmap 的文件缓冲等 runtime 之外的内存。

调参取舍：

| 调整 | 收益 | 代价 |
| --- | --- | --- |
| GOGC 调大（200/400/off） | GC 次数少、吞吐高 | 堆峰值高、内存占用大 |
| GOGC 调小（50） | 堆紧凑、省内存 | GC 频繁、CPU 被 GC/assist 吃掉 |
| GOGC 大 + GOMEMLIMIT 兜底 | 吞吐与内存上限兼得 | 软限附近时延迟抖动 |

**容器（k8s）落地**：`GOGC=off + GOMEMLIMIT=目标值`——不按堆增长率触发、只按内存上限触发 GC，适合想固定内存占用的服务：

```yaml
env:
  - name: GOMEMLIMIT
    value: "1800Mi"   # limit 2Gi 的 ~90%：给 cgo、线程栈、页错误留 headroom
```

**必须留 headroom**：GOMEMLIMIT 只算 runtime 管理的内存，不含 cgo/mmap 分配；贴着 cgroup limit 设，容器照样被 OOM 杀。

## 6. sync.Pool 为什么能减 GC 压力

**用法与三条语义（可能随时被丢弃 / 每轮 GC 清空 / 放回前必须 Reset）见 [06-sync并发原语.md](06-sync并发原语.md) 第 6 节**，这里只说它与 GC 的关系。

结构上是**每个 P 一份本地池**（Get/Put 无锁）+ 全局共享 + victim 缓冲——缓冲把「清空」摊到相邻两轮，避免 GC 一过全 miss。

WHY 每轮清空还能显著减压：

1. 清空是「不再白送」，不是「立即回收」——本轮内的 Get/Put 照常命中；
2. 真正的收益在**分配速率**：高 churn 对象（每请求一个 buffer）从百万次分配降到接近零，GC 触发频率（由分配驱动，见第 5 节）与标记量双降；
3. 反面教材：往池里塞超大 buffer 会抬高内存驻留，命中越久驻留越久——池大小的上界要想清楚。

**清理时机为什么挂在 GC 上**：池对象常驻等于人为抬高「存活堆」，按第 5 节的目标堆公式，存活堆越大越容易触发下一轮 GC。victim 缓冲就是这个矛盾的折中——复用率与堆目标之间的取舍。

## 7. GC 慢的三个定位方向

先拿数据：`GODEBUG=gctrace=1 ./app`（对延迟敏感时可只看趋势，不常驻）：

```text
gc 12 @6.234s 3%: 0.058+1.2+0.031 ms clock, 0.46+0.35/2.3/0+0.25 ms cpu,
   47->48->24 MB, 48 MB goal, 0 MB stacks, 0 MB globals, 8 P
```

解读：第 12 轮 @6.234s；GC 累计占 3% CPU；STW 开始 0.058ms + 并发标记 1.2ms + STW 结束 0.031ms；堆 47MB→48MB，标记后存活 24MB，目标 48MB。

三个方向：

| 方向 | gctrace 特征 | 定位手段 | 解法 |
| --- | --- | --- | --- |
| **分配速率高** | GC 轮次密、每轮 heap 涨得快 | `pprof` 的 `alloc_space` 看分配热点 | sync.Pool / 预分配 / 消灭逃逸 / 减少中间对象 |
| **存活对象多** | live（第三个 MB 数）大且不降 | `inuse_space`、前后两份 heap diff、`runtime.NumGoroutine` | 查泄漏：全局 map 只增不减、goroutine 泄漏持有引用、`time.After` 未清理 |
| **标记耗时高** | 并发标记段（中段 ms）长 | `pprof` 看指针密集结构、`gcMarkTermination` 耗时 | 降低指针密度：用索引/slice 替代指针图、值类型数组、拆分大对象 |

注意 STW（前后两段）通常只有 µs 量级，明显偏大才值得怀疑；中段长是标记扫描问题；轮次密是分配问题——**先分类，再动手**。
