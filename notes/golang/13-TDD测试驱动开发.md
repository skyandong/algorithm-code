# TDD：测试驱动开发

> **核心认知：** TDD 不是「先写测试」这个动作本身，而是一种**用测试把需求翻译成可执行规格**的设计手法——红（写一个会失败的测试，明确下一步目标）→ 绿（写让它通过的最小实现，忍住不多写）→ 重构（在绿灯保护下整理代码）。它对设计的改造是副产品：**先想怎么调用、再想怎么实现**，函数签名天然是消费者视角的，可测试性和接口最小化（01 篇说的消费者侧接口）是同一件事的两面。Go 是 TDD 顺风局：`go test` 内建、无断言库依赖、表驱动是社区统一姿势——本仓 golang 模块的实验就是「纯逻辑用例 + 冒烟用例」两层测试的真实样本。
> **边界同样重要：** TDD 是手段不是信仰。探索性 spike、一次性脚本、UI 布局不值得测试先行；核心业务规则、并发协议、边界条件才值得。覆盖率是探针不是 KPI。

按 Go 1.26 语义说明。前置知识：benchmark 规范见 10 篇，接口在消费者侧定义见 `notes/design-pattern/01`，错误包装见 09 篇。

## 1. TDD 是什么：红-绿-重构循环

传统流程：写实现 → 补测试 → 修到绿。TDD 把顺序倒过来，每一小步都遵守同一节奏：

```
红：写一个小测试，跑一遍，看它失败（失败信息就是下一步的任务清单）
绿：写「刚好让它通过」的最小实现——允许丑陋，不允许过度设计
重构：绿灯保护下消除重复、改命名、提函数——测试不动，随时可以重跑
      └─回到红：下一个测试……循环 5~10 分钟一个来回
```

WHY 测试先行三条硬理由：

1. **需求翻译损耗显性化**：写测试的过程就是逼自己回答「这个函数输入什么、输出什么、错的时候怎么办」。答不出来，说明需求没懂——问题在设计阶段暴露，成本最低；
2. **可测试性是设计质量的探针**：先写测试意味着先当一次消费者。如果测起来很痛苦（要连数据库、要 sleep、要全局变量复位），说明设计耦合了——TDD 在第一行实现代码之前就把这个问题顶到你脸上；
3. **回归保护是免费的**：每个测试都是一次需求确认的快照。半年后改这段代码，测试列表就是当时的业务规则清单——这是文档做不到的（文档会撒谎，测试不会）。

一个常见误解先拆掉：TDD 的目的**不是**「测试覆盖率高」，而是「以可验证的规格驱动设计」。覆盖率是副作用。

## 2. Go 测试基建速成

Go 测试文件与被测代码同包（`xxx_test.go`），无独立断言库，`t` 就是断言器：

```go
func TestSplitBill(t *testing.T) {
    got, err := SplitBill(10000, 4)          // 100 元 4 人分
    if err != nil {
        t.Fatalf("意外报错: %v", err)         // Fatal：后续依赖它，挂了就停
    }
    if got != 2500 {
        t.Errorf("每人 %d 分, want 2500", got) // Error：断言失败但还能继续
    }
}
```

四个必须养成的习惯：

1. **Fatal vs Error 的分工**：前置条件失败用 `Fatalf`（后面全白跑），独立断言用 `Errorf`（一次跑出所有失败点）；
2. **`t.Helper()`**：自定义辅助函数开头调用，报错行号指向调用方而不是辅助函数内部（本模块 `00_helpers_test.go` 的 `captureStdout` 就是）；
3. **`t.Cleanup(f)`**：替代「函数尾部手工还原」——临时文件、全局状态复位，中途 `Fatal` 也能执行；
4. **`-run`、`-v`、`-short` 三件套**：`-run TestXxx/子用例名` 单点重跑、`-v` 看每个用例、`-short` 跳过慢用例（本模块 Makefile 的 test-unit 就是 `-short`）。

testify 的定位（本模块用它做断言）：`assert`（失败继续）/`require`（失败即停）语义清晰、错误信息可读。标准库够用，但表驱动用例一多，testify 的可读性优势真实存在——项目里二选一，别混。

## 3. 一个完整的 TDD 循环

需求：AA 收账，总额（分）按人头均摊。跟着节奏走一遍。

**红 1**：写第一个会失败的测试——

```go
func TestSplitBill(t *testing.T) {
    got, _ := SplitBill(10000, 4)
    if got != 2500 { t.Errorf("got %d want 2500", got) }
}
```

跑：`undefined: SplitBill`——编译失败也是「红」。此时 `SplitBill` 的签名已经被消费者（测试）定死了：入参 `(int, int)`，出参 `(int, error)`——**测试先行 = 签名先设计**。

**绿 1**：最小实现（丑没关系）——

```go
func SplitBill(total, people int) (int, error) {
    return total / people, nil
}
```

跑：绿。错误分支？还没被测试要求，**忍住不写**——TDD 的纪律就是不做没被要求的事（YAGNI 的执行机制）。

**红 2**：加边界用例——`SplitBill(100, 0)` 应该报错。跑：panic 整数除零，红。

**绿 2**：加校验——

```go
func SplitBill(total, people int) (int, error) {
    if people <= 0 { return 0, fmt.Errorf("人数 %d 必须为正", people) }
    if total < 0   { return 0, fmt.Errorf("总额 %d 不能为负", total) }
    return total / people, nil
}
```

跑：绿。注意校验分支是**测试逼出来的**，不是想象的——这就是「最小实现」和「没被要求的健壮性」的区别：前者每个分支有测试背书，后者是死代码候选人。

**重构**：用例多起来后把手工断言升级为表驱动（第 4 节），实现本身此时已经没有重复可消——重构阶段经常是「测试代码重构」而不是产品代码。

## 4. 表驱动与子测试：Go 的统一姿势

Go 官方 CodeReviewComments 力荐的形态，也是本仓全部实验测试的写法：

```go
func TestSplitBill(t *testing.T) {
    tests := []struct {
        name    string
        total   int
        people  int
        want    int
        wantErr error
    }{
        {"整除", 10000, 4, 2500, nil},
        {"不整除向下取整", 10001, 4, 2500, nil},   // 需求要定：余数给谁？
        {"零人报错", 100, 0, 0, errPeople},
        {"负总额报错", -1, 4, 0, errNegative},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {      // 子测试：独立报告、独立重跑
            got, err := SplitBill(tt.total, tt.people)
            if !errors.Is(err, tt.wantErr) {
                t.Fatalf("err = %v, want %v", err, tt.wantErr)
            }
            if got != tt.want {
                t.Errorf("got %d, want %d", got, tt.want)
            }
        })
    }
}
```

三个关键点：

- **用例名是规格**：`"零人报错"` 这一行同时是测试名、文档和回归清单。写不出用例名，说明这个用例自己也不知道在测什么；
- **错误用例是主角不是配角**：正常路径往往只有两三行，业务价值全在边界——零、负数、空、并发。错误分支必须有哨兵错误（09 篇）配合 `errors.Is` 断言，字符串匹配 `err.Error() == "..."` 是脆断言，改个措辞全崩；
- **`t.Run` 的子测试名可定位重跑**：`go test -run 'TestSplitBill/零人报错'` 精确到单个用例，调试时省命。

新增用例的纪律：**发现一个 bug，先写一个红测试复现它，再修**。修完测试留下，bug 永不复发——这是 TDD 在维护期的最高价值场景。

## 5. mock 与 stub：消费者侧接口的免费午餐

被测代码依赖外部世界（DB、RPC、时钟、随机数）时，测试才需要替身。Go 的答案极简：**接口在消费者侧定义（design-pattern/01），替身就是几行结构体**——

```go
// 生产者不需要预定义任何接口，消费者按需定义最小视角：
type Notifier interface {
    Paid(orderID string, cents int64) error
}

// 被测对象只依赖这个最小接口
type SettleService struct{ notify Notifier }

func (s *SettleService) Settle(orderID string, cents int64) error {
    if err := s.notify.Paid(orderID, cents); err != nil {
        return fmt.Errorf("通知失败: %w", err)
    }
    return nil
}

// stub：手写 3 行，记录调用供断言（比任何 mock 框架都便宜）
type stubNotifier struct {
    calls []string
    err   error
}

func (s *stubNotifier) Paid(orderID string, cents int64) error {
    s.calls = append(s.calls, fmt.Sprintf("%s:%d", orderID, cents))
    return s.err
}
```

测试里两种用法：`err: nil` 断言 `calls == [...]{"o1:2500"}` 验证交互内容；`err: errors.New("boom")` 注入失败路径——**失败分支不用真连一个会失败的下游**。

手写 stub vs gomock 的决策：

| | 手写 stub | gomock（代码生成） |
|---|---|---|
| 接口方法数 | 少（≤5），手写更快 | 多，生成省力 |
| 断言需求 | 只关心「调没调/参数对不对」 | 要调用次数、顺序、精细匹配 |
| 依赖 | 零 | 工具链 + 生成物入库 |

Go 社区主流是**能手写就不生成**——stub 本身就是消费者侧接口哲学的一部分。gomock 用在接口膨胀（proto 生成的 client 动辄几十个方法）且确实要精细校验交互的场景。

另一类特殊替身：**时钟、随机数、环境变量**。办法是注入函数值（`now func() time.Time`）或抽象成小接口，测试注入确定值——永不 sleep、永不 `time.Now()` 裸调（10 篇 pprof 实验同样用注入时钟）。

## 6. 测试金字塔与本仓实践

经典三层：单元测试（多、快、毫秒级）→ 集成测试（少、慢、碰真依赖）→ E2E（最少）。Go 落地的关键问题是**怎么在同一棵代码树里分层**——本仓的答案：

1. **纯逻辑用例打底**：只测函数，任何环境秒级跑完，CI 兜底。`go test -short` 全绿是提交前最低标准；
2. **冒烟用例带门槛**：完整跑一遍实验断言关键输出，开头 `requireDemoRun` 检查 `testing.Short()`——`-short` 时跳过而不是挂死；
3. **集成依赖带守卫**：akafka 的 `requireKafka` 先探测 broker，探测不到就 `t.Skip`——CI runner 没有 Kafka 也能全绿，本地起了容器自动升级为真集成测试（同一份代码两种形态）；
4. **benchmark 是另一个维度**：测试断言「对不对」，benchmark 回答「多快」。规范（`-benchtime`、b.ResetTimer、ReportMetric）见 10 篇。

这套「守卫 + 分层」模式可直接抄到任何项目：**CI 里跑的必须是无依赖纯逻辑，依赖真环境的用例要么 Skip 要么单列 job**——CI 挂掉的测试会迅速失去所有人的信任，然后形同虚设。

测试文件放哪：同包（`foo_test.go` 在 `foo` 包内）能测私有函数，是默认选择；黑盒视角（测公共 API 契约、防测试代码偷用私有实现）用 `foo_test` 包。Go 标准库两种都有，公开库更适合后者。

## 7. 边界与误区：什么时候不 TDD

诚实的边界（面试答出这个，比背概念加分）：

| 不值得测试先行 | 原因 | 替代 |
|---|---|---|
| 探索性 spike（验证 API 行为、算法可行性） | 需求本身在流动，测试规格写不出 | 扔掉式原型 + 事后关键路径补测 |
| 一次性脚本、本地工具 | 投入产出倒挂 | 跑通即交付 |
| UI 布局、视觉 | 断言成本高且脆 | 截图对比/E2E 少量冒烟 |
| 并发时序的正确性测试 | 时序不稳定，测试本身 flaky | `-race` + 压测 + 确定性重放（见 04/05 篇） |

四个高频误区：

1. **先写完所有实现再补测试**：那是「测试背书」不是 TDD——设计已经定型，测试只能顺着实现写，测不出耦合问题；
2. **测试写实现细节**：断言内部调用顺序、私有字段值 → 重构必碎，测试从保护网变成绊马索。断言**可观察行为**（返回值、对外状态、接口交互），不问「怎么做到的」；
3. **覆盖率当 KPI**：为数字而写的测试专挑 getter/setter 下手，覆盖率 90% 而边界条件全裸奔。覆盖率用来**找漏测的分支**（`go test -coverprofile` + `go tool cover -func` 看低分函数），不用来发奖金；
4. **红步骤被跳过**：新测试没跑就绿了 = 它什么都没测（恒真断言或用例写错）。纪律：先亲眼看它红。

## 8. 面试高频

**Q1：TDD 的循环是什么？为什么测试先行？**
红-绿-重构：写失败测试（明确目标）→ 最小实现（忍住不多写）→ 绿灯下重构。测试先行的价值：需求翻译损耗在写测试时暴露、签名被消费者视角定死（可测试性即设计质量）、回归保护免费累积。核心是「每个分支都被测试逼出来」而不是先写完再补。

**Q2：表驱动测试怎么写？为什么 Go 社区偏好它？**
匿名结构体切片 + `t.Run` 子测试：用例名即规格、错误用例一等公民、`-run 'Test/子名'` 精确重跑。Go 无注解无参数化框架，表驱动用纯数据表达全部用例，是最小机制；配合 `errors.Is` 断言哨兵错误，不匹配字符串。

**Q3：Go 里怎么做 mock？要上框架吗？**
消费者侧定义最小接口 + 手写 stub（3 行结构体记录调用 + 注入错误）。gomock 只在接口方法多（proto client）且要校验调用次数/顺序时用。时钟/随机数注入函数值。原则：能手写不生成，stub 本身就是接口最小化的证明。

**Q4：集成测试依赖外部服务，CI 里怎么处理？**
守卫模式：测试开头探测依赖（拨号/健康检查），探测不到 `t.Skip` 而不是失败——同一份代码，CI 无依赖时纯逻辑绿，本地有容器时自动升级为真集成。慢用例用 `-short` 分层。CI 里的用例必须确定性，flaky 测试比没有测试更糟。

**Q5：什么时候不该 TDD？**
探索性 spike（需求在流动）、一次性脚本、UI 视觉、并发时序（用 -race 和确定性工具替代）。TDD 的适用判据：需求稳定到能写成规格、且这段代码会活过今天。答出边界比背流程加分。

**Q6：覆盖率多少算合格？**
没有及格线。覆盖率是探针：`go test -coverprofile` 找出低覆盖函数看是不是边界漏测；为凑数字写 getter/setter 测试是自欺。高质量 60% 的核心域覆盖 > 低质量 95% 的全量覆盖。真正要盯的是：改到的代码有没有测试保护（diff coverage 思路）。
