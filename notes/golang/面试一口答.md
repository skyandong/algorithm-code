> **记忆主线：** Go 的一切「简单语法」下面都藏着机制——`go func()` 下面是 GMP，`append` 下面是扩容拷贝，`err != nil` 下面是接口二元组。回答任何 Go 问题的第一反应：**这个语法糖的底层机制是什么**。

## 一、slice、string 与 map（01）

### 1. slice 底层？append 超 cap 会怎样？
(ptr, len, cap) 三字段头，赋值传参**拷贝头不拷贝数据**。底层数组长度固定，所以「扩容」是**新分配一块数组 + 把旧元素搬过去 + 返回新 header**：新 slice 与旧数组脱钩，旧 slice 看不见新元素。搬的是**元素值（浅拷贝）**——元素含指针时只拷指针，指向的对象仍共享。每次多给多少容量是实现细节、随版本变，不背；要确定容量就 `make([]T, 0, n)` 预分配。

**追问：元素是指针时，扩容后改指向的对象会怎样？** 答：双方可见。浅拷贝只拷贝指针值（地址），新旧 slice 的指针指向同一个对象，修改对象内容双方都能看到。实验：`experiments/01_1_slice_test.go:TestSliceAppendShallowCopy`

### 2. 共享底层数组的经典坑？
`a := s[:2]; b := append(a, x)`——若 cap 够，b 直接改写 s[2]！同理两个子 slice 头写同一数组 = data race。口诀：**append 可能就地写，要隔离就完整拷贝**（copy 或 `s[:2:2]` 限三索引 cap）。

### 3. 大切片传参会拷贝数据吗？
**不会**。slice 是三字段头（ptr/len/cap，共 24 字节），传参拷贝的是头，底层数组不拷贝。所以传 1GB 的 slice 只拷 24 字节，开销接近指针传递。但修改元素会影响调用方（共享底层数组），要隔离就显式 `copy`。map/channel 同理（都是指针或小头）。

### 4. string 的底层结构？
(数据指针, 长度) 二字段头。**无 `\0`、长度显式存储**——可存任意二进制。子串 s[i:j] 零拷贝（只造新头），但持有子串会钉住整个大字符串（要独立就 strings.Clone）。

### 4. 为什么 string 不可变？得到什么？
共享安全（传值零风险）、字面量驻留（相同常量一份只读内存）、map key 哈希稳定。代价：所有「修改」都新分配——循环 `s += x` 是 O(n²)，正解 strings.Builder + Grow（String() 用 unsafe.String 零拷贝导出）。

### 5. len(s) 返回什么？
**字节数**。字符数是 utf8.RuneCountInString。for range 按码点迭代、索引是**字节偏移**；s[0] 是字节不是字符；s[:4] 按字节截断会切碎多字节字符（碎码）。

### 6. string ↔ []byte 什么时候免拷贝？
默认拷贝（不可变契约）。两个编译器特例：①`[]byte(s)` 不逃逸且不被修改 → 直接引用底层；②`m[string(b)]` map 索引就地比较免分配。热路径原则：流水线统一类型，只在边界转一次。

### 7. []byte 为什么不能做 map key？
slice 头不可比较（不满足 comparable）。string 不可变 + == 是 memcmp（先比长度）+ 哈希稳定，天生 key。[N]byte 定长数组按值可比也行（网络库零分配 key 惯用法）。

### 8. unsafe.Pointer 和 uintptr 的区别？
unsafe.Pointer 是编译器认可的「任意指针 ↔ 具体指针」转换桥梁，**GC 能追踪它**；uintptr 只是无 GC 语义的整数。红线：`unsafe.Pointer → uintptr` 后必须在**同一个表达式内**算完并转回指针，跨语句暂存等于让 GC 失去线索（对象可能在两句之间被搬走/回收）——偏移用 `unsafe.Add`，全程保持 unsafe.Pointer。合法出场只有两类：**类型双关、零拷贝**（strings.Builder.String() 是正面示范）。

### 9. map 底层？为什么无序？
Swiss Table，三层：Map（目录）→ table（定长 group 数组）→ group（槽位 + 同数量的控制字）。查找靠**一次定宽比较**筛掉整组里不可能命中的槽，只在控制字对得上的槽上比 key——无效比对几乎归零。负载因子超限触发 rehash（翻倍或分裂；单表有容量上限，到顶只能分裂）；删除打墓碑而不是清空（清空会打断探测序列），墓碑也计入负载 → **容量只增不减，要真正释放只能换新 map**。无序：顺序被刻意随机化，防依赖顺序。

### 10. map 并发读写？
**runtime 直接 fatal（throw），不可 recover**——因为 map 内部状态可能已损坏，继续跑比崩更危险。sync.Map 或 map+Mutex 解决。

**追问：读多写少场景怎么优化？** 答：看场景选方案：sync.Map（写一次读多次/不相干key）适合配置注册表，写锁在子树级；分片锁（高并发写+key均匀）锁冲突降到~1/N；map+Mutex通用简单。sync.Map 限制：无 len()、写多场景慢、不适合遍历。实验：`experiments/01_3_map_test.go:TestMapConcurrentSafe`

## 二、interface 与反射（02）

### 11. interface 底层？nil != nil 的原理？
二元组：空接口 eface{类型指针, 数据指针}，非空 iface{itab, 数据指针}。`var p *T = nil; var i any = p` → i 是「(类型=T, 值=nil)」，`i != nil` 成立——**有类型无值不是 nil 接口**。判空要 `reflect.ValueOf(i).IsNil()` 或类型断言后判。

### 12. 方法集：T 和 *T 的区别？
*T 的方法集包含值方法和指针方法；T 只有值方法。所以 `*T` 实现的接口，T 不实现（T 存接口时无法自动取址——T 可能不可寻址）。

**追问：值接收者方法内修改接收者字段，外部能看到吗？** 答：看不到。值接收者是拷贝，修改副本不影响原值。要修改必须用指针接收者。

**追问：什么时候 T 无法自动取址？** 答：① T 存在接口中（接口里是副本）；② map 的值（`m[k]` 不可寻址）；③ 临时对象（如函数返回值 `getUser().Method()` 中的 User）。

## 三、泛型（03）

### 13. 泛型的实现机制？
**GC shape 分组 + 字典**：内存布局相同的类型（所有指针类型一组）共享一份机器码，shape 内差异靠编译期生成的字典（类型元数据、操作函数、方法入口）运行时传递。非 C++ 全量展开（膨胀可控），非 Java 全擦除（值类型零装箱、运行时有类型信息）。

**追问：为什么不像 C++ 那样全量展开？** 答：代码膨胀。C++ 每个 `template<T>` 实例化都生成独立代码，最终二进制巨大。Go 选择 GC shape 平衡性能和大小。

**追问：字典访问有多大性能开销？** 答：指针间接跳转（几纳秒），现代 CPU 分支预测准确率高。字典查找通常在个位数纳秒，与 itab 间接相当或更快。

### 14. `~` 是什么？
近似约束：`~int` 匹配所有**底层类型**为 int 的类型——`type UserID int` 通过。不带 ~ 只匹配 int 本身。代价：~int 集合内无法再按方法区分成员。

### 15. comparable 的精确语义？
「== 可用且不 panic」的**类型集合**：数值/string/指针/channel/数组/纯值 struct。不含 slice/map/function（== 只能与 nil 比）。`func Keys[K comparable, V any]` 这类签名的基础。

### 16. 为什么方法不能有类型参数？
方法级类型参数会让**接口满足性检查不可判定**（S 要实现多少个 Map[U] 才算实现接口）。绕法：包级泛型函数——slices 包全是这个风格（slices.SortFunc 而不是 xs.SortFunc）。

### 17. 泛型 vs 接口怎么选？
同一**算法**对多类型（容器/工具函数）→ 泛型：编译期约束、值语义零装箱。运行时多态/依赖注入/mock/异构集合 → 接口。组合：泛型管类型维度、接口管行为维度（泛型结构体里存接口字段）。

### 18. 泛型一定比接口快吗？
通常不慢：省装箱（int 装 any 逃逸即堆分配，>255 无小整数缓存）；字典间接 vs itab 分发相当或略快。但泛型体内对 T 的操作经字典间接、部分内联失效——性能敏感处 benchmark 说话。

## 四、并发内存模型（04）

### 19. 什么是 data race？三要素
多个 goroutine 访问**同一内存位置**，**至少一个写**，且访问之间**没有同步关系**（mutex/channel/atomic）。后果是未定义行为：读到旧值、撕裂值、甚至死循环（可见性问题，`for !ready {}` 可能永远不退出）。

### 20. happens-before 是什么？
Go 内存模型给出的同步保证：A happens-before B 则 A 的写对 B 可见。建立 happens-before 的机制：channel 收发、mutex 加解锁、atomic 操作、`sync.Once`、`wg.Wait` 返回。**没有同步关系的读写，编译器和 CPU 可以任意重排**。

### 21. `for !ready {}` 为什么可能死循环？
无同步 → 编译器可合法把 ready 缓存进寄存器（甚至优化成 `if !ready { for {} }`）。修复三选一：atomic.Bool、channel、mutex。**volatile 在 Go 里不存在，atomic 就是答案**。

## 五、channel 与 nil（05）

### 22. channel 底层结构？
hchan：环形缓冲区 buf + sendx/recvx 索引 + **sendq/recvq 两个等待队列**（sudog 链表）+ 一把 lock。直接读 hchan.buf 无锁竞争时很快；阻塞时 goroutine 挂进 sudog，由发送方/接收方唤醒。

### 23. 向 nil channel 发送/接收/关闭？
发送 → 永久阻塞；接收 → 永久阻塞；关闭 → **panic**。对已关闭的 channel：发送 panic、接收读完剩余后返回零值（ok=false）、再关闭 panic。这九种组合是必背表（05 篇）。

### 24. 关闭 channel 为什么是广播？
close 后所有 `<-ch` 立即返回零值——**任意多接收者同时解除阻塞**；而发送只能唤醒一个且可能丢。所以「通知退出」用 close，事件扇出也用 close。

### 25. 无缓冲 channel 的同步语义？
发送发生在接收完成之前（happens-before）——发收双方「会合」，无缓冲 channel 是一次同步点。这也是「用无缓冲 channel 传递所有权零竞争」的原理。

### 26. select 多个 case 同时就绪怎么办？
**随机选一个**（伪随机，防止依赖顺序）。Go 编译器生成的选择序列打乱 case 的评估顺序，保证公平性。default 存在时永不阻塞。空 `select{}` 永久阻塞（常用于 main 防止进程退出）。

### 27. for-select 怎么退出？
三种方式：① `return` 直接退出函数；② `break 标签` 跳出循环；③ `<-ctx.Done()` 配 return。**错误做法**：`break` 只跳出 select 不跳出 for，仍继续循环。标签用法：`Loop: for { select { case <-ch: break Loop } }`。

## 六、sync 并发原语（06）

### 26. Mutex 公平吗？
非绝对公平。正常模式：被唤醒 waiter 与新来者竞争（新来者在 CPU 上常赢），吞吐高；waiter 等太久切**饥饿模式**：锁直接交接队头，新来者不自旋不抢；拿到锁时等待很短或已是队尾，切回正常。双模式 = 吞吐与公平的折中。

**追问：等多久切饥饿模式？** 答：waiter 等待超过 **1ms** 触发饥饿模式。

**追问：为什么新来者常赢？** 答：新来者已在 CPU 上运行（热缓存、寄存器就绪），waiter 需要从睡眠唤醒（冷启动、上下文切换），有几微秒劣势。

### 27. Unlock 的三个冷知识？
①无属主校验——他人 Unlock 合法（但禁止）；②未加锁 Unlock 是 **fatal 不可 recover**；③Mutex 不可复制（含 Mutex 的结构体也不可复制，vet copylocks 检查）。

### 28. 自旋的条件？
多核 && GOMAXPROCS>1 && 本 P 本地队列为空 && 自旋未到上限 && 非饥饿模式。本质赌临界区几十 ns 内结束，用空转换微秒级的调度唤醒。

### 29. RWMutex：写锁排队后新读者？
**被阻塞**（Lock 把 readerCount 打负，RLock 见负睡 readerSem）→ 写者不饿死。推论：读锁**不能升级**（持读锁再 Lock 死锁）、**能降级**（Lock→RLock→RUnlock→Unlock）。RWMutex 不一定快：单次成本更高，读临界区 <100ns 是负优化，微秒级+读写比 >10:1 才赚。

### 30. WaitGroup 协议？
Add 在启动方先于 go；子 goroutine defer Done；两条 fatal：Wait 后并发 Add（misuse）、Done 多于 Add（负计数）。归零后可复用但有竞态窗口。需要超时/错误收集/并发上限 → errgroup.WithContext + SetLimit。

### 31. atomic 的边界？
**只保护一个机器字**——两个 atomic 字之间无原子性，二元状态必须打包（位运算/atomic.Pointer[T] 整体换快照）或上锁。无原子浮点 Add；atomic.Value 必须同类型，泛型时代用 atomic.Pointer[T]。Go 只有一种内存序（happens-before），Store/Load 配合即 release/acquire。

**追问：两个 atomic 字段怎么保证原子性？** 答：三种方案：① 打包进一个 uint64（位运算拆分字段）；② 用 atomic.Pointer[T] 指向整个快照结构体（原子换指针）；③ 加锁（Mutex）。

**追问：atomic 一定比 mutex 快吗？** 答：单变量读写快（几纳秒 vs 几十纳秒），但 CAS 循环在竞争激烈时可能比 mutex 慢（无队列，失败就空转 CPU；mutex 有等待队列，休眠不空转）。

### 32. sync.Pool 语义？
**缓存不是容器**：Get 无保证（New 必须给）、每次 GC 清空（有 victim 缓冲把清空摊到两轮，但不保证留住）、Put 后再 Get 可能拿到同一对象（**放回前必须 Reset**）。定位：减 GC 压力（bytes.Buffer/大对象），不是缓存/连接池/free list。

### 33. sync.Map 适用场景？
①key 写一次读多次且集合稳定（注册表/路由）；②多 goroutine 写不相干的 key。内部：**HashTrieMap**（哈希 trie，写锁子树级）。写多场景 map+Mutex 更快；没有 len()。

### 34. sync.Once 为什么快？双检查锁
Once.Do：先 atomic.Load 快路径（已初始化直接返回），慢路径加锁后**再查一次**（双检查），再执行 f，最后 atomic.Store 发布。fast path 是一次原子读，几乎零开销。

### 35. sync.Once 的初始化函数 panic / 重入会怎样？
panic：`Once` 仍算「已执行」——后续 `Do` 直接返回、**不重试**（实测：panic 后初始化函数调用次数仍为 1），调用方拿到的是未完成初始化的状态；要么保证初始化不 panic，要么在 `f` 里自己 recover。重入：在 `Do` 的初始化函数里再调同一个 `once.Do` 是**死锁**（实测不返回）——内层在等外层 `f` 结束，外层在等内层。

### 36. 锁 vs channel 怎么选？
锁保护**共享状态的不变量**；channel **传递数据/所有权/事件**。围绕一份数据反复读写 → 锁；流水线生产消费 → channel。锁保护的是不变量不是代码行——先写清楚约束，锁边界自然出来。

## 七、GMP 与调度（07）

### 37. G/M/P 分别是什么？为什么要有 P？
G=goroutine（栈+调度信息），M=OS 线程，P=执行资格（本地运行队列+mcache）。P 的数量=GOMAXPROCS，M 按需创建、有上限。GM 模型全局队列锁竞争 → 引入 P 固化资源局部性：本地队列无锁、mcache 绑 P、work-stealing 均衡。**goroutine 轻量的根源是 G 阻塞时 M 不停**。

### 38. 调度循环的查找顺序？
runnext（刚唤醒的，最高优先）→ 本地队列（无锁）→ 全局队列（加锁，周期性兼顾防饿死）→ netpoll → 偷其他 P 本地队列的**一半**。

### 39. channel 阻塞和系统调用阻塞的区别？
channel/网络阻塞：G 挂起，**M 换下一个 G 继续跑**（netpoller 把 fd 交给 epoll 管理）。CGO/磁盘等系统调用：**M 陪绑进内核，P 被 hand off 给别的 M**。所以大量系统调用会创建大量 M。

**追问：如何避免大量系统调用创建过多 M？** 答：① 用 Go 的网络库（走 netpoller，不阻塞 M）；② CGO 调用池化复用；③ 监控 `runtime.NumCGOCall()` 和线程数（`runtime.NumThreads()` 或 `/proc/self/status` 的 Threads）。

**追问：netpoller 怎么工作的？** 答：底层用 epoll（Linux）/kqueue（BSD）多路复用，单独的系统线程监听所有非阻塞 fd。fd 就绪时通知 runtime，唤醒对应 G 继续执行。M 不进内核等待，实现高并发。

### 40. 抢占机制怎么演进的？
双机制：函数调用点是**协作式**抢占点（栈检查复用）；纯 CPU 循环靠 **SIGURG 信号异步抢占**，最多独占 P 一个时间片。sysmon（监控线程）负责触发。

### 41. GOMAXPROCS=1 还并发吗？
并发不并行：单 P 上 G 交错执行，抢占保证公平。（Linux）GOMAXPROCS 自动感知 cgroup CPU limit（quota 向上取整、定期重读），容器配 2 核不再按宿主机 96 核跑 GC。

### 42. sysmon 是什么？它管哪些事？
不需要 P 的监控线程，自适应地周期性巡视：触发超时间片的抢占、retake 卡在系统调用里的 P、兜底 netpoll、兜底强制 GC、归还闲置内存给 OS。

### 43. goroutine 泄漏三大来源？
①阻塞在没人再发的 channel 收/没人再收的发送上；②长任务不检查 ctx 取消；③子 goroutine panic 未 recover 拖垮进程/提前退出。排查：`NumGoroutine` 监控 + pprof goroutine profile 看卡在哪个 chan 收发。

## 八、内存与 GC（08）

### 44. 逃逸分析决定什么？
对象分配在栈还是堆。逃逸路径：返回局部变量指针、闭包捕获、动态长度、interface 装箱、指针跨 goroutine。**逃逸不是坏事**，只优化 profiling 证明热的路径。验证：`go build -gcflags="-m -l"`。

**追问：逃逸分析有什么局限？** 答：保守策略，宁可逃逸也不冒栈溢出风险。闭包捕获、interface 装箱、大对象（>32KB）、复杂数据流都倾向逃逸。编译器看不穿的间接调用也会逃逸。

**追问：能强制栈分配吗？** 答：不能。Go 没有 C++ 的 placement new。只能通过改代码引导编译器：避免返回指针、减少闭包捕获、用值类型、预分配切片容量。

### 45. 堆分配三级结构？
TCMalloc 思想：mcache（绑 P，无锁快路径）→ mcentral（按 sizeclass 加锁补充）→ mheap（页堆，向 OS 要）。小对象走快路径纳秒级，超出档位的大对象直接 mheap。

### 46. new 和 make 的区别？
new(T) 分配并返回 `*T`（零值）；make 只用于 slice/map/channel，返回**初始化后的 T**（不是指针）。日常几乎不用 new。

### 47. 三色标记 + 混合写屏障？
白/灰/黑三色，从根标记可达对象。并发标记期间用户代码改指针，靠**混合写屏障（Yuasa 删除 + Dijkstra 插入）**维持不变式：堆上写指针旧值新值都置灰，**栈全程免屏障**。STW 只剩标记开始/结束两个极短窗口（µs 量级）。

### 48. 写屏障为什么不上栈？
栈写太热。代价是标记开始时把所有栈标黑（STW 窗口之一）+ 栈上对象保守处理。当前实现：仍是三色，标记按 span 页批量扫（页级广度优先 + 每对象少量元数据 + SIMD），cache 友好，开销明显下降。

### 49. GOGC 语义？GOMEMLIMIT 是软限还是硬限？
目标堆 = 存活堆 × (1 + GOGC/100)，默认 GOGC=100。GOGC 大 → GC 少、吞吐高但堆峰值高，调小则相反。GOMEMLIMIT 是**软限**（逼近时强制 GC），不是 OOM 保护；`GOGC=off` 不会立刻 OOM——只要 GOMEMLIMIT 兜底，两者都不设才轮到 OOM killer。容器常见组合：`GOGC=off GOMEMLIMIT=<limit×80%>`。

### 50. GC 触发条件？
①堆增长到目标（GOGC 公式）；②sysmon 兜底强制；③手动 runtime.GC()；④逼近 GOMEMLIMIT。后台标记工人占一部分 CPU，分配太快的 G 被 mutator assist 罚去做标记。

## 九、context 与错误处理（09）

### 51. context 取消的传播机制？
With* 把子 ctx 挂进父的 children；cancel() = 关自己 done channel + 递归 cancel children + 从父摘除。**Done 是 channel 关闭不是发值**——广播语义，任意多监听者同时解除阻塞。父先取消则新子挂树时立即自取消。

### 52. 为什么必须 defer cancel()？
三条后果，不是「整棵子树无法 GC」这么笼统。第一，`WithTimeout` 注册的 runtime timer 不 cancel 就一直挂在定时器堆里，要到超时点才停。第二，下游阻塞在 `<-ctx.Done()` 上的 goroutine 不会自己醒，这是泄漏最直接的来源。第三，子 ctx 被挂进父的 `children` 后要等父取消或自己 cancel 才摘除——**这一条只在父可取消时成立**，父是 `Background` 时它的 `Done()` 是 nil，压根不挂树。共同点是同一个：不 cancel，资源就要拖到超时点才释放。

**追问：WithCancel（无 timer）也要 defer cancel 吗？** 答：要。不 cancel，子 ctx 一直挂在父的 children map 里，直到父取消才摘除。如果父是长生命周期（如 Background、请求 ctx），就是泄漏。

### 53. 子超时能比父长吗？
不能。`WithDeadline` 一旦发现父的截止更早，就直接退化成 `WithCancel(parent)`，所以 Deadline 取更早者，子给 10s 也会被父剩余的 100ms 截断。Value 全部继承，取消单向从父流到子。

### 54. Background 和 TODO 到底有什么区别？
实现只差一个字节：`String()` 的输出。两者都是内嵌 `emptyCtx` 的空壳，**永不取消、没有 deadline、没有值、`Err()` 恒为 nil**，区别只是写给人看的意图——`Background` 是「我就是根」，用在 main、init、测试和请求入口，`TODO` 是「还没想好」，等着被真正的 ctx 替换。考点有两个。**①`Done()` 返回的是 nil channel，不是已关闭的 channel**：nil 上的接收永远阻塞，`select` 里那个 case 被永久禁用，这才是「永不取消」的实现方式，返回已关闭的 channel 就变成「已取消」了。**②最大的坑是拿 `Background` 顶替上游传下来的 ctx**，那等于切断取消链：上游超时、客户端断开，这棵子树一个信号都收不到，下游 goroutine 跑到底。收尾任务要用 `WithoutCancel`（留 Value、剥取消），不知道传什么就用 `TODO()`，绝不能传 nil，`With*` 收到 nil 父节点会直接 panic。

### 55. Value 的边界？
只放请求级横切数据（traceID/身份），key 用私有类型；业务参数必须显式在签名里——偷读 Value = 隐式依赖 + 不可测试。收尾工作要 Value 不要取消：`WithoutCancel`。

### 56. 取消 ctx 能停掉 CPU 循环吗？
不能。context 是**协作式**取消：只唤醒阻塞在 Done()/支持 ctx 的 IO 上的代码；CPU 循环必须自己周期检查。Go 没有抢占式 kill goroutine。

### 57. context.Cause 和 Err 有什么区别？
`Err()` 只有 `Canceled` 和 `DeadlineExceeded` 两个取值，说不清**为什么**被取消；`Cause()` 补的就是这个原因，要用 `WithCancelCause` / `WithTimeoutCause` 才设得上。三条规则：判定照旧看 `Err()`（超时还是被取消，哨兵没变），写日志、定位「谁取消的」才用 `Cause()`；cause **沿树向下可见**，父设的在任意子 ctx 上都读得到；父子各有 cause 时**先取消的赢**。未取消的 ctx 和 `WithoutCancel` 派生的 ctx，`Cause` 返回 nil。

### 58. errors.Is vs errors.As？
Is 沿 Unwrap 树找**相等**节点（哨兵：io.EOF/context.Canceled）或调用节点的 Is 方法；As 找**可赋值类型**的节点取结构化字段。前提：包装用 **%w**（成链）不用 %v（断链）。多 %w 与 errors.Join 成树。

### 59. 为什么禁止字符串判错？
`strings.Contains(err.Error(), "timeout")` 依赖消息文本——改版/本地化/中间层重写即失效，且编译期不报错。正解：errors.Is(err, context.DeadlineExceeded) / errors.As(err, &netErr)。

### 60. 什么时候应该返回 error，什么时候 panic？
**error**：可预期的失败（文件不存在、网络超时、参数错误、业务校验失败）。**panic**：程序员错误（nil 解引用、数组越界、类型断言失败）、不可恢复的初始化错误（配置文件损坏、依赖服务全挂）。**库永不 panic**，业务代码 panic 留给 init/启动阶段的配置解析。

### 61. 自定义 error 类型怎么设计？
四要素：① 实现 `Error() string`；② 包含结构化字段（Code、Detail、Cause）；③ 支持 `errors.Is`（实现 `Is(error) bool` 方法）或直接用 == 比较；④ 可包装（返回 `fmt.Errorf("context: %w", cause)`）。示例：`type NotFoundError struct { Resource string }` 配 `func (e *NotFoundError) Error() string { return "not found: " + e.Resource }`。

### 62. panic/recover 的规则？
recover 必须在 **defer 的函数体内直接调用**（defer helper() 里调无效）；**只救当前 goroutine**（子 goroutine panic 外层拦不住，进程退出）。panic 留给程序员错误与初始化致命；可预期失败用 error。库 API 永不 panic。吞 panic 前想清楚：锁没释放、map 写一半——状态未知比崩溃危险。

### 63. defer 四个陷阱？
①参数**立即求值**拷贝（要延迟就包闭包）；②命名返回值可被 defer 改写（recover 转 error 的标准姿势）；③循环内 defer 累积到函数结束（抽函数）；④LIFO。性能：开放编码 defer ~1ns，「defer 慢」是老黄历。

## 十、工程哲学与设计（新增）

### 64. Go 的零值可用（zero-value ready）是什么？
类型零值（nil、0、false、""）无需显式初始化就能安全使用。设计哲学：① `sync.Mutex` 零值可用（无需 Init()）；② `bytes.Buffer` 零值可用；③ `strings.Builder` 零值可用。反例：slice/map/channel 零值是 nil，不能直接使用。好处：减少初始化负担，避免忘记 init 的错误。

### 65. pprof 各 profile 类型的用途？
- **cpu**：函数耗时热点（`-cpuprofile=cpu.prof`）；看谁花时间最多
- **heap(inuse_space)**：当前内存占用排序；定位大内存用户
- **heap(alloc_space)**：分配速率排序；定位分配压力（vs 泄漏）
- **goroutine**：goroutine 泄漏定位；`debug=2` 看卡在哪
- **mutex**：锁竞争热点；找争执最剧烈的锁
- **block**：channel/select 阻塞分析；定位 IO/通信瓶颈

## 十一、性能调优（10）

## 十一、性能调优（10）

### 66. 调优闭环三步？
压测复现 → pprof 定位热点 → benchmark 前后对比（benchstat）验证。没测量不优化，没对比的优化是自我感动。

### 67. 优化性价比排序？
算法/数据结构 > 减少分配（预分配/复用）> 逃逸与内联治理 > sync.Pool > 微优化。CPU profile 里 GC 标记占 30% 时优化业务循环是白费劲——先看全局再看局部。

### 68. 线上 CPU 高怎么查？
①**定范围**：top / 容器 metrics 确认是本进程（区分 user / IO wait / 别的进程）；②**采样**：`go tool pprof http://host/debug/pprof/profile?seconds=30`；③**分型**：flat 高的业务函数 → `list` 定位行级，`gcBgMarkWorker`/`runtime.mallocgc` 高 → 是分配问题，转 heap(alloc_space) 找源头，syscall/网络高 → IO 问题；④**验证**：benchmark + benchstat，灰度看曲线回落。

### 69. GC 调优决策？
先 gctrace 看频率与耗时：GC 频繁（CPU 被 GC 吃）→ GOGC 调大；内存吃紧 → GOMEMLIMIT 兜底；容器 OOM → GOMEMLIMIT=limit×80%。开关组合取舍见 08 篇第 5 节表。

### 70. 内存一直涨怎么查？
先按三条曲线分型（RSS / HeapAlloc(inuse) / goroutine 数）：①goroutine 数同步线性涨 → **泄漏**，`goroutine?debug=2` 看卡点；②HeapAlloc 持续涨 → **内存泄漏**，heap profile 两个时刻 `-base` diff，增量集中处即凶手；③inuse 平稳但 GC 频繁 → 不是泄漏是**分配压力**，看 alloc_space 速率做减法；④RSS 涨但 HeapAlloc 稳 → runtime 外的内存（cgo/线程栈）或页归还延迟。口诀：**inuse_space 看泄漏（增长），alloc_space 看压力（抖动）**。

## 考前 60 秒主线串讲

**并发**：data race 三要素 → happens-before → channel 底层（buf+两个 sudog 队列）→ 关闭是广播 → GMP（P=GOMAXPROCS，M 按需，work-stealing 偷一半）→ 信号异步抢占 → 泄漏三来源。调度疑似拥塞：`GODEBUG=schedtrace=1000` 看队列长度，`runtime/trace` 看单 G 时间线。
**内存**：逃逸分析（-m 验证）→ mcache/mcentral/mheap → 三色+混合写屏障（栈免屏障）→ 标记按 span 页批量扫（cache 友好）→ GOGC 目标公式 → GOMEMLIMIT 软限。
