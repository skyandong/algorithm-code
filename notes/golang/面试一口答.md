## 一、并发基础（05/06）

### 1. 什么是 data race？三要素
多个 goroutine 访问**同一内存位置**，**至少一个写**，且访问之间**没有同步关系**（mutex/channel/atomic）。后果是未定义行为：读到旧值、撕裂值、甚至死循环（可见性问题，`for !ready {}` 可能永远不退出）。

### 2. happens-before 是什么？
Go 内存模型给出的同步保证：A happens-before B 则 A 的写对 B 可见。建立 happens-before 的机制：channel 收发、mutex 加解锁、atomic 操作、`sync.Once`、`wg.Wait` 返回。**没有同步关系的读写，编译器和 CPU 可以任意重排**。

### 3. `for !ready {}` 为什么可能死循环？
无同步 → 编译器可合法把 ready 缓存进寄存器（甚至优化成 `if !ready { for {} }`）。修复三选一：atomic.Bool、channel、mutex。**volatile 在 Go 里不存在，atomic 就是答案**。

### 4. sync.Once 为什么快？Double-Check 锁
Once.Do：先 atomic.Load 快路径（已初始化直接返回），慢路径加锁后**再查一次**（双检查），再执行 f，最后 atomic.Store 发布。fast path 是一次原子读，几乎零开销。

### 5. channel 底层结构？
hchan：环形缓冲区 buf + sendx/recvx 索引 + **sendq/recvq 两个等待队列**（sudog 链表）+ 一把 lock。直接读 hchan.buf 无锁竞争时很快；阻塞时 goroutine 挂进 sudog，由发送方/接收方唤醒。

### 6. 向 nil channel 发送/接收/关闭？
发送 → 永久阻塞；接收 → 永久阻塞；关闭 → **panic**。对已关闭的 channel：发送 panic、接收读完剩余后返回零值（ok=false）、再关闭 panic。这九种组合是必背表（06 篇）。

### 7. 关闭 channel 为什么是广播？
close 后所有 `<-ch` 立即返回零值——**任意多接收者同时解除阻塞**；而发送只能唤醒一个且可能丢。所以「通知退出」用 close，事件扇出也用 close。

### 8. 无缓冲 channel 的同步语义？
发送发生在接收完成之前（happens-before）——发收双方「会合」，无缓冲 channel 是一次同步点。这也是「用无缓冲 channel 传递所有权零竞争」的原理。

## 二、goroutine 与调度（08/12）

### 9. goroutine 泄漏三大来源？
①阻塞在没人再发的 channel 收/没人再收的发送上；②长任务不检查 ctx 取消；③子 goroutine panic 未 recover 拖垮进程/提前退出。排查：`NumGoroutine` 监控 + pprof goroutine profile 看卡在哪个 chan 收发。

### 10. G/M/P 分别是什么？为什么要有 P？
G=goroutine（栈+调度信息），M=OS 线程，P=执行资格（本地运行队列+mcache）。P 的数量=GOMAXPROCS，M 按需创建上限 1 万。GM 模型全局队列锁竞争 → 引入 P 固化资源局部性：本地队列无锁、mcache 绑 P、work-stealing 均衡。**goroutine 轻量的根源是 G 阻塞时 M 不停**。

### 11. 调度循环的查找顺序？
runnext（刚唤醒的，约 1/61 次强插）→ 本地队列（无锁）→ 全局队列（加锁，周期性兼顾防饿死）→ netpoll → 偷其他 P 本地队列的**一半**。

### 12. channel 阻塞和系统调用阻塞的区别？
channel/网络阻塞：G 挂起，**M 换下一个 G 继续跑**（netpoller 把 fd 交给 epoll 管理）。CGO/磁盘等系统调用：**M 陪绑进内核，P 被 hand off 给别的 M**。所以大量系统调用会创建大量 M。

### 13. 抢占机制怎么演进的？
Go 1.13 前只有函数调用点的协作式抢占（纯 CPU 死循环饿死调度）；**Go 1.14 起基于信号（SIGURG）异步抢占**，纯 CPU 循环最多独占 P 约 10ms。sysmon（监控线程）负责触发。

### 14. GOMAXPROCS=1 还并发吗？
并发不并行：单 P 上 G 交错执行，抢占保证公平。Go 1.25+（Linux）GOMAXPROCS 自动感知 cgroup CPU limit（quota 向上取整、定期重读），容器配 2 核不再按宿主机 96 核跑 GC。

## 三、内存与 GC（09）

### 15. 逃逸分析决定什么？
对象分配在栈还是堆。逃逸路径：返回局部变量指针、闭包捕获、动态长度、interface 装箱、指针跨 goroutine。**逃逸不是坏事**，只优化 profiling 证明热的路径。验证：`go build -gcflags="-m -l"`。

### 16. 堆分配三级结构？
TCMalloc 思想：mcache（绑 P，无锁快路径）→ mcentral（按 sizeclass 加锁补充）→ mheap（页堆，向 OS 要）。小对象走快路径纳秒级，大对象（>32KB）直接 mheap。

### 17. 三色标记 + 混合写屏障？
白/灰/黑三色，从根标记可达对象。并发标记期间用户代码改指针，靠**混合写屏障（Yuusa 删除 + Dijkstra 插入，Go 1.8）**维持不变式：堆上写指针旧值新值都置灰，**栈全程免屏障**。STW 只剩标记开始/结束两个极短窗口（典型 <1ms）。

### 18. 写屏障为什么不上栈？
栈写太热。代价是标记开始时把所有栈标黑（STW 窗口之一）+ 栈上对象保守处理。Go 1.26 Green Tea GC：仍是三色，改为按 8KiB span 页批量扫描（页级广度优先 + 每对象 2bit 元数据 + SIMD），cache 友好，GC 开销降 10%~40%。

### 19. GOGC 语义？GOMEMLIMIT 是软限还是硬限？
目标堆 = 存活堆 × (1 + GOGC/100)，默认 GOGC=100。GOGC 大→GC 少吞吐高但堆峰值高；GOMEMLIMIT 是**软限**（逼近时强制 GC），不是 OOM 保护。容器常见组合：`GOGC=off GOMEMLIMIT=<limit×80%>`。

### 20. GC 触发条件？
①堆增长到目标（GOGC 公式）；②2 分钟强制（sysmon）；③手动 runtime.GC()；④逼近 GOMEMLIMIT。标记工人默认占 25% CPU，分配太快的 G 被 mutator assist 罚去做标记。

## 四、slice / map / interface（01/03）

### 21. slice 底层？扩容策略？
(ptr, len, cap) 三字段头，赋值传参**拷贝头不拷贝数据**。append 超 cap：`cap<256` 翻倍，之后 `newcap += (newcap+768)/4` 平滑滑向 1.25x（Go 1.18 起；1.17 及以前是 1024 阈值）。注意 sizeclass 对齐后实际 cap 可能更大。

### 22. 共享底层数组的经典坑？
`a := s[:2]; b := append(a, x)`——若 cap 够，b 直接改写 s[2]！同理两个子 slice 头写同一数组 = data race。口诀：**append 可能就地写，要隔离就完整拷贝**（copy 或 `s[:2:2]` 限三索引 cap）。

### 23. map 底层？为什么无序？
hmap 指向桶数组（2^B 个 bmap，每桶 8 槽 + overflow 链）。负载因子 6.5 触发翻倍扩容，**增量搬迁**（每次写顺带搬 1-2 桶，不是一次性 rehash）。无序：搬迁后 key 分散 + 遍历起点随机化（刻意设计，防依赖顺序）。（Go 1.24+ 内部换 Swiss Table：负载因子 7/8，group 16 槽 SIMD 加速——对外语义不变。）

### 24. map 并发读写？
**runtime 直接 fatal（throw），不可 recover**——因为 map 内部状态可能已损坏，继续跑比崩更危险。sync.Map 或 map+Mutex 解决。

### 25. interface 底层？nil != nil 的原理？
二元组：空接口 eface{类型指针, 数据指针}，非空 iface{itab, 数据指针}。`var p *T = nil; var i any = p` → i 是「(类型=T, 值=nil)」，`i != nil` 成立——**有类型无值不是 nil 接口**。判空要 `reflect.ValueOf(i).IsNil()` 或类型断言后判。

### 26. 方法集：T 和 *T 的区别？
*T 的方法集包含值方法和指针方法；T 只有值方法。所以 `*T` 实现的接口，T 不实现（T 存接口时无法自动取址——T 可能不可寻址）。反射与泛型的性能姿势：边界做一次、缓存结果，热循环走预编译路径。

## 五、锁与原子操作（07）

### 27. Mutex 公平吗？
非绝对公平。正常模式：被唤醒 waiter 与新来者竞争（新来者在 CPU 上常赢），吞吐高；waiter 等超 **1ms** 切**饥饿模式**：锁直接交接队头，新来者不自旋不抢；拿到锁时等待 <1ms 或是队尾切回正常。双模式 = 吞吐与公平的折中。

### 28. Unlock 的三个冷知识？
①无属主校验——他人 Unlock 合法（但禁止）；②未加锁 Unlock 是 **fatal 不可 recover**；③Mutex 不可复制（含 Mutex 的结构体也不可复制，vet copylocks 检查）。

### 29. 自旋的条件？
多核 && GOMAXPROCS>1 && 本 P 本地队列为空 && <4 次 && 非饥饿模式。本质赌临界区几十 ns 内结束，用空转换微秒级的调度唤醒。

### 30. RWMutex：写锁排队后新读者？
**被阻塞**（Lock 把 readerCount 打负，RLock 见负睡 readerSem）→ 写者不饿死。推论：读锁**不能升级**（持读锁再 Lock 死锁）、**能降级**（Lock→RLock→RUnlock→Unlock）。RWMutex 不一定快：单次成本更高，读临界区 <100ns 是负优化，微秒级+读写比 >10:1 才赚。

### 31. WaitGroup 协议？
Add 在启动方先于 go；子 goroutine defer Done；两条 fatal：Wait 后并发 Add（misuse）、Done 多于 Add（负计数）。归零后可复用但有竞态窗口。需要超时/错误收集/并发上限 → errgroup.WithContext + SetLimit。

### 32. atomic 的边界？
**只保护一个机器字**——两个 atomic 字之间无原子性，二元状态必须打包（位运算/atomic.Pointer[T] 整体换快照）或上锁。无原子浮点 Add；atomic.Value 必须同类型，泛型时代用 atomic.Pointer[T]。Go 只有一种内存序（happens-before），Store/Load 配合即 release/acquire。

### 33. sync.Pool 语义？
**缓存不是容器**：Get 无保证（New 必须给）、每次 GC 清空（1.13+ victim 两代，对象活两个 GC 周期）、Put 后再 Get 可能拿到同一对象（**放回前必须 Reset**）。定位：减 GC 压力（bytes.Buffer/大对象），不是缓存/连接池/free list。

### 34. sync.Map 适用场景？
①key 写一次读多次且集合稳定（注册表/路由）；②多 goroutine 写不相干的 key。内部：Go 1.23- 是 read/dirty 双 map + misses 晋升；**Go 1.24 起 HashTrieMap**（写锁子树级）。写多场景 map+Mutex 更快；没有 len()。

### 35. 锁 vs channel 怎么选？
锁保护**共享状态的不变量**；channel **传递数据/所有权/事件**。围绕一份数据反复读写 → 锁；流水线生产消费 → channel。锁保护的是不变量不是代码行——先写清楚约束，锁边界自然出来。

## 六、context 与错误处理（10）

### 36. context 取消的传播机制？
With* 把子 ctx 挂进父的 children；cancel() = 关自己 done channel + 递归 cancel children + 从父摘除。**Done 是 channel 关闭不是发值**——广播语义，任意多监听者同时解除阻塞。父先取消则新子挂树时立即自取消。

### 37. 为什么必须 defer cancel()？
两重泄漏：runtime timer 到超时才释放；cancelCtx 挂在父 children 里整棵子树无法 GC。高频派生不 cancel = goroutine/RSS 缓慢上涨的经典来源。

### 38. 子超时能比父长吗？Background vs TODO？
不能，Deadline 取更早者。Value 继承全部、取消单向（父→子）。Background = 主动选根（main/init/测试）；TODO = 占位未定。行为一致，给人看的。

### 39. Value 的边界？
只放请求级横切数据（traceID/身份），key 用私有类型；业务参数必须显式在签名里——偷读 Value = 隐式依赖 + 不可测试。收尾工作要 Value 不要取消：`WithoutCancel`（Go 1.21+）。

### 40. 取消 ctx 能停掉 CPU 循环吗？
不能。context 是**协作式**取消：只唤醒阻塞在 Done()/支持 ctx 的 IO 上的代码；CPU 循环必须自己周期检查。Go 没有抢占式 kill goroutine。

### 41. errors.Is vs errors.As？
Is 沿 Unwrap 树找**相等**节点（哨兵：io.EOF/context.Canceled）或调用节点的 Is 方法；As 找**可赋值类型**的节点取结构化字段。前提：包装用 **%w**（成链）不用 %v（断链）。Go 1.20+ 多 %w 与 errors.Join 成树。

### 42. 为什么禁止字符串判错？
`strings.Contains(err.Error(), "timeout")` 依赖消息文本——改版/本地化/中间层重写即失效，且编译期不报错。正解：errors.Is(err, context.DeadlineExceeded) / errors.As(err, &netErr)。

### 43. panic/recover 的规则？
recover 必须在 **defer 的函数体内直接调用**（defer helper() 里调无效）；**只救当前 goroutine**（子 goroutine panic 外层拦不住，进程退出）。panic 留给程序员错误与初始化致命；可预期失败用 error。库 API 永不 panic。吞 panic 前想清楚：锁没释放、map 写一半——状态未知比崩溃危险。

### 44. defer 四个陷阱？
①参数**立即求值**拷贝（要延迟就包闭包）；②命名返回值可被 defer 改写（recover 转 error 的标准姿势）；③循环内 defer 累积到函数结束（抽函数）；④LIFO。性能：Go 1.13 开放编码 defer ~1ns，「defer 慢」是老黄历。

## 七、性能调优（11）

### 45. 调优闭环三步？
压测复现 → pprof 定位热点 → benchmark 前后对比（benchstat）验证。没测量不优化，没对比的优化是自我感动。

### 46. 优化性价比排序？
算法/数据结构 > 减少分配（预分配/复用）> 逃逸与内联治理 > sync.Pool > 微优化。CPU profile 里 GC 标记占 30% 时优化业务循环是白费劲——先看全局再看局部。

### 47. 线上 CPU 高的排查路径？
`import _ "net/http/pprof"` → `go tool pprof http://host/debug/pprof/profile?seconds=30` → top/cum → flame。内存：heap profile 看 alloc_objects/alloc_space 找分配热点。goroutine 暴涨：goroutine profile 看卡在哪个收发。

### 48. GC 调优决策？
先 gctrace 看频率与耗时：GC 频繁（CPU 被 GC 吃）→ GOGC 调大；内存吃紧 → GOMEMLIMIT 兜底；容器 OOM → GOMEMLIMIT=limit×80%。开关组合取舍见 09 篇 §5 表。

## 八、string 底层（02）

### 49. string 的底层结构？
(数据指针, 长度) 二字段头。**无 `\0`、长度显式存储**——可存任意二进制。子串 s[i:j] 零拷贝（只造新头），但持有子串会钉住整个大字符串（要独立就 strings.Clone）。

### 50. 为什么 string 不可变？得到什么？
共享安全（传值零风险）、字面量驻留（相同常量一份只读内存）、map key 哈希稳定。代价：所有「修改」都新分配——循环 `s += x` 是 O(n²)，正解 strings.Builder + Grow（String() 用 unsafe.String 零拷贝导出）。

### 51. len(s) 返回什么？
**字节数**。字符数是 utf8.RuneCountInString。for range 按码点迭代、索引是**字节偏移**；s[0] 是字节不是字符；s[:4] 按字节截断会切碎多字节字符（碎码）。

### 52. string ↔ []byte 什么时候免拷贝？
默认拷贝（不可变契约）。两个编译器特例：①`[]byte(s)` 不逃逸且不被修改 → 直接引用底层；②`m[string(b)]` map 索引就地比较免分配。热路径原则：流水线统一类型，只在边界转一次。

### 53. []byte 为什么不能做 map key？
slice 头不可比较（不满足 comparable）。string 不可变 + == 是 memcmp（先比长度）+ 哈希稳定，天生 key。[N]byte 定长数组按值可比也行（网络库零分配 key 惯用法）。

### 54. unsafe.String 零拷贝的红线？
绝不修改底层（可能污染驻留常量、破坏 map key 哈希）；生命周期与源绑定（源回收即悬挂视图）；只在边界库少数文件。标准库正面示范：strings.Builder.String()。

## 九、泛型（04）

### 55. 泛型的实现机制？
**GC shape 分组 + 字典**：内存布局相同的类型（所有指针类型一组）共享一份机器码，shape 内差异靠编译期生成的字典（类型元数据、操作函数、方法入口）运行时传递。非 C++ 全量展开（膨胀可控），非 Java 全擦除（值类型零装箱、运行时有类型信息）。

### 56. `~` 是什么？
近似约束：`~int` 匹配所有**底层类型**为 int 的类型——`type UserID int` 通过。不带 ~ 只匹配 int 本身。代价：~int 集合内无法再按方法区分成员。

### 57. comparable 的精确语义？
「== 可用且不 panic」的**类型集合**：数值/string/指针/channel/数组/纯值 struct。不含 slice/map/function（== 只能与 nil 比）。`func Keys[K comparable, V any]` 这类签名的基础。

### 58. 为什么方法不能有类型参数？
方法级类型参数会让**接口满足性检查不可判定**（S 要实现多少个 Map[U] 才算实现接口）。绕法：包级泛型函数——slices 包全是这个风格（slices.SortFunc 而不是 xs.SortFunc）。

### 59. 泛型 vs 接口怎么选？
同一**算法**对多类型（容器/工具函数）→ 泛型：编译期约束、值语义零装箱。运行时多态/依赖注入/mock/异构集合 → 接口。组合：泛型管类型维度、接口管行为维度（泛型结构体里存接口字段）。

### 60. 泛型一定比接口快吗？
通常不慢：省装箱（int 装 any 逃逸即堆分配，>255 无小整数缓存）；字典间接 vs itab 分发相当或略快。但泛型体内对 T 的操作经字典间接、部分内联失效——性能敏感处 benchmark 说话。

### 61. Go 1.21+ 标准库泛型工具？
slices（Sort **不稳定**/Contains/Index/Delete/Clone/Equal）、maps（Keys/Values 返回 **Go 1.23+ 迭代器** `func(yield func(K,V) bool)`、Copy/DeleteFunc）、cmp（Compare、Ordered）。先查标准库再手写。

**并发**：data race 三要素 → happens-before → channel 底层（buf+两个 sudog 队列）→ 关闭是广播 → GMP（P=GOMAXPROCS，M 按需，work-stealing 偷一半）→ 1.14 信号抢占 → 泄漏三来源。
