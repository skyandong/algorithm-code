# 泛型

> **核心认知：** Go 泛型 = 「**类型参数 + 类型集约束**」——函数和类型的签名里可以声明类型参数（`[T any]`），约束不再是「实现了哪些方法」而是「**属于哪些类型的集合**」（union、`~` 近似、comparable）。它解决的是 interface 的两个结构性缺陷：**装箱逃逸**（值进接口要分配，见 `03` 篇）和**丢失静态类型**（取出来要断言）。实现上是 **GC shape 分组 + 字典**：所有指针类型共享一份机器码、不同底层类型各一份——所以泛型不是 C++ 式全量模板展开，代码膨胀可控，但值类型操作要多一次字典查找。工程定位：**容器、算法、工具函数**用泛型；**多态行为（不同类型做不同事）**仍然用接口。

按 Go 1.26 语义说明（泛型 Go 1.18 引入，标准库 slices/maps Go 1.21 转 standard）。前置知识：interface 二元组与装箱见 `03-interface与反射.md`。

## 1. 动机：interface 的两个结构性缺陷

Go 1.18 之前「写一个适用于多种类型的函数」只有两条路，都有硬伤：

```go
// 路 A：interface{}——装箱 + 断言
func MaxI(a, b interface{}) interface{} {
    // 取出来要断言，运行时才炸；int 装箱 = 堆分配（03 篇）
}

// 路 B：代码生成 / 手写 N 份 MaxInt/MaxFloat64...
// 维护 N 份逻辑，改一处漏一处
```

**缺陷一：装箱。** 值进接口头（`03` 篇 eface）要么逃逸堆分配，要么走 0~255 的小整数缓存——热路径上这是纯税。

**缺陷二：丢失静态类型。** `interface{}` 把编译期检查降级成运行时断言，错误从编译期推迟到线上。

泛型把两个问题同时解决——**编译期单态化的类型安全 + 零装箱的值语义**：

```go
func Max[T cmp.Ordered](a, b T) T {
    if a > b {  // T 有 <，编译期已由约束保证
        return a
    }
    return b
}
Max(1, 2)        // 推断 T=int，值语义，无装箱
Max(1.5, 2.5)    // T=float64，同一份源码
```

注意边界：泛型解决的是「**同一算法适用于多种类型**」（容器/算法/工具）；不解决「**同一调用点混装不同类型**」——那本质是动态分发，仍是 interface 的领地。

## 2. 语法全景：参数、推断、显式实例化

```go
// 类型参数列表 [T1 E1, T2 E2]：T 是参数名，E 是约束（constraint，本质是接口类型）
func Map[T, U any](xs []T, f func(T) U) []U {
    r := make([]U, 0, len(xs))
    for _, x := range xs {
        r = append(r, f(x))
    }
    return r
}

// 泛型类型：字段/方法里用 T
type Stack[T any] struct{ items []T }

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) } // 接收者带 [T]
func (s *Stack[T]) Pop() (T, bool) {
    if len(s.items) == 0 {
        var zero T    // zero value 也能拿到
        return zero, false
    }
    v := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return v, true
}

// 实例化：推断（多数场景）或显式（歧义/可读性）
Map([]int{1, 2}, strconv.Itoa)   // T=int, U=string 推断
Map[int, string](nums, f)        // 显式指定
s := Stack[int]{}                // 泛型类型必须显式
```

细节速记：

- **约束即接口**：`any` 是 `interface{}` 的别名（`03` 篇装箱规则不适用于类型参数位——约束位置不装箱）；
- **`var zero T`** 拿零值是惯用法（不能写 `nil`——T 可能不是可空类型）；
- 泛型函数的**方法不能再加类型参数**（§5），这是目前最大的表达力缺口；
- 类型推断支持从实参、赋值目标、**无名函数的字面量**推（Go 1.21+ 推断规则大幅增强，大部分场景不用写显式参数）。

## 3. 类型集：约束的语义升级

Go 1.18 对 interface 做了语义扩展：**接口现在描述一个类型集合（type set）**——凡是落在集合里的类型都满足约束。

```go
// 1) 方法约束（传统）：实现了 Error() 的类型
type Stringer interface{ String() string }

// 2) 类型 union：集合运算
type Number interface {
    ~int | ~int64 | ~float64     // 底层类型是这三者之一
}

// 3) 方法 + 类型 混合约束
type StringableNumber interface {
    ~int | ~float64
    String() string              // 且实现了该方法
}

// 4) 内置约束
// any      = interface{}        任意类型
// comparable                  可用 == 比较的类型（是「集合」不是「方法」！）
// cmp.Ordered                 ~int|~uint|~float|~string 全体有序类型
```

**`~` 近似约束是必考点**：

```go
type UserID int          // 底层类型 int，但它是新类型
type Number interface{ int }        // UserID 不满足！（严格匹配 int 本身）
type Number interface{ ~int }       // UserID 满足（底层类型是 int 即可）
```

WHY 设计成这样：严格匹配会让「为语义贴类型标签」（`UserID`、`Celsius`）的惯例在泛型里全部失效；`~` 放宽到底层类型，代价是失去「新类型的额外方法约束」（`~int` 的集合是所有底层为 int 的类型，无法再要求它们实现某方法之外的区分）。

**comparable 的精确语义**：`==` **可用且不 panic** 的类型集合——string、数值、指针、channel、数组、只含这些的 struct；**不含 slice/map/function**（它们 == 只能和 nil 比，会 panic，Go 1.20 起 comparable 约束允许但 == 仍限 nil 比较）。

**约束嵌套**：约束里可以再嵌约束（`interface{ Number; String() string }`），组合出精确的类型集合。

## 4. 实现：GC shape 分组 + 字典

面试深水区。Go 没有走两个极端（C++ 全量模板展开 / Java 全擦除），而是中间路线：

**GC shape（形状）**：内存布局与 GC 需要的元信息相同的类型归为一组。关键分组规则：

- **所有指针类型同一个 shape**（GC 都只需跟踪一个指针）；
- `int`、`uint64`、`float64`、`struct{ x int }`……**不同底层类型各是一个 shape**。

**编译策略**：每个 **shape × 泛型函数** 生成一份机器码；shape 内不同具体类型（如 `*Cat` 和 `*Dog` 都在指针 shape）共享这份代码，**通过运行时「字典」（dictionary）传递差异**——字典是编译期生成的只读表：类型元信息、操作函数（怎么 ==、怎么 hash）、方法的实际入口。

```text
Map[T any](...) 的实例化产物：
  Map[指针shape] 一份机器码 + 字典：[*Cat → {cat元数据, ...}, *Dog → {...}]
  Map[int]      一份机器码（int 自己的 shape，字典可能退化为常量折叠）
```

工程推论：

1. **代码膨胀可控**：N 个具体类型 ≈ N 个 shape 份代码，不是 N 份全展开（指针类型们合并成一份）；
2. **值类型泛型代码多一层字典间接**：调用 T 的方法要走字典查入口——比接口动态分发略快（少一次 itab 查找）或相当，**但省掉装箱**；
3. **指针类型参数是最优形状**：`*T` 全体共享一份代码，泛型容器存 `*T` 时代码最少；
4. **闭包/内联受限**：泛型函数体内对 T 的操作经字典间接，部分内联优化失效——`-gcflags="-m"` 观察（`11` 篇总纲：先测再优化，不要凭「泛型慢/快」的传言决策）。

**和 Java 擦除的对照**（面试常问）：Java 泛型擦成 Object（值类型必须装箱、运行时拿不到 T）；Go 保留 shape 级实例化 + 字典，值类型零装箱、运行时可通过字典拿到类型信息（`reflect` 对实例化后的泛型类型完全可见）。

## 5. 限制：方法不能有类型参数

```go
type Stack[T any] struct{ items []T }

// ✗ 编译错误：method cannot have type parameters
func (s *Stack[T]) Map[U any](f func(T) U) *Stack[U] { ... }
```

规则：**类型可以有类型参数，方法不能**（接收者用 T 可以，方法自己再声明 U 不行）。WHY：接口满足性检查会变得不可判定——`S` 要实现多少个 `Map[...]` 才算实现接口？这是类型论层面的 decision problem，设计者选择先砍掉。

**工程绕法**（都是把「方法」升级成「包级函数」）：

```go
// 绕法一：包级泛型函数（slices 包就是这个风格）
func StackMap[T, U any](s *Stack[T], f func(T) U) *Stack[U]

// 绕法二：返回接口
func (s *Stack[T]) Map(f func(T) any) []any // 丢失静态类型，不推荐

// 需要运行时再决定类型参数的场景，老老实实 interface/反射（03 篇）
```

其他值得知道的限制：

- 类型参数不能用在**类型别名**上（`type S[T any] = Stack[T]` ✗）；
- 泛型结构体**不能做枚举式常量泛型**、switch 对 T 只能按约束允许的操作来；
- **约束里的 union 成员不能有方法**的重复定义冲突（如 `~int | MyInt` 且 MyInt 有方法）。

## 6. 标准库 slices / maps / cmp

Go 1.21 起泛型工具从 `x/exp` 转正，**日常 90% 的「手写泛型」需求已经被覆盖**——先查标准库再动手：

```go
import "slices"
import "maps"
import "cmp"

// slices：排序列表全家桶
slices.Sort(xs)                          // cmp.Ordered
slices.SortFunc(people, func(a, b Person) int { return cmp.Compare(a.Age, b.Age) })
slices.Contains(xs, 42)
slices.Index(xs, 42)
i, found := slices.BinarySearch(xs, 42)
xs = slices.Delete(xs, 1, 3)             // 原地删 [1,3)
slices.Reverse(xs)
slices.Clone(xs)                         // 注意：浅拷贝
slices.Equal(a, b)

// maps：map 的键值操作
for k := range maps.Keys(m) { ... }      // Go 1.23+：返回迭代器（func(yield)），零分配
for v := range maps.Values(m) { ... }
maps.Copy(dst, src)
maps.DeleteFunc(m, func(k, v) bool { return v < 0 })

// cmp：比较原语
cmp.Compare(a, b)                        // -1/0/1，自定义排序的积木
```

**迭代器（Go 1.23+）** 是泛型的最新应用面：`func(yield func(K, V) bool)` 标准签名让 map/链表/懒序列都能被 `for range` 直接消费——`push 模型`（数据推给 yield）替代 `pull 模型`（调用方反复拉），和泛型容器配合是现代 Go 库的标配写法。

实操提醒：`slices.Sort` 是**不稳定的**（快排变种 pdqsort），需要保序用 `slices.SortStableFunc`；这些函数吃 `cmp.Ordered`/自定义比较，**值语义零装箱**。

## 7. 泛型 vs 接口：选型决策

| 维度 | 泛型 | 接口 |
|---|---|---|
| 解决什么 | 同一**算法**对多种**类型**复用 | 同一**行为**由多种**实现**提供 |
| 类型检查 | 编译期（约束保证操作合法） | 编译期方法集 + 运行时动态分发 |
| 值语义 | 零装箱，T 就是值 | 装箱进 eface/iface（`03` 篇） |
| 类型信息 | 字典携带，实例化后静态 | itab 动态查 |
| 异构集合 | ✗（T 在一个实例里固定） | ✓（[]any 装不同类型） |
| 运行时插件式实现 | ✗ | ✓ |

决策三问：

1. **「不同类型做的是同一件事还是不同的事？」** 同一件事（比较、求和、入栈出栈）→ 泛型；不同的事（日志后端写文件/写网络）→ 接口；
2. **「要在运行时换实现吗？」** 要（依赖注入、mock、插件）→ 接口；不要 → 泛型更直接；
3. **「调用点混装多种类型吗？」** 混（一个容器里放 int 和 string）→ 只能 any+断言/反射。

**两者经常组合**：泛型容器内部用接口约束行为（`type Cache[K comparable, V any] struct { evict EvictPolicy[V] }`）——泛型管类型维度，接口管行为维度，各司其职。

反模式清单：

- 「泛型 interface 化」：处处 `[T any]` 然后函数体里 `any(x).(int)` ——比直接写接口还糟；
- 「过早泛化」：只有一种实现时先写具体类型，第二次需求出现再抽象（Rule of Three 的 Go 版）；
- 「约束过宽」：能写 `cmp.Ordered` 就别写 `any` + 运行时断言；约束越精确，函数体能用的操作越多、越安全。

## 8. 面试高频

**Q1：Go 泛型的实现机制？**
GC shape 分组 + 字典。内存布局相同的类型（所有指针类型）共享一份机器码；shape 内差异通过编译期生成的字典（类型元数据、操作函数、方法入口）运行时传递。不是 C++ 全量展开（膨胀可控），不是 Java 全擦除（值类型零装箱、运行时有类型信息）。

**Q2：`~` 是什么意思？**
近似约束（approximation）：`~int` 匹配所有**底层类型**是 int 的类型（含 `type UserID int`）。不带 ~ 的 `int` 只匹配 int 本身。代价：~int 集合无法再按方法区分成员。

**Q3：comparable 是什么？**
「== 可用且不 panic」的类型集合：数值/string/指针/channel/数组/纯值 struct。不含 slice/map/function（== 只能与 nil 比）。定义 `func Keys[K comparable, V any](m map[K]V)` 这类签名的基础。

**Q4：泛型和接口怎么选？**
同一算法对多类型（容器/算法/工具）→ 泛型，值语义零装箱、编译期约束；运行时多态/依赖注入/异构集合 → 接口。组合用法：泛型管类型维度、接口管行为维度。

**Q5：为什么方法不能有类型参数？**
方法级类型参数会让接口满足性检查不可判定（S 要实现多少 Map[U] 才算实现接口）。绕法：包级泛型函数（slices 包风格）。

**Q6：泛型比 interface 快吗？**
通常不慢：省装箱；shape 内字典间接 vs itab 分发相当或略快。但泛型体内对 T 的操作经字典间接，部分内联失效——性能敏感处用 benchmark 说话，别信传言。

**Q7：Go 1.21+ 标准库有哪些泛型工具？**
slices（Sort/Contains/Index/Delete/Clone/Equal…，Sort 不稳定）、maps（Keys/Values 返回 Go 1.23+ 迭代器、Copy、DeleteFunc）、cmp（Compare、Ordered）。先查标准库再手写。

**Q8：`var zero T` 和 nil 有什么区别？**
T 的约束若是 any，T 可能是不可空类型（int/struct），nil 不合法；`var zero T` 统一拿到零值，是泛型函数里处理「空/缺省」的惯用法。

**Q9：迭代器和泛型怎么配合？**
Go 1.23 标准化 `func(yield func(K,V) bool)` 迭代器：泛型容器暴露 Keys()/All() 等零分配迭代方法，调用方 for range 直接消费——maps.Keys、slices.Values 都是此模式。
