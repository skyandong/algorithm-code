# 性能调优实战：从 benchmark 到 pprof 的完整闭环

> **核心认知：** 性能调优是一个闭环，不是一次灵光乍现——「压测入口（复现问题）→ pprof 定位（找到热点）→ 基准验证（证明改对了）」。没测量之前的优化是猜测，没基准对比的优化是自我感动。优化动作永远按性价比排序：算法/数据结构 > 减少分配 > 逃逸与内联治理 > sync.Pool > 位运算级别的微优化。Go 的工具链（benchmark / pprof / trace）已经把测量的成本降到极低，稀缺的是按正确顺序使用它们的纪律。

本文按 Go 1.26 语义；版本分界处单独标注。前置知识：逃逸分析、MemStats、GOGC 基础见 `09-内存管理与GC.md`，slice/map 扩容机制见 `01-slice与map底层.md`。

## 1. 调优总纲：先测量，后优化

三条铁律：

1. **用户抱怨的是延迟和资源，不是某行代码**——先量化症状（P99？CPU？RSS？GC 频率？），再定位代码。
2. **先看全局再看局部**——CPU profile 里 GC 标记占 30% 时，优化业务循环是白费劲。
3. **每次优化必须可验证**——benchmark 前后对比（benchstat），线上灰度观察指标回落。

闭环全流程（本文主线）：

```text
① 压测入口      wrk / vegeta / k6 恒定流量复现问题（P99 锯齿 / CPU 打满 / 内存上涨）
    ↓
② 粗定位        GODEBUG=gctrace=1、runtime metrics 看 GC 频率与触发原因
    ↓
③ pprof 细定位  CPU profile 找热点 / heap(alloc_space) 找分配源 / goroutine 看泄漏
    ↓
④ 修复          按 §3 性价比排序动手
    ↓
⑤ 验证          go test -bench + benchstat 证明 → 灰度 → 观察 P99 / GC 周期回落
```

WHY：跳过 ①② 直接猜代码是最常见的坑——「我觉得这里慢」在 profile 面前经常被打脸；跳过 ⑤ 则无法区分「真的优化了」和「本机噪声波动」。

## 2. benchmark 规范

### 2.1 标准命令

```bash
go test -bench=. -benchmem ./...
# -benchmem：额外输出 B/op 与 allocs/op
#   分配指标比耗时更稳定、更有指导性——先降 allocs/op，往往耗时自动跟着降

go test -bench=BenchmarkFoo -benchtime=2s -count=10 ./... | tee old.txt
# -count≥10 + benchstat 才有统计意义；-benchtime=100x 可固定迭代次数
```

输出解读：

```text
BenchmarkFoo-10   1523418   786.1 ns/op   412 B/op   6 allocs/op
                  ↑次数      ↑每次耗时     ↑每次分配字节  ↑每次分配次数
```

### 2.2 b.N 的自适应机制

框架先以 `b.N=1` 试跑拿到单次耗时，据此预估能让总时长达到 benchtime（默认 1s）的 N 再跑；若实际耗时仍明显偏离目标则继续调整重跑。因此：

- **同一个 benchmark 函数可能被完整执行多次**，函数体内不要有跨次累积的状态（全局计数、已关闭的 channel 等）。
- 手动给 `b.N` 赋值是无效操作，永远让框架自适应。

### 2.3 sink：防止死代码被优化

```go
var sinkInt int // 包级 sink：结果被"使用"，编译器不能删

func BenchmarkFib(b *testing.B) {
    for i := 0; i < b.N; i++ {
        sinkInt = fib(20)
    }
}
```

WHY：Go 编译器目前对跨函数调用很保守（不假设无副作用），但内联后的纯计算可能被 SSA 常量折叠消除；写入包级全局变量一定有副作用，是零成本的保险，也是社区标准写法。

### 2.4 计时器控制：ResetTimer / StopTimer / StartTimer

```go
func BenchmarkProcess(b *testing.B) {
    data := loadHugeFile() // setup 可能秒级
    b.ResetTimer()         // 清零已消耗的时间和内存计数
    for i := 0; i < b.N; i++ {
        process(data)
    }
}

func BenchmarkWithPerIterSetup(b *testing.B) {
    for i := 0; i < b.N; i++ {
        b.StopTimer()
        in := generateInput(i) // 每次迭代的 setup：排除计时
        b.StartTimer()
        process(in)
    }
}
```

注意：StopTimer/StartTimer 自身有数百 ns 开销，迭代体极小时会失真——把 setup 移出循环或加大每次迭代的工作量。Go 1.24+ 直接用 `b.Loop()`（见 2.6）。

### 2.5 子基准 b.Run 与并行基准 b.RunParallel

```go
func BenchmarkInsert(b *testing.B) {
    for _, n := range []int{10, 1_000, 100_000} { // 输出形如 BenchmarkInsert/n=100000
        b.Run(fmt.Sprintf("n=%d", n), func(b *testing.B) {
            for b.Loop() {
                sinkInt = insertN(n)
            }
        })
    }
}

func BenchmarkMutexCounter(b *testing.B) {
    var mu sync.Mutex
    var n int
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() { // 多个 goroutine 按 GOMAXPROCS 并行消费迭代
            mu.Lock()
            n++
            mu.Unlock()
        }
    })
    sinkInt = n
}
```

RunParallel 测的是吞吐与争用（典型：带锁结构、sync.Pool）；报出的 ns/op 是墙钟时间摊到每次迭代。**并行基准里不要写包级 sink**（多 goroutine 同时写会 data race），用局部变量收尾再合并。

### 2.6 Go 1.24+：b.Loop()

```go
func BenchmarkWork(b *testing.B) {
    setup()
    for b.Loop() { // 自动管理 N + 排除循环外 setup 计时 + 防循环体被优化掉
        work()
    }
}
```

`b.Loop()` 一次解决 2.3/2.4 两个问题（框架层面保证循环体不被消除），循环体内不要再引用 b.N 或调用 ResetTimer。新代码首选它。

### 2.7 benchstat：统计显著性

```bash
go install golang.org/x/perf/cmd/benchstat@latest
go test -bench=. -count=10 ./... > old.txt   # 优化前
# ... 改代码 ...
go test -bench=. -count=10 ./... > new.txt   # 优化后
benchstat old.txt new.txt                    # 输出 p-value，差异是否显著
```

## 3. 优化性价比排序（从高到低）

| 序 | 手段 | 典型收益 | 适用前提 |
|---|---|---|---|
| 1 | 算法 / 数据结构 | 数量级（O(n²)→O(n log n)） | 有热点数据可换结构 |
| 2 | 减少分配（预分配/复用） | 分配密集路径 2~10× | allocs/op 或分配速率高 |
| 3 | 逃逸与内联治理 | 10%~30% | 热函数、微基准 |
| 4 | sync.Pool | 大对象热路径显著 | 高频、大对象、无状态残留 |
| 5 | 位运算等微优化 | 1%~5% | 最后手段 |

WHY 这个排序：算法是**乘法关系**（数据量翻倍差距翻倍），分配优化是常数级改善但覆盖面广；位运算只在前面都做完后才值得碰。分配的代价不只是 malloc 本身（几十 ns），还有 GC 标记压力与 cache miss。

### 3.1 算法 / 数据结构

- 线性查找 map → slice 下标；O(n) 去重 → map/set；反复排序 → 维护有序结构。
- `sort.Search` 手写二分、`slices.SortFunc` 泛型零拷贝排序替代 `sort.Slice` 的 interface 装箱。

### 3.2 减少分配

**预分配**：

```go
s := make([]int, 0, len(keys))        // append 不再触发 ~20 次扩容
m := make(map[string]int, len(rows))   // 不触发渐进式扩容搬迁
sb := strings.Builder{}; sb.Grow(4096) // 拼接前预留
```

WHY：append 容量不足时新开底层数组 + memcpy（小 slice 约 2 倍、大 slice 约 1.25 倍增长），累计分配约为最终大小的 2 倍；map 扩容桶组翻倍且渐进搬迁期间新旧桶并存、读路径变慢。细节见 `01-slice与map底层.md`。

**string 与 []byte 互转的分配成本**：

```go
b := []byte(s) // 堆分配 len(s) 字节 + 拷贝
s2 := string(b) // 同样
```

零拷贝只在编译器认得的少数内建场景：

```go
m[string(b)]           // map 索引：不分配
string(b) == "ping"    // 比较：不分配
switch string(b) { … } // switch：不分配
```

unsafe 做法（Go 1.20+ `unsafe.String` / `unsafe.SliceData`）的红线：转换后**严禁修改原 []byte**——string 的不可变性是语言级契约，map key 的哈希缓存、编译器优化都建立在它上面；改了底层，作为 map key 使用过的 string 会直接产生未定义行为。只允许「确认只读 + 生命周期可控 + 热路径证明值得」的场景。

**大结构体传参：值 vs 指针的实测取舍**：

- 指针传参本身极便宜（8B），但 `&x` 可能让 x 逃逸到堆：一次堆分配 + GC 追踪 + cache miss。
- 值传递零 GC 压力，但大 struct 每次调用都复制。
- 经验阈值：**< 64B 值传递无感；> 1KB 考虑指针；中间地带用 benchmark 定**（本篇实验第 4 节直接对比）。
- slice/map/chan/string 本身就是小 header（slice 24B），直接传值。

WHY：逃逸与否取决于「callee 是否让指针活过 caller 的栈帧」——过程间分析的结果，不是「写了 * 就上堆」。

### 3.3 内联与逃逸

```bash
go build -gcflags="-m" ./...        # 逃逸判定 + 内联决策一起看
go build -gcflags="-m -m" ./...     # 更详细的推导链
```

输出示例：

```text
./handler.go:23:9:  &User{} escapes to heap
./handler.go:30:13: ... argument does not escape
./util.go:12:6:     can inline add
```

- 常见逃逸源：返回局部变量指针、interface 装箱（fmt 系列参数）、发送指针到 channel、闭包捕获外流、存入逃逸的容器。详见 `09-内存管理与GC.md` §1。
- 内联预算约 80 个节点：小函数自动内联，消掉调用开销，还让逃逸分析能跨函数边界做准（`return &local` 的小函数被内联后，若调用处不外流则栈分配）。
- 反向认知：**逃逸不一定是坏事**。栈空间有限，把大对象强行留在栈上会引发频繁 morestack；先 profile 确认热，再治逃逸。

### 3.4 sync.Pool

机制速览（详见 `09-内存管理与GC.md`）：Get 顺序为私有槽 → 本 P shared → 偷其他 P → victim → New；**GC 时 local 转入 victim、下一轮 GC 丢弃 victim——对象最多活两轮 GC**，所以 pool 是「复用」不是「缓存」。

- 适合：高频 + 单对象大（≥ 数 KB）+ 并发热路径（如每请求的编解码 buffer）。
- 不适合：小对象（分配本来约 25ns，池的原子操作开销可能反超）、需要精确生命周期、容量差异大的对象（自己做分级池）。
- Put 前手动 reset 指针字段——否则被池对象引用的内容会跟着多活两轮 GC。

### 3.5 微优化（最后才做）

位运算替乘除、`for i := range n`（Go 1.22+）省一个循环变量、避免 `defer` 在超热循环里堆积……收益 1%~5%，只在前面全部做完、且 profile 证明该函数就是瓶颈时才值得。

## 4. pprof 实战

### 4.1 挂载到 debug 端口

```go
import _ "net/http/pprof" // 注册到 DefaultServeMux

func main() {
    go func() {
        // 只绑 localhost：生产经 sidecar/socat/kubectl port-forward 访问
        // 若必须暴露：独立端口 + 网络策略 + 鉴权（pprof 无内置鉴权，暴露=信息泄露）
        log.Println(http.ListenAndServe("localhost:6060", nil))
    }()
    serve() // 业务照常
}
```

注意：业务框架若用自定义 mux，需要单独起一个裸 `http.Server`（DefaultServeMux 上才是 pprof 路由）。

### 4.2 四种核心 profile

```bash
# CPU 热点（默认 100Hz 采样，30s ≈ 3000 个样本）
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30

# 内存：默认 inuse_space；分配压力（GC 频率问题的根源）看 alloc_space
go tool pprof -sample_index=alloc_space http://localhost:6060/debug/pprof/heap

# goroutine 全量栈（debug=2 含每个 g 的状态、等待时长、卡点）
curl 'http://localhost:6060/debug/pprof/goroutine?debug=2' > g.txt

# 阻塞（默认关闭，需先 runtime.SetBlockProfileRate(10000) 开启采样）
go tool pprof http://localhost:6060/debug/pprof/block
```

| profile | 回答的问题 | 关键看什么 |
|---|---|---|
| **CPU** | CPU 时间烧在哪 | top 的 flat/cum；`gcBgMarkWorker` 占比高 → 不是 CPU 问题而是分配问题，转 heap(alloc_space) |
| **heap** | 内存分配/存活在哪 | `inuse_space` 找泄漏（当前存活）；`alloc_space` 找 GC 压力（累计分配） |
| **goroutine** | 卡在哪、数量对不对 | debug=2 完整栈；数量随时间线性涨 = 泄漏 |
| **block** | 等在哪（锁/channel） | 记录 sync.Mutex/Channel 阻塞事件，不含 syscall/网络 IO |

### 4.3 交互命令与对比分析

```text
(pprof) top10      # 按样本量排序，flat 是函数自身、cum 含子调用
(pprof) list Func  # 行级耗时（需要本地有对应源码）
(pprof) traces     # 完整调用栈聚合
(pprof) web        # 调用图（需 graphviz）
```

火焰图：`go tool pprof -http=:8080 <profile文件>`（自带 Web UI）。

两个时刻 diff（泄漏排查的标准动作）：

```bash
curl -o h1.pprof 'http://localhost:6060/debug/pprof/heap?gc=1'
# …运行 10 分钟…
curl -o h2.pprof 'http://localhost:6060/debug/pprof/heap?gc=1'
go tool pprof -base h1.pprof h2.pprof   # 增量视角：谁在涨一目了然
```

## 5. go tool trace

```bash
curl 'http://localhost:6060/debug/pprof/trace?seconds=5' > trace.out
go tool trace trace.out   # 打开浏览器可视化
```

一句话分工：**pprof 告诉你「什么占资源」，trace 告诉你「时间花在哪」**——调度延迟（G 在 runqueue 排队、P 空转）、GC STW 与并发标记时间片、syscall 阻塞，在时间轴上一眼可见。

## 6. GC 调优：GOGC / GOMEMLIMIT 与容器

```text
GOGC=100（默认）：GC 目标堆 ≈ live × (1 + GOGC/100) = 2× live
GOGC=200         → 目标 3× live：GC 更少、内存占用更高、CPU 省在标记上
GOGC=off         → 关闭 GC（须配合 GOMEMLIMIT 兜底）
GOMEMLIMIT       → 软上限（Go 1.19+）：覆盖 Go 运行时管理的全部内存（堆+栈+运行时结构，不含 cgo/mmap）
```

验证语义：强制 GC 后 `HeapAlloc=a`，则 `NextGC≈2a`（本篇实验第 5 节直接观察）。

**容器（k8s）配合**：

```yaml
env:
  - name: GOMEMLIMIT
    value: "1800Mi"   # limit 2Gi 的 ~90%：给 cgo、线程栈、页错误留 headroom
```

- GOMEMLIMIT 是**软限制**：超过后 GC 频率暴增（thrashing，吞吐骤降）来防溢出，不是硬保护；OOMKilled 仍由 cgroup hard limit 决定。
- Go 1.25 起 GOMAXPROCS 自动感知 cgroup CPU quota（未显式设置时）；老版本需手动设为 quota 核数，否则 CFS throttling 造成长尾延迟。
- 组合拳：`GOGC=off + GOMEMLIMIT=目标值`——不按堆增长率触发、只按内存上限触发 GC，适合想固定内存占用的服务。

## 7. 真实案例框架（示意）

> 以下数字为教学示意，非真实线上数据；流程与手段是通用的。

```text
背景   ：核心 API 服务，QPS ~8k，P99 从 12ms 劣化到 45ms
① 压测 ：恒定 8k QPS 压 10 分钟，RT 曲线呈周期性锯齿 → 疑似 GC
② 观察 ：GODEBUG=gctrace=1 输出每 ~8ms 一轮 GC，
         CPU profile 中 gcBgMarkWorker 合计占 35%          → 判定：分配速率过高
③ 定位 ：heap profile（alloc_space）top 显示每请求 +2.1MB：
         - io.ReadAll(body) 每次新分配不定量 buffer
         - handler 内 bytes.Buffer 未预分配、反复扩容
④ 修复 ：body 读取用 sync.Pool 的 64KB buffer；已知大小处 make(...,0,expected)
⑤ 验证 ：微基准 benchstat：allocs/op 14→2，ns/op -38%
         线上：分配速率 1.2GB/s → 90MB/s，GC 周期 8ms → 300ms，P99 回到 13ms
```

要点：整个链路没有一步靠「猜」——每一步都有工具输出作为证据，最后闭环到业务指标（P99）。

## 8. 面试高频：线上排查标准路径

### 「线上 CPU 高怎么查？」

1. **定范围**：`top` / 容器 metrics 确认是本进程 CPU 高（区分 user/IO wait/其他进程）。
2. **采样**：`go tool pprof http://…/debug/pprof/profile?seconds=30`。
3. **分型**：
   - flat 高的业务函数 → `list` 定位行级，优化算法/热点；
   - `gcBgMarkWorker` / `runtime.mallocgc` 高 → 是**分配问题**，转 heap(alloc_space) 找分配源；
   - syscall/网络高 → IO 问题，看连接数与下游 RT。
4. **验证**：benchmark + benchstat 证明，灰度发布观察 CPU 曲线回落。

### 「内存一直涨怎么查？」

先分型再动手（三条曲线：RSS / HeapAlloc(inuse) / goroutine 数）：

1. **goroutine 数同步线性涨** → goroutine 泄漏：`goroutine?debug=2` 看卡点（channel 无 reader、`http.Response.Body` 没 Close、锁等待、`time.After` 在循环里堆积）。
2. **HeapAlloc 持续涨** → 内存泄漏：heap profile 两个时刻 `-base` diff，`inuse_space` 增量集中在同一处即凶手（全局 map 只增不删、slice 持有底层数组、缓存无淘汰）。
3. **inuse 平稳但 GC 频繁** → 不是泄漏，是分配压力：看 `alloc_space` 的分配速率，做减法（预分配/池化）。
4. **RSS 涨但 HeapAlloc 稳** → runtime 外内存（cgo、线程栈）或页归还延迟；看 `/memory/classes/*` metrics 细分。Go 1.16+ Linux 默认 MADV_DONTNEED，空闲页一般能归还。

> 核心区分：**inuse_space 看泄漏（增长），alloc_space 看压力（抖动）**——用错模式会把「GC 压力」误诊为「泄漏」。

## 9. 常见坑速查表

| 坑 | 症状 | 正解 |
|---|---|---|
| benchmark 结果没接 sink | 某些场景计算被优化掉，耗时虚快 | 包级 sink / Go 1.24+ 用 `b.Loop()` |
| StopTimer 在极小迭代里频繁调用 | 计时失真 | setup 移出循环 / `b.Loop()` |
| `-count=1` 就下结论 | 噪声当优化成果 | `-count=10` + benchstat |
| 只看耗时不看 allocs/op | 优化了吞吐却加重 GC | 两个指标一起看 |
| 用 heap 默认模式（inuse）找 GC 压力 | 找不到分配源 | 切 `-sample_index=alloc_space` |
| sync.Pool 池化小对象 | 池开销 > 分配开销 | 只池化大对象热路径 |
| unsafe.String 转换后修改 []byte | string 不可变性破坏，map key 未定义行为 | 只读 + 生命周期可证才用 |
| GOMEMLIMIT 设成等于 k8s limit | GC thrashing 吞吐骤降 | 留 10%~15% headroom |
| b.RunParallel 里写包级 sink | data race | 局部变量收尾合并 |
| 凭感觉优化没 profile | 投入产出比随机 | 先测量后优化，闭环五步 |

## 实验

本篇对应实验: experiments/11_performance.go

```bash
cd notes/golang
go run ./experiments/ perf
```

实验内容：
1. 预分配 vs 动态 append：100 万元素的耗时 + TotalAlloc 双维度对比

4. 4KB 大结构体值传递 vs 指针传递（`//go:noinline` 排除内联干扰）
5. GC 触发观测：NextGC ≈ 2×live 验证 GOGC=100 语义，分配垃圾观察 NumGC 增长
6. 标准 benchmark / pprof 命令行提示（main 包跑不了 go test，命令以打印输出）
