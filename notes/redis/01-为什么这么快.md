# 为什么 Redis 这么快

> **核心认知：Redis 快不是"因为单线程所以快"，而是"瓶颈不在 CPU，所以单线程就够了"。
> 数据在内存，CPU 不是瓶颈，瓶颈在网络和内存带宽。单线程的价值是无锁、无上下文切换，让单核跑接近极限。
> 一切设计（内存、数据结构、事件循环、持久化、淘汰）都围绕这一事实展开。**

---

## 四个支柱

| 支柱 | 一句话解释 |
|------|-----------|
| 基于内存 | 读写直接操作内存，避开磁盘 IO（内存 100ns vs 机械盘 10ms，差 10 万倍） |
| 高效数据结构 | SDS / 跳表 / listpack / 渐进式 rehash，操作时间复杂度低 |
| 单线程命令执行 | 无锁、无上下文切换，单核跑满 |
| I/O 多路复用 | epoll 事件循环，单线程高效处理海量并发连接 |

---

## 单线程：是"够用"而不是"最优"

**antirez 的原话核心：** Redis 的瓶颈从来不在 CPU，而在网络和内存带宽。既然 CPU 不是瓶颈，多线程带来的锁竞争和上下文切换反而是负资产。

单线程的代价（必须答出来）：

- **一条慢命令会阻塞所有后续命令** —— 单线程的放大效应
- 这正是官方强调"避免大 key（>10KB）、避免 `KEYS *`"的根本原因
- 推论：Redis 适合小而快的操作，不适合做重型计算

```
客户端A: SET k1 v1        ─┐
客户端B: KEYS *  (2s)      ├─→ 主线程串行执行队列
客户端C: GET k2  ← 等 2s  ─┘
```

---

## I/O 多路复用：单线程 ≠ 串行处理连接

一个常见误解：单线程怎么同时服务几万个连接？

```
              ┌── conn1 ──┐
              ├── conn2 ──┤
epoll 事件循环 ── conn3 ──┤ → 谁就绪处理谁
              ├── ...    ─┤
              └── connN ──┘

单线程 + epoll ≠ 串行处理连接
单线程 + epoll = 并发接收请求，串行执行命令
```

epoll（Linux）/ kqueue（macOS）/ select（兜底）让单线程同时监听所有连接的可读/可写事件，哪个连接有数据就处理哪个，不需要为每个连接开一个线程。

对应实验：100 个并发客户端 × 1000 次 SET，单线程全部接住，吞吐轻松上万 ops/s。

---

## Redis 6.0 多线程 I/O：补网络，不是推翻单线程

6.0 之前：网络读写（socket 读、协议解析、回包写）和命令执行都在主线程。当 QPS 上到 10 万+，**网络 IO 成了新瓶颈**。

6.0 的做法：

- 把**协议解析和回包写**分摊到 I/O 线程池（`io-threads`，官方建议 2 或 4，4 核以上才考虑）
- 读侧默认仍是单线程，需 `io-threads-do-reads yes` 显式开启（官方认为读并行的收益通常不明显）
- **命令执行仍是单线程** —— 数据结构操作依然无锁，线程安全
- 为什么只动 I/O：这一环节可并行且无共享数据，改造性价比最高

| 版本 | 网络读写 | 命令执行 |
|------|---------|---------|
| < 6.0 | 主线程 | 主线程 |
| 6.0+ | I/O 线程池 | 依然主线程 |

## Pipeline：把 N 次 RTT 压成 1 次

逐条命令的真实开销大头不是 Redis 处理，而是**网络往返（RTT）**：

```
逐条：     write → flush → read | write → flush → read | ...     N 次 RTT
pipeline： write×N → flush → read×N                             1 次 RTT
```

- Pipeline 不是服务端特性，是**客户端用法**：攒一批命令一次发出，一次读回全部响应
- 服务端按序执行、按序回包，天然保持顺序
- 官方基准：pipeline 能把吞吐拉到数倍到数十倍
- 注意：pipeline 只省网络，**不保证原子性**（对比见《07-事务-Lua-Pipeline》）

对应实验：10000 次 SET，逐条 vs pipeline 差距明显（本机模拟 RTT 下提升约一个数量级；跨机房 RTT 越大提升越夸张）。

## RESP 协议：快的基础设施

RESP（REdis Serialization Protocol）是客户端与服务端之间的 TCP 文本协议，解析成本极低：

```
+ 简单字符串   +OK\r\n
- 错误        -ERR unknown command\r\n
: 整数        :1000\r\n
$ 批量字符串   $5\r\nhello\r\n     ← 带长度前缀，二进制安全
* 数组        *3\r\n$3\r\nSET\r\n... ← 命令本身就是字符串数组

SET name redis 在协议层的真实字节：
*3\r\n$3\r\nSET\r\n$4\r\nname\r\n$5\r\nredis\r\n
```

文本协议人能读、调试容易、解析不需要复杂状态机，这是"快"里容易被忽略的一环。（Redis 6.0 另有 RESP3，支持 push 等新语义。）

## 一句话总结答题模板

> "Redis 快有四个原因：纯内存操作、高效数据结构、单线程避免锁和切换、epoll 多路复用。但要强调，单线程是'瓶颈不在 CPU 所以够用'，不是快的原因。代价是慢命令会阻塞一切，所以生产上要避免大 key、用 SCAN 代替 KEYS。6.0 之后网络读写也用了多线程，但命令执行仍是单线程。"
