# 分布式锁

> **核心认知：Redis 分布式锁的正确性由三块拼图构成，缺一不可：
> 加锁原子（SET NX PX 一条命令）、释放原子（Lua 判断+删除）、续期（watchdog）。
> 每一块都对应一类经典事故：两条命令加锁会死锁、GET+DEL 释放会删别人的锁、TTL 定不好会中途失守。
> 面试考的不是"会用"，而是每一块"为什么必须这样"。**

---

## 加锁：为什么必须一条命令

**正确写法：**

```
SET lock_key <唯一token> NX PX 30000
```

- `NX`：不存在才设置（互斥）
- `PX 30000`：30 秒过期，防持锁方宕机死锁
- value 用唯一 token（UUID）：释放时验证"锁还是不是我的"

**错误写法（两条命令不原子）：**

```
SETNX lock_key token    ← 成功
EXPIRE lock_key 30      ← 这里宕机 → 锁永不过期 → 死锁
```

`SET NX PX` 是单条命令，Redis 单线程执行天然原子——这是分布式锁最经典的演进：从两条命令到一条命令。

---

## 释放：为什么必须 Lua

**错误写法（GET + DEL 两步）：**

```
T1: 客户端A GET → 是自己的 token，准备 DEL
T2: 锁恰好过期，客户端B SET NX 成功拿到锁
T3: 客户端A 执行 DEL → 删掉了 B 的锁     ← 灾难：B 以为独占，A 也进来了
```

**正确写法（Lua，判断+删除不可分割）：**

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

token 的唯一性保证"只有持有者能释放自己的锁"。这也解释了为什么 value 不能写死固定值——两个客户端写同样的值，就无法区分持锁者。

实验验证：错误 token 释放返回 0（拒绝），锁安然无恙；正确 token 释放返回 1。

## 并发正确性验证

实验：100 个 goroutine 并发对同一计数器 +1：

```
无锁：结果 < 100（丢失更新——读改写竞态）
有锁：结果 = 100（锁把读改写串行化）
```

注意有锁版本要处理"抢锁失败重试"，失败时短暂 sleep 退避再抢，避免打爆 Redis。

## TTL 悖论与 watchdog 续期

**锁超时的本质矛盾：**

```
TTL 太短 → 业务没跑完锁过期 → 两个客户端同时持锁 → 并发破坏
TTL 太长 → 持锁方宕机后，别人要干等很久才能拿锁
```

**watchdog（看门狗）方案**（Redisson 的默认行为）：

```
TTL 设短（默认 30s）
后台线程每隔 TTL/3（10s）检查业务是否仍在执行 → 续期到 30s
业务完成 → 主动释放锁，续期停止
持锁进程宕机 → 续期线程一起死 → 锁到期自动释放
```

精髓：**TTL 不再需要预估业务时长**——它是"心跳丢失后的兜底熔断"，而不是"业务超时上限"。

实验复现：TTL=100ms 但业务跑 200ms → 中途被其他客户端抢走；加 watchdog 每 100ms 续期后，业务跑 350ms 锁依然在手，完成后正常释放。

## 可重入锁

基础实现不可重入：同一线程嵌套加锁第二次，会因为锁已被"自己"持有而失败。

**Redisson 用 Hash 实现重入计数：**

```
HSET lock_key token 1        第一次加锁，计数 = 1
HINCRBY lock_key token 1     重入一层，计数 +1
HINCRBY lock_key token -1    释放一层，计数 -1
计数 = 0 时才真正删除锁
```

field 是"锁持有者标识"（客户端ID:线程ID），value 是重入次数。

## Redlock：多节点锁与它的争议

**antirez 提出的方案：**

```
向 N 个（通常 5 个）完全独立的 Redis 实例依次 SET NX
超过半数（N/2+1）成功 且 总耗时 < 锁有效期 → 加锁成功
失败或释放 → 向所有节点执行 Lua 释放
```

**Martin Kleppmann（《数据密集型应用系统设计》作者）的反驳核心：**

```
客户端持锁期间发生 GC pause / 时钟漂移
锁在 Redis 侧已过期，另一个客户端拿到了锁
原客户端恢复后浑然不觉，继续操作共享资源 → 并发破坏
Redlock 没有 fencing token（单调递增令牌），无法根本解决
```

antirez 的回应：Redlock 已足够好，GC pause 极端场景是系统性问题。

**实际生产选择（务实版）：**

| 场景 | 选择 |
|------|------|
| 大多数场景 | 单节点 Redis 锁 + watchdog，简单可靠 |
| 锁失效会造成资金/数据损失 | ZooKeeper / etcd（Raft 强一致，天然单调 revision 可当 fencing token） |
| Redlock | 不建议：实现复杂、边界情况多、收益有限 |

## 完整链路总览（面试答题模板）

```
1. 加锁    SET key token NX PX 30000        ← 一条命令保证原子
2. 业务    执行临界区代码
3. 续期    watchdog 每 10s 续到 30s          ← 防业务超时
4. 释放    Lua: token 匹配才 DEL             ← 原子防误删
5. 兜底    进程宕机 → TTL 自然过期           ← 防死锁
```

每一环都有明确的"防什么"：NX 防并发、PX 防死锁、token 防误删、watchdog 防超时。答出这条链 + 每环的理由，基本满分。
