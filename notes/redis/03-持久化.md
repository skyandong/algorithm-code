# 持久化

> **核心认知：持久化的本质是"内存数据结构 → 磁盘文件"的翻译，两条路线对应两种哲学：
> RDB 是"拍照片"（某一刻的全量二进制快照，恢复快、可能丢数据），
> AOF 是"记流水账"（每条写命令追加，数据全、文件大恢复慢）。
> 混合持久化（4.0+）= 照片 + 照片之后的流水账，是生产默认答案。
> 所有持久化操作都绕不开 fork + COW——这是贯穿本章的核心机制。**

---

## RDB：快照

先厘清三个词的关系：**RDB 是持久化格式的名字，bgsave 是触发它的命令，dump.rdb 是产物文件。**

### RDB 的触发时机

| 触发源 | 说明 |
|--------|------|
| 手动 `BGSAVE` | 运维主动触发 |
| `save` 配置阈值 | 默认 3600s 内 1 次修改 / 300s 内 100 次 / 60s 内 10000 次 |
| 主从全量同步 | slave 发起同步时 master 自动触发 |
| `SHUTDOWN` | 未开 AOF 时关机前自动触发，但走的是**同步 save**（主线程直接 rdbSave 写完才退出，且会先杀掉运行中的 bgsave 子进程），不是 bgsave |

### bgsave 过程

```
主进程 fork 子进程（主进程立即返回，继续处理请求）
        ↓
子进程把内存数据序列化成二进制写到临时文件
        ↓
写完后 rename 替换旧的 dump.rdb（原子替换，永远不会写到一半损坏旧文件）
        ↓
子进程退出
```

### fork + COW：本章最重要的机制

```
fork 后：父子进程共享同一份内存页（只读）
父进程收到写请求修改某页时：
    内核 COW（Copy-On-Write）复制该页给父进程
    子进程继续读原始页 → 写出的永远是 fork 那一刻的完整快照
```

**两个必须答出的工程代价：**

1. **fork 本身阻塞主线程**：fork 要复制页表，实例内存越大越慢——几十 GB 实例可达几百 ms
   监控指标：`latest_fork_usec`（注意版本差异：6.x 在 `INFO stats` 里，7.x 在 `INFO persistence` 里），或 `LATENCY HISTORY fork`
2. **COW 导致内存暴涨**：bgsave 期间写量越大，被修改的页越多，COW 复制越多
   极端情况（写全部命中）内存使用翻倍 → **大实例必须预留一半内存余量**
   注意：COW 的开销要看 `used_memory_rss`（OS 视角），Redis 自身视角的 `used_memory` 看不到 COW——它只统计自己申请的内存

### 子进程写期间父进程崩了怎么办

RDB 先写临时文件，完成后才原子 rename。父进程崩了，临时文件直接丢弃，旧 RDB 完好无损。最坏结果只是丢这一次快照。

## AOF：追加日志

每条写命令以 RESP 格式追加到 `appendonly.aof`。

### fsync 策略（appendfsync）：安全与性能的三档

| 策略 | 行为 | 宕机丢失 | 吞吐 |
|------|------|---------|------|
| `always` | 每条命令刷盘 | 不丢 | 最慢（几百~几千 ops/s） |
| `everysec` | 每秒刷一次（**推荐**） | 最多约 1 秒 | 接近无 AOF |
| `no` | 交 OS 决定 | 可能几十秒 | 最快 |

**追问：everysec 真的最多丢 1 秒吗？** 不一定。fsync 线程与主线程异步，如果上一次 fsync 未完成，主线程会等待最多 2 秒，叠加系统负载，极端情况丢 2 秒以上。

### AOF 重写（bgrewriteaof）

流水账会越记越厚（一个 key 被 SET 一万次就有一万条记录）。重写 = 用当前内存状态生成最精简命令集：

```
fork 子进程把当前内存状态转成最精简命令集 → 写新文件
重写期间父进程的新写命令同时写到：
  1. 旧 AOF 文件          ← 保证旧文件仍然完整可用
  2. AOF 重写缓冲区        ← 暂存重写期间的新增量
子进程写完后：
  rewrite buffer 追加到新文件 → rename 原子替换旧文件
```

**面试高频追问：重写缓冲区是干什么的？**
重写期间父进程不能停服务，新写命令必须有暂存地。没有它，子进程生成的新文件就落后于内存状态，rename 的瞬间会丢重写期间的数据。两个观察指标：`aof_current_size`（当前大小）重写后应明显小于重写前（冗余命令被消除），`aof_base_size`（重写后的基准）。

> 版本注脚：以上是经典模型（≤6.2 的标准答案）。Redis 7.0 改为 Multi-Part AOF（manifest 管理 base + incr 多文件），重写期间的新命令直接写新的 incr 文件，不再需要内存中的重写缓冲区——但"fork 生成精简快照 + 增量不丢"的语义不变。

## 混合持久化（Redis 4.0+，5.0 默认开启）

```
aof-use-rdb-preamble yes

AOF 文件 = 前半段 RDB 格式（重写时的全量快照）
         + 后半段 AOF 增量命令（重写之后的流水账）

重启恢复：先加载 RDB 段（快）→ 再重放 AOF 增量（少）
```

| 方案 | 恢复速度 | 数据完整性 |
|------|---------|-----------|
| 纯 RDB | 快 | 丢最后一次快照后的数据 |
| 纯 AOF | 慢（重放全部命令） | 最多丢 1 秒 |
| **混合（推荐）** | 快（RDB 段秒级） | 最多丢 1 秒 |

## 怎么选

```
纯缓存、丢得起         → 不开持久化，或只 RDB
数据尽量不丢           → AOF everysec
生产默认答案           → 混合持久化
大实例注意             → maxmemory 最多用到机器内存的一半，给 fork+COW 留余量
```

**一个反直觉的点**：持久化和主从复制不要绑在同一台机器的同一时间窗——bgsave（RDB 触发）+ 全量同步（也触发 bgsave）+ AOF 重写同时发生时，三次 fork + 三份 COW 叠加，内存和延迟双杀。

## 过期 key 与持久化的交互（高频追问）

"已经过期但还没被删除的 key，会写进 RDB/AOF 吗？"

| 场景 | 行为 |
|------|------|
| bgsave / AOF 重写时 | **跳过已过期的 key**（按逻辑过期判断，不管是否已物理删除），不会污染持久化文件 |
| AOF 正常追加时 | key 被删除（惰性/定期触发）的那一刻，追加一条 `DEL`——所以 AOF 里出现过期 key 的写命令 + DEL，重放语义正确 |
| 重启加载时 | RDB/AOF 中加载的 key 若已过期，**不载入内存** |

配套的一条放主从（见《04-高可用》）：**从库不主动删过期的 key**，只等主库的 DEL 命令同步过来。所以"从库能读到已过期的数据"是设计行为，不是 bug。
