# 生产排查与运维

> **核心认知：Redis 生产问题 90% 落在四类：慢（慢命令/慢事件）、大（bigkey）、热（hotkey）、满（内存/连接）。
> 排查工具是有层次的：SLOWLOG 抓慢命令、Latency Monitor 抓非命令延迟（fork/expire/aof-write）、
> --bigkeys/--hotkeys 抓数据倾斜。先定性"哪一类"，再选对工具，不要上来就 MONITOR。**

---

## bigkey

### 定义与危害

| 类型 | 大 key 标准（经验值） |
|------|---------------------|
| String | > 10KB |
| Hash/Set/ZSet/List | 元素 > 1 万 或 总大小 > 1MB |

四大危害，全部源自单线程模型：

1. **阻塞主线程**：大 key 的 O(N) 操作（HGETALL / SMEMBERS / LRANGE 0 -1）拖慢所有命令
2. **删除阻塞**：DEL 同步释放内存（解法 UNLINK，见《06-内存管理与淘汰》）
3. **网络拥塞**：一次返回几 MB 数据，占满带宽（1MB value × 1000 QPS = 1GB/s 流量）
4. **集群迁移卡顿**：迁移大 key 期间该槽位近乎不可用

### 排查工具对比

| 工具 | 原理 | 生产可用性 |
|------|------|-----------|
| `redis-cli --bigkeys` | SCAN 采样，按元素数找 | ✓ 不阻塞，可在线跑；**集群模式只扫当前节点**，全集群要对每个 master 单独跑 |
| `redis-cli --memkeys` | 对每个 key 调 MEMORY USAGE，按内存找 | △ key 多时大量 O(N)，**非高峰期才跑** |
| `MEMORY USAGE key` | 精确测单个 key | ✓ 但对聚合类型是 O(N)，先有嫌疑对象再查 |

### 处理三板斧

```
拆分    按业务维度拆成多个小 Hash（100 万字段 → 1000 个千字段）
删除    UNLINK 异步删 + lazyfree 配置
遍历    HSCAN 代替 HGETALL，渐进式读取
```

## hotkey

单个 key 访问频率极高，**单节点**扛不住（集群也救不了——一个 key 只在一个槽）。

### 排查

```
redis-cli --hotkeys      需要 maxmemory-policy 为 LFU 系策略（OBJECT FREQ 才有数据）
OBJECT FREQ key          查单个 key 访问频率（LFU 模式）
MONITOR                  实时看所有命令 —— 生产慎用，本身就有性能损耗
```

### 处理

- **本地缓存**：应用进程内 L1 缓存热点数据，拦截大部分请求
- **复制拆分**：把 hotkey 复制成 hotkey:1 ~ hotkey:10，读时随机选一个（写时全部更新）
- **读写分离**：热点读打到 slave

## KEYS vs SCAN

```
KEYS pattern     O(N) 一次扫全库，持有全局资源，期间阻塞所有命令 —— 生产严禁
SCAN cursor [MATCH pattern] [COUNT n]
                 渐进式：每次返回一批 key + 新 cursor
                 cursor 从 0 开始，回到 0 结束（完成一轮）
```

SCAN 的三个特性必须说清：

1. **不阻塞**：每次只处理一小批，间隙里其他命令照常执行
2. **可能重复返回**（rehash 期间同一个 key 被扫到两次）——客户端要去重
3. **可能遗漏**（遍历期间被删除/新增的 key）——保证的是"遍历开始前就存在且遍历结束前没被删的 key 一定返回"

`COUNT` 是给服务端的**建议值**不是精确值。同族命令：SSCAN / HSCAN / ZSCAN（遍历聚合类型内部元素）。

### 追问：SCAN 的游标为什么不会漏（原理）

游标不是"第几个 bucket"的下标，而是**反向二进制迭代**：每轮把有效位逐个从低位到高位翻转。

```
以 size=8 的表为例,游标推进顺序:
0 → 4 → 2 → 6 → 1 → 5 → 3 → 7 → 0(回到 0 结束)

普通顺序 0,1,2...  扩容后桶的映射全变,遍历会漏
反向二进制       扩容(×2)后:旧的每个桶 i 恰好映射到 i 和 i+8,
                之前扫过的前缀仍然连续 —— 保证开始前就存在的 key 一定被访问到
```

这就是"可能重复、不会漏（遍历期间未被删除的）"的实现根基：rehash 期间同一个 key 可能被新旧两张表各扫到一次（重复，客户端去重），但已扫过的区间不会因扩容而跳过（不漏）。

## slowlog：慢命令日志

```
CONFIG SET slowlog-log-slower-than 10000   # 阈值（微秒），默认 10ms
CONFIG SET slowlog-max-len 128             # 队列长度
SLOWLOG GET [n]                            # 查最近 n 条
SLOWLOG LEN / SLOWLOG RESET                # 长度 / 清空
```

常见上榜命令：`KEYS *`、大 Hash 的 `HGETALL`、`LRANGE 0 -1`、大 Set 的 `SMEMBERS`、复杂 Lua、`DEBUG SLEEP`（实验专用）。

注意：slowlog 的计时是**命令执行时间**，不含网络传输和排队。

## Latency Monitor：抓"不是命令"的延迟

SLOWLOG 只能看到命令，但很多延迟来自**内部事件**：fork 卡顿、过期循环、AOF 刷盘、UNLINK、淘汰循环。这些 SLOWLOG 一个都抓不到。

```
CONFIG SET latency-monitor-threshold 100    # 开启，阈值 100ms（默认 0 关闭）

LATENCY DOCTOR          # 文字诊断建议（先跑这个）
LATENCY HISTORY event   # 某类事件的历史时序（fork/expire-cycle/aof-write/unlink/command...）
LATENCY LATEST          # 每类最近一次
LATENCY RESET           # 清空
```

**SLOWLOG vs Latency Monitor：互补，生产两个都开。**

## CPU 毛刺/延迟抖动排查顺序（背下来）

```
① SLOWLOG GET                  → 有没有慢命令
② LATENCY HISTORY fork         → bgsave/重写的 fork 卡顿（大实例常见）
③ LATENCY HISTORY expire-cycle → 过期 key 集中淘汰
④ redis-cli --bigkeys          → 大 key 嫌疑
⑤ CLIENT LIST                  → 有没有 MONITOR 没关 / 连接数异常
⑥ INFO memory                  → 是否逼近 maxmemory（触发淘汰）
⑦ 查 OS                        → THP（透明大页）/ swap / CPU 未隔离 / 端口耗尽
```

## 内存暴涨排查路径（与 CPU 毛刺并行的另一半）

```
① INFO memory                  → 先看 used_memory 还是 used_memory_rss 涨（区分业务数据 vs COW/碎片）
② CLIENT LIST 看 omem          → 某连接输出缓冲堆积（replica 断线/读得慢最常见）
   对策: client-output-buffer-limit replica 256mb 64mb 60(硬限/软限/软限时长)
③ INFO replication             → repl_backlog_size、master_repl_offset 涨幅(backlog 可被调大)
④ 是否正在 bgsave/bgrewriteaof  → COW 使 RSS 涨(见 03 章,fork 期间翻倍是正常上限)
⑤ INFO memory mem_fragmentation_ratio → 碎片(>1.5 开 activedefrag)
⑥ --bigkeys / --memkeys        → 新写入的大 key
```

记忆锚点：**内存暴涨三嫌疑人——输出缓冲、COW、碎片；数据本身涨不涨看 used_memory**。

## 渐进式删除：超大 key 的清退方案

DEL 阻塞、UNLINK 后台释放期间内存也不降。百万级 key 用渐进式删除——每次删一小批，批次间 sleep：

```
Hash   HSCAN → HDEL           每批 ~100 个字段
Set    SSCAN → SREM           每批 ~100 个成员
ZSet   ZREMRANGEBYRANK 0 99   每次砍排名前 100 个（无需 SCAN）
List   LTRIM 0 -101           每次砍掉尾部 100 个（保留 0 ~ 倒数第 101）
String UNLINK（无法拆分）
```

实验数据：5 万字段 Hash，直接 DEL 单次约 5ms 阻塞；渐进式总耗时更长（有 sleep + 每批一个 RTT），但 DEL 是一次性集中阻塞，渐进式把压力摊到时间轴上——客户端测到的单批耗时主要是网络 RTT，服务端执行微秒级。

实现要点：HSCAN 的游标必须逐轮推进（用上一轮返回值），**不要每轮都从 0 开始**——从 0 重扫会跳过越积越多的空桶，越删越慢（O(N²)）。

**生产建议**：bigkey 清退放低峰期跑脚本，不要在线上高峰直接删。

## 常用运维命令速查

```
INFO [section]        全景：memory/persistence/stats/keyspace
INFO memory           used_memory、fragmentation_ratio（碎片率 > 1.5 关注）
DBSIZE                key 总数（O(1)，别用 KEYS * 数）
CLIENT LIST           连接清单（抓 MONITOR、idle 连接、omem 大的连接）
CONFIG GET / SET      在线改配置（重启失效的记得改配置文件）
DEBUG SLEEP           实验专用，生产禁用
LATENCY DOCTOR        延迟自诊断
redis-cli --bigkeys / --hotkeys / --memkeys
redis-check-aof --fix appendonly.aof   AOF 尾部损坏(宕机截断)时截掉不完整命令修复
redis-check-rdb dump.rdb               RDB 完整性校验
```
