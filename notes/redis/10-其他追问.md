# 其他常见追问

> **核心认知：这一章收拢前面各章没覆盖、但面试官偏爱的横向对比题。
> 答题心法：对比题不答"谁更好"，答"各自为谁优化"——
> Redis vs Memcached（本章）、跳表 vs B+ 树（02 章）、Redis 锁 vs ZK 锁（08 章），本质都是同一个思维模板。**

---

## Redis vs Memcached

| 维度 | Redis | Memcached |
|------|-------|-----------|
| 数据结构 | String/Hash/List/Set/ZSet/bitmap 等 | 纯 KV 字符串 |
| 持久化 | RDB / AOF / 混合 | 无 |
| 高可用 | 主从 / 哨兵 / 集群 | 客户端分片，无官方 HA |
| 线程模型 | 命令单线程（6.0+ 网络 IO 多线程） | 多线程 |
| value 上限 | 512MB | 1MB（Slab 分配器设计使然） |
| 附加能力 | Lua、事务、发布订阅、过期策略丰富 | 纯缓存 |

**答题模板**：Memcached 是纯缓存（多线程、无持久化、结构单一）；Redis 是"内存数据结构服务器"（结构丰富、可持久化、可当轻量存储）。纯 KV 高并发缓存场景 Memcached 依然能打，但业务一旦需要结构、原子操作、持久化，只能 Redis。

## Redis 是单线程的，怎么还这么快？

（详见《01-为什么这么快》，这里是 30 秒版）

1. 纯内存操作，CPU 不是瓶颈
2. 单线程免锁、免上下文切换
3. epoll 多路复用并发接请求
4. 高效数据结构 + 简单文本协议（RESP）

**反问陷阱**："单线程"指**命令执行**——6.0 起网络读写已多线程；且后台线程一直存在（bgsave 子进程、AOF fsync 线程、UNLINK 的 lazyfree 线程、关闭文件的 close 线程）。

## 缓存用 String 存 JSON 还是 Hash 存字段？

| | String + JSON | Hash |
|--|---------------|------|
| 读字段 | 整体取出反序列化 | `HGET` 只取一个字段 |
| 改字段 | 读→改→写回整体 | `HSET` 原地改 |
| 内存 | 一整块 value | 小 Hash 走 listpack 更省 |
| 过期 | 整体 TTL，精细 | 只能对 key 整体过期，**字段级过期需业务模拟** |

规则：只整体读写 → String 简单直接；需要字段级读写/更新 → Hash。

## 批量操作怎么选？

| 命令 | 特性 |
|------|------|
| `MGET / MSET` | 一次网络往返，但集群下要求 key 分组到各节点由客户端聚合 |
| Pipeline | 任意命令批量，不保证原子 |
| Lua | 批量 + 原子，但脚本过长阻塞 |
| `DELETE 多个 key` | 一条 DEL/UNLINK 可传多个 key |

大集合禁止整取：`HGETALL`/`SMEMBERS`/`LRANGE 0 -1` 对大 key 都是 O(N) 阻塞操作，用 `HSCAN`/`SSCAN` 渐进式。

## Redis 为什么不适合当主数据库？

1. **内存成本**：数据量大时内存远贵于磁盘
2. **持久化不是强保证**：RDB 丢快照间隙、AOF everysec 丢秒级、宕机瞬间的写入可能丢失
3. **事务弱**：无回滚、无关系模型、无复杂查询
4. **淘汰策略**：内存满时可能主动删数据（noeviction 之外都会删）

正确定位：缓存、计数器、排行榜、会话存储、消息流（Stream/List）、分布式锁——**热数据加速层**，权威数据永远在 DB。

## 发布订阅（Pub/Sub）与 Stream

**Pub/Sub**：`PUBLISH/SUBSCRIBE`，fire-and-forget——订阅者不在线消息就丢，无持久化、无回溯。只适合"丢了无所谓"的场景（如聊天室广播、配置刷新通知）。

**Stream（5.0+）**：持久化的消息队列，消费者组、ACK、pending 列表、历史回溯——对标 Kafka 的轻量替代。和 Kafka 对比：Redis Stream 胜在轻量、低延迟、和 Redis 同栈；Kafka 胜在海量堆积、分区水平扩展、生态。

**为什么很多团队用 List（LPUSH/BRPOP）做队列**：简单够用，但无 ACK——消费者取走即删，处理失败消息就丢了；且不能多消费者负载均衡（是"抢"不是"分"）。

## keyspace notification（过期事件通知）

`notify-keyspace-events Ex` 开启后可订阅 key 过期事件。

**两个坑：**

1. 过期事件在 key **被删除时**发布（惰性/定期删除触发时），不是 TTL 到点准实时——可能有延迟
2. 过期事件不携带 value——只告诉你"谁过期了"，取不到过期时的值

所以"过期回调取值"类需求要靠业务自己实现（如再存一份带 TTL 的副本，或用 Stream）。

## Redis 的内存碎片

`INFO memory` 的 `mem_fragmentation_ratio` = used_memory_rss / used_memory：

```
≈ 1.0~1.5   健康
> 1.5       碎片多（频繁增删不同大小 value、页未归还 OS）
< 1.0       用了 swap，严重告警
```

4.0+ 开启 `activedefrag yes` 主动碎片整理（复制整理期间的性能开销要评估）。

## 一个 key 的过期时间到了，Redis 会立刻删除吗？

不会。（详见《06-内存管理与淘汰》）惰性 + 定期删除的组合决定了：到期后到真正删除之间有时间差，期间 key 还占内存；`EXISTS` 在被清理前可能仍返回 1（取决于访问是否触发惰性删除）。追问延伸：`INFO keyspace` 的 expires 是"带 TTL 的 key 数"，不是"未过期的 key 数"。

## Redis 怎么实现延迟队列？

三板斧对比：

1. **ZSet**：score 存执行时间戳，轮询 `ZRANGEBYSCORE key now +limit` 取到期任务，配合 Lua 保证"取出+删除"原子——最常用
2. **Keyspace notification**：订阅过期事件——有延迟且不可靠（见上），不推荐做核心链路
3. **Redisson DelayedQueue**：基于 List + 定时搬运的成熟封装

都不如专业 MQ 的延迟队列可靠，量级大、可靠性要求高时选 RocketMQ/RabbitMQ。

## 客户端连接数暴涨/耗尽排查

```
① CLIENT LIST          看 idle 时间长的僵尸连接、有没有 MONITOR
② INFO clients          connected_clients、blocked_clients
③ maxclients 配置       达到上限时新连接直接被拒
④ 应用侧连接池配置      池大小、是否泄漏（借出不还）
⑤ timeout 配置          空闲连接自动断开
```
