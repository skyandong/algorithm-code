# 高可用

> **核心认知：Redis 高可用是三个递进的层次——主从复制（数据冗余）、哨兵（自动故障转移）、集群（水平扩展）。
> 每一层解决上一层解决不了的问题：主从解决"机器坏了数据丢"，哨兵解决"主从坏了要人切"，集群解决"单机装不下/写不动"。
> 不要一上来就上集群——集群的复杂性（槽迁移、hash tag、客户端改造）本身就是新的故障源。**

---

## 主从复制

### PSYNC 协议：全量 + 部分重同步

**全量同步**（第一次连接，或断线太久 backlog 不够用）：

```
slave 发 PSYNC ? -1
        ↓
master 执行 bgsave 生成 RDB 发给 slave
        ↓
发送期间的新命令缓存在 replication buffer
        ↓
slave 清空旧数据 → 加载 RDB → 执行缓存命令 → 追平
```

**部分重同步**（断线重连，offset 还在 backlog 范围内）：

```
slave 发 PSYNC <replid> <offset>
        ↓
master 从 repl_backlog 找到 offset 位置，只补发差量命令
        ↓
免去一次全量 RDB（大实例全量同步代价极高）
```

**关键参数**：`repl-backlog-size`（默认 1MB）。断线时间长或写量大时 backlog 不够 → 降级为全量同步 → 主库 bgsave + 网络传输，性能抖动。写量大的集群建议调大到 64MB~1GB。

### 两个"缓冲区"必须分清（高频混淆点）

| | replication buffer（输出缓冲区） | repl_backlog（复制积压缓冲区） |
|--|------|------|
| 归属 | **每个 slave 一个**（client output buffer） | **全局一份**，所有 slave 共享 |
| 作用 | 全量同步期间暂存发给该 slave 的增量命令（RDB 传完接着回放它） | 环形缓冲区，存最近的写命令流，断线重连时按 offset 补差量 |
| 淘汰 | 超过 `client-output-buffer-limit replica` 直接断开该 slave | 环形覆写，旧数据被新命令冲掉（backlog 不够 → 全量同步） |

经典事故：某个 slave 读得慢，replication buffer 堆积撑爆 → master 内存暴涨。排查看 `CLIENT LIST` 的 `omem` 字段（见《09-生产排查与运维》）。

### PSYNC2（4.0+）：故障切换后的部分重同步

PSYNC1 的缺陷：故障转移后新 master 的 replid 变了，其他 slave 只能全量同步。
PSYNC2 让新 master 记住两套 replid（`replid` + `replid2`）——只要 slave 的 replid 与其中之一匹配且 offset 在范围内，仍可部分重同步。
回答"哨兵切换后从库要全量同步吗"：4.0+ 大概率不用（PSYNC2），但切换瞬间的增量仍可能丢。

### 无盘复制（repl-diskless-sync）

磁盘慢或实例大时，全量同步不落盘：master 不再 bgsave 写 RDB 文件，直接边生成边通过 socket 发给 slave。适合磁盘 IO 差的云主机和容器环境。

### 复制是异步的

master 写入后**不等 slave 确认**就回复客户端，所以 slave 数据天然可能落后——这是后面"哨兵数据丢失"和"延迟双删要考虑主从延迟"的根源。

主从复制本身**不提供高可用**：master 挂了需要人工切换。它只提供读扩展（读写分离）和数据冗余。

**从库的过期 key**：从库不主动删除过期 key（不跑惰性/定期删除），只等主库删掉后把 DEL 同步过来。所以"从库能读到已过期的数据"是设计行为——读写分离场景下要在业务层容忍或加判断。

## 哨兵（Sentinel）

解决"master 宕机要人半夜爬起来切"的问题。

### 四个职责

1. **监控**：定期 PING master / slave / 其他哨兵
2. **通知**：节点状态变化时通知运维
3. **自动故障转移**：master 下线后自动选新 master
4. **配置中心**：客户端通过哨兵查询当前 master 地址

### 故障转移全流程（面试必背）

```
单个哨兵 ping 不通 master          → 主观下线 SDOWN（可能只是网络抖动）
quorum 个哨兵都认为不通            → 客观下线 ODOWN（真的挂了）
哨兵之间 Raft 选举 Leader          → Leader 独家执行故障转移
        ↓
选最优 slave 提升为新 master
   依次比较：replica-priority（手动配置的优先级）
           → 复制偏移量 offset（数据最全）
           → runid 最小（兜底，结果稳定）
        ↓
其余 slave 改为复制新 master
哨兵通知客户端新 master 地址
旧 master 恢复后以 slave 身份加入
```

**两个数字不是一回事（常被追问）**：
- `quorum` 只用于 **ODOWN 判定**（多少哨兵同意"master 挂了"）
- **Leader 选举需要 majority（半数以上哨兵）**，与 quorum 无关——quorum 配 1 也要过半哨兵活着才能选出 Leader 执行转移
- 推论：3 个哨兵最多容忍 1 个挂；quorum 调小只是降低误判门槛，不能提高可用性

### 数据丢失的两种场景

1. **异步复制丢失**：master 写入还没同步到 slave 就宕机——这部分数据永远丢了
2. **脑裂丢失**（更隐蔽）：master 假死（网络分区），哨兵判定下线并选出新 master；但旧 master 还活着，客户端还在往它写；分区恢复后旧 master 降级为 slave，**清空自己同步新 master，分区期间写入的数据全部丢失**

### 防脑裂配置

```
min-replicas-to-write 1    # 至少 1 个 slave 确认同步，master 才接受写入
min-replicas-max-lag 10    # slave 落后超过 10 秒视为失联
```

脑裂时旧 master 身边没有可用 slave → 拒绝写入 → 分区期间的数据丢失从"全部"降到"被拒绝的部分"。
代价：可用性略降（slave 全挂时 master 只读）。这是 CAP 取舍，不是免费午餐。

## 集群（Cluster）

解决单机内存上限和写入瓶颈。

### 哈希槽

```
共 16384 个槽
slot = CRC16(key) % 16384
每个节点负责一段槽区间，数据随槽分布

key → 槽 → 节点，两层映射
```

**为什么是 16384 不是 CRC16 全范围的 65536**（antirez 在 GitHub issue #2576 亲自回答）：

1. 心跳包要携带槽位 bitmap：65536 槽 = 8KB（太大），16384 槽 = 2KB（合适）
2. 集群规模设计上限约 1000 节点，16384/1000 ≈ 16 槽每节点，粒度足够

**为什么不用一致性哈希**：

| | 一致性哈希 | 哈希槽 |
|--|-----------|--------|
| 节点职责 | 负责一段弧 | 负责固定数量的槽 |
| 扩容 | 自动均衡，但迁移范围不可控 | 手动指定迁哪些槽，**精确可控** |
| 数据分布 | 弧段天然不均，需虚拟节点补偿 | 槽粒度细，分布均匀 |

核心优势：扩缩容时运维能精确控制迁移哪些槽到哪些节点，按节点容量调配；一致性哈希的自动均衡反而是黑盒。

### ASK / MOVED：槽迁移时的重定向

```
MOVED 3999 127.0.0.1:6381   # 槽已永久迁移 → 客户端更新本地槽映射表
ASK   3999 127.0.0.1:6381   # 槽正在迁移，key 可能在目标节点
                            # → 本次去目标节点试试，但不更新路由表
```

### 集群的代价（限制）

- **多 key 操作要求同槽**：`MGET`/事务/Lua 涉及的所有 key 必须落在同一节点
  解法：**hash tag**——key 里 `{}` 括住的部分才参与哈希
  `{user:1000}:profile` 和 `{user:1000}:order` 必然同槽
- 只有 db0，不支持 SELECT
- 批量操作要客户端按槽分组分发

### Gossip 协议：集群怎么发现节点挂了（追问必考）

节点间通过 Gossip 消息扩散状态（PING/PONG/MEET/FAIL），交换各自视角的集群拓扑：

```
节点A 发现节点B 等待 PONG 超时        → 给 B 打上 pfail（疑似下线，主观）
A 在 Gossip 中扩散 "B pfail"
半数以上 master 都标记 B 为 pfail     → 广播 B fail（客观下线）
B 的 slave 发起选举，半数以上 master 同意 → 晋升为新 master
```

对比哨兵：哨兵靠独立的哨兵进程投票，集群靠 master 节点自己投票——同样的"主观 + 过半客观"套路，只是投票人换了。

## Codis（了解即可）

代理式分片方案（豌豆荚 2014 年开源），出现在官方集群 3.0（2015）之前：

```
客户端 → Codis Proxy（路由层）→ Codis Server（魔改版 Redis）
              ↓
       ZooKeeper/etcd 存槽位元数据
```

被淘汰的原因：Proxy 多一跳延迟、魔改版 Redis 跟不上官方演进、依赖 ZK 运维复杂、团队停止维护。

面试答法：官方集群成熟前的过渡方案，新项目不应选用。

## 选型决策树

```
数据量单机装得下、能接受人工切主？   → 主从（最简单）
需要 7×24 自动故障转移？            → 哨兵（1 主 + 2 从 + 3 哨兵起步）
内存超单机上限 或 写 QPS 打满单机？  → 集群（做好复杂度预算）
```

| 方案 | 解决 | 代价 |
|------|------|------|
| 主从 | 数据冗余、读扩展 | 无自动切换 |
| 哨兵 | 自动故障转移 | 数据仍受单机内存上限 |
| 集群 | 水平扩展 | 槽迁移、hash tag、客户端改造、多 key 受限 |
