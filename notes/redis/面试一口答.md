# Redis 面试一口答清单

> 从各篇笔记提炼的"张口就来"清单：被问到要能不带停顿直接说出来。
> 对应章节：`01-为什么这么快` ~ `10-其他常见追问`，实验代码在 `experiments/`。
>
> **记忆主线：Redis 快不是因为单线程，而是"瓶颈不在 CPU，单线程刚好够用"—— 数据在内存，瓶颈在网络。一切设计（内存、数据结构、事件循环、持久化、淘汰）都围绕这一事实展开。**

---

## 一、为什么这么快（最高频）

### 1. 为什么 Redis 这么快？（四个支柱）
1. **基于内存**：读写直接操作内存，避开磁盘 IO
2. **高效数据结构**：SDS、跳表、listpack、哈希表，时间复杂度低
3. **单线程命令执行**：无锁、无上下文切换，单核跑满
4. **I/O 多路复用**：epoll 事件循环（`ae.c`），单线程高效处理海量连接

### 2. 单线程：别把"单线程"说成快的原因（必背）
> **antirez 观点**：Redis 快**不是"因为单线程所以快"**，而是**"瓶颈不在 CPU，所以单线程就够了"**。数据在内存，CPU 不是瓶颈，瓶颈在网络。单线程的好处是避免锁竞争和上下文切换，让单核跑接近极限。

**代价**：单条命令慢会**放大**阻塞所有后续命令 → 官方强调**避免大 key（>10KB）**。

### 3. Redis 6.0 多线程 I/O
- 6.0 只把**网络读写**（socket 读、协议解析、回包写）分摊到 I/O 线程池（`io-threads`，建议 2-4）
- **命令执行仍是单线程** —— 数据结构操作不加锁，线程安全
- 为什么只动 I/O：网络成了新瓶颈，这一环节可并行且无共享数据，性价比最高

## 二、数据类型与底层结构

### 4. 各类型底层编码（Redis 7.0+）
| 类型 | 底层编码 | 说明 |
|------|---------|------|
| String | **SDS** | 空间预分配、二进制安全、O(1) 取长度 |
| Hash | listpack / hashtable | 元素少且小用 listpack，否则 hashtable |
| List | **quicklist**（节点为 listpack） | 兼顾内存与随机访问 |
| Set | intset / listpack / hashtable | 全整数用 intset，少量小元素用 listpack |
| ZSet | listpack / **skiplist + dict** | skiplist 支持范围查询，dict 支持 O(1) 取分值 |

> **listpack 替代 ziplist 的原因**：ziplist 有"连锁更新"问题（连续 entry 都接近 253 字节时，一个变更触发全连锁扩容）。

**编码升降级触发条件**：以 Hash 为例，`hash-max-listpack-entries`（默认 128）和 `hash-max-listpack-value`（默认 64 字节），两者任一超过阈值 listpack 升级为 hashtable；**缩小后不会自动降级**（避免频繁转换）。List/Set/ZSet 各有类似阈值（`list-max-listpack-size`、`set-max-intset-entries`、`zset-max-listpack-entries` 等）。

### 5. SDS 相比 C 字符串的优势
- O(1) 获取长度（C 字符串要遍历到 `\0`）
- 二进制安全（不依赖 `\0` 判断结束，可存图片/序列化数据）
- 空间预分配 + 惰性释放，减少内存重分配
- 兼容部分 C 字符串函数

### 6. Sorted Set 为什么用跳表不用红黑树
- 范围查询（ZRANGE / ZRANGEBYSCORE）实现更简单
- 实现复杂度更低、内存可控、并发友好
- 配合 dict 实现 O(1) 取分值，各司其职

**跳表核心机制**：每个节点的层数由随机算法决定（每往上一层的概率为 0.25，最高 32 层），期望层数 O(log N)，查找/插入/删除平均时间复杂度均为 O(log N)。范围查询只需找到下界节点后沿链表顺序遍历，实现极简。

### 7. 渐进式 rehash 是什么？
dict 扩容时不做一次性全量迁移（会阻塞），而是**分批渐进**：每次 CRUD 操作顺带迁移 1 个 bucket，同时维护 ht[0]（旧表）和 ht[1]（新表）并存。

触发时机：负载因子 > 1 时正常扩容（翻倍）；负载因子 > 5 时强制扩容（不管是否 bgsave）；负载因子 < 0.1 时触发缩容。

迁移期间：查找先查 ht[0] 再查 ht[1]；新增 key 只写 ht[1]；迁移完成后 ht[0] 释放，ht[1] 变成 ht[0]。

## 三、持久化

### 8. RDB（快照）
- 二进制文件，定时 `bgsave` 触发
- **bgsave = fork + COW（Copy-On-Write）**：子进程写 RDB，父进程继续处理请求；父进程修改某页时内核才复制该页
- 恢复快、文件小；**缺点**：宕机丢最后一次快照后的数据

**fork 的实际代价**：fork 是**同步阻塞**操作（复制父进程页表），10GB 内存实例 fork 可能阻塞数百毫秒。COW 在写入密集场景下内存实际使用可能**翻倍**（父进程每次修改页都触发复制）。监控：`LATENCY HISTORY fork`，`INFO persistence` 的 `rdb_last_bgsave_time_sec`。

### 9. AOF（追加日志）
- 记录每条写命令，**fsync 策略三档**：
  - `always`：每条命令都刷盘，最安全最慢
  - `everysec`：每秒刷一次（**推荐**，宕机最多丢 1 秒）
  - `no`：交由 OS 决定
- **AOF 重写（bgrewriteaof）**：fork 子进程，把当前内存状态转成命令重写，压缩体积（去重复命令、过期 key）
- 数据更完整；**缺点**：文件大、恢复慢

**自动重写触发条件**：`auto-aof-rewrite-percentage 100`（AOF 文件比上次重写后增长 100%）且 `auto-aof-rewrite-min-size 64mb`（至少 64MB），两个条件同时满足才触发。生产通常调大 min-size（如 1GB）避免过于频繁重写。

### 10. 混合持久化（4.0+，5.0 默认开启）
- `aof-use-rdb-preamble yes`：AOF 文件**前半段 RDB 格式（全量快照）+ 后半段增量命令**
- 重启先加载 RDB（快），再重放 AOF 增量（少丢），兼具两者优点

## 四、高可用

### 11. 哨兵故障转移流程（必背）
```
① 主观下线（SDOWN）：单个哨兵认为 Master 不可达
② 客观下线（ODOWN）：quorum 个哨兵达成一致
③ 选举 Leader 哨兵执行转移（raft 协议）
④ 选最优 Slave 提升为新 Master，通知其他 Slave 和客户端
```

**数据丢失两种风险 + 解决**：
- **异步复制丢失**：Master 未同步到 Slave 就宕机
- **脑裂丢失**：假死导致 Client 继续写入孤立 Master，恢复后被覆盖
- 解决：`min-replicas-to-write 1`（至少 1 个从节点确认才接受写入）

**脑裂（split-brain）防护**：网络分区时，客户端继续向孤立 Master 写入，分区恢复后该 Master 降为 Slave，期间写入**全部丢失**。防护：`min-replicas-to-write 1`（至少 1 个从节点 ACK 才接受写入）+ `min-replicas-max-lag 10`（从节点最大落后秒数），两者配合——无从库可用时 Master 拒绝写入。

### 12. 集群：哈希槽
- 共 **16384** 个槽，`CRC16(key) % 16384` 映射到槽，节点各负责一部分
- **为什么是 16384 不是 65536**：心跳包体积小（CRC16 对 16384 槽已足够分散）；网络带宽友好

### 13. ASK vs MOVED（必背）
- **MOVED**：槽位**已永久迁移**到新节点 → 客户端应**更新本地槽映射**
- **ASK**：槽位**正在迁移**，Key 可能在目标节点 → **临时重定向，客户端不更新本地路由**

### 14. 集群限制 + hash tag
- 多 Key 操作（MGET / 事务 / Lua）要求 Key 在同一槽 → 用 **hash tag**：`user:{1000}:profile`、`user:{1000}:order` 落同槽
- 不支持跨槽多键命令

### 15. 主从复制（PSYNC）
- **全量同步**：`PSYNC ? -1`，Master 执行 bgsave 发送 RDB + 缓冲区命令
- **部分重同步**（断线重连）：Slave 带 `replid` + `offset`，若 offset 在 `repl_backlog` 内则只补差异
- 关键参数：`repl-backlog-size`（默认 1MB，断线时间长需调大）

**repl_backlog_size 的影响**：默认 1MB，断线时间稍长就会 offset 超出 backlog 范围，触发全量重同步（bgsave + 传输 RDB，代价极高）。生产建议调大：`repl-backlog-size 100mb`，并监控 `INFO replication` 的 `master_repl_offset - slave_repl_offset` 差值。

### 16. 主从延迟怎么监控和处理？
监控：`INFO replication` 的 `master_repl_offset - slave_repl_offset` 差值（字节数）；或 Master 写入一个带时间戳的特殊 key，Slave 读取后计算延迟秒数。

常见原因：大 key 操作（单命令耗时长阻塞复制线程）、写入 QPS 超过 Slave 重放速度、网络带宽不足。

注意陷阱：`replica-lazy-expire no`（默认），Slave 不主动删过期 key，等 Master 下发 DEL 命令才删；在此之前，Slave 读到的是已过期但未删除的 key（设计行为，不是 bug）。生产通过读主或设短 TTL 规避。

### 17. 集群脑裂（split-brain）怎么发生？
网络分区后，集群分成两个子集群，少数派子集群仍有 Master 节点继续服务，客户端写入孤立 Master；分区恢复后，孤立 Master 因落后太多被降为 Replica，期间所有写入**全部丢失**。

防护：`cluster-require-full-coverage no`（不要求所有槽位可用才提供服务）+ `min-replicas-to-write`；但根本上，集群脑裂在 Redis Cluster 中难以完全避免，应用层需要有幂等设计和对账机制。

### 18. 集群扩缩容流程？
扩容：① `CLUSTER MEET <ip> <port>` 将新节点加入集群；② `CLUSTER ADDSLOTS` 或 `redis-cli --cluster reshard` 迁移 slot；③ 迁移期间 slot 上的 key 通过 ASK 重定向访问目标节点（与 MOVED 区别：ASK 不更新客户端路由）。

缩容：① 先用 reshard 把该节点所有 slot 迁移走；② `CLUSTER FORGET <node-id>` 从集群移除（60秒内所有节点都要执行）；③ 关闭节点。

## 五、缓存常见问题（穿透 / 击穿 / 雪崩）

### 19. 穿透（查不存在数据）
> 查询根本不存在的数据，绕过缓存直击 DB（常被恶意攻击）。
- **布隆过滤器**：请求前先过滤，空间高效
- **缓存空对象**：查不到也缓存 null，设短 TTL

### 20. 击穿（热点 Key 过期瞬间）
> 热点 Key 过期瞬间，高并发直击 DB。
- **互斥锁**：只让一个线程查 DB 并回填缓存，其他等待
- **逻辑过期**：热点数据不设 TTL，value 中存逻辑过期时间，后台异步更新

### 21. 雪崩（大量 Key 同时过期）
- **过期时间加随机值**，打散过期时间
- **多级缓存**（本地 + Redis）
- 熔断降级保护 DB

### 22. 缓存与数据库一致性
- **首选旁路缓存（Cache Aside）：更新数据库 → 删除缓存**
  - 为什么删除而不是更新？避免并发更新导致缓存与 DB 不一致
- **延迟双删**：先删缓存 → 更新 DB → 休眠毫秒级 → 再删一次（解决"读线程把旧值回填缓存"）
- **消息队列异步重试**：删除失败发 MQ 重试，保证最终一致性
- **Canal 订阅 binlog**：监听 DB 变更异步刷缓存，业务代码无侵入

**争议核心**：为什么是"先更新 DB 再删缓存"而不是"先删缓存再更新 DB"？先删缓存存在窗口期：删除后更新 DB 完成前，有线程读缓存 miss → 读 DB 旧值 → 写入缓存，造成旧缓存持续存在。延迟双删就是为了清除这个旧值回填。Canal/binlog 订阅的优势：业务代码零侵入，适合强一致要求场景，但引入 Canal 组件增加运维复杂度。

## 六、内存管理与淘汰

### 23. 过期 Key 删除机制（两机制结合）
- **惰性删除**：访问时才检查过期并删除（被动，兜底）
- **定期删除**：每隔一段时间随机抽样检查删除（主动）
- 两者结合，平衡 CPU 与内存

### 24. 大 Key 删除
- 删除大 Key（如几十万元素的 Hash）会**阻塞主线程**
- Redis 4.0+：**`UNLINK` / `lazyfree-*` 异步释放内存**，删大集合务必用 `UNLINK` 而非 `DEL`

### 25. 淘汰策略（8 种，`maxmemory-policy`）
| 策略 | 范围 | 说明 |
|------|------|------|
| `noeviction` | - | 不淘汰，写报错（默认） |
| `allkeys-lru` / `allkeys-lfu` / `allkeys-random` | 所有 key | 近似 LRU / 近似 LFU（4.0+）/ 随机 |
| `volatile-lru` / `volatile-lfu` / `volatile-random` / `volatile-ttl` | 设了过期的 | 只淘汰带 TTL 的 |

- **近似 LRU**：不维护全局链表（太贵），**随机采样**（默认 5 个，`maxmemory-samples` 可调）选最久未用的淘汰
- **LFU**：Morris 计数器 + 随时间衰减，更贴合热点访问模式

**选择建议**：纯缓存（所有 key 均可淘汰）→ `allkeys-lru`（通用）或 `allkeys-lfu`（热点不均匀，LFU 更准确）；缓存 + 持久数据混合 → `volatile-lru`（只淘汰有 TTL 的缓存 key）；默认 `noeviction` 生产一定要改，否则内存满了写命令直接报错。

### 26. 内存碎片与 active defrag？
`INFO memory` 中 `mem_fragmentation_ratio > 1.5` 说明碎片严重（实际内存/逻辑内存 > 1.5）。

原因：频繁分配/释放不同大小的内存块，jemalloc 无法紧凑复用，形成碎片。大量小 key 过期删除后尤为明显。

解决：Redis 4.0+ `activedefrag yes` 开启在线碎片整理，后台渐进清理（主线程执行，有 CPU 开销）。关键配置：`active-defrag-ignore-bytes 100mb`（碎片超过 100MB 才启动）+ `active-defrag-threshold-lower 10`（碎片率超 10% 才启动）。

## 七、事务 / Lua / Pipeline（三连对比高频）

### 27. 三者对比（必背）
| | 原子性 | 网络优化 | 回滚 |
|--|--------|----------|------|
| Pipeline | 否 | **是（省 RTT）** | - |
| 事务 MULTI | 顺序执行，**不保回滚** | 否 | 无 |
| **Lua** | **是（真原子）** | 否 | - |

### 28. 事务
- `MULTI` 开启 → 命令入队 → `EXEC` 顺序执行
- **不支持回滚**：某条命令执行报错（如类型错误），其他命令仍会执行
- **WATCH 乐观锁**：监视 Key，事务执行前若被修改则整个事务放弃（CAS 模式）
- Redis 事务本质是"批量执行"，**不满足 ACID 的原子性**

### 29. Lua 脚本
- 脚本在 Redis 内**单线程执行，中间不会插入其他命令** → 真原子
- 经典用途：**分布式锁释放**（判断+删除原子性）
- `EVAL` / `EVALSHA`（缓存脚本省带宽）

### 30. Redis Stream 与 Pub/Sub 有什么区别？
| | Pub/Sub | Stream（5.0+） |
|--|---------|----------------|
| 消息持久化 | 否（断线丢失） | **是**（AOF/RDB 持久化） |
| 历史消息 | 不支持 | **支持**（按 ID 消费历史） |
| 消费者组 | 不支持 | **支持**（XREADGROUP，消费者竞争消费） |
| ACK 机制 | 无 | **有**（XACK，未 ACK 消息在 PEL 中挂起） |
| 适用场景 | 实时广播，允许丢失 | 可靠消息队列，需要确认 |

Stream 适合替代简单 MQ 场景（日志收集、任务队列），但不适合替代 Kafka（无分区、吞吐有限）。

## 八、分布式锁（必背完整链路）

### 31. 加锁
```bash
SET lock_key <request_id> NX PX 30000
```
- `NX`：不存在才设置（互斥）
- `PX 30000`：设过期，防止持有方宕机导致死锁
- value 用**唯一 request_id**（UUID），用于释放时验证归属

### 32. 释放（必须 Lua，保证原子性）
```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```
避免"先 get 判断再 del"之间被其他客户端删掉/重入。

### 33. 过期续期
- 业务执行超过锁 TTL → 锁被自动释放，其他客户端拿到锁 → 并发问题
- **Redisson watchdog**：后台线程定期（默认 TTL/3）续期，业务完成才停止

### 34. Redlock
- **动机**：单实例锁在主从切换时丢锁——锁没来得及异步复制，master 宕机，slave 晋升后锁消失，两个客户端同时持锁
- **方案**：在 N（通常 5）个**互相不做主从复制**的独立实例上依次加锁，**超过半数（N/2+1）成功且总耗时小于锁有效期** → 加锁成功
- **争议**：Martin Kleppmann 指出 GC pause / 时钟漂移会破坏安全性，Redlock 没有 fencing token；antirez 反驳
- 实际生产：单 Redis 实例锁 + 容错降级，或直接用 ZooKeeper / etcd

## 九、生产排查与运维（经验题加分项）

### 35. bigkey / hotkey
- bigkey：`redis-cli --bigkeys`（采样）、`MEMORY USAGE key`（精确）；危害：阻塞主线程、网络拥塞、迁移卡顿；处理：拆分、`UNLINK` 删、`lazyfree`
- hotkey：`redis-cli --hotkeys`（需开 LFU）、`OBJECT FREQ key`；处理：本地缓存、拆分热点、读写分离

### 36. KEYS vs SCAN（必背）
- **`KEYS pattern` 阻塞主线程，生产严禁**
- **`SCAN cursor`** 渐进式遍历不阻塞，但遍历期间 rehash 可能**返回重复/遗漏**

### 37. slowlog
- `SLOWLOG GET`，阈值 `slowlog-log-slower-than`（默认 10ms）
- 常见慢：`KEYS *`、大 Key 操作、`LRANGE 0 -1`、复杂 Lua

### 38. CPU 毛刺排查（按频率排）
1. **bgsave / AOF 重写的 fork()** —— 头号嫌疑人：fork 是主线程同步操作复制页表，实例越大越慢；特征：毛刺和保存周期相关；查 `LATENCY HISTORY fork`、`INFO persistence`
2. **大 key 的 O(N) 操作或同步删除**：`DEL`/`HGETALL`/`LRANGE 0 -1`/`SMEMBERS`；查 `--bigkeys`、SLOWLOG
3. **慢命令**：`KEYS *`、`SORT` 大集合、`SINTER`/`ZUNIONSTORE`、重 Lua；查 SLOWLOG、`INFO commandstats`
4. **过期 key 集中淘汰**：大量 key 同时过期；特征：与过期时间点对齐的周期毛刺；解决：TTL 加随机值打散
5. **MONITOR 没关**：每条命令同步发给 monitor 客户端；查 `CLIENT LIST`；生产别用
6. **内存淘汰触发**：`INFO stats` 的 `evicted_keys`
7. **active defrag**：`activedefrag yes` 在主线程跑

**OS 层面**（看着像 Redis 毛刺，其实是宿主）：THP（透明大页，官方建议关闭）、swap（`free -m`）、CPU 没隔离、NUMA。

### 39. 杀手锏：Latency Monitor（2.8.13+）
- 把**超过阈值**的操作记成"延迟事件"（时间戳+耗时），专门抓毛刺
- **默认关闭**：`CONFIG SET latency-monitor-threshold 100` 才开始记录（建议常驻）
- 命令：`LATENCY DOCTOR`（直接给文字诊断）/ `LATENCY HISTORY event` / `LATENCY LATEST` / `LATENCY GRAPH` / `LATENCY RESET`

### 40. SLOWLOG vs Latency Monitor（关键区别）
| | SLOWLOG | Latency Monitor |
|--|--------|-----------------|
| 记什么 | **慢命令**（命令执行耗时） | **延迟事件**（含内部非命令操作） |
| 能抓 fork/expire/aof-write | **不能**（不是命令） | **能** |
| 默认 | 开（阈值 10ms） | **关**（阈值 0） |

> 毛刺若由 fork、过期淘汰、AOF 写这类**内部操作**引起，SLOWLOG 是空的，只有 Latency Monitor 抓得到。**两者互补，生产都开。**

**一句话排查顺序**：`SLOWLOG` → `LATENCY`（fork/expire）→ `--bigkeys` → 查 `MONITOR` → 查 OS（THP/swap）

### 41. Redis 7.0 有哪些重要变化？
1. **listpack 全面替代 ziplist**：quicklist 的节点、Hash/ZSet 的小对象编码全部换成 listpack，彻底消灭连锁更新问题
2. **redis-function 替代 Lua Script 管理**：函数可命名、持久化到 RDB/AOF、支持主从复制，解决 EVALSHA 在 failover 后 script 丢失的问题
3. **multi-part AOF**：将 AOF 分成 base（RDB 快照）+ incremental（增量命令）两部分分开管理，重写期间不再需要临时文件，稳定性提升

### 42. Redis ACL（6.0+）有什么用？
多用户权限控制：`ACL SETUSER <name> on ><password> ~key* +get +set` 可精细配置命令权限（允许/禁止某类命令）、Key 访问范围、密码。

生产价值：① 不同服务用不同账号，最小权限原则；② 防止误操作（禁止 FLUSHALL/KEYS *）；③ 审计追踪（ACL LOG 记录违规访问）。

相比 `requirepass` 单密码方案：支持多用户、精细权限、在线修改（无需重启）。

## 十、其他常见追问

- **Pipeline vs 事务 vs Lua**：Pipeline 省网络不保原子；事务保顺序不保回滚；Lua 真原子
- **Redis 6.0 多线程**：仅网络 I/O，命令仍单线程（避免引入锁）
- **集群为什么不用一致性哈希**：哈希槽更可控、扩缩容迁移明确
- **布隆过滤器**：位数组 + 多哈希；可能有**假阳性**（误判存在），**不会假阴性**；不支持删除（Counting Bloom Filter 可删）
- **跳表 vs B+ 树**：跳表实现简单、内存友好；B+ 树适合磁盘（矮胖，IO 少）
- **过期 key 会写进 RDB/AOF 吗**：bgsave/重写跳过已过期的；AOF 在删除时补一条 DEL；加载时过期不载入
- **从库会删过期的 key 吗**：不会，只等主库 DEL 同步——从库读到已过期数据是设计行为
- **哨兵的 quorum 和 majority**：quorum 管 ODOWN 判定；Leader 选举要过半，两者无关
- **replication buffer vs repl_backlog**：前者每个 slave 一个的输出缓冲（全量同步暂存增量）；后者全局一份的环形缓冲（部分重同步依据）
- **SCAN 游标原理**：反向二进制迭代，扩容后已扫前缀仍连续——保证不漏（可能重复）

## 十一、场景题（张口就来）

- **亿级 UV**：HyperLogLog，PFADD/PFCOUNT/PFMERGE，固定 12KB、误差 0.81%、取不了明细
- **签到/连续签到**：Bitmap，SETBIT/BITCOUNT/BITPOS，user+年 做 key、天数做偏移
- **日活/连续活跃**：Bitmap + BITOP AND（服务端原生交并）
- **附近的人**：GEO（底层 ZSet + geohash 52bit 做 score），GEOADD/GEOSEARCH；删用 ZREM
- **秒杀防超卖**：库存预热到 Redis → Lua 原子"判断+预扣"（99% 流量被挡）→ MQ 异步扣 DB/建单 → 超时取消回补库存 → 对账兜底
- **分布式限流**：固定窗口（INCR+EXPIRE，临界突刺）/ 滑动窗口（ZSet+Lua）/ 令牌桶（允许突发，Hash+Lua）；单机用 x/time/rate，分布式才上 Redis
- **全局唯一 ID**：INCR（注意宕机回退重号）或雪花（时钟回拨）；趋势递增即可用 INCR
- **延迟队列**：ZSet score 存执行时间 + 轮询 ZRANGEBYSCORE + Lua 原子取出删除（详见 10 章）

## 速查：面试高频三连问

**Q1. Redis 为什么快？**
> 内存存储 + 高效数据结构 + 单线程无锁 + epoll I/O 多路复用。核心：瓶颈不在 CPU 而在网络，单线程刚好够用，还避免了锁竞争和上下文切换。

**Q2. 缓存穿透 / 击穿 / 雪崩怎么区分和解决？**
> 穿透=查不存在（布隆过滤器 / 缓存空对象）；击穿=热点 key 过期瞬间（互斥锁 / 逻辑过期）；雪崩=大量 key 同时过期（TTL 加随机值 / 多级缓存 / 熔断降级）。

**Q3. 分布式锁完整链路？**
> `SET key uuid NX PX` 加锁 → 业务执行 → Lua 脚本（get 验证归属 + del）释放 → 长业务用 Redisson watchdog 续期 → 极端场景考虑 Redlock（半数成功，但有 GC/时钟争议）。
