# 数据类型与底层结构

> **核心认知：Redis 的每种类型都有"小数据用紧凑结构省内存、大数据用高效结构保性能"的双层设计，转换阈值由配置控制且不可逆。
> 理解这套"以时间换空间/以空间换时间"的取舍，比背编码表重要——所有设计的出发点都是：Redis 是内存数据库，字节就是钱。**

---

## 编码总览（Redis 7.x）

| 类型 | 底层编码 | 适用场景 |
|------|---------|---------|
| String | **SDS**（简单动态字符串） | 所有字符串/数值 |
| Hash | listpack / hashtable | 小且少用 listpack |
| List | **quicklist**（节点为 listpack） | 兼顾内存与操作效率 |
| Set | intset / listpack / hashtable | 全整数用 intset |
| Sorted Set | listpack / **skiplist + dict** | 小用 listpack |

查看当前编码：`OBJECT ENCODING key`

**版本差异警报（跑实验前必看）**：

| 行为 | Redis < 7.0 | Redis 7.0+ | Redis 7.2+ |
|------|-------------|-----------|------------|
| OBJECT ENCODING 显示 | `ziplist` | `listpack` | `listpack` |
| Hash entries 阈值默认 | **512** | **512**（配置改名 hash-max-listpack-entries，阈值未变；128 是 ZSet 的默认） | 512 |
| Set 插入非整数后 | 直接 `hashtable` | 直接 `hashtable` | 先转 `listpack` |

本地 docker 实例若是 6.2，实验会看到：Set 插字符串后直接 hashtable、编码名显示 ziplist——这与实验代码注释的预期输出（基于 7.x）不同，属版本差异而非 bug。（Hash 是第 513 个字段才触发转换，6.2 与 7.x 行为相同，不属版本差异；"129 触发"是 ZSet 的行为。）

## SDS：为什么不用 C 字符串

| 特性 | C 字符串 | SDS |
|------|---------|-----|
| 取长度 | O(N) 遍历到 `\0` | **O(1)**，头部直接存 len |
| 二进制安全 | 否（`\0` 即结尾） | **是**，可存图片/序列化数据 |
| 内存重分配 | 每次修改都可能 realloc | **空间预分配 + 惰性释放** |

空间预分配：扩容时若 < 1MB 多分配一倍，≥ 1MB 多分配 1MB，把连续 append 的 realloc 次数降到对数级。

## listpack：取代 ziplist，杀死连锁更新

**ziplist 的问题**：每个 entry 头部存 `prevlen`（前一个 entry 的长度）。前一个 entry 从小变大时，当前 entry 的 prevlen 也要变大，可能引发连锁更新，最坏 O(N²)：

```
ziplist entry: | prevlen | encoding | data |
               ↑ 记录前一个 entry 的长度
               前一个变大 → 我也要变 → 下一个也要变 → ...连锁

listpack entry: | encoding | data | backlen |
                ↑ 只在末尾记录自己的长度
                改一个 entry 完全不影响其他 entry
```

**工程取舍的典范**：listpack 为了消除最坏情况，放弃了"从任意位置找前驱"的能力——而 Redis 的使用场景根本不需要这个能力。牺牲用不到的功能，换取最坏情况的确定性。

## 编码转换阈值（默认值，触发后不可逆）

| 类型 | 转换 | 触发条件 | 配置项 |
|------|------|---------|--------|
| Hash | listpack → hashtable | 元素 > 512 或 value > 64B | hash-max-listpack-entries / value |
| List | 始终 quicklist，无整体转换 | 节点大小超限自动分裂新节点 | list-max-listpack-size（默认单节点 8KB） |
| Set | intset → hashtable | 元素 > 512 | set-max-intset-entries |
| Set | intset → listpack | 插入非整数（7.2 前直接跳 hashtable） | — |
| Set | listpack → hashtable | 元素 > 128 或 value > 64B | set-max-listpack-entries |
| ZSet | listpack → skiplist | 元素 > 128 或 member > 64B | zset-max-listpack-entries / value |

三个关键实验现象（7.x 实例）：

1. **第 513 个字段触发转换**：512 个字段是 listpack，第 513 个进来立刻变 hashtable（默认配置下 6.2 与 7.x 行为相同；"第 129 个触发"是 ZSet 的行为——zset 阈值为 128）
2. **单个 value 65B 也触发**：value=64B 是 listpack，65B 立刻 hashtable，跟元素数无关（实测 6.2 同样成立）
3. **转换不可逆**：删回 1 个字段，编码仍是 hashtable——回不去 listpack

**生产事故模式**：有人把 `hash-max-listpack-entries` 调到几千想省内存，结果单个大 Hash 的 `HGETALL`（listpack 是 O(N) 顺序扫描）直接打出慢查询，拖垮主线程。阈值是保护，不是负担。

## intset：整数集合的紧凑存储

Set 全是整数时用 intset（有序数组，二分查找）：

- 三个编码档位 int16 / int32 / int64，按最大元素自动选择
- **升级不可逆**：插入超 int16 的大整数 → 按需升档（仍在 int32 范围内如 70000 只升 int32，超 int32 才升 int64），删掉它编码也降不回去
- 内存对比实验：10 个小整数共 84B，插入 `99999999999` 后全部翻 4 倍；删掉它内存只减该元素本身（152B → 144B），**回不到 84B——数组仍是 int64 编码**

**生产陷阱**：以为删掉大整数内存会回到从前，结果只是少了一个元素，其余元素仍按升级后的宽度存——升级是一锤子买卖。

## Sorted Set：skiplist + dict 双结构

转换后同时持有两个结构，各司其职：

```
skiplist（跳表）           → 范围查询 ZRANGE / 排名  O(log N)
dict（哈希表）             → ZSCORE 精确查分值       O(1)
```

**为什么用跳表不用红黑树**（高频追问）：

| | 跳表 | 红黑树 |
|--|------|--------|
| 范围查询 | 找到起点后顺序遍历链表，自然 | 需要中序遍历，实现绕 |
| 实现复杂度 | 插入/删除只改指针 | 插入/删除要旋转重染色 |
| 内存 | 每节点平均 1.33 个指针（层高概率 0.25） | 每节点固定 2 指针 + 颜色位 |

**追问：跳表 vs B+ 树**（对照 MySQL）：

```
跳表                          B+ 树
内存友好，指针少               每个节点存多个 key，为磁盘块优化
瘦高：查询路径长，每跳随机内存访问   矮胖：树高 3~4 层，磁盘 IO 次数少
实现简单                      实现复杂（页分裂/合并）
不适合磁盘                    为磁盘而生
```

**各自适配存储介质**：Redis 在内存，随机访问廉价，跳表够用且简单；MySQL 在磁盘，必须用矮胖的 B+ 树压 IO 次数。

## 渐进式 rehash

dict 扩容不是一次性搬完（大表百万 key 一次性迁移会阻塞主线程几百 ms），而是分摊到每次操作：

```
ht[0]       旧表（待迁移）
ht[1]       新表（2 倍大小）
rehashidx   迁移进度，初始 -1，完成后置回 -1

每次增删改查顺手迁移一个 bucket
```

**迁移期间的行为：**

- **写**：只写 ht[1]，保证 ht[0] 只减不增，迁移终会完成
- **读**：先查 ht[0]，没有再查 ht[1]（key 可能还没迁过去）

**触发条件：**

- 扩容：负载因子（used/size）> 1；**BGSAVE / BGREWRITEAOF 期间阈值提高到 5**
- 缩容：负载因子 < 0.1

**为什么 BGSAVE 期间抑制 rehash**：fork 后父子进程共享内存页（COW）。rehash 大量写新表 → 大量页被修改 → COW 复制暴增 → 内存暴涨。这是"持久化"与"内存管理"两章的知识交汇点。

**工程影响**：大量写入时 rehash 持续进行，每次操作多一个 bucket 迁移开销，压测会看到轻微延迟抖动——这是正常的，不是故障。

## 场景选型速查

| 需求 | 用什么 |
|------|--------|
| 对象多字段存储 | Hash（比 String 存 JSON 省——可单独读写字段，不用整体反序列化） |
| 排行榜 | ZSet（ZREVRANGE 直接拿 TopN） |
| 去重/共同关注 | Set（SINTER/SUNION 交并集） |
| 消息列表 | List（LPUSH/BRPOP 阻塞队列） |
| 计数器/分布式锁 | String（INCR 原子 / SET NX PX） |
| 位统计（签到） | String 当 bitmap 用（SETBIT/BITCOUNT） |
