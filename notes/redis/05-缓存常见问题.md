# 缓存常见问题

> **核心认知：穿透、击穿、雪崩本质上都是同一件事——"本该被缓存挡住的请求打到了 DB"，只是原因不同：
> 穿透是"查的数据根本不存在"（缓存无法填充），
> 击穿是"热点 key 过期的瞬间"（并发集中打一个点），
> 雪崩是"大量 key 同时过期"（并发打一大片）。
> 先分清原因，方案自然对号入座。**

---

## 三兄弟对比速查

| 问题 | 触发原因 | 典型场景 | 核心解法 |
|------|---------|---------|---------|
| 穿透 | 查询**不存在**的数据 | 恶意攻击、爬虫遍历 ID | 缓存空对象 / 布隆过滤器 |
| 击穿 | **热点 key** 过期瞬间 | 秒杀商品详情 | 互斥锁 / 逻辑过期 |
| 雪崩 | **大量 key 同时**过期或 Redis 挂 | 批量预热的缓存统一 TTL | TTL 加随机值 / 多级缓存 |

---

## 穿透：查不存在的数据

```
请求 user:999999（不存在）
   ↓ 缓存 miss（缓存里永远不会有它）
   ↓ DB 查询 → 也没有 → 无法回填缓存
   ↓ 下次请求同样直达 DB
```

### 解法一：缓存空对象（默认选择）

查不到也缓存一个 null 标记，设**短 TTL**（如 30s）：

- 优点：实现零成本，覆盖绝大多数场景
- 缺点：首波并发 miss 时仍会打到 DB（回填前的竞态窗口，需要配合互斥/singleflight 收窄）；大量不同的非法 key 会占内存（每个都要缓存 30s）；DB 新增该数据后最多 30s 不可见

### 解法二：布隆过滤器（BF）

启动时预加载所有合法 key，请求先过 BF：

```
BF 判断 → 一定不存在 → 直接拒绝（不碰 DB）
       → 可能存在   → 走正常 缓存→DB 流程
```

**BF 原理**（bit 数组 + k 个哈希函数）：

```
写入：对 item 计算 k 个哈希，把对应 bit 位置 1
查询：k 个 bit 全是 1 → "可能存在"（哈希碰撞会误判）
      任意 bit 是 0  → "一定不存在"（写入置的 bit 不会消失）
```

| 特性 | 说明 |
|------|------|
| 假阳性 | ≈ 1~3%，误判"存在"→ 放行去查 DB（无害，量小） |
| 假阴性 | **0%**，存在的 key 一定查得到（不会漏挡） |
| 不支持删除 | 一个 bit 被多个 key 共享，删一个会误伤其他 |
| 内存 | 极省：16KB bitmap 管 1 万个 key（对比 SET 存 key 名约 500KB~1MB） |

不支持删除的补丁：**Counting Bloom Filter（CBF）**，bit 换成 4bit 计数器，加 1 减 1 支持删除，代价是内存翻几倍。

### 何时值得上 BF

不是每个缓存都要 BF。满足"对外可枚举查询（用户名/手机号/ID 探测）+ key 空间稀疏 + 高 QPS 且 DB 敏感"才值得，否则空值缓存足够。

BF 的代价清单：预加载全量 key、新增 key 要同步写入、假阳性、占内存。

### 完整防御纵深

```
云厂商 DDoS/WAF     ← 挡洪水，越靠前越好
   ↓
网关限流            ← 挡低频异常
   ↓
布隆过滤器          ← 挡穿透到 DB
   ↓
空值缓存            ← 挡 BF 假阳性漏过的
   ↓
熔断降级            ← DB 的保命符
```

BF 防"穿透到 DB"，不防"服务被瘫痪"——瘫痪要靠限流和熔断。

## 击穿：热点 key 过期

热点 key（如秒杀商品）过期的瞬间，成百上千并发同时 miss，全部涌向 DB。

### 解法一：互斥锁

只放一个请求去查 DB 回填，其他人等：

```
miss → SET NX 抢锁 → 抢到：查 DB → 回填缓存 → 释放锁
                    → 没抢到：sleep 短暂等待 → 重试读缓存
```

- 优点：强一致，缓存永远不会有脏数据窗口
- 缺点：等待期间请求阻塞，锁持有方挂了要等锁超时

**Go 生态更优雅的等价物：`singleflight`**——同 key 并发请求只有一个真正执行，其余等待并直接共享结果，无需重试逻辑：

```
互斥锁       抢不到的重试，逻辑自己控制
singleflight 等待者直接拿结果，代码更干净
```

注意 singleflight 是**进程内**去重（单实例有效），分布式场景仍需 Redis 锁，或接受每个实例各查一次 DB。

### 解法二：逻辑过期

热点数据**物理上永不过期**（不设 TTL），过期时间作为字段存进 value：

```
读到"已逻辑过期" → 返回旧值（立即可用）→ 异步触发后台线程重建缓存
```

- 优点：请求永不阻塞，高可用
- 缺点：重建完成前读到的都是旧数据（最终一致）；内存中常驻不淘汰

| | 互斥锁 | 逻辑过期 |
|--|--------|---------|
| 一致性 | 强 | 最终一致 |
| 可用性 | 有阻塞窗口 | 永不阻塞 |
| 适用 | 不接受脏数据 | 热点数据可容忍短暂旧值 |

## 雪崩：大量 key 同时失效

两种成因对应两种解法：

**成因一：统一 TTL 同时到期**（批量预热埋的雷）

```
解法：TTL = 基础值 + random(0, 波动区间)
例如 30min + rand(0~5min)，把过期时间打散在时间轴上
```

**成因二：Redis 实例本身挂了**（所有 key 等于同时失效）

```
解法：Redis 高可用（哨兵/集群，见 04-高可用）
     多级缓存：本地缓存(L1) → Redis(L2) → DB
     熔断降级：DB 前挂闸，流量超限时快速失败或返回兜底数据
```

**配套手段：缓存预热**——冷启动/重启后缓存是空的，第一波流量全部打到 DB（等于一次人为雪崩）。上线前主动把热点数据灌进缓存（脚本灌 / 流量回放），再灰度放量。预热本身注意别用统一 TTL（否则埋下一次真雪崩的雷）。

**统一 TTL vs 随机 TTL 的实验数据**（200 个 key、2s 基础 TTL、随机组 TTL 打散到 2~4s）：2.2s 时统一组命中率 0%，随机组约 90% 存活——DB 压力从"瞬间脉冲"摊平为"缓慢爬坡"。

## 缓存与数据库一致性

### 删除顺序：先删缓存 vs 先更 DB（正面对比）

| | 先删缓存，再更 DB | 先更 DB，再删缓存（推荐） |
|--|------|------|
| 脏数据窗口 | 删除后到 DB 更新完成前，读请求 miss → 读到**旧 DB 值**回填 | 只有"读线程恰在更 DB 前查了旧值"的窄窗口 |
| 窗口大小 | 与 DB 写耗时同量级（较长） | 与一次读的耗时同量级（极窄，需精确交错才触发） |
| 结论 | 差，需延迟双删补救 | 首选 |

先更 DB 再删缓存的脏数据前提非常苛刻：读线程要在更 DB 之前 miss、又要在删缓存之后才回填——前后两个条件中间隔着整个 DB 写。所以它是"极小概率"而非"零概率"，追求彻底干净才需要延迟双删/Canal。

### 首选：旁路缓存（Cache Aside），更新 DB 后删除缓存

**为什么删除而不是更新缓存**——并发写覆盖问题：

```
线程A 更新 DB(新值) → 线程B 更新 DB(旧值) → 线程B 更新缓存(旧值) → 线程A 更新缓存(新值)
结果：DB = 旧值，缓存 = 新值 → 不一致，且没人修复
```

删除缓存则下次读时自然回填最新值，不存在写覆盖。

### 延迟双删：补上删除方案的窗口期

普通"先更 DB 后删缓存"的漏洞——读线程在写线程更新 DB 前读了旧值，还没回填：

```
T1: 写线程更新 DB(新值)
T2: 读线程缓存 miss，查 DB —— 拿到旧值（T1 前发起的查询）
T3: 写线程删除缓存
T4: 读线程把旧值回填缓存        ← 脏数据诞生
```

延迟双删：

```
删缓存 → 更新 DB → sleep(主从延迟 + 读线程回填耗时) → 再删一次缓存
```

第二次删除把可能被回填的旧值清掉，下次读拿到新值。

**两个必须知道的深坑：**

1. **主从延迟陷阱**：读线程查的是从库，主从同步没完成时拿到旧值回填；双删的 sleep 必须覆盖主从同步延迟，但延迟本身不可精确预知——sleep 时间是玄学
2. **彻底解法是 Canal 订阅 binlog**：监听从库同步完成后的 binlog 事件再删缓存，从机制上消除窗口期，业务代码零侵入

### 其他方案

- **MQ 异步重试**：删除失败发消息重试，保证最终一致
- **订阅 binlog（Canal）**：DB 变更 → Canal → 删缓存，业务无侵入，适合大规模
