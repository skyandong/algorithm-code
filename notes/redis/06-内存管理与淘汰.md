# 内存管理与淘汰

> **核心认知：Redis 是内存数据库，内存是唯一稀缺资源。围绕内存有三条主线：
> 过期（key 到了 TTL 怎么删）、淘汰（内存满了删谁）、阻塞（删除动作本身会不会卡住主线程）。
> 三者的共同设计哲学：把大动作拆小、把同步变异步、把开销分摊——和渐进式 rehash 一脉相承。**

---

## 过期 Key 的删除机制

单靠任何一种机制都有缺陷，Redis 用两种组合：

### 惰性删除（被动）

```
访问 key 时才检查：过期 → 删除并返回 nil
```

- 优点：零额外 CPU
- 缺点：过期 key 如果一直没人访问，**内存永远不释放**

### 定期删除（主动）

```
每 100ms（hz 配置，默认 10）从设置了 TTL 的 key 中随机抽 20 个
  → 删掉其中已过期的
  → 若过期比例 > 25%，立刻再抽 20 个（说明积压严重）
```

- 优点：兜住"没人访问的过期 key"
- 缺点：随机抽样，小概率 key 长期漏网

**实验现象**：写 1000 个 100ms TTL 的 key，等 200ms 后查 `INFO keyspace`——expires 数量可能仍不为零（定期删除还没扫到）；此时 GET 其中一个立即返回 nil（惰性删除触发）。**结论：过期 ≠ 立刻释放内存，"删除有延迟"是设计行为，不是 bug。**

监控：`INFO keyspace` 的 expires 字段观察待过期 key 积压量。

## 大 Key 删除的阻塞问题

`DEL` 是**同步**操作：删一个 100 万元素的 Hash，主线程要把所有内存释放完才返回，期间阻塞一切命令（几百 ms 级）。

```
DEL     主线程同步释放全部内存 → 阻塞所有命令
UNLINK  主线程只做 O(1) 的"解除引用" → 实际释放交给后台线程
```

Redis 4.0+ 的异步释放全家桶：

```
UNLINK key                       命令级：代替 DEL
lazyfree-lazy-eviction yes       淘汰时异步释放
lazyfree-lazy-expire yes         过期删除时异步释放
lazyfree-lazy-server-del yes     服务端内部 DEL 也走异步
```

**生产规则**：元素数 > 1 万或内存 > 1MB 的 key 一律 `UNLINK`，或直接开 lazyfree 配置。实验数据：10 万字段的 Hash，DEL 毫秒级、UNLINK 微秒级，相差两个数量级。

超大 key（百万元素）连 UNLINK 都有内存曲线问题（后台释放期间内存不降反升），终极方案是渐进式删除（见《09-生产排查与运维》）。

## 淘汰策略（maxmemory-policy）

内存达到 `maxmemory` 时的行为，8 种策略一张表记牢：

| 策略 | 范围 | 方式 |
|------|------|------|
| **noeviction（默认）** | — | 不淘汰，写命令直接报错 |
| allkeys-lru | 所有 key | 近似 LRU |
| allkeys-lfu | 所有 key | LFU（4.0+） |
| allkeys-random | 所有 key | 随机 |
| volatile-lru | 仅设了 TTL 的 key | 近似 LRU |
| volatile-lfu | 仅设了 TTL 的 key | LFU |
| volatile-random | 仅设了 TTL 的 key | 随机 |
| volatile-ttl | 仅设了 TTL 的 key | 优先删快过期的 |

**volatile 系列的语义**：没设 TTL 的 key 永不淘汰——把"哪些数据可以被淘汰"的决定权交给业务（设不设 TTL）。

### 近似 LRU：为什么不是真 LRU

真 LRU 需要全局双向链表：每次访问都要摘节点、插头部，内存开销（每 key 两个指针）和 CPU 开销都大。

```
近似 LRU：随机抽 maxmemory-samples 个（默认 5）
         淘汰其中最久未访问的
采样数越大越接近真 LRU，CPU 开销越高
```

3.0 起引入候选池（eviction pool），采样结果会积累复用，效果进一步逼近真 LRU。每个 key 只需记录一个 24bit 的最近访问时间戳，代价极小。

### LFU：为热点场景而生

LRU 的缺陷：**历史热点**只要最近有一段时间没访问，就会被当冷数据淘汰；偶发的批量扫描（如一次全量导出）会把真正的热点挤出去。

LFU 用 **Morris 计数器**记录访问频率（8bit，逻辑最大 255，对数递增——访问次数越多，计数增长的门槛越高），并随时间衰减（久不访问频率自动降）。

```
LRU  淘汰"最久未访问"     历史热点可能被误杀
LFU  淘汰"访问频率最低"   历史热点因累计频率高而存活
```

查询单个 key 的频率：`OBJECT FREQ key`（需 LFU 策略）。

### 怎么选

```
纯缓存（key 可随时重建）      → allkeys-lru / allkeys-lfu
有明确冷热数据分层            → allkeys-lfu 更精准
部分 key 是重要数据不能丢     → volatile-lru（重要的不设 TTL）
Redis 同时承担存储角色        → noeviction + maxmemory 告警
```

**一个易忽略的点**：noeviction（默认）下内存打满后**所有写命令报错**——如果 Redis 是存储而非缓存，必须在监控里盯住 `used_memory / maxmemory` 比例，别等业务写炸了才发现。

## 内存优化速查

| 手段 | 收益 |
|------|------|
| 控制编码转换阈值 | 小 Hash/ZSet 留在 listpack，省数倍内存 |
| 拆分大 key | 100 万字段的 Hash 拆成 1000 个千字段 Hash |
| 用 Hash 存对象代替 String 存 JSON | 可增量读写字段，省序列化 |
| 善用 intset/bitmap | 全整数 Set 用 intset；签到场景用 bitmap |
| `MEMORY USAGE key` | 精确测单个 key 占用（聚合类型 O(N)） |
| `redis-cli --bigkeys` | 采样找大 key（详见 09） |
