# 场景题专题：用 Redis 怎么实现 X

> **核心认知：面试的最后一公里是场景题——"用 Redis 怎么实现签到/排行榜/限流/秒杀"。
> 答题心法：先给方案对比（两三个候选 + 取舍），再给推荐方案的落地细节（命令 + 关键参数 + 已知缺陷）。
> 每个题都尽量回扣前面章节的原理（Bitmap=String、GEO=ZSet、限流=Lua 原子、秒杀=预扣+异步落库）。**

---

## HyperLogLog：亿级 UV 统计

**问题**：统计页面 UV（独立访客数）。SET 去重一个用户几十字节，1 亿用户就是几个 GB；BITCOUNT 的 bitmap 按用户 ID 建位图也要 1亿/8 ≈ 12MB（可接受但精确）。

**HLL 的取舍：用 0.81% 的误差换 12KB 的固定内存。**

```
PFADD page:uv:20260831 user1 user2 user3   # 记录访客(同一用户重复加无影响)
PFCOUNT page:uv:20260831                    # 返回估算的基数(有 ~0.81% 误差)
PFMERGE week:uv page:uv:20260831 ...        # 合并多天的 HLL 得周活
```

原理一句话：把每个元素哈希后用低 14 位（hash & 16383）做桶索引分到 16384 个桶，每桶寄存器记录哈希剩余位从低位起连续 0 的个数（"000…01" 模式的长度），桶越多、观测到的最长前导零越长，基数越大——概率估计，所以内存固定 12KB 与元素量无关。

| 特性 | 说明 |
|------|------|
| 内存 | 固定 ~12KB（16384 桶 × 6bit） |
| 误差 | 标准误差 ~0.81% |
| 能否取出元素 | **不能**，只有计数，没有明细 |
| 能否删除某个元素 | **不能**（重置只能 PFMERGE 绕不开，干脆 DEL 重来） |

**追问"要精确怎么办"**：用户量可控时用 SET（SADD + SCARD，内存换精确）；ID 连续时用 bitmap。

## Bitmap 深入：签到与活跃统计

Bitmap 不是新类型，就是**位数组编码的 String**（SETBIT 位偏移最大 2^32，value 上限 512MB）。

### 场景一：签到

```
# 用户 1001 在 2026 年 8 月签到(一年一个 key,天数做偏移)
SETBIT sign:1001:2026 240 1        # 第 241 天(0 起数)
GETBIT sign:1001:2026 240          # 查某天是否签到
BITCOUNT sign:1001:2026            # 年累计签到天数
BITPOS sign:1001:2026 0            # 第一个未签到的天(算连续签到的起点)
```

### 场景二：日活/月活（用户做偏移）

```
# 某天所有活跃用户:user_id 做 bit 偏移
SETBIT active:20260831 1001 1
BITCOUNT active:20260831           # 当日 DAU
# 连续 7 天都活跃的用户(交集):
BITOP AND active:week active:20260825 active:20260826 ... active:20260831
BITCOUNT active:week
```

**BITOP AND/OR/XOR/NOT 是服务端原生命令**（不是客户端逐位算），对多张位图做交并——这是 bitmap 活跃统计的核心武器。

| | Bitmap | Hash/Set |
|--|--------|----------|
| 内存 | 用户 ID 连续时极省（1 亿用户 ≈ 12MB） | 每用户几十字节起 |
| 适用前提 | **元素可映射为连续整数**（用户 ID） | 任意字符串 |
| 语义 | 只有"在/不在" | 可带值 |

**两个坑**：
1. 用户 ID 稀疏/随机字符串时，位偏移浪费巨大（一个 offset=10 亿的 bit 直接占 125MB）——先做内部映射（用户→自增序号），或改用 HLL
2. 签到 key 按"用户+年"设计，一个用户一年 365 bit ≈ 46B——千万别按"天+全量用户"散着存成千上万个 key

## GEO：附近的人 / 附近的店

```
GEOADD stores:city 116.397 39.909 "shop:1001"     # 加坐标(经度 纬度 member)
GEOSEARCH stores:city FROMLONLAT 116.40 39.91 BYRADIUS 3 km ASC COUNT 20
# 6.2+ 用 GEOSEARCH(旧命令 GEORADIUS 已废弃)
GEOPOS stores:city shop:1001                       # 取坐标
GEODIST stores:city shop:1001 shop:1002 km         # 两点距离
```

**底层就是 ZSet**：坐标经 geohash 编码成 52bit 整数当 score，member 不变。所以：
- GEO 的 key 就是 ZSet，可用 ZRANGE 等命令（但别这么干，可读性差）
- geohash 是**前缀编码**：相近的坐标共享前缀 → 框选某区域 = 按 score 区间 ZRANGEBYSCORE——这就是"附近"查询能走 ZSet 跳表范围查询的原因
- 误差：geohash 有边界问题（相邻区域的边界点会被分到不同块），生产按"扩大一圈查询后精确过滤"处理
- 删除 member 用 ZREM（GEO 没有专门的删除命令，这也是"GEO=ZSet"的证据）

## 秒杀库存扣减

**问题本质**：库存是共享计数器，超卖 = "查 + 判 + 减"不原子；DB 抗不住瞬时流量。

**方案演进（答题按这个顺序讲）：**

```
方案1: DB 行锁直接扣        UPDATE stock SET n=n-1 WHERE id=? AND n>0
      → 简单正确,但热点行锁 + DB 抗不住秒杀峰值

方案2: Redis Lua 原子预扣(推荐)
      → 库存放 Redis,Lua 里"判断+扣减"原子执行,扛住峰值
      → 扣成功发 MQ,异步落库真正扣 DB 库存、创建订单

方案3: 库存分段
      → 库存 10000 拆成 10 个 key 各 1000,流量打散到 10 个 key
      → 单 key 热点时才需要
```

方案 2 的核心 Lua：

```lua
-- KEYS[1]=库存key, ARGV[1]=本次扣减数
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil or stock < tonumber(ARGV[1]) then
    return -1                    -- 库存不足,直接失败
end
redis.call('decrby', KEYS[1], ARGV[1])
return stock - tonumber(ARGV[1]) -- 返回剩余库存
```

为什么必须 Lua 而不是"GET 判断 + DECR"：两步之间可能穿插其他请求的扣减——和分布式锁释放必须 Lua 是同一个道理（见《08-分布式锁》）。

完整链路：

```
① 提前把库存同步到 Redis(预热,防冷启动击穿)
② 请求进来 → Lua 原子预扣 Redis 库存
   - 失败 → 直接返回"已抢完"(99% 的流量在这里被挡掉)
   - 成功 → 发 MQ
③ 消费者异步:扣 DB 库存 + 创建订单(DB 削峰)
④ 对账兜底:定时任务比对 Redis 预扣量与 DB 实际成单量(丢单/回补)
⑤ 活动结束:MQ 消费完、库存清零
```

**追问必考**：
- **Redis 扣成功但 MQ 丢了怎么办**：Producer 侧confirm + 本地消息表重发；极端丢单靠对账回补
- **扣了 Redis 库存但用户没付款**：订单超时取消 → 回补 Redis 库存（INCRBY）
- **能不能不扣 Redis、直接乐观锁扣 DB**：可以（n>0 的 UPDATE 就是乐观锁），但峰值全打到 DB——Redis 预扣的意义就是"把 DB 的峰值削成均值"

## 分布式限流

三种经典算法，Redis 都能落地：

### 1. 固定窗口（最简单）

```
INCR rate:user:1001:2026083113      # key 带时间片(小时)
结果 == 1 → EXPIRE key 3600         # 首次设置过期
结果 > 阈值 → 拒绝
```

**致命缺陷：临界突刺**——窗口交界处（59 分 59 秒 + 1 分 00 秒）两倍的流量在 2 秒内打进来，各自都不超限。简单场景够用，限流要求高时不接受。

### 2. 滑动窗口（ZSet 实现）

```
每次请求:
ZADD rate:1001 <now_ms> <uuid>           # score=时间戳
ZREMRANGEBYSCORE rate:1001 0 <now_ms - window>   # 删掉窗口外的老记录
ZCARD rate:1001                           # 窗口内请求数
> 阈值 → 拒绝,否则放行
```

窗口内真实计数，无临界问题。代价：内存与窗口内请求数成正比（高频接口要评估），三步必须包进 Lua 保证原子。

### 3. 令牌桶（匀速放行）

```lua
-- KEYS[1]=桶key, ARGV=速率/容量/当前时间
local rate, capacity, now = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local bucket = redis.call('hmget', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(bucket[1]) or capacity
local ts = tonumber(bucket[2]) or now
tokens = math.min(capacity, tokens + (now - ts) * rate / 1000)  -- 补充令牌
if tokens < 1 then return 0 end
redis.call('hmset', KEYS[1], 'tokens', tokens - 1, 'ts', now)
redis.call('pexpire', KEYS[1], math.ceil(capacity / rate * 1000 * 2))
return 1
```

允许突发（桶里攒的令牌一次消费），又能限制长期速率——Google Guava RateLimiter、Sentinel 底层同思路。单机限流直接用进程内 `golang.org/x/time/rate`，**分布式限流才需要 Redis**。

| | 固定窗口 | 滑动窗口 | 令牌桶 |
|--|---------|---------|--------|
| 实现 | INCR+EXPIRE | ZSet+Lua | Hash+Lua |
| 精度 | 差（临界突刺） | 好 | 好 |
| 内存 | O(1) | O(窗口内请求数) | O(1) |
| 允许突发 | 否 | 否 | 是（受桶容量控制） |

## 全局唯一 ID

| 方案 | 思路 | 优缺点 |
|------|------|--------|
| Redis INCR | `INCR id:order` 自增，可按业务加前缀、按天分段 | 简单、单调、性能高；持久化/主从切换可能**重号**（回退到旧值） |
| 雪花算法 | 时间戳+机器ID+序列号拼 64bit，纯本地生成 | 无外部依赖、趋势递增；依赖时钟（时钟回拨出问题）、机器 ID 要分配 |
| DB 自增/号段 | 美团 Leaf：批量从 DB 取一段号在内存发 | DB 压力小；重启浪费号段 |

Redis 方案的**重号风险**要点出：INCR 后还没持久化/没同步到 slave 就宕机，恢复后计数回退——所以要么接受（大多数业务 ID 只需唯一+趋势递增，重号概率极低且可用业务校验兜底），要么雪花/号段。

## 场景题速查表

| 需求 | 方案 | 关键命令/机制 |
|------|------|--------------|
| 亿级 UV（容许 0.8% 误差） | HyperLogLog | PFADD / PFCOUNT / PFMERGE |
| 签到/连续签到 | Bitmap | SETBIT / BITCOUNT / BITPOS |
| 日活/连续活跃 | Bitmap | BITOP AND |
| 排行榜 | ZSet | ZADD / ZREVRANGE（见 02 章） |
| 附近的人 | GEO（=ZSet+geohash） | GEOADD / GEOSEARCH |
| 秒杀防超卖 | Lua 原子预扣 + MQ 异步落库 | DECR 判断+扣减一体 |
| 分布式限流 | 令牌桶/滑动窗口（Lua 原子） | ZADD+ZREMRANGEBYSCORE+ZCARD |
| 延迟队列 | ZSet 轮询 | ZRANGEBYSCORE + Lua（见 10 章） |
| 全局唯一 ID | INCR（或雪花） | INCR，注意重号风险 |

**万变不离其宗**：场景题 = 挑数据结构（02）+ 保原子（07）+ 防击穿/雪崩（05）+ 必要时异步削峰。答完方案主动说缺陷和兜底，是区分度所在。
