# TLS 1.2 握手：一步步拆

> **核心认知：握手就是四封往返的信。
> 第一封：客户端报家底（我会什么）；第二封：服务器亮证件 + 挑方案；
> 第三封：客户端出钥匙；第四封：双方对暗号确认没被动手脚。
> 把每封信"为什么必须存在"想通，整个流程就不用背了。**

---

## 全景图（2-RTT）

```
客户端                                        服务器
  │                                              │
  │ ① ClientHello ────────────────────────────▶ │  "我会这些版本/算法/曲线"
  │                                              │
  │ ◀────────────────────────── ServerHello ──  │  "就选这套"（第一轮结束）
  │ ◀──── Certificate（我的证件）                │
  │ ◀──── ServerKeyExchange（我的DH公钥+签名）   │
  │ ◀──── ServerHelloDone（说完了）              │
  │                                              │
  │ ② ClientKeyExchange（我的DH公钥）─────────▶ │  ← 此刻双方各自算出同一把密钥
  │    ChangeCipherSpec（下面开始加密）           │
  │    Finished(加密)（暗号核对）                 │
  │                                              │
  │ ◀───────────────────── ③ ChangeCipherSpec ─│
  │ ◀───────────────────── ④ Finished(加密) ──  │  ← 握手完成，开始加密通信
```

---

## 每封信拆开讲

### ① ClientHello：亮家底

客户端把"我会的东西"全报上来：

| 字段 | 人话 |
|------|------|
| client_version | 我最高会说 TLS 1.2 |
| random | 32 字节随机数（后面派生钥匙的原料之一） |
| cipher_suites | 我会的算法组合清单，按喜好排序 |
| **SNI 扩展** | **我要访问哪个域名**——一台 IP 托管多个 HTTPS 站全靠它 |
| supported_groups | 我会哪些椭圆曲线（x25519 等） |

### ② ServerHello + Certificate + ServerKeyExchange

服务器三连发：

**ServerHello**：拍板——选哪个版本、哪个算法套件、再出自己的 32 字节随机数。

**Certificate**：亮证件（证书链）。证书里最关键的是**服务器的公钥**和 **CA 的签名**（下一章细讲）。

**ServerKeyExchange**：服务器的 DH 临时公钥 + **用私钥做的签名**。

> **为什么 DH 公钥要签名？** DH 公钥是随手生成的，谁知道是不是真服务器的？中间人完全可以塞一个自己的 DH 公钥进来。用证书私钥签一下 = "这个 DH 公钥确实是我本人发的"。

**ServerHelloDone**：一封空信，"我说完了，该你了"。

### ③ ClientKeyExchange + ChangeCipherSpec + Finished

**ClientKeyExchange**：客户端也出自己的 DH 临时公钥。

**关键魔法时刻**——双方各自计算：

```
客户端：我的私钥 a × 服务器的公钥 bG  = abG
服务器：我的私钥 b × 客户端的公钥 aG  = abG   ← 数学保证结果相同
                                              ← 而且abG从未在网络上传输过！
```

这个 `abG` 就是原料（pre-master secret），加上两个 random，派生出最终的会话密钥。**偷听者拿不到 a 和 b，永远算不出 abG。**

**ChangeCipherSpec**：一句话通知——"从下一条消息起，我说的都是加密的"。

**Finished**：**整个握手最重要的安全保险**。内容是把之前所有握手消息做哈希再用密钥加密。中间人哪怕改过任何一个字节（比如偷偷把客户端的强算法清单删了），双方算出的哈希对不上，立即翻脸断连。

### ④ 服务器 ChangeCipherSpec + Finished

服务器同样切换到加密模式、回暗号。至此四封信完毕，通道建立。

---

## 密钥派生：一把钥匙切成好几把

从 pre-master secret 派生出的密钥块切成多把，**收发方向用不同的钥匙**：

```
client_write_key   客户端 → 服务器 加密用
server_write_key   服务器 → 客户端 加密用
（MAC 密钥同理，各方向一把）
```

为什么分开？防的是跨方向反射——把 Client→Server 的密文原样塞回 Server→Client 方向当响应回放。同方向转发防不住（服务器本来就能解客户端的密文）；同方向重放靠每次连接独立密钥和记录序列号防。

---

## 记忆锚点（面试 30 秒版）

> "TLS 1.2 握手两个 RTT：客户端先报 ClientHello，服务器回 ServerHello+证书+DH 公钥，客户端再回自己的 DH 公钥，双方各自算出共享密钥；最后双方交换 Finished——对全部握手消息的哈希做验证，防篡改。密钥本身从不在网络上传输。"
