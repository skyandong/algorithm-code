# 为什么需要 TLS

> **核心认知：** TLS 解决的是「隔着不可信的网络，怎么安全地说话」——偷听对应加密、篡改对应校验、冒充对应证书。而它的全部性能智慧就一句话：**贵的非对称密码只用一次（商量钥匙），之后全程用便宜的对称密码传数据**。

---

## 先用寄快递理解三个威胁

你要给朋友寄一份机密文件，快递路上要经过很多中转站（不可信）：

```
威胁1 偷听    中转站拆开看 → 需要加密（把文件锁进箱子）
威胁2 篡改    中转站偷换内容 → 需要完整性校验（封条，动过就能发现）
威胁3 冒充    骗子假装你朋友收件 / 假装快递公司 → 需要身份认证（证件）
```

HTTPS = HTTP + TLS。TLS 就是那把锁 + 封条 + 证件检查，HTTP 只是被保护的内容。

## 对称 vs 非对称：一把钥匙 vs 两把钥匙

**对称加密（AES）**——同一把钥匙加密和解密：

```
明文 ──[钥匙K加密]──▶ 密文 ──[同一把钥匙K解密]──▶ 明文

快：硬件加速后每字节纳秒级
致命问题：怎么把钥匙 K 安全地交给对方？
          钥匙走网络 → 半路被抄 → 白加密了
```

**非对称密码（RSA / ECDH）**——公钥和私钥两把：

```
RSA：公钥（可以随便发）加密 → 只有私钥（自己藏着）能解开
ECDH：不是加密算法，是密钥协商——双方各持一对公私钥，
      不传输密钥就"凭空"算出同一把共享密钥
（"公钥加密只有私钥能解"这话，只对 RSA 成立）

解决了"传钥匙"问题
但慢：比对称慢 100~1000 倍
```

**TLS 的混合策略（这是理解整个握手的钥匙）：**

```
① 握手阶段：用非对称密码学的办法，双方"凭空"商量出一把相同的钥匙
            （全程不传输钥匙本身！）
② 通信阶段：用这把钥匙做对称加密传数据

类比：先用贵的方式对暗号，对上之后全程说"黑话"，快得很。
```

## TLS 在协议栈的哪一层

```
┌─────────────────────────────┐
│ HTTP / SMTP / IMAP ...      │  应用层（内容）
├─────────────────────────────┤
│ TLS                         │  安全层（加密/认证/校验）
├─────────────────────────────┤
│ TCP                         │  传输层（可靠字节流）
├─────────────────────────────┤
│ IP                          │  网络层
└─────────────────────────────┘
```

先 TCP 三次握手（建立管道），再 TLS 握手（在管道里装保险箱），最后才跑 HTTP。

**TLS 内部又分两层：**

| 层 | 干什么 |
|---|--------|
| 握手层 | 商量密钥、验证书（干活前先谈好） |
| 记录层 | 把数据切块、加密、校验（干活本身） |

记录层每帧的头部固定五段，理解它就能读懂抓包：

| 字段 | 长度 | 说明 |
|------|------|------|
| Content Type | 1 字节 | 22 握手 / 20 切换密码规格 / 21 告警 / 23 应用数据 |
| Protocol Version | 2 字节 | **TLS 1.3 固定写 `0x0303`（即 1.2）**——中间设备太多，伪装成 1.2 才不被拦；真实版本靠 `supported_versions` 扩展协商 |
| Length | 2 字节 | 单帧明文上限 2^14 字节 |
| Data | 变长 | 上层载荷（握手消息或应用数据） |
| MAC | 变长 | 完整性校验：1.2 用独立的 HMAC 字段，1.3 统一 AEAD，校验内嵌进密文，不再单列 |

所以在 1.3 的抓包里看到"版本 1.2"别慌，那是刻意的伪装；判断真实版本要看 `supported_versions` 扩展。

## 版本演进一句话史

| 版本 | 一句话 |
|------|--------|
| SSL 3.0 / TLS 1.0 / 1.1 | 全部已废弃（各有致命攻击） |
| **TLS 1.2**（2008） | 至今主力，2-RTT 握手 |
| **TLS 1.3**（2018） | 1-RTT 握手 + 砍掉所有不安全算法 |

记住方向就行：**1.3 = 更快 + 更安全**（后面两篇专门讲怎么快、怎么安全）。
