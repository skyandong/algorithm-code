## 0. 全局写作惯例（三个模块都必须遵守）

1. **目录结构**：`notes/<模块名>/`，内含：
   - 编号笔记 `NN-标题.md`（每篇 9~12KB，含「核心认知」开头、目录、分节、面试高频、文末「本篇对应实验」行）
   - `experiments/NN_*.go` 可运行验证代码 + `main.go` 分发入口（模式：`go run ./experiments/ <名字>`，支持 all）
   - 独立 `go.mod`（module 名 `a<模块名>`，go 1.26，**零外部依赖**，全内存模拟）
   - `README.md`（目录 + 重点回顾自测清单 + 跑实验说明 + 与其他模块衔接）
   - `面试一口答.md`（每篇 3-5 题一问一答 + 文末「考前 60 秒主线串讲」）
2. **文风**：中文技术笔记；每篇开头 `> **核心认知：**` 一段话总结灵魂；正文多用「WHY」追问；代码示例注释讲清意图；表格优先于长段落。
3. **交叉引用**：引用已有模块时写明相对路径，已有素材（必须引用，体现知识串联）：
   - `notes/golang/01~13`（语言核心/并发/运行时/工程）
   - `notes/design-pattern/01~08`（原则/创建/结构/行为/接口/并发/错误/反模式）
   - `notes/distributed/01~07`（CAP/Raft/事务/锁/分片/时钟/故障检测）
   - `notes/mysql/11`（分库分表）、`notes/mysql/13`（主从复制）
   - `notes/redis/05`（缓存三问）、`notes/redis/08`（分布式锁）
   - `notes/akafka`（Kafka 削峰/ISR/事务）
   - `notes/nginx/03`（限流）
   - `engineering/consistenthash`、`engineering/ringcounter`
4. **实验质量红线**（重要，本仓库踩过的坑）：
   - 计量实验的准备工作（make/sink 分配）必须发生在 `ReadMemStats` **之前**，否则测量值被污染
   - 一致性哈希实验**禁用 fnv32a**（对 "node-0"/"node-1" 相似短串极度聚集，实测 5 节点挤在 1.5% 环长）——用 md5 取前 4 字节（ketama 同款）
   - 时序实验用双 sleep 护栏 + 同步 channel，保证 3 次运行输出一致
   - 每个实验跑完的数据要能对上理论值（在 README 里放「数据锚点表」）
   - `go vet` 必须过（注意 unused import/变量、printf 的 %w 只能用于 Errorf）

## 模块三：notes/system-design 系统设计专题（8 篇 + 实验）

**主线认知（写给每篇的总纲）**：系统设计考察的不是标准答案，是**决策过程**——问需求、给简单方案再演进、每个选型讲 trade-off、估算带数字。全模块按 **4S 框架**组织：Scenario（场景约束）→ Storage（存储选型）→ Scale（容量估算）→ Schema/演进。

### 01-方法论与估算
- 4S 流程详解；怎么「先问再答」（要问的 5 个问题：QPS/读写比/一致性/可用性/数据量）
- 速查表（必背数值）：一天≈10^5 秒；峰值=均值×3~10；单机 MySQL 写 ~2k QPS；单机 Redis ~10 万 QPS；MySQL 单表 <2000 万行；100B 行 × 1 亿 ≈ 10GB
- 通用演进骨架：LB → 无状态横扩 → 缓存 → MQ 削峰 → 主从/分片 → 多机房
- 实验：估算计算器（打印各级 QPS/存储推导链）

### 02-秒杀系统
- 六层削峰：静态化+CDN → nginx 限流（引用 notes/nginx/03 的 rate/burst/nodelay）→ 答题验证码 → Redis 预扣（DECR，<0 回滚）→ MQ 异步下单（引用 notes/akafka）→ MySQL 兜底（`UPDATE ... WHERE n>0` 条件更新防超卖）
- 不超卖闭环：Redis 挡量 + DB 最终正确 + 对账任务；库存分桶防热点 key（引用 distributed/05）
- BASE 的 UX 中间态：显示「抢到」订单异步生成（引用 distributed/01）
- 实验：内存模拟 Redis 预扣+DB 条件更新的完整闭环，含并发压测计数（10 万请求 0 超卖）

### 03-短链服务
- 发号器选型对照：自增 base62 / 雪花 / 号段双 buffer / 哈希查重（优劣表格）
- 读路径：Redis 全量热缓存（算账：1 亿×100B=10GB，3 分片）+ 布隆过滤器挡穿透（误判率与位数的计算公式）
- 301 vs 302：要统计点击选 302
- 实验：base62 编解码 + 简易布隆过滤器（插入 10 万、误判率实测 vs 理论）

### 04-Feed 流
- 推（写扩散）vs 拉（读扩散）对照表；**推拉结合**：大 V 只写发件箱、普通用户推收件箱、刷新时混合聚合
- 收件箱：Redis ZSet 存最近 100 条 + 老数据落库；排序按业务分数不是时钟（引用 distributed/06）
- cursor 翻页不用 offset（深翻页扫描爆炸，引用 notes/mysql/01）
- 扇出风暴用 MQ 异步；活跃/非活跃用户分策略
- 实验：推/拉/推拉结合三种模式的写读成本模拟对比（固定数据集，输出各自读写次数）

### 05-IM 系统
- 三大件：长连接网关（无状态化：连接映射存 Redis/etcd，断线任意网关接管；心跳+φ-accrual 判死引用 distributed/07）
- 可靠性铁三角：seqId（会话内单调，不乱序）+ ack+离线收件箱（不丢）+ messageId 幂等（不重，引用 design-pattern/07）
- 存储：消息表按会话 hash 分片（同会话同分片保有序，引用 distributed/05）；群聊不存储扇出
- 多端同步：每端记 sync_time 位点增量拉（类比 binlog 位点，引用 notes/mysql/13）
- 实验：seqId+ack+补洞的投递模拟（乱序到达后客户端重组还原）

### 06-分布式ID
- 理论引用 distributed/06，本篇讲工程：号段双 buffer 原理（buffer1 发到 10% 异步加载 buffer2；双号段库交替保高可用）
- 严格单调（fencing 语义）只有号段/etcd revision 做到，雪花只「趋势」
- UUIDv4 做 MySQL 主键的灾难分析（页分裂，引用 notes/mysql/01）
- 实验：双 buffer 号段发号器（模拟 DB 抖动期间发号不中断）

### 07-延迟任务系统
- 三方案对照：Redis zset 轮询 / 时间轮 / MQ 延迟分桶 topic（1m/5m/30m 逐级中转）
- **时间轮原理（重点，现场画图级）**：环形数组 60 格，任务挂格子链表，指针每秒走一格；超一圈用轮数字段（扫过减 1 不执行）；分布式化按任务 hash 分片多实例
- 可靠性：任务先落库再进内存轮（「内存是索引，DB 是真相」）；宕机重启重灌；执行幂等
- 实验：时间轮完整实现（单轮+轮数），对比 ringcounter 的差异；调度 1000 个跨多圈任务全部按时触发

### 08-缓存体系设计
- 三级缓存：本地（ns，小而热）→ Redis（ms，共享）→ DB；一致性代价随级别升高
- 串联 redis/05 三问的「架构叙事版」答案：穿透（bloom+空值）、击穿（锁单飞+逻辑过期）、雪崩（TTL 抖动+多级+熔断）
- 一致性：Cache-Aside + 先更库后删缓存为默认；失败补：延迟双删、binlog 订阅异步删；强一致路径直接读库（别为缓存上分布式事务）
- 热点 key：本地缓存 + key 分片打散（与秒杀库存分桶同构）
- 实验：三问各一个小重现（击穿时单飞重建的并发 DB 查询次数对比：无锁 100 次 vs 有锁 1 次）

### README + 面试一口答
- README 含「实验数据锚点表」（秒杀 0 超卖、布隆误判率±20%、时间轮 100% 按时等）
- 一口答 20 题左右 + 考前 60 秒串讲

## 模块四：notes/microservice 微服务治理（6 篇 + 实验）

**主线认知**：微服务的全部代价是「网络成了函数调用」——治理件解决由此产生的五类问题：找不到（注册发现）、改不动（配置）、连不稳（熔断限流）、看不见（可观测）、说不清（网关路由）。

### 01-注册与发现
- 服务定义（实例/服务名/元数据/健康状态）；心跳与 TTL（引用 distributed/07 的 φ-accrual）
- 三种实现对照：etcd（Raft 强一致，引用 distributed/02）/ consul（gossip 最终一致 + 健康检查丰富）/ nacos（AP+CP 可切换）
- 客户端发现 vs 服务端发现（sidecar/网关）；优雅上下线：先摘流量再停进程（发布事故的根源）
- 实验：内存注册中心（注册/心跳/摘除/发现），模拟实例宕机后列表收敛

### 02-配置中心
- 配置分层（静态/环境/动态）；热更新链路：推送（watch，引用 distributed/04）→ 校验 → atomic.Pointer 整体换快照（引用 notes/golang/07 §5.1）
- 灰度发布配置；回滚机制；敏感配置加密
- 实验：watch + atomic 快照的热更新闭环（更新瞬间并发读者全部读到一致的新旧版本，无中间态）

### 03-熔断降级限流（重点篇）
- 三者定位区分：限流保自己、熔断保下游（快速失败不拖死）、降级保核心（有损服务）
- **熔断器三态机**：closed → open（错误率超阈值）→ half-open（探活）；恢复策略（引用 design-pattern/04 状态机：转移表+纯函数）
- 滑动窗口计数（引用 engineering/ringcounter）；限流算法四件套：计数器/滑动窗口/漏桶/令牌桶（应用内版对照 notes/nginx/03）
- 实验：完整熔断器（三态+滑动窗口+探活），模拟下游故障→熔断→恢复全周期

### 04-网关
- 职责：路由/鉴权/限流/协议转换/灰度；网关 vs BFF vs LB 的层次关系（引用 notes/nginx/02 反代）
- 灰度路由：按 header/uid 百分比分流（发布的核心保障）
- 实验：内存网关路由表 + 中间件链（复用 design-pattern/03 的 Chain）

### 05-可观测性
- 三支柱：metrics（聚合数字）/ logging（离散事件）/ tracing（跨服务因果链）；采样策略（头部/尾部采样）
- OpenTelemetry 统一模型；trace_id 全链路透传（引用 demos/tracing 现成 demo）
- 四个黄金指标：延迟/流量/错误率/饱和度（SRE 信号）
- 实验：进程内 trace 上下文透传（多函数调用链 span 组装，输出调用树）

### 06-服务网格 intro（了解级）
- sidecar 做了什么（把治理件从 SDK 下沉到基础设施）；istio 架构（envoy 数据面 + istiod 控制面）
- SDK 模式 vs sidecar 模式取舍（升级成本/语言无关/一跳延迟）
- 无实验，纯概念篇 + 与模块四前五篇的对照表

## 生成顺序与验证清单

**顺序**：模块三（01→08 逐篇）→ 模块四 → 模块五 → 最后更新根目录 `README.md` 的 notes 清单。

**每篇完成后的验证（让 AI 自己跑）**：

```bash
export PATH=$HOME/sdk/go1.26.3/bin:$PATH   # 或本机对应 go 路径
cd notes/<模块名>
go vet ./experiments/                      # 必须 0 error
go run ./experiments/ all                  # 全部跑通, 输出对齐理论值
go run -race ./experiments/ all            # 0 data race
```

**验收红线**：
1. vet/编译/运行/race 四项全过
2. 实验数据可对理论值（每模块 README 放锚点表）
3. 交叉引用路径真实存在（grep 校验 `notes/` 引用）
4. 每篇有「核心认知」开头、「面试高频」结尾、文末「本篇对应实验」行
5. commit 信息用 conventional 风格（docs(system-design): ... 等），不含 AI 信息
