# 分库分表

> **核心认知：分库分表是"最后的手段"，不是"第一选择"。它解决的是单机容量和写入瓶颈，代价是放弃数据库的大部分原生能力（跨表事务、跨表 JOIN、全局索引、自增 ID）。先穷尽索引优化、读写分离、冷热归档，再谈拆分。**

---

## 一、什么时候需要拆

单表经验阈值：**2000 万行左右性能开始明显下降**——不是硬限制，本质是 B+ 树变高（3 层 → 4 层）、单表数据文件过大（Buffer Pool 装不下热数据）、DDL/备份/恢复时间不可接受。

**拆之前的优化阶梯（按成本从低到高）：**

```
① 索引优化 + SQL 改写（解决 80% 的"慢"）
② 读写分离（解决读压力大）
③ 冷热分离 / 归档（解决数据总量大，但热数据不多）
④ 分库分表（解决单机写入瓶颈 / 单表数据量极限）
⑤ 换存储（NewSQL: TiDB 等）
```

只有 ①②③ 都解决不了（写入 QPS 单机扛不住、单表行数已经影响 DDL 和备份），才走 ④。

---

## 二、垂直拆分

**垂直分库**：按业务域拆到不同数据库实例——订单库、用户库、商品库。伴随微服务化进行，每个服务独享自己的库。

**垂直分表**：单表列太多时拆成多表：
- 冷热拆：高频访问的小字段一张表，大字段（TEXT/BLOB/长 JSON）另一张表，按主键关联
- 好处：热表行变小，一页能放更多行，Buffer Pool 命中率上升

垂直拆分不改变行数，只改变"宽度"，实现简单，风险低。

---

## 三、水平拆分与分片策略

同一张表按行拆到多个库/表：`order_0 ~ order_63`。

### 分片键（Sharding Key）选择——最重要的决策

**原则：用最高频查询条件做分片键**。订单场景 90% 的查询带 `user_id` → 按 `user_id` 分片，绝大多数查询路由到单分片。

选错的代价：不分片的查询要**广播全部分片再聚合**，性能比分库分表之前还差。

### 分片算法对比

| 算法 | 规则 | 优点 | 缺点 | 场景 |
|------|------|------|------|------|
| 哈希取模 | `shard = user_id % 64` | 数据均匀，实现简单 | **扩容要迁移几乎全部数据** | 分片数固定的场景 |
| 范围分片 | id/时间分段（0~1000万 → 分片1） | 扩容只加新分片，老数据不动 | 热点集中（最新分片写入最热） | 按时间天然递增的数据 |
| 一致性哈希 | 哈希环 + 虚拟节点 | 扩容只迁移相邻小部分数据 | 实现复杂 | 节点数会动态变化的场景 |
| 查表法 | 单独的路由表记录 key→shard | 随时可调，灵活 | 路由表本身是瓶颈和单点，需缓存 | 需要频繁调整路由 |

**翻倍扩容技巧（哈希取模的救赎）：** 4 库扩 8 库时，`id % 8 == old_shard` 或 `old_shard + 4`——每个旧分片的数据一半留在原地，一半迁到确定的下一个分片，且分片键哈希不变，只做**双向同步 + 逐个切换**，无需停机。

## 四、拆分后的四大问题

### 1. 全局唯一 ID

单库 `AUTO_INCREMENT` 不再可用（各分片会重复）。

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| UUID | 本地生成 | 无序 → B+ 树插入页分裂，索引碎片化；太长（36 字符）；**不适合做主键** |
| 雪花算法（Snowflake） | 64bit = 符号位1 + 时间戳41 + 机器ID10 + 序列12 | 趋势递增，本地生成无网络开销；**时钟回拨问题**需处理 |
| 号段模式 | DB 存 `max_id, step`，一次取一段缓存到应用 | 简单可靠；DB 是依赖；中间件（美团 Leaf） |
| Redis INCR | 原子自增 | 简单；引入 Redis 依赖和持久化风险 |

雪花算法是最常用的答案，面试要能画出 64 位结构。

### 2. 跨分片查询

- **分片键路由**：带分片键的查询 → 精确路由单分片，无性能损失
- **非分片键查询**：
  - 广播所有分片 + 内存聚合（分页、排序代价 ×N）
  - **冗余一份异构索引**：如按 `user_id` 分片的订单表，再按 `order_id` 建一张 `order_id → user_id` 的映射表（或异构到 ES）
  - **基因法**：把 user_id 的部分比特编入 order_id，按 order_id 也能算出分片

### 3. 跨分片 JOIN

- 同分片（关联表用同一分片键，"ER 分片"）：正常 JOIN
- 小表广播：字典表/配置表在每个分片放一份全量
- 其他：应用层组装（两次查询 + 内存 join）或异构到宽表 / ES

### 4. 分布式事务

- **避免**：设计上让一个事务只落在单分片（按分片键聚合写入）
- **最终一致**：本地消息表 / 事务消息（RocketMQ）+ 对账补偿——主流选择
- **强一致**：2PC/TCC（侵入大，性能差），或直接换支持分布式事务的存储

## 五、数据迁移方案（双写迁移）

存量单库大表平滑迁到分片，标准四步：

```
① 双写：老库 + 新分片同时写（以老库为准，新库写失败只记日志）
② 存量迁移：按主键分批把老数据搬到新分片（分批防长事务）
③ 增量补偿 + 校验：对账程序持续比对两边数据，追平差异
④ 切换：读切到新库（灰度）→ 观察稳定 → 写切到新库 → 停老库双写
   每一步都可回滚
```

关键点：**迁移读之前必须先校验一致**；切换要有灰度（按用户比例）和回滚开关。

## 六、中间件

| 类型 | 代表 | 特点 |
|------|------|------|
| 客户端模式 | ShardingSphere-JDBC | 无代理层，性能好，Java 生态成熟 |
| 代理模式 | ShardingSphere-Proxy、MyCat | 应用无感知，多一跳网络，代理要高可用 |
| Go 生态 | 应用层自研 / gen 分片路由居多 | 常直接在 DAO 层做路由 |

Go 项目常见做法：不引入中间件，在数据访问层按分片键计算目标库表，配合连接池管理多个实例。

---

## 七、面试一句话总结

- 单表 2000 万是经验阈值，本质是 B+ 树变高 + Buffer Pool 失效 + DDL 成本，**先索引/读写分离/归档，最后才分库分表**。
- 分片键选最高频查询条件；哈希取模数据均匀但扩容难，范围分片扩容易但有热点，翻倍扩容可解决取模扩容问题。
- 拆分后四大代价：全局 ID（雪花）、跨分片查询（异构索引/基因法）、跨分片 JOIN（ER 分片/小表广播）、分布式事务（最终一致）。
- 迁移用双写 + 存量分批 + 对账 + 灰度切换，每步可回滚。
- UUID 为什么不适合做主键：无序 → 页分裂 → 索引碎片化。
