# 主从复制与高可用

> **核心认知：主从复制的本质是"主库把 Binlog 发给从库重放"。所有高可用方案（半同步、GTID、MGR）都是在回答两个问题：数据丢不丢（RPO）、切换快不快（RTO）。**

---

## 一、复制基本流程

```
主库：事务提交 → 写 Binlog → dump 线程推送 Binlog
从库：IO 线程接收 → 写 Relay Log → SQL 线程（applier）重放 Relay Log
```

- 复制是**异步**的：主库提交不等从库，默认配置下主库崩溃可能丢最后一批事务
- 从库重放是串行的（单 SQL 线程），是主从延迟的主要来源 → 并行复制

---

## 二、三种复制模式对比

| 模式 | 机制 | 数据丢失风险 | 性能 | 说明 |
|------|------|-------------|------|------|
| 异步（默认） | 主库提交即返回，不等从库 | 崩溃可丢未传的事务 | 最高 | 日志类业务可接受 |
| 半同步（5.5+） | 至少 1 个从库**收到** Binlog 才返回 | 极小（从库收到但未重放） | 中 | 生产常用 |
| 全同步 / MGR | 多数派**落盘确认**（Paxos） | 不丢 | 低 | MGR（8.0），强一致 |

**半同步的两个变体（面试高频）：**

```
AFTER_COMMIT（5.5 老半同步）：主库先提交事务，再等从库 ACK
  → 幻读风险：主库已提交可见，此时崩溃切换，从库没收到 → 已读到的数据"消失"

AFTER_SYNC（5.7 增强半同步，rpl_semi_sync_master_wait_point 默认值）：
  主库先等从库 ACK，再提交
  → 无幻读风险，loss-less（无损），8.0 半同步即指它
```

## 三、GTID 复制（5.6+）

传统复制靠**位点**（binlog 文件名 + 偏移量）定位，切换主库要人工计算新位点，极易出错。

**GTID = `server_uuid:事务序号`**，每个事务全局唯一：

```
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='new_master',
  SOURCE_AUTO_POSITION=1;   -- 基于 GTID 自动定位，从库知道自己缺哪些事务
```

- 优点：自动定位、failover 时从库自动补齐差异事务、复制拓扑变更简单
- 从库提升为新主：其余从库 `SOURCE_AUTO_POSITION=1` 指向它即可
- 生产必开：`gtid_mode=ON, enforce_gtid_consistency=ON`

## 四、并行复制（解决 SQL 线程串行瓶颈）

| 版本 | 方式 | 并行度 |
|------|------|--------|
| 5.5 | 单线程重放 | 1 |
| 5.6 | 按库并行（schema 级） | 库的数量（没用） |
| 5.7 | LOGICAL_CLOCK：**同一组内提交的事务**可并行 | 主库组提交越并行，从库越并行 |
| 8.0 | WRITESET（5.7.22 引入，8.0 常用推荐）：基于**行冲突检测**，无冲突的事务都并行 | 最高 |

```
slave_parallel_type  = LOGICAL_CLOCK
slave_parallel_workers = 16
binlog_transaction_dependency_tracking = WRITESET   # 8.0 推荐
```

本质：**主库并发执行且互不冲突的事务，从库也能并发重放**。LOGICAL_CLOCK 依赖主库提交顺序；WRITESET 依赖修改行集合不重叠，并行度更高。

---

## 五、主从延迟

延迟成因与对策（详见 [05-日志体系.md](05-日志体系.md)）：大事务、串行重放、从库机器差。大事务是头号杀手——主库 1 秒改 100 万行的事务，从库重放同样要锁同一张表 1 秒以上且无法并行。

---

## 六、读写分离与读到旧数据

```
写 → 主库；读 → 从库（扩展读能力）
```

**问题：** 写后立刻读（写主库、读从库），从库还没重放 → 读到旧数据。典型：改完昵称刷新页面昵称没变。

**解法（按代价从低到高）：**

| 方案 | 做法 | 适用 |
|------|------|------|
| 写后短窗口读主 | 写入后 N ms 内该用户读主库 | 简单通用，最常用 |
| 强制读主 | 关键路径（支付、下单后确认页）直接读主 | 低频关键查询 |
| GTID 等待 | 写入拿到 GTID，读从库前 `WAIT_FOR_EXECUTED_GTID_SET` 等其重放完成 | 精确但增加延迟 |
| 半同步 + 并行复制 | 降低延迟本身 | 通用基础设施 |

## 七、高可用架构

| 方案 | 原理 | 特点 |
|------|------|------|
| 主从 + 手动切换 | 最原始，人工定位新位点 | 教学用 |
| MHA / Orchestrator | 探测主库故障，提升最新从库，其余从库跟随 | 传统方案，位点复制时代主流 |
| **MGR（5.7.17+）** | 多数派协议（Paxos 变种）同步事务，自动选主 | 强一致、自动切换；要求网络好、限制多 |
| 云 RDS 高可用 | 半同步 + 自动切换 + 代理层 | 上云即得 |

选型一句话：**能上云就上云；自建中小规模半同步 + Orchestrator 够用；强一致要求高（金融）考虑 MGR 或 NewSQL。**

**一主多从扩展读**：读 QPS 高时挂多个从库；从库再挂从库（**级联复制**）避免主库为每个从库起一个 dump 线程。

---

## 八、面试一句话总结

- 复制流程：主库 dump 线程推 Binlog → 从库 IO 线程写 Relay Log → SQL 线程重放。
- 三种模式：异步（默认，可能丢）、半同步（至少一个从库收到才返回）、MGR（多数派落盘，不丢）。
- 半同步 AFTER_COMMIT 有幻读风险，AFTER_SYNC（5.7+ 默认）先 ACK 后提交，更安全。
- GTID = server_uuid:序号，`SOURCE_AUTO_POSITION=1` 自动定位，failover 不再手工算位点。
- 并行复制演进：按库（5.6）→ LOGICAL_CLOCK 组提交并行（5.7）→ WRITESET 行冲突检测（5.7.22 引入，8.0 常用）。
- 读写分离读到旧数据：写后短窗口读主 / 强制读主 / GTID WAIT；根治靠降低从库延迟。
- 大事务是主从延迟头号杀手（从库无法并行重放单大事务）。
