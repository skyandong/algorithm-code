# 执行计划 (EXPLAIN)

> **核心认知：EXPLAIN 是优化器的"自白书"，告诉你它打算怎么跑这条 SQL。看懂它的顺序：先看 type（有没有用索引），再看 rows（扫了多少行），最后看 Extra（有没有额外代价）。**

---

## 核心字段

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 1 AND status = 1;
```

| 字段 | 含义 | 关注点 |
|------|------|--------|
| `type` | 访问方式（最重要） | 越靠前越好 |
| `key` | 实际使用的索引 | NULL 表示没用索引 |
| `key_len` | 索引使用的字节数 | 可推算联合索引用了几列 |
| `rows` | 预估扫描行数 | 越小越好 |
| `filtered` | 条件过滤后剩余比例 | rows × filtered% = 最终行数估算 |
| `Extra` | 额外信息 | 重点看 Using filesort / Using temporary |

---

## type 性能排序

```
const > eq_ref > ref > range > index > ALL
```

| type | 场景 | 例子 |
|------|------|------|
| `const` | 主键或唯一索引等值查询，最多一行 | `WHERE id = 1` |
| `eq_ref` | JOIN 中被驱动表用主键/唯一索引匹配 | `JOIN t2 ON t1.id = t2.id` |
| `ref` | 非唯一索引等值查询 | `WHERE user_id = 1` |
| `range` | 索引范围扫描 | `WHERE id BETWEEN 1 AND 100` |
| `index` | 全索引扫描（遍历整个二级索引） | 索引覆盖但无法精确定位 |
| `ALL` | 全表扫描 | 没走任何索引 |

`index` 比 `ALL` 好一点（索引通常比表小），但两者都不理想，需要优化。

---

## Extra 关键值

| Extra | 含义 | 处理 |
|-------|------|------|
| `Using index` | 覆盖索引，无需回表 | 理想，保持 |
| `Using where` | Server 层再过滤 | 检查是否可以用索引下推 |
| `Using filesort` | 需要额外排序操作 | 为 ORDER BY 字段建索引 |
| `Using temporary` | 需要临时表 | 常见于 GROUP BY、DISTINCT，考虑加索引 |
| `Using index condition` | 索引条件下推（ICP），减少回表 | 5.6+ 自动启用 |
| `Using join buffer` | 被驱动表没有可用索引 | 为 JOIN 条件列加索引 |

**最糟糕的组合：** `type=ALL` + `Extra=Using filesort` + `Extra=Using temporary`，三个同时出现说明这条 SQL 需要大改。

---

## 优化器为什么有时不用索引

`possible_keys` 有值但 `key=NULL`，说明优化器放弃了索引：

1. **选择性太低**：索引列基数小（如 status 只有 0/1/2），走索引 + 回表的成本 > 全表扫描
2. **查询量太大**：预计返回 30%+ 的行，全表扫描反而更快（连续 IO vs 随机 IO 回表）
3. **左模糊**：`LIKE '%xx'` 无法用 B+ 树定位起始键
4. **统计信息偏差**：`ANALYZE TABLE t` 可以刷新统计信息，让优化器重新评估

强制使用/忽略索引（慎用，只在明确知道优化器判断错误时用）：

```sql
SELECT * FROM orders FORCE INDEX(idx_user_status) WHERE user_id = 1;
SELECT * FROM orders IGNORE INDEX(idx_user_status) WHERE user_id = 1;
```

## EXPLAIN ANALYZE（8.0+）

普通 EXPLAIN 是优化器的**估算**，不真实执行。EXPLAIN ANALYZE 会真正执行 SQL 并返回实际耗时：

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 1;

-> Index lookup on orders using idx_user_status (user_id=1)
   (cost=3.21 rows=10) (actual time=0.045..0.052 rows=8 loops=1)
```

| 字段 | 含义 |
|------|------|
| `cost` | 优化器估算成本 |
| `rows`（估算） | 优化器预计扫描行数 |
| `actual time=X..Y` | 第一行返回耗时 Xms，全部行返回耗时 Yms |
| `rows`（actual） | 实际扫描行数 |
| `loops` | 该节点执行次数（JOIN 被驱动表会 >1） |

估算 rows 和实际 rows 差距大 → 统计信息过期，执行 `ANALYZE TABLE t` 刷新。

## 多表 JOIN 执行计划怎么读

```sql
EXPLAIN SELECT * FROM orders o JOIN users u ON o.user_id = u.id WHERE o.status = 1;
```

```
id | table | type  | key        | rows | Extra
1  | o     | ref   | idx_status | 50   |              ← 驱动表，先扫
1  | u     | const | PRIMARY    | 1    |              ← 被驱动表，每行匹配一次
```

- **id 相同**：从上到下执行，上面是驱动表
- **id 不同**：id 越大优先级越高，先执行（子查询场景）
- **驱动表选择**：优化器选过滤后行数最少的；`STRAIGHT_JOIN` 可强制指定顺序
- **被驱动表无索引** → `Extra=Using join buffer`，触发 Block Nested Loop，性能极差，必须加索引

## 生产定位慢 SQL 的完整流程

```
① 慢查询日志找到慢 SQL
   slow_query_log = ON
   long_query_time = 1        超过 1 秒记录
   mysqldumpslow -s t -t 10 /var/log/mysql/slow.log   按耗时排 Top10

② EXPLAIN 看执行计划
   重点：type / key / rows / Extra

③ EXPLAIN ANALYZE 确认真实耗时（8.0+）
   对比估算 rows 和实际 rows，差距大则 ANALYZE TABLE

④ 针对性优化
   type=ALL          → 加索引或检查索引失效原因
   Using filesort    → ORDER BY 列加索引，或调整联合索引列顺序
   Using temporary   → GROUP BY 列加索引
   rows 估算严重偏差 → ANALYZE TABLE 刷新统计信息
   回表行数多        → 扩展联合索引覆盖 SELECT 字段（覆盖索引）
```

## key_len 计算

用于判断联合索引 `(a, b, c)` 实际用了几列：

- `INT`：4 字节，可为 NULL 则 +1 = 5
- `BIGINT`：8 字节，可为 NULL 则 +1 = 9
- `VARCHAR(N)` utf8mb4：`N × 4 + 2`（变长长度标记），可为 NULL 则 +1

例：`VARCHAR(64) NOT NULL` utf8mb4 = `64 × 4 + 2 = 258`
