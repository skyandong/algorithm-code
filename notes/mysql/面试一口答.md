## 零、整体架构

### 0. 一条 SQL 的完整执行流程？
```
连接器（权限认证 + 连接管理）
  → 查询缓存（8.0 已删：多写场景命中率极低、维护成本高、缓存失效太激进）
  → 解析器（词法分析 + 语法分析，生成解析树）
  → 预处理器（校验表/列是否存在，展开 * ）
  → 优化器（逻辑优化：等价变换；物理优化：基于代价选执行计划、确定 JOIN 顺序和索引）
  → 执行器（调用存储引擎 API，逐行或批量获取数据）
  → InnoDB（Buffer Pool 命中直接返回；未命中读磁盘，写 Undo/Redo，加锁）
```

**追问：优化器选错执行计划怎么办？** `optimizer_trace` 查决策过程；`ANALYZE TABLE` 刷新统计信息；`FORCE INDEX(idx)` 强制指定（副作用：索引变更后可能更慢，慎用）。

## 一、索引

### 1. 为什么选 B+ 树？
非叶子节点只存键+指针，扇出大（16KB / 14B ≈ 1170），树矮（3~4 层覆盖 2200 万 ~ 256 亿行），把随机 IO 压到 3~4 次；叶子节点双向链表天然支持范围查询。

- **vs B 树**：B 树非叶子节点存数据，扇出小、树更高、IO 更多
- **vs 哈希**：哈希只支持等值，不支持范围查询和排序
- **扇出** = 页大小 ÷ 单个键大小，直接决定树高

### 2. 聚簇索引 vs 非聚簇索引？
- **聚簇索引**：叶子节点 = 完整数据行。InnoDB 选主键做聚簇；没主键选第一个 NOT NULL 唯一索引；再没有用隐藏 `_rowid`（6 字节）
- **二级索引**：叶子节点只存 **索引列值 + 主键**，查询要**回表**（N 条结果 = N 次随机 IO）
- **覆盖索引**：查询字段全在二级索引上，免回表，EXPLAIN Extra = `Using index`；优化手段：把 SELECT 字段追加到联合索引末尾

### 3. 最左前缀为什么必须从最左开始？
联合索引按 a→b→c 拼接排序，B+ 树二分定位必须逐层确定；跳过 b 找 c，c 在 a 的范围内无序，只能全扫。

**范围条件之后的列全部失效**（`>`/`<`/`BETWEEN`/`LIKE 'prefix%'`），但范围列本身可以用。

### 4. 索引失效场景（一口气报完）
| 场景 | 原因 |
|------|------|
| 对索引列函数运算 | 破坏有序性：`WHERE YEAR(created_at)=2024` |
| 隐式类型转换 | 数字 > 字符串优先级，**varchar 列传数字 → CAST 列，失效**；int 列传字符串 → CAST 常量，正常 |
| 左模糊 / 全模糊 | 无法确定起始键：`LIKE '%张'` |
| OR 两侧有非索引列 | OR 无法走单一索引 |
| JOIN 两表字段字符集不同 | 对索引列 CONVERT，等同函数运算 |
| `NOT IN` / `!=` | 优化器判断回表成本 > 全表扫描 |
| 索引选择性太低 | 低基数字段（如性别）走索引不如全扫 |

**特征**：`possible_keys` 有值但 `key=NULL` = 隐式转换最典型特征。

### 5. 优化器对回表的两个优化
- **ICP（索引条件下推，5.6+）**：能下推的条件在存储引擎层先过滤再回表，减少无效回表。Extra = `Using index condition`
- **MRR（多范围读取，5.6+）**：回表前把主键排序，随机 IO → 近似顺序 IO。Extra = `Using MRR`

### 6. 联合索引列顺序三规则
1. **等值列在前，范围列在后**（范围列之后的列全部失效，等值不受限）
2. **高区分度在前**（先过滤更多数据）
3. **SELECT 字段追加末尾**（消灭回表）

例：`WHERE user_id=? AND status=? AND created_at>?  SELECT amount` → `(user_id, status, created_at, amount)`

### 7. InnoDB 行格式与行溢出？
主流行格式：COMPACT（5.0+）和 DYNAMIC（5.7+ 默认）。差异：DYNAMIC 对 VARCHAR/TEXT/BLOB 大字段更激进地使用"溢出页"（off-page）——只在本行存 20 字节指针，实际数据放到独立溢出页；COMPACT 会保留 768 字节在本行。

影响：① 大字段 DYNAMIC 行更小 → 一页装更多行 → B+ 树更矮 → IO 更少；② 索引长度限制：DYNAMIC 下 VARCHAR 索引前缀最长 3072 字节（COMPACT 下 767 字节）。

行溢出触发：单行超过页大小约一半（~8KB）时触发；TEXT/BLOB 默认溢出，`SELECT *` 会回捞溢出页。

### 8. 索引统计信息与优化器选错索引？
原因：InnoDB 统计信息基于随机采样（`innodb_stats_persistent_sample_pages` 默认 20 页），不精确，尤其是新导入数据后误差大。

诊断：`EXPLAIN` 的 `rows` 列严重偏离实际 → `EXPLAIN ANALYZE`（8.0.18+）对比 `estimated rows vs actual rows`；`optimizer_trace` 查看优化器选择每个索引的代价计算。

修复：`ANALYZE TABLE t` 重新采样统计信息（会加 MDL 读锁）；调大 `innodb_stats_persistent_sample_pages`；极端情况用 `FORCE INDEX(idx)` 强制（但维护负担高，优先靠统计信息解决）。

## 二、事务与 MVCC

### 9. ACID 各由谁保证？
| 特性 | 实现 |
|------|------|
| 原子性 | Undo Log |
| 持久性 | Redo Log + Binlog 两阶段提交 |
| 隔离性 | MVCC + 锁 |
| 一致性 | 前三者共同保障 |

### 10. 四种隔离级别一句话
- **RU**：直接读最新数据
- **RC**：MVCC，每次 SELECT 生成新 ReadView → 能看到别人最新已提交修改（不可重复读）
- **RR（默认）**：MVCC，事务首次 SELECT 生成 ReadView 复用 → 可重复读
- **Serializable**：普通 SELECT 隐式加 S 锁（等同 `LOCK IN SHARE MODE`），写操作加 X 锁

**RR 下幻读**：快照读被 MVCC 屏蔽；当前读（FOR UPDATE）靠 Next-Key Lock 防。

**追问：RR 下 `SELECT ... FOR UPDATE` 的幻读怎么防？** 当前读靠 **Next-Key Lock**（行锁 + 间隙锁）防幻读——锁住查询范围内的间隙，阻止其他事务在此间隙插入新行。MVCC 只防快照读的幻读，当前读必须靠锁。

### 11. MVCC 可见性判断（背口诀）
行隐藏列：`DB_TRX_ID`（最后修改事务 ID）、`DB_ROLL_PTR`（指向 Undo 版本链）、`DB_ROW_ID`（无主键隐式主键）。

ReadView 四元组：`creator_trx_id` / `m_ids`（活跃事务集）/ `min_trx_id` / `max_trx_id`。

```
DB_TRX_ID == creator_trx_id          → 可见（自己改的）
DB_TRX_ID < min_trx_id               → 可见（快照前已提交的老事务）
DB_TRX_ID >= max_trx_id              → 不可见（快照后才开启的事务）
min_trx_id <= DB_TRX_ID < max_trx_id → 在 m_ids 里不可见，不在则可见
以上不可见时沿 DB_ROLL_PTR 找 Undo 链上一个版本，重复判断。
```

### 12. 快照读 vs 当前读
- **快照读**：普通 SELECT，不加锁，读 MVCC 版本链历史快照
- **当前读**：`FOR UPDATE` / `LOCK IN SHARE MODE` / INSERT / UPDATE / DELETE，加锁，读最新已提交

**同一事务混用两会看到不一致结果**（COUNT 快照读 5 行，FOR UPDATE 当前读 6 行）—— 经典陷阱。

## 三、锁

### 13. 加锁规则（RR，基本单位 Next-Key Lock，左开右闭）
| 场景 | 加锁结果 |
|------|---------|
| 主键等值，记录存在 | 退化行锁，仅锁该行 |
| 主键等值，记录不存在 | 退化间隙锁，锁两侧间隙 |
| 主键范围查询 | Next-Key Lock 覆盖范围 + 右侧 Gap Lock |
| 普通索引等值 | 命中记录的 Next-Key Lock（记录 + 左侧间隙）+ 右侧第一个不匹配记录的 Gap Lock + 回表后主键 Record Lock |
| **无索引 WHERE** | **全表每行 X Lock，退化成表锁（生产大坑）** |

锁兼容矩阵：S/S 兼容，X 与一切冲突；意向锁（IS/IX）加速表锁检测，意向锁之间互相兼容。

**意向锁（IS/IX）**：InnoDB 加行锁前先在表上加意向锁（IS=意向共享，IX=意向排他），用来解决"判断表上是否有行锁"的效率问题——否则检查表锁冲突要全表扫描行锁。意向锁之间互相兼容，IS/IX 与 S 锁冲突，IX 与 X 锁冲突。

**AUTO_INC 锁**：`innodb_autoinc_lock_mode` 三档：0=语句级表锁（最安全，并发最差）/ 1=轻量互斥（默认，混合插入用表锁，简单插入用轻量锁）/ 2=全轻量（并发最好，binlog 必须 ROW 格式才安全）。

### 14. 死锁
循环等待即死锁。InnoDB 死锁检测（默认开）回滚代价小的事务，报 `Error 1213: Deadlock found`。

**预防**：统一加锁顺序（按主键从小到大）、短事务、`FOR UPDATE NOWAIT`（锁不到立即报错）、`SKIP LOCKED`（跳过被锁行）。

**排查**：`SHOW ENGINE INNODB STATUS\G` 看最近死锁详情。

### 15. SKIP LOCKED 场景
任务队列并发抢占：多 worker 抢任务，跳过已锁行直接拿下一个可用任务，无等待无阻塞。

```sql
SELECT * FROM tasks WHERE status = 'pending'
ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;
```

### 16. 大事务的危害与治理？
**危害五条**：① Undo Log 膨胀（回滚段撑大，清理 purge 线程追不上，ibdata1 不收缩）；② MVCC 版本链过长（全表慢查询要遍历更多版本）；③ 持锁时间长（并发写吞吐下降）；④ 从库延迟（单事务无法并行重放）；⑤ MDL 持有期间阻塞 DDL。

**检测**：
```sql
SELECT * FROM information_schema.INNODB_TRX
WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 10\G
```

**治理**：拆分事务（按批分批提交）、设 `lock_wait_timeout` 防止锁等待堆积、监控 `information_schema.INNODB_TRX` 超阈值告警。

## 四、日志

### 17. 三大日志一句话
| 日志 | 层 | 作用 | 写入时机 |
|------|----|------|---------|
| Undo Log | InnoDB | 如何撤销（回滚 + MVCC 版本链） | 修改前 |
| Redo Log | InnoDB | 做了什么（崩溃恢复，保证持久性） | 事务执行中（WAL） |
| Binlog | Server | 行变更 / SQL（主从复制 + 时间点恢复） | 事务提交时 |

### 18. WAL 为什么快
直接写数据页 = 随机 IO（找页 + 写回 ≈ 20ms）；WAL = 顺序追加 Redo Log（≈ 0.1ms）+ 改内存 Buffer Pool，脏页后台异步刷盘。**SSD 上仍需要**（写放大：最小擦除单位 128KB+）。

### 19. Redo 环形 + checkpoint
- **checkpoint**：此位置之前脏页已全部刷盘，之前空间可复用
- **write pos 追上 checkpoint** = 日志写满，强制刷脏页推进 checkpoint，业务卡顿
- `innodb_flush_log_at_trx_commit`：**0**=每秒刷（崩溃丢 1 秒）/ **1**=每次 fsync（默认，不丢）/ **2**=写 OS 缓存每秒刷（OS 崩溃丢）

### 20. 两阶段提交（必背）
```
写 Redo Log（prepare） → 写 Binlog → Redo Log 标记 commit
```
**崩溃恢复对账规则**：
- Redo 有 prepare + Binlog 存在 → 补 commit，提交
- Redo 有 prepare + Binlog 不存在 → 回滚

保证主从在任何时间点崩溃后必然一致。Binlog 生产推荐 **ROW** 格式（记录前后值，结果精确）。

**Binlog 组提交（Group Commit）**：5.6+ 引入，把多个事务的 Redo fsync 和 Binlog fsync 各合并一次，大幅提升高并发写入吞吐。关键参数：`binlog_group_commit_sync_delay`（等待微秒，积攒更多事务）+ `binlog_group_commit_sync_no_delay_count`（超过 N 个事务立即提交）。

**双1配置**：`innodb_flush_log_at_trx_commit=1`（每次事务 Redo fsync）+ `sync_binlog=1`（每次事务 Binlog fsync），最安全但吞吐最低；高性能场景改为 `(2, 100)` 或 `(0, 0)` 但需接受宕机丢数据风险。

### 21. 主从延迟原因
串行重放（5.6 前，升级 5.7+ 并行复制 `LOGICAL_CLOCK`）、大事务（拆小）、从库性能差、网络。`Seconds_Behind_Master` 看 SQL 线程落后秒数。

## 五、EXPLAIN 与慢 SQL

### 22. type 性能排序
```
system > const > eq_ref > ref > range > index > ALL
```
- system：表仅一行（const 特例）
- const：主键/唯一索引等值（最多一行）
- eq_ref：JOIN 被驱动表用主键/唯一索引匹配
- ref：非唯一索引等值
- range：索引范围扫描
- index：全索引扫描（比 ALL 好一点，仍不理想）
- ALL：全表扫描

### 23. Extra 关键值
| Extra | 含义 | 处理 |
|-------|------|------|
| `Using index` | 覆盖索引，免回表 | 理想，保持 |
| `Using filesort` | 额外排序 | ORDER BY 列加索引 |
| `Using temporary` | 临时表 | GROUP BY 列加索引 |
| `Using join buffer` | 被驱动表无索引 | JOIN 条件列加索引 |
| `Using index condition` | ICP，减少回表 | 5.6+ 自动 |

**最糟组合**：`type=ALL` + `Using filesort` + `Using temporary` 同时出现 → SQL 需要大改。

### 24. 慢 SQL 定位流程
```
① 慢查询日志：slow_query_log=ON, long_query_time=1, mysqldumpslow -s t -t 10
② EXPLAIN：看 type / key / rows / Extra
③ EXPLAIN ANALYZE（8.0.18+）：对比估算 rows vs 实际 rows，差距大 → ANALYZE TABLE
④ 对症优化：ALL→加索引；filesort→ORDER BY 加索引；temporary→GROUP BY 加索引；回表多→覆盖索引
```

**key_len 速算**：INT=4（可空+1=5）、BIGINT=8（可空+1=9）、VARCHAR(N) utf8mb4 = `N×4+2`（可空+1）。推算联合索引实际用了几列。

**批量分析**：`pt-query-digest /var/log/mysql/slow.log` 按响应时间/调用频率汇总，找出系统级热点 SQL（比 mysqldumpslow 更详细）。`performance_schema.events_statements_summary_by_digest`：运行中无需开慢查询日志，按 SQL 指纹实时聚合耗时/调用次数/扫描行数，适合在线诊断。

## 六、Online DDL 与 MDL

### 25. MDL 雪崩（必背）
```
txA：普通 SELECT，持 MDL 读锁，事务未提交（长事务）
  ↓
ALTER TABLE：申请 MDL 写锁，被阻塞，进入等待队列
  ↓
后续所有 SELECT/INSERT/UPDATE 申请 MDL 读锁：被写锁请求挡住，全部阻塞
  → 连接堆积 → 连接耗尽 → 数据库雪崩
```

**执行 DDL 前必须**：查 `information_schema.INNODB_TRX` 确认无长事务 + 查 `performance_schema.metadata_locks` 确认无 MDL 等待。

**大表 DDL 最佳实践**：8.0 加列用 Instant DDL（只改元数据）→ 其次 `ALGORITHM=INPLACE, LOCK=NONE` 低峰执行 → 超大表（>5000 万行）用 gh-ost。

**排查与处置**：① `SELECT * FROM performance_schema.metadata_locks WHERE OBJECT_SCHEMA='db' AND OBJECT_NAME='table'\G` 查看 MDL 持有情况；② `SHOW PROCESSLIST` 找到阻塞链头部的 thread_id；③ `KILL <thread_id>` 释放长事务；④ 提前用 `information_schema.INNODB_TRX` 确认无长事务再执行 DDL。

### 26. gh-ost vs pt-osc
| | pt-osc | gh-ost |
|-|--------|--------|
| 增量同步 | **触发器**（侵入原表，每次 DML 有额外开销） | 模拟从库读 **Binlog**（零侵入） |
| 限速 | 较粗 | `--max-load` 监控主库负载自动暂停 |
| 可演练 | 无 | `--dry-run` |
| 生产推荐 | 次选 | **首选** |

两者核心思路相同：建影子表 → 全量复制 + 增量同步 → 原子 RENAME 切换 → 可暂停/回滚。

## 七、JOIN

### 27. JOIN 本质与最优形态
JOIN = 嵌套循环，成本随形态变化：
```
Simple NLJ        N + N×M        （朴素版，不用）
Index NLJ         N + N×logM     （被驱动表 JOIN 列有索引 → 最理想）
Block NLJ         N + N/batch×M  （无索引兜底，join_buffer）
Hash Join (8.0.18+) O(N+M)       （无索引救星，替代 BNLJ）
```

### 28. 驱动表
- **"小表" = WHERE 过滤后行数小**，不是表本身小
- **被驱动表 JOIN 列有索引，比驱动表大小更关键**（最常被忽略）
- 优化器自动选驱动表，书写顺序 ≠ 执行顺序；确认选错时用 `STRAIGHT_JOIN` 强制（慎用）

### 29. 一对多 JOIN + `SELECT *` + GROUP BY 必挂
Error 1055（only_full_group_by）：功能依赖只在 **GROUP BY 列能唯一决定 SELECT 列**（如主键）时成立；一对多决定不了。

- 要明细 → 别 GROUP BY
- 要每组一条 → 窗口函数 `ROW_NUMBER() OVER(PARTITION BY ...) ... WHERE rn=1`

## 八、WHERE vs HAVING

### 30. 聚合避坑六条
1. 计数用 `COUNT(*)`，`COUNT(字段)` 忽略 NULL；**LEFT JOIN 统计右表行数用 `COUNT(右表主键)`**——无匹配的扩展行全 NULL，`COUNT(*)` 会把它数成 1
2. 保留全部维度用 `LEFT JOIN`，INNER JOIN 会丢无数据维度
3. WHERE 过滤原始行，HAVING 过滤聚合结果
4. GROUP BY 严格模式：SELECT 非聚合字段全进 GROUP BY；**GROUP BY 里有主键 → 功能依赖可豁免**（但显式写出更稳）
5. NULL 数值计算用 `IFNULL(字段, 0)` 兜底（防 NULL 参与算术/除零；注意 AVG 本身忽略 NULL，把 NULL 当 0 计入才会拉低平均——按业务语义选择）
6. 窗口函数排名必加 `PARTITION BY`，否则变全局排名

## 九、MySQL 8 速记

1. **窗口函数**：`ROW_NUMBER` 无并列 / `RANK` 并列跳号 / `DENSE_RANK` 并列不跳号；`LAG`/`LEAD` 做环比同比；CTE（`WITH`）替代嵌套子查询，`WITH RECURSIVE` 处理树形
2. **自增持久化**：8.0 前自增值只存内存，重启可能回退复用已删 id；8.0 写 Redo Log 不回退
3. **utf8mb4**：MySQL 的 `utf8` 是 utf8mb3（3 字节），存不了 Emoji；8.0 默认 utf8mb4。索引长度限制：5.6 及以前 767 字节（Compact 行格式），5.7+/8.0 默认 DYNAMIC 行格式下为 3072 字节
4. **Instant DDL**：加列只改元数据瞬间完成（限制：无全文索引、非压缩表、8.0.29+ 支持任意位置）
5. **原子 DDL**：8.0 起 DDL 写 Redo Log，崩溃不留半成品
6. **EXPLAIN ANALYZE**：真实执行，返回 actual time / rows / loops

## 十、分库分表

### 31. 什么时候拆、怎么拆
单表 ~2000 万行开始性能下降（本质：B+ 树变高、BP 失效、DDL 成本大）。**先穷尽索引优化 → 读写分离 → 冷热归档，最后才分库分表**。

- 垂直：按业务分库（伴随微服务）、按冷热/大字段分表（热表行变小，一页多行）
- 水平：哈希取模（均匀但扩容难）、范围（扩容易但有热点）、一致性哈希；**翻倍扩容**解决取模扩容

### 32. 拆分后的四大代价
- **全局 ID**：雪花算法（符号1+时间戳41+机器10+序列12，趋势递增；时钟回拨需处理）；UUID 无序 → 页分裂，不适合主键
- **跨分片查询**：异构索引表 / 基因法；广播聚合性能差
- **跨分片 JOIN**：ER 分片（关联表同分片键）、小表广播、应用层组装
- **分布式事务**：尽量按分片键聚合单分片；跨分片用最终一致（本地消息表/事务消息）

### 33. 平滑迁移四步
双写 → 存量分批迁移 → 增量对账校验 → 灰度切读、切写，**每步可回滚**。

### 34. 分布式事务怎么做？
MySQL 原生 XA（两阶段提交）：性能差（各分片串行锁定）、协调者单点故障会导致悬挂事务，生产极少用。

工程实践选型：
- **TCC（Try-Confirm-Cancel）**：业务侵入最重，但强一致、性能好；适合对一致性要求极高的核心链路（支付）
- **Saga**：每步正向操作 + 补偿操作，无全局锁，性能最好；适合长流程（订单→库存→物流）最终一致
- **本地消息表 / 事务消息（RocketMQ）**：最简单、侵入最小；适合跨服务通知场景，用消息队列的可靠投递保证最终一致

## 十一、Buffer Pool 与内存

### 35. 改进版 LRU
分 new/old 两区（old 默认 37%），新页**从 old 区头部插入**；在 old 区**活过 1 秒（innodb_old_blocks_time）再被访问**才晋升 new 区——全表扫描的页一扫而过，进不了热区，**防缓存污染**。

**多实例**：`innodb_buffer_pool_instances`（默认 8，BP≥1GB 时生效），多实例并行减少锁竞争，但 innodb_lru_scan_depth 的工作量也乘以实例数。

**重启预热**：`innodb_buffer_pool_dump_at_shutdown=ON`（关闭时把热页列表 dump 到文件）+ `innodb_buffer_pool_load_at_startup=ON`（启动时自动加载），避免重启后冷启动性能抖动。

### 36. 脏页刷新四时机
Redo 快写满（**业务写卡顿**）、BP 不足淘汰脏页、后台自适应刷新、正常关闭。写卡顿两大内存侧根因：Redo 容量小 / 脏页比例过高。

### 37. Change Buffer 与 Doublewrite
- **Change Buffer**：二级索引页不在 BP 时缓存写、延迟 merge，**仅非唯一二级索引**（唯一索引必须读页校验唯一性）——"唯一 vs 普通索引怎么选"的答案
- **Doublewrite**：刷脏前先顺序写副本再写数据文件，防**页断裂**——Redo 是页内物理日志，前提是页完整，修不了半页

## 十二、主从复制与高可用

### 38. 复制流程与三种模式
主库 dump 线程推 Binlog → 从库 IO 线程写 Relay Log → SQL 线程重放。

| 模式 | 丢数据风险 |
|------|-----------|
| 异步（默认） | 崩溃可丢未传事务 |
| 半同步 | 至少 1 从库收到才返回；**AFTER_SYNC（5.7+ 默认）先 ACK 后提交，无幻读；AFTER_COMMIT 有幻读风险** |
| MGR（5.7.17+） | 多数派落盘（Paxos），不丢 |

**Binlog 格式对比**：STATEMENT 记录 SQL 语句（体积小，但含 `NOW()`/`UUID()`/触发器时不幂等，存在复制不一致风险）；ROW 记录行的前后镜像（体积大，但结果精确，**5.7.7+ 默认**）；MIXED 自动选择（含非确定函数时切 ROW）。`binlog_row_image`：FULL（完整行，默认）/ MINIMAL（只存变更列）/ NOBLOB（排除未变更的大字段）。ROW 格式配合 `binlog2sql`/`MyFlash` 可做误操作闪回。

### 39. GTID 与并行复制
- **GTID = server_uuid:序号**，`SOURCE_AUTO_POSITION=1` 自动定位，failover 不再手工算位点
- 并行复制三代：按库（5.6）→ LOGICAL_CLOCK 组提交并行（5.7）→ WRITESET 行冲突检测（5.7.22 引入，8.0 常用）
- **大事务是主从延迟头号杀手**（单事务无法并行重放）

### 40. 读写分离读到旧数据
写后短窗口读主（最常用）/ 关键路径强制读主 / GTID `WAIT_FOR_EXECUTED_GTID_SET`；根治靠降低从库延迟。

### 41. 高可用方案对比？
| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| MHA | 主故障时从库中选最优提升，补齐 relay log | 成熟稳定，社区广泛 | 需要额外 Manager 节点，切换期间有秒级不可用 |
| Orchestrator | 基于 HTTP API 的拓扑管理 + 自动故障转移 | 可视化拓扑，支持复杂部署 | 复杂度高 |
| MGR/InnoDB Cluster | Paxos 多数派落盘，强一致 | 原生官方支持，不丢数据 | 写入延迟比异步复制高（需等多数派确认），网络要求高 |

半同步追问：`AFTER_COMMIT`（主库提交后再等从库 ACK，有幻读——ACK 前宕机从库无此事务）vs `AFTER_SYNC`（Binlog 落盘 + 从库 ACK 后才提交，真正不丢，**5.7+ 默认**）。

### 42. 连接数与连接池调优？
`max_connections`：默认 151，生产通常调到 500-2000；但不是越大越好——连接本身消耗内存（每个连接约 1-8MB），过多连接反而因上下文切换降低吞吐。经验值：连接数 ≈ CPU 核数 × 2（OLTP）。

`thread_cache_size`：缓存空闲线程避免频繁创建销毁，建议等于 `max_connections` 的 5-10%。

`wait_timeout` / `interactive_timeout`：默认 28800 秒（8 小时），生产建议调到 300-600 秒，避免连接泄漏占满 `max_connections`。

连接泄漏排查：`SHOW STATUS LIKE 'Threads_connected'` 持续增长 + `SHOW PROCESSLIST` 找 Sleep 时间长的连接 + `pt-kill` 批量清理。

## 十三、SQL 优化实战

### 43. 深分页
`LIMIT 1000000,10` 慢在扫偏移量那么多行再丢掉。
- **延迟关联**：子查询走覆盖索引只拿 id，再回表 10 行——治标（少回表）
- **游标分页** `WHERE id > last_id LIMIT 10`：索引直接定位，O(10)——治本，但只能连续翻页

### 44. COUNT 与大表 DML
- InnoDB 不存行数（**MVCC 下每个事务可见行数不同**），COUNT(*) 选最小索引扫；近似值用 EXPLAIN rows，精确值用计数表/Redis
- 大表 DELETE 三害：长事务 Undo 膨胀、主从延迟、锁持久的久 → **主键游标分批删**；整表清空用 TRUNCATE

### 45. 批量写入与 IN/EXISTS
- multi-values 一条 SQL 一个事务一次 fsync（GORM 用 `CreateInBatches`）；超大导入用 `LOAD DATA INFILE`
- 5.6+ IN 子查询被改写为 **semijoin**，IN/EXISTS 执行计划趋同；`NOT IN` 遇 NULL 返回空集，用 `NOT EXISTS`

## 速查：面试高频三连问

**Q1. 一条 UPDATE 提交，日志怎么走？**
> 写 Undo（旧值）→ 改 Buffer Pool（内存，脏页）→ 写 Redo prepare（WAL 顺序写）→ 提交时写 Binlog → Redo 标 commit → 返回。

**Q2. 事务隔离级别 + 幻读怎么解？**
> 快照读靠 MVCC（RR 复用 ReadView），当前读靠 Next-Key Lock（行锁 + 间隙锁，锁住间隙阻止插入）。

**Q3. 慢 SQL 怎么排查？**
> 慢查询日志 → EXPLAIN 看 type/rows/Extra → EXPLAIN ANALYZE 对比实际 → 加索引 / 覆盖索引 / 刷新统计信息。
