# 索引体系

> **核心认知：MySQL 的架构本质是在用软件设计绕开硬件的物理限制。**
>
> 磁盘随机 IO 比内存慢 10 万倍，这是一切设计的出发点：
> - **B+ 树**：最大化扇出，压低树高，把随机 IO 次数压到 3~4 次
> - **聚簇索引**：数据按主键物理有序，range scan 变顺序 IO
> - **Buffer Pool**：热数据留内存，根本不碰磁盘
> - **WAL / Redo Log**：随机写数据页 → 顺序追加日志，快 100 倍
> - **MRR**：回表前排序主键，随机 IO → 近似顺序 IO
> - **自增主键**：顺序插入，杜绝页分裂，杜绝随机写
>
> 读懂这条线，索引的所有设计决策都能推导出来，不需要死记。

## 索引类型速览

| 类型 | 特点 | 场景 |
|------|------|------|
| 主键索引 | 唯一且非空，自动聚簇 | 表主键 |
| 唯一索引 | 值唯一，允许 NULL | 手机号、邮箱等业务唯一约束 |
| 普通索引 | 无唯一约束 | 频繁查询的字段 |
| 组合索引 | 多列，遵循最左前缀 | 多条件组合查询 |
| 前缀索引 | 只索引字符串前 N 字符 | 长字符串（URL、TEXT）节省空间，但丢失了排序和覆盖索引能力 |

## B+ 树结构

```
非叶子节点（只存键 + 指针，不存数据）
        [10 | 30 | 50]
       /     |     |     \
[5|10]   [20|30]  [40|50]  [60]   ← 叶子节点（双向链表）
  ↓          ↓        ↓      ↓
数据页      数据页    数据页   数据页
```

**为什么选 B+ 树而非其他结构：**

- vs B 树：B 树非叶子节点存数据，扇出更小，树更高，IO 次数更多；B+ 树非叶子节点纯指针，一个 16KB 数据页能放更多键，树更矮（3-4 层覆盖亿级数据）
- vs 哈希：哈希只支持等值查询，不支持范围查询和排序；B+ 树叶子链表天然支持 range scan
- vs 跳表/LSM：B+ 树适合读多写少的磁盘场景；LSM 写放大严重，适合写密集型

**扇出（Fan-out）：**

扇出 = 一个节点能指向多少子节点 = **页大小 ÷（单个键大小 + 子指针大小）**，直接决定树高。

```
B  树非叶子节点存 键+数据+指针：16384 / (8 + 1024 + 6) ≈ 15
B+ 树非叶子节点只存 键+指针：  16384 / (8 + 6)        ≈ 1170
```

扇出相差 78 倍 → 树高少 2 层 → IO 次数少 2 次，这是 B+ 树比 B 树快的核心原因。

**层数估算（为什么 3-4 层够用）：**

非叶子节点：一个键 8B（bigint）+ 一个指针 6B = 14B，扇出 = 16384 / 14 ≈ **1170**

叶子节点：假设一条记录 1KB，每页能放 16384 / 1024 ≈ **16 条**

| 树高 | 容量 |
|------|------|
| 2 层 | 1170 × 16 ≈ 1.8 万 |
| 3 层 | 1170² × 16 ≈ **2200 万** |
| 4 层 | 1170³ × 16 ≈ **256 亿** |

**为什么页是 16KB：**
- 太小 → 扇出小，树更高，IO 更多
- 太大 → 单次 IO 读入大量用不到的数据，Buffer Pool 浪费
- 16KB 是工程经验值，可通过 `innodb_page_size` 调整（实例级参数，只能在初始化数据目录时设置，实例生命周期内不可改）

**Buffer Pool 与扇出的关系：**
```
Buffer Pool 默认 128MB ≈ 可缓存 8000 个页

3 层 B+ 树的第 1、2 层共 1171 个页 ≈ 18MB，可以完全常驻内存
查询时：前两层走内存，只有读叶子页时才触发 1 次真实磁盘 IO
```

磁盘 IO 以页（块）为单位而非字节，是因为机械盘寻道约 10ms，既然寻道了就多读，减少寻道次数比减少读取字节数更重要。

## 磁盘 IO 基础

**机械盘一次随机读的三步：**
```
① 寻道（Seek）       磁臂移到目标磁道   ≈ 5~10ms
② 旋转等待           盘片转到目标扇区   ≈ 2~4ms（7200RPM）
③ 数据传输           读出数据          ≈ 0.1ms
─────────────────────────────────────────────────
合计随机读一次 ≈ 10ms，比内存（100ns）慢 10 万倍
```

**顺序 IO vs 随机 IO：**

| | 机械盘 | SSD |
|--|--------|-----|
| 顺序读吞吐 | 100~200 MB/s | 1~7 GB/s |
| 随机读 IOPS | 100~200 | 10万~100万 |
| 随机读延迟 | 10ms | 0.1ms |

**MySQL 所有设计都在逃避随机 IO：**

| 设计 | 目的 |
|------|------|
| B+ 树叶子双向链表 | range scan 变顺序 IO |
| 自增主键 | 追加插入，不触发页分裂，避免随机写 |
| Buffer Pool | 热数据留内存，根本不碰磁盘 |
| Redo Log 顺序写（WAL） | 事务提交只追加日志，脏页异步批量刷盘 |
| MRR 主键排序后回表 | 随机回表 → 近似顺序 IO |

**WAL（Write-Ahead Logging）为什么快：**
```
直接写数据页：找到目标页（随机 IO）→ 改数据 → 写回磁盘（随机 IO） ≈ 20ms
WAL：         追加写 Redo Log（顺序 IO）→ 改 Buffer Pool（内存）    ≈ 0.1ms
              脏页后台异步批量刷盘
```
崩溃时重放 Redo Log 恢复数据，持久性由此而来。

**SSD 上还需要 WAL 吗：** 需要。SSD 写放大问题（最小擦除单位是块 128KB+，写 1 字节要读-改-擦-写整个块），顺序写仍然显著优于随机写。

**页分裂（Page Split）：**

一个 16KB 数据页满了，新数据要插到中间时：申请新页 → 迁移 50% 数据 → 更新指针。
结果是空间利用率从 100% 降到 50%，且产生随机 IO。

**自增主键为什么好：** 顺序插入永远追加到末尾，不触发页分裂。UUID 随机插入位置，频繁分裂，索引碎片化严重。

## 聚簇索引 vs 非聚簇索引

**聚簇索引（Clustered Index）：**
- 叶子节点 = 完整数据行，数据和索引存在一起
- InnoDB 选主键作为聚簇索引；没主键则选第一个 NOT NULL 唯一索引；再没有则自动生成隐藏 `_rowid`（6 字节）

**非聚簇索引（Secondary Index）：**
- 叶子节点存的是 **主键值**，不是完整数据
- 查询时要"回表"：走二级索引找主键 → 再走聚簇索引拿数据，**两次 B+ 树查询**

**二级索引叶子节点存什么：**
- 只存**索引列的值 + 主键值**，不存完整行
- 例如 `idx_user_status(user_id, status)` 的叶子：`[user_id=1, status=0 | 主键=7]`

**回表的完整路径：**
```
SELECT id, amount FROM orders WHERE user_id = 1

Step 1: 走 idx_user_status，找到 user_id=1 的所有叶子 → 得到主键列表 [3, 7, 12, ...]
Step 2: 每个主键再走一次聚簇索引 → 拿完整行 → 取 amount

N 条结果 = N 次回表，每次回表是一次随机 IO
```

**覆盖索引（Covering Index）：**
- 查询所需字段全在某个二级索引上，无需回表
- EXPLAIN 的 Extra 列会显示 `Using index`
- 高频查询场景下，专门为查询列建联合索引来避免回表，是最常用的性能优化手段
- 设计技巧：把 `SELECT` 的字段追加到联合索引末尾，例如 `(user_id, status, amount)` 就能覆盖 `SELECT amount WHERE user_id=?`

## 最左前缀原则

联合索引 `(a, b, c)` 等价于建了三个索引：`(a)`、`(a, b)`、`(a, b, c)`。

**为什么必须从最左列开始：**

联合索引 `(a, b, c)` 在 B+ 树里按 a→b→c 拼接排序：
```
[a=1, b=1, c=1] → [a=1, b=1, c=2] → [a=1, b=2, c=1] → [a=2, b=1, c=1]
```
B+ 树靠二分定位，必须先确定 a 的范围，才能在 a 确定的子树里定位 b，以此类推。
跳过 b 直接找 c：c 在 a=1 的范围内随 b 变化而无序，无法二分，只能全扫。

**能用索引的查询：**
```sql
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3
WHERE a = 1 AND b > 2           -- a 用索引，b 范围后 c 失效
```

**不能用索引（跳过前缀）：**
```sql
WHERE b = 2                     -- 跳过了 a，b 在全局无序
WHERE b = 2 AND c = 3           -- 同上
WHERE a = 1 AND c = 3           -- a 确定后 b 未知，c 在 a=1 范围内无序
```

**范围查询截断原因：**
`WHERE a=1 AND b>2 AND c=3`：b 是范围，b>2 区间内 c 值随 b 变化重新排列，c 在该区间整体无序，无法继续用索引定位。
范围条件（`>`/`<`/`BETWEEN`/`LIKE 'prefix%'`）之后的列无法再用索引，但范围列本身可以用。

## 索引失效场景

| 场景 | 原因 | 例子 |
|------|------|------|
| 对索引列做函数运算 | 破坏索引有序性 | `WHERE YEAR(created_at) = 2024` |
| 对索引列做隐式类型转换 | MySQL 按优先级（数字>字符串）把**索引列**整列 CAST，等同函数运算 | `WHERE phone = 13800138000`（phone 是 varchar → 列被 CAST） |
| 左模糊/全模糊 | 无法确定起始键 | `WHERE name LIKE '%张'` |
| OR 两侧有非索引列 | OR 无法走单一索引 | `WHERE id = 1 OR name = '张三'`（name 无索引） |
| JOIN 两表字段字符集不同 | MySQL 对索引列做 CONVERT，等同函数运算，被驱动表索引失效 | `ON a.phone(utf8mb4) = b.phone(utf8)` |
| `NOT IN` / `!=` | 优化器按成本权衡：可拆为两个 range 区间或走覆盖索引/ICP 时仍可能用索引，否则走全表 | `WHERE status != 1` |
| 索引选择性太低 | 优化器估算回表成本 > 全表扫描，主动走全表 | 性别字段（50% 选择率）加索引无意义 |

**隐式转换方向决定是否失效：**
- 索引列是 `varchar`，传数字 → MySQL CAST **列**，索引失效
- 索引列是 `int`，传字符串 `'1'` → MySQL CAST **常量**，索引正常

陷阱：`EXPLAIN` 的 `possible_keys` 有值但 `key=NULL`，是隐式转换最典型的特征。

## 优化器对回表的两个优化

**ICP：索引条件下推（Index Condition Pushdown，5.6+）**

没有 ICP 时：二级索引找到主键 → 无条件回表 → 在 Server 层过滤不符合的行。
有 ICP 时：把能在索引上判断的条件下推到存储引擎层，先过滤再回表，减少无效回表次数。

```sql
-- idx(user_id, status)
SELECT * FROM orders WHERE user_id = 1 AND status > 0 AND amount > 100

-- amount 不在索引里，必须回表才能判断
-- 无 ICP：找到所有 user_id=1 的行全部回表，Server 层再过滤 amount
-- 有 ICP：status>0 在索引层先过滤，只有通过的行才回表，再判断 amount
-- EXPLAIN Extra = Using index condition
```

**MRR：多范围读取（Multi-Range Read，5.6+）**

普通回表是**随机 IO**：按索引顺序拿到主键 [7, 3, 15, 2, ...]，乱序回表，每次都可能跨页。
MRR：把回表的主键**先排序**，再按主键顺序批量读取，随机 IO → 顺序 IO。

```sql
-- 没有 MRR：主键 [7,3,15,2] → 随机读 4 个数据页
-- 有  MRR：排序后 [2,3,7,15] → 顺序读，可能只需 1-2 次 IO
-- EXPLAIN Extra = Using MRR
```

代价：需要额外内存排序主键（`read_rnd_buffer_size` 控制），小结果集反而有额外开销，优化器会自行决定是否启用。

## 索引设计原则

1. **高选择性优先**：`COUNT(DISTINCT col) / COUNT(*)` 越接近 1 越好；性别、状态这类低基数字段建索引意义不大
2. **覆盖高频查询**：为查询中的 `SELECT`、`WHERE`、`ORDER BY`、`GROUP BY` 列联合建索引
3. **不要过度建索引**：每个索引都要维护，INSERT/UPDATE/DELETE 都会更新所有索引，影响写性能
4. **前缀索引权衡**：长字符串用前缀索引节省空间，但不能做覆盖索引，也无法用于 ORDER BY
5. **隐藏索引（8.0+）**：索引设为 `INVISIBLE` 后优化器不再使用，但仍然维护。用于安全测试"删掉这个索引会怎样"，验证没问题再真正删除，避免删错无法回头。

   ```sql
   ALTER TABLE t ALTER INDEX idx_status INVISIBLE;  -- 隐藏，观察业务影响
   ALTER TABLE t ALTER INDEX idx_status VISIBLE;    -- 确认没问题，恢复；或直接 DROP
   ```

6. **降序索引（8.0+）**：联合索引可以对每列指定升降序，避免 ORDER BY 触发 filesort。

   ```sql
   -- 查询：ORDER BY created_at DESC, id ASC
   -- 对应索引：
   CREATE INDEX idx ON orders(created_at DESC, id ASC);
   -- EXPLAIN Extra 不再出现 Using filesort
   ```

7. **联合索引排列顺序**：三条规则按优先级叠加：

   | 优先级 | 规则 | 原因 |
   |--------|------|------|
   | ① | 等值列在前，范围列在后 | 范围列之后的列全部失效，等值不受此限制 |
   | ② | 高区分度列在前 | 先过滤掉更多数据，减少后续扫描量 |
   | ③ | SELECT 字段追加到末尾 | 消灭回表，且不影响前面列的查询能力 |

   ```sql
   -- WHERE user_id=? AND status=? AND created_at>?  SELECT amount
   -- 最优：(user_id, status, created_at, amount)
   --   user_id   等值+高区分度 → 第一
   --   status    等值+低区分度 → 等值就算区分度低也要在范围列前
   --   created_at 范围        → 等值列之后
   --   amount    追加覆盖     → 最后
   ```
