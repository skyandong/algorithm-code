# 锁机制

> **核心认知：锁是 MVCC 的补充——快照读不加锁，当前读才加锁。理解"什么操作加什么锁、锁住多大范围"，才能在高并发场景下写出既正确又不阻塞的代码。**

---

## 锁分类

```
InnoDB 锁
├── 行级锁
│   ├── S Lock（共享锁）    SELECT ... LOCK IN SHARE MODE
│   ├── X Lock（排他锁）    SELECT ... FOR UPDATE / INSERT / UPDATE / DELETE
│   └── 意向锁（IS / IX）  表级，加行锁前先加意向锁，加速表锁检测
├── 间隙锁（Gap Lock）      锁索引键之间的间隙，防止幻读
├── 临键锁（Next-Key Lock） 行锁 + 间隙锁，RR 级别默认
└── 自增锁（Auto-inc Lock） 表级，保证自增 ID 不重复
```

**S 与 X 的兼容矩阵：**

| | S | X |
|-|---|---|
| S | 兼容 | 冲突 |
| X | 冲突 | 冲突 |

**意向锁存在的意义：** 事务要加表锁时，不需要逐行检查有没有行锁——只需看有没有 IX/IS 意向锁，O(1) 判断。

**意向锁兼容矩阵（意向锁之间互相兼容，只和表级 S/X 冲突）：**

| | IS | IX | S 表锁 | X 表锁 |
|-|----|----|--------|--------|
| IS | 兼容 | 兼容 | 兼容 | 冲突 |
| IX | 兼容 | 兼容 | 冲突 | 冲突 |
| S 表锁 | 兼容 | 冲突 | 兼容 | 冲突 |
| X 表锁 | 冲突 | 冲突 | 冲突 | 冲突 |

## 间隙锁与临键锁

RR 级别下，`FOR UPDATE` 查询一个范围时，InnoDB 会对这个范围加 Next-Key Lock（行锁 + 间隙锁）。

假设表中有 id = 1, 2, 10：

```sql
SELECT * FROM stocks WHERE id > 2 FOR UPDATE;
```

会锁定：
- `(2, 10]`：临键锁（锁住 id=10 这行 + 它左边的间隙）
- `(10, +∞)`：间隙锁

在这期间，其他事务插入 `id = 3~9` 都会被阻塞，直到当前事务提交。

**副作用：** 间隙锁范围越大，插入并发越低。高并发写场景下，可以降级为 RC 以禁用间隙锁（代价：不再防幻读）。

## 加锁规则（RR 级别）

InnoDB 加锁基本单位是 **Next-Key Lock**（左开右闭），根据查询类型退化：

| 场景 | 加锁结果 |
|------|---------|
| 主键等值，记录存在 | 退化为行锁，仅锁该行 |
| 主键等值，记录不存在 | 退化为间隙锁，锁住不存在记录两侧的间隙 |
| 主键范围查询 | Next-Key Lock 覆盖范围 + 右侧 Gap Lock |
| 普通索引等值 | 索引行 X Lock + 两侧 Gap Lock + 回表主键行 X Lock |
| 无索引 WHERE | 全表每行 X Lock，退化为表锁 |

**具体例子（表中 id: 1, 5, 10）：**

```sql
WHERE id = 5 FOR UPDATE          -- 锁: id=5 行锁
WHERE id = 7 FOR UPDATE          -- 锁: (5, 10) 间隙锁（7 不存在）
WHERE id > 5 FOR UPDATE          -- 锁: (5,10] Next-Key + (10,+∞) Gap
UPDATE t SET x=1 WHERE name='a'  -- name 无索引 → 全表 X Lock（生产大坑）
```

## 死锁

**经典死锁模式：**

```
tx1: 锁 A → 等 B
tx2: 锁 B → 等 A   → 循环等待，死锁
```

InnoDB 有死锁检测（innodb_deadlock_detect = ON 默认开启），检测到后回滚代价更小的那个事务（通常是改动行数少的），另一个继续执行。被回滚的事务会收到 `Error 1213: Deadlock found`。

**预防措施：**
1. 所有事务以相同顺序加锁（如按主键从小到大）
2. 缩短事务，减少持锁时间
3. `SELECT ... FOR UPDATE NOWAIT`（MySQL 8.0+）：锁不到立即报错，而非等待
4. `SELECT ... FOR UPDATE SKIP LOCKED`（8.0+）：跳过被锁的行，适合任务队列抢占

**排查：**

```sql
-- 查看最近一次死锁详情
SHOW ENGINE INNODB STATUS\G

-- 开启所有死锁日志（生产慎用，日志量大）
SET GLOBAL innodb_print_all_deadlocks = ON;
```

## 常见加锁场景

| SQL | 加锁类型 |
|-----|---------|
| `SELECT ...` | 不加锁（MVCC 快照读） |
| `SELECT ... LOCK IN SHARE MODE` | S Lock（行锁） |
| `SELECT ... FOR UPDATE` | X Lock（行锁 + 可能 Gap Lock） |
| `INSERT` | X Lock（插入意向锁 + 行锁） |
| `UPDATE WHERE 主键` | X Lock（行锁） |
| `UPDATE WHERE 普通索引` | X Lock（行锁 + Gap Lock） |
| `UPDATE WHERE 无索引` | 全表 X Lock（退化为表锁！） |

最后一条是生产中常见的大坑：**UPDATE/DELETE 的 WHERE 条件没有索引，会锁全表。**

**SKIP LOCKED 实战——任务队列并发抢占：**

```sql
-- 多 worker 并发抢任务，普通 FOR UPDATE 会让后来的 worker 排队等待
-- SKIP LOCKED 跳过已锁行，直接拿下一个可用任务，无等待、无阻塞
SELECT * FROM tasks
WHERE status = 'pending'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED
```

## 实验

对应代码：[experiments/03_lock.go](experiments/03_lock.go)

```bash
go run ./experiments/ lock
```

实验内容：
1. FOR UPDATE X 锁互斥：tx1 持锁期间，tx2 阻塞等待
2. 死锁复现：两个事务反序加锁，InnoDB 自动回滚其中一个
3. 间隙锁阻塞插入：FOR UPDATE 范围查询后，落在间隙内的 INSERT 超时
4. 无索引 UPDATE 退化表锁：WHERE 无索引导致不相关的行也被阻塞
5. SKIP LOCKED 任务队列：多 worker 并发抢任务，无等待无阻塞
