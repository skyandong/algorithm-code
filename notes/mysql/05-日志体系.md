# 日志体系

> **核心认知：三种日志各司其职——Undo Log 保原子性、Redo Log 保持久性、Binlog 保主从一致。理解它们的写入时机和 2PC 的协作关系，就能推导出崩溃恢复、主从延迟等所有生产问题的根因。**

---

## 三大核心日志

| 日志 | 所在层 | 作用 | 写入时机 |
|------|--------|------|---------|
| Redo Log（重做日志） | InnoDB 层 | 崩溃恢复，保证持久性（D） | 事务执行中持续写（WAL） |
| Undo Log（回滚日志） | InnoDB 层 | 事务回滚 + MVCC 版本链 | 数据修改前写入 |
| Binlog（归档日志） | Server 层 | 主从复制 + 时间点恢复 | 事务提交时写入 |

---

## Redo Log：WAL 机制

**WAL（Write-Ahead Logging）：** 先写日志，再写数据页。

- 数据修改先写入 Redo Log（顺序写，极快），然后修改 Buffer Pool 中的脏页
- 脏页由后台线程异步刷盘，不阻塞业务
- 崩溃重启时，用 Redo Log 重放已提交但未落盘的数据

**为什么不直接写数据文件：** 数据文件是随机写（页分散在磁盘各处），Redo Log 是顺序追加，性能差一个数量级。

**innodb_flush_log_at_trx_commit 控制持久性：**

| 值 | 行为 | 性能 | 风险 |
|----|------|------|------|
| 0 | 每秒写一次 log buffer → 磁盘 | 最高 | 崩溃丢 1 秒数据 |
| 1（默认） | 每次提交都 fsync | 最低 | 不丢数据 |
| 2 | 每次提交写 OS 缓存，每秒 fsync | 中等 | OS 崩溃丢数据 |

**Redo Log 物理结构（环形）：**

```
       write pos（当前写入位置）
            ↓
┌───────────●────────────────────────────────┐
│   ib_logfile0            ib_logfile1       │
│   ████████████░░░░░░░░░░░░░░░░░░░░░░░░░░  │
│               ↑                            │
│           checkpoint（脏页已刷盘的位置）     │
└────────────────────────────────────────────┘
```

- **checkpoint**：标记"此位置之前的脏页已全部刷盘"，checkpoint 前的空间可被复用
- **write pos 追上 checkpoint**：日志写满，MySQL 停止接受新写入，强制刷脏页推进 checkpoint，业务出现卡顿
- 调整：8.0.30 前用 `innodb_log_file_size`（单文件 48MB × 2，生产建议 1~4GB）；**8.0.30+ 改用 `innodb_redo_log_capacity`（默认 100MB，可在线动态调整）**，日志文件也移入 `#innodb_redo` 目录

## Undo Log：回滚 + MVCC

- 记录的是"如何撤销"：INSERT 对应的 Undo 是 DELETE；UPDATE 对应的 Undo 是反向 UPDATE
- MVCC 用 Undo Log 的版本链实现历史版本读（详见 [02-事务与MVCC.md](02-事务与MVCC.md)）
- 长事务会使 Undo Log 无法被清理（purge 线程需要确认没有活跃事务在读老版本），导致表空间膨胀

**生产建议：** 设置 `innodb_undo_log_truncate = ON`，并监控 `information_schema.INNODB_TRX` 里的长事务。

---

## Binlog：复制与恢复

**三种格式：**

| 格式 | 记录内容 | 优缺点 |
|------|---------|--------|
| STATEMENT | SQL 语句原文 | 体积小，但 `NOW()`/`UUID()` 等函数从库执行结果不一致 |
| ROW（默认） | 每行数据变更前后值 | 结果精确，体积大（100 万行变更 = 100 万条记录） |
| MIXED | 安全 SQL 用 STATEMENT，含不确定函数自动切 ROW | 折中，生产仍推荐 ROW |

**为什么生产推荐 ROW：**
```sql
UPDATE orders SET status = 1 WHERE user_id = 100;  -- 影响 50 行

STATEMENT: 记录这条 SQL，从库执行时若数据有细微差异结果可能不同
ROW:       记录 50 行的 [before, after]，从库直接应用，必然一致
```

**sync_binlog 控制：**
- `sync_binlog = 0`：OS 自己决定何时 fsync，最快但崩溃可能丢 Binlog
- `sync_binlog = 1`：每次提交都 fsync，双一配置（配合 `innodb_flush_log_at_trx_commit=1`），最安全

## 两阶段提交（2PC）

```
事务执行
    ↓
写 Redo Log（prepare）
    ↓
写 Binlog
    ↓
Redo Log 标记 commit
    ↓
返回客户端
```

**为什么需要 2PC：** 保证 Redo Log 和 Binlog 的一致性。

- 若先提交 Redo，再写 Binlog 时崩溃：主库有数据，从库没有 → 主从不一致
- 若先写 Binlog，再提交 Redo 时崩溃：从库多了数据，主库没有 → 主从不一致

崩溃恢复时：Redo Log 有 prepare 但没 commit，检查对应 Binlog 是否存在：
- 存在 → 提交（补 commit）
- 不存在 → 回滚

## Relay Log 与主从复制延迟

```
主库：事务提交 → 写 Binlog
从库：IO 线程拉取 Binlog → 写 Relay Log → SQL 线程重放

延迟 = 主库写入时间 − 从库重放完成时间
```

**延迟的常见原因：**

| 原因 | 说明 | 解决 |
|------|------|------|
| 串行重放 | 5.6 之前 SQL 线程单线程，主库并发写从库排队放 | 升级 5.7+，开启并行复制 |
| 大事务 | 主库一个事务改 100 万行，从库重放完才算同步 | 拆分大事务，控制单次影响行数 |
| 从库性能差 | IO/CPU 跟不上主库写入速度 | 提升从库配置，或只读不写 |
| 网络延迟 | IO 线程拉 Binlog 慢 | 优化网络，或用半同步复制 |

**监控延迟：**
```sql
SHOW SLAVE STATUS\G
-- Seconds_Behind_Master: SQL 线程落后主库的秒数
-- 注意：这个值不完全准确，IO 线程已拉取但 SQL 线程未重放的部分才体现在这里
-- 8.0.22+ 语法改为 SHOW REPLICA STATUS\G（Seconds_Behind_Source）
```

**并行复制（5.7+）：**
```
slave_parallel_type = LOGICAL_CLOCK  # 按事务提交顺序并行
slave_parallel_workers = 8           # 并发重放线程数
```

## 崩溃恢复完整流程

```
MySQL 重启

Step 1: 扫描 Redo Log，收集所有 prepare 状态的事务（XID）

Step 2: 对每个 prepare 事务查 Binlog：
        Binlog 有此 XID → 补 commit，提交
        Binlog 无此 XID → 回滚

Step 3: 重放已提交事务的 Redo Log，恢复未刷盘的脏页

Step 4: 启动完成，主从 Binlog 必然一致
```

任何时间点崩溃，重启后 Redo 和 Binlog 必然对齐，这就是 2PC 的价值。
