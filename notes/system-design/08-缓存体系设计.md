# 缓存体系设计：三级缓存与一致性全景

> **核心认知：** `notes/redis/05` 讲过缓存三问（穿透/击穿/雪崩）的**现象与对策**，本篇把它们组装成**架构叙事**——面试官问"你的系统怎么用缓存"时，你要能从分层讲到一致性讲到热点治理，而不是零散地背三个名词。骨架是三级缓存：**本地缓存（ns 级，小而热）→ Redis（ms 级，共享）→ DB**——越靠近用户的层越快越小越容易不一致，**一致性的代价随层级升高而指数增长**，所以默认策略是"Cache-Aside + 先更库后删缓存"，失败补丁是延迟双删/binlog 订阅，**强一致需求的路径是绕过缓存直读库**——绝不要为缓存上分布式事务。热点的终极答案和 02 篇库存分桶同构：本地缓存顶住读 + key 分片打散写。本篇是全模块收尾：前面 7 篇里每个系统的缓存决策，都能在本篇的框架里找到位置。

前置知识：缓存三问（`notes/redis/05`）、Redis 数据结构（`notes/redis/02`）、主从复制与 binlog（`notes/mysql/13`）、库存分桶（本模块 `02`）、Feed 收件箱即缓存（本模块 `04`）。

## 1. 三级缓存：分层与代价模型

```text
┌────────────────────────────────────────────┐
│ L1 本地缓存 (进程内 map/LRU, ns 级)          │ 小而热: 配置/元数据/热点 key 顶梁
├────────────────────────────────────────────┤
│ L2 Redis (集中式, ms 级, 共享)               │ 主力: 全量放得下的读多写少数据
├────────────────────────────────────────────┤
│ L3 MySQL (真相层, 持久化事务)                 │ 唯一可信源
└────────────────────────────────────────────┘
```

**代价模型**（每升一层，付出什么）：

| 层级 | 延迟 | 容量 | 不一致窗口 | 新增问题 |
|---|---|---|---|---|
| L1 本地 | ~100ns | 进程内存（百 MB 级） | 秒~分钟（取决于失效策略） | **多实例各自为政**：A 改了 B 不知道 |
| L2 Redis | ~1ms | 集群内存（百 GB 级） | ms~秒 | 缓存三问、主从延迟 |
| L3 DB | ~10ms+ | 磁盘（TB 级） | 0（定义） | 慢、贵、连接数有限 |

**WHY 不直接两级（Redis+DB）**：Redis 网络一跳 ~1ms，10 万 QPS 的热点 key 光网络就 100 核 ms 的 CPU 时间；本地缓存把这条路缩成一次内存读。**L1 的存在理由只有一个字：热**——不热的数据放 L1 纯属浪费进程内存还引入失效复杂度。

**L1 的失效广播问题**（本层最大的坑）：多实例本地缓存的一致性靠"删除广播"（Redis pub/sub 通知所有实例失效自己的副本）——pub/sub 是尽力而为，漏通知 = 实例间永久不一致直到 TTL。所以 L1 的数据选择标准：**能容忍 TTL 级不一致的**（配置、元数据、点赞数），不能容忍的（库存、余额）直接跳过 L1。

## 2. 三问的架构叙事版

`notes/redis/05` 逐个讲过，这里给"架构叙事版"——面试时把三问串成一个故事讲出来：

### 2.1 穿透：请求打向"根本不存在的 key"

**叙事线**：恶意流量/脏链接查随机 key → 缓存永不命中 → 全量透传 DB（`notes/redis/05` §1）。**架构位次：布隆过滤器是读路径的第一道闸**（03 篇短链已示范：120MB 挡住全部随机 key），空值缓存是轻量补丁（短 TTL 的 NULL 标记），入口限流（`notes/nginx/03`）是兜底。设计顺序：**布隆 → 空值 → 限流**，从治本到治标。

### 2.2 击穿：热 key 失效瞬间的高并发重建

**叙事线**：百万 QPS 的 key 到期 → 全部请求同时 miss → 同时回源重建 → DB 被同一查询打死。**架构解法两个**：①**单飞重建**（singleflight 语义）：miss 后抢一把锁，抢到的查库回填，其余请求等结果或返回旧值——重建次数从 100 并发降到 1 次（本篇实验的核心对照）；②**逻辑过期**：value 里带过期时间字段，物理永不过期，发现逻辑过期的请求异步触发重建、先返回旧值——**用短暂陈旧换零击穿**。选型：能容忍陈旧选逻辑过期（体验最顺滑），不能容忍选单飞。

### 2.3 雪崩：大面积同时失效/Redis 整体挂

**叙事线**：批量 key 同 TTL 到期（或 Redis 宕机）→ 请求洪峰整体砸向 DB → DB 挂 → 重启中重启……连环雪崩。**三层防线**：①**TTL 加随机抖动**（基础值±20%，把同时到期摊开）；②**多级缓存**（L1 在 Redis 挂时还能顶住热点读——L1 的第二个存在理由）；③**熔断限流降级**（DB 前挂限流，宁可拒部分服务也不全死，模块四 `notes/microservice/03` 的熔断器就是干这个的）。雪崩和击穿的区别要一句话说清：**击穿是单 key、雪崩是大面积**；共同点都是"缓存层失效后 DB 扛不住回源洪峰"。

## 3. 一致性：默认策略与补丁链

### 3.1 默认策略：Cache-Aside + 先更库后删缓存

```text
写:  ① UPDATE DB  ② DEL cache          （顺序固定: 先库后删）
读:  miss → 查 DB → SET cache (带 TTL)
```

**WHY 是"删"不是"更"缓存**：更新缓存在并发写下会乱序覆盖（A 写库 v2、B 写库 v3，B 先更缓存 v3、A 后更缓存 v2 → 缓存 v2 库 v3 永久错）；删除把"重建"交给下一个读请求，天然收敛到库的值。**WHY"先库后删"而不是"先删后库"**：先删的话，删后-库提交前的窗口里读请求 miss → 读到旧值 → 回填旧值 → 库是新的缓存是旧的（且这个错不会被下次写修正，直到 TTL）。先库后删的反例窗口窄得多（详见 3.2 的并发反例）。

### 3.2 补丁链：已知缺陷逐个补

**缺陷一：并发读写的竞态窗口**（先库后删的经典反例）：

```text
读 A miss → 查库得 v1（此时库还没被改）
写 B 更库 v2 → 删缓存（无东西可删）
读 A 回填 v1 → 缓存 v1, 库 v2 —— 错!
```

**补丁：延迟双删**——写完删一次，延迟 500ms~1s 再删一次（把回填的旧值清掉）。延迟多久看读请求的耗时分布（P99+ 余量）。仍有极小窗口，但工程上够用——**完美一致只有一条路：别用缓存**（§3.4）。

**缺陷二：删除失败**（DB 更新成功、DEL 网络超时）→ 旧值活到 TTL。**补丁：binlog 订阅异步删**（Canal 解析 binlog → 发删除消息，`notes/mysql/13` 的 binlog 消费者语义）——把"删缓存"从业务事务里解耦出来，失败可重试，还天然覆盖了所有写入口（直接改库的 DBA 操作也能触发删）。

### 3.3 补丁选型（按一致要求升序）

| 方案 | 不一致窗口 | 复杂度 | 适用 |
|---|---|---|---|
| TTL 兜底 | ≤TTL | 零 | 大多数数据 |
| 延迟双删 | ~ms 级竞态窗口 | 低 | 读多写少 |
| binlog 订阅删 | ~ms（消费延迟） | 中（要 Canal 链路） | 写入口多、要覆盖 DB 直改 |
| 强一致读路径 | 0 | **绕过缓存直读库** | 库存/余额的下单关键时刻 |

### 3.4 铁律：不为缓存上分布式事务

强一致需求（扣库存、转账）的正解是**关键路径直读库 + DB 条件更新**（02 篇秒杀的 DB 兜底层），而不是"缓存+分布式事务"——后者把缓存的性能收益全部吐给协调成本（`notes/distributed/03` 的 2PC 代价），还引入了新的故障域。**缓存的价值前提就是容忍不一致，不能容忍就别缓存**——这是决策，不是技术难题。

## 4. 热点 key：本地缓存与分片

热点 key 的定义：单 key QPS 高到单分片扛不住（`notes/distributed/05` §热点）。**读写两条治理路线**：

```text
读热点（明星微博、爆款商品详情）:
  L1 本地缓存 —— 就地消化, 请求根本不出进程
  + 逻辑过期 —— 连 miss 重建都省了
  → 本篇实验之: 100 并发读, L1 命中后 Redis QPS 从 100 → 1（仅 L1 过期那一瞬）

写热点（秒杀库存、明星收礼物）:
  key 分片打散 —— stock:1001:0..9 分散到多分片（02 篇 §4 完整论述）
  → 写压力 ÷ 分片数
```

**读热点与写热点的解法为什么不同**：读可以复制（N 份副本消化 N 倍读），写必须串行化到真相层（副本写的合并代价 >> 分片直写）。所以读靠"复制缓存"，写靠"拆分片"——**复制和分片是扩展性的两个正交方向**（`notes/distributed/05` 的复制 vs 分片章节，在这里各找到最佳应用位）。

## 5. 全模块缓存决策回顾

把前 7 篇的缓存决策放到本篇框架里（知识串联自检）：

| 模块 | 缓存决策 | 本篇定位 |
|---|---|---|
| 02 秒杀 | Redis 预扣库存（非缓存，是**原子计数器**）+ DB 真相 | §3.4 强一致路径：关键金额不走缓存 |
| 03 短链 | 全量缓存 + 布隆挡穿透 | §2.1 穿透防御 + 数据不可变所以无一致性问题 |
| 04 Feed | 收件箱 ZSet（可重建缓存） | "缓存是索引, DB 是真相"的读路径典型 |
| 05 IM | 离线收件箱 + route 表 | 状态外置——L2 Redis 承担有状态语义 |
| 06 ID | 号段 buffer（本地内存"缓存"号段） | L1 的变体：预取+快照切换 |
| 07 延迟 | 时间轮（内存索引）+ DB 任务表 | 同 04：内存可重建，重灌即恢复 |

**规律**：凡是"可由真相层重建的数据"都敢放内存/Redis（收件箱/时间轮/route 表）；凡是"真相本身"（库存/订单/余额）永远以 DB 为准、缓存层只做流量整形不做正确性承诺——**这条线画清楚了，缓存体系的设计就不会错**。

## 6. 面试高频

**Q1：讲讲你的缓存架构。**
三级：本地（ns，配置/元数据/热点）→ Redis（ms，主力读多写少）→ DB（真相）。一致性默认 Cache-Aside 先更库后删缓存；补丁按需升级：延迟双删（收敛竞态窗口）、binlog 订阅删（覆盖所有写入口+可重试）；强一致路径（库存/余额）直读库走条件更新，绝不为缓存上分布式事务。

**Q2：为什么是删缓存而不是更新缓存？**
并发写下更新会乱序覆盖：A 库 v2、B 库 v3，缓存却停在 v2 永久错。删除把重建交给下个读，收敛到库值。配套顺序"先库后删"：先删后库的窗口里 miss 读会回填旧值。

**Q3：缓存和 DB 一致性怎么保证到极致？**
承认做不到绝对一致，按需求选档：TTL 兜底 → 延迟双删 → binlog 订阅异步删 → 强一致直读库。极致一致的代价是放弃缓存性能，**正确的回答是给出档位并说明数据该在哪一档**，而不是背"用分布式事务保证"。

**Q4：热点 key 怎么处理？**
先分读写：读热点 L1 本地缓存 + 逻辑过期（请求不出进程）；写热点 key 分片打散（stock:0..N，分片数除以写压力）。读靠复制写靠分片——复制和分片是扩展性的两个正交方向。

**Q5：缓存雪崩和击穿的区别？**
击穿是单个热 key 失效瞬间的并发重建（解法：单飞/逻辑过期）；雪崩是大面积失效或 Redis 整体挂（解法：TTL 抖动 + 多级 + 熔断限流）。共同本质：缓存层失效后回源洪峰超过 DB 容量——所以兜底手段都是"控制回源速率"。

**Q6：本地缓存什么时候用？**
两个判据：够热（单 key QPS 高到 1ms 的 Redis 网络往返成为显著成本）+ 能容忍 TTL 级不一致（失效广播是尽力而为，多实例可能短暂不一致）。配置/元数据/热门内容详情是标准用户；库存余额这类强一致数据禁止上 L1。
