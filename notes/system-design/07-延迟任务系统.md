# 延迟任务系统：时间轮的完整原理

> **核心认知：** "30 分钟后未支付自动取消订单"——这类延迟任务有三条实现路线：Redis zset 轮询（简单但扫描成本随任务数线性涨）、MQ 延迟分桶逐级中转（Kafka 原生不支持任意延迟，要 1m/5m/30m 桶接力）、**时间轮**（O(1) 插入删除，Netty/Kafka 内部同款）。时间轮的核心思想值得"现场画图级"掌握：**环形数组 60 格代表 60 秒，任务挂在格子的链表上，指针每秒走一格，走到哪格就执行哪格的任务；超过一圈的任务用"轮数"字段——指针扫过时轮数减 1，减到 0 才真正执行**。它把"何时执行"映射成"在环上的哪个格子"——用空间（60 个槽）换掉了时间（每秒扫全量任务）。而生产级延迟系统的可靠性铁律是"**内存是索引，DB 是真相**"：任务先落库再进内存轮，宕机重启从 DB 重灌，执行必须幂等——这三条任何一条缺失，宕机一次就把任务丢光。

前置知识：环形计数器（`engineering/ringcounter`——同为环形结构但目的完全不同）、MQ 削峰（`notes/akafka/01`）、φ-accrual 与心跳（`notes/distributed/07`）、幂等（`notes/design-pattern/07`）。

## 1. 需求与三方案对照

**典型需求**（电商/IM 通用）：订单 30min 未支付取消、优惠券到期、重试退避、定时推送。特征：**量大**（百万级在途）、**精度要求秒级即可**、**绝不能丢**。

| 方案 | 原理 | 复杂度 | 适用 |
|---|---|---|---|
| **Redis zset 轮询** | score=执行时间，每秒 `ZRANGEBYSCORE now +inf LIMIT n` 取出到期任务 | 插入 O(logN)，**扫描每秒全量排序开销** | 十万级以下，快糙猛 |
| **MQ 延迟分桶** | topic-delay-1m/5m/30m，消费 1m 桶发现未到期转投 5m 桶 | 逐级中转，延迟粒度受桶限制 | 已有 Kafka 且延迟档位固定 |
| **时间轮** | 环形槽 + 指针步进，任务挂槽 | **插入/删除 O(1)**，到期检查 O(槽内链表) | 百万级在途、海量高频 |

**zset 的隐性成本**：每秒一次的范围查询要遍历跳表前缀，任务量到百万级时 Redis CPU 可观；且所有实例只有主节点能扫（单点扫描）。**时间轮把"到期检查"变成指针移动这个常数动作**——检查成本与任务总量无关。

**Kafka 为什么没有原生延迟消息**：分区是追加日志，按时间取"中间的某条"与顺序消费的模型冲突。RocketMQ 有（基于固定 delay level，本质就是分桶思想）——所以用 Kafka 就得自己造轮子，分桶或时间轮二选一。

## 2. 时间轮原理：现场画图级详解

**结构**（面试要能在白板上画出来）：

```text
            ┌───┬───┬───┬───┬───┬───┐
            │ 0 │ 1 │ 2 │ 3 │ 4 │...│ 60 格 = 60 秒一圈
            └─┬─┴───┴─┬─┴───┴───┴───┘
              │      └─ [task-A 轮数=0] [task-C 轮数=2]
              └─ [task-B 轮数=1]

指针 currentTime: 每秒 +1, 走到格子 → 遍历该格链表:
    轮数 > 0 : 轮数 -= 1, 留在格子里（等下一圈）
    轮数 = 0 : 执行！从链表摘除
```

**三个关键计算**：

```text
插入延迟 d 秒的任务:
    轮数 rounds = (d-1) / 60        # 差几个整圈
    槽位 slot   = (currentTime + d) % 60
    挂到 slots[slot] 链表尾部

指针每秒走一格（tick）:
    slot = (slot+1) % 60 → 扫描链表按轮数判定
```

**WHY 插入是 O(1)**：两次除法取模 + 链表尾插，与任务总量无关——对比 zset 的 O(logN) 跳表插入 + 每秒全量扫描。**WHY 用"轮数"而不是开 86400 格**：一天的延迟用 60 格+1440 轮即可表达；若要开 86400 格，内存和指针空转成本爆炸——**环的大小是时间粒度，轮数是圈数补偿**，两级配合用小环表达任意延迟。

**层级时间轮**（Kafka 内部实现，进阶）：单轮不够时叠多层——第一轮 1s 粒度 60 格，第二轮 1min 粒度 60 格，第三轮 1h 粒度……第一轮转满一圈，第二轮指针走一格并把该格任务**降级**投放回第一轮。像时钟的秒→分→时进位。**好处**：任意大延迟都在 O(1) 插入；**代价**：降级投放的复杂度。秒级精度的业务单轮+轮数就够（本篇实验实现单轮版）。

**删除/取消**（用户提前支付了订单）：任务节点存"已取消"标记或从链表摘除（双向链表 O(1) 删除）——延迟任务的取消和执行一样高频，**设计时必须原生支持**。

## 3. 可靠性三件套：落库、重灌、幂等

**内存轮是缓存，DB 是真相**（02/04/05 篇反复出现的架构原则在延迟场景的落地）：

```text
提交任务:
  ① DB: INSERT delay_task(status=pending, run_at, payload, idempotent_key)  -- 先落库
  ② 内存轮: 挂槽（携带 task_id）
  （①②之间宕机 → 任务晚执行但仍在 DB, 重灌后补跑）

宕机重启:
  ③ 重灌: SELECT * FROM delay_task WHERE status=pending AND run_at < now+窗口
     全部重新计算轮数挂回内存轮
  （重灌期间任务可能"迟到"——延迟系统的 SLA 本来就是"不早于", 迟到用监控兜底）

执行:
  ④ 状态机推进: pending → running → done/failed(重试)
     ③④之间宕机 → 重启重灌把 running 的也捞回来 → 重复执行!
  ⑤ 幂等: 执行器必须按 idempotent_key 去重（notes/design-pattern/07）
```

**WHY 顺序是"先落库再挂轮"**：反过来则宕机窗口丢任务且无从恢复。**WHY 执行要幂等**：从"取出"到"标记完成"之间必然存在宕机窗口，at-least-once 是重灌机制的必然代价——和 02 篇 MQ 重复消费、05 篇消息重传是同一个结论：**重试与幂等是成对出现的设计**。

**执行与调度分离**（架构升级）：轮只负责"到点触发"，执行走 worker 池 + 队列——调度线程绝不执行业务逻辑（一个慢任务卡住指针，全轮任务集体迟到）。

## 4. 分布式化与高可用

单机时间轮容量：百万任务 × ~100B/任务 = 100MB 内存，**单机毫无压力**——分布式化的动机不是容量，是高可用与隔离性：

```text
分片: 按 task_id hash 分给 N 个调度实例（notes/distributed/05 的 hash 分片）
     每实例只灌/只扫自己的分片 —— 横向扩容 + 故障隔离
HA:  每分片一个主 + 备（备不跑轮, 只 standby）
     主挂 → 备从 DB 重灌接管（就是 §3 的重灌逻辑, 天然故障转移路径）
     分片所有权用分布式锁/租约仲裁（notes/redis/08, 带租约防脑裂）
```

**WHY 备机不跑轮**：两个实例同时扫同一分片 = 双倍执行触发（幂等能兜住但浪费且制造监控噪音）。**主备的本质是"DB 是真相"的再利用**：备机不需要复制内存状态，接管 = 重灌，简单可靠。

**时钟问题**：run_at 用服务端统一时钟（或混入单调序，`notes/distributed/06`），不信任客户端时间；实例间 NTP 偏差 ≤1s 对秒级精度无影响——**延迟任务的 SLA 决定了时钟要求，反过来"纳秒级同步"是过度设计**。

## 5. 与 ringcounter 的差异

`engineering/ringcounter`（环形计数器）和本篇时间轮同为"环形数组"，面试容易混，对照记忆：

| | ringcounter | 时间轮 |
|---|---|---|
| 环的语义 | 环的每格是一个**计数桶**，环滚动覆盖最老数据 | 环的每格是一个**任务槽**，指针步进触发执行 |
| 目的 | 固定窗口内的**滑动计数**（限流统计） | 延迟任务的**到期调度** |
| 指针 | 隐式（每次写"当前格"，过期格清零） | 显式（定时器驱动，每 tick +1） |
| 数据生命周期 | 写入后活一个窗口长度被覆盖 | 执行完即摘除，未到轮数跨圈存活 |

一句话区分：**ringcounter 是"时间上的滑动窗口统计"，时间轮是"时间上的离散触发调度"**。两者可以组合：时间轮的执行器里用 ringcounter 统计每秒执行量做监控。

## 6. 面试高频

**Q1：延迟任务有哪几种实现？**
Redis zset 轮询（score=执行时间，每秒范围取——量小可用）；MQ 延迟分桶（1m/5m/30m topic 逐级中转——已有 Kafka 且档位固定）；时间轮（环形槽+指针+轮数——百万级在途、O(1) 插入）。选型看量级和已有基础设施。

**Q2：讲一下时间轮的原理。**
60 格环形数组，每格挂任务链表；指针每秒走一格，扫到的格子里轮数>0 减 1 留守，轮数=0 执行摘除。插入：`轮数=(d-1)/60, 槽=(now+d)%60`，O(1)。超一圈靠轮数字段表达，多层时间轮（秒分时三级降级）可表达任意延迟，Kafka/Netty 内部在用。

**Q3：时间轮怎么保证任务不丢？**
三件套：任务先落 DB 再挂轮（宕机窗口只迟到不丢失）；重启从 DB 重灌 pending 任务（重灌就是故障转移路径）；执行按 idempotent_key 幂等（重灌窗口的重复执行是 at-least-once 的必然代价）。核心原则：内存是索引，DB 是真相。

**Q4：任务提前完成要取消，怎么设计？**
任务节点可标记取消（执行时检查）或双向链表 O(1) 摘除；DB 侧同步 status=cancelled。取消和执行同级高频，设计期就要原生支持——事后补丁只能靠执行时查 DB 状态兜底（慢一拍但正确）。

**Q5：调度和执行为什么要分开？**
调度线程只负责到点触发，执行投递给 worker 池——一个慢任务（DB 卡 5s）若在调度线程里执行，指针卡 5 秒，全轮任务集体迟到。隔离故障域是调度器的第一设计原则（和 netty 的 event loop 不做阻塞 IO 同理）。

**Q6：多实例怎么部署时间轮？**
按 task_id hash 分片，每实例只灌只扫自己的分片（横向扩容+故障隔离）；每分片主备，备机 standby 不跑轮，主机挂后备从 DB 重灌接管，分片所有权用租约仲裁防双主。备机不复制内存状态——接管=重灌，DB 是唯一真相。
