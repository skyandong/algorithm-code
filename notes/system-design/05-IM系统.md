# IM 系统：长连接网关与投递可靠性

> **核心认知：** IM 的三座大山——**连接、可靠、有序**——分别对应三个工程决策。连接：HTTP 短连接撑不住亿万在线，必须 TCP 长连接网关，但长连接是**有状态**的（连接↔用户绑定关系），这与无状态横扩的天性冲突——解法是把状态外置到 Redis/etcd，让网关随时可替换。可靠：网络只能给你 at-most-once，业务要 exactly-once，中间的鸿沟用** seqId（会话内单调，保有序）+ ack + 离线收件箱（保不丢）+ messageId 幂等（保不重）** 的铁三角填补——注意"不丢"和"不重"是矛盾的（重传必然带来重复），所以工程上从不追求传输层 exactly-once，而是在**应用层用幂等去重**。有序：全局有序既不可能也不必要，**会话内有序**才是正确目标——所以消息按会话 hash 分片，同会话永远走同一分片，天然保序。这三条加上多端同步的位点设计，就是 IM 的全部骨架。

前置知识：φ-accrual 判死与心跳（`notes/distributed/07`）、幂等模式（`notes/design-pattern/07`）、hash 分片（`notes/distributed/05`）、binlog 位点类比（`notes/mysql/13`）、雪花时钟（`notes/distributed/06`）。

## 1. 需求拆解与总体架构

**Scenario**：日活 1000 万，同时在线 ~300 万，人均日收发 50 条。关键约束：**在线状态实时感知（秒级）、消息秒达、不丢不重不乱序、多端同步**。

```text
                    ┌─────────── 接入层（有状态,可替换） ───────────┐
 客户端 A ══TCP 长连接══▶ 网关集群 gw-1..N
                    │   职责: 维持连接、编解码、心跳、推消息
                    │   状态(uid→连接)外置: Redis route 表
                    └──────────────────┬───────────────────────────┘
                                       │
                    ┌─────────── 逻辑层（无状态） ────────────────┐
                    │   消息服务: 鉴权/seqId 分配/落库/触发推送
                    │   存储层: 消息表(按会话 hash 分片) + 离线收件箱(Redis)
                    └─────────────────────────────────────────────┘
```

**WHY 网关和逻辑层分开**：网关层专注于连接管理（百万连接的内存/epoll 调优，`notes/nginx/01` 的事件驱动同理），逻辑层专注于业务（无状态可任意横扩）。连接迁移的代价极高（重建 TCP+TLS+握手+鉴权），把"贵的状态"压缩到最小边界内，是所有有状态系统（Redis 主从、MQ broker）的共同设计。

## 2. 长连接网关：无状态化的骗术

长连接的本质矛盾：**连接是物理状态（绑定在某台机器的某个端口上），但架构想要无状态横扩**。解法是把"逻辑状态"从机器里抽出来：

```text
route 表（Redis）:  uid → {gateway_id, conn_id, last_heartbeat}
消息推送:  查 route → 得到目标网关 → RPC 调该网关的 push 接口 → 网关找到连接写出去
网关宕机:  客户端断线重连（指数退避）→ 连到任意存活网关 → 新网关写 route 表
           → 对端下次推送查 route 自然路由到新网关
```

**"任意网关可接管"的 WHY**：route 表是唯一真相，网关只是执行器。这和 04 篇"收件箱是缓存、DB 是真相"、07 篇"内存是索引、DB 是真相"一脉相承——**状态外置 = 状态的单一可信源 + 计算节点可丢**。

**心跳与判死**：TCP keepalive 太钝（默认 2 小时），应用层心跳 30s 间隔 + φ-accrual 判死（`notes/distributed/07`）——移动网络频繁闪断，固定超时误杀率高，φ 自适应不同设备的网络分布。心跳顺便携带 seq 位点，一石二鸟（§4 多端同步用）。

**连接数容量**：单网关 50 万连接是工程常见值（内存 ~10KB/连接 × 50 万 = 5GB）。300 万在线 → 6+ 台网关，按网关容量弹性扩缩。

## 3. 可靠性铁三角：seqId + ack + 幂等

网络消息的三个天然缺陷：**可能丢、可能重复、可能乱序**（TCP 只保证单连接内有序，多连接/重连/多端之间没有免费保证）。铁三角逐一应对：

### 3.1 不丢：ack + 离线收件箱 + 重传

```text
投递: 服务端推消息(seqId=42) → 客户端
ack:  客户端处理完回 ACK(42) → 服务端标记该端已收
重传: 超时未 ack → 重传（指数退避，上限 N 次）
离线: 用户不在线 → 消息 ID 进离线收件箱（Redis List/ZSet, 按 uid）
      上线时: 拉离线消息 → 追平 → 清空收件箱
```

**WHY 必须 ack**："发出去"≠"收到了"——推送成功的 TCP write 只代表进了内核缓冲区，客户端可能下一秒崩溃。**投递语义要在应用层闭环**，这也是 `notes/akafka/02` 消费 offset 提交的同款问题：生产者的完成点必须由消费者的确认定义。

### 3.2 不重：messageId 幂等

重传 + 离线补拉 = 必然重复投递。客户端按 messageId 去重（本地 LRU 记最近的 ID，或按会话检查"已处理的最大 seqId"）——**传输层追求 exactly-once 是伪命题，应用层幂等才是正解**（`notes/design-pattern/07` 的幂等原则）。

### 3.3 不乱序：会话内单调 seqId

**全局有序不需要也做不到**（跨会话的先后没有业务意义，且全局序号是单点）；**会话内有序是刚需**（"先问后答"反了没法聊）。

```text
seqId 分配: 每个会话一个计数器（Redis INCR conv:{cid}:seq 或 DB 行）
           会话内严格 +1 单调
接收端:    检测 seqId 断档（收到 43 但没 42）→ 按 messageId 触发补洞
           → 从服务端拉缺失区间 → 缓冲重组 → 依序上抛 UI
```

**乱序的来源**：重连换网关、多端并发收、离线补拉与实时推交错。补洞 + 重组窗口是接收端的必备复杂度——实验 05 完整模拟了这个过程。

## 4. 存储按会话分片与多端同步

**消息表分片**（01 篇算过账：日 5 亿条必须拆）：

```text
分片键 = hash(会话ID) % 256
WHY 会话做键: ①同会话消息落同分片 → 分片内按 seqId 排序即会话序（天然保序）
             ②读模式是"按会话拉历史"，同键聚集查询快（notes/distributed/05）
冷热:  最近消息热存（Redis 按会话缓存尾部 N 条），历史走 DB 分片查询
```

**WHY 不用 uid 做分片键**：一条消息属于两个 uid（收发双方），按 uid 分片要么双写（一致性噩梦）要么查询两次。**分片键跟着"读的单位"走**——IM 的读单位是会话。

**多端同步**（手机+电脑同时登录）：每端记自己的**同步位点 sync_key**（该端已同步的最大"全局提交序号"），上线后 `WHERE commit_seq > sync_key` 增量拉——这就是 binlog 位点消费的语义（`notes/mysql/13`）。全局提交序号用发号器（06 篇）或时间戳+ID 复合（`notes/distributed/06` 的混合时钟）。

## 5. 群聊不存储扇出

**群消息绝不推扩散**（04 篇 Feed 的反面教材警示：10 万人的群一条消息写 10 万收件箱 = 灾难）。群聊是**读扩散**：

```text
发消息: 写一次群会话表（获得群内 seqId）→ 完成
收消息: 在线成员: 网关按成员列表推（推的是"通知"，不落个人收件箱）
       离线/拉模式: 各自按位点来群会话增量拉
已读回执: 群成员各自上报自己的 read_seq，服务端只存每成员一个数字
```

**对比总结**（面试必背的对称性）：

| | 单聊 | 群聊 |
|---|---|---|
| 扩散 | 写扩散到离线收件箱（量小：1 个） | 读扩散（量小：每人只读自己要的） |
| 存储 | 消息表按会话分片 | 同左，只是会话成员多 |
| 已读 | 双端位点 | 每成员一个 read_seq |

本质：**扇出成本永远和"接收者数量×消息频率"相关，单聊选择推因为接收者=1，群聊选择拉因为写扩散不可承受**。万人群再做分级（活跃成员推、非活跃拉）——和 04 篇完全同构。

## 6. 面试高频

**Q1：IM 怎么保证消息不丢不重不乱序？**
不丢：应用层 ack + 离线收件箱 + 超时重传；不重：messageId 客户端幂等去重（重传必然带来重复，应用层去重是唯一正解）；不乱序：会话内单调 seqId + 断档检测补洞重组。三者合称铁三角——传输层只保证尽力而为，语义全部在应用层闭环。

**Q2：长连接网关怎么做高可用？**
状态外置：连接↔用户映射存 Redis，网关本身无逻辑状态可随时替换；宕机时客户端指数退避重连到任意网关，新网关刷新 route 表，后续推送自动路由。心跳 30s + φ-accrual 判死防误杀（`notes/distributed/07`）。

**Q3：消息表怎么分片？为什么按会话不按用户？**
按会话 hash 分 256 表：同会话同分片天然保序（分片内 seqId 即会话序），读单位是会话所以聚集查询快。按 uid 要么双写（两份一致性）要么双查。**分片键 = 读的单位**。

**Q4：多端同步怎么设计？**
每端记 sync_key（已同步的全局提交序号），上线增量拉 `> sync_key` 的消息——binlog 位点消费的语义（`notes/mysql/13`）。每端独立位点互不干扰，端内乱序由会话 seqId 补洞兜住。

**Q5：万人群消息怎么处理？**
读扩散：消息只写一次群会话表，成员各自按位点拉；在线成员推"通知"不落收件箱；已读回执每人只存一个 read_seq 数字。绝不写扩散（10 万收件箱×每条消息=灾难）。超大群再按活跃度分级推拉——与 Feed 推拉结合同构。

**Q6：seqId 为什么不用雪花？**
雪花是**趋势递增**不保证严格连续单调（多机并发时钟回拨，`notes/distributed/06`），而 seqId 的价值恰恰是**连续性**——断档检测依赖"+1 连续"这个性质。会话级计数器（Redis INCR / DB 行锁自增）量级完全可控（单会话 QPS 低），没有雪花的分布式需求。
