# 分布式 ID：工程视角的发号器

> **核心认知：** 理论篇（`notes/distributed/06`）已经讲过 Lamport 时钟、向量时钟和雪花；本篇讲**工程落地**：生产系统真正用的发号器就三类——雪花（本地生成、趋势递增）、号段（美团 Leaf-segment，DB 依赖降到最低）、UUIDv4（几乎总是一个错误答案，尤其在 MySQL 主键场景——随机性直接打死 B+ 树的局部性）。一个容易被忽视的语义分层：**雪花只保证"趋势递增"，号段/etcd revision 才能提供"严格单调"（fencing 语义）**——这个区别决定了"锁的持有者版本号""资源创建顺序裁决"这类正确性场景该选谁。本篇展开号段双 buffer 的完整原理（为什么是"发到 10% 预取下一段"而不是用完再取），以及 UUID 做 MySQL 主键的灾难分析。

前置知识：时钟与顺序理论（`notes/distributed/06`）、MySQL 索引与页分裂（`notes/mysql/01`）、短链发号器选型（本模块 `03`）、fencing token（`notes/redis/08` §锁的续期问题）。

## 1. 需求：什么样的系统需要分布式 ID

单库 `AUTO_INCREMENT` 在三个时刻死掉：①分库分表后多库各自增必然冲突（`notes/mysql/11`）；②写入要预知 ID（消息先组包后落库）；③业务上游合并多数据源（对账、多机房）。需求维度：

| 维度 | 问题 | 典型答案 |
|---|---|---|
| 有序性 | 要严格单调还是趋势就行？ | 趋势：日志/消息 ID；严格：fencing/创建顺序 |
| 可用性 | DB 抖 100ms 能不能忍？ | 能→号段；不能→雪花（本地生成） |
| 长度 | 能给多少 bit？ | 64bit 数字 vs 128bit 字符串 vs 业务短码 |
| 依赖 | 允许依赖什么基础设施？ | 雪花零依赖；号段要 DB；etcd 要共识集群 |

**4S 里这属于 Scenario 的子问题**——先明确"要什么程度的有序"，再选方案，而不是拿到"分布式 ID"四个字就背雪花。

## 2. 三大方案工程对照

| | 雪花 Snowflake | 号段 Segment（Leaf） | UUIDv4 |
|---|---|---|---|
| 组成 | 41bit 时间+10bit 机器+12bit 序列 | DB 预分配区间 [start, end) 本地发 | 122bit 随机 |
| 有序性 | **趋势递增**（同毫秒内按序列） | 段内严格+1，**跨段也递增**（段区间递增分配） | 完全无序 |
| 依赖 | 时钟（回拨是命门）+ 机器号分配 | 一张 DB 表（发号器高可用） | 无 |
| 吞吐 | 本地生成，**千万级/秒/机** | 段内本地，受取段频率限制（默认百万级） | 本地生成，极高 |
| 长度 | 64bit | 64bit | 36 字符 |
| 主要坑 | 时钟回拨、机器号手工分配 | 重启浪费一段、DB 高可用 | **MySQL 主键灾难**、无序不可比 |

**趋势 vs 严格**（本篇 §5 展开）：雪花的 41bit 时间戳来自**本地时钟**——两台机器的"递增"没有可比性（NTP 误差 ms 级），跨机器无法裁决先后；号段的段区间由同一个 DB 行分配，**全局任意两个 ID 的先后关系是确定的**（段号大的必然后发）——这在裁决语义上是质的区别。

## 3. 号段双 buffer：完整原理

号段方案把"每个 ID 一次 DB 写"变成"每 step 个 ID 一次 DB 写"，DB 压力降 3 个数量级。但单 buffer 有一个问题：

```text
单 buffer 的坑:
  段用到 0 → 同步去 DB 取下一段（~10ms-100ms）→ 这段时间所有发号请求阻塞
  DB 恰好抖动 → 发号服务整体卡顿 → 上游雪崩

双 buffer 的解法:
  buffer1 发号中，用到剩余 10% 时 → 异步线程预取 buffer2 装好备用
  buffer1 用尽 → 原子指针切换到 buffer2（纳秒级, 零阻塞）
  DB 抖动发生在"还有 10% 余量"的窗口内 → 完全无感
```

**WHY 是 10% 不是 50%**：预取太晚（1%）余量撑不过取段耗时；太早（50%）两段并发活跃时间长、DB 写频翻倍、且重启浪费的号段期望更大。10% 的含义是：**余量消耗时间 ≥ 10×取段耗时**（step=1 万、发号 1000/s → 余量可撑 1 秒，取段 100ms 内完成即可）——它是"预取窗口"和"DB 压力"的折中，可按发号速率调。

**切换的实现**：两个 buffer 加 atomic 指针（`notes/golang/07` §原子操作），读者永远从当前指针读；预取线程只写"备胎"buffer，装好后原子换指针——**无锁切换，读者无感知**。这和模块四配置中心的热更新快照（`notes/microservice/02`）是同一个模式：**一写多读 + 整体换快照**。

**高可用**：发号服务多实例时，DB 段表用 `UPDATE segment SET max_id=max_id+step WHERE biz=?` 的行锁保证两实例取到不相交的段（02 篇秒杀条件更新的同款技巧——用单语句原子性替代显式锁）。实例挂掉浪费未用完的段，**可用性用号的浪费率换**（step 越小浪费越少但 DB 压力越大——又一个 trade-off）。

## 4. UUID 做 MySQL 主键的灾难分析

面试高频陷阱题："表主键用 UUID 行不行？"——**能跑，但生产上是灾难**，三个原因层层递进：

**① 页分裂（最核心）**：InnoDB 是聚簇索引，数据按主键物理有序存放（`notes/mysql/01`）。自增 ID 永远追加到 B+ 树最右页——**顺序写**，页写满开新页；UUIDv4 随机落点——每次插入大概率落在已满的页中间，**分裂成两页各半满**：①写入放大（一页数据搬两次）；②页缓存命中率崩（热页被随机稀释，buffer pool 装不下"正在分裂的随机页"，`notes/mysql/12`）；③空间碎片 50% 起步。

**② 体积**：36 字符 vs 8 字节 bigint——主键要复制进**每一个二级索引**（二级索引叶子存主键值），全表所有索引体积×4.5，内存/IO 全链路放大。

**③ 不可比**：无序 ID 无法做"按创建时间排序"的近似查询（雪花/号段的前缀时间戳可以直接范围扫）——业务上白丢一个索引能力。

**正确的随机性需求用别的方式满足**：要防枚举（03 篇短链）→ ID 可逆混淆或独立短码字段；要跨系统全局唯一不落库 → 雪花；**UUIDv4 在存储层没有合理席位**（UUIDv7 时间戳前缀版解决了有序性，若一定要 UUID 形态选 v7）。

## 5. 严格单调 vs 趋势递增：fencing 语义

**fencing 场景**（`notes/redis/08` 的锁续期问题变体）：分布式锁的持有者 A 卡在 GC/长暂停，锁租约过期后 B 获得锁去写存储——A 苏醒后带着旧锁继续写，怎么拦？

```text
答案: 每次获得锁附带一个单调递增的 fencing token
     存储层拒绝 token 比已见过的最大值小的写入
     A(token=33) 苏醒 → B 已用 token=34 写过 → 存储层拒绝 33
```

**这个 token 的硬要求是"严格单调"**——谁提供？雪花**不行**：两台机器的时钟偏差让"33/34"这种全局裁决不可能（A 机器时钟快 5ms，它可能永远发出比 B 大的时间戳）。**号段/etcd revision 可以**：段区间由单一 DB 行/共识日志分配，全局序是权威的——**严格单调的来源必须是"单一序列化点"**（DB 行锁、Raft 日志、共识 revision——`notes/distributed/02`）。

这个分层是选型的隐藏维度：

| 场景 | 需要的语义 | 选型 |
|---|---|---|
| 日志/消息 ID、短链 | 趋势递增（索引局部性够用） | 雪花/号段都行 |
| fencing token、创建顺序裁决 | 严格单调 | 号段/etcd revision |
| 纯去重不排序 | 全局唯一即可 | 雪花（便宜） |

## 6. 面试高频

**Q1：分布式 ID 有哪些方案？你怎么选？**
雪花（零依赖本地生成、趋势递增、时钟回拨要处理）、号段（DB 取段本地发、严格单调、双 buffer 零抖动）、UUID（唯一但无序，MySQL 主键场景否决）。选型看三点：有序性要求（趋势 vs 严格）、可用性要求（能不能容忍 DB 依赖）、长度预算。业务主流：雪花 + 号段双 buffer 两分天下。

**Q2：雪花时钟回拨怎么办？**
三层：①回拨小（<几十 ms）：自旋等待时钟追平；②回拨大：拒绝发号 + 告警（不能发"过去"的 ID，会和已发的撞）；③备用位：留 2-3 bit 做扩展位，回拨时换"序列偏移"继续发（牺牲寿命）。根本解：机器部署 NTP 渐进校时（slewing 不回拨）+ 监控时钟偏差。

**Q3：号段双 buffer 为什么能消除取段抖动？**
当前段用到剩余 10% 时异步预取下一段装进备胎 buffer，用尽后原子换指针——切换零阻塞。10% 的语义是余量消耗时间 ≥10× 取段耗时，DB 在预取窗口内抖动完全无感。本质：**用提前量把同步依赖从关键路径挪走**（和 CPU 指令预取、MQ 预取同构）。

**Q4：UUID 做 MySQL 主键为什么不行？**
①聚簇索引按主键物理有序，随机主键导致页分裂——写放大、buffer pool 命中率崩、碎片 50%；②36 字符比 bigint 大 4.5 倍且复制进所有二级索引；③无序丢掉按时间查询的索引能力。要随机性用可逆混淆，要 UUID 形态用 v7（时间戳前缀）。

**Q5：严格单调的 ID 为什么不能用雪花？**
雪花的序来自各机器的本地时钟，跨机器不可比（NTP 误差）——只保证"趋势"。严格单调必须经过单一序列化点：DB 行锁的段区间、Raft 日志、etcd revision。fencing token 这类正确性场景（锁旧持有者拦截）必须用严格单调，否则裁决结果取决于机器间时钟偏差——等于没有裁决。

**Q6：号段方案的号浪费怎么办？**
浪费来源：实例重启丢未用完的段。缓解：step 调小（DB 压力升，trade-off）；优雅停机把余量还回（写回 DB，复杂度升）；接受浪费（号空间 2⁶⁴ 实际上取之不尽——**先算空间上限再决定要不要优化**，多数场景答案是"不用"）。
