# 秒杀系统：六层削峰与不超卖闭环

> **核心认知：** 秒杀的本质矛盾是**瞬时流量与系统容量的不对等**——100 万人在 1 秒内抢 1000 件商品，99.9% 的请求注定无效，却足以打死任何同步架构。解法只有一个字：**削**——把 100 万 QPS 一层层削到 DB 能承受的量级，让真正到达存储层的请求只剩"和库存同量级"的少数。整套架构就是六层漏斗：静态化+CDN → nginx 限流 → 答题验证码 → Redis 预扣库存 → MQ 异步下单 → MySQL 条件更新兜底。**不超卖是贯穿始终的正确性红线**：Redis 挡量（原子 DECR）、DB 兜底（`UPDATE ... WHERE n>0`）、对账任务（最终校验），三层各司其职——这正是 `notes/distributed/01` 里 BASE 的经典落地：用户看到"抢到"的瞬间，订单还在异步生成。

前置知识：4S 框架与容量数字（本模块 `01`）、nginx 限流三件套（`notes/nginx/03`）、Kafka 削峰（`notes/akafka/01`）、热点 key 与分片（`notes/distributed/05`）。

## 1. 需求拆解：秒杀到底难在哪

用 01 篇的 5 问过一遍（数字假设显式声明）：

| 维度 | 假设 | 推论 |
|---|---|---|
| QPS | 100 万人 1 秒内涌入，峰值 **100 万 QPS** | 超过任何单层组件容量，必须层层削 |
| 读写比 | 前期查询页面 100:1，下单瞬间写洪峰 | 静态化先解决读，写靠削峰 |
| 一致性 | **绝不超卖**；少卖可接受（回流再卖） | 正确性要求集中在库存这一个 key 上 |
| 可用性 | 秒杀时刻挂 = 事故，但可降级（售罄页） | 每层都要有失败预案 |
| 数据量 | 库存 1000 件，订单 ≤1000 条 | 存储量极小，难点全在流量 |

结论：**秒杀是流量问题不是存储问题**。100 万请求里 999,000 个注定失败，架构目标就是让这 99.9% 的请求在最便宜的层被拒之门外。

## 2. 六层削峰漏斗

```text
100 万 QPS    L1 静态化+CDN     页面/商品详情全部静态，动态数据Ajax拉
              │ 拦截 ~90% 读流量
~10 万 QPS    L2 nginx 限流      limit_req rate=100r/s burst=50 nodelay
              │ 超量直接 503/跳转排队页（notes/nginx/03）
~1 万 QPS     L3 答题/验证码     错峰 + 拦机器人，人类答题 1-2 秒摊平峰值
              │
~5 千 QPS     L4 Redis 预扣库存   DECR 原子扣减，<0 立即回滚并标记售罄
              │ 拦截 99% 的无效写（只剩 ~1000 个成功者向下）
~1000         L5 MQ 异步下单      订单请求进 Kafka，DB 按消费能力匀速写
              │ （notes/akafka/01 的削峰语义）
~200 QPS      L6 MySQL 兜底       UPDATE stock SET n=n-1 WHERE id=? AND n>0
                条件更新防超卖，影响行数=0 则补偿回滚 Redis
```

**WHY 每层的拦截率能这么高**：L1 拦的是"看热闹"（每次秒杀 90% 用户只是刷新页面）；L2 拦的是"超频"（脚本刷新）；L3 拦的是"机器人 + 峰值"（把 1 秒的洪峰摊成 10 秒）；L4 是真正的业务闸门（库存只有 1000，第 1001 个之后全是拒绝）；L5/L6 是把"幸存者"以 DB 舒服的速率写进去。**每层解决一个量级的问题，缺一层下一层就会被击穿**。

L4 细节（Redis 预扣的原子性）：

```text
扣:  n = DECR seckill:stock:1001     # 单命令原子
     if n < 0:  INCR 回滚 + 返回"已售罄"   # 回滚是必须的：并发下 -3 和 -1 都要还原
     else:     进入 L5（带上 n 作为扣减凭证）
```

不能用 `GET` 再 `DECR` 两步——检查与执行之间有竞态窗口（`notes/redis/08` 同理）。也不能用 `DECRBY n` 一次扣多件——拆单失败时要按件回滚，逻辑复杂。

## 3. 不超卖闭环：三层防线

不超卖 = 任何时刻已支付订单数 ≤ 初始库存。三层各自应对一类失效：

| 防线 | 应对的问题 | 机制 |
|---|---|---|
| Redis 挡量 | 洪峰下的并发扣减竞态 | DECR 原子性，挡掉 99.9% 无效写 |
| MySQL 兜底 | Redis 与 DB 状态漂移（宕机/回滚丢失/重复消费） | `UPDATE ... WHERE n>0`，DB 行锁串行化，影响行数=0 拒绝 |
| 对账任务 | 一切未知漂移 | 定时比对 Redis 余量 + DB 库存 + 订单数，发现负漂移告警并修复 |

**WHY DB 兜底是必须的**：Redis 预扣成功后走 MQ，消息可能重复投递（at-least-once，`notes/akafka/02`）；Redis 可能在预扣后、下单前宕机，恢复后余量来自旧快照。DB 的条件更新是最终裁判——它是唯一有持久化事务保证的地方（`notes/mysql/02`）：

```sql
-- 扣库存：单语句原子，行锁天然串行化
UPDATE seckill_stock SET stock = stock - 1
 WHERE sku_id = 1001 AND stock > 0;
-- affected_rows = 0 → 已售罄（真实状态），发消息回滚 Redis 并标记终态
```

**回滚的一致性方向**：Redis 多扣了（<0）要 INCR 回去；Redis 少扣（预扣成功但 DB 拒绝）也要 INCR 还原并把"售罄"标记提前。所有回滚都以 DB 为准——**Redis 是流量视角，DB 是真相视角**（07 篇延迟任务同款原则）。

## 4. 热点库存：分桶打散

单 key 库存是最后一个集中点：1000 件商品的 key 上压着 5000 QPS 有效扣减，单分片 Redis 的单 key DECR 虽快（10 万级），但所有请求路由到同一分片，**分片集群的横向扩容对单 key 无效**（`notes/distributed/05` 的热点 key 问题）。

解法与 `notes/redis/11` 场景题、`notes/distributed/05` 分片思路同构——**库存分桶**：

```text
总库存 1000 → 拆 10 个桶: stock:1001:0 ~ stock:1001:9，每桶 100
扣减: 随机/按 uid hash 选桶 → DECR；该桶 <0 时换桶重试（最多试几个桶）
合并: 某桶提前空不影响其他桶；DB 侧仍按总量条件更新兜底
```

**WHY 桶间不会超卖**：每桶独立 DECR 各自不超卖；DB 层按总库存 `WHERE stock>0` 收口，即使桶的分配不均导致 Redis 总扣减数与真实库存有出入，DB 条件更新保证最终不超。**桶是性能优化，不是正确性来源**——正确性永远在 DB。

代价：售罄判断变模糊（某桶空了但别的桶还有，用户可能多试一次）；桶间调拨需要后台任务。属于典型的"用一点 UX 换一个量级的吞吐"。

## 5. 用户体验与一致性：BASE 的中间态

同步架构里"下单成功"意味着 DB 事务已提交；异步架构里用户点完按钮，订单可能 500ms 后才落库。怎么交代？

**中间态设计**（`notes/distributed/01` 的 BASE 应用语义）：

```text
点击抢购 → Redis 预扣成功 → 返回"抢购资格已锁定，订单生成中"（200 + 排队号）
                         → 前端轮询订单状态（或推送）
MQ 消费落库 → 订单状态: 待支付 → 推送"下单成功，请在 15 分钟内支付"
超时未支付 → 订单取消 + 库存回滚（Redis INCR + DB 加回）
```

**WHY 敢用最终一致**：秒杀的"不超卖"正确性由 DB 兜底保证，而"看到结果"允许几百毫秒延迟——这是一致性与可用性的显式取舍（01 篇 5 问里的第 3 问）。若强一致（同步下单），系统容量被 DB 锁死在 2000 QPS，秒杀场景直接不可用——**CAP 里选了 A，用 BASE 补 UX**。

降级预案（面试加分项）：Redis 全挂 → 降级为"纯 DB 条件更新 + nginx 限流到 2000 QPS"（慢但正确）；MQ 堆积 → 提示"排队人数过多"，消费侧保证幂等不重复下单。

## 6. 面试高频

**Q1：秒杀怎么防止超卖？**
三层：Redis `DECR` 原子预扣挡流量（<0 立即回滚）；MySQL `UPDATE stock=stock-1 WHERE stock>0` 条件更新兜底（行锁串行化，affected=0 即拒绝）；对账任务定时三方比对（Redis/DB/订单数）修复漂移。核心认知：**性能靠 Redis，正确性靠 DB**。

**Q2：为什么 Redis 预扣失败还要 INCR 回滚？**
DECR 到负数说明并发请求超过了余量，多个请求都会看到负值（-1、-2、-3...），每个失败者都必须把自己的那次减法还原，否则余量被虚耗、少卖。回滚后置一个"售罄"标记，后续请求直接短路不进 Redis。

**Q3：MQ 下单消息重复消费怎么办？**
消费幂等：订单表以 (用户, 商品, 场次) 建唯一索引，重复消息 insert 冲突直接 ack 跳过；或消费前查 Redis 去重标记。at-least-once 语义下重复不可避免，**幂等是消费者的义务**（`notes/akafka/02`）。

**Q4：单 key 库存 10 万 QPS 打满一个 Redis 分片怎么办？**
库存分桶：总库存拆 N 个子 key 分散到不同分片（或本地内存预扣），桶内独立 DECR，DB 按总量条件更新收口。桶是吞吐优化，正确性不依赖桶。同构问题：热点账户余额、明星微博计数（`notes/redis/11`）。

**Q5：秒杀链路里 nginx 限流参数怎么配？**
`limit_req zone=seckill burst=100 nodelay`：rate 按下游容量×安全系数（如 Redis 层 1 万 → rate=100r/s 每节点×100 节点）；burst 吸收瞬时毛刺；nodelay 让 burst 内请求立即处理不排队（`notes/nginx/03`）。超量返回 503 + 静态"太火爆"页——在网关层拒绝的请求成本最低。

**Q6：用户下单后多久能看到订单？怎么设计这个等待？**
预扣成功立即返回"资格锁定 + 排队号"，订单异步落库后（通常 <1s）推送/轮询可见。UX 上必须有中间态而不是白屏等待——这是 BASE 的基本素养：中间态可见、收敛时长可控（监控 MQ lag）、失败有补偿路径。
