# 系统设计方法论与估算：4S 框架与必背数字

> **核心认知：** 系统设计面试考察的不是标准答案，是**决策过程**——面试官想看你怎么思考，而不是你背过多少架构图。正确的姿势是：先问需求（5 个关键问题）→ 给一个能跑的简单方案 → 按瓶颈逐级演进 → 每个选型讲清 trade-off → 全程带数字。**没有数字的设计是聊天，有数字的设计才是工程**。「一台 Redis 10 万 QPS」「单表不超 2000 万行」这些数字决定了你的方案在第几层演进时需要拆——它们是所有架构决策的地基。本模块后续 7 篇（秒杀/短链/Feed/IM/分布式ID/延迟任务/缓存）全部用 4S 框架逐题演练。

前置知识：本篇是模块总纲，无前置；后续每篇都会引用本篇的速查表与演进骨架。缓存与队列的细节见 `notes/redis/05`、`notes/akafka/01`。

## 1. 4S 框架：设计一台机器还是一间工厂

系统设计题（"设计一个秒杀系统"）和算法题的本质区别：算法题有唯一解，系统设计题是**在约束下做取舍**。4S 是把混乱的思考过程标准化的脚手架：

| 阶段 | 回答的问题 | 产出 | 时间占比 |
|---|---|---|---|
| **S**cenario 场景 | 系统给谁用？量多大？ | 需求清单 + 量化约束 | 20% |
| **S**torage 存储 | 数据长什么样？放哪？ | 存储选型 + schema 草图 | 25% |
| **S**cale 规模 | 瓶颈在哪？怎么扩？ | 容量估算 + 演进路径 | 40% |
| **S**chema/演进 | 怎么继续变好？ | 分片/多机房/降级预案 | 15% |

**WHY 顺序不能乱**：不先问 QPS 就谈分库分表，是"上来就开药方"；不先定存储模型就谈缓存，是"没病吃药"。面试中 80% 的减分项是跳过 Scenario 直接画架构图——那说明你只会背方案，不会解决问题。

Storage 排第二的原因：数据模型决定一切上层架构。短链是 KV 读多写少（Redis 全量缓存合理）、Feed 是时间线读多写多（推拉结合）、IM 是写多读少且要保序（按会话分片）——存储形态不同，后面所有选型全部不同。这和 `notes/design-pattern/01` 里"先领域模型后实现"是同一个道理。

## 2. 先问再答：5 个必问问题

拿到题目后第一句话不是"我会设计"，而是"我先确认几个约束"。这 5 个问题每个都直接改变方案：

| 问题 | 为什么关键 | 典型分叉 |
|---|---|---|
| **QPS 多少？峰值多少？** | 决定要不要缓存/队列/分片 | 100 QPS 单机搞定；10 万 QPS 必须缓存+横扩 |
| **读写比？** | 读路径和写路径的优化预算完全不同 | 读写 100:1 → 缓存收益巨大；1:1 → 缓存意义小 |
| **一致性要求？** | 强一致和最终一致的架构差一个数量级 | 银行余额强一致（同步复制/读主）；点赞数最终一致（异步合并） |
| **可用性要求？** | 99.9% 和 99.99% 的成本差 10 倍 | 三个 9 允许年停 8.7h；四个 9 只允许 52min → 必须多机房 |
| **数据量多大？增量多快？** | 决定分片时机与 key 设计 | 1 亿行×100B=10GB 单库能扛；千亿行必须分片（`notes/mysql/11`） |

问法示范（秒杀题）："日活多少？峰值秒杀瞬间 QPS 预估多少？库存多少件？允许超卖吗？下单后多久能看到结果？"——最后两问直接决定了用 Redis 预扣还是 DB 条件更新兜底（02 篇详解）。

**面试官不回答怎么办？** 自己给假设并显式声明："假设日活 100 万，按互联网典型分布峰值 QPS 取均值×5..."。有假设的推导过程本身就是得分点。

## 3. 必背数字速查表

所有估算的原料。背不下来就等于没有尺子：

### 3.1 时间量级

| 数值 | 记法 | 用途 |
|---|---|---|
| 1 天 ≈ **10⁵ 秒**（86400） | "一天十万秒" | 日活→QPS 换算 |
| 峰值 = 均值 × **3~10** | 秒杀类取 10，普通业务取 3 | 容量规划 |
| 内存随机访问 ~100ns；SSD 随机读 ~100μs；同机房网络 RTT ~0.5ms | 每级差 1000× | 判断哪层是瓶颈 |
| TCP 连接建立 + TLS 握手 ~ms 级 | — | 为什么长连接（05 篇 IM） |

### 3.2 单机容量红线

| 组件 | 单机容量 | 推论 |
|---|---|---|
| 单机 MySQL 写 | **~2k QPS**（行锁+fsync 决定） | 1 万写 QPS → 至少 5 台分库 |
| 单机 MySQL 读 | ~5k-1w QPS（命中 buffer pool） | 读先走缓存别浪费这层 |
| MySQL 单表 | **<2000 万行**（B+树 3~4 层内） | 超了索引退化，分表（`notes/mysql/11`） |
| 单机 Redis | **~10 万 QPS**（单线程事件循环） | 50 万 QPS → 3 分片 + 客户端分流 |
| 单机 nginx | ~5w 并发连接（epoll） | 限流层够用（`notes/nginx/03`） |
| 千兆网卡 | ~1Gbps ≈ 100MB/s | 大响应体先算带宽 |

### 3.3 存储换算

| 需求 | 算式 | 结论 |
|---|---|---|
| 1 亿条记录×100B | 10⁸×100 = **10GB** | 单库轻松，缓存也能全量进 Redis |
| 10 亿条×1KB | 10⁹×10³ = **1TB** | 必须分库，Redis 只能放热数据 |
| 日增 100 万×1KB | 一年 ~360GB | 一年一拆的节奏 |

**推导链比结论重要**：面试官换个数字（3000 万用户），你要能当场重算，而不是换一张背过的表。

## 4. 通用演进骨架：从单机到多机房

所有题目共用同一条演进路径，每一步都是"当前层顶不住了→加下一层"：

```text
L0  单机 MySQL + 单机应用
     │ 顶不住：读多了
L1  + LB（nginx）+ 无状态应用横扩
     │ 顶不住：DB 读压力
L2  + Redis 缓存（读多写少场景的银弹）
     │ 顶不住：DB 写压力 / 瞬时洪峰
L3  + MQ 削峰异步化（写路径从同步变异步）
     │ 顶不住：单库容量/连接数
L4  + 主从分离（读扩展）→ 分库分表（写+容量扩展）
     │ 顶不住：机房级故障
L5  + 多机房（同城双活→异地多活）
```

**WHY 这个顺序**：每层的成本和复杂度递增，能力也递增——LB 解决"应用层单点"最便宜，先做；多机房解决"机房级故障"最贵（数据跨机房复制，`notes/distributed/05`），最后做。跳级的代价：日活 1 万就上分库分表，是给自己找运维麻烦（跨分片 join/分布式事务全来了，`notes/mysql/11`）。

每层的"顶不住"信号也要会背：LB 层是应用 CPU；缓存层是 DB 读 QPS；MQ 层是写延迟与连接数堆积；分片层是单表行数与磁盘；多机房是可用性指标。

这个骨架在本模块反复出现：秒杀（02）在 L3 的 MQ 上重点展开，Feed（04）在 L2/L4 之间做推拉权衡，IM（05）的难点在 L1 长连接网关的状态化问题。

## 5. 估算实战：两个完整推演

### 5.1 推演一：短链服务的读 QPS（03 篇前菜）

**已知**：日活 1 亿，人均每天点 10 次短链。

```text
日请求 = 10⁸ × 10 = 10⁹（10 亿次/天）
均值 QPS = 10⁹ / 10⁵ 秒 = 10⁴（1 万）
峰值 QPS = 1 万 × 5 = 5 万
Redis 分片 = 5 万 / 10 万 = 1 台（留余量 ×3 → 2 台 + 1 副本）
```

结论：5 万 QPS 的纯读，Redis 两台带副本即可，**根本轮不到分库分表上场**——这就是"先算再选型"的价值，没算之前你可能已经在画 32 个分片的图了。

### 5.2 推演二：IM 消息存储（05 篇前菜）

**已知**：日活 1000 万，人均每天收发 50 条消息，单条消息（含索引）1KB。

```text
日消息量 = 10⁷ × 50 = 5×10⁸（5 亿条）
日增存储 = 5×10⁸ × 1KB = 500GB → 一年 ~180TB
单表行数红线 2000 万 → 5×10⁸/天 ÷ 2×10⁷ ≈ 25 张表/天才不爆
→ 按会话 hash 分 256 张表，每张日增 200 万，10 天到达红线 → 必须按月+会话双维度拆
```

结论：IM 的量决定了"消息表按会话分片 + 冷热分离"是刚需不是优化（05 篇）。

### 5.3 估算的心法

1. **从业务量到技术量**：日活×人均行为=日请求；日请求÷10⁵=均值 QPS；×峰值系数=峰值。
2. **给余量**：所有结论 ×2~3 的安全系数（故障转移时单机要扛双倍流量）。
3. **算带宽**：QPS×响应体大小，别让千兆网卡成为隐形瓶颈。
4. **每步写算式**：面试白板上算式比结论值钱。

## 6. 面试高频

**Q1：系统设计面试你一般怎么开始？**
先问 5 个约束：QPS/峰值、读写比、一致性要求、可用性要求、数据量。没答案就自己给假设并声明。然后给最简单能跑的方案（单体+单库），按瓶颈逐层演进（LB→横扩→缓存→MQ→分片→多机房），每个选型讲 trade-off，全程带数字。

**Q2：为什么单机 MySQL 只有 2000 写 QPS？**
每个写事务要 fsync redo log（~1ms 磁盘）+ 行锁串行化热点行，加上 binlog 双 1 刷新，单机磁盘 IOPS 决定上限。所以写扩展靠分库（每库独立 fsync 并行），不是靠升级机器——磁盘再快也是毫秒级，量变引起不了质变。

**Q3：峰值为什么取均值×3~10？**
互联网流量的日周期性（晚高峰）+ 事件突发性（整点秒杀）。普通业务方差小取 3，秒杀/推热点的重尾分布取 10。本质是给容量规划留余量，具体值应从监控的历史峰值/均值比取，3~10 是没监控时的经验先验。

**Q4：日活 1 亿怎么估 QPS 和存储？**
QPS：假设人均日请求 100 次 → 10¹⁰/天 ÷ 10⁵ 秒 = 10 万均值，峰值 50 万。存储：看单条记录大小，1KB×10¹⁰=10TB/天就离谱了，说明假设错（活跃用户人均行为没那么多），回头修假设。**估算的闭环是检查结果是否反直觉**。

**Q5：你的方案什么时候需要分库分表？**
三个信号任一：单表行数逼近 2000 万（B+ 树变高，索引扫描多一次 IO）；单库磁盘容量吃紧；单库写 QPS 逼近 2000。前两个先考虑归档冷数据（成本低的动作），写瓶颈才是分库的硬理由（`notes/mysql/11`）。
