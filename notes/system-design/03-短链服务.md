# 短链服务：发号器与读路径设计

> **核心认知：** 短链是"读远大于写"的教科书案例——写（生成短链）每天几百万次，读（跳转）每天几十亿次，**读写比 1000:1**。这个比例直接决定了架构的一切：读路径必须全量进缓存（1 亿短链×100B=10GB，Redis 三分片放得下，为什么要让请求碰到 MySQL？），写路径的核心难题只有一个——**发号器怎么选**：自增 base62（简单但连续可枚举）、雪花（无依赖但不保证唯一冲突需处理）、号段双 buffer（美团 Leaf 路线，DB 压力降 1000 倍）、哈希查重（看起来优雅实则暗坑最多）。另一个高频考点 301 vs 302 的选择，本质是"统计需求 vs 缓存效率"的 trade-off。本篇也是 06 篇分布式 ID 的前菜——发号器就是分布式 ID 的一种业务化应用。

前置知识：容量估算（本模块 `01`）、布隆过滤器原理（`notes/redis/05` §穿透）、分片与热点（`notes/distributed/05`）、雪花与时钟（`notes/distributed/06`）。

## 1. 需求与估算：为什么全量缓存是合理的

**Scenario（5 问）**：

| 维度 | 假设 | 数值 |
|---|---|---|
| 量级 | 1 亿条存量短链，日增 100 万 | 写 QPS 均值 ~10，峰值 ~500 |
| 读写比 | 营销场景，每条短链被点 ~1000 次 | 读峰值 **~50 万 QPS** |
| 一致性 | 短链→长链映射不可变（生成后不改） | 读多写少 + 不可变 = 缓存天堂 |
| 可用性 | 跳转服务必须高可用（营销投放花钱了） | 4 个 9 |
| 数据量 | 1 亿×100B（短码+长链+元数据） | **10GB** |

**Storage**：KV 结构（短码→长链），Redis 是天然选型。

**Scale 的关键一算**（01 篇推导链）：

```text
读 50 万 QPS ÷ 单 Redis 10 万 = 5 分片（×2 副本 = 10 台）
存量 10GB ÷ 5 分片 = 每分片 2GB —— 远小于内存压力线
→ 全量缓存可行，读路径理论上可以不碰 MySQL
```

**WHY"全量"而不是 LRU 热缓存**：短链访问有长尾（老营销链接隔几个月还会被点），LRU 会把长尾打成穿透；10GB 的量不值得为省这点内存引入穿透治理。**缓存策略跟着访问分布走**：全量放得下就全量，放不下才谈热度。

## 2. 发号器选型：四种方案对照

短码 = 发号器产出的 ID 做 base62 编码（62⁷ ≈ 3.5 万亿，7 位够用到天荒地老）。

| 方案 | 原理 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **自增 ID + base62** | DB `AUTO_INCREMENT`，63→"01" | 简单、短码有序 | 单点瓶颈；**连续可枚举**（爬虫遍历你的全量链接） | 小规模/内部系统 |
| **雪花** | 时间戳+机器+序列号（`notes/distributed/06`） | 无 DB 依赖、本地生成、趋势递增 | 64 位直接 base62 码长 11 位；时钟回拨要处理 | 已有 ID 基础设施时 |
| **号段双 buffer** | 一次从 DB 取一段（如 1~10000），内存发号，用到 10% 异步取下一段 | DB 压力降 1000 倍；双 buffer 保证切换零抖动 | 重启浪费一段；需要 DB 高可用 | **主流选择**（美团 Leaf） |
| **哈希查重** | MD5(长链) 取前 N 位，冲突重试 | 同一长链短码不变（幂等） | **暗坑最多**：冲突率不可控（生日悖论，1 亿条 7 位码冲突率 ~100%）；可预测 | 一般不选，除非强需求"同链同码" |

**WHY 号段双 buffer 是甜点位**：它把"每个 ID 一次 DB 写"变成"每 1 万个 ID 一次 DB 写"，DB 从 500 QPS 的瓶颈变成 0.05 QPS 的旁观者；双 buffer（当前段用到 10% 就异步加载下一段）让取段耗时完全不在关键路径上——即使 DB 抖动 100ms，发号不中断（06 篇有完整实现）。

**防枚举**：自增/号段的短码连续，可被爬虫 `a→b→c` 遍历。两种治理：①号段起始随机化（每次取段跳到随机区间）；②短码 = ID + 可逆混淆（如 Feistel 网络），遍历短码空间无法映射回连续 ID。**安全属性也是需求的一部分**（01 篇 5 问常被漏掉的一问）。

**同链同码需求**（可选）：若要求同一长链返回同一短码，用 `长链 hash → 短码` 的去重表，新号先查表。注意这是**空间换便利**，去重表本身又要 10GB 级存储——没有免费的午餐。

## 3. 读路径：缓存 + 布隆过滤器挡穿透

```text
请求 t.cn/Ab3xK
  │
  ├─ 布隆过滤器: 该短码存在过吗？──否──→ 404（挡住恶意随机码的穿透）
  │
  ├─ Redis: GET short:Ab3xK ──命中──→ 302 跳转 + 异步计计数
  │
  └─ 未命中（理论不该发生，因全量缓存）──→ 查 MySQL 回填（防御路径）
```

**WHY 全量缓存还要布隆**：全量缓存假设"存量都在"，但扩容/迁移/淘汰窗口、以及**恶意流量故意查随机码**（缓存永不命中，全打到 DB——穿透攻击，`notes/redis/05` §1）。布隆过滤器 1 亿 key 只需 ~120MB（误判率 1%），说不存在的就一定不存在——**用 120MB 内存保护 DB 不被打穿，极其划算**。

布隆误判率公式（面试要会推）：

```text
位数 m、key 数 n、哈希数 k:  误判率 p ≈ (1-e^(-kn/m))^k
最优 k = (m/n)ln2；m = -n·lnp/(ln2)²
1 亿 key、p=1%: m ≈ 1亿×9.6 bit ≈ 9.6 亿 bit ≈ 120MB，k=7
```

**计数异步化**：点击数统计（CTR 结算）不能阻塞跳转——计数先进内存/本地队列，批量聚合后落库（每短链 PV 聚合到分钟级再写）。跳转 P99 控制在 10ms 内。

## 4. 301 vs 302：统计决定协议

| | 301 Moved Permanently | 302 Found |
|---|---|---|
| 语义 | 永久重定向 | 临时重定向 |
| 浏览器行为 | **缓存**后续请求不再问短链服务 | 每次都回短链服务 |
| 统计 | 缓存后计数丢失 | **每次点击都计数** |
| 性能 | 缓存命中后零延迟 | 每次一跳 RTT |

**结论：要统计选 302**（短链的商业价值就是 CTR 数据，301 的缓存让数据残缺）；纯内部跳转、不在乎统计才用 301。这是"协议选型由业务需求驱动"的标准案例——面试答出"看统计需求"这句话，这题就过了。

顺带一提：302 响应头加 `Cache-Control: no-cache` 防中间层代理缓存，否则代理替你"301 化"了。

## 5. 演进与高可用

**写路径 HA**：号段服务双实例（DB 号段表按 biz 打 tag，`UPDATE segment SET max=max+step WHERE biz=?` 的行锁天然防双实例取到同段）；发号是本地内存操作，实例挂了客户端换实例，只浪费当前未用完的段。

**读路径 HA**：Redis 分片 2 副本（哨兵/cluster，`notes/redis/04`）；Redis 整体挂 → 降级直读 MySQL（此时布隆挡住的穿透就体现价值了——DB 只承担合法 key 的回源）。

**扩容路径**：1 亿→10 亿时，Redis 需 100GB → 分片扩到 20+；MySQL 按 short_code hash 分 16 库（此时才引入分片，之前单库够用——**演进时机由 01 篇的数字决定**）。

**与 06 篇的衔接**：号段双 buffer 的完整原理、与雪花/UUID 的工程对比、fencing 语义讨论，在 `notes/system-design/06` 展开——本篇只覆盖"作为短链组件"的选型视角。

## 6. 面试高频

**Q1：短链怎么设计？**
4S：量级 1 亿条、读 50 万 QPS、读写 1000:1、映射不可变。写路径：号段双 buffer 发号器 + base62（7 位）；读路径：布隆过滤器挡穿透 + Redis 全量缓存（10GB/3 分片）+ 302 跳转 + 异步计数。正确性依赖：短码不可变所以缓存无失效问题。

**Q2：发号器为什么选号段而不是雪花/自增？**
自增单点且可枚举；雪花码长 11 位且时钟回拨要处理；号段把 DB 写压降 3 个数量级、双 buffer 消除取段抖动、短码 7 位。若已有全局 ID 基础设施则雪花也行——选型讲 trade-off 不是背答案。

**Q3：布隆过滤器原理？误判率怎么算？**
位数组 + k 个哈希：插入置 k 位，查询 k 位全 1 才"可能存在"，有 0 则"一定不存在"。误判率 p≈(1-e^(-kn/m))^k，最优 k=(m/n)ln2；1% 误判 1 亿 key 约 120MB。**不能删除**（位共享），重建用计数布隆或双布隆滚动。用途：挡穿透、挡缓存击穿的第一道闸。

**Q4：301 和 302 怎么选？**
要点击统计选 302（每次回源可计数），不在乎统计选 301（浏览器缓存，快）。短链的商业本质是 CTR 数据，主流选 302 + no-cache 头。

**Q5：短码会被爬虫枚举怎么办？**
号段随机化起始 + 短码与 ID 可逆混淆（Feistel），或直接用随机短码 + 冲突检测（代价：写入变两步）。安全性与简洁性的取舍，答出"意识到枚举风险"即得分。

**Q6：全量缓存放不下了（10 亿条）怎么办？**
先分片扩容（100GB/20 分片，仍可全量）；再不行转热度缓存 + 布隆（此时布隆的价值从"防攻击"升级为"防穿透主闸"），长尾 miss 回源 MySQL 按 short_code 分片。每一步都是"先算内存账再选策略"。
