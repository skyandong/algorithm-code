# 接口设计模式：io.Reader 生态的启示

> **核心认知：** Go 标准库最伟大的设计不是 GC 也不是 goroutine，而是 **`io.Reader` / `io.Writer` 这对单方法接口**——它们证明了「**小到只有一个方法的接口 + 隐式实现**」能长出多大的生态：文件、网络、内存、压缩、加密、哈希全部无缝互换，`io.Copy` 一个函数连接了它们所有。这就是「接口即协议」的极致：**接口的值不在方法多少，而在它捕捉的抽象是否恰好是问题域的不变量**。学 Go 的接口设计，把 io 包读透就够了——「读什么」比「怎么读」稳定一万倍。

按 Go 1.26 语义说明。前置知识：iface/eface 与动态分发成本见 `notes/golang/03-interface与反射.md`。

## 1. io.Reader/Writer 为什么伟大

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}
```

两个方法，撑起了整个 Go 的 IO 生态：

```go
// 一个函数，永远不用改，连接一切：
io.Copy(dst, src) // 文件→网络、网络→压缩、压缩→哈希、哈希→内存……

// 组合出的复合流（全是「实现 io.Writer 的东西包着另一个 Writer」——03 篇装饰器）：
var w io.Writer = file                          // 磁盘
w = bufio.NewWriter(w)                          // 加缓冲
w = gzip.NewWriter(w)                           // 加压缩
w = multiwriter.New(w, os.Stderr)               // 加分流
w = myTimingWriter{w}                           // 加自定义计时（03 篇模板）

// 读端同理：从任何 Reader 无差别消费
r := strings.NewReader("hello")                 // 内存当文件
r = io.LimitReader(r, 4)                        // 限量
r = bufio.NewReader(r)                          // 缓冲
```

WHY 它能这么大：接口捕捉的抽象是 **「数据流动」这个问题的最小不变量**——无论来源是网卡还是内存，「给我一块 buffer，你还我字节数和错误」永远成立。对比 Java 的 `InputStream` 家族（十几个类、FilterInputStream 继承链），Go 用 1 个方法 + 隐式实现 + 装饰器组合达到了同样的扩展性，还更轻。

**Read 的三个契约**（实现 Reader 的人必须刻在脑子里）：

1. `n < len(p)` 是合法的（哪怕没 EOF）——**绝不假设一次读满**；
2. `n > 0` 时不得同时返回 error（数据优先于错误）；
3. 返回 `(0, nil)` 是允许的死循环陷阱——阻塞实现里别这么干。

这三个契约就是「里氏替换」在 Go 的真实形态：接口语义靠文档约定，实现方必须遵守，否则所有 `io.Copy` 都会坏。

## 2. 单方法接口定律

Go 惯例：**接口方法越少越好，1 个是黄金，3 个是上限**。为什么：

1. **实现成本**：接口每加一个方法，世上就多 N 个实现类要补方法——大接口是给实现方上税；
2. **满足概率**：一个方法 100% 被隐式满足的概率高；五方法接口要求五个全中，可用组合骤减；
3. **拆分无损**：大接口可以拆成小的让消费者按需引用，反之需要侵入修改。

标准库的示范（全是 1-2 方法）：

```go
type Stringer interface{ String() string }        // fmt 家族的通用钩子
type Error interface{ Error() string }             // error 本身就是单方法接口！
type Marshaler interface{ MarshalJSON() ([]byte, error) }
type Handler interface{ ServeHTTP(w, r) }          // 整个 web 生态的根基
type Closer interface{ Close() error }             // 单独存在，就是为了按需约束
```

**error 是单方法接口定律的终极案例**：`type error interface { Error() string }`——Go 最大的「设计模式」藏在语言里，任何有 Error() 方法的类型都是 error，自定义错误结构体、哨兵、包装链（golang 10 篇）全部建立在这个单方法接口上。

需要多方法时怎么办？**组合小接口**：

```go
// io 包的答案：按需组合，而不是造大接口
type ReadWriter interface {
    Reader
    Writer
}
type ReadWriteCloser interface {
    Reader
    Writer
    Closer
}
```

## 3. 接口在消费者侧定义

01 篇 §3 讲过原则，这里讲工程形态。**库作者不定义接口、使用者定义**带来的三个红利：

```go
// 你在写一个业务模块，需要打日志。标准库的 log.Logger 太重，你只要 Log 一条——
type Logger interface {                       // 定义在使用它的包里，不导出
    Log(msg string)
}

func NewProcessor(l Logger) *Processor        // 依赖面：1 个方法
```

红利一：**依赖最小**——调用方传 `*log.Logger`、zap、自定义 stub 都行，只要能 Log。

红利二：**mock 免费**——测试时：

```go
type fakeLogger struct{ msgs []string }
func (f *fakeLogger) Log(m string) { f.msgs = m }   // 3 行搞定，不用 gomock
```

红利三：**库不知道接口存在，永远不会因为接口演化打架**。对比 Java：生产者定义 `ISomethingService`，一次方法签名变更全线下游升级。

什么时候由生产者定义接口？**当接口本身就是产品**——`sort.Interface`、`http.Handler`、`driver.Driver`（database/sql）：你在发布一个「插件协议」，让全世界给你写实现。业务代码 99% 的接口应该在消费者侧。

## 4. 从 stdio 抽象出的接口家族

io 包是一个完整的「接口设计教学模式」——每个接口对应一个**正交的流维度**：

| 接口 | 抽象的不变量 | 正交维度 |
|---|---|---|
| Reader/Writer | 字节流动 | 方向 |
| Closer | 释放资源 | 生命周期 |
| Seeker | 随机定位 | 位置 |
| ReaderAt/WriterAt | 偏移读写（并发安全） | 偏移 |
| Flusher | 强制落盘 | 时机 |

组合出能力分级（消费者按需收窄）：

```go
func SaveFile(r io.Reader)                    // 只需要流
func SaveFileAt(r io.ReaderAt)                // 需要随机读（能传的少了，但能做的多了）
func Process(r io.ReadCloser)                 // 流 + 要负责关闭
func CopyAndClose(dst io.Writer, src io.ReadCloser) error {
    _, err := io.Copy(dst, src)
    if cerr := src.Close(); err == nil {      // 错误处理顺序是模式的一部分
        err = cerr                            // Close 的错误不能吞——写缓冲可能失败在 close 时
    }
    return err
}
```

「需要什么就要求什么」的反面教材：参数声明为 `*os.File`（能读能写能 seek 能关）却只用 Read——依赖面是实际需要的 4 倍，测试必须造真文件。

## 5. 接口设计的四个检查点

给自己的接口做 code review 时过一遍：

1. **超过 3 个方法了吗**——是则拆（按消费者分组）或改结构体；
2. **有只有一个实现、且可预见的未来也只有一个的接口吗**——删除它，直接依赖结构体（08 篇反模式「interface 污染」）；为测试而 mock 不是理由——该测的是**协作方式**，不是实现细节；
3. **接口是动词还是名词**——Go 接口习惯动词/能力命名：`Reader`（能读）、`Closer`（能关）、`Authorizer`（能授权），而 `UserService` 这类名词接口是 Java 思维残留；
4. **文档契约写清了吗**——隐式实现没有编译器帮你检查语义（`Read` 三契约），接口注释是唯一的契约载体。「实现了但语义不对」是隐式接口的暗坑。

## 6. 面试高频

**Q1：io.Reader 为什么是好的接口设计？**
单方法捕捉了「字节流动」的最小不变量，所有 IO 场景（文件/网络/内存/压缩）都满足；隐式实现让生态零成本扩张；配合装饰器组合出复合流。对比 Java InputStream 继承树：1 个方法 + 组合 > 10 个类 + 继承。

**Q2：Go 接口多大合适？**
1 个方法是黄金，3 个是上限。方法多=给实现方上税+满足概率骤减。需要多能力用小接口组合（io.ReadWriter）。接口大小本质是「依赖面大小」。

**Q3：error 是接口吗？说明什么？**
是——`interface { Error() string }`。Go 把最重要的「模式」做成了语言内置的单方法接口：任何类型实现 Error() 即是 error，自定义错误/哨兵/包装链全建立在这上面。单方法接口表达力的极致证明。

**Q4：接口应该由谁定义？**
默认消费者侧（使用它的包里定义、不导出、按需最小方法集）——依赖最小、mock 免费、不因协议演化打架。只有「接口本身是产品」（发布插件协议：http.Handler、sort.Interface、sql driver）时才由生产者定义。

**Q5：Read 实现要遵守什么契约？**
①n<len(p) 合法，调用方不能假设读满；②n>0 不得同时返回 error（数据优先）；③(0,nil) 是死循环陷阱。隐式接口没有编译器查语义——契约靠文档，违反即破坏所有 io.Copy 使用方。这就是 Go 版的里氏替换。
