# 结构型：装饰器、中间件链与代理

> **核心认知：** Go 的结构型模式几乎全部围绕一句话展开——**同一个接口，包一层，做点额外的事**。装饰器（加行为：日志/重试/限流）和代理（管访问：延迟加载/权限/远程调用）在 Java 里是两个 UML 框，在 Go 里是**同一种代码形态**：新类型嵌入或持有旧接口，转发时前后插逻辑。而 HTTP 中间件链 `func(Handler) Handler` 是这个形态的函数版——**类型实现接口 = 对象级装饰，函数签名的自映射 = 函数级装饰**。识别信号：你想给某类调用统一加横切逻辑（日志/计时/重试），却不想改任何业务代码。

按 Go 1.26 语义说明。前置知识：嵌入与方法提升见 `01-设计原则的Go式解读.md` §2。

## 1. 同一种形态：包装并转发

```go
// 万能模板
type Wrapper struct {
    inner Service          // 或嵌入 inner Service（见 §2 对比）
}

func (w *Wrapper) Do(ctx context.Context, req Req) (Resp, error) {
    // ① 前置：日志/校验/限流
    start := time.Now()
    // ② 转发：真正干活
    resp, err := w.inner.Do(ctx, req)
    // ③ 后置：计时/指标/错误加工
    metrics.Observe(time.Since(start), err)
    return resp, err
}
```

调用方拿到的还是 `Service` 接口，完全无感——**这就是「对扩展开放」**（01 篇 §5 的 v3）。net/http 的 `gzipHandler`、grpc 的 `UnaryInterceptor`、database/sql 的 driver 包装、prometheus 的 instrument 中间件，全是这个模板。

## 2. 装饰器：嵌入包装 vs 持有包装

两种写法的唯一区别是**要不要转发全部方法**：

```go
type Service interface {
    Do(ctx context.Context, req Req) (Resp, error)
    Health() bool
}

// 写法 A：嵌入 —— 未覆写的方法自动转发（接口嵌入）
type loggingService struct {
    Service                       // 嵌入接口：借全部方法
}

func (s loggingService) Do(ctx context.Context, req Req) (Resp, error) {
    log.Printf("before Do")       // 只装饰 Do
    return s.Service.Do(ctx, req) // 显式转发被装饰的那个
}
// Health() 不用写——嵌入自动转发。接口加方法，这里自动兼容
```

```go
// 写法 B：持有 —— 每个方法都要手写转发
type retryService struct {
    svc Service
}

func (r *retryService) Do(ctx context.Context, req Req) (Resp, error) {
    // 重试逻辑
}
func (r *retryService) Health() bool { return r.svc.Health() } // 漏写就少个方法
```

选择标准：

| | 嵌入 A | 持有 B |
|---|---|---|
| 装饰部分方法 | ✓（其余自动转发） | 要手写全部转发 |
| 构造时换实现 | 不能（嵌入谁就是谁） | ✓（可注入任意 Service） |
| 接口演化 | 自动跟上新方法 | 新方法漏写直接编译错（好处：强迫你决策） |
| 典型用途 | 日志/指标这类「只加不改」的横切 | 重试/熔断这类要精细控制每个方法的 |

工程建议：**横切逻辑用嵌入（少写转发），需要精细控制或多实现切换用持有**。

装饰器可以叠罗汉——同一接口反复包装：

```go
var svc Service = &realService{}
svc = loggingWrap{svc}   // 最内层先包日志
svc = retryWrap{svc, 3}  // 再包重试（重试调用日志版本）
svc = metricsWrap{svc}
// 调用链：metrics → retry → logging → real
// 顺序即语义：外层看到的是内层包装后的行为
```

## 3. 函数级装饰：中间件链

当「被装饰的东西」是函数而不是对象时，中间件是 Go 生态最成熟的形态：

```go
// 中间件 = 「Handler 的函数」——签名自映射，天然可组合
type Middleware func(http.Handler) http.Handler

func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)                       // 转发
        log.Printf("%s %s %v", r.Method, r.URL.Path, time.Since(start))
    })
}

func Auth(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.Header.Get("Token") == "" {
            http.Error(w, "unauthorized", 401)
            return                                // 拦截：不转发
        }
        next.ServeHTTP(w, r)
    })
}

// 组合器：把一串中间件叠成一个
func Chain(h http.Handler, mws ...Middleware) http.Handler {
    for i := len(mws) - 1; i >= 0; i-- { // 倒序包裹：第一个 mw 在最外层
        h = mws[i](h)
    }
    return h
}

// 使用
mux := http.NewServeMux()
mux.HandleFunc("/api", handler)
http.ListenAndServe(":8080", Chain(mux, Logging, Auth))
// 请求路径：Logging → Auth → handler
```

三个要点：

1. **`http.HandlerFunc(f)` 适配**：普通函数转接口——它本身就是 05 节的适配器模式实例（标准库内置的最小适配器）；
2. **倒序包裹的语义**：Chain 里倒着 for，让**参数顺序 = 执行顺序**（Logging 在最外层先执行）。这是所有中间件框架（chi/echo/gin）的共同约定；
3. **拦截 vs 透传**：中间件可以在 `next.ServeHTTP` 之前 return（请求终结，如 401）——这是对象装饰器做不到的流控（对象版只能加工返回值）。

grpc 的 `UnaryInterceptor`、kratos 的 `middleware.Middleware` 是同构的 RPC 版：签名 `func(ctx, req, handler) (resp, err)`，转发前后插逻辑——**rpc/grpcserver 里的 interceptor.go 就是现成案例**。

## 4. 代理：管访问的三张面孔

代码形态与装饰器相同（同接口 + 转发），意图不同——**装饰器加行为，代理管访问**：

**① 远程代理（RPC stub）**：grpc 生成的 `helloClient` 就是代理——你调本地方法，它跨网络转发到服务端。client.go 里的 `grpc.Dial` 拿到的就是这个东西。

**② 延迟代理（惰性加载）**：

```go
type lazyImage struct {
    once  sync.Once
    path  string
    image decode.Image
}

func (l *lazyImage) Pixels() []Pixel {
    l.once.Do(func() { l.image = decode.FromFile(l.path) }) // 第一次用才解码
    return l.image.Pixels()
}
```

**③ 保护代理（权限/缓存）**：

```go
type protectedRepo struct {
    inner Repo
    role  string
}

func (p *protectedRepo) Delete(id string) error {
    if p.role != "admin" {
        return ErrForbidden   // 访问控制：不转发
    }
    return p.inner.Delete(id)
}
```

面试表述：「代理模式和装饰器在 Go 里代码完全一样——同接口、持内部、转发——**区分它们的只有意图**：装饰器回答『怎么加功能』，代理回答『谁能在什么条件下访问』」。

## 5. 适配器：缝合两个接口

场景：手里有个 `LegacyAuth`（老接口），系统要的是 `Authorizer`（新接口），改老代码代价大：

```go
type LegacyAuth struct{ /* 老代码，不能动 */ }
func (l *LegacyAuth) CheckToken(token string) bool { ... }

type Authorizer interface {
    Authorize(ctx context.Context, token string) (bool, error)
}

// 适配器：小结构体做两边的翻译
type legacyAdapter struct{ *LegacyAuth }

func (a legacyAdapter) Authorize(ctx context.Context, token string) (bool, error) {
    ok := a.CheckToken(token)          // 老接口的输出
    if !ok {
        return false, ErrDenied        // 翻译成新世界的错误
    }
    return true, nil
}

// 客户代码只认 Authorizer，老代码原样存活
var _ Authorizer = legacyAdapter{&LegacyAuth{}}
```

三个细节：

1. **`var _ Authorizer = ...` 编译期断言**：接口实现的静态检查惯用法（不用等到使用处才发现漏了方法）——标准库 `var _ http.Handler = mux` 的用法，值得在每个适配器/装饰器旁写一行；
2. **适配器是新世界和旧世界的边界**：只做翻译（签名/错误/单位的转换），**不夹带业务逻辑**——一旦适配器开始写业务，它就变成没人看得懂的灰色地带；
3. `http.HandlerFunc`、`io.NopCloser`、`sort.Reverse` 都是标准库的微型适配器——一个函数就能完成的「接口翻译」。

## 6. 组合的真实成本

结构型模式不是免费的，叠加前想清楚：

1. **栈深与可读性**：三层装饰 + 四层中间件，一次请求穿 7 层。排查问题时 goroutine 栈里全是转发帧——「日志为什么打了两次」的经典事故是包装顺序错了（同一个装饰器套了两层）；
2. **顺序即语义**：retry 在 timeout 外层 → timeout 触发被当成可重试错误；timeout 在 retry 外层 → 整体时间上限正确。横切件的包裹顺序是**架构决策**，值得一段注释；
3. **错误要小心穿透**：内层装饰器换了错误类型，外层 `errors.Is` 就断了（对照 golang 10 篇 %w 链）。装饰器加工错误必须用 `%w` 包装，保留链。

## 7. 面试高频

**Q1：装饰器模式在 Go 里怎么写？**
新类型实现同一接口，持有（或嵌入）内部实现，转发时前后插逻辑。嵌入版未覆写的方法自动转发（适合日志/指标横切）；持有版全手写（适合精细控制）。可叠罗汉，顺序即语义。

**Q2：Go 的中间件和装饰器什么关系？**
函数级 vs 对象级。中间件 `func(Handler) Handler` 用签名自映射实现组合，且能在转发前拦截（401 短路）——对象装饰器只能加工返回值。Chain 倒序包裹让参数顺序 = 执行顺序。grpc UnaryInterceptor 是 RPC 版同构。

**Q3：装饰器和代理的区别？**
Go 里代码形态一样（同接口+转发），**意图不同**：装饰器加行为（日志/重试/压缩），代理管访问（远程 stub、惰性加载、权限/缓存）。面试考的就是这句意图区分。

**Q4：适配器什么时候用？注意什么？**
接口不兼容又不能改老代码时，用小结构体做翻译（签名/错误/单位）。只翻译不夹业务；旁边写 `var _ Interface = adapter{}` 编译断言。标准库 HttpHandlerFunc/NopCloser/sort.Reverse 是微适配器。

**Q5：装饰器叠加的坑？**
①顺序：retry/timeout 的包裹顺序决定重试是否遵守总时限；②错误链：装饰器加工错误必须 %w，否则外层 errors.Is 断链；③重复包装导致日志打两次、栈变深难排查。
