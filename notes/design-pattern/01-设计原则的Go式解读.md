# 设计原则的 Go 式解读

> **核心认知：** Go 没有 Java 式的类体系（无继承、无构造函数、无注解），所以经典 SOLID 在 Go 里的落地形态完全不同——**里氏替换靠接口契约而非继承层级，开闭靠函数值和新类型而非模板方法，依赖倒置靠「接受接口、返回结构体」这条铁律**。Go 社区的共识：模式不是 UML 图上的框，是「让代码在 6 个月后还能改」的结构决策。判断标准只有一条：**加一个新需求，你要改几处代码**——改 0 处（组合进去）优于加 1 处（扩展点）远优于改 N 处（散弹式修改）。

按 Go 1.26 语义说明。前置知识：接口二元组与方法集见 `notes/golang/03-interface与反射.md`，泛型约束见 `notes/golang/04-泛型.md`。

## 1. SOLID 在 Go 里的真实形态

| 原则 | Java 语境 | Go 语境 |
|---|---|---|
| S 单一职责 | 一个类一个变化原因 | **一个包/文件一个变化原因**；小到函数，大到模块 |
| O 开闭 | 继承 + 模板方法扩展 | **函数值 / 接口参数 / 新类型包装**，旧代码不动 |
| L 里氏替换 | 子类不破坏父类契约 | **接口实现方不破坏接口文档语义**（无继承也要管语义） |
| I 接口隔离 | 小接口，客户端不依赖用不到的方法 | Go 的招牌：「接口在消费者侧定义」（§3），天然隔离 |
| D 依赖倒置 | 抽象工厂注入 | 构造函数收 `io.Writer` 这类**小接口参数** |

S 和 O 的 Go 式要点展开：

**S 的尺度感**：Go 没有 class，职责的载体是包。一个包既做业务计算又做 HTTP 编解码又写 SQL——三个变化原因，就是失职。信号：「这个包为什么会被毫无关联的两批 MR 改动？」

**O 的真身**：Go 里「对扩展开放」几乎总是这三招之一：

```go
// 招式一：函数值当策略（sort.Slice 就是这么设计的）
func Report(rows []Row, format func(Row) string) string

// 招式二：接口参数当插件点
func NewServer(opts ...Option) // 02 篇 functional options

// 招式三：新类型包装旧类型（开闭而不改旧码）
type RetryClient struct{ Client } // 嵌入包装，见 03 篇装饰器
```

## 2. 组合优于继承：Go 最重要的一条

Go 刻意砍掉了继承，只留**嵌入（embedding）**。区别是本质性的：

```go
type Logger struct{ /* ... */ }

// 嵌入：Logger 的方法被「提升」为 Service 的方法，但 this 永远是 Logger 自己
type Service struct {
    Logger          // 不是 is-a，是 has-a + 方法转发
}

// Java 里 Service extends Logger 意味着：Service IS A Logger，可当 Logger 用，可覆写方法
// Go 嵌入意味着：Service HAS A Logger，方法调用被转发给内层实例
```

三条推论（面试可背）：

1. **没有虚函数**：`s.Logger.Info()` 调用的永远是 Logger 的实现——嵌入无法「覆写」，想换行为只能换内层实例（依赖注入），这正是 03 篇装饰器的机制基础；
2. **嵌入是语法糖**：`type A struct{ B }` ≈ `type A struct{ b B }` + 一堆转发方法。用来「借方法」，不能用来「建类型体系」；
3. **多态只有一个来源**：接口。想让 `Report` 接受「任何会 Log 的东西」，就定义接口，而不是造继承树。

经典的「正方形不是长方形」问题在 Go 里天然消失——因为没人能用继承造出「继承自 Rectangle 的 Square 却违反面积契约」的怪胎；但里氏替换的**精神**仍在：你实现 `io.Writer` 就不能写一半返回 nil error（调用方契约破坏）。

## 3. 接受接口，返回结构体

Go 社区流传最广的一条工程格言（Dave Cheney）：

```go
// ✓ 惯用：入口收窄（调用方可以传 *os.File、bytes.Buffer、任何 Writer）
func New(w io.Writer) *Encoder

// ✗ 反面：入口放宽（强迫调用方先构造具体类型；而且接口是结构体时很难判断 nil）
func New(w *bytes.Buffer) *Encoder  // 只认一种写入目标

// ✓ 惯用：出口给具体（调用方拿到全部字段方法，还能按需转接口）
func New(...) *Encoder

// ✗ 反面：出口给接口（调用方想访问字段要断言；mock 自己更难）
func New(...) Writer  // 返回的到底是什么？
```

WHY 出口给结构体：结构体是「实物」，接口是「视角」。实物可以随时被看作任何它满足的视角（隐式实现），反之不行。返回接口等于**替调用方提前做了视角选择**——他要不了别的。

「接口在消费者侧定义」是同一枚硬币的另一面：

```go
// 生产者（库）不需要预定义任何接口——
type StdLogger struct{ /* ... */ }
func (l *StdLogger) Log(msg string) {}

// 消费者按自己的需要定义最小视角——
type logger interface { Log(msg string) } // 单方法，包内私有

func Run(l logger) { l.Log("start") } // StdLogger 隐式满足，无需声明
```

Java 里接口通常由生产者定义（`implements`）；Go 里**谁用谁定义**，生产者甚至不知道接口的存在。这就是 I（接口隔离）的 Go 式自动实现——你的视角只有你用到的方法。

## 4. 耦合的三个层级

改代码的成本由耦合决定。Go 里从坏到好：

1. **数据耦合（最坏）**：两个模块共享同一个全局变量/结构体。改字段名，两处崩；
2. **接口耦合（中间）**：模块间只认方法签名。实现随便换（这就是 mock 的基础）；
3. **无耦合/值耦合（最好）**：数据以**不可变值**流过（channel 传值、纯函数）。上游改内部实现，下游无感。

推论：**依赖注入在 Go 里不需要框架**——构造函数收接口参数就是注入：

```go
// ✗ 隐式全局依赖：NewOrderService 内部写死了 *sql.DB
func NewOrderService() *OrderService { ... sql.Open(...) ... }

// ✓ 显式注入：依赖在签名里可见、可测、可换
func NewOrderService(db OrderRepo, cache Cache) *OrderService
```

Java 的 Spring 扫描注解自动织入；Go 的答案朴素得多：**main.go 手工组装**（或 wire 代码生成）。依赖图摊开在 main 里，谁依赖谁一目了然——「显式优于隐式」这条 Unix 信条的 Go 实践。

## 5. 一个需求演进的对照实验

需求：报表服务输出账单。演进三步，看不同结构的修改成本。

**v1（具体依赖）**：

```go
func Generate(path string) {
    f, _ := os.Create(path)      // 写死文件
    f.WriteString(bill())        // 写死格式
}
```

新需求「输出到网络/输出 JSON」→ **改函数体**（违 O）。文件每多一种目的地就多一个 if——散弹式修改。

**v2（接口参数）**：

```go
func Generate(w io.Writer) {     // 目的地开闭：文件/网络/内存随便传
    io.WriteString(w, bill())
}
```

新需求 → **加调用方**，Generate 零改动。目的地这一维度闭合了，但格式维度还写死。

**v3（双维度开闭）**：

```go
type Formatter interface{ Format(b Bill) []byte }

func Generate(w io.Writer, f Formatter) {
    w.Write(f.Format(bill()))
}
// 未来加 XML：type xmlFormatter struct{} —— 新文件新类型，旧代码不动
```

这就是「改 0 处 > 加 1 处 > 改 N 处」的具象化。实验 01 完整跑通这三步并断言输出一致。

## 6. 面试高频

**Q1：Go 怎么实现多态？没有继承怎么做代码复用？**
多态唯一来源是接口（隐式实现 + 动态分发）。复用靠三个手段：组合/嵌入（借方法不建体系）、函数值（策略注入）、泛型（同算法多类型，见 golang 04 篇）。Go 的立场：继承树是「预测未来」的产物，未来往往预测错。

**Q2：嵌入和继承的区别？**
嵌入是 has-a + 方法转发，is-a 是 Java 的语义。嵌入没有虚函数——`inner.Method()` 永远调内层实现，不能覆写；想换行为换内层实例。嵌入的唯一用途：借一组方法（struct 嵌入 sync.Mutex、嵌入接口做默认实现/拦截）。

**Q3：「接受接口返回结构体」为什么？**
入口收窄：调用方可传任何实现，依赖面最小。出口给实物：结构体可被随时看作接口（隐式满足），反之要断言；返回接口是替调用方锁死视角，还引入 nil 接口 != nil 的坑（golang 03 篇）。

**Q4：依赖注入在 Go 里怎么做？要上框架吗？**
构造函数收接口参数 + main 手工组装。框架（wire/fx）只在依赖图大到手工组装难维护时才有价值。Go 的哲学：显式优于隐式——依赖图摊在 main 里就是最好的文档。

**Q5：开闭原则在 Go 的落地手段？**
三招：函数值当策略（sort.Slice）、接口参数当插件（io.Writer）、新类型包装旧类型（嵌入 + 转发）。判断是否真的 OCP：新需求来时改 0 处（组合）还是加 1 处（新实现新文件），还是改 N 处（散弹修改）。

**Q6：Go 需要singleton吗？**
多数 Java singleton 场景（配置、连接池）在 Go 里就是一个**包级变量**——包本身就是延迟初始化的单例容器（配合 sync.Once 或直接 main 里 init）。不需要 singleton「类」，也就没有它的经典问题（隐藏依赖、测试困难、并发陷阱）。见 02 篇。
