# 反模式清单：Go 代码腐化的十二条路

> **核心认知：** 反模式是「看起来像模式、实际是债务」的结构——它们当初都出于好意（提前抽象、方便测试、对齐 Java 习惯），腐化机制却一致：**为想象中的未来写的代码，维护成本永远大于想象中的收益**。这份清单的价值在 review 时当 checklist 用：每一条都能在真实项目里认出来，认出来的那一刻就值一次 review。共同解药只有一条：**等第二个用例出现再抽象**（Rule of Three），其余都是它的变体。

按 Go 1.26 语义说明。各条目前置知识散见 01-07 篇，文内标注。

## 1. 抽象类（过早抽象）

```go
// 只有一个实现的「BaseService」
type BaseService struct{ /* 公共字段 */ }
type UserService struct{ BaseService }
type OrderService struct{ BaseService }
```

腐化路径：两个服务有 3 个相同字段 → 提 BaseService → 第三个服务只需要其中 1 个字段也被迫全盘继承 → 第四个服务不需要某个字段的行为，开始互相踩。**共性 ≠ 类型层级**——3 个重复字段用组合（各嵌各的小结构体）或干脆重复三次（重复是廉价的，错误抽象是昂贵的）。

解药：Rule of Three——第三次重复出现，且**重复的是行为不只是字段**，再抽。

## 2. 接口污染

```go
// 每个结构体都配一个同名接口（Java 思维的移植）
type UserService interface { Get / Create / Update / Delete / List / Count / Export }
type UserServiceImpl struct{}  // 实现它
```

三个症状判别：**接口和实现一一对应**（I:Impl 命名）；接口方法 > 5 个；**只有一个实现且可预见的未来也只有一个**。这样的接口什么都没换来：不能换实现（没有第二个）、mock 成本没降（还得 mock 一堆方法）、依赖面没变小——只多了一层间接和两个文件。

解药（01 篇 §3）：删接口直接用结构体；要接口，让**消费者**按需定义单方法小接口。

## 3. Singleton 滥用与全局状态

```go
// 到处 GetInstance，依赖完全隐藏
db := database.GetInstance()
cache := cache.GetInstance()
config := config.GetInstance()
func processOrder(o Order) {
    if config.GetInstance().DryRun { ... }   // ← 测试这个函数必须先改全局配置
}
```

症状：单测之间相互污染（改了全局忘了改回）；函数签名说谎（看不出依赖 DB/配置）；并发事故（全局 map 被多处并发写）。

解药（02 篇 §5）：进程级一份的东西用包级变量 + Once 且**只限真正的进程资源**（配置、监控）；业务依赖一律构造函数注入（`NewOrderService(db, cfg)`）——依赖在签名里可见、测试可替换。

## 4. 包循环与上帝包

```go
// user 包 import order 包，order 包也 import user 包 —— 编译器直接拒绝（Go 的保护）
// 于是「聪明」地把两者都依赖的 Person 放进 common 包
// 半年后 common 里有什么？Person、Order、utils.go、helper.go、constants.go、main_test.go...
```

上帝包（common/shared/utils/helpers）是包循环的泄洪道，最终成为「什么都放、谁都能 import」的泥潭——每次改动它都触发全仓库编译。

解药：**依赖方向单向**——业务包 → 基础包，同层互不依赖；共享类型放在「双方都依赖的更底层包」（不是 common，而是有名字的领域包如 `model`）；`go list -deps` / golangci-lint 的 import 边界检查做门禁。

## 5. interface{} 逃生舱

```go
// 类型系统挡路了？塞 any！
func Process(data any) any {
    switch v := data.(type) {   // 万能函数：调用方和实现方都要 type switch
    case int: ...
    case string: ...
    }
}
```

症状：函数签名零信息量；调用方强转 panic；泛型时代还在手写 type switch。

解药：同构处理多类型 → **泛型**（`func Process[T any](v T)`，golang 04 篇）；异构集合（真的混装）才允许 any+断言，且断言必须 comma-ok；「泛型 interface 化」（签名用 any、体内 `.(int)`）比直接写接口还糟，是双倍逃生舱。

## 6. 错误吞咽与二次报告

```go
// 吞咽
_ = cache.Set(k, v)             // 缓存失败静默丢弃？数据不一致的种子
defer file.Close()              // 写场景吞掉 Close 错误 = 丢数据（07 篇 §4）

// 二次报告
log.Error("failed:", err)       // handler 打了
return err                      // 又原样上抛，上层再打一遍 → 告警×N
```

解药（07 篇 §5）：处理或上抛二选一；`_ =` 仅限「失败确实无副作用」（如 metrics 上报）；写文件 `defer` 里收 Close 错误合并返回。

## 7. goroutine 裸奔

```go
go func() {
    for {
        task := <-queue         // ① queue 永远没人关 → 永久泄漏
        handle(task)            // ② panic 没 recover → 进程崩
    }                            // ③ 没有 ctx 检查 → 取消不停
}()
```

解药（06 篇 §1）：启动前回答三问（何时退出/谁 recover/谁等）；标准形态 `select + ctx.Done()`；`go vet` + pprof goroutine profile 定期巡检。

## 8. 锁粒度错配

```go
// 粗粒度：一把大锁罩全业务
type Service struct{ mu sync.Mutex }
func (s *Service) Get()  { s.mu.Lock(); defer s.mu.Unlock(); ...慢操作... }
func (s *Service) Stat() { s.mu.Lock(); defer s.mu.Unlock(); ...另一件慢事... }

// 细粒度陷阱：两把锁嵌套拿且顺序不一
func (s *Service) A() { s.mu1.Lock(); s.mu2.Lock(); ... }
func (s *Service) B() { s.mu2.Lock(); s.mu1.Lock(); ... }   // 死锁
```

解药（golang 07 篇）：锁保护**不变量**不是代码——每条不变量一把锁；临界区内不放 IO/慢操作；多锁固定全局获取顺序（或抽象出锁层级注释）；高竞争读多写少先 benchmark 再上 RWMutex/分片。

## 9. 过度分层

```go
// handler → service → manager → logic → dao → db，每层都是纯转发
func (s *UserService) GetUser(id int) (*User, error) { return s.manager.GetUser(id) }
func (m *UserManager) GetUser(id int) (*User, error) { return m.logic.GetUser(id) }
```

症状：一个字段变更穿透 6 层；一半的层是「调下一个同名方法」；新人不知道逻辑该写在哪层。

解药：层数由**部署边界**决定（同进程内 2-3 层足够：transport / domain / repo）；「加一层解决混乱」多半是把混乱平移；纯转发的层是删除对象。

## 10. init 滥用

```go
func init() {
    db = mustConnect(...)        // main 之前连 DB：失败只能 panic
    config = mustLoad(...)       // 测试跑任何函数都触发全量初始化
    seedData()                   // 副作用藏在 import 里
}
```

症状：`import _ "pkg"` 触发不可见副作用；测试环境必须准备全套外部依赖；初始化顺序依赖包名字典序。

解药（02 篇 §5）：显式初始化函数 `func New() (*Service, error)` 由 main 依次调用；惰性 Once 替代 init；`import _` 只允许注册驱动（database/sql、net/http/pprof 这类真正的「注册协议」）。

## 11. 时间依赖

```go
func isExpired(t time.Time) bool {
    return time.Now().After(t)   // 看不见的依赖：测试结果取决于几点运行
}
```

症状：测试偶发失败（午夜/月末边界）；无法测试「30 天后过期」这类逻辑。

解药：时间从参数注入——`func isExpired(now, t time.Time) bool`；或注入 `clock func() time.Time`（接口/函数值，04 篇策略）；标准库 `testing/fakeclock` 思路。对照：Docker 环境里时间依赖还会撞时区问题（TZ 必须显式设置）。

## 12. 配置散落

```go
const maxRetry = 3                          // 硬编码
os.Getenv("MAX_RETRY")                     // 环境变量直接散读
if v := viper.GetString("max_retry"); ...  // 又一个读取点
```

症状：一个配置项三个定义处；改默认值要全仓库搜索；不知道线上实际生效值。

解药：**配置结构体统一装载**（一个 `Config` 类型 + 一个加载函数 + 一处默认值），02 篇 config 阶梯的运行时形态；热更新走 atomic.Pointer 快照（golang 07 篇）。

## 13. 识别信号总表

Review checklist——左列出现，右列对照：

| 信号（代码味道） | 大概率是 | 药方 |
|---|---|---|
| interface + Impl 一一同名 | 接口污染 | 删接口 / 消费者侧定义 |
| `XxxBase` / `AbstractXxx` | 过早抽象 | Rule of Three，组合替代 |
| `GetInstance()` 出现在函数体内 | 全局状态 | 构造注入 |
| `common`/`utils` 包 > 10 个文件 | 上帝包 | 按领域拆包，单向依赖 |
| `any` 参数 + type switch | interface 逃生舱 | 泛型 / 重定义类型 |
| 同一错误两条日志 | 二次报告 | 只在顶层打 |
| `go func(){ for { <-ch } }()` 无退出 | goroutine 裸奔 | ctx + close 三问 |
| 函数签名 8+ 参数全 bool/int | 配置膨胀 | 02 篇三阶梯 |
| 纯转发的层 | 过度分层 | 删层 |
| `func init()` 里有 IO | init 滥用 | 显式 New + main 组装 |
| `time.Now()` 埋在逻辑深处 | 时间依赖 | 注入 now/clock |
| 每层一个 `fmt.Errorf("%v")` | 错误断链 | %w + 只包一次（07 篇） |

## 面试高频

**Q：说说你见过的 Go 反模式 / 代码腐化信号？**（这题考的就是本篇——挑 3 条讲透优于背 12 条）

推荐组合：**接口污染**（I:Impl 一一对应——Java 思维移植，Go 应该消费者侧小接口）、**过早抽象**（BaseService——错误抽象比重复昂贵，Rule of Three）、**全局状态**（GetInstance——测试相互污染，构造注入替代）。每条给「症状→腐化机制→解药」三段式，最后收在共同解药「等第二个用例出现再抽象」——展示的是判断力不是记忆力。
