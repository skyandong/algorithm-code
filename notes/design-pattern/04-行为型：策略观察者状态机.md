# 行为型：策略、观察者、状态机

> **核心认知：** 行为型模式回答「**逻辑的归属和流转**」。Go 的答案是函数值和 channel 把三种模式全量简化：**策略 = 函数参数**（Java 要建 Strategy 接口 + N 个实现类，Go 传个 `func` 就完了）；**观察者 = channel 广播**（close 语义天然就是「通知所有订阅者退出」）；**状态机 = 显式状态字段 + 转移函数**（Go 没有 enum-backed state，反而逼你把转移写成可测试的纯函数）。识别信号：出现「按类型/条件分派行为」的大 switch、或「一处变化要通知多方」的耦合。

按 Go 1.26 语义说明。前置知识：channel 关闭广播见 `notes/golang/06-Channel内部与nil语义.md`，errgroup 见 `notes/golang/07-sync锁与原子操作.md` §4。

## 1. 策略：函数参数就是策略

Java 版策略（接口 + 实现类）在 Go 里的对照：

```go
// Java: Comparator 接口 + 按名称/按价格/按销量 N 个实现类
// Go: 直接传函数
type Compare func(a, b Item) int

func SortBy(items []Item, cmp Compare) { /* ... */ }

SortBy(items, func(a, b Item) int { return cmp.Compare(a.Price, b.Price) })
```

三个层次的选择：

```go
// 层次一：匿名函数——一次性、局部逻辑
SortBy(items, func(a, b Item) int { return cmp.Compare(a.Price, b.Price) })

// 层次二：命名函数——可复用、可测试、有文档
func byPrice(a, b Item) int { return cmp.Compare(a.Price, b.Price) }

// 层次三：函数类型 + 命名值——当策略本身成为一个领域概念
type EvictPolicy func(m *Cache) *Entry
var (
    LRU  EvictPolicy = lruEvict
    LFU  EvictPolicy = lfuEvict
)
cache := NewCache(WithEvict(LFU))   // 和 02 篇 options 无缝组合
```

标准库标杆：`sort.Slice(data, less)`、`sort.Search(n, f)`、`http.ListenAndServe(addr, handler)`——handler 就是一个策略。**策略接口只在策略需要多个方法或携带状态时才出现**（如 `heap.Interface`：Len/Less/Swap/Push/Pop 五件套，单函数表达不了）。

判据：一个函数够用就传函数；策略需要「一组相关操作」才升级为接口。

## 2. 观察者：channel 与回调的分界

「一处变化，多方感知」的两个 Go 方案：

**方案 A：回调（同步、点对点）**——监听方数量少、事件处理快：

```go
type Subscriber func(event Event)

type EventBus struct {
    mu     sync.RWMutex
    subs   []Subscriber
}

func (b *EventBus) Subscribe(fn Subscriber) {
    b.mu.Lock(); defer b.mu.Unlock()
    b.subs = append(b.subs, fn)
}

func (b *EventBus) Publish(e Event) {
    b.mu.RLock(); defer b.mu.RUnlock()
    for _, fn := range b.subs {
        fn(e) // 同步调用：简单，但一个订阅者 panic 会拖垮发布方（要 recover 包一层）
    }
}
```

**方案 B：channel（异步、解耦）**——监听方是独立 goroutine、消费速度不同：

```go
type Broker struct {
    subs map[chan Event]struct{}
}

// 订阅者各自持有 channel，按自己的速度消费
func (b *Broker) Subscribe() chan Event {
    ch := make(chan Event, 16) // 有缓冲：削峰，满了就阻塞发布方（背压）
    return ch
}

// 广播：一方发送多方收 → 用「每方一个 channel」复制事件
func (b *Broker) Publish(e Event) {
    for ch := range b.subs {
        select {
        case ch <- e:
        default: // 满了丢弃 or 阻塞，按业务定——这是观察者的核心决策点
        }
    }
}
```

工程决策点（面试深挖处）：

1. **满时策略**：阻塞发布方（背压传导到上游）还是丢弃（保实时性丢完整性）？日志/指标可丢，订单事件不可丢——不可丢的应该走 MQ（对照 notes/akafka：Kafka 就是持久化的观察者）；
2. **退出广播**：订阅 goroutine 的退出信号用**同一个 channel 的 close**，还是独立的 done channel？golang 06 篇的结论：close 是广播、发送是单播——`close(ch)` 所有 range 自动结束，这是观察者的「取消订阅」形态；
3. **fan-out 复制成本**：channel 方案每个订阅者一份拷贝，大事件用 `*Event` 指针 + 不可变约定。

## 3. 状态机：把转移写成纯函数

订单/支付/连接管理/熔断器（M4 模块会写）都是状态机。Go 没有 enum，但正好逼出**最佳实践**——转移逻辑写成无副作用的纯函数，全部可单测：

```go
type State string

const (
    StateCreated   State = "created"
    StatePaid      State = "paid"
    StateShipped   State = "shipped"
    StateClosed    State = "closed"
    StateCancelled State = "cancelled"
)

type Event string

const (
    EventPay     Event = "pay"
    EventShip    Event = "ship"
    EventClose   Event = "close"
    EventCancel  Event = "cancel"
)

// 转移表：状态机的全部业务规则集中在一处——加规则只改这张表
var transitions = map[State]map[Event]State{
    StateCreated:   {EventPay: StatePaid, EventCancel: StateCancelled},
    StatePaid:      {EventShip: StateShipped, EventCancel: StateCancelled},
    StateShipped:   {EventClose: StateClosed},
    StateCancelled: {},
    StateClosed:    {},
}

// Next 是纯函数：同输入同输出，不碰库不改字段——单测不用 mock 任何东西
func Next(s State, e Event) (State, error) {
    next, ok := transitions[s][e]
    if !ok {
        return "", fmt.Errorf("invalid transition: %s --%s-->", s, e)
    }
    return next, nil
}

// Order 只负责持状态和并发安全
func (o *Order) Fire(e Event) error {
    o.mu.Lock()
    defer o.mu.Unlock()
    next, err := Next(o.state, e)
    if err != nil {
        return fmt.Errorf("order %s: %w", o.id, err)
    }
    o.state = next
    return nil
}
```

四个要点：

1. **非法转移显式报错**，而不是默认留在原状态——「paid 再 pay」是 bug 信号，吞掉它比报错危险；
2. **转移表 vs if-else 树**：状态 × 事件超过 3×3 就该上表——`if s == Paid && e == Ship {...}` 散落各处是状态机腐化的起点；
3. **纯函数 + 锁分离**：Next 无锁可并发单测；Order.Fire 只管互斥。状态机的「规则」和「执行」分离；
4. **分布式状态机**：Redis 订单状态用 Lua 原子做 check-and-set（对照 notes/redis 07 篇）——本篇的表结构直接搬进 Lua 脚本。

## 4. 命令模式：任务队列的骨架

「把请求封装成对象」——Java 里是为了回放/撤销/排队。Go 里命令就是**一个闭包或小接口**：

```go
// 轻量版：闭包即命令——goroutine 池 / 延迟队列的通用形态
type Task func(ctx context.Context) error

// 重试包装器：命令模式的「加工」用法
func Retry(t Task, n int) Task {
    return func(ctx context.Context) error {
        var err error
        for i := 0; i < n; i++ {
            if err = t(ctx); err == nil {
                return nil
            }
            if ctx.Err() != nil { // 取消优先于重试
                return ctx.Err()
            }
        }
        return fmt.Errorf("after %d retries: %w", n, err)
    }
}

// 队列消费
for task := range taskCh {
    _ = Retry(task, 3)(ctx)
}
```

闭包捕获了「做什么 + 参数」，Task 就是最小命令对象。需要**撤销/审计**等富语义时才升级为接口（`Execute/Undo/Name`）——大多数任务队列（asynq、machinery）的任务定义就是 `func(ctx) error`。

## 5. 模板方法：被组合替代的继承经典

Java 模板方法（父类定骨架 `run()` 调抽象 `step1/step2`，子类填空）在 Go 里**不能用继承做**（不能覆写嵌入方法，见 01 篇 §2），替代方案是**骨架函数收钩子**：

```go
// Java: abstract class Pipeline { run() { validate(); transform(); load(); } }
// Go: 骨架函数 + 函数字段（或接口钩子）

type PipelineHooks struct {
    Validate  func(Record) error
    Transform func(Record) Record
    Load      func([]Record) error
}

// 骨架固定，步骤注入——流程和实现双向解耦
func RunPipeline(rows []Record, h PipelineHooks) error {
    var out []Record
    for _, r := range rows {
        if err := h.Validate(r); err != nil {
            return fmt.Errorf("validate: %w", err)
        }
        out = append(out, h.Transform(r))
    }
    return h.Load(out)
}
```

对比模板方法的实质优势：**骨架也能换**（另一个函数可以有不同流程），而继承版骨架焊死在父类。代价是钩子多时 PipelineHooks 膨胀——那就是 03 篇接口装饰器登场的信号。

## 6. 面试高频

**Q1：策略模式 Go 怎么实现？和 Java 区别？**
Go 传函数值就是策略（sort.Slice 的 less 参数），不需要接口+实现类。三层：匿名函数（一次性）、命名函数（可复用）、函数类型+命名值（领域概念如 EvictPolicy）。只有策略需要一组相关方法时才升级为接口（heap.Interface）。

**Q2：观察者在 Go 里怎么做？channel 满了怎么办？**
回调版（同步、少订阅者、快处理）和 channel 版（异步、订阅方各自消费）。核心决策点是满时策略：阻塞发布方（背压）vs 丢弃（保实时）——不可丢事件走 MQ（Kafka 就是持久化观察者）。退出订阅用 close（广播）而不是发零值。

**Q3：Go 写状态机的最佳实践？**
状态/事件用自定义类型常量；**转移表 map[State]map[Event]State 集中规则**；转移函数写成纯函数（无锁、单测零 mock）；Order 层加锁执行；非法转移显式报错。分布式版把转移表搬进 Redis Lua 原子 check-and-set。

**Q4：命令模式 Go 形态？**
`type Task func(ctx) error` 闭包即命令——任务队列/重试/延迟执行的通用骨架。Retry(task, 3) 就是命令加工（装饰器+命令的合体）。需要撤销/审计才升级为多方法接口。

**Q5：没有继承怎么实现模板方法？**
骨架函数 + 钩子函数（结构体字段或参数）。流程（骨架）和步骤（钩子）双向可换，比继承版更灵活——继承版骨架焊死在父类。这也是「组合优于继承」在行为型上的落点。
