# 架构风格：分层、六边形、CQRS、事件溯源

> **核心认知：** 领域逻辑组织（09 篇的事务脚本/领域模型）决定**函数放哪**，架构风格决定**依赖往哪指、数据怎么流**。这层最重要的洞察只有一句：**六边形、洋葱、整洁架构是同一个思想的四种叫法——依赖只能指向领域，外部世界全是细节**。CQRS 和事件溯源则解决另一个维度的问题：数据形状——写的时候要规范化守不变量，读的时候要反规范化出报表，两边的最优解天然不同。这些风格不是互斥选项，而是按业务复杂度、读写比例、审计需求叠加的组合拳；一开始全上，就是设计期版本的分布式单体。
> **判断标准不变：** 架构风格的价值 = 它替你挡住的那类腐化 × 项目的真实发病率。没病的项目吃药，全是副作用。

按 Go 1.26 语义说明。前置知识：依赖倒置与消费者侧接口见 01 篇，DDD 分层与聚合见 09 篇，读写分离的存储视角见 `notes/system-design/02` 与 `notes/mysql/11`，事件管道见 `notes/akafka/01`。

## 1. 分层架构：默认起点与漏层病

分层是所有人的默认：请求从上往下走，依赖只准向下。09 篇的分层表（接口/应用/领域/基础设施）就是它。分层的真正规则只有一条，但 violations 无处不在：

> **第 N 层只能调用第 N+1 层，不能跳层，不能反向。**

三种漏层病（面试现场画得出才算懂）：

1. **跨层调用**：handler 绕过 service 直接拿 dao——业务规则失去唯一住所，下一个改规则的人不知道要改几处；
2. **模型穿透（最常见）**：数据库的 PO（Persistent Object）一路向上泄漏成 API 响应。表加个 `deleted_at` 字段，前端接口文档莫名多一个字段；改列名，API 契约跟着崩——**存储结构变成了对外的公共接口**；
3. **反向依赖**：领域层 import 了 gorm/sql 驱动——领域被基础设施劫持，单测必须连库。

Go 没有 ArchUnit 这样的架构测试框架，治理靠两条：**包结构把路堵死**（领域包目录里不放任何驱动 import）+ **`go list -deps` 验收**（领域包的依赖闭包里不许出现 sql/http/proto）。

## 2. 六边形：端口与适配器

六边形架构（Hexagonal / Ports & Adapters，Alistair Cockburn）回答分层没回答的问题：**领域层的边界长什么样**。

- **核心（六边形内部）**：领域模型 + 应用服务，零外部依赖；
- **端口（port）**：核心定义的**接口**，分两种——
  - **驱动端口（左）**：核心**实现**、外部调用。`PlaceOrder` 用例接口，HTTP handler 是它的消费者；
  - **被动端口（右）**：核心**定义**、外部实现。`OrderRepository`、消息发送器——09 篇的仓储和防腐层全是它；
- **适配器（adapter）**：端口的具体实现或消费者——MySQL 仓储、内存 stub、HTTP handler、gRPC handler。

```go
// 被动端口：核心定义（09 篇消费者侧接口的直接应用）
type OrderStore interface {
    ByID(ctx context.Context, id string) (*Order, error)
    Save(ctx context.Context, o *Order) error
}

// 核心：只认识端口，不认识 MySQL/内存
type PlaceOrder struct{ store OrderStore }
func (u *PlaceOrder) Exec(ctx context.Context, cmd Cmd) error { /* ... */ }

// 适配器可插拔：生产用 MySQL，测试用 3 行 stub，压测用内存——核心零改动
```

**洋葱（Onion）与整洁（Clean）是它的同心圆重画**：Jeffrey Palermo 的洋葱、Uncle Bob 的整洁架构（entities → use cases → interface adapters → frameworks），圈层名字不同，规则同一条——**源码依赖只准指向内圈，外圈（DB、Web、框架）是可替换细节**。面试说出这层关系就赢了一半：三家吵的不是谁对，是画的图标哪个好记。

验收标准（09 篇说过，这里升级为架构级）：`go list -deps <领域包>` 的输出里看不到任何驱动包；替换存储实现，核心包 diff 为零。

## 3. CQRS：读写分开建模

CQRS（Command Query Responsibility Segregation，命令查询职责分离）的核心观察：**写模型和读模型的最优形状天然相反**。

- 写侧要**规范化 + 不变量**：订单聚合把字段收拢、方法守「总额恒等」，代价是取一个订单要拼聚合；
- 读侧要**反规范化 + 快**：订单列表要的是一行宽表（订单号、买家名、金额、状态），join 都不想做，更别说装配合取聚合。

强行用一个模型伺候两边，结果是：读路径被迫装配合聚合（慢），或写模型被读需求腐蚀（加一堆冗余字段，不变量失守）。

CQRS 按成本分三级，**别直接上最高级**：

| 级别 | 形态 | 代价 |
|---|---|---|
| 轻量 | 同一个库，写走领域方法、读走专用查询函数直接 SQL 出 DTO | 几乎为零，推荐默认 |
| 中量 | 读写分离库/主从，读模型独立演进 | 主从延迟见 mysql/13 |
| 重量 | 独立读存储（ES、Redis、宽表），写后投影同步 | 最终一致性 + 投影维护，system-design/02 秒杀的预扣视图、Feed 的推拉收件箱都是它 |

**判定信号**：同一条数据的读形状和写形状差异显著（写是一个聚合，读是跨多实体的宽表）→ 值得；纯 CRUD 读写同形 → CQRS 是纯开销。CQRS **不要求**事件溯源也不要求消息队列——「读写分开建模」本身是零成本的。

## 4. 事件溯源：存事实不存状态

传统存储存「当前状态」（可覆盖的快照）；事件溯源（Event Sourcing）存**导致状态的全部事实**，状态 = 事件按序重放：

```go
type Event interface{ ApplyTo(*OrderState) }   // 每个事实知道自己怎么改状态

type OrderCreated struct{ ID string }
type ItemAdded   struct{ Name string; Cents int64 }
type OrderPaid   struct{ Cents int64 }

func (e OrderCreated) ApplyTo(s *OrderState) { s.ID, s.Status = e.ID, "pending" }
func (e ItemAdded)   ApplyTo(s *OrderState) { s.Total += e.Cents }
func (e OrderPaid)   ApplyTo(s *OrderState) { s.Status = "paid" }
// replay(events) *OrderState —— 任何时候都能从头算出当前状态
```

好处（都是同一枚硬币的面）：

1. **审计天然完备**：不是「记录了日志」，而是**事实序列就是唯一真相**——状态只是缓存视图，想篡改状态没有入口；
2. **时间旅行**：重放到任意时刻即得任意历史状态，调试「昨晚 3 点它为什么变成这样」是原生能力；
3. **和领域事件零缝隙**：写聚合时攒下的领域事件（09 篇第 7 节）直接成为存储本身，不用再翻译成 UPDATE。

代价（面试必答，答不出代价=没用过）：

1. **重放成本**：事件上了千次，每次读都重放不可行 → **定期快照**（存第 N 号事件时的状态，之后只重放增量）；
2. **模式演进最难**：旧事件的字段语义冻结在历史里，改字段要 upcasting（读旧事件时转换成新版本），比改表列难一个量级；
3. **查询要另建投影**：事件流按聚合组织，跨聚合查询（"所有已支付订单"）必须投到读模型——所以事件溯源几乎总与 CQRS 成对出现。

**和 Kafka 的关系**（本仓 akafka 的视角）：Kafka 的 append-only log + 按 offset 重放就是事件溯源的**存储原语**，但 Kafka 不是事件溯源数据库——它没有「按实体 ID 检索某实体的全部事件」的原生能力，也没法做快照。Kafka 常当事件溯源系统的事件**传输层**，事实存储落专门的库（EventStoreDB）或表。

**判定**：审计合规是硬需求、领域演进复杂、需要时间旅行 → 值得；普通业务 → 传统状态存储 + 审计日志表就够。

## 5. 事件驱动：从进程内到跨进程

事件驱动（EDA）是数据流的第四种形态：组件不直接互调，靠**发布事实**协作。注意它和前几节的嵌套关系：

- 09 篇的**领域事件**是进程内的最小形态（聚合攒事件 → 应用服务发布 → 同进程订阅者）；
- 事件溯源把事件升级为**存储**；
- EDA 把事件升级为**通信**：跨服务发布订阅，生产者不知道消费者是谁。

跨进程后多出一个设计选择（distributed/03 的 Saga 语境）：

- **编排（orchestration）**：一个中央协调者发命令给各服务——流程清晰，但协调者是中心化瓶颈；
- **协同（choreography）**：各服务订阅事件自行反应——松耦合，但流程散落在订阅关系里，不画图没人看得懂全貌。

可靠性问题（事件丢了/重了怎么办）直接对接 distributed/03 的本地消息表与 akafka/02 的消息保障——跨进程事件不再是「攒在聚合里事务后发布」就能保真的，需要 outbox。

## 6. 怎么选：组合决策

四种风格回答四个独立问题，正交可叠加：

| 问题 | 风格 | 默认答案 |
|---|---|---|
| 依赖往哪指 | 分层 → 六边形 | 分层起步，领域被基础设施污染时升级 |
| 读写形状差多大 | 单模型 → CQRS | 同库两模型是零成本默认 |
| 状态怎么存 | 状态表 → 事件溯源 | 状态表 + 审计日志 |
| 组件怎么通信 | 直接调用 → 事件驱动 | 进程内函数调用 |

组合推荐（面试可背）：

- **CRUD 小服务**：分层 + 事务脚本，到此为止；
- **复杂领域长期演进**：DDD 领域模型 + 六边形端口（09 篇全套）；
- **读写悬殊**（秒杀、Feed）：上面任意组合 + CQRS 中/重量级；
- **审计硬需求**（支付、风控、账务）：+ 事件溯源 + 快照；
- **多服务协作**：+ EDA，编排起步、稳定后下沉为协同。

反模式警告：这些风格全是**对腐化的疫苗，不是勋章**。看别人家架构图抄一套全家桶，得到的是分布式单体的设计期版本——每个风格都有维护税，没人交税的疫苗等于白打。

## 7. 面试高频

**Q1：六边形架构和分层架构的区别？**
分层管「垂直切」，六边形管「核心的边界」。六边形把分层里的领域层拿出来当成被保护的核心：核心定义端口（接口），外部世界通过适配器插进来，依赖只准指向核心。可以理解为分层架构 + 严格的依赖倒置 + 显式的可替换边界；分层里的漏层病（PO 穿透、领域 import 驱动）在六边形里是结构性禁止的。

**Q2：洋葱、整洁、六边形什么关系？**
同一个思想的三种叫法：源码依赖只准指向内圈，领域在内、框架数据库 Web 在外、全是可替换细节。区别只在圈层命名（整洁架构四圈：entities/use cases/adapters/frameworks）和叙事情绪。答出「它们在吵谁画的图好记」是加分项。

**Q3：CQRS 是什么？为什么要读写分开？**
命令侧用领域模型守不变量（规范化），查询侧直接出反规范化的 DTO，因为两边最优形状相反：写要聚合完整，读要宽表扁平。分三级落地：同库两模型（零成本默认）→ 读写分离库 → 独立读存储投影。纯 CRUD 读写同形，上 CQRS 是纯开销。

**Q4：CQRS 的代价？**
重量级有最终一致性（读模型落后于写）、投影维护、双模型心智负担。轻量级（同库两套查询函数）几乎没有代价——所以正确问题是「读形状和写形状差多大」，而不是「要不要 CQRS」。

**Q5：事件溯源的优缺点？什么时候不用？**
优点：审计天然完备（事实序列即真相）、时间旅行、与领域事件零缝隙。缺点：重放成本（要快照）、模式演进最困难（旧事件字段冻结，要 upcasting）、查询必须另建投影。审计合规、领域演进复杂才值得；普通业务状态表 + 审计日志足够。

**Q6：事件溯源和审计日志的区别？**
审计日志是状态的旁路记录（可以删、可以漏、和状态不一致也发现不了）；事件溯源里事实序列是唯一真相，状态只是重放出来的缓存视图——想改状态只能追加事实。一个是「记录发生了什么」，一个是「发生过什么决定了什么是」。

**Q7：这些架构风格怎么选？**
四个正交问题四张票：依赖污染了吗（→六边形）、读写形状差多大（→CQRS）、审计/演进需求（→事件溯源）、通信要不要解耦（→EDA）。默认组合是分层+事务脚本，按真实发病率逐项升级；全上全家桶是设计期的分布式单体。
