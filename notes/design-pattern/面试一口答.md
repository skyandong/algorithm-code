# 设计模式面试一口答清单

> 从 01~10 篇笔记提炼的「张口就来」清单：被问到要能不带停顿直接说出来。
> 对应章节：`01-设计原则的Go式解读` ~ `10-架构风格`，实验代码在 `experiments/`。
>
> **记忆主线：** Go 没有类体系，模式全部落在**接口、函数值、组合、channel** 四样东西上。每个模式能说出三段式：Go 形态是什么 → 标准库谁在用 → 什么时候不该用。

---

## 一、原则与组合（01）

### 1. Go 怎么实现多态和复用？
多态唯一来源是接口（隐式实现）。复用三手段：组合/嵌入（借方法不建体系）、函数值（策略注入）、泛型（同算法多类型）。Go 砍继承的理由：继承树是预测未来，未来往往预测错。

### 2. 嵌入和继承的区别？
嵌入 = has-a + 方法转发，没有虚函数——inner.Method() 永远调内层实现，不能覆写；换行为 = 换内层实例（依赖注入）。嵌入唯一用途是借方法，不是建类型体系。

### 3. 「接受接口返回结构体」为什么？
入口收窄：调用方可传任何实现，依赖面最小。出口给实物：结构体可随时被看作接口（隐式满足），返回接口是替调用方锁死视角，还有 nil 接口陷阱。

### 4. 接口应该由谁定义？
消费者侧：使用它的包里定义、不导出、单方法最小集——依赖最小、mock 免费（3 行 stub）、不因协议演化打架。只有「接口本身是产品」（http.Handler、sort.Interface、sql driver）才由生产者定义。

### 5. 依赖注入要上框架吗？
不需要。构造函数收接口参数 + main 手工组装就是 Go 的 DI——依赖图摊开在 main 里，显式优于隐式。wire/fx 只在依赖图大到手工难维护时才有价值。

## 二、创建型（02）

### 6. functional options 解决什么？
Go 无重载/无默认值下的参数膨胀：`NewServer(opts ...Option)`，Option 是 `func(*options)` 闭包。默认值集中、调用自文档（WithTimeout(3s)）、加配置不破坏调用方。gRPC/kitex 都在用。

### 7. 三阶梯怎么选？
≤5 参数且零值即默认 → config 结构体；可选参数多/需区分没填和填零/要热更新通道 → options（内部指针字段）；多步有序组装+终点校验 → Builder。options 是无序平面覆写，builder 是有序组装——本质区别。

### 8. Go 怎么写单例？
包级变量 + sync.Once 惰性初始化——包本身就是单例容器。不用 init()：它无法传参、无法优雅失败、时机不可控。Once.Do 返回即完成（happens-before），并发安全。单例的测试困难仍在，业务依赖还是构造注入。

## 三、结构型（03）

### 9. 装饰器 Go 怎么写？
新类型实现同一接口，持有或嵌入内部实现，转发时前后插逻辑。嵌入版未覆写方法自动转发（适合日志/指标横切）；持有版手写全部转发（适合精细控制）。可叠罗汉，顺序即语义。

### 10. 中间件和装饰器的关系？
函数级 vs 对象级。`func(Handler) Handler` 签名自映射可组合；能在转发前拦截（401 短路）——对象装饰器只能加工返回值。Chain 倒序包裹让参数顺序=执行顺序。grpc UnaryInterceptor 是 RPC 同构。

### 11. 装饰器和代理的区别？
代码形态完全一样（同接口+转发），**意图不同**：装饰器加行为（日志/重试/压缩），代理管访问（远程 stub/惰性加载/权限缓存）。面试考的就是这句意图区分。

### 12. 适配器注意什么？
只做翻译（签名/错误/单位），不夹业务逻辑——夹了业务就是灰色地带。旁边写 `var _ Interface = adapter{}` 编译期断言。HttpHandlerFunc/NopCloser/sort.Reverse 是标准库微适配器。

## 四、行为型（04）

### 13. 策略模式 Go 形态？
传函数值就是策略（sort.Slice 的 less）。三层：匿名函数（一次性）、命名函数（可复用）、函数类型+命名值（领域概念如 EvictPolicy）。策略需要一组相关方法才升级为接口（heap.Interface）。

### 14. 观察者两方案？
回调版（同步、少订阅者、快处理——注意 panic 要 recover 包住）；channel 版（异步、各自消费速度——核心决策是满时策略：阻塞背压 vs 丢弃）。不可丢事件走 MQ——Kafka 就是持久化观察者。退出订阅用 close（广播）。

### 15. Go 状态机最佳实践？
自定义类型常量 + **转移表 map[State]map[Event]State 集中规则** + Next 纯函数（无锁单测零 mock）+ Order 层加锁执行 + 非法转移显式报错。分布式版把转移表搬进 Redis Lua 原子 check-and-set。

### 16. 没有继承怎么做模板方法？
骨架函数 + 钩子函数（结构体字段或参数）：`RunPipeline(rows, hooks)`。流程和步骤双向可换——继承版骨架焊死在父类，组合版连骨架都能换。

## 五、接口设计（05）

### 17. io.Reader 为什么是好设计？
单方法捕捉「字节流动」的最小不变量，文件/网络/内存/压缩全部满足；隐式实现生态零成本扩张；配装饰器组合出复合流。1 个方法+组合 > Java 的 10 个类+继承树。

### 18. 接口多大合适？
1 个方法是黄金，3 个是上限。方法多 = 给实现方上税 + 满足概率骤减。多能力用小接口组合（io.ReadWriter）。**error 本身就是单方法接口**——Go 最大的模式藏在语言里。

### 19. Read 的三条契约？
①n<len(p) 合法，调用方不假设读满；②n>0 不得同时返回 error（数据优先）；③(0,nil) 是死循环陷阱。隐式接口没有编译器查语义——契约靠文档，这就是 Go 版里氏替换。

## 六、并发模式（06）

### 20. goroutine 启动前三问？
何时退出（ctx/上游关闭）、谁 recover panic（入口 defer）、谁等它（WaitGroup/errgroup）。三问没有答案的 goroutine 迟早泄漏。

### 21. pipeline 的关闭规则？
发送方负责关闭；每阶段 defer close 自己的输出；fan-in 用 WaitGroup 等全部输入枯竭后关总输出——多路合流唯一正确的关灯方式。

### 22. errgroup 好在哪？
一次解决三件事：Wait 返回首个 error（收集）、任一任务出错自动 cancel 派生 ctx（传播）、SetLimit 并发上限。裸 WaitGroup 要手工加锁存 error + 手动 WithCancel。局限：不替你 recover panic。

### 23. worker pool 和信号量怎么选？
一次性批次 → SetLimit/缓冲 channel；持续任务流（MQ 消费、请求处理）→ 长生命周期 worker pool 固定 N 个 worker 反复取活。进程内限流用信号量，跨进程用 rate.Limiter/Redis。

## 七、错误处理（07）

### 24. 错误三分法？
哨兵（包级 var，errors.New，Is 判「哪种错」）、结构化类型（As 取字段）、即时包装（fmt.Errorf 动词+实体+参数加语境）。选择看调用方：要分支给哨兵、要数据给类型、只排障就包装。

### 25. 为什么错误只处理一次？
三层各打日志 = 告警翻倍 + 栈混乱（以为是三个 bug）。中间层只加语境上抛零日志；顶层打唯一一次（错误+请求上下文）并定对外语义。例外：边界回执（DLQ/RPC 返回）是最终归宿。

### 26. 什么错误可重试？
判临时性（net.Error.Timeout()）而不是猜类型。三前提：幂等（非幂等写带幂等键）、上限+指数退避+抖动、**Canceled 绝不重试**（方向信号不是失败）。

## 八、反模式（08）

### 27. 常见 Go 反模式？（挑三条讲透）
**接口污染**：I:Impl 一一同名——Java 思维移植；Go 应消费者侧小接口或直接结构体。**过早抽象**：BaseService——错误抽象比重复昂贵，Rule of Three。**全局状态**：GetInstance 散落函数体——测试相互污染；构造注入。

### 28. 共同解药是什么？
等第二个用例出现再抽象（Rule of Three 及其一切变体）。反模式的腐化机制一致：为想象中的未来写的代码，维护成本永远大于想象中的收益。

## 九、DDD（09）

### 29. DDD 和设计模式什么关系？
层次不同：原则管评判（什么是好）、模式管解法（怎么写）、DDD 管边界（切在哪）。战略设计用通用语言+限界上下文划边界，战术设计用实体/值对象/聚合守不变量；落地时借设计模式——防腐层用适配器、仓储用消费者侧接口。

### 30. 贫血模型为什么不好？什么时候贫血反而对？
实体只剩字段，不变量散落在 N 个 service 里靠自觉维护——Total 任何代码都能改坏；业务规则读代码读不出来。解药是充血。但 CRUD 场景没有不变量要守，贫血 + 事务脚本（handler-service-dao，Fowler 三档之一）就是最优解——贫血的骂名来自「拿事务脚本的架构干领域模型的活」。

### 31. 实体和值对象怎么分？聚合根三铁律？
实体有身份（属性变了还是它），值对象只有值（全等即相等、不可变、改值换新）。聚合根：外部只引用根、跨聚合只存 ID、一个事务只改一个聚合；聚合按不变量切不按表切，聚合间一致性靠领域事件 + Saga。升级信号：同一规则漂移 3 处、状态机长 if-else、并发靠改前再查。

### 32. 领域事件和防腐层各自解决什么？
事件：聚合间解耦（发 OrderPaid，库存/积分各自订阅互不知晓）+ 业务留痕；先攒在聚合里，持久化成功后才发布。防腐层：在上下文边界把外部模型翻译成本地通用语言，外部字段渗透一次领域就脏一片。

## 十、架构风格（10）

### 33. 六边形和分层架构的区别？
分层管垂直切，六边形管核心的边界：核心定义端口（接口），外部通过适配器插进来，依赖只准指向核心。等于分层 + 严格依赖倒置 + 显式可替换边界；PO 穿透、领域 import 驱动这类漏层病在六边形里结构性禁止。验收：`go list -deps` 领域包看不到驱动。

### 34. 洋葱、整洁、六边形什么关系？
同一个思想三种叫法：源码依赖只准指向内圈，领域在内、DB/Web/框架在外全是可替换细节。区别只在圈层命名（整洁四圈：entities/use cases/adapters/frameworks）。它们吵的不是谁对，是画的图标哪个好记。

### 35. CQRS 是什么？代价是什么？
写模型规范化守不变量，读模型反规范化出 DTO——两边最优形状天然相反。分三级：同库两模型（零成本默认）→ 读写分离库 → 独立读存储投影。重量级代价：最终一致性、投影维护、双模型心智；判据是读写形状差多大，纯 CRUD 同形别分。

### 36. 事件溯源的优缺点？和审计日志的区别？
优点：审计天然完备（事实序列即真相）、时间旅行、与领域事件零缝隙。缺点：重放成本（要快照）、模式演进最难（旧事件字段冻结要 upcasting）、查询要另建投影。审计日志是状态的旁路记录（可删可漏）；事件溯源里状态只是重放出来的缓存视图，想改状态只能追加事实。Kafka 的 log 是它的存储原语，但不是事件溯源数据库。

## 考前 60 秒主线串讲

**原则**：组合优于继承（嵌入无虚函数）→ 接受接口返回结构体 → 消费者侧定义接口 → 依赖注入就是构造函数收参数。
**创建**：config → options（WithXxx 闭包+默认值集中）→ Builder（有序组装终点校验）→ 单例 = 包变量+Once。
**结构**：装饰器 = 同接口包一层（嵌入自动转发/持有精细控制）→ 中间件 = 函数级+可拦截 → 代理 = 同代码不同意图 → 适配器只翻译+编译断言。
**行为**：策略 = 函数值 → 观察者 = channel+满时策略 → 状态机 = 转移表+纯函数 → 命令 = 闭包 Task。
**接口**：单方法黄金 → io.Reader 生态 → error 即接口 → Read 三契约。
**并发**：三问 → pipeline 关灯规则 → fan-in 等齐 → errgroup 三合一 → 信号量/池。
**错误**：三分法 → 语境公式 → 只处理一次 → Canceled 不重试。
**反模式**：I:Impl / GetInstance / common 包 / any 转义 / init 滥用——解药都是 Rule of Three。
**DDD**：贫血三症状 → 实体/值对象（身份判据）→ 聚合根三铁律 → 事件攒聚合提交后发 → 防腐层翻译外部模型 → 层次口诀（规则进实体/流程进应用/跨聚合进领域服务）。
**架构风格**：漏层病（PO 穿透）→ 六边形=洋葱=整洁（依赖指向领域）→ CQRS 三级（读写形状差）→ 事件溯源（事实即真相+快照）→ 组合按发病率，全家桶是设计期分布式单体。
