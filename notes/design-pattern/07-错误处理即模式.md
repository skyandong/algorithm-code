# 错误处理即模式：三分法与包装链

> **核心认知：** Go 社区把「怎么处理错误」沉淀成了明确的模式语言：**哨兵（这是哪种错）→ 包装（发生在哪、当时在干什么）→ 判定（Is/As 沿链找）**。三分法决定「创建什么错误」，`%w` 链决定「错误怎么流动」，一个约束贯穿始终——**错误只处理一次**：要么处理掉，要么带着上下文上抛，绝不在中间层反复打日志。这套模式和 07 篇的并发模式一样，是「代码能不能运维」的分水岭——线上排障时，你读到的第一行错误文本决定了要花 5 分钟还是 5 小时。

按 Go 1.26 语义说明。本篇是 `notes/golang/10-context与错误处理.md` §5-§6 的模式化收口，底层机制（%w/Is/As/Join 的树遍历）以该篇为准。

## 1. 三分法：三种错误创建形态

写 `return err` 之前先问：这个错误要被调用方**怎么用**？

```go
// 形态一：哨兵错误（sentinel）——「这是哪种错」
// 用于：调用方要按类型分支处理（重试/忽略/换路）
var (
    ErrNotFound   = errors.New("not found")
    ErrForbidden  = errors.New("forbidden")
)

// 形态二：结构化错误类型——「错在哪、相关数据是什么」
// 用于：调用方要取字段做逻辑（哪个字段校验失败、DB 冲突键是什么）
type ValidationError struct {
    Field string
    Rule  string
}
func (e *ValidationError) Error() string { return e.Field + ": " + e.Rule }

// 形态三：即时包装——「当时在干什么」
// 用于：中间层给错误加语境，不改类型（判定仍可穿透到根因）
if err := saveOrder(o); err != nil {
    return fmt.Errorf("save order %s: %w", o.ID, err)
}
```

选择判据一张表：

| 调用方需要 | 创建形态 | 判定方式 |
|---|---|---|
| 「是不是 X 错」 | 哨兵（包级 var，导出） | `errors.Is` |
| 「错的细节字段」 | 结构化类型 | `errors.As` 取出 |
| 只看日志排障 | 即时 `fmt.Errorf("...: %w")` | 不判定，读文本 |

哨兵的两条纪律：**少而精**（一个包 2-4 个哨兵，每个都有明确的调用方分支；20 个哨兵=没人记得住）；**文案稳定**（哨兵文本一旦发布就是 API——改了等于破坏所有做字符串比较的下游）。

## 2. 包装的语境公式

中间层包装错误的固定句式——**动词 + 实体 + 参数**：

```go
// ✗ 没有语境：调用方拿到错误不知道哪一步、哪个对象
return err

// ✗ 语境无效：和代码行号一样，等下就过时
return fmt.Errorf("line 42 error: %w", err)   // 行号会变；而且 %w 都用对了，语境却没用

// ✓ 动词（在做什么）+ 实体（对谁）+ 参数（哪个）：
return fmt.Errorf("load user %d: %w", uid, err)
// 读日志的人 0.5 秒定位：加载用户 123 的时候挂的，根因在链下游
```

语境是给**未来的自己**的：三个月后凌晨被告警叫醒，`"open db: connection refused"` 和裸 `err` 的差距就是排障时间。这不是编码风格问题，是可运维性问题。

升级语境：跨层时可以把底层错误翻译成领域错误，但**必须保留链**：

```go
// 数据层 → 业务层：把 sql 的 ErrNoRows 翻译成领域哨兵，同时留链
if errors.Is(err, sql.ErrNoRows) {
    return fmt.Errorf("order %s: %w", id, ErrNotFound)  // 双层：哨兵 + 语境
}
```

## 3. 判定模式：调用方的三分支

收到错误的调用方，标准处理是三分支——**处理、判定后分支、上抛**：

```go
err := svc.CreateOrder(o)
switch {
case err == nil:
    // 分支 1：成功——正常流

case errors.Is(err, ErrForbidden):
    return 403Resp         // 分支 2a：哨兵 → 有既定处理

case errors.Is(err, context.DeadlineExceeded):
    retry(o)               // 分支 2b：可重试错误 → 策略（04 篇）

default:
    // 分支 3：不认识的错误——判定要不要拆开看
    var v *ValidationError
    if errors.As(err, &v) {
        return 400Resp(v.Field)   // 结构化：取字段
    }
    log.Errorf("create order: %+v", err)  // 兜底：带 %w 链的文本足够排障
    return 500Resp
}
```

三分支的本质是**错误分类器**：Is 判「种类」，As 判「取据」，兜底交给日志。写不出分支 2 的错误（没有任何调用方关心它是什么）就不该存在——这是哨兵「少而精」的反向验证。

## 4. 临时性错误与重试的边界

重试决策要回答「这个错误会不会自己好」——**不要用错误类型硬猜**，用接口判定临时性：

```go
// net.Error 的 Timeout() 是「临时性」的官方信号之一
var netErr net.Error
if errors.As(err, &netErr) && netErr.Timeout() {
    // 超时：大概率可重试
}

// context 错误是方向信号，不是失败：
//   DeadlineExceeded —— 超时（上游设的时限到了，重试要看哪个 ctx 超的）
//   Canceled        —— 主动取消（用户跑了/上游放弃了：绝不重试，直接返回）

// 连接拒绝 vs 连接重置：前者可能服务没起（重试无意义，先告警），后者可能瞬时抖动
```

工程判断三原则：

1. **重试幂等前提**：非幂等写（下单）重试前必须带幂等键（对照 notes/redis 08 篇分布式锁 + 幂等设计）；
2. **重试要有上限和退避**：无限重试 = 把故障放大成雪崩；`Retry(t, 3)` 的指数退避 + 抖动（jitter）是标准姿势（04 篇命令模式的 Retry 可作骨架，system-design 模块秒杀篇会展开）；
3. **Canceled 一律上抛**：把取消当错误重试是 goroutine 卡死不退出的经典来源（golang 10 篇 Q：ctx 取消后 CPU 循环不停）。

## 5. 错误只处理一次

反模式排行第一：**同一条错误链在三层各打一次日志**——

```go
// ✗ 三层各打一次：告警群里同一事件三条（栈还各不相同），排障时怀疑是三个 bug
func handler() { log.Error(err) ; return err }   // 第一遍
func service()  { log.Error(err) ; return err }  // 第二遍
func repo()     { log.Error(err) ; return err }  // 第三遍
```

正确姿势：**处理和上抛二选一**——

```go
// 中间层：只加语境上抛，不打日志
func service() error {
    if err := repo.Save(o); err != nil {
        return fmt.Errorf("order %s: %w", o.ID, err)  // 无日志
    }
    return nil
}

// 顶层（handler / 消费循环）：打一次、打全——错误 + 请求上下文 + 决定对外语义
func handler() {
    if err := service(); err != nil {
        log.Errorf("create order failed: req=%+v err=%+v", req, err)  // 唯一一次
        var v *ValidationError
        switch {
        case errors.Is(err, ErrForbidden): respond(403)
        case errors.As(err, &v):           respond(400, v.Field)
        default:                           respond(500)
        }
    }
}
```

「一次」的例外：**边界回执处**必须记录（消息队列消费失败写 DLQ、RPC 返回前上报）——那是错误的最终归宿，不算重复。

## 6. API 错误码映射

Web/RPC 服务的错误出口是**错误码**——把三分法和传输协议接起来：

```go
// 内部错误 → HTTP 状态码的映射表：集中一处，别散在 handler 里
func httpStatus(err error) int {
    var v *ValidationError
    switch {
    case errors.Is(err, ErrNotFound):  return 404
    case errors.Is(err, ErrForbidden): return 403
    case errors.Is(err, context.DeadlineExceeded): return 504
    case errors.As(err, &v):           return 400
    default:                           return 500
    }
}

// 反向：解析外部错误（调用下游后）转成自己的领域错误
// grpc: status.FromError(err) → code 对应表
// 语义铁律：400 类是客户端的错（带原因，可修正）；500 类是自己的错（隐藏细节，记日志）
```

grpc 版本见 `rpc/grpcserver` 的 status.WithDetails——`InvalidArgument` 携带结构化 detail，客户端 `errors.As` 取出，正是本篇三分法在 RPC 协议上的完整实现。

## 7. 面试高频

**Q1：Go 错误处理的三种创建形态？**
哨兵（errors.New 包级 var，Is 判「是哪种错」）、结构化类型（As 取字段）、即时包装（fmt.Errorf+动词实体参数加语境）。选择看调用方：要分支给哨兵、要数据给类型、只排障就包装。

**Q2：包装错误的语境怎么写？**
动词+实体+参数（`load user %d: %w`）。不写行号（会过时）、不裸 return err（没语境）。翻译领域错误时保留 %w 链（ErrNoRows → ErrNotFound 双层包装）。

**Q3：为什么「错误只处理一次」？中间层做什么？**
三层各打一次日志 = 告警翻倍 + 栈混乱。中间层只加语境上抛零日志；顶层打唯一一次（错误+请求上下文）并决定对外语义。例外：边界回执（DLQ/RPC 返回）是最终归宿。

**Q4：什么错误可以重试？**
判临时性（net.Error.Timeout）而不是猜类型；幂等前提（非幂等写带幂等键）；上限+指数退避+抖动。Canceled 绝不重试（方向信号，不是失败）；DeadlineExceeded 看哪个 ctx 超的。

**Q5：错误码映射怎么做？**
集中一张表：哨兵/类型 → HTTP 状态/grpc code。400 类（客户端错）带原因可修正，500 类（自己错）隐藏细节记日志。grpc 的 status.WithDetails 是结构化版本，errors.As 解包——三分法的协议实现。
