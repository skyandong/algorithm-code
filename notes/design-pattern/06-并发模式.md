# 并发模式：pipeline、fan-in、errgroup、semaphore

> **核心认知：** Go 并发模式解决的问题只有一个——**goroutine 的生命周期管理**：谁启动、谁等待、错了怎么办、怎么停。四个基础件覆盖 90% 场景：**pipeline**（生产消费成链）、**fan-out/fan-in**（分摊与汇总）、**errgroup**（等齐 + 错误传播 + 取消，sync.WaitGroup 的生产级替代）、**semaphore**（并发上限）。设计铁律一条：**每个 goroutine 都要有明确的退出条件**（Dave Cheney：never start a goroutine without knowing how it will stop）——违反它的代码迟早泄漏。所有模式都建立在一个原语语义上：**channel 关闭是广播**（golang 06 篇）。

按 Go 1.26 语义说明。前置知识：channel 六组合、select、errgroup 协议见 `notes/golang/06`、`07` 两篇；goroutine 泄漏三大来源见 `notes/golang/12-面试题集`。

## 1. 生命周期：一切模式的地基

启动一个 goroutine 前，三个问题必须有答案：

```go
go func() {
    // ① 它什么时候退出？（任务完成？channel 关闭？ctx 取消？）
    // ② 它 panic 了谁负责？（入口 defer recover——子 goroutine panic 拖垮整个进程）
    // ③ 谁在等它/观察它？（WaitGroup/errgroup/统计监控）
}()
```

**每个 goroutine 的标准形态**（背下来）：

```go
func worker(ctx context.Context, in <-chan Task, out chan<- Result) {
    defer close(out)                    // 产线 goroutine：自己负责关自己的输出
    defer recoverLog("worker")          // panic 兜底：recover + 带栈日志
    for {
        select {
        case <-ctx.Done():              // 退出条件 1：全局取消
            return
        case t, ok := <-in:             // 退出条件 2：上游关闭
            if !ok {
                return
            }
            out <- process(ctx, t)       // process 内部也要检查 ctx（协作式取消）
        }
    }
}
```

两个方向的责任约定（Go 官方博客 Pipelines 的规矩）**

- **发送方关闭** channel（接收方关闭会和发送竞争，panic）；
- **每个阶段自己 close 自己的输出**——下游靠 `ok=false` 知道上游枯竭。

## 2. pipeline：阶段性流式处理

```go
// gen：源头。返回只读 channel，内部 goroutine 生产完关闭
func gen(ctx context.Context, nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            select {
            case out <- n:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}

// square：中间阶段。输入输出都是 channel，形态统一就能无限串联
func square(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {             // 上游 close 后 range 自动结束
            select {
            case out <- n * n:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}

// 串联：数据在 goroutine 之间流动，每个阶段一个独立并发单元
for v := range square(ctx, square(ctx, gen(ctx, 2, 3, 5))) {
    fmt.Println(v) // 16, 81, 625
}
```

三个设计价值：

1. **流式**：不攒全量数据——100GB 文件逐块过管道，内存恒定（对照 golang 09 篇的 GC 压力）；
2. **阶段并行**：gen 生产第 3 个时，第一个 square 已在处理第 2 个——吞吐取决于最慢阶段；
3. **形态统一**：每个阶段 `chan A -> chan B`，可任意重排组合——这就是函数式组合的并发版。

## 3. fan-out / fan-in：并行分摊与汇总

pipeline 的瓶颈阶段（最慢的那节）复制 N 份分摊，结果汇回一条：

```go
// fan-out：同一输入 channel 接到 N 个 worker——channel 天然支持多读者
const workers = 4
outs := make([]<-chan int, workers)
for i := range outs {
    outs[i] = square(ctx, in)           // N 个 square 并发消费同一个 in
}

// fan-in：merge 把 N 条输入合成一条——启动 N+1 个 goroutine，用 WaitGroup 等齐后关总输出
func merge(ctx context.Context, chans ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    wg.Add(len(chans))
    for _, c := range chans {
        go func(c <-chan int) {
            defer wg.Done()
            for v := range c {
                select {
                case out <- v:
                case <-ctx.Done():
                    return
                }
            }
        }(c)
    }
    go func() {
        wg.Wait()        // 所有输入都枯竭后
        close(out)       // 才关总输出——「最后一个人走时关灯」
    }()
    return out
}
```

`wg.Wait()` 后 `close(out)` 这个小 goroutine 是 fan-in 的灵魂：**关闭时机 = 所有生产者的枯竭时机**，多路输入时这是唯一正确的关灯方式（单输入时阶段自己 defer close 就够）。

## 4. done channel 与 context 取消

上游放弃时，整条管道必须停止——否则所有 goroutine 阻塞在 send 上泄漏（golang 12 篇泄漏来源①）：

```go
// 原始形态：done channel
done := make(chan struct{})
go func() {
    os.Exit(callSome())    // 消费者提前退出，不再读 out
    close(done)            // 广播退出信号
}()
select {
case out <- v:
case <-done:               // 每个阻塞 send 都要挂上这个逃生门
    return
}
```

生产形态是 context（golang 10 篇的取消树）——`ctx.Done()` 就是标准化的 done channel：

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel()              // 消费者函数返回 = 管道全线取消
```

要点：**消费者跑路不通知 = 泄漏**。任何「从 channel 读」的函数返回时，都要么 cancel ctx，要么把 done 关掉。

## 5. errgroup：生产级编排器

裸写 pipeline + WaitGroup 的三大痛点（错误丢失、不能取消、并发上限）被 `golang.org/x/sync/errgroup` 一次解决：

```go
import "golang.org/x/sync/errgroup"

func fetchAll(ctx context.Context, urls []string) ([]string, error) {
    g, ctx := errgroup.WithContext(ctx)  // ① ctx 派生：任一任务出错自动取消
    g.SetLimit(8)                        // ② 并发上限：内置信号量（见 §6）

    results := make([]string, len(urls)) // 预分配：按索引写，无竞争
    for i, url := range urls {
        i, url := i, url                 // Go 1.22 前的循环变量捕获惯例
        g.Go(func() error {              // ③ 错误收集：第一个非 nil error 被 g.Wait 返回
            body, err := fetch(ctx, url)
            if err != nil {
                return fmt.Errorf("fetch %s: %w", url, err)
            }
            results[i] = body            // 各写各的下标——无需锁
            return nil
        })
    }
    if err := g.Wait(); err != nil {     // 等齐 + 拿第一个错误
        return nil, err
    }
    return results, nil
}
```

四个替代关系（面试对照着说）：

| 裸写 | errgroup 等价 |
|---|---|
| `sync.WaitGroup` + 手工 error 变量 + 锁 | `g.Wait()` 返回首个 error |
| `context.WithCancel` 手动触发 | `g, ctx := WithContext(ctx)`，出错自动 cancel |
| 手写信号量 channel | `g.SetLimit(n)` |
| 手写超时 Wait（golang 12 篇题 5） | 外层套 `context.WithTimeout` + g.Wait 配 select |

**局限**：`g.Go` 没有 panic 隔离（子任务 panic 照样崩进程——errgroup 不替你 recover）；`TryGo` 非阻塞版本慎用。

## 6. semaphore 与 worker pool

「限制同时跑 N 个」的三个层次：

```go
// 层次一：带缓冲 channel 当信号量（最轻）
sem := make(chan struct{}, 8)
for _, t := range tasks {
    sem <- struct{}{}        // 拿到名额才能进（满了阻塞 = 排队）
    go func(t Task) {
        defer func() { <-sem }()  // 干完归还名额
        process(t)
    }(t)
}

// 层次二：worker pool（长生命周期，任务不固定批次）
func pool(ctx context.Context, jobs <-chan Task, workers int) <-chan Result {
    out := make(chan Result)
    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {        // 固定 N 个 worker 反复取活
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                select {
                case <-ctx.Done():
                    return
                case j, ok := <-jobs:
                    if !ok {
                        return
                    }
                    select {
                    case out <- run(j):
                    case <-ctx.Done():
                        return
                    }
                }
            }
        }()
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

// 层次三：errgroup.SetLimit（批次任务 + 错误传播的需求都盖上）
```

选择：一次性批次 → SetLimit；持续到来的流（任务来自 MQ/用户请求）→ worker pool；纯限流不关心结果 → 缓冲 channel。

**限流提示**：信号量限的是「本进程内的并发」，外部系统（DB、下游 API）的限流用 rate.Limiter（notes/nginx 03 篇漏桶的应用内版本）或 Redis 全局限流（notes/redis 11 篇）。

## 7. 选型速查

| 需求 | 模式 |
|---|---|
| 流式多阶段处理，内存恒定 | pipeline（chan→chan 阶段串联） |
| 最慢阶段拖累整体 | fan-out 复制瓶颈阶段 + fan-in merge |
| 一批并发任务，要错误和取消 | errgroup.WithContext + SetLimit |
| 持续任务流 + 固定开销控制 | worker pool |
| 只限并发数 | 缓冲 channel 信号量 / g.SetLimit |
| 通知所有协程退出 | close(done) / ctx 取消（广播语义） |

元规则：**channel 传递数据的所有权，errgroup 管协程的生命周期，锁保护共享状态**（golang 07 篇选型表的并发版）。

## 8. 面试高频

**Q1：pipeline 模式的关闭规则？**
发送方负责关闭；每个阶段 defer close 自己的输出；多路合流（fan-in）用 WaitGroup 等全部输入枯竭后关总输出。接收方靠 range 的 ok=false 感知上游结束。接收方关闭 channel 会 panic。

**Q2：goroutine 泄漏怎么防？**
启动前回答三问：何时退出/谁 recover panic/谁等它。每个阻塞 send 挂 select+ctx.Done() 逃生门；消费者函数返回时必须 cancel。排查：pprof goroutine profile 看卡在哪个 chan 收发（golang 12 篇）。

**Q3：errgroup 相比 WaitGroup 好在哪？**
一次解决三件事：错误收集（Wait 返回首个 error）、取消传播（任一任务出错自动 cancel 派生 ctx）、并发上限（SetLimit）。裸 WaitGroup 要手工加锁存 error、手动 WithCancel。局限：不 recover panic、Go 循环变量捕获注意版本。

**Q4：fan-in 怎么知道该关了？**
N 路输入各起 goroutine 消费并 wg.Done，另起一个 goroutine wg.Wait 后 close 总输出——关闭时机=所有生产者枯竭，这是多路合流唯一正确的关灯方式。

**Q5：worker pool 和信号量怎么选？**
一次性批次任务用 SetLimit/缓冲 channel（任务完就散）；持续任务流（MQ 消费、请求处理）用长生命周期 worker pool（worker 固定反复取活，省去每任务起 goroutine）。进程内并发限流用信号量，跨进程限流用 rate.Limiter/Redis。
