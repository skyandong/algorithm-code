# 十一、存储结构与读路径 —— Kafka 怎么根据 offset 找到消息

上一篇（03-原理与消费者）讲了 Kafka"写得快"，这一篇讲"**读得快**"和"**存在哪**"。面试问"Kafka 为什么快"，答完零拷贝往往会被追问：**那它是怎么定位数据的？**

---

## 1. 磁盘上的目录结构

一个分区对应一个目录，命名 `topic-name-分区号`：

```
/var/lib/kafka/data/
└── order-events-0/
    ├── 00000000000000000000.log        ← 消息本体
    ├── 00000000000000000000.index      ← offset → 物理位置（稀疏索引）
    ├── 00000000000000000000.timeindex  ← timestamp → offset（稀疏索引）
    ├── 00000000000000000000.snapshot   ← 生产者状态快照（幂等/事务用）
    ├── 00000000000000567890.log        ← 下一个 segment
    ├── 00000000000000567890.index
    ├── 00000000000000567890.timeindex
    └── leader-epoch-checkpoint         ← leader 任期记录（防截断/数据丢失）
```

## 2. Segment 分段

一个分区的日志不是单个大文件，而是切成多个 **Segment**。文件名是**该 segment 的起始 offset**（base offset），用 20 位数字补零，方便二分。

滚动生成新 segment 的时机（`log.segment.bytes` 默认 1GB，或 `log.roll.hours` 默认 7 天）：

```
新消息 offset 达到 → 写入当前 active segment
active segment 超过 1GB 或存活超 7 天 → 关闭，创建新 segment
```

**只有 active segment（最后一个）可写**，其余只读。这也意味着**清理日志时 active segment 永远不会被删** —— 磁盘快满但删不掉文件时，这就是原因之一。

## 3. 稀疏索引：为什么不用 B+ 树

Kafka 的索引是**稀疏**的：不是每条消息都建索引，而是每写入 `index.interval.bytes`（默认 **4096 字节**）才建一条索引项。

```
.index 文件：     [offset=100, position=0]
                 [offset=180, position=4096]
                 [offset=260, position=8192]   ← 每 4KB 一条
```

索引项本身是**定长 8 字节**（4 字节相对 offset + 4 字节物理位置），所以可以**直接二分查找**，而且整个索引文件能被**mmap 到内存**，全部查询在内存完成，不碰磁盘。

> 对比 RocketMQ 的 ConsumeQueue 是**全量索引**（每条消息一条，定长 20 字节）。Kafka 用稀疏换空间，代价是定位后还要在 .log 里顺序扫一小段（最多 4KB），这点开销可以忽略。

## 4. 从 offset 到消息：三步定位

假设要读 `order-events-0` 分区 offset = 234 的消息：

```
第 1 步：找 segment
  所有 segment 文件名（base offset）有序 → 二分查找
  00000000000000000000 (0 ~ 567889)
  00000000000000567890 (567890 ~ ...)
  → offset 234 落在第一个 segment

第 2 步：找索引项
  在 .index 中二分查找 ≤ 234 的最大索引项
  → 命中 [offset=180, position=8192]

第 3 步：顺序扫描
  从 .log 的 8192 字节处顺序扫描，直到 offset == 234
  → 最多扫 4096 字节
```

**按时间戳消费**走的是 `.timeindex`：先二分找到 ≤ 目标时间戳的最大索引项得到 offset，再走上面三步。

## 5. 完整读路径（接上零拷贝）

```
Consumer 发 FetchRequest(topic, partition, offset)
  ↓
Broker 定位 segment + 索引（上面三步，全在内存/页缓存完成）
  ↓
确定要读的字节区间 [position, position+maxBytes)
  ↓
sendfile() 零拷贝：页缓存 → 网卡（不进用户态）
  ↓
Consumer 收到字节流，按 RecordBatch 格式自行解析
```

注意最后一步：**消息的反序列化发生在消费者端，不在 Broker**。所以 Broker 不需要理解消息内容，这也是 Kafka 能扛极高吞吐的原因之一。

## 6. 日志清理与保留策略

Kafka **不会因为消息被消费就删除它**（这是它和传统 MQ 的根本区别——日志模型 vs 队列模型）。删除只由保留策略触发。

### 策略一：delete（默认，按时间/大小删）

| 参数 | 默认值 | 说明 |
|------|-------|------|
| `log.retention.hours` | 168（7 天） | 保留时长，优先级低于 ms |
| `log.retention.ms` | null | 精确到毫秒，设了它会覆盖 hours |
| `log.retention.bytes` | -1（不限） | 分区总大小上限 |
| `log.retention.check.interval.ms` | 300000（5 分钟） | 巡检周期 |

**重要推论：消费积压超过保留期 = 数据永久丢失。** 这是线上最严重的事故之一（见 09-监控与运维）。

### 策略二：compact（按 key 压缩，保留每个 key 的最新值）

```
压缩前：  k1=v1  k2=v1  k1=v2  k3=v1  k2=v2
压缩后：  k1=v2  k3=v1  k2=v2
```

- 语义从"消息队列"变成"**KV 状态流**"，适合做 CDC 同步、物化视图、配置中心
- 压缩在后台线程做，**active segment 不参与压缩**
- **墓碑消息（tombstone）**：value = null 的消息表示"删除这个 key"。它不会被立刻清掉，要保留 `delete.retention.ms`（默认 24 小时）让消费者看到"删除"这个事实，之后才真正物理删除
- 可以设为 `compact,delete`：既压 key 又按时间兜底删

## 7. 分区数与文件句柄的关系

这是"分区数不能无脑加"的底层原因：

```
总文件数 ≈ 分区数 × 每分区 segment 数 × 3（.log/.index/.timeindex）
```

1000 个分区 × 每分区 10 个 segment × 3 = 30000 个文件。每个打开的 segment 都要占文件句柄和页缓存。所以分区数需要按容量规划，见 07-分区与容量设计。

**面试金句：** Kafka 定位消息是「二分 segment 文件名 → 二分稀疏索引 → 顺序扫 4KB」三步，索引定长 8 字节且被 mmap 进内存，所以整个查找过程几乎不碰磁盘；找到物理位置后用 sendfile 零拷贝直接发网卡。另外 Kafka 不因消费而删消息，只按保留策略删，所以积压超过保留期会直接丢数据。

## 实验

对应代码：[experiments/08_storage.go](experiments/08_storage.go)

```bash
cd notes/akafka
make up && make topics
go run ./experiments/ storage
```

实验内容：
1. 生产带业务时间戳的消息，模拟"按时间回放"场景
2. 分区首尾 offset：用 kadm 查 `ListStartOffsets` / `ListEndOffsets`，观察每分区消息量与 start offset
3. 按时间戳定位 offset：`ListOffsetsAfterMilli` 走 .timeindex，得到"30 秒前"那条消息在每分区的 offset
4. 日志段大小：`DescribeAllLogDirs` 观察各 broker 上该 topic 分区的日志段字节数（对应 .log/.index/.timeindex 总和）
