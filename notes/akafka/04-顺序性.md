# 十、顺序性保证 —— Kafka 到底能不能保证顺序

这是 Kafka 面试里**问得最多、答错率也最高**的一题。核心结论先摆出来：

> **Kafka 只保证分区内有序，不保证全局有序。而且"分区内有序"这句话，生产端和消费端各有一半。**

---

## 1. 顺序性的边界

| 维度 | 是否有序 | 说明 |
|------|---------|------|
| 单个 Partition 内 | 有序 | 追加写日志，offset 单调递增 |
| 同一个 Topic 跨 Partition | **无序** | 不同分区之间没有任何顺序关系 |
| 全局（跨 Topic） | **无序** | 更谈不上 |

所以"Kafka 保证消息顺序"是错的，"Kafka 保证分区内顺序"才对。

## 2. 生产端：怎么让需要保序的消息进同一个分区

靠 **key 路由**。默认分区器对 key 做 murmur2 哈希后取模：

```
partition = murmur2(key_bytes) % numPartitions
```

- **key 不为 null**：按哈希值路由，相同 key 一定落到同一分区 → 同 key 的消息天然有序
- **key 为 null**：Kafka 2.4 之前是 round-robin（轮询），之后改为**粘性分区**（UniformSticky）：先粘住一个分区攒批，批满或 linger 到期后换下一个。粘性分区减少了小批次请求数，吞吐更好

**关键推论：想保序就必须指定 key。** 保序粒度由 key 决定：

| key 设计 | 顺序粒度 | 适用场景 |
|---------|---------|---------|
| 订单 ID | 单个订单内的事件有序 | 订单状态机（创建→支付→发货→完成） |
| 用户 ID | 单个用户的行为有序 | 用户资料变更流 |
| 不指定 key | 无任何顺序 | 日志采集、埋点 |

### 代价：热点分区

按 key 路由意味着某个大客户的消息全挤在一个分区，造成分区倾斜（见案例 10）。工程上的缓解手段是**复合 key**：`hash(bizId + "_" + (seq % N))` 把热点打散到 N 个分区，代价是需要按 bizId 在消费端重新聚合排序。

### 陷阱：分区扩容会破坏顺序映射

`partition = hash(key) % numPartitions`，分区数一变，映射关系全变。

**所以"先建 1 个分区，不够了再加"是错误做法** —— 加分区的瞬间，同一个 key 的新消息会写到新分区，与旧分区里的历史消息形成顺序断裂。如果业务强依赖顺序，只能：
1. 建 Topic 时就按终态规划好分区数
2. 或者建新 Topic（新分区数）双写迁移

## 3. 生产端第二个坑：重试导致的乱序

场景：Producer 连发 batch A（seq 0）、B（seq 1），A 超时重试，B 先到达 → 日志变成 B、A，顺序反了。

这是 `max.in.flight.requests.per.connection > 1`（默认 5）的经典问题。

**解法：开启幂等（`enable.idempotence=true`）**。Broker 为每个 (PID, partition) 缓存最近 5 个 batch 的序列号，能识别出"A 是重复/迟到"并拒绝或重排，从而把单个分区内在途的 5 个 batch 也纳入顺序保证。

> 这也是为什么 **Kafka 0.11 之后推荐无条件开启幂等** —— 它不只是去重，还顺带修好了重试乱序。代价只是极小的元数据开销。

**注意 franz-go 的差异**：franz-go 的 `kgo.Client` **默认就是幂等的**，要显式调 `kgo.DisableIdempotentWrite()` 才关闭。这点和 Java 客户端（需要显式打开）不同，容易被误判。

## 4. 消费端：单分区不等于消费有序

这是最容易漏掉的一半。生产端保证了"写入分区的顺序"，但消费端可能把它读乱：

| 消费方式 | 是否保序 | 原因 |
|---------|---------|------|
| 单线程 poll + 处理 | 有序 | 一条处理完再取下一条 |
| poll 出来丢进 goroutine 池/线程池 | **乱序** | 处理耗时不同，先取到的可能后处理完 |
| 多进程同 group | 分区间无序（本来就没序） | 但每个分区内部仍是单线程有序 |

**所以完整答案：分区内有序 + 消费端对同一分区串行处理 = 端到端有序。**

多线程下既要并行又要保序的标准做法是 **按 key 分发到固定 worker**：

```
poll → 按 hash(key) % workerNum 分发到对应 worker 的单队列
       → 同一 key 永远进同一个 worker → 同 key 串行
       → 不同 key 分散到不同 worker → 跨 key 并行
```

这样既拿到了并行度，又保证了同 key 顺序。代码见案例 9。

## 5. 真正的全局有序

只有一条路：**单分区**。一个 Topic 只有一个 Partition，吞吐上限就是单个分区的吞吐（通常几 MB/s 到十几 MB/s），且无法水平扩展。

所以面试时应该反问一句业务：**"全局有序"通常是伪需求** —— 绝大多数场景真正要的是"同一个业务实体的事件有序"，用业务 key 路由就够了。

**面试金句：** Kafka 的顺序性要分三段答——写入侧靠 key 路由保证同 key 进同分区；单分区内靠追加日志保证 offset 有序；消费侧必须对这个分区串行处理才算端到端有序。中间任何一环用了并发，顺序就没了。另外分区扩容会改变 key 到分区的映射，强顺序场景下分区数必须一开始规划到位。

```bash

```

实验内容：
1. 同 key 路由验证：同一个 orderID 的 5 个状态事件全部落到同一分区
2. 无 key 对比：key 为 null 时消息被粘性/打散到不同分区，顺序无法保证
3. 消费端乱序复现：多线程并发处理同一 key 的消息，观察到状态机错乱（如"已完成"先于"已支付"被处理）
4. 消费端保序方案：按 key 分发到固定 worker，同一 key 串行执行，顺序恢复
