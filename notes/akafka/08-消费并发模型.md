# 十四、消费并发模型与位移提交竞态

这是 Kafka 工程里**最容易出线上事故**的一块，也是面试区分"用过"和"踩过坑"的分水岭。

---

## 1. 三种消费模型

| 模型 | 并行度 | 顺序性 | 复杂度 | 适用 |
|------|-------|-------|-------|------|
| A. 单线程 poll + 处理 | 1 | 有序 | 低 | 低吞吐、强顺序 |
| B. 多进程/多实例同 group | = 分区数 | 分区内有序 | 低 | **首选**，绝大多数场景 |
| C. poll + 内部 worker pool | 可调 | **破坏顺序** | 高 | 单条处理慢（IO 密集）但分区数受限 |

**重要认知：模型 B 才是 Kafka 推荐的扩展方式。** 加机器、加进程，让分区数 ≥ 实例数，天然并行且不破坏分区内顺序。

**模型 C 是不得已的选择**：分区数已经固定、又没法加实例（比如消费逻辑必须读本地缓存），才在进程内用多线程。但一旦用了，就必须解决下面两个问题。

## 2. 位移提交竞态：并发消费的经典陷阱

场景：poll 拉到 offset 10 ~ 14 五条消息，丢进 5 个 goroutine 并发处理。

```
offset 10  处理中（慢，卡在 DB）
offset 11  完成
offset 12  完成
offset 13  完成
offset 14  完成
           ↓
        提交 offset = 15   ← 错误！10 还没处理完
           ↓
        进程崩溃
           ↓
        从 15 继续消费 → offset 10 永久丢失
```

反过来，如果"处理完再提交"是按完成顺序提交的，还会出现**提交更小 offset 覆盖更大 offset**的倒退问题。

### 解法：滑动窗口（只提交连续已完成的 offset）

维护一个按 offset 排序的完成状态窗口：

```
完成状态：  10:✓  11:✓  12:✗  13:✓  14:✓
                          ↑
                     卡在这里
水位线 = 12        → 只提交 offset 12（即"12 及之前都完成了"）
```

实现要点：
- 用 `map[int64]bool` 或一个有序结构记录每条消息的完成状态
- 从上次提交点开始向后扫描，停在第一个未完成的位置
- 提交的是**水位线 offset**（不是"最大已完成 offset"）

代码见 [experiments/09_concurrent.go](experiments/09_concurrent.go)，里面同时实现了错误做法和正确做法，可以直接对比。

### 更简单的替代方案

如果不想维护滑动窗口，有两个更省事的选择：

1. **按 key 分发到固定 worker**（见 04-顺序性）：同 key 串行，天然无竞态
2. **批量处理 + 整体提交**：一次 poll 一批，全部处理完再提交这一批的 offset。牺牲一点并行粒度，换实现简单

## 3. max.poll.* 三件套与心跳

这四个参数搞混是高频面试失分点：

| 参数 | 默认值 | 作用 | 超时后果 |
|------|-------|------|---------|
| `max.poll.records` | 500 | 单次 `poll()` 最多返回多少条 | — |
| `max.poll.interval.ms` | 300000（5 分钟） | **两次 poll 之间**的最大间隔 | 判定"消费卡死"，踢出组 → Rebalance |
| `session.timeout.ms` | 45000（45 秒） | 心跳超时判定消费者死亡 | 踢出组 → Rebalance |
| `heartbeat.interval.ms` | 3000（3 秒） | 心跳发送频率 | 应 ≤ session.timeout / 3 |

**关键区别**：

- **心跳（session.timeout）证明"我还活着"** —— 由后台心跳线程发送，与业务处理无关
- **max.poll.interval 证明"我还在干活"** —— 只要你在 5 分钟内再次调用 poll() 就续期；如果处理逻辑卡了 6 分钟没回到 poll 循环，即使心跳正常也会被踢

> 这是最隐蔽的坑：**心跳正常但 Rebalance 依然发生**，原因就是 poll 循环被慢处理阻塞了。

### 调优建议

```
heartbeat.interval.ms   = session.timeout.ms / 3
session.timeout.ms      = 10 ~ 45 秒（网络差的环境取大值）
max.poll.interval.ms    = 单批最长处理时间 × 2 ~ 3
max.poll.records        = 让"单批处理时间"远小于 max.poll.interval
```

如果单条消息处理要 100ms，`max.poll.records=500` 意味着单批最多 50 秒 —— 已经逼近 5 分钟。所以**处理慢的场景必须调小 `max.poll.records`**，或者改用模型 C。

## 4. 静态成员资格（避免滚动发布引发 Rebalance）

Kafka 2.3+ 的 `group.instance.id`：

**问题**：K8s 滚动发布时，Pod 优雅退出又立刻拉起。默认情况下 coordinator 认为"成员离开 → 触发 Rebalance"，紧接着"成员加入 → 再触发一次 Rebalance"。整个发布过程反复重平衡，消费停顿。

**解法**：给每个实例配置固定且唯一的 `group.instance.id`（如 Pod 名）。这样：
- 实例离开时不会立即移除成员资格，会等 `session.timeout.ms` 到期
- 期间重启回来的实例带着同样的 ID 加入，直接恢复原分区分配
- **不触发 Rebalance**

franz-go 里对应 `kgo.InstanceID(...)`。

## 5. 背压：消费不过来时怎么办

当处理速度跟不上 poll 速度时，消息会在客户端缓冲区堆积，最终 OOM 或触发 max.poll.interval 超时。

franz-go 提供了分区级的暂停/恢复：

```go
client.PauseFetchPartitions(map[string][]int32{"topic": {0, 1, 2}})
// ... 处理积压 ...
client.ResumeFetchPartitions(map[string][]int32{"topic": {0, 1, 2}})
```

**这是比 sleep 好得多的背压方式**：sleep 会阻塞 poll 循环，可能触发 max.poll.interval 超时；而 Pause 只是告诉客户端"暂时别拉这个分区的数据"，poll 循环照常运行，心跳和续期都不受影响。

## 6. Rebalance 优化清单

结合 03-原理与消费者里的分配策略，实际调优项：

| 措施 | 作用 |
|------|------|
| `cooperative-sticky` 分配策略 | 增量式 Rebalance，只迁移必要分区（Kafka 2.4+） |
| `group.instance.id` 静态成员 | 消除滚动发布/短暂重启引发的 Rebalance |
| 调大 `max.poll.interval.ms` | 容忍慢批次 |
| 调小 `max.poll.records` | 减少单批处理时间 |
| poll 循环里禁止同步阻塞 IO | 慢 IO 一律丢给 worker 池或异步化 |
| 关注 GC 停顿 | JVM 客户端的长 GC 是 Rebalance 的常见元凶 |

**面试金句：** 并发消费的核心坑是位移提交竞态——先完成的大 offset 提交了、小的没完成，崩溃后会丢消息，解法是滑动窗口只提交连续完成的水位线。另外心跳正常也会 Rebalance，因为 max.poll.interval.ms 是独立的"在干活"证明，poll 循环被慢处理阻塞超过 5 分钟就会被踢出组。生产上用 group.instance.id 静态成员消除滚动发布的重平衡，用 Pause/Resume 做背压而不是 sleep。
