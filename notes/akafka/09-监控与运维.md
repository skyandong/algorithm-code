# 十五、监控指标与线上排查手册

前面所有笔记都在讲"应该怎么做"，这一篇讲"**线上出问题了怎么办**"。面试时如果能顺着讲一个真实排查过程，说服力远超背参数。

---

## 1. 分层监控指标

### Broker 层（JMX）

| 指标 | 含义 | 告警阈值 |
|------|------|---------|
| `UnderReplicatedPartitions` | 副本数不足的分区数 | **> 0 且持续 → 立即告警**（正常集群应恒为 0） |
| `OfflinePartitionsCount` | 无 leader 的分区数 | > 0 → P0，该分区完全不可用 |
| `ActiveControllerCount` | 活跃 Controller 数 | **必须 = 1**。= 0 或 > 1 都是严重故障 |
| `ISRShrinksPerSec` / `ISRExpandsPerSec` | ISR 收缩/扩张频率 | 频繁波动 → 副本同步跟不上 |
| `RequestHandlerAvgIdlePercent` | 请求处理线程空闲率 | **< 0.3 → 告警**，说明 Broker 处理能力到瓶颈 |
| `NetworkProcessorAvgIdlePercent` | 网络线程空闲率 | < 0.3 → 告警 |
| `UncleanLeaderElectionsPerSec` | 非 ISR 选举次数 | > 0 → 丢过数据 |
| `LogFlushRateAndTimeMs` | 刷盘速率与耗时 | 结合磁盘 IO 看 |

### Topic / Partition 层

| 指标 | 用途 |
|------|------|
| `BytesInPerSec` / `BytesOutPerSec` | 流量基线，异常突增要查 |
| `MessagesInPerSec` | 生产 TPS |
| `LogEndOffset` 增速 | **判断是生产突增还是消费变慢**（见排查场景 1） |
| `LogStartOffset` | 保留策略删到哪了，逼近 end offset 说明积压到临界 |

### Consumer 层

| 指标 | 含义 | 告警阈值 |
|------|------|---------|
| `records-lag` / `records-lag-max` | 每个分区的积压量 | 见下面第 2 节的分级告警 |
| `records-consumed-rate` | 消费速率 | 突然掉到 0 → 消费线程卡死 |
| `commit-rate` / `commit-latency-avg` | 提交速率与延迟 | 提交延迟高 → 消费者压力大 |
| `rebalance-rate` / `rebalance-total` | Rebalance 频率 | **> 0 就要查**，正常集群应接近 0 |
| `fetch-latency-avg` | 拉取延迟 | 高 → 网络或 Broker 问题 |
| `heartbeat-rate` / `heartbeat-response-time-max` | 心跳 | 响应慢 → 网络或 coordinator 压力 |

### Producer 层

| 指标 | 含义 |
|------|------|
| `record-error-rate` | 发送失败率，**应接近 0** |
| `record-queue-time-avg` | 消息在缓冲区等待时间，高 → 生产跟不上 |
| `request-latency-avg` | 请求往返延迟 |
| `record-retry-rate` | 重试率，高 → 网络抖动或 Broker 压力 |
| `compression-rate` | 压缩率 |

## 2. 积压告警：不要 lag > 0 就告警

**错误做法**：`lag > 1000 就告警`。结果：每天抖动几十次，告警疲劳，最后没人看。

**正确做法**：分层 + 看趋势。

| 级别 | 条件 | 动作 |
|------|------|------|
| Info | lag 存在但在下降 | 观察，不告警 |
| Warning | lag **持续增长**超过 N 分钟 | 记录，通知 owner |
| Critical | **预计恢复时间 > 保留期剩余时间** | P0，会丢数据 |

核心指标不是 lag 绝对值，而是**预计追平时间**：

```
消费速率 v = (lag_t0 - lag_t1) / (t1 - t0)
预计追平时间 = lag / v
```

如果算出来是负数（lag 还在涨），那就是消费能力不足，必须扩容。

**这条最关键**：`预计追平时间 > 保留期剩余时间` 意味着数据在追平前就被保留策略删掉了 —— 这是唯一需要半夜叫醒人的告警。

## 3. 排查手册：六个典型场景

### 场景 1：消费 lag 突然暴涨

```
第 1 步：区分是"生产突增"还是"消费变慢"
    看 LogEndOffset 增速 vs 消费速率
    ├─ end offset 增速也涨了 → 生产突增（上游流量洪峰）
    └─ end offset 平稳，lag 涨   → 消费变慢（本服务问题）

第 2 步：消费变慢的定位路径
    消费 RT 是否变长？
    ├─ 是 → 查下游依赖（DB 慢查询、外部 HTTP 超时、缓存击穿）
    ├─ 否 → 消费者数量是否减少？（实例被驱逐？Rebalance？）
    └─ 都不是 → 查 GC（JVM）/ 网络 / 磁盘 IO

第 3 步：检查 Rebalance
    rebalance-rate > 0 → 转场景 2
```

### 场景 2：频繁 Rebalance

```
排查顺序：
1. max.poll.interval.ms 超时   ← 最常见
   → 单批处理时间是否超过 5 分钟？调小 max.poll.records
2. 长 GC 停顿（JVM 客户端）
   → 看 GC 日志，停顿超过 session.timeout 就会掉线
3. 网络抖动 / coordinator 压力
   → 看 heartbeat-response-time-max
4. 滚动发布 / 实例重启
   → 配 group.instance.id 静态成员
5. 分区数变化
   → 有人扩了分区

证据链：consumer 日志搜 "Attempt to heartbeat failed" 或
        "Member ... has left group"
```

### 场景 3：消息丢了

```
按 02-消息保障的三段式逐段排查：

Producer 段：
  acks 是不是 all？retries 是否 > 0？失败回调里有没有兜底？
  → 查 record-error-rate 和发送端日志

Broker 段：
  min.insync.replicas 是否 ≥ 2？（=1 时 acks=all 退化成 acks=1）
  unclean.leader.election.enable 是不是 true？（true 会丢数据）
  → 查 UncleanLeaderElectionsPerSec

Consumer 段（最常见）：
  是不是"先提交 offset 再处理业务"？（顺序反了必丢）
  是不是并发消费时的提交竞态？（见 08-消费并发模型）
  是不是用了 auto commit？（默认 5 秒自动提交，业务没处理完就提交了）
```

### 场景 4：磁盘快满了

```
第 1 步：确认保留策略是否生效
    log.retention 参数对不对？active segment 删不掉（正常）
第 2 步：紧急处理（按侵入性从低到高）
    a. 临时缩短 log.retention.ms（会丢数据，需业务确认）
    b. 扩磁盘 / 加 Broker
    c. 扩分区（只能加不能减，谨慎）
第 3 步：根因
    是不是某个 Topic 流量异常？查 BytesInPerSec 找出元凶
    是不是 compact 没生效？（cleaner 线程挂了？）
```

### 场景 5：ISR 持续收缩

```
含义：Follower 追不上 Leader
排查：
  1. Follower Broker 磁盘 IO 打满？（iostat）
  2. 网络带宽？
  3. replica.lag.time.max.ms 是否过小（默认 30 秒，大流量下可能不够）
  4. num.replica.fetchers 是否太小（副本拉取线程数）

影响：UnderReplicatedPartitions > 0 → 此时再挂一个 Broker 就可能丢数据
```

### 场景 6：重复消费

```
1. 是不是"先处理再提交"但提交前崩溃了？→ 这是 at-least-once 的正常表现，需业务幂等
2. 是不是 Rebalance 时没提交 offset？→ 在 OnPartitionsRevoked 回调里提交
3. 是不是 auto commit + 业务处理超过 5 秒？→ 关掉自动提交
4. 幂等方案选一个：唯一索引 / Redis setnx / 状态机校验
```

## 4. 常用运维命令

```bash
# Topic 列表与详情
kafka-topics.sh --bootstrap-server localhost:9092 --list
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders

# 消费者组与积压（最常用）
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group order-service

# 重置 offset（慎用，会丢或重复消费）
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group order-service \
  --topic orders --reset-offsets --to-earliest --execute
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group order-service \
  --topic orders --reset-offsets --to-latest --execute      # 跳过积压（丢数据）

# 扩分区
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic orders --partitions 12

# 查看 Topic 各分区起止 offset
kafka-run-class.sh kafka.tools.GetOffsetShell --bootstrap-server localhost:9092 \
  --topic orders --time -1    # -1=最新, -2=最早

# 消费指定 offset 的消息排查问题
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders \
  --partition 0 --offset 12345 --max-messages 1

# 查看 Broker 配置
kafka-configs.sh --bootstrap-server localhost:9092 --describe --entity-type brokers --entity-name 1
```

## 5. 上线前检查清单

- [ ] `replication.factor >= 3`，`min.insync.replicas >= 2`
- [ ] Producer `acks=all` + `retries > 0` + 失败回调兜底
- [ ] Consumer 关闭自动提交，业务处理完再提交
- [ ] `unclean.leader.election.enable = false`
- [ ] 保留期 ≥ 预计最长故障恢复时间 × 3
- [ ] lag 告警配置（按"预计追平时间"而非绝对值）
- [ ] `UnderReplicatedPartitions`、`ActiveControllerCount` 告警已配
- [ ] Rebalance 监控已配
- [ ] 消费端业务幂等已实现
- [ ] 分区数与消费者实例数已压测验证

**面试金句：** 监控分 Broker/Topic/Consumer/Producer 四层看，最关键的是 UnderReplicatedPartitions（应为 0）、ActiveControllerCount（应为 1）和消费者 lag。lag 告警不能看绝对值，要看增长趋势和预计追平时间——真正需要半夜叫醒人的只有一种情况：预计追平时间超过了保留期的剩余时间，因为那意味着数据在追平前就被删掉了。
