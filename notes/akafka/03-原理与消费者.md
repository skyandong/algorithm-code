# 五、ISR、HW、LEO 与副本同步

## 核心概念

- **ISR（In-Sync Replicas）**：与 Leader 保持同步的副本集合。只有 ISR 中的副本才有资格竞选 Leader
- **LEO（Log End Offset）**：下一条待写入消息的 Offset（= 最后一条消息的 Offset + 1）
- **HW（High Watermark）**：ISR 中所有副本的最小 LEO，Consumer 只能读到 HW 之前的数据

## 同步流程

1. Producer 发消息到 Leader，Leader 写入本地 Log
2. Follower 拉取消息并写入自己的 Log，更新自己的 LEO
3. Leader 收到 Follower 的 ACK 后，更新 HW = min(所有 ISR 副本的 LEO)
4. Consumer 只能消费 HW 之前的数据，保证即使 Leader 挂了也不会读到未同步的数据

## Leader 选举

优先从 ISR 中选新 Leader

如果 ISR 全挂了：
- `unclean.leader.election.enable=false`：等待旧 Leader 恢复，不丢数据但不可用
- `unclean.leader.election.enable=true`：选非 ISR 副本当 Leader，可用但可能丢数据

**面试金句：** HW 是消费者的可见边界，LEO 是副本的写入边界，ISR 是高可用的候选池。Kafka 通过 HW 机制保证了已提交消息的可靠性。

# 六、高性能原理

Kafka 为什么这么快？顺序写 + 页缓存 + 零拷贝 + 批量压缩

| 技术 | 原理 |
|------|------|
| 顺序写磁盘 | 磁盘顺序写的性能接近内存随机写，避免了磁头寻道 |
| 页缓存（Page Cache） | 数据先写 OS 的 Page Cache，由 OS 异步刷盘，而不是 JVM 堆内存 |
| 零拷贝（Zero-Copy） | 通过 `sendfile()` 系统调用，数据直接从 Page Cache 发送到网卡，不经过用户态，减少 2 次 CPU 拷贝 |
| 批量处理 | Producer 批量发送（`batch.size`、`linger.ms`），Consumer 批量拉取（`fetch.min.bytes`） |
| 压缩 | 支持 GZIP、Snappy、LZ4、ZSTD，减少网络传输和磁盘占用 |
| 分区并行 | 不同 Partition 可分布在不同 Broker，实现水平扩展 |

**面试金句：** Kafka 的高性能不是因为它用了磁盘，而是因为它把磁盘用成了内存的顺序写，再配合 OS 的零拷贝，让数据从磁盘到网卡只经过内核态。

# 七、消费者组与 Rebalance

## 消费者组特性

- 一个 Partition 只能被同一个 Consumer Group 内的一个 Consumer 消费
- 消费者数 > Partition 数时，多余的消费者空闲
- 消费者数 < Partition 数时，一个消费者消费多个 Partition

## Rebalance（重平衡）

**触发条件：** 消费者加入/退出组、Topic Partition 数变化、消费者心跳超时

**过程：** Eager 协议下所有消费者停止消费，Coordinator 重新分配 Partition，期间整个组不可用；CooperativeSticky（Kafka 2.4+）增量式重平衡，只撤销需要迁移的分区，未受影响的分区持续消费

**分配策略：**

| 策略 | 特点 |
|------|------|
| Range（默认） | 按 Topic 范围分配，可能不均匀 |
| RoundRobin | 轮询分配，较均匀 |
| Sticky | 尽量保持原有分配，减少变动 |
| CooperativeSticky（Kafka 2.4+） | 增量式重平衡，先撤销再分配，减少停顿 |

**面试金句：** Rebalance 是 Kafka 消费者的性能杀手，线上要避免频繁 Rebalance，关键是保证消费者心跳正常、消费逻辑不阻塞 poll()、合理设置 session.timeout.ms 和 max.poll.interval.ms。
