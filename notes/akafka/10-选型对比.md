# 十六、消息中间件选型对比

面试问"Kafka 和 RocketMQ 怎么选"，**最差答案是"Kafka 更好"**。这类题考的是你有没有按场景做判断的能力。

---

## 1. 一句话定位

| 中间件 | 本质 | 一句话 |
|--------|------|-------|
| **Kafka** | 分布式**日志**（Log） | 为高吞吐流数据而生，生态最强，功能最朴素 |
| **RocketMQ** | 分布式**队列 + 日志** | 阿里系，业务消息功能最全（延迟/事务/重试） |
| **RabbitMQ** | 传统**消息代理**（Broker） | 路由灵活、延迟最低，吞吐是短板 |
| **Pulsar** | **存算分离**的日志 | 架构最先进，多租户原生，运维最重 |

## 2. 关键维度对比

| 维度 | Kafka | RocketMQ | RabbitMQ | Pulsar |
|------|-------|----------|----------|--------|
| 单机吞吐 | **百万级 TPS** | 十万级 TPS | 万级 TPS | 百万级 TPS |
| 延迟 | 毫秒级（攒批换吞吐） | 毫秒级 | **微秒 ~ 毫秒级** | 毫秒级 |
| 顺序性 | 分区内有序 | 队列内有序 | 单队列有序（多消费者会乱） | 分区内有序 + **key_shared 同 key 有序** |
| 延迟消息 | 无原生，需自建时间轮 | **原生 18 个级别** | 插件（延迟交换机） | 原生（任意时间） |
| 事务消息 | **Kafka 内部事务** | **业务事务消息**（半消息 + 回查） | 无 | 有 |
| 消息重试 / DLQ | 需自建 | **原生重试 + 死信** | 原生死信交换机 | 原生 |
| 消息过滤 | 无（需消费端过滤） | **Tag / SQL92 属性过滤** | 交换机 + routing key | 有 |
| 消息回溯 | **原生**（按 offset/时间戳） | 按时间 | 不支持（消费即删） | 原生 |
| 存储模型 | 分区日志 + 本地磁盘 | CommitLog + ConsumeQueue | 内存/磁盘队列 | BookKeeper 分片 |
| 架构 | KRaft（去 ZK） | NameServer（轻量） | 单节点/镜像集群 | Broker + BookKeeper + ZK（**最重**） |
| 多租户 | 弱（靠命名 + ACL） | 一般 | 一般 | **原生最强** |
| 生态 | **最强**（Connect / Streams / Flink 一等公民） | 好（国内） | 好 | 较弱 |
| 语言 | Scala/Java | Java | Erlang | Java |

## 3. 三个关键差异点（面试加分项）

### 差异一：延迟消息

- **RocketMQ 原生支持**，18 个固定延迟级别（1s/5s/10s/30s/1m/2m/3m/4m/5m/6m/7m/8m/9m/10m/20m/30m/1h/2h）
- **Kafka 没有**。业界做法是：
  1. 多级时间轮 + 中转 Topic（延迟 Topic → 到期转发到业务 Topic）
  2. 或用外部调度（Redis ZSet / 定时任务扫表）
- 所以"订单 30 分钟未支付自动取消"这种需求，RocketMQ 一行代码，Kafka 要搭一套

### 差异二：事务消息的语义不同

这是容易混淆的点：

- **Kafka 事务**：保证"写多个 Kafka 分区"和"提交消费位移"的原子性，**不管外部系统**
- **RocketMQ 事务消息**：两阶段 + 回查机制 —— 先发半消息（对消费者不可见）→ 执行本地事务 → 提交/回滚 → **如果 Producer 挂了，Broker 会主动回查本地事务状态**

**RocketMQ 的方案更贴近"业务分布式事务"**（本地事务 + 消息投递的一致性），Kafka 的方案更贴近"流处理的 EOS"。场景不同，不能说谁更好。

### 差异三：Pulsar 的 key_shared 订阅

Kafka 要保证同 key 顺序，受限于分区数（并行度上限 = 分区数）。

Pulsar 的 **key_shared** 订阅模式：同一个 key 的消息发给同一个消费者（保序），但**不受分区数限制**，消费者可以任意扩容。

这是 Kafka 需要靠"加盐 + 消费端聚合"绕过的限制，Pulsar 是原生的。代价是 Pulsar 运维复杂度高得多。

## 4. 选型决策树

```
需求是什么？
│
├─ 日志采集 / 埋点 / CDC / 流处理（Flink）
│     └─► Kafka（生态和吞吐碾压，没得选）
│
├─ 业务消息：需要延迟消息 / 事务消息 / 消息重试 / Tag 过滤
│     ├─ Java 技术栈、国内团队  ──► RocketMQ（开箱即用）
│     └─ 已有 Kafka + 能接受自建  ──► Kafka + 自建中间件层
│
├─ 任务队列 / RPC / 需要极低延迟 / 路由规则复杂
│     └─► RabbitMQ（交换机路由灵活，吞吐要求不高）
│
├─ 多租户 / 超大集群 / 需要存算分离弹性扩缩
│     └─► Pulsar（能接受运维复杂度）
│
└─ 想不清楚 / 团队没运维经验
      └─► Kafka（或直接用云厂商托管版）

补充：消息量小（日百万级以下）且团队小 —— 别自建，用云托管
（阿里云 MQ / 腾讯云 CKafka /  AWS MSK / Confluent Cloud）
```

## 5. 面试怎么答这道题

**结构建议**：先说"看场景"，再给一个对比维度，最后落到具体问题。

> "这几种 MQ 定位不太一样，不能简单说谁更好。Kafka 本质是分布式日志，优势在吞吐和生态，适合日志采集、CDC、流处理这类场景；RocketMQ 更像业务消息队列，延迟消息、事务消息、重试这些都是原生支持的，业务开发效率高；RabbitMQ 延迟最低、路由最灵活，但吞吐是短板，适合任务队列；Pulsar 架构最先进，存算分离和多租户是原生的，但运维复杂度也最高。
>
> 如果让我选，我会先看业务形态 —— 如果是数据流、要接 Flink，那没得选就是 Kafka；如果是订单这类业务消息、还经常有'30 分钟不支付关单'的需求，RocketMQ 会省很多事。另外还要考虑团队运维能力，量不大的话直接上云托管版比自建划算。"

**加分动作**：主动提一句"但是这几个都用过/踩过 XX 的坑"，比纯背表格真实得多。
