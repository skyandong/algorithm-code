# 二、消息可靠性 —— 如何保证消息不丢失

消息丢失可能发生在 Producer 端、Broker 端、Consumer 端，需要三段式防护：

## 1. Producer 端

`acks` 参数：
- `acks=0`：发完不管，最快但最不可靠
- `acks=1`：Leader 落盘就返回，Follower 没同步就挂了会丢
- `acks=all`（或 `-1`）：Leader + 所有 ISR 中的 Follower 都落盘才返回，最可靠

重试机制：设置 `retries > 0`，网络抖动时自动重发

失败回调：实现回调接口处理发送失败的消息，做兜底（如记日志、入死信队列）

## 2. Broker 端

副本机制：设置 `replication.factor >= 3`，保证多副本

刷盘策略：
- `flush.messages` 和 `flush.ms` 控制刷盘频率
- 生产环境建议配合 RAID + 多副本，而不是强制同步刷盘（性能太差）

**`unclean.leader.election.enable = false`**：禁止非 ISR 副本当选 Leader，防止丢数据

## 3. Consumer 端

手动提交 Offset：关闭自动提交（`enable.auto.commit=false`），业务处理完再手动 `commitSync()`

先处理业务，再提交 Offset：防止业务失败但 Offset 已提交导致消息丢失

**面试金句：** Kafka 的消息可靠性是三段式保障——Producer 靠 acks=all + 重试，Broker 靠多副本 + ISR，Consumer 靠手动提交 + 先业务后 Offset。

# 三、消息幂等性 —— 如何保证消息不重复

重复消息产生的原因：网络超时导致 Producer 重试、Consumer 消费失败重新消费等。

## 1. Producer 幂等性（Kafka 原生支持）

开启参数：`enable.idempotence=true`

原理：Producer 为每个消息分配 PID（Producer ID）和 Sequence Number，Broker 端去重

限制：只能保证**单分区、单会话**的幂等，Producer 重启后 PID 会变

## 2. Kafka 事务（跨分区幂等）

开启事务：配合幂等性使用，通过 `initTransactions()`、`beginTransaction()`、`commitTransaction()`

作用：保证跨 Partition 的多条消息原子性写入，要么全成功要么全失败

场景：Exactly-Once 语义（EOS），常用于 Kafka Streams 或 Flink + Kafka

## 3. Consumer 端业务幂等（最实用）

- 数据库唯一索引：插入前判断唯一键
- Redis setnx / 分布式锁：用消息 ID 去重
- 业务状态机校验：如订单状态只能由未支付→已支付，重复消息不会改变状态

**面试金句：** Kafka 自带的幂等性只能解决单分区单会话的重复，真正的 Exactly-Once 需要配合事务或消费者端业务去重。

# 四、消息积压 —— 如何处理消息堆积

## 常见原因

- 消费者数量不足或消费逻辑太慢
- 消费者频繁 Rebalance，停止消费
- 分区数太少，消费并行度不够
- 某条消息处理异常，阻塞了后续消费

## 解决方案

| 方案 | 具体操作 |
|------|---------|
| 扩容消费者 | 增加 Consumer 实例数，但不超过 Partition 数（一个 Partition 只能被一个 Consumer 消费） |
| 扩容分区 | 增加 Topic 的 Partition 数，同时增加消费者，提升并行度 |
| 优化消费逻辑 | 异步处理、批量消费、减少 IO 操作、优化 SQL |
| 跳过非关键消息 | 紧急情况下，重置 Consumer Offset 到最新位置，牺牲部分数据保证服务可用 |
| 临时队列削峰 | 积压消息导入临时 Topic，额外部署消费者组消费 |

**面试金句：** Kafka 消费者并行度上限等于 Partition 数，所以扩容消费者之前必须先扩容分区。遇到线上积压，先定位是消费慢还是 Rebalance，消费慢就扩容+异步，Rebalance 就查消费者心跳和分区分配策略。
