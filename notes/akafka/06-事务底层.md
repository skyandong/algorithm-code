# 十二、事务底层原理 —— EOS 到底保到哪里

02-消息保障讲了事务的**用法**（`beginTransaction` / `commitTransaction`），这一篇讲**底层**。面试问到事务，答完 API 一定会被追问：协调者是谁？状态存哪？消费者怎么知道这批消息提交了没？

---

## 1. EOS 的三个层次

| 层次 | 手段 | 保证范围 | 局限 |
|------|------|---------|------|
| 最多一次（at most once） | 先提交 offset 再处理 | 不重复 | 会丢 |
| 至少一次（at least once） | 先处理再提交 offset | 不丢 | 会重复（**默认语义**） |
| 精确一次（exactly once） | 幂等 + 事务 | 不丢不重 | 仅限 Kafka 内部（见第 6 节） |

**幂等和事务是两件事**：幂等解决"单分区单会话内重试不重复"，事务解决"跨分区跨会话的原子性"。事务依赖幂等（开事务会自动开幂等）。

## 2. 事务的三大组件

```
┌──────────────┐   1. InitProducerID(transactional.id)
│   Producer   │ ─────────────────────────────►  TransactionCoordinator
│ (带 TxID)    │ ◄─────────────────────────────  返回 PID + epoch
└──────┬───────┘
       │ 2. 生产消息（带 PID + epoch + seq）
       ▼
┌──────────────┐   3. AddPartitionsToTxn / AddOffsetsToTxn
│ 用户 Topic   │ ◄─────────────────────────────  Coordinator 记录参与方
└──────┬───────┘
       │ 4. EndTxn(COMMIT / ABORT)
       ▼
┌──────────────────────┐
│ __transaction_state  │  事务状态日志（内部 Topic，默认 50 分区）
│ (Coordinator 状态)   │  存 TxID → 状态/参与分区/PID/epoch/超时
└──────────────────────┘
       │ 5. 写 control batch（COMMIT/ABORT marker）到各参与分区
       ▼
┌──────────────┐
│ 用户 Topic   │  消费者据此判断这批消息是否可见
└──────────────┘
```

- **TransactionCoordinator**：运行在某个 Broker 上的模块，不是独立进程。每个 `transactional.id` 按哈希映射到 `__transaction_state` 的某个分区，该分区的 leader 就是这个 TxID 的协调者
- **`__transaction_state`**：内部 Topic，持久化事务状态，Broker 重启后能恢复未完成的事务
- **epoch（producer epoch）**：每次 `InitProducerID` 时单调递增

## 3. epoch 与僵尸写防护（zombie fencing）

这是事务里最值得讲的设计，也是面试区分度最高的一题。

**问题场景**：Producer 实例 A 网络卡顿被判定超时，业务起了一个新实例 B（相同 `transactional.id`）。过一会 A 活过来了，继续写消息 —— 这就是**僵尸实例**，它的数据会污染 B 的事务。

**解法**：A 和 B 用同一个 TxID，B 调 `InitProducerID` 时 epoch 从 5 变成 6。之后：
- A 发来的请求携带 epoch=5 < 6 → Coordinator 和分区 Leader 直接拒绝，返回 `ProducerFencedException`
- A 被"围栏"住，无法再写入

**关键前提**：`transactional.id` 必须**稳定且唯一**（通常取服务实例标识或分区编号），不能每次启动随机生成 —— 随机的话每次都是新 TxID，fencing 就失效，僵尸实例照样能写。

## 4. LSO：Last Stable Offset

事务消息**写入分区后立刻就存在**，只是对 `read_committed` 的消费者**不可见**。可见性边界就是 **LSO**。

```
分区日志：  ...  msg100   msg101   msg102(Tx-A)  msg103(Tx-A)  msg104
                                   ↑                           ↑
                               Tx-A 未提交                   HW / LEO
                                   ↑
                                  LSO = 102  ← 第一个未决事务的起始 offset
```

- **LSO = 第一个仍未提交（未决）事务的起始 offset**
- `isolation.level=read_committed`（默认就是这个）的消费者只能读到 **LSO 之前**的消息
- `isolation.level=read_uncommitted` 能读到全部（包括未提交和已中止的），一般只在排查问题时用

**这条推论非常重要**：一个长时间不提交的事务会把 LSO 卡死，**后面所有正常消息都读不出来** —— 消费者的 lag 会暴涨，但 Kafka 本身没有任何异常。所以 `transaction.timeout.ms`（默认 60 秒）不能设太大。

## 5. control batch（事务标记）

Coordinator 在收到 `EndTxn` 后，会向每个参与分区写一条特殊的 **control batch**（也叫 transaction marker），内容是 `COMMIT` 或 `ABORT`。

消费者读到 control batch 时：
- 是 COMMIT → 之前那些属于该事务的消息可以放行
- 是 ABORT → 那些消息直接丢弃（**注意：消息仍然占磁盘，只是被跳过**）

**所以 abort 的事务消息不会被物理删除**，消费者要额外读一遍再丢弃，还占保留期内的空间。事务用得越多，这类垃圾越多。

## 6. EOS 的边界：它不是端到端的

这是最容易被过度宣传的一点。**Kafka 的事务只覆盖 Kafka 内部**。

```
read from topic A → 处理（写 MySQL）→ write to topic B
```

如果处理环节写了数据库，事务管不到 MySQL。真正的"端到端 EOS"需要：

1. **消费位移也进事务**：用 `AddOffsetsToTxn` 把"消费了 A 的 offset 100"和"生产到 B"放进同一个事务 —— 这一步 Kafka 原生支持，是整个方案里最漂亮的部分
2. **外部系统自己做幂等**：写入 MySQL 时用业务主键 / 唯一索引 / 状态机去重（回到 02-消息保障的"消费端业务幂等"）

**结论**：Kafka 的 EOS 严格说叫"**读-处理-写回 Kafka 的 EOS**"。一旦链路里出现外部存储，就必须业务侧兜底。

## 7. 代价：事务为什么不能滥用

- 每条事务额外增加 `AddPartitionsToTxn` + `EndTxn` + 每个分区写 marker 的 RPC 往返
- 事务消息要等 marker 才能被消费，**端到端延迟明显上升**
- abort 的消息占空间占 IO
- 未决事务卡住 LSO 会拖垮整个分区的消费者

**实践建议**：只在"消费-处理-生产"这类真正需要原子的链路用事务；普通场景用**幂等生产 + 消费端业务去重**，成本低得多，效果等价。

**面试金句：** 事务靠 TransactionCoordinator 协调，`__transaction_state` 存状态，用 epoch 做僵尸实例 fencing（所以 transactional.id 必须固定），用 control batch 标记提交或中止，消费者靠 LSO 判断可见边界。事务只覆盖 Kafka 内部，一旦涉及外部存储就必须业务侧幂等兜底。另外未决事务会卡死 LSO 导致消费者读不到新消息，所以 transaction.timeout.ms 不能设太大。
