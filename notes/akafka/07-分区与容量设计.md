# 十三、分区数与容量设计 —— 建 Topic 之前要想清楚的事

这一篇是纯工程题。面试官问"你的 Topic 分区数怎么定的"，答"随便定的 / 默认 3 个"基本就结束了；答出**估算方法 + 代价 + 不可逆性**，才是做过生产的样子。

---

## 1. 分区数怎么估

### 核心公式

```
分区数 = max( 目标吞吐 / 单分区吞吐 , 峰值消费者实例数 )
```

**单分区吞吐基准**（经验值，务必说明是经验值）：

| 场景 | 单分区生产吞吐 | 单分区消费吞吐 |
|------|--------------|--------------|
| 小消息（100B ~ 1KB），acks=1 | 5 ~ 10 MB/s | 10 ~ 20 MB/s |
| 小消息，acks=all + RF=3 | 2 ~ 5 MB/s | 10 ~ 20 MB/s |
| 大消息（10KB+） | 条数下降，字节吞吐略升 | 同上 |

消费通常远快于生产（消费是顺序读 + 零拷贝，生产要同步副本），所以**瓶颈一般在生产端**。

### 算一遍

假设：峰值 50 MB/s，消息平均 1KB，acks=all + RF=3，消费者最多部署 12 个实例。

```
按吞吐：  50 MB/s ÷ 3 MB/s ≈ 17 个分区
按消费者：12 个实例 → 至少 12 个分区
取 max → 17，再留 50% 余量 → 24 ~ 32 个分区
```

**留余量的原因**：分区只能加不能减（见第 3 节），而加分区会破坏 key 顺序映射（见 04-顺序性）。所以宁可一开始就多一点。

### 验证手段

分区数定完必须压测。Kafka 自带工具：

```bash
# 生产压测
kafka-producer-perf-test.sh --topic bench --num-records 5000000 \
  --record-size 1024 --throughput -1 --producer-props bootstrap.servers=localhost:9092 acks=all

# 消费压测
kafka-consumer-perf-test.sh --topic bench --messages 5000000 --bootstrap-server localhost:9092
```

## 2. 分区过多的代价

分区不是越多越好，这四个代价必须能说出来：

| 代价 | 说明 |
|------|------|
| **文件句柄与内存** | 每分区每 segment 至少 3 个文件（见 05-存储与读路径），1000 分区 × 10 segment × 3 = 30000 文件 |
| **端到端延迟上升** | 生产端要等所有副本同步完才 ack，分区越多、批次越碎，延迟越高。有实测：分区从 8 加到 256，acks=all 的 p99 延迟显著上升 |
| **故障恢复变慢** | 分区多 → leader 选举与元数据广播的量变大，Broker 重启后恢复时间从秒级涨到分钟级 |
| **元数据膨胀** | 每个分区的元数据要在 KRaft/ZK 里维护，超大规模集群（十万分区）元数据同步会成为瓶颈 |

**经验上限**：单集群总分区数控制在**几万**以内（业界常见建议单 Broker 不超过 2000~4000 个分区，含副本）。

## 3. 分区只能增，不能减

**Kafka 不支持减少分区数**（`kafka-topics.sh --alter --partitions N` 只接受更大的 N）。

原因：删掉一个分区意味着丢弃该分区全部数据，且 key→partition 映射全变，无法保证语义。

**所以"先建 1 个分区，不够了再加"是双重错误**：
1. 加分区破坏了同 key 的顺序保证
2. 如果之后发现过多，还减不回去 → 只能重建 Topic 迁移

## 4. 消息体大小的三件套

Kafka 默认单条消息上限 **1 MB**。调大必须**三处配套改**，只改一处会出诡异错误：

| 位置 | 参数 | 默认 |
|------|------|------|
| Broker / Topic | `max.message.bytes` | 1 MB |
| Producer | `max.request.size` | 1 MB |
| Consumer | `fetch.max.bytes`（单次 fetch 总量）、`max.partition.fetch.bytes`（单分区） | 50 MB / 1 MB |
| Broker 副本同步 | `replica.fetch.max.bytes` | 1 MB ← **最容易漏**，漏了会导致副本同步失败、ISR 收缩 |

### 大消息的真实问题

技术上能调到 10 MB，但工程上**强烈不建议**：

- 页缓存被大消息占满，影响其他正常消息
- 单条处理耗时长，容易触发 `max.poll.interval.ms` 超时
- 网络和磁盘的吞吐曲线在小消息时反而更差

**推荐做法：消息只放引用（claim-check 模式）**

```
Kafka 消息：{"order_id":"ORD-1","payload_url":"s3://bucket/xxx.json"}
大 payload：放对象存储（S3/OSS/COS）
```

把消息体控制在 **1 ~ 10 KB** 是这个模式的甜点区。

## 5. 副本数与可用性配置

生产标准配置：

| 参数 | 推荐值 | 说明 |
|------|-------|------|
| `replication.factor` | 3 | 3 副本是可靠性与成本的平衡点，2 副本无法容忍"一挂一维护" |
| `min.insync.replicas` | 2 | 与 `acks=all` 配合：至少 2 个副本同步成功才确认 |
| `acks` | all | Producer 侧 |
| `unclean.leader.election.enable` | false | 禁止非 ISR 副本当 leader（见 03-原理与消费者） |

**这组配置的语义**：容忍 1 个 Broker 宕机而不丢数据、不中断写入。如果 `min.insync.replicas=1`，acks=all 就退化成 acks=1，多副本形同虚设 —— 这是个常见配置错误。

## 6. 分区倾斜（数据热点）

按 key 路由时，如果某些 key 的消息量远超其他，就会造成**分区倾斜**：

```
分区 0: ████████████████████  (某大客户，占 60%)
分区 1: ███
分区 2: ██
分区 3: ███
```

后果：只有 1 个消费者在扛 60% 的流量，**其他消费者空转**，加消费者也没用。

**排查**：看各分区的 end offset 增速是否均衡。
**解法**：
1. 加盐：`hash(key + "_" + (seq % N))` 打散，消费端按原始 key 聚合
2. 识别热点 key，单独路由到专属 Topic
3. 用 `UniformSticky` 而不是纯 key 分区（牺牲顺序换均衡）

## 7. Topic 设计规范清单

- **命名**：`<业务域>.<事件类型>.<版本>`，如 `trade.order.created.v1`。版本后缀让 schema 演进有退路
- **一个 Topic 只放一种事件**（同一 schema），不要混装
- **保留期按业务定**：可重放的流水类设 7 天；状态类可用 compact；审计类可设 30 天
- **不要建超大 Topic**：单 Topic 分区数超过 100 通常说明该拆分了
- **禁止无 key 又要求顺序**（见 04-顺序性）

**面试金句：** 分区数按「目标吞吐 ÷ 单分区吞吐」和「峰值消费者数」取最大值再留 50% 余量，因为分区只能加不能减、加了还会破坏 key 的顺序映射。分区过多的代价是文件句柄、端到端延迟、故障恢复时间和元数据膨胀。消息体默认 1MB 上限，调大要同时改 broker/producer/consumer/replica-fetch 四处，但工程上推荐只传引用，大 payload 放对象存储。
