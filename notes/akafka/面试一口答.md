# Kafka 面试一口答清单

> 从各篇笔记提炼的"张口就来"清单：被问到要能不带停顿直接说出来。
> 对应章节：`01-架构.md` ~ `10-选型对比.md`，实验代码在 `experiments/`。
>
> **记忆主线：Kafka 本质是分布式「追加日志」（Log），不是队列——消息消费后不删、靠 offset 记进度、可回溯。一切设计（顺序写、零拷贝、分区、HW、compact）都围绕"把磁盘当顺序日志用"展开。**

---

## 一、架构与副本（最高频概念题）

### 1. 六个核心概念（背口诀）
**Topic 管逻辑，Partition 管物理，Leader 管读写，Follower 管同步，Offset 管进度，Group 管竞争。**

- Topic 是逻辑队列，物理上切成多个 **Partition**（每个是有序日志，跨分区无序）
- 每个分区多个副本，**Leader 负责读写，Follower 只同步**
- Consumer 靠 **Offset** 记录消费进度（不是 Broker 记录）
- 同一 Group 内一条消息只被一个消费者消费

### 2. 为什么去 ZooKeeper（KRaft）
- ZK 模式（<3.3）：靠 ZK 管元数据 + 选 Controller，运维复杂、ZK 成瓶颈、故障切换慢
- **KRaft**（2.8 预览 / 3.3 正式）：去掉 ZK，用内置 **Raft** 在 Broker 内选 Controller、存元数据——简化架构、提升扩展性

## 二、消息可靠性（不丢 / 不重 / 积压）

### 3. 怎么保证消息不丢？（三段式，必背）
| 端 | 手段 |
|----|------|
| **Producer** | `acks=all`（ISR 全部写入才确认）+ `retries>0` 重试 |
| **Broker** | `replication.factor≥3` + `unclean.leader.election.enable=false`（禁止非 ISR 当 leader） |
| **Consumer** | 关闭自动提交，**先处理业务、再提交 offset**（防止"业务失败但 offset 已提交"丢消息） |

> acks 与 fsync 无关：acks=all 只保证写入 ISR 各副本的 Page Cache，刷盘交给 OS 异步，持久性靠**多副本冗余**而非同步刷盘。

### 4. acks 三档
- `acks=0`：发完不管，最快最不可靠
- `acks=1`：Leader 写本地即确认，Follower 没同步就挂会丢
- `acks=all`（-1）：ISR 全确认，最可靠

### 5. 怎么保证不重复？（两个层次 + 业务兜底）
- **Producer 幂等**：Broker 分配 **PID**，消息带单调递增 **SequenceNumber**，按 (PID, partition, seq) 去重——**只保证单分区、单会话**，重启 PID 变
- **Kafka 事务**：跨分区原子写（详见第七节）
- **消费端业务幂等**（最实用）：唯一索引、Redis setnx、状态机校验——重复消息不改变状态

### 6. 消息积压怎么办？
> 先定位"消费慢"还是"Rebalance"。
- 消费慢 → 扩容消费者（**上限 = 分区数**）、异步化、批量、优化 SQL
- 分区少 → **先扩分区再扩消费者**
- 紧急 → 重置 offset 跳消息 / 临时 Topic 削峰

## 三、ISR / HW / LEO（原理必考）

### 7. 三个概念一句话
- **ISR**：与 Leader 保持同步的副本集合，只有它能竞选 Leader
- **LEO**：下一条待写入的 offset（最后一条 offset + 1）
- **HW**：ISR 中**所有副本的最小 LEO**——**消费者只能读到 HW 之前的数据**

### 8. 同步流程
Producer → Leader 写本地 → Follower 拉取更新自己 LEO → Leader 收到 ACK 后 **HW = min(ISR 各 LEO)** → 消费者只读 HW 前。

### 9. ISR 全挂了怎么办？
- `unclean.leader.election.enable=false`（默认/推荐）：等旧 Leader 恢复，**不丢数据但暂时不可用**
- `=true`：选非 ISR 副本当 Leader，**可用但可能丢数据**

---

## 四、高性能原理（"为什么快"四板斧）

### 10. Kafka 为什么快？
**顺序写 + 页缓存 + 零拷贝 + 批量压缩 + 分区并行**：
- **顺序写**：磁盘顺序写接近内存随机写，避免磁头寻道
- **页缓存**：写 OS Page Cache，异步刷盘，不经过 JVM 堆
- **零拷贝**：`sendfile()` 让数据从 Page Cache 直达网卡，不进用户态（省 2 次 CPU 拷贝）
- **批量 + 压缩**：Producer 攒批（batch.size/linger.ms）、Consumer 批量拉、Snappy/LZ4/ZSTD 压缩

> 金句：Kafka 不是"用了磁盘所以慢"，而是"把磁盘用成了内存的顺序写 + 内核零拷贝"。

## 五、顺序性（高频陷阱题）

### 11. Kafka 能保证顺序吗？（分段答）
1. **写入侧**：同 key 路由到同一分区（`hash(key) % 分区数`），分区内 append 保证 offset 有序
2. **消费侧**：单分区不等于消费有序——多线程并发处理会打乱
3. **端到端有序** = 同 key 同分区 + **消费端对该 key 串行处理**

### 12. 三个坑
- **无 key**：消息被粘性/打散到多分区，无顺序可言
- **重试乱序**：同分区内 `max.in.flight.requests.per.connection` 设 >1 时，前一条重试会让后面的先落盘
- **分区扩容破坏映射**：`hash(key) % N` 的 N 变了，同 key 会换分区 → **强顺序场景分区数必须一开始定死**

## 六、存储与读路径（"怎么根据 offset 找到消息"）

### 13. 磁盘结构
一个分区一个目录 `topic-0/`，里面是一组 **Segment** 文件：`.log`（消息本体）、`.index`（offset→物理位置）、`.timeindex`（时间戳→offset）、`.snapshot`、`leader-epoch-checkpoint`。

### 14. 三步定位（必背）
```
① 二分 segment 文件名（base offset 有序）→ 找到所在 segment
② 二分 .index 稀疏索引（≤目标 offset 的最大项）
③ 从该物理位置顺序扫描 ≤ 4KB，命中 offset
```
- **稀疏索引**：每 `index.interval.bytes`（默认 4KB）一条，索引项**定长 8 字节**、可 mmap 进内存、直接二分——所以查找几乎不碰磁盘
- 按时间戳读 = 先走 `.timeindex` 得 offset，再走上面三步

### 15. 日志清理（delete vs compact）
- **Kafka 不因消费而删消息**（日志模型 vs 队列模型的根本区别），删除只由保留策略触发
- `delete`（默认）：按时间（`log.retention.hours`=168）/大小删
- `compact`：按 key 保留最新值，语义变成"KV 状态流"；**墓碑消息**（value=null 表示删 key）保留 `delete.retention.ms`（24h）后物理删除
- **重要推论：积压超过保留期 = 数据永久丢失**（线上最严重事故之一）

## 七、事务底层（EOS 保到哪里）

### 16. EOS 三层次
| 层次 | 手段 | 保证 |
|------|------|------|
| 最多一次 | 先提交 offset 再处理 | 不重复，会丢 |
| 至少一次 | 先处理再提交 | 不丢，会重复（**默认**） |
| 精确一次 | 幂等 + 事务 | 仅 Kafka 内部 |

> 幂等解决"单分区单会话重试不重复"，事务解决"跨分区原子性"。事务依赖幂等。

### 17. 事务三大组件
- **TransactionCoordinator**：运行在某个 Broker 上的模块，每个 `transactional.id` 哈希到 `__transaction_state` 某分区，该分区 leader 即协调者
- **`__transaction_state`**：内部 Topic，持久化事务状态（TxID→状态/参与分区/PID/epoch）
- **epoch**：每次 `InitProducerID` 递增，用于僵尸写防护

### 18. 僵尸写防护（zombie fencing，区分度题）
实例 A 卡顿被判定超时 → 新实例 B（同 TxID）启动，epoch 5→6 → A 恢复后带 epoch=5 的请求被 Coordinator/Leader 拒绝（`ProducerFencedException`）。**前提：`transactional.id` 必须稳定唯一**，随机生成则 fencing 失效。

### 19. LSO 与 control batch
- **LSO = 第一个未决（未提交）事务的起始 offset**，`read_committed`（默认）只能读到 LSO 之前
- 事务消息写入后立刻占位，Coordinator 收到 EndTxn 后向各分区写 **control batch**（COMMIT/ABORT marker），消费者据此放行或跳过（abort 消息不物理删除）
- **推论：未决事务卡死 LSO，后面所有消息都读不到** → `transaction.timeout.ms`（默认 60s）不能设太大

### 20. EOS 的边界
**Kafka 事务只覆盖 Kafka 内部**。涉及外部系统（写 MySQL）时：消费位移进事务（`AddOffsetsToTxn`）+ 外部系统业务侧幂等。所以它严格叫"读-处理-写回 Kafka 的 EOS"。

## 八、分区与容量设计（工程题）

### 21. 分区数怎么估？（必背公式）
```
分区数 = max( 目标吞吐 ÷ 单分区吞吐 , 峰值消费者实例数 ) × (1 + 50% 余量)
```
单分区吞吐经验值：小消息 acks=1 约 5~10 MB/s；acks=all+RF=3 约 2~5 MB/s。**消费通常远快于生产，瓶颈在生产端。**

### 22. 分区过多的代价
文件句柄与内存（每分区每 segment 3 个文件）、端到端延迟上升、故障恢复变慢、元数据膨胀。经验上限：单 Broker 2000~4000 分区。

### 23. 分区只能增不能减
`kafka-topics --alter --partitions` 只接受更大的 N。**"先建 1 个不够再加"是双重错误**：加分区破坏 key 顺序映射，且减不回去只能重建迁移。

### 24. 消息体 1MB 上限（三件套 + 一个易漏）
默认单条 **1MB**，调大必须四处配套：`max.message.bytes`(broker)、`max.request.size`(producer)、`max.partition.fetch.bytes`(consumer)、**`replica.fetch.max.bytes`(副本同步，最容易漏，漏了副本同步失败 ISR 收缩)**。工程上推荐 **claim-check**：消息只放引用，大 payload 放对象存储。

### 25. 副本可用性配置
`RF=3` + `min.insync.replicas=2` + `acks=all` + `unclean.leader.election.enable=false` = 容忍 1 台宕机不丢数据不中断。**若 min.insync=1，acks=all 退化成 acks=1，多副本形同虚设**（常见配置错误）。

## 九、消费并发模型（踩坑分水岭）

### 26. 三种消费模型
- **A. 单线程 poll+处理**：有序，低吞吐
- **B. 多实例同 group**：并行度=分区数，**首选**，天然有序
- **C. poll + worker pool**：单条慢但分区受限时才用，**破坏顺序**

### 27. 位移提交竞态（必背）
并发处理 offset 10~14，13、14 先完成就提交 15，但 10 还在处理——进程崩溃后从 15 继续，**10 永久丢失**。解法是**滑动窗口**：维护完成位图，只提交到"最长连续已完成前缀"的水位线，绝不提交空洞之后。

### 28. max.poll.* 三件套与心跳（高频失分点）
| 参数 | 默认 | 作用 |
|------|------|------|
| `max.poll.records` | 500 | 单次 poll 返回条数 |
| `max.poll.interval.ms` | 5min | **两次 poll 间隔上限**，超时踢出组 |
| `session.timeout.ms` | 45s | 心跳超时判死，踢出组 |
| `heartbeat.interval.ms` | 3s | 心跳频率，应 ≤ session/3 |

> **心跳证明"我还活着"（后台线程发），max.poll.interval 证明"我还在干活"**。最隐蔽的坑：心跳正常但 Rebalance 依然发生——因为 poll 循环被慢处理阻塞超 5 分钟。

### 29. 静态成员与背压
- `group.instance.id`（2.3+）：滚动发布时实例短暂离开不触发 Rebalance，重连后恢复原分配
- 背压用 **Pause/Resume**（暂停拉取某分区）而不是 sleep（sleep 会阻塞 poll 循环触发超时）

## 十、监控与运维（经验题加分）

### 30. 分层指标三个最关键
**UnderReplicatedPartitions（应为 0）、ActiveControllerCount（应为 1）、消费者 lag**。lag 告警不能看绝对值，要看**增长趋势 + 预计追平时间**——真正要半夜叫醒人的只有一种：**预计追平时间 > 保留期剩余时间**（追平前数据就被删了）。

### 31. 六个典型事故一句话
- **lag 暴涨**：先分"消费慢"还是"Rebalance"
- **频繁 Rebalance**：查心跳/poll 阻塞/GC，上静态成员 + cooperative-sticky
- **消息丢了**：查 acks、unclean election、offset 提交时机、保留期
- **磁盘快满**：active segment 不会被删（清理不碰它），查大分区
- **ISR 收缩**：查 Follower 拉取瓶颈、`replica.fetch.max.bytes` 是否漏配
- **重复消费**：默认至少一次语义，靠业务幂等兜底

## 十一、选型对比（"Kafka 和 RocketMQ 怎么选"）

### 32. 一句话定位
Kafka=分布式**日志**（吞吐+生态最强，功能朴素）；RocketMQ=**业务队列**（延迟/事务/重试原生）；RabbitMQ=**消息代理**（延迟最低路由最灵活，吞吐短板）；Pulsar=**存算分离**（架构最新，运维最重）。

### 33. 三个关键差异（加分项）
- **延迟消息**：RocketMQ 原生 18 级；Kafka 要自建时间轮+中转 Topic
- **事务消息语义**：Kafka 管"写 Kafka 内部 + 提交位移"的原子；RocketMQ 是"半消息 + 本地事务 + 回查"，贴近业务分布式事务
- **Pulsar key_shared**：同 key 保序且不受分区数限制，Kafka 要"加盐 + 消费端聚合"绕过

### 34. 答题结构
先说"看场景"，再给维度，最后落到具体问题。**数据流/CDC/接 Flink → Kafka；订单等业务消息带延迟/事务 → RocketMQ；低延迟路由 → RabbitMQ；多租户弹性 → Pulsar；量小团队小 → 云托管别自建。**

## 速查：面试高频三连问

**Q1. Kafka 怎么保证消息不丢？**
> 三段式：Producer `acks=all` + 重试；Broker `RF≥3` + ISR + 禁止非 ISR 当选；Consumer 关自动提交、先处理业务再提交 offset。持久性靠多副本而非同步刷盘。

**Q2. Kafka 怎么保证顺序消费？**
> 只有分区内有序，无全局有序。同 key 路由到同分区保证写入有序；消费端必须对该分区串行处理才端到端有序。多线程会打乱、分区扩容会破坏 key 映射。

**Q3. Kafka 的事务（EOS）到底怎么回事？**
> TransactionCoordinator 协调，`__transaction_state` 存状态，epoch 做僵尸写 fencing（所以 transactional.id 必须固定），control batch 标记提交/中止，消费者靠 LSO 判断可见边界。但事务只覆盖 Kafka 内部，涉及外部存储必须业务侧幂等兜底；未决事务卡 LSO 会让消费者读不到新消息。
