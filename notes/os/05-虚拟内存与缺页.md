# 虚拟内存与缺页

> **核心认知：** 每个进程都以为自己独占一整块连续内存——这是**页表**变出来的幻觉。真实物理页只在**第一次访问某地址**时才分配，那次访问就是**缺页中断**。理解缺页，才能理解为什么"申请内存很快、第一次写很慢"，以及 RSS 为什么不能直接当"用了多少内存"。

---

## 1. 地址翻译：虚拟地址怎么变成物理地址

```
虚拟地址 ──▶ CR3（页表基址）──▶ 逐级查表 ──▶ 物理页框 + 页内偏移
                                    │
x86-64 四级页表（4KB 页，48 位虚拟地址）：
   PML4[9bit] → PDPT[9bit] → PD[9bit] → PT[9bit] → offset[12bit]
```

- 每次访存都查四级页表太慢 → **TLB**（地址翻译缓存）缓存最近用过的映射。TLB 命中约 1 个周期，未命中的页表遍历要几十个周期。
- 大页（Huge Page，2MB / 1GB）让一条 TLB 表项覆盖更大范围，**显著减少 TLB miss**——这是数据库与 JVM/Go 应用对大页感兴趣的原因。
- 透明大页（THP）由内核自动合并 2MB 页，但 `khugepaged` 的合并与碎片整理会造成**延迟抖动**，所以延迟敏感服务常见做法是 `echo madvise > /sys/kernel/mm/transparent_hugepage/enabled`。

## 2. 缺页：两种性质完全不同的中断

| 类型 | 触发场景 | 代价 |
|------|---------|------|
| **minor fault** | 页已在物理内存，只缺映射：匿名页首次写、COW 复制、mmap 的文件页已在页缓存 | 微秒级（纯内核操作） |
| **major fault** | 页不在内存，要从磁盘/swap 读进来 | 毫秒级（等 IO） |

**一次 `malloc` 之后立刻写，走的就是 minor fault**：`malloc`/`mmap` 只是登记了一段虚拟地址（VMA），物理页要等第一次访问才分配。这解释了两个现象：

- `malloc(1GB)` 瞬间返回（只登记了地址空间），
- 真正 memset 那 1GB 时耗时明显（一万多次缺页）。

**页表项还带着权限位**（可读/可写/可执行/用户态），所以缺页也是**内存保护**的实现方式：写只读页 → 缺页 → 内核判断是 COW 还是非法写（非法就发 SIGSEGV）。

## 3. 写时复制（COW）

```
fork()
  ├─ 父进程页表 ─┐
  └─ 子进程页表 ─┴─▶ 同一批物理页（全部标为只读）
                   │
   任一方写入 ──▶ 缺页 ──▶ 内核复制该页 ──▶ 各自拿到可写副本
```

- `fork` 因此极快（不复制内存，只复制页表）。
- 但"快"是有代价的：子进程一写，页就复制一次——所以 `fork` + 大量写 = 大量 minor fault + 内存翻倍。
- 现代程序多用 `fork` 后立刻 `exec`（复制的东西立刻被丢弃），内核为此有 `vfork`/`posix_spawn` 优化。

Go 里 `exec.Command` 最终走的就是 clone/vfork + exec 路径，所以"Go 起子进程慢"通常不是 COW 问题。

## 4. mmap：文件直接映射进地址空间

```go
data, err := syscall.Mmap(fd, 0, size, syscall.PROT_READ, syscall.MAP_SHARED)
// data 是 []byte，直接读就等于读页缓存里的内容，没有 read 的拷贝
```

| | `read` | `mmap` |
|---|---|---|
| 拷贝 | 页缓存 → 用户缓冲（一次 CPU 拷贝） | 无拷贝，直接访问页缓存 |
| 缺页 | 无（read 时已就位） | 首次访问触发 major fault（要读盘） |
| 随机访问 | 需要 seek + read | 天然支持，按页惰性加载 |
| 适用 | 顺序读、小文件 | 大文件随机读、共享内存 |

**代价**：缺页是同步的，且错页粒度是 4KB——顺序读大文件时"一页一次缺页"反而比 `read` 的批量预读慢。所以"mmap 一定更快"是错的。

## 5. RSS / PSS / VSS：三个数各是什么

| 指标 | 含义 | 陷阱 |
|------|------|------|
| **VSS**（Virtual） | 申请的虚拟地址空间总量 | 含已 mmap 未访问的段，通常大得吓人，无实际意义 |
| **RSS**（Resident） | 真正占用的物理页 | **共享页在多进程里各算一份**，N 个进程共享同一库时总和虚高 |
| **PSS**（Proportional） | 共享页按共享进程数均摊 | 最接近"这个进程实际该背多少内存" |
| **USS**（Unique） | 独占页 | 杀掉这个进程能省多少 |

```bash
cat /proc/<pid>/status | grep -E 'VmRSS|VmSize|RssAnon|RssFile'
cat /proc/<pid>/smaps_rollup        # 一行给出 Pss/Pss_Anon/Pss_File
```

**线上看内存别只看 RSS**：一个加载了大量共享库的服务，RSS 很高但 PSS 可能只有一半；排查"到底谁占了内存"时按 PSS 排序才公平。

## 6. Go 程序的内存视角

```
用户视角：runtime.ReadMemStats 的 HeapAlloc（活对象）
中间层：  HeapInuse（span 占用）、HeapIdle（已归还但保留）、HeapReleased（还给 OS）
OS 视角： RSS
```

几个常见困惑：

- **为什么 `HeapReleased` 涨了 RSS 却没降？** 因为归还用的是 `madvise(MADV_FREE)` 而非 `MADV_DONTNEED`——页还给内核但 RSS 计数要等内存压力才更新。Go 1.12~1.15 正是这个行为（可用 `GODEBUG=madvdontneed=1` 临时切回），**Go 1.16 起默认改回 `MADV_DONTNEED`**，RSS 会及时下降。
- **为什么大块内存不还给 OS？** Go 的 scavenger 是渐进式归还，为了平衡 syscall 开销与内存占用；`debug.FreeOSMemory()` 会强制归还一次。
- **为什么第一次分配慢？** 缺页——Go 从 OS 拿到的页要等写入才真正落物理内存。

## 7. 观测

```bash
getconf PAGESIZE                                  # 页大小，通常 4096
cat /proc/<pid>/stat | awk '{print "minflt="$10, "majflt="$12}'
perf stat -e page-faults,minor-faults,major-faults -p <pid> sleep 5
```

判读：

- **major fault 持续增长** → 真的在读盘（或 swap），查内存压力与 IO。
- **minor fault 极高** → 频繁申请/释放内存、COW、频繁 mmap；Go 服务里常对应高分配率（看 `allocs/op`）。
- 缺页本身不可怕，**缺页引发的同步 IO** 才可怕（延迟毛刺的直接来源）。

## 8. 记忆锚点（面试 30 秒版）

> "虚拟内存靠多级页表和 TLB 把虚拟地址翻译成物理页；malloc 只登记地址空间，物理页在第一次访问时才分配，这次访问就是缺页——页已在内存的 minor 很快，要从磁盘读的 major 要走 IO。fork 靠写时复制共享只读页，写的时候才复制。RSS 把共享页重复计数，PSS 才是均摊后的真实占用。"
