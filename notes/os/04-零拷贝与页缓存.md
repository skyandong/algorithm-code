# 零拷贝与页缓存

> **核心认知：** 一次"读文件发网络"的朴素写法要拷 **4 次**、切换 **4 次**用户态/内核态。零拷贝不是"不拷贝"，而是**不把数据搬进用户态**——省掉的正是那两次最没必要的拷贝。而这一切的前提是页缓存：磁盘的数据本来就已经在内存里了。

---

## 1. 页缓存：所有文件 IO 的中转站

```
读文件：磁盘 ──DMA──▶ page cache ──CPU 拷贝──▶ 用户缓冲
写文件：用户缓冲 ──CPU 拷贝──▶ page cache ──回写──▶ 磁盘
```

- 读时先查页缓存，命中则**完全不碰磁盘**（第二次读同一个文件往往快一个数量级）。
- 写默认是**写缓存**（writeback），延迟回写：脏页攒到 `dirty_ratio`（默认 20%）或超过 `dirty_expire_centisecs`（默认 30s）才批量落盘。
- 所以 `write()` 返回不代表落盘；要保证持久化必须 `fsync`。**`fsync` 刷数据 + 元数据（如 mtime、大小），`fdatasync` 只刷数据**——日志追加场景用 fdatasync 能省一次元数据 IO。

页缓存占的是"可回收内存"：`free` 里的 `buff/cache` 高不是问题，`available` 才是可用内存。

---

## 2. 朴素的 read + write：4 次拷贝

```
用户态            内核态                          硬件
  │
  │ read() ───────▶ ①DMA: 磁盘 → page cache
  │                ②CPU: page cache → 用户缓冲
  │ ◀──────────────
  │
  │ write() ──────▶ ③CPU: 用户缓冲 → socket 发送缓冲
  │                ④DMA: socket 缓冲 → 网卡
  │ ◀──────────────
```

| 次数 | 类型 | 内容 |
|------|------|------|
| ① | DMA | 磁盘 → 页缓存 |
| ② | CPU 拷贝 | 页缓存 → 用户缓冲 |
| ③ | CPU 拷贝 | 用户缓冲 → socket 缓冲 |
| ④ | DMA | socket 缓冲 → 网卡 |

加上 4 次用户态/内核态切换。**关键在于 ②③ 这两次 CPU 拷贝完全是多余的**——应用只是想把数据从文件送到网卡，根本没打算处理它。

---

## 3. sendfile：两次拷贝、两次切换

```
sendfile(out_fd=socket, in_fd=file)
  │
  │ ──────────────▶ ①DMA: 磁盘 → page cache
  │                 ②数据被挂到 socket 缓冲（CPU 拷贝，或 SG-DMA 直接引用）
  │                 ③DMA: socket 缓冲 → 网卡
```

- **CPU 拷贝降到 0**（网卡支持 scatter-gather DMA 时，描述符直接指向页缓存，连 ② 都省掉）。
- **用户态完全不经手数据**，上下文切换只有 2 次。
- 局限：数据只能"进到 fd 里"，应用改不了内容（要改就得回到用户态）。

Nginx 的 `sendfile on`、Kafka 的消息下发、静态文件服务，走的都是这条路。

```nginx
sendfile on;            # 打开 sendfile
tcp_nopush on;          # 配合 sendfile，攒满一包再发
```

## 4. mmap + write：三次拷贝、四次切换

```
mmap(file) → 页缓存直接映射进用户地址空间（不拷贝）
write(socket) → 页缓存 → socket 缓冲（CPU 拷贝）→ 网卡（DMA）
```

| 方案 | 拷贝次数 | 切换次数 | 适用 |
|------|---------|---------|------|
| read + write | 4（2 次 CPU） | 4 | 需要对数据做处理 |
| mmap + write | 3（1 次 CPU） | 4 | 随机访问大文件、需要原地改 |
| sendfile | 2（0 次 CPU，SG-DMA 下） | 2 | 纯转发（文件→socket） |
| splice | 2（pipe 传页引用） | 2 | 代理转发（socket→socket 也可） |

**注意一个反直觉结论**：小文件用 sendfile 不一定最快——省下的 CPU 拷贝抵不过 syscall 与 DMA 的固定开销，实践中大文件收益才明显（这也是"小文件用 nginx 反而要关 sendfile"的说法来源，实际取决于负载）。

## 5. Go 里怎么吃到零拷贝

Go 的 `io.Copy(dst, src)` 会先看 `dst` 有没有实现 `ReaderFrom`——`*net.TCPConn` 实现了，于是走 `sendfile`：

```go
// 这段代码在 Linux 上会走 sendfile（零拷贝），不是逐块拷贝
f, _ := os.Open("/data/big.bin")
defer f.Close()
conn.WriteHeader-ish... // 略
io.Copy(conn, f)        // *os.File → *net.TCPConn ⇒ sendfile
```

**但很容易无意中破坏它**：

```go
io.Copy(conn, bufio.NewReader(f))   // ❌ 包了一层，ReaderFrom 用不上，退回用户态拷贝
io.Copy(io.MultiWriter(conn, log), f) // ❌ 多路写，必须经过用户态
```

判断标准：**只有"源是文件、宿是 socket"且中间没夹任何包装时**才可能走 sendfile。`bufio`、`gzip`、`LimitReader` 一加，零拷贝就没了。

## 6. Direct IO：绕过页缓存的那条路

`O_DIRECT` 让读写**不经过页缓存**，直接对着磁盘做 DMA。数据库（MySQL InnoDB 的 `innodb_flush_method=O_DIRECT`）、自研存储引擎会用它，因为：

- 它们自己有更懂业务的缓存（Buffer Pool），页缓存是重复缓存，白占内存。
- 避免"双缓冲"导致的额外一次拷贝。

代价：

- **对齐要求苛刻**：偏移、长度、内存地址都要按块大小（通常 512B 或 4KB）对齐，不对齐直接 `EINVAL`。
- **失去预读**：页缓存会做顺序预读，Direct IO 不做，顺序读要自己攒大块。
- 小随机写会退化：每次都要落盘，没有合并机会。

**结论：应用层除非在写存储引擎，否则别碰 O_DIRECT。**

## 7. 观测

```bash
iostat -x 1                 # %util、await、r/s w/s：判断是不是真的在打盘
vmstat 1                    # bi/bo（块设备读写）、cache 增长、si/so
grep -E 'Cached|Dirty|Writeback' /proc/meminfo   # 页缓存规模与脏页量
```

排查"读文件慢"时先看页缓存：

- 第一次读慢、第二次快 → 页缓存生效，正常。
- 每次都慢 → 文件太大/被 `posix_fadvise(DONTNEED)` 丢弃，或用了 Direct IO。
- `Dirty` 长期很高 + `iostat` 写满 → 回写跟不上写入速度，`fsync` 会突然变慢。

## 8. 记忆锚点（面试 30 秒版）

> "朴素地 read 文件再 write 到 socket 要 4 次拷贝、4 次切换，其中两次 CPU 拷贝完全多余，因为应用不碰数据。sendfile 让数据从页缓存直接挂到 socket 缓冲，CPU 拷贝降到 0、切换降到 2 次；Kafka 和 nginx 的静态下发都靠这个。前提是页缓存——数据已经在内存里，才谈得上'不拷贝'。Go 的 io.Copy 在文件→TCPConn 时会走 sendfile，但一加 bufio 就退化了。"
