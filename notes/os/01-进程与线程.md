# 进程与线程

> **核心认知：** 进程是**资源容器**（地址空间、fd 表、信号处理），线程是**调度单位**。Linux 内核对两者一视同仁——都是 `task_struct`，差别只在于 `clone` 时共享了哪些东西。Go 的 goroutine 既不是进程也不是线程，它是**用户态调度的协程**，最终仍要跑在内核线程上。

---

## 1. 一视同仁的 task_struct

Linux 没有"进程"这个结构体，只有 `task_struct`。`fork()` / `pthread_create()` 最终都走 `clone(flags)`，靠标志位决定共享粒度：

| 标志 | 共享什么 | 后果 |
|------|---------|------|
| `CLONE_VM` | 地址空间（同一份 mm_struct） | 线程间改内存立即可见 |
| `CLONE_FILES` | fd 表 | 一个线程 close，所有线程都看不到 |
| `CLONE_FS` | 当前目录、umask | `chdir` 影响全进程 |
| `CLONE_SIGHAND` | 信号处理函数 | 信号可以由任意线程处理 |
| `CLONE_THREAD` | 线程组（同一 TGID） | `ps` 里显示为同一进程下的多个线程 |

`pthread_create` 用的是 `CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | ...`；`fork` 一个都不加（靠写时复制共享物理页，但地址空间是两份）。

**面试常问"线程共享什么、独有什么"**，标准答法：

- 共享：地址空间（代码/堆/全局变量）、fd 表、信号处理、当前目录、进程 ID
- 独有：栈、寄存器上下文、线程 ID、`errno`、信号屏蔽字、调度优先级

## 2. 切换成本：线程便宜，进程贵

| | 同进程线程切换 | 跨进程切换 |
|---|---|---|
| 地址空间 | 不变，**不换页表** | 换 CR3，TLB 失效 |
| 内核开销 | 保存/恢复寄存器、切换内核栈 | 额外切换 mm、刷新 TLB、cache 局部性变差 |
| 典型量级 | 1~2 µs | 数 µs（TLB 缺失后更高） |

切换永远是**内核态**动作：即使两个用户态线程，也要陷入内核、保存上下文。所以"协程切换便宜"的本质是**压根不陷内核**——Go 的 goroutine 切换在用户态完成，只要几十纳秒。

## 3. Go 的三层模型：G / M / P

```
G (goroutine)  用户态协程：自己的栈（初始 2KB，按需增长，上限 1GB）
     ↕ 绑定
M (machine)    内核线程：真正被 CPU 调度的实体，有独立的内核栈
     ↕ 需要
P (processor)  执行许可：本地运行队列 + mcache，数量 = GOMAXPROCS
```

- **M 是内核线程**，Go runtime 直接 `clone` 出来（不是走 pthread），每个 M 有一个 `g0` 栈专供调度器用。
- **阻塞系统调用**时，M 会带着 G 一起阻塞，runtime 把 P **hand off** 给别的 M 继续跑其他 G——所以"Go 里一个阻塞调用不会拖死整个程序"。
- 但**阻塞得太多会真的创建大量线程**：每个阻塞中的 M 都要占一个内核线程 + 栈（Go 里默认 8KB 是 OS 线程栈的起步量级，不是 8MB 的 pthread 默认值）。

**这就是"goroutine 泄漏"和"线程暴涨"的因果链**：大量 goroutine 卡在阻塞 syscall（读文件、cgo 调用、无超时的网络 IO）→ runtime 不断创建 M → `Threads` 数飙升 → 内存与调度开销一起涨。

---

## 4. 栈：2KB 对比 8MB

| | goroutine | pthread 线程 |
|---|---|---|
| 初始栈 | 2KB（连续栈，按需倍增/收缩） | 8MB（`ulimit -s` 默认，预留下来） |
| 增长方式 | 拷贝到更大的栈（连续栈） | 固定大小，溢出即崩 |
| 1 万个的成本 | 约 20MB 起步 | 理论 80GB（所以线程池才有存在意义） |

所以"起 10 万 goroutine"是常规操作，而"起 10 万线程"直接 OOM。但**栈小也意味着不能递归太深**，Go 的栈增长靠逃逸分析无法解决的深递归会触发多次栈拷贝。

## 5. 观测：怎么确认是线程问题还是协程问题

```bash
ps -o pid,nlwp,comm -p <pid>        # nlwp = 线程数（Linux）
cat /proc/<pid>/status | grep Threads
top -H -p <pid>                     # 按线程看 CPU，找出最忙的线程
```

Go 侧三种手段：

```go
runtime.NumGoroutine()              // 当前协程数（监控兜底）
pprof.Lookup("threadcreate").Count() // 创建过的内核线程数（M 的上限估计）
pprof.Lookup("goroutine").WriteTo(w, 1) // 每个协程卡在哪一行
```

判读：

- `NumGoroutine` 稳定增长 + `Threads` 不涨 → 协程泄漏（阻塞在 channel/锁）
- 两者一起涨 → 阻塞在**系统调用**上，runtime 在为它创建 M
- `Threads` 接近上限（`ulimit -u`）→ 已经危险，先查 cgo / 阻塞 IO

## 6. 记忆锚点（面试 30 秒版）

> "进程是资源容器，线程是调度单位；Linux 里都是 task_struct，靠 clone 的标志位决定共享地址空间、fd 表、信号处理。线程切换不换页表所以比进程切换便宜，但都要陷内核；goroutine 的切换在用户态，只要几十纳秒。Go 的 M 就是内核线程，阻塞系统调用会 hand off P 并可能新建 M——所以大量阻塞 goroutine 会真的把线程数顶上去。"

## 实验

`go run ./experiments/ threads` 观察协程数与内核线程数的关系：

- 起 1 万个阻塞在 channel 上的 goroutine：`NumGoroutine` 涨到 1 万，`threadcreate` 计数基本不动
- 对比结论：协程是"用户态排队"，不占内核线程；只有阻塞系统调用才需要新 M
