# 锁与协调实践：etcd vs Redis vs ZK

> **核心认知：** 分布式锁的正确性上限由它的存储层决定——**etcd 的锁是 Raft 提交（线性一致，主挂了锁状态也不丢），Redis 的锁是主库内存 + 异步复制（主挂了锁可能凭空消失），ZK 是 ZAB（同为共识，会话语义更细腻）**。所以「Redis 锁不安全」不是实现 bug，是 01 篇 PACELC 选择的必然：AP 存储 + 基于超时的租约 = 客户端时钟漂移/进程停顿都可能让「持锁者还在干活，锁已经被别人抢走」。工程正解分层：**互斥访问（缓存击穿防护、任务去重）用 Redis 锁（便宜、快、偶尔重叠可接受）；正确性攸关（选主、唯一性分配、分布式事务决策）用 etcd/ZK（贵、慢、绝不重叠）**——Redlock 想用多数派 Redis 补正确性，但被 Kleppmann 证明在时钟假设下依然不严格安全，它的定位是「更好一点的 Redis 锁」而不是 etcd 平替。

前置知识：Redis 单节点锁与看门狗（`notes/redis/08-分布式锁.md`——本篇的对照基线）、Raft 提交语义（本模块 `02`）。

## 1. 锁正确性的两个前提

一把锁「安全」需要同时满足：

1. **互斥（safety）**：任一时刻最多一个客户端认为自己持锁；
2. **活性（liveness）**：锁最终会被释放（持锁者崩溃后，别人能拿到）。

分布式环境对这两个前提各有攻击手段：

- **互斥的攻击者：故障切换**。持锁的 Redis 主挂了，从库接管但还没收到锁记录——第二个客户端成功加锁，此刻两个「持锁者」。根本原因：锁状态建立在**异步复制**的存储上（对照 01 篇：AP 选择的代价）；
- **互斥的攻击者：进程停顿**。客户端 A 拿到锁（TTL 10s）→ GC/VM 暂停/页错误 15s → 醒来时锁早过期、B 已持锁——A 继续按「我持锁」干活。**这个攻击对所有基于超时的锁都成立，无解，只能靠 fencing 收敛**；
- **活性的攻击者：持锁者崩溃**。必须有人替它释放——**租约（lease/TTL）** 是万能答案：锁绑定一个会过期的时间，崩溃后自动开放。

由此得出锁设计的两个必备件：**租约（保活性）** + ** fencing token（保互斥的降级手段）**。fencing token：锁服务每次授锁发一个单调递增的令牌（33），资源方（存储）拒绝携带旧令牌（32）的写——迟到的旧持锁者即使「以为」自己持锁，写入也会被拒。**这把互斥的执行点从客户端自觉转移到了资源侧强制**。

## 2. 三套存储的锁语义对比

| 维度 | Redis 单节点 | etcd | ZooKeeper |
|---|---|---|---|
| 存储一致性 | 异步复制（AP） | Raft 线性一致（CP） | ZAB 线性一致（CP） |
| 加锁 | `SET key val NX PX ttl` | 事务：比较 revision + put + lease | 创建 `/lock/xx-` 顺序临时节点 |
| 崩溃自愈 | TTL 过期 | lease TTL 过期 | **会话断开自动删** |
| 持锁者判定 | 抢到 key 的人 | **revision 最小者**（天然公平队列） | 序号最小者 |
| 锁唤醒 | 轮询/发布订阅 | watch 前一个 key | watch 前一个节点 |
| fencing | Lua 返回计数器（要自建） | revision 天然单调（现成） | cversion（现成） |
| 性能 | 最高（内存） | 中 | 中 |
| 正确性 | 会丢锁（故障切换） | 严格 | 严格 |

一条主线贯穿：**Redis 锁是「抢占式」（靠 NX 原子性抢 key），etcd/ZK 锁是「排队式」（靠全序建队列，天然公平 + 天然带 fencing）**。排队式还送一个礼物——watch 前驱节点，锁释放时精确唤醒（对照 02 篇选主的随机超时：抢占式在竞争激烈时要重试，排队式睡到被叫醒）。

## 3. etcd 锁的实现：lease + revision 排队

etcd 官方 `clientv3/concurrency` 的锁机制（拆开看，每一步都能对上已有知识）：

```text
① 客户端创建 lease（TTL 10s）——崩溃后租约到期自动收（活性保障）
② 事务原子执行：
     If   revisions(mykey) == 0        (没被占)
     Then Put(mykey = leaseID)          (占用)
③ 没抢到（事务失败）→ Get 所有竞争 key 按 revision 排序
     自己不是最小 revision → Watch 排在自己前面的那个 key
     前驱删除（释放/租约过期）→ 我成为队头 → 持锁
④ 会话期间 KeepAlive 续约（对照 notes/redis/08 的看门狗——同一思想）
⑤ 释放 = Delete(mykey)（watch 我的人被唤醒）
```

正确性来源（每条都能用本模块前两篇解释）：

1. **Put 走 Raft 提交**——线性一致：不存在「两个客户端都成功 Put 同一个 key」（02 篇：每任期一个 Leader、log 串行）；
2. **故障切换不丢锁状态**——锁记录已提交到多数派（02 篇：提交不可逆）；
3. **revision 全序 = 现成的 fencing token**——后拿锁的 revision 必然更大，资源侧可校验；
4. **lease 过期 = 崩溃自愈**，KeepAlive = 正常续命。

## 4. ZK 锁与会话语义

ZK 的锁用**顺序临时节点**（ephemeral sequential）：

```text
① create /lock/txn-00000001 EPHEMERAL_SEQUENTIAL  (ZK 分配全序递增序号)
② GetChildren(/lock) 排序, 自己序号最小 → 持锁
③ 否则 Watch 前一个节点（/lock/txn-00000000）
④ 前驱删除（释放 or 持有者会话断开）→ 被唤醒 → 重新比较 → 持锁
```

ZK 的独门武器是**会话（session）**：客户端和 ZK 之间维持心跳，会话断开（崩溃/网络断）**服务端立即删除该客户端的所有临时节点**——比「等 TTL 过期」精确得多（秒级 TTL 的 Redis/etcd 要权衡「TTL 短误杀正常持锁者」vs「TTL 长崩溃后锁久不开放」；ZK 的删除粒度是「连接生死」，没有这个权衡）。

代价：会话对**长 GC 停顿**极敏感——客户端 STW 20s，服务端判定会话死亡删了节点，客户端醒来仍以为持锁（和 §1 的进程停顿攻击同一形态，ZK 也没有免死金牌，fencing 仍然必要）。Curator 的 `SessionAwareConnectionListener` 处理的就是这个。

## 5. Redlock 之争

**Redlock 算法**（Salvatore Sanfilippo / antirez 提出）：5 个**完全独立**（无主从复制）的 Redis 实例，加锁要在**多数派（≥3）**实例上 `SET NX` 成功、且总耗时小于 TTL——明显借鉴了 quorum 思想（01 篇 W>maj）。

**Kleppmann 的批评**（《How to do distributed locking》）：Redlock 的安全性依赖**时钟以相同速率流动**的假设——

```text
客户端 A 拿到 3/5 锁，TTL 剩 2s
某 Redis 节点时钟跳快 2s → A 的 key 提前过期
客户端 B 拿到 3/5 锁
A 仍在临界区 → 两个持锁者, 互斥被打破
（NTP 校时、VM 迁移、闰秒都是时钟跳变的现实来源——06 篇的主题）
```

结论分层记忆：

- Redis 官方立场：**效率用途**（efficiency，避免重复劳动——缓存击穿防护、任务去重）下 Redlock/单节点锁足够，偶尔两客户端重叠只是浪费一点资源；
- **正确性用途**（correctness——重叠即数据损坏/资金错误）必须 etcd/ZK 这类共识存储 + fencing；
- antirez 的回应也没否认时钟假设，只是论证工程上可控——**共识存储 + fencing 是唯一严格答案**。

## 6. watch：锁之外的第二大能力

协调服务（etcd/ZK）的第二支柱是**变更通知**——把「轮询」变「订阅」：

- **etcd watch**：`Watch(key prefix)`，任何 Put/Delete 推送到 channel（实现：MVCC revision 流，客户端从任意历史 revision 续看——「断线重连不丢事件」）；
- **ZK watch**：一次性通知（触发即失效，要重设）+ 不带数据（需再 Get）——工程上用 Curator 的 Cache 封装成持续 watch。

生产形态（配置中心 / 服务发现的骨架）：

```go
// 配置热更新的完整闭环（对照 notes/golang/07 atomic.Pointer 快照 + 10 WithoutCancel）
ch := client.Watch(ctx, "/config/app")
for resp := range ch {
    newCfg := parse(resp)               // 收到变更
    cfg.Store(newCfg)                   // atomic 整体换快照
}
```

Kafka 消费组的 rebalance、Nacos 配置推送、K8s 的控制器（informer watch API server）——全部是「共识存储 + watch」这个组合的实例。**把 etcd 理解为「带 watch 的线性一致 KV」**，它的全部产品形态（注册中心/配置中心/选主/锁）都是这个底座上的薄封装。

## 7. 选型决策

| 场景 | 选择 | 理由 |
|---|---|---|
| 缓存击穿防护、定时任务去重 | Redis `SET NX PX` + 看门狗 | 效率用途；重叠可容忍；已有 Redis 零新增依赖 |
| 主备选主 / leader election | etcd `concurrency.Election` | 正确性用途；lease 自动收 |
| 全局唯一操作（一次性的迁移、发号） | etcd/ZK 锁 | 绝不重复；revision 即 fencing |
| 配置中心 / 服务发现 | etcd/ZK + watch | 线性一致 + 变更推送 |
| 高频短临界区（每秒万次） | **重新设计**（分片锁/本地缓存），别上分布式锁 | 网络往返毫秒级，锁本身成瓶颈 |

元规则（和 03 篇选型同构）：**先问能不能不用分布式锁**（单机锁 + 数据分片归属、幂等设计天然免锁）；要用就按「重叠的代价」选存储——重叠只费钱用 Redis，重叠出事用共识存储 + fencing。

## 8. 面试高频

**Q1：Redis 锁和 etcd 锁的本质区别？**
存储层一致性：etcd 加锁走 Raft 线性一致提交（主挂锁状态不丢，互斥严格）；Redis 锁是主库内存 + 异步复制（故障切换瞬间锁可能凭空消失，两客户端同时「持锁」）。一句话：**锁的正确性上限 = 存储的一致性上限**。

**Q2：为什么锁必须带 TTL/lease？fencing 是什么？**
TTL/lease 保活性：持锁者崩溃后锁自动开放，不会死锁。fencing token 保互斥的降级：锁服务授锁时发单调递增令牌，资源侧拒绝旧令牌的写——长 GC 停顿后「自以为持锁」的旧客户端写入被资源侧强制拒绝。etcd 的 revision 天然就是 fencing。

**Q3：etcd 加锁的流程？**
建 lease（崩溃自愈）→ 事务原子 Put 抢 key（Raft 线性一致）→ 没抢到则按 revision 排序 watch 前驱 → 前驱释放被唤醒 → 持锁期间 KeepAlive 续约 → 释放 Delete。排队式：公平、精确唤醒、revision 现成 fencing。

**Q4：ZK 的临时节点比 TTL 好在哪？**
会话断开服务端**立即**删临时节点——崩溃的响应粒度是「连接生死」；TTL 方案要权衡「短 TTL 误杀正常持锁者 vs 长 TTL 崩溃后锁久不开放」。但 ZK 会话对长 GC 同样敏感（客户端醒来仍以为持锁）——fencing 仍不可省。

**Q5：Redlock 安全吗？**
多数派独立 Redis + 总耗时 < TTL 的加锁。Kleppmann 证明其安全性依赖时钟同速假设——节点时钟跳变（NTP/VM 迁移）会破坏互斥。定位：效率用途够用（重叠=浪费资源），正确性用途必须共识存储 + fencing。antirez 的回应聚焦工程可控，未否认假设。

**Q6：怎么选？**
效率用途（缓存防护/任务去重）→ Redis 锁（已有设施，快）；正确性用途（选主/唯一性）→ etcd/ZK；高频临界区 → 先重新设计（分片/幂等），分布式锁的网络往返本身是瓶颈。永远先问：能不能不用锁。
