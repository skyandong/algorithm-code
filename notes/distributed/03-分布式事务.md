# 分布式事务：从 2PC 到本地消息表

> **核心认知：** 分布式事务的全部困境来自一句话——**跨多个存储的写，无法共享一把本地锁、无法共用一个 undo log**。2PC 试图用协调者模拟原子提交，但协调者本身会挂（阻塞 + 脑裂风险），于是工程路线掉头：**放弃跨库原子性，改为「本地事务保证单库原子 + 补偿/重试保证最终一致」**——TCC 用业务层补偿，Saga 用逆操作回滚，本地消息表/事务消息用「和业务同库的消息 + 异步投递」消灭「业务成功但消息丢了」这个最常见的不一致。选型口诀：**强一致追求用 Seata-AT/TCC（有侵入），高吞吐用消息最终一致（无阻塞），跨行转账这种不能回滚的用 Saga**。

前置知识：MySQL 事务与 MVCC（`notes/mysql/02`）、2PC 的数据库前身XA（`notes/mysql/05-日志体系.md`）、Kafka 事务与投递语义（`notes/akafka/06` 附近）、错误重试边界（`notes/design-pattern/07`）。

## 1. 问题定义：哪些场景真的需要分布式事务

先泼冷水：**多数「分布式事务需求」是伪需求**。判别三问：

1. **真的跨存储吗**？同库两张表用本地事务就够了；分库分表后的跨分片写（notes/mysql/11）才算；
2. **真的要原子吗**？「下单成功 + 积分到账」差 5 秒用户无感（最终一致够）；「A 扣 100 + B 入 100」差一拍就是资金错误（要强一致）；
3. **能改成不跨吗**？同库冗余一张关联表、或把强关联数据哈希到同一分片——**最好的分布式事务是不发生分布式事务**。

真需求的典型：跨行转账（跨机构系统）、订单+库存+积分（跨服务跨库）、缓存/DB/ES 三处写（对照 notes/redis/05 双写一致——那是同一问题的弱一致版本）。

## 2. 2PC/3PC：原子提交及其代价

**2PC（两阶段提交）**——数据库 XA 事务的协议形态：

```text
阶段一（准备/投票）:  协调者 → 所有参与者: prepare
                      参与者执行事务但不提交, 锁住资源, 持久化 undo/redo → 回 "yes"/"no"
阶段二（提交/中止）:  全 yes → 协调者发 commit; 有 no → 发 rollback
                      参与者执行提交/回滚, 释放锁
```

它的三个致命伤（面试必须能讲出至少两个）：

1. **同步阻塞**：阶段一到阶段二之间，所有参与者持锁等待协调者指令——期间任何对这些数据的并发访问全部阻塞。跨网络的持锁窗口从毫秒变秒，吞吐断崖；
2. **协调者单点**：协调者在两阶段之间崩溃，参与者**既不能提交也不能回滚**（不知道决议），只能干等——数据被无限期锁住。XA 的 `heuristic` 决策（参与者自行猜测）正是这个死局的逃生门，但可能猜错；
3. **脑裂数据不一致**：协调者发 commit，部分收到执行了、部分没收到（网络分区）——参与者状态分裂。2PC 对此无解，只能靠人工/ reconciliation 修复。

**3PC** 的改进：把阶段一拆成 CanCommit（不锁资源的询问）+ PreCommit，并给参与者加超时（超时自行提交）——消除阻塞死锁，但**超时自行提交在分区时会造成不一致**（一侧提交一侧没收到）——用可用性换一致性，且多一轮 RTT 更慢。实践里 3PC 几乎没人用，工程界直接跳到「放弃原子提交」的路线。

## 3. TCC：业务层的两阶段

TCC（Try-Confirm-Cancel）把 2PC 的「锁资源」改成「业务冻结」：

```text
Try:     预留资源——冻结金额 100（余额 1000 可用 900）、占住库存 1 件
Confirm: 确认扣减——冻结的 100 真正扣掉（只许成功）
Cancel:  取消预留——解冻 100（只许成功）

转账示例:
  Try:    A 冻结 100          B 冻结 0（或预记一笔待入账）
  Confirm: A 扣冻结 100        B 入账 100
  Cancel:  A 解冻 100          B 删预记
```

和 2PC 的本质区别：**没有资源锁，冻结是业务字段**（`available`/`frozen` 两个余额列）——并发不阻塞，吞吐高；代价是**每个参与方要写三个方法**，侵入性极大。

工程铁律（TCC 的坑都在细节里）：

1. **Confirm/Cancel 必须幂等**——重试网络下会重复调用（对照 notes/design-pattern/07 重试边界）；
2. **空回滚处理**：Try 因网络没到达，Cancel 却先来了（协调者超时触发回滚）——Cancel 要能识别「没有 Try 过」并记录，否则空回滚后 Try 再到就出现「挂起事务」；
3. **防悬挂**：空回滚之后迟到的 Try 才到达——必须拒绝执行（用一个事务状态表挡住）；
4. **允许 Confirm 失败吗？不允许**——Confirm 失败只能无限重试（资源已预扣，回滚更危险）。

## 4. Saga：长事务的补偿回滚

长流程（订机票+订酒店+租车，跨三个外部系统，总耗时秒级分钟级）不适合持有任何预留——外部系统不给你 Try 接口。Saga 的解法：**正向执行每一步，失败时执行前面各步的补偿**：

```text
正向:  T1(订机票) → T2(订酒店) → T3(租车)   每步都是本地事务
失败:  T3 失败 → C2(退酒店) → C1(退机票)     补偿逆序执行

vs 2PC: 没有全局锁/预留——中间态对外可见（订了票还没订到酒店）
vs TCC: 补偿是"业务逆操作"（退款），不是解冻——机票可能已出票, 退票有手续费
```

实现形态两派：

- **编排（orchestration）**：中央状态机驱动（对照 notes/design-pattern/04 的转移表状态机——Saga 引擎本质就是个长状态机）；Seata Saga、Temporal 是这条路线；
- **协同（choreography）**：事件驱动，各服务订阅上游事件决定自己的动作——没有中心，但**流程散在事件订阅里，没人能一眼看懂全链路**（审计噩梦）。

**Saga 没有隔离性**（中间态裸奔）——语义上就是 01 篇的 BASE/最终一致。工程缓解：业务上允许（订票后酒店失败、稍后退款，用户可接受）或加「处理中」状态（01 篇 §4 的 UX 中间态）。

## 5. 本地消息表 / 事务消息：最常用的方案

线上使用率最高的方案，解决的是**最普遍的不一致源**：「DB 写成功了，发 MQ 失败/进程崩了」——业务成功但下游永远不知道。

**本地消息表（最容易落地，无任何中间件依赖）**：

```sql
-- 和业务同库！这是全部魔法的来源
BEGIN;
  UPDATE account SET balance = balance - 100 WHERE id = 'A';
  INSERT INTO outbox (id, topic, payload, status, retry, next_retry_at)
         VALUES ('msg-1', 'order.paid', '{...}', 'PENDING', 0, now());
COMMIT;  -- 业务写 + 消息写 在同一个本地事务里：要么都成要么都不成
```

```text
投递器（独立 goroutine / 定时任务）:
  SELECT * FROM outbox WHERE status='PENDING' AND next_retry_at <= now() LIMIT 100;
  逐条发 MQ（带消息 id）
  发送成功 → UPDATE status='SENT'        -- 消费方幂等去重（见下）
  发送失败 → retry+1, next_retry_at = now() + 退避(retry)   -- 指数退避重试
  超过上限 → status='DEAD'，告警人工介入  -- DLQ 思想
```

三个工程要点：

1. **消费方必须幂等**：投递是 at-least-once（重试会重复发）——消费端用消息 id 去重（`INSERT IGNORE` 到已处理表 / Redis SETNX，对照 notes/redis/05 幂等设计）；
2. **为什么能保证不丢**：消息和业务同库同事务——「业务成功而消息表没记录」这个状态不存在；投递失败靠扫表重试——「表里有而永远发不出去」被重试+死信兜住。合起来 = 最终一致；
3. **消息表要清理**：SENT 的行定期归档删除，否则表无限膨胀。

**事务消息（RocketMQ 半消息）**：把「本地消息表」搬进 MQ——先发半消息（对消费者不可见）→ 执行本地事务 → commit/rollback 半消息；本地事务成功但回查前崩溃 → MQ **回查**生产者「这个事务成没成」。etcd/Kakfa 生态里 Kafka 原生没有事务消息（transactional producer 解决的是 Kafka 内部跨分区原子性，不是「DB+MQ」原子性，对照 notes/akafka 的事务边界）——所以 **Kafka 场景的标配就是本地消息表**。

## 6. 选型决策表

| 方案 | 一致性 | 侵入性 | 吞吐 | 适用 |
|---|---|---|---|---|
| 2PC/XA | 强（有脑裂窗口） | 低（DB 层） | 差（跨网持锁） | 传统中间件、低频关键操作 |
| TCC | 强（准实时） | 高（每方 3 方法+幂等+防悬挂） | 好 | 资金类：冻结/预扣语义天然的业务 |
| Saga | 最终（中间态可见） | 中（补偿逻辑） | 好 | 长流程、跨外部系统、可回滚 |
| 本地消息表 | 最终（秒级收敛） | 低（一张表+投递器） | 高 | **默认选择**：业务写+异步通知 |
| 事务消息 | 最终（秒级收敛） | 低（MQ 要支持） | 高 | RocketMQ 生态的本地消息表平替 |

决策顺序（背下来）：**先问能不能不跨（同库/同分片）→ 默认本地消息表（侵入最小）→ 资金强一致上 TCC → 长流程可补偿用 Saga → XA/2PC 基本只活在教科书里**。

## 7. 面试高频

**Q1：2PC 的问题？**
①同步阻塞：prepare 后参与者持锁等指令，跨网持锁窗口秒级；②协调者单点：两阶段间崩溃则参与者无限期锁死（heuristic 决策可能猜错）；③脑裂：commit 只到一部分参与者——不一致需人工修复。3PC 加超时缓解阻塞但分区下更不一致，实践没人用。

**Q2：TCC 三个方法各做什么？三个坑？**
Try 冻结资源（业务字段，不是锁）；Confirm/Cancel 真扣/解冻。坑：①Confirm/Cancel 幂等（网络重试）；②空回滚（Try 没到 Cancel 先来——识别并记录）；③防悬挂（空回滚后迟到 Try 要拒绝）。用事务状态表统一治理。

**Q3：Saga 和 TCC 的区别？**
TCC 有资源预留（Try 冻结），并发不脏读；Saga 无预留直接正向执行、失败逆序补偿（业务逆操作，不是解冻）。Saga 中间态对外可见（无隔离性）适合长流程跨外部系统；TCC 适合资金冻结语义。

**Q4：本地消息表为什么能保证最终一致？**
「业务成功但消息丢」被同库同事务消灭（消息和业务共生死）；「消息在但发不出」被扫表重试+指数退避+死信兜住。消费端靠消息 id 幂等（at-least-once 语义下重复不可避免）。

**Q5：为什么 Kafka 配本地消息表而不是事务消息？**
Kafka 事务解决的是「多分区发送的原子性」，不覆盖「本地 DB + MQ」的跨系统原子；RocketMQ 半消息+回查才是这个问题的 MQ 内置解。所以 Kafka 生态用本地消息表（代价：一张表+投递器+清理任务）。

**Q6：怎么选型？**
先避（同库/同分片冗余设计）→ 默认本地消息表（侵入最小、吞吐高）→ 资金类强一致 TCC（可承受三方法侵入）→ 长流程可补偿 Saga → XA 只在遗留系统见到。一句话：能用最终一致就不用强一致。
