# 故障检测：从心跳超时到 phi-accrual

> **核心认知：** 分布式系统的根本困境之一：「**收不到消息**」有两种解释——对方挂了，或者只是网络慢/对方在 GC。**心跳超时是最粗暴的裁决：超时即死亡**——但阈值是拍脑袋的：短了误杀（一次 GC 就触发切主，旧主复活变双主），长了迟钝（真挂了要等半分钟才有替补）。工程演进两步：**φ-accrual 故障检测**（Akka/etcd 内置）输出「怀疑程度 φ」而不是 0/1 判决，把「什么时候算死」的决策权交给上层（想要低延迟选小 φ，想稳选大 φ）；**gossip**（Cassandra/consul）用「人传人」把成员信息扩散到 N 节点只需 O(log N) 轮——成员清单不需要强一致存储，最终一致就够。这两个原语 + 02 篇的 Raft 选主，构成所有「集群成员管理」的底座。

前置知识：Raft 选主的超时参数（本模块 `02`）、GC 停顿即分区（本模块 `01` §1）、MySQL 主从延迟的心跳监测（`notes/mysql/13`）。

## 1. 完美故障检测不存在

理论地基（FLP 的推论，不用背证明背结论）：**异步网络 + 可能崩溃的节点，不存在既能检测死亡又不误判的完美算法**。因为「慢」和「死」在网络外在表现上不可区分——消息没到，你永远不知道是它丢了、它排队中、还是发件人死了。

工程界的应对是把「检测」和「决策」拆开：

```text
朴素:    超时 3s → 判死 → 切主          （检测和决策焊死, 阈值一刀切）
成熟:    检测层输出"怀疑度"(φ) → 决策层按业务选阈值
         低延迟场景 φ=1 就动手（接受误杀）
         稳定场景 φ=8 才动手（接受迟钝）
```

把不可消除的不确定性，变成显式可调的参数——这是分布式工程的通用思路（和 01 篇「一致性谱系可调」同构）。

## 2. 心跳超时的工程权衡

心跳检测的标准形态（notes/mysql/13 的 `SLAVE` 心跳、Redis 哨兵的 `PING`、etcd 的 lease 都是它）：

```go
// 被检测方周期性心跳；检测方维护 last-seen
go func() {
    for range time.Tick(interval) { // interval = 1s
        sendHeartbeat()
    }
}()

// 检测方
if time.Since(lastSeen) > timeout { // timeout = 3~5 × interval
    markDead() // 触发故障转移
}
```

**阈值选择的两个错误方向**：

- **timeout 过短**（如 1.5×interval）：目标机器一次 Young GC 100ms + 网络抖动 200ms → 误判死亡 → 触发切主 → 旧主 GC 完复活 → **双主**（脑裂的常见起点）。对照 02 篇：Raft 用随机超时 150-300ms 是「够短能快速选主、够长不误杀心跳」的折中；
- **timeout 过长**（如 30s）：真死亡要等半分钟才有替补——可用性受损（SLA 的故障检测窗口直接算进 MTTR）。

工程经验值：**timeout ≥ 3×interval**（覆盖 1~2 次丢包 + 平均 GC）+ 心跳走独立连接池（别被业务流量阻塞）+ 观察分布再定（P99 心跳间隔 × 安全系数）。

## 3. φ-accrual：输出怀疑度

φ-accrual（Hayashibara，2004；Akka 的默认故障检测器、etcd 内部也在用）的核心思想：**心跳间隔是随机变量，学它的分布，用当前间隔的偏离程度算怀疑度**：

```go
// 离线看: 心跳间隔近似正态/指数分布, 收集最近窗口（如 1000 次）的
//   mean μ, 标准差 σ
//
// 在线算: 距上次心跳已过 t, 问 "正常情况下间隔超过 t 的概率是多少?"
//   φ = -log10(P(间隔 > t))
//
//   t 刚过 μ        → P≈0.5 → φ≈0.3（正常波动）
//   t = μ + 2σ      → P≈0.02 → φ≈1.7（有点可疑）
//   t = μ + 5σ      → P≈10⁻⁶ → φ≈6（非常可疑）
//
// 上层按需选阈值 φ_threshold:
//   想 100ms 内切换: φ=1（误报率高但快）
//   想稳如老狗:      φ=8（慢但基本不误杀）
```

三个工程红利：

1. **阈值语义稳定**：φ=3 在不同集群、不同负载下对应「偏离常态 3 个数量级」——比拍脑袋的「3 秒」可迁移（机器快慢、网络好坏自动适配）；
2. **单调的怀疑过程**：φ 随时间持续增长，上层还能做渐进响应（φ=2 时预热备用节点、φ=5 时切换）——0/1 判决做不到；
3. **窗口自适应**：网络变慢（整体分布右移），μ/σ 自动跟上，不误杀。对照 02 篇 pre-vote 的思路：用「观察常态」替代「拍死常数」。

## 4. gossip：人传人协议

成员信息（谁活着谁死了）要告诉 N 个节点。方案对比：

- 中心广播（一台告诉所有）：中心挂了就聋——违背分布式的初衷；
- 全互联（两两直连）：连接数 O(N²)，N=1000 时 50 万条连接；
- **gossip：每轮每人随机挑几个聊**——像传染病传播。

```go
// 每个节点周期性执行（如 1s 一轮）
func gossipRound(self *node, members map[int]*member) {
    peers := randomPick(members, k) // 随机挑 k 个（k=3 常见, 也用 fanout 术语）
    for _, p := range peers {
        p.receive(myState + 我知道的传闻) // 交换彼此的成员视图
    }
}

// 接收方: 合并信息（新状态覆盖旧的——用 06 篇的逻辑时钟定新旧）
```

数学性质：**每轮每人传染 k 个，ln(N) 轮后全员知情**——N=1000、k=3 约 6~7 轮（秒级全网收敛）。规模无关的收敛速度是它的王牌（Cassandra 上万节点的成员管理、consul 的 serf、比特币交易传播同构）。

三个设计细节：

1. **传播内容带版本**（incarnation number / 06 篇向量时钟）：合并时新旧可判，否则传闻打架无解；
2. **anti-entropy 模式**：除了随机聊，周期性找一个人**全量对账**——把 gossip 丢掉的消息补回来（和 05 篇无主复制的反熵同名同义：gossip 管快但可能丢，anti-entropy 管慢但保兜底）；
3. **故障信息的传播不对称**：alive 传闻立即信，suspect/dead 传闻要求更高 incarnation——**「说人坏话」要更谨慎**（防止误判被 gossip 放大成全网拉黑）。

## 5. 成员清单与故障转移

把 3+4 节的原语组装成真实的成员管理（consul/serf 的形态）：

```text
状态机（每个节点的视角）:
  alive → suspect（φ 超阈值或收到 suspect 传闻）→ dead（suspect 超时确认）
       ↑ 间接探测：suspect 前先请 k 个节点帮我 ping 一次（排除自己链路问题）

关键约束:
  ① suspect → dead 需要超时或多数确认 —— 单点的误判不能直接全网广播 dead
  ② dead 判定后, 新节点（同地址重生）用 incarnation 更大的 alive 传闻入场
  ③ 成员清单本身走 gossip 最终一致 —— 不需要 Raft（对照: 谁是 Leader 要共识, 谁活着只要趋势）
```

**故障转移的正确姿势**（把 02 篇选主和本篇检测拼起来）：

1. φ 超阈值 → suspect（不行动，仅标记）；
2. 间接探测确认（k 个其他节点也 ping 不通）→ 才升级 dead；
3. dead → 触发选主（Raft/哨兵投票）→ 新主产生；
4. **旧主复活** → 发现更大 term（02 篇）→ 退位成从。

第 2 步的间接探测是 Cassandra/Swim 协议的关键设计：**自己 ping 不通可能是自己的网络问题**——让第三方裁决。「多问几个人」是分布式故障检测的廉价保险。

## 6. 面试高频

**Q1：心跳超时阈值怎么定？**
≥3×interval 起步（覆盖丢包+GC），生产按实测分布调（P99 心跳间隔×安全系数）。过短误杀（GC 触发切主→双主脑裂），过长迟钝（MTTR 变差）。心跳走独立连接，别和业务流量共池。

**Q2：φ-accrual 是什么，比固定超时好在哪？**
学心跳间隔的分布（μ/σ），算当前偏离的怀疑度 φ=-log₁₀P(间隔>t)，输出连续怀疑度而非 0/1。好处：①阈值语义可迁移（不同集群/负载自适应）；②单调增长支持渐进响应（预热→切换）；③分布右移自动跟上不误杀。Akka/etcd 在用。

**Q3：gossip 为什么快？规模上限在哪？**
每轮每人随机传染 k 个，ln(N) 轮收敛——1000 节点约 6-7 轮（秒级），规模无关。配套：anti-entropy 周期全量对账兜底 gossip 的丢失；传闻带 incarnation/向量时钟判新旧。Cassandra/consul/比特币在用。

**Q4：怎么避免误判引发的脑裂？**
三道闸：①suspect 不直接 dead——间接探测（k 个第三方帮我 ping）排除自身链路问题；②dead 需要超时/多数确认，单点误判不能全网广播；③旧主复活靠 Raft 更大 term 自动退位。检测层输出怀疑度，决策层保守消费。

**Q5：成员清单为什么不用 Raft 存？**
「谁是 Leader/配置是什么」是 correctness（错了就脑裂）——需要共识；「谁活着」是 trending 信息（晚一秒知道没实质损失）——最终一致的 gossip 足够，还免去了共识的写入瓶颈。按信息的不一致代价选一致性等级（01 篇谱系的成员管理应用）。
