# 分布式理论面试一口答清单

> 从 01~07 篇笔记提炼的「张口就来」清单：被问到要能不带停顿直接说出来。
> 对应章节：`01-CAP-BASE-PACELC` ~ `07-故障检测`，实验代码在 `experiments/`。
>
> **记忆主线：** 两个根本困难——**网络不可靠**（CAP 的分区、故障检测的不确定、锁的租约）和**时钟不可信**（LWW 丢写、term/向量时钟、雪花回拨）。每个协议都是对这两点的应对；每个结论都能在 MySQL/Redis/Kafka 里找到实例对照。

---

## 一、CAP 与一致性谱系（01）

### 1. CAP 的准确表述？
不是三选二。P 是前提（分区必然发生），真命题是**分区时 C/A 二选一**：选 C 的节点必须拒答，选 A 的必须答旧值。且 CAP 只约束分区期间——常态下还有 PACELC 的 else 分支：延迟 vs 一致。

### 2. PACELC？
无分区时也要在 L（延迟）和 C 之间选：强一致复制要同步等多数副本，任一副本慢整个写就慢。ZK 是 PC/EC，Cassandra 可调，MySQL 异步主从 AP/EL。

### 3. 线性一致和顺序一致差在哪？
线性一致：操作顺序符合真实时间（你先写完我开始读，必读到新值）。顺序一致：所有节点看到的顺序相同，但可重排真实时间。线性一致贵在把真实时间编进全序，需要同步协调。

### 4. 最终一致要补什么才算工程可用？
收敛规则（LWW/向量时钟/CRDT/业务裁决）、收敛时长的监控与 SLA（主从延迟/lag）、中间态的产品设计（「处理中」或读主库）。缺这三样=不知道什么时候算错。

### 5. MySQL 主从 / Redis 哨兵 / Kafka acks=all 是什么组合？
MySQL 异步主从 AP/EL（主库照答可能丢尾部写）；Redis 哨兵同理（故障切换丢最后一段写）；Kafka acks=all+min.insync.replicas 过半 CP/EC（不足副本不可写）。一张 PACELC 表答完。

## 二、Raft 共识（02）

### 6. Raft 选主流程？
Follower 随机超时（150-300ms）→ Candidate、term+1、自投票拉票 → 过半当选；分裂等下轮随机重选。term 是逻辑时钟：收到更大 term 立刻退位。每任期每节点一票 + 过半交集 → 每任期最多一个 Leader。

### 7. 为什么 Raft 是 CP？
分区时少数派凑不够过半：选不出 Leader、无法提交——只能拒答；多数派照常。牺牲少数派可用性，换已提交数据永不丢。

### 8. 旧 Leader 复活怎么办？
旧 term 指令被见过更大 term 的 Follower 拒绝；旧 Leader 收到更大 term 自动退位，未提交日志被新 Leader 覆盖截断。无需显式换届。

### 9. 新 Leader 怎么保证不丢已提交日志？
选举限制：投票时只投「日志至少和自己一样新」的 Candidate。已提交日志过半持有 ∧ 当选集合与之相交 → 新 Leader 必然持有 → 提交不可逆。

### 10. 日志复制的连续性检查？
AppendEntries 带 prevLogIndex/Term，Follower 对不上就拒绝——Leader 逐级回退找分叉点重发，自动修复缺口（比 MySQL 手动指 binlog 位点先进）。

### 11. 为什么一次只能加减一个节点？
成员变更瞬间旧多数派和新多数派可能不相交——两个 Leader 各自合法当选，脑裂。单步变更保证必相交。etcd MemberAdd 就是单步的。

### 12. Raft vs Paxos？
能力等价，Raft 是工程化重构：选主/复制/安全三分解 + Leader 日志只追加（Paxos 允许乱序 accept，工程难做）。工业实现几乎全用 Raft。

## 三、分布式事务（03）

### 13. 2PC 的问题？
①跨网持锁（prepare 后等指令，秒级锁窗口）；②协调者单点（两阶段间崩溃=参与者无限期锁死）；③脑裂（commit 只到一部分）。3PC 加超时缓解但分区更不一致，实践没人用。

### 14. TCC 三方法三坑？
Try 冻结（业务字段非锁）/Confirm 真扣/Cancel 解冻。坑：Confirm/Cancel 幂等、空回滚（Try 没到 Cancel 先来）、防悬挂（空回滚后迟到 Try 拒绝）——用事务状态表治理。

### 15. Saga vs TCC？
TCC 有资源预留（冻结）并发不脏读；Saga 无预留直接正向执行、失败逆序补偿（业务逆操作）。Saga 中间态可见（无隔离性）适合长流程跨外部系统。

### 16. 本地消息表为什么能保证最终一致？
「业务成功消息丢」被同库同事务消灭（消息和业务共生死）；「消息在发不出」被扫表重试+退避+死信兜住。消费端按消息 id 幂等（at-least-once 重复不可避免）。

### 17. 怎么选型？
先避（同库/同分片）→ 默认本地消息表（侵入最小）→ 资金强一致 TCC → 长流程 Saga → XA 只在教科书。能用最终一致就不用强一致。

## 四、锁与协调（04）

### 18. Redis 锁和 etcd 锁的本质区别？
存储一致性：etcd 加锁走 Raft 线性提交（故障切换不丢锁状态，互斥严格）；Redis 是主库内存+异步复制（切换瞬间锁凭空消失，双持锁）。**锁的正确性上限=存储的一致性上限**。

### 19. TTL/lease 和 fencing 各解决什么？
TTL/lease 保活性（持锁者崩溃锁自动开放）；fencing token 保互斥的降级：授锁发单调令牌，资源侧拒绝旧令牌——长 GC 后「自以为持锁」的写被资源强制拒绝。etcd revision 天然 fencing。

### 20. Redlock 安全吗？
多数派独立 Redis+总耗时<TTL。Kleppmann：安全性依赖时钟同速——节点时钟跳变（NTP/VM 迁移）破坏互斥。定位：效率用途够（重叠=浪费资源），正确性用途必须共识存储+fencing。

### 21. ZK 临时节点比 TTL 好在哪？
会话断开服务端立即删——响应粒度是连接生死；TTL 要权衡「短 TTL 误杀 vs 长 TTL 迟钝」。但 ZK 对长 GC 同样敏感，fencing 不可省。

### 22. watch 的价值？
把轮询变订阅。etcd watch 走 MVCC revision 流（断线重连不丢事件）；配置中心/服务发现/K8s informer 全是「共识存储+watch」。etcd=带 watch 的线性一致 KV。

## 五、复制与分片（05）

### 23. 复制和分片解决什么？能一起用吗？
复制=可用性/读扩展（同份数据多处放）；分片=容量/写扩展（数据切开摆）。正交，生产大集群都用：Kafka partition+ISR、HBase region+副本。

### 24. 主从/多主/无主怎么选？
默认主从（无写冲突）。跨机房双活才多主（代价：LWW/CRDT 冲突处理）。写吞吐极高+最终一致可接受用无主（quorum+读修复+反熵）。多主/无主的复杂度全来自并发写无全序数据。

### 25. 半同步的价值？
把全异步「切换丢任意长尾部写」压到「确认从库同时挂才丢」。MySQL semi-sync、Kafka acks=all+min.insync.replicas=2 同构——「过小半数确认」的性价比点。

### 26. 一致性哈希为什么只挪 1/N？
节点和 key 共享环、key 顺时针归属最近节点——节点增删只改变附近一段弧的归属。虚拟节点解决少节点不均+摘除负载均匀散开；Redis Cluster 用 16384 槽变体。哈希函数要雪崩好的（md5/murmur；fnv32a 对相似短串聚集）。

### 27. 不停机扩容的通用骨架？
增量追平（双写/binlog 同步）→ 校验 → 元数据原子切换（etcd 一次事务）→ 老分片退场；限速迁移。「追平+原子切换」复用于 MySQL 扩容、Kafka 重分配、缓存重建。

## 六、时钟与顺序（06）

### 28. 为什么不能信时间戳？
晶振漂移、NTP 跳变（同一时刻观察两次）、VM 迁移/闰秒。LWW 按物理时间戳=「时钟漂移范围内允许丢写」（Cassandra 官方语义）。严格方案只有 Google TrueTime（GPS+原子钟给置信区间）。

### 29. Lamport vs 向量时钟？
Lamport 单计数器：因果保序（a→b 则 L(a)<L(b)），不能辨并发。向量 N 维：逐维比较能判「并发还是因果」——Dynamo 用它检测并发写触发裁决，而非 LWW 悄悄丢一个。

### 30. 雪花 ID 结构与回拨？
64=1+41 时间戳+10 机器+12 序列，趋势递增利于 B+ 树。回拨：小回拨等待/借序列，大回拨拒服务（唯一性优先）；Leaf-snowflake 用 ZK 对账；号段模式时钟无关。不做 fencing（只趋势不严格单调）。

### 31. Raft 的 term 和逻辑时钟的关系？
term 是 Lamport 时钟特例：竞选+1、消息携带、见大就更新——因果上更晚的 Leader 必然 term 更大。Raft 全程不碰物理时钟（超时只做触发器不做排序）。

## 七、故障检测（07）

### 32. 心跳超时怎么定？
≥3×interval 起步（覆盖丢包+GC），按实测 P99 分布调。过短误杀（GC 触发切主→双主），过长 MTTR 差。心跳走独立连接。

### 33. φ-accrual 比固定超时好在哪？
学心跳分布（μ/σ），算偏离怀疑度 φ=-log₁₀P(间隔>t)，输出连续值而非 0/1。阈值语义可迁移（负载自适应）、单调增长支持渐进响应、分布右移自动跟上不误杀。Akka/etcd 在用。

### 34. gossip 为什么快？
每轮每人随机传染 k 个，ln(N) 轮收敛——1000 节点约 8 轮，规模无关。anti-entropy 周期对账兜底。Cassandra/consul 在用。

### 35. 怎么防误判脑裂？
三道闸：suspect 不直接 dead（间接探测排除自身链路）；dead 需超时/多数确认；旧主复活靠更大 term 退位。检测层出怀疑度，决策层保守消费。

## 考前 60 秒主线串讲

**CAP**：P 前提、分区时二选一、平时 L vs C（PACELC）→ 谱系线性>顺序>因果>最终 → MySQL AP/EL、etcd CP/EC → 按读写路径选。
**Raft**：随机超时打散 → term 逻辑时钟（旧主见大退位）→ 过半交集（每期一主）→ 选举限制（新主必有已提交日志）→ 连续性检查自修复 → 单步成员变更。
**事务**：2PC 三伤 → TCC 冻结三坑 → Saga 补偿 → 本地消息表（同库共生死+重试死信+消费幂等）→ 能不跨就不跨。
**锁**：正确性=存储+fencing → etcd 排队锁（revision 即 fencing）→ TTL 攻击无解只能资源侧强制 → Redlock 卡在时钟假设。
**分片**：range 热点 vs hash 广播 → 一致性哈希 1/N → vnode 均衡+雪崩哈希 → 追平+原子切换的迁移骨架。
**时钟**：NTP 跳变 → LWW 丢写 → Lamport 保因果、向量判并发、HLC 合体 → 雪花回拨小等大拒。
**检测**：完美检测不存在 → φ 怀疑度自适应 → gossip ln(N) 收敛 → suspect→间接探测→dead 防脑裂。
