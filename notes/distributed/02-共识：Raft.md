# 共识：Raft 逐角色讲

> **核心认知：** 共识协议解决的问题是「**让多台机器对一串日志的顺序达成一致，从而表现出像单机一样**」——它同时给你容错（少数节点挂了不影响）和线性一致（所有节点按同序执行）。Raft 把这个难题拆成三个几乎独立的子问题：**选主（Leader Election）**、**日志复制（Log Replication）**、**安全性（Safety）**，每个子问题单独可懂——这是它击败 Paxos 的原因（Paxos 数学上更早，但讲不清楚）。理解 Raft 不能停在「过半投票」：真正的灵魂是**任期（term）作为逻辑时钟** + **「过半」保证任意两个多数派必有交集**这两个工具。etcd/consul/nacos 的分布式能力全部建立在这上面。

前置知识：CAP 的 C（`01-CAP-BASE-PACELC.md`）、MySQL 主从复制作为对照组（`notes/mysql/13`）。

## 1. 共识到底共识什么

「共识」这个词有歧义，精确定义：**N 个节点对「值/日志序列」达成一致，且协议保证一旦决定就不可更改**（agreement + validity + termination 三性质）。

它**不是**：

- 不是「所有节点实时一样」（只是收敛，那是最终一致——共识比它强）；
- 不是「选个主」——选主只是 Raft 的手段，不是目的（ZAB/Paxos 不用选主也能共识）；
- 不是拜占庭容错——Raft 假设节点诚实（崩溃/失联，不作恶）；作恶场景要 PBFT 一族，代价大得多，区块链才需要。

共识的威力在「决定不可逆」：一旦 log index 7 被提交为 `set x=5`，**任何后续新主都必然持有这条提交**——这给了你单机语义。对比 MySQL 异步主从：主库提交的 binlog 在故障切换时可能没到从库（丢失）——因为它的「提交」不需要过半确认。**Raft 的每次提交 = 过半节点持久化确认**，这就是 CAP 里 C 的来源，也是 PACELC 里 E（延迟高）的来源。

## 2. 选主：随机超时 + 任期 + 过半票

Raft 的角色三态：**Leader**（唯一处理写）、**Follower**（被动接受）、**Candidate**（竞选中）。

```text
正常期:   Leader ──心跳──> Follower 们（心跳维持权威）
Leader 挂: Follower 等心跳超时（150~300ms 随机）→ 变 Candidate
竞选:     Candidate 自增任期, 投自己一票, 向所有人拉票
          得过半票 → 当选新 Leader
          得不到   → 等下一轮（随机超时重新洗牌）
```

三个精妙设计（每个都是面试考点）：

**① 随机超时打散竞选**。如果所有 Follower 同时超时，全部变 Candidate、各投自己、谁也拿不到过半——活锁。超时在区间内随机，几乎必然有人先醒、先拉票、先赢。**这是用随机性解决对称性问题的经典**（和 07 篇 phi-accrual、以太网退避同思想）。

**② 任期（term）是逻辑时钟**。每次竞选 term+1，全局单调不减。任何消息都带 term：

- 收到 term 比自己大 → 立刻自贬为 Follower（对方的世界更新，我旧了）；
- 收到 term 比自己小 → 拒绝（过期领导的指令无效）。

**任期解决了「旧 Leader 复活」**：老 Leader 分区恢复后带着旧 term 回来，发现新 Leader 的 term 更大，自动退位——不需要显式的「换届仪式」。

**③ 过半票的数学**：N=5 时 3 票当选。任意两个过半集合（3+3>5）必有交集，交集里的节点不可能投两票（每任期每节点只投一票，先到先得，持久化后不再改）——**每任期最多一个 Leader**，这是安全性的第一块基石。

分裂场景走一遍（面试必考）：

```text
N=5, 分区成 {A,B} 和 {C,D,E}：
- {C,D,E} 侧: C 竞选得过半(3)票 → 当选, 继续接受写
- {A,B} 侧:   A 竞选最多 2 票 < 3 → 永远选不出 → 拒答（CP：不可用）
- 分区恢复:   A 看到 C 的更大 term → 退位; A 分区期间未提交的日志被 C 的覆盖
→ 完美对应 01 篇: Raft 是 CP——少数派牺牲可用性换一致性
```

## 3. 日志复制：主从复制的 Raft 严格版

Leader 的写流程（对照 MySQL 主从，标注差异）：

```text
客户端 → Leader: set x=5
Leader:  追加到本地 log（未提交）
Leader ──AppendEntries(带上前一条日志的 index/term)──> 所有 Follower
Follower: 检查「前一条对得上」(日志连续性检查)
          ├── 对得上 → 追加本地, ACK
          └── 对不上 → 拒绝 → Leader 回退发更早的, 直到找到分叉点
Leader:  收到过半 ACK（含自己）→ 提交(mark committed), 应用到状态机
Leader ──提交标记(随下一次心跳)──> Follower → Follower 也提交应用
Leader:  响应客户端 ✓
```

四个要点：

1. **提交 = 过半持久化**（MySQL 的差异点：主库自己持久化 binlog 就算提交，从库异步追）——这是「不丢已提交数据」的来源：少数副本的丢失不影响过半的存活；
2. **日志连续性检查（prevLogIndex/prevLogTerm）**：Follower 拒绝「接不上」的日志。这让复制具备**自修复**能力——Follower 宕机期间的日志缺口，Leader 靠逐级回退自动补齐（对比 MySQL 从库断点续传要人工指定 binlog 位点）；
3. **提交只由 Leader 宣布，且只提交当前任期的日志**（图 8 问题，§4 展开）；
4. **读写都在 Leader**（线性一致写；线性一致读要 ReadIndex 或走 log——否则会读到旧值，对应 01 篇 etcd 的 serializable 读选项）。

## 4. 安全性：三个不变量

Raft 的正确性全靠三个不变量撑住（合并自论文的 5 条性质）：

**不变量一：每任期最多一个 Leader**（选主 §2 的过半交集保证）。

**不变量二：日志只能从 Leader 流向 Follower，且 Leader 永不覆盖自己的日志**（只追加，不删除）。新 Leader 对「别人的旧日志」不覆盖——**用自己的日志把 Follower 不一致的部分覆盖掉**（Follower 的多余日志被截断）。为什么不整合两边日志？Raft 的选择：简单压倒一切，以当选者的日志为准。

**不变量三（选举限制，最精妙的一条）：Candidate 的日志必须「至少和过半节点一样新」才可能当选**——投票前，Follower 检查 Candidate 的最后日志 (term, index) 是否 ≥ 自己的；旧则拒票。

推论链：**已提交的日志（过半持有）→ 任何能当选的 Candidate 必然持有它（两个过半集合相交）→ 新 Leader 必然保有全部已提交日志 → 提交不可逆**。这一条是「状态机安全」的全部来源。

**图 8 问题**（面试深水区）：一条**旧任期**的日志即使被当前过半节点持有，也不能直接判提交——因为未来新 Leader 可能不持有它（见论文 Figure 8 的反例）。Raft 的解法：**Leader 只通过提交自己任期的日志来「间接」提交旧日志**（新日志提交时，它前面的历史必然已安全）。工程上等 Leader 上任先写入一条空操作（no-op）日志，就是为了让「自己任期的提交」尽快发生。

## 5. 成员变更与快照（工程补丁）

论文正文之外的工程必需：

**成员变更**：直接从 3 节点改 5 节点会产生**两个不相交的多数派**（旧配置 2/3 和新配置 3/5 可以各自形成 quorum），安全性崩塌。解法是**单步变更（joint consensus 的简化）**：一次只加/减一个节点，任何时刻旧多数派和新多数派必相交。etcd 的 `MemberAdd/MemberRemove` 就是单步变更——所以扩缩容要逐个来。

**快照（snapshot）**：日志无限增长不可持续。定期把状态机全量快照 + 截断之前的日志；落后的 Follower 直接发快照再增量追（对照 notes/redis/03 的 RDB + 增量 AOF 混合持久化——同一思想的两处实现）。

**预投票（pre-vote，工程标配）**：被分区隔离的节点不断竞选、term 疯涨；分区恢复后它的大 term 把正常 Leader 打下台（无谓扰动）。pre-vote 在真正拉票前先探一次「大家是否需要新 Leader」，没人响应就不涨 term。

## 6. 和已有知识的连接

| 已有知识 | Raft 对照 |
|---|---|
| MySQL 主从（notes/mysql/13） | 复制模型同构；差异：MySQL 提交=主库本地持久化（可能丢），Raft 提交=过半确认（不丢） |
| Redis 哨兵（notes/redis/04） | 哨兵选主 = 简化版 Raft 投票（过半哨兵同意才切换），但 Redis 的数据复制是异步的——**选主共识 ≠ 数据共识**，这是 Redis 丢写的根源 |
| Kafka ISR（notes/akafka/01） | `acks=all` + `min.insync.replicas=2` ≈ Raft 的「过半确认才提交」；ISR 收缩 = 成员变更的简化 |
| MySQL 组复制（MGR） | 就是 Paxos 变体（单主模式 ≈ Raft 形态） |
| 雪花 ID 时钟回拨（06 篇） | Raft 用 term 规避了物理时钟——逻辑时钟的胜利 |

## 7. 面试高频

**Q1：Raft 选主流程？**
Follower 随机超时（150-300ms）→ 变 Candidate、term+1、自投票、拉票 → 过半票当选；票分裂则等下轮随机超时重选。term 是逻辑时钟：收到更大 term 立刻退位。每任期每节点一票 + 过半交集 → 每任期最多一个 Leader。

**Q2：为什么 Raft 是 CP？**
分区时少数派凑不够过半：选不出 Leader（不能写）、作为 Candidate 无法提交——只能拒答；多数派照常服务。牺牲少数派可用性，换已提交数据永不丢。

**Q3：旧 Leader 复活怎么办？**
带着旧 term 发号施令 → Follower 看到更大 term（新 Leader 的）→ 拒绝旧 Leader → 旧 Leader 收到比自己大的 term 自动退位成 Follower，未提交的日志被新 Leader 的日志覆盖截断。

**Q4：新 Leader 怎么保证不丢已提交日志？（选举限制）**
投票时 Follower 只投「日志至少和自己一样新」的 Candidate。已提交日志被过半持有；能当选者的日志集合和它必相交 → 当选者必然持有全部已提交日志 → 提交不可逆。

**Q5：日志复制的连续性检查是干嘛的？**
AppendEntries 携带前一条日志的 (index, term)，Follower 对不上就拒绝——Leader 据此找到分叉点逐级回退重发，自动修复 Follower 宕机期的缺口（比 MySQL 手动指定 binlog 位点先进）。

**Q6：为什么一次只能加/减一个节点？**
成员变更瞬间，旧配置的多数派和新配置的多数派可能不相交——两个「Leader」各自合法当选，脑裂。单步变更保证任何时刻新旧多数派必相交。etcd MemberAdd 就是单步的。

**Q7：Raft 和 Paxos 什么关系？**
等价能力（都是非拜占庭共识），Raft 是 Paxos 的工程化重构：分解成选主/复制/安全三个独立子问题 + 强约束 Leader 日志（Paxos 允许乱序 accept，工程难做）。Raft 赢在可理解性和可验证性——工业实现几乎全用 Raft（etcd/consul/tidb/cockroachdb）。
