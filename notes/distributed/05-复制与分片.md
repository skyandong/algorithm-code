# 复制与分片：数据怎么摆

> **核心认知：** 单机到分布式只有两个动作：**复制（同份数据多处放，为可用/读扩展）** 和 **分片（不同数据切开摆，为容量/写扩展）**——两者正交，大集群两者都用。复制的核心权衡在 01 篇（一致性 vs 可用 vs 延迟），本篇补工程侧：**主从/多主/无主的拓扑选型**，以及**分片的最大难题——数据分布**：按什么切（range vs hash）、切完怎么路由、加机器怎么办（**一致性哈希就是把「加机器只挪 1/N 数据」变成系统性质**——对照 `engineering/consistenthash`，本篇是它的理论篇）。一句话总纲：**复制解决「单点」，分片解决「单机」，扩展性瓶颈在哪种就先上哪种**。

前置知识：CAP/PACELC（本模块 `01`）、MySQL 分库分表（`notes/mysql/11`——分片的数据库形态）、一致性哈希工程实现（`engineering/consistenthash`——本篇的理论对照）。

## 1. 复制三拓扑：主从 / 多主 / 无主

```text
主从（single-leader）        多主（multi-leader）        无主（leaderless）
   ┌──→ 副本1                 ┌──→ 副本1  ←──┐            客户端写任意 W 个副本
 写─┤                          写A─┤            ├─写B       客户端读任意 R 个副本
   └──→ 副本2                 └──→ 副本2  ←──┘            （Dynamo/Cassandra）
所有写经 Leader              两侧都可写（互相同步）
MySQL/Redis/Kafka            跨机房写、离线协作
```

| 维度 | 主从 | 多主 | 无主 |
|---|---|---|---|
| 写冲突 | 不存在（单点定序） | **存在**（两主同时改一行） | **存在**（并发写不同副本） |
| 冲突解法 | — | LWW/手动合并/CRDT | quorum 读裁决/读修复/CRDT |
| 故障切换 | 需选主（哨兵/Raft） | 天然多活 | 无主可切 |
| 典型 | MySQL 主从、Redis、Kafka | 跨机房双活、CouchDB | Cassandra、DynamoDB、RIak |

**选型直觉**：默认主从（简单、顺序明确，工程 80% 场景）；跨机房写延迟不可接受才上多主（吞下冲突处理的复杂度）；写吞吐极高 + 无强一致需求可用无主。**多主和无主的全部复杂度都来自「并发写同一份没有全序的数据」**——又是 01 篇的谱系选择。

## 2. 主从复制的工程参数

主从看似简单，工程上有三个参数旋钮（对照已有笔记）：

**① 同步程度**：

- 全同步（等所有从库）——一个慢从库拖垮主库，没人用；
- 全异步（不等）——MySQL/Redis 默认：主库提交即返回，故障切换可能丢尾部写（01 篇的 AP/EL）；
- **半同步（semi-sync）**——至少 1 个从库确认才返回：丢写风险从「任意多」压到「恰好确认的那个也挂」——MySQL 半同步插件、Kafka `acks=all`+`min.insync.replicas=2` 同构。

**② 复制方式**：语句复制（重放 SQL，now()/rand() 会错）/ 行复制（binlog ROW，体积大但正确——MySQL 8 默认）/ 逻辑日志。对照 notes/mysql/05 的 binlog 三种格式。

**③ 读路由**：读写分离省下的钱，用一致性付账——「写后立读」问题。三档处理：读主库（最贵最对）、粘性会话（同用户同从库）、版本戳路由（GTID 比对，notes/mysql/13 的复制位点思想）。对应 01 篇的「读己之写」一致性档位。

## 3. 无主与 quorum：Dynamo 风格

无主把「协调」彻底去掉：客户端（或协调节点）**并行写 W 个副本、并行读 R 个副本**，读到的多版本里取最新的（时间戳/版本向量裁决）。

- **W+R>N 保证读到已写值**（01 篇实验已证明：写集合与读集合必相交）；
- **W+R≤N 换性能**：W=1, R=1——写一份读一份，最快但可能旧；
- **读修复（read repair）**：读时发现某副本版本旧，顺手写回——读路径上做异步修复；
- **反熵（anti-entropy）**：后台对账任务，把读路径修不完的慢慢补齐（对照 01 篇 BASE 的「收敛时长」）。

Sloppy quorum（宽松仲裁）：分区时凑不齐 W 个「正式」节点，就先写进任意可达节点（临时顶替），恢复后再回迁——**可用性优先，接受暂时不在正式节点集合上**。这是 Dynamo 对 AP 的极致追求。

## 4. 分片：range vs hash

复制不扩容量（每台都放全量），扩容量靠分片。切法两派：

**Range（按区间）**：key 有序，按区间切——`[a-m]` 分片1、`[n-z]` 分片2。

- 优点：**范围扫描高效**（一个分片内连续读）——MySQL 按 ID 区间分表、Bigtable/HBase 的 rowkey 分区；
- 致命伤：**热点**——顺序写（自增 ID、时间戳）永远打到最后一片。HBase 的 rowkey 设计（加盐/反转）就是在给这个伤打补丁。

**Hash（按散列）**：`shard = hash(key) % N`——分布均匀，热点免疫。

- 优点：均匀、简单；
- 伤：**范围查询全分片广播**（相邻 key 散落在各处）；**N 变化时全量重分布**（`% N` 的 N 一变，几乎所有 key 换位置）——notes/mysql/11 分库分表里「扩容 = 全量迁移 + 双写切换」的痛苦来源。

**路由谁来做**：

1. 客户端直连（路由表下发到客户端——Redis Cluster 的 16384 槽位 + MOVED 重定向）；
2. 代理层（proxy 统一路由——分库分表中间件 MyCat/ShardingSphere）；
3. 协调节点（元数据在 etcd/ZK，请求先问路由——HBase Meta 表、Kafka 的 controller + metadata）。

## 5. 一致性哈希：增删节点只挪 1/N

朴素 hash 的死穴是 `% N`。一致性哈希（1997，Karger）的改造：

```text
① 节点和 key 都哈希到同一个环空间（2^64 圆环）
② key 顺时针找到第一个节点 = 归属
③ 节点 N 加入：只影响它和逆时针前驱之间的 key —— 从该前驱手里接管
   节点 N 离开：它的 key 全部交给顺时针下一个节点
```

数学性质：**N 个节点的环上加/删一个节点，平均只挪 1/N 的 key**（普通取模挪走几乎全部）。MySQL 分库扩容从「全量迁移」变「挪八分之一」。

两个必须知道的工程补丁（对照 `engineering/consistenthash` 的实现——那里有虚拟节点代码与测试）：

1. **虚拟节点（vnode）**：每个物理节点打散成 100~200 个虚拟点——否则节点少时环上分布极不均匀（3 节点最坏 70/20/10），虚拟化后均衡到 ±5%；附带红利：异构机器按权重分虚拟节点数、节点摘除时其负载**均匀**散给所有剩余节点（无虚拟节点是整包给顺时针下一个——下一节点被压垮的经典连锁故障）；
2. **有界负载（bounded loads，Google 2016）**：给一致性哈希加每节点容量上限，超了顺延给下一个——修掉虚拟节点也压不平的突发热点。

一个实测踩过的坑（实验验证过）：**哈希函数必须选雪崩特性好的**——fnv32a 对 `node-0`/`node-1` 这类相似短串极度聚集（实测 5 个节点挤在 1.5% 环长内，迁移量 0.3%、不均衡 21x），换 md5 取前 4 字节（ketama 同款）后迁移量 15%、不均衡 1.1x 全部符合理论。「哈希取模」四个字里藏着的第一个工程决策就是选对哈希函数。

生产实例定位：DynamoDB/Cassandra（数据分片）、Memcached 客户端分片（ketama）、Redis Cluster 的 **hash slot** 是改良变体（固定 16384 槽，节点只认槽——槽的迁移可以做成原子逐步的，比环上连续区间好管控）。

## 6. 热点与再平衡

分片系统运维两大难题：

**热点（skew）**：

- 识别：分片级 QPS/存储量监控的方差（Cassandra 的 `nodetool tpstats`、ES 的 shard 大小分布）；
- 自愈：自动分片分裂（HBase region split——超阈值自动对半切，所以 HBase 敢用 range）；请求侧加随机前缀打散（DynamoDB 的 hot partition 处理）；小表不分片（分片有路由开销，MB 级表别凑热闹）。

**再平衡（rebalancing）**：

- 何时：节点增减、数据倾斜超阈值、手动；
- 怎么不伤业务：**限速迁移**（HBase 的 region 迁移有带宽节流——迁移本身是 IO 大户，不限速等于对线上执行了一次压测）；
- **元数据原子切换**：先双写/增量追平 → 原子改路由表（etcd 一次事务）→ 老分片只读退场——和 03 篇本地消息表、MySQL 双写扩容同构：**「追平 + 原子切换」是所有无停机迁移的通用骨架**。

## 7. 面试高频

**Q1：复制和分片解决什么问题？能一起用吗？**
复制解决可用性/读扩展（同份数据多处放），分片解决容量/写扩展（数据切开摆）——正交，生产大集群两者都上：先分片再每片多副本（Kafka 的 partition + ISR、HBase 的 region + 多 region server）。

**Q2：主从/多主/无主怎么选？**
默认主从（无写冲突、顺序明确）。跨机房双活才上多主（代价：冲突处理 LWW/CRDT/手动）。写吞吐极高且可接受最终一致用无主（quorum 读写 + 读修复 + 反熵）。多主/无主的复杂度全部来自「并发写无全序数据」。

**Q3：半同步解决什么？**
把全异步的「故障切换丢任意长尾部写」压到「确认从库也同时挂才丢」——主库要等至少 1 个从库确认。MySQL semi-sync、Kafka acks=all+min.insync.replicas=2 同构：都是「过小半数确认」的性价比点。

**Q4：一致性哈希为什么能做到只挪 1/N？**
节点和 key 共享环空间、key 顺时针归属最近节点——节点增删只改变它附近一段弧的归属，数学期望 1/N。虚拟节点解决少节点不均 + 摘除负载均匀散开；Redis Cluster 用固定 16384 槽变体（迁移可控性优先）。

**Q5：range 和 hash 分片怎么选？**
要范围扫描（按时间/ID 拉区间）→ range（代价：顺序写热点，用预分裂/加盐缓解）。要均匀无热点 → hash（代价：范围查询广播、扩容重分布，用一致性哈希/槽位缓解）。数据库分表常见 hash(id)，时序/日志常见 range(time)。

**Q6：不停机扩容分片的通用骨架？**
增量追平（双写或 binlog 同步）→ 校验差异 → **元数据原子切换**（路由表一次改）→ 老分片退场。限速迁移保护线上。同一骨架复用于：MySQL 扩容、Kafka 分区重分配、缓存重建——「追平+原子切换」是通用答案。
