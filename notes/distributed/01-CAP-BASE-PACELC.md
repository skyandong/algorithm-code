# CAP / BASE / PACELC：一致性谱系

> **核心认知：** CAP 不是「三选二」的选择题——**分区（P）不是选项是前提**：网络分区迟早发生，发生时你只能在 C（一致）和 A（可用）之间二选一；**分区恢复后**还要在 L（延迟）和 C 之间继续选（PACELC 补丁）。工程上真正的问题从来不是「选哪个主义」，而是**按业务逐个决策**：余额扣减要 C（宁可不服务也不能错），feed 流要 A（旧一点没关系）。一致性也不是二值的——它是**谱系**：线性一致性 > 顺序一致性 > 因果一致性 > 最终一致，代价依次递减，选谱系上的哪一点才是架构师每天做的决定。

前置知识：MySQL 主从复制（`notes/mysql/13-主从复制与高可用.md`）、Redis 哨兵（`notes/redis/04-高可用.md`）、Kafka ISR（`notes/akafka/01-架构.md`）——本篇给这三处已有的实践一个统一的理论框架。

## 1. CAP 的准确表述

先纠正最普遍的误读。CAP 三个字母：

- **C（Consistency，线性一致性）**：任何读都能读到最近一次写——所有节点表现得像一份数据；
- **A（Availability，可用性）**：每个非故障节点对请求都给出（非错误）响应——注意不是「快」，是「有答」；
- **P（Partition tolerance，分区容忍）**：网络分区（节点间断联/消息丢失/延迟）时系统继续工作。

**为什么 P 不是可选项**：只要部署在多台机器上、走网络通信，分区就一定会发生（交换机故障、跨机房光纤被挖断、GC 停顿造成的「假分区」）。所以真实的命题是：**分区发生时，C 和 A 不可兼得**——

```text
N1、N2 互为副本。分区发生：
客户端写 N1，请求复制到 N2 的消息丢了。

- 选 C：N2 必须拒绝读（它不知道最新值）→ N2 不可用
- 选 A：N2 照常回答旧值 → 客户端读到过期数据，违背一致性

没有第三条路。
```

两个精细点（面试拉开差距的地方）：

1. **CAP 只在分区期间生效**。无分区时（常态），C 和 A 可以都要——单机 MySQL 就是。所以「系统是 CP」的准确含义是「分区时牺牲 A 保 C」，不是永远缺 A；
2. **A 的牺牲可以是部分的**。CP 系统通常不是完全不可用，而是**降级**： zk 分区时少数派不可服务但多数派照常——牺牲了少数派的 A。

**GC 也是分区**：一台 JVM/Go 服务 STW 30s，对集群来说它就是「分区了」。所以 CAP 不是极端场景理论——每次 GC、每次网络抖动都在逼你做 CP/AP 的瞬时选择。

## 2. PACELC：被忽略的 L

CAP 的完整工程版（2012 年，Abadi）：**分区时选 A 或 C；无分区时（else）选 L（latency）或 C**。

```text
if 分区:   选 A 或 C
else:      选 L 或 C        ← CAP 没讲的部分
```

WHY else 分支成立：保证强一致的复制要**等多数副本确认**（同步复制）——任何一个副本慢，整个写就慢。想低延迟就得放弃「等所有人」（异步复制），于是读到旧值的窗口出现（弱一致）。**延迟和一致性在日常运行中就是冲突的**，不需要等分区来触发。

对应到已有笔记的实例：

| 系统 | 分区时 | 平时 | 定位 |
|---|---|---|---|
| ZooKeeper/etcd | CP（少数派拒服务） | EC（写要过半确认，延迟高） | 强一致协调 |
| 单机 MySQL | 无分区问题 | C + L（无复制延迟） | 单点 |
| MySQL 异步主从 | 主库照常（A） | EL（从库延迟） | AP/EL |
| Redis 哨兵 | 主库照答（可能丢写） | EL（异步复制） | AP/EL |
| Kafka `acks=all` + `min.insync.replicas=2` | 分区剩 1 副本时不可写（C） | EC（等 ISR 确认） | CP/EC |
| DynamoDB/Cassandra | 可调（QUORUM/ONE） | 可调 | 谱系上任选 |

背下这张表，CAP/AP/CP 的面试题就从背诵变成对照表陈述。

## 3. 一致性谱系

「一致性」一词被滥用，严格说有两族：**数据一致性（副本一致）**和**读写一致性（客户端观察）**。谱系按客户端视角从强到弱：

**① 线性一致性（Linearizability，强一致 / CAP 的 C）**
所有操作看起来在「调用和返回之间的某个瞬间」原子地生效，且符合真实时间序。读一定读到「已完成的最新写」。代价：每次写要同步多数副本（或中心节点），跨机房 RTT 直接进延迟。实现：ZooKeeper/etcd 的写、单机 MySQL。

**② 顺序一致性（Sequential）**
所有节点看到**相同的操作顺序**，但这个顺序不必符合真实时间。比线性一致弱在：不同客户端的「真实先后」可能被重排（你先写完我再读，我仍可能读到旧值——只要所有节点的重排一致）。实现：ZooKeeper 的读（各节点本地读，顺序一致但可能旧）、主从复制的从库读。

**③ 因果一致性（Causal）**
有因果关系的操作，所有人看到的顺序一致；并发的操作顺序可以不同。例：我回复了你的帖子（回复因果依赖于帖子），任何人必须先看到帖子再看到回复——「回复在前帖子在后」的错乱不可接受；但两个人并发发的两个帖子，不同人看到不同顺序可以。实现：社交 feed、Cassandra 的 CLUSTERED LOCAL。

**④ 读己之写（Read-your-writes）**：自己写的一定立刻被自己读到（会话一致性）。实现：粘性读同库/版本号路由。

**⑤ 单调读（Monotonic reads）**：一次读到新值后，不会回头读到更旧的值。实现：从库版本戳路由（读到 v5 后只路由到 ≥v5 的从库）。

**⑥ 最终一致性（Eventual）**：停止写入后，经过有限时间所有副本收敛到相同值。**不保证中间过程的任何顺序**——它是谱系的地板，也是唯一「免费」的（异步复制就送）。

工程决策的心法：**逐功能、逐读写路径选，而不是逐系统选**。同一个系统里：余额扣减走线性一致（DB 主库），商品浏览走最终一致（缓存 + 异步同步）——这是「按业务逐个决策」的真正含义。

## 4. BASE：最终一致的工程契约

BASE（Basically Available, Soft state, Eventually consistent）是 AP 路线的工程宣言：接受中间态（软状态），承诺收敛（最终一致）。但「最终」两个字里藏着三个必须回答的问题，否则 BASE 就是耍赖：

1. **收敛到什么**？需要有「冲突裁决规则」——最后写入优先（LWW，依赖时钟，见 06 篇）、版本向量（谁赢）、CRDT（数学上保证收敛，如计数器求和、集合并集）、业务裁决（转账场景人工介入）；
2. **多久收敛**？要有可度量的复制延迟监控（MySQL `Seconds_Behind_Master`、Redis `master_repl_offset` 差值、Kafka 消费 lag）——「最终」没有 SLA 就是事故；
3. **中间态给用户看什么**？下单后 5 秒订单才出现 → 前端要么「支付处理中」的中间态展示，要么读走主库。**UX 设计是 BASE 的一部分**。

对照已有笔记：notes/redis/05-缓存常见问题 里的「缓存与 DB 双写不一致」就是 BASE 的中间态问题，那里的「先更库后删缓存 + 延迟双删」就是收敛手段；notes/mysql/13 的主从延迟章节就是收敛时长问题。

## 5. 真实系统在谱系上的位置

把仓库里学过的系统放进谱系（面试的「知识串联」题型）：

```text
强 ←————————————————————————————→ 弱
线性一致      顺序一致        因果/会话      最终一致
   │             │                │              │
etcd 写        ZK 读           feed 流        DNS
ZK 写          MySQL 从库读     Cassandra     异步主从
单机 MySQL                     因果一致模式    Redis 复制
Kafka acks=all                                              Kafka acks=1
```

三个「看似矛盾」的常见追问：

1. **「etcd 是 CP，为什么读可以走本地？」**——etcd 的共识只保证写线性一致；读到旧值时是顺序一致不是线性一致（线性读要走 Raft log 或 ReadIndex）。etcd 提供 `serializable` 读选项就是这个谱系选择；
2. **「Kafka 到底 CP 还是 AP？」**——按 acks 配置逐条选：`acks=all`+`min.insync.replicas=majority` 是 CP（宁可 NotEnoughReplicas 不可写）；`acks=1` 是 AP（可能丢）；`acks=0` 是「fire and forget」。Kafka 的可调一致性正是「谱系上逐点选择」的示范；
3. **「Redis 主从 + 哨兵是 CP 还是 AP？」**——AP：主库异步复制，故障切换可能丢最后一段写（官方文档明说）。这也是「Redis 锁不安全」的根源（04 篇展开）。

## 6. 面试高频

**Q1：CAP 说说你的理解？（80% 的人答错这题）**
不是三选二。P 是前提（网络分区必然发生），真命题是**分区时 C/A 二选一**：分区中选 C 的节点必须拒答（不可用），选 A 的必须答旧值（不一致）。且 CAP 只约束分区期间；常态下还要面对 PACELC 的 else 分支——延迟 vs 一致。

**Q2：PACELC 是什么？为什么需要它？**
补上 CAP 没讲的部分：**无分区时也要在 L（延迟）和 C 之间选**——强一致复制要同步等多数副本，任一副本慢整个写就慢；想快就得异步，于是有旧读窗口。例：ZK 是 PC/EC，Cassandra 可调。

**Q3：线性一致和顺序一致差在哪？**
线性一致：操作顺序符合真实时间（你先写完，我后开始读，必读到新值）。顺序一致：所有节点看到的顺序相同，但可以重排真实时间（不同客户端的先后可以颠倒）。线性一致贵在要把真实时间编进全序，需要同步协调。

**Q4：最终一致需要补齐什么才是工程可用的？**
三件事：收敛规则（LWW/版本向量/CRDT/业务裁决）、收敛时长的可观测（复制延迟监控 + SLA）、中间态的产品设计（「处理中」状态或读主库）。没有这三样，「最终一致」=「不知道什么时候算错」。

**Q5：MySQL 主从、Redis 哨兵、Kafka acks=all 分别是什么组合？**
MySQL 异步主从：分区时 A（主库照答可能丢）+ 平时 EL（从库延迟）→ AP/EL。Redis 哨兵同理 AP/EL（故障切换丢最后一段写）。Kafka acks=all+min.insync.replicas 过半：分区剩不足副本时不可写 → CP/EC。一张 PACELC 表答完。

**Q6：什么业务选 C，什么选 A？**
账务/库存/分布式锁 → C（错数据比不可用更糟，宁可拒绝交易）。feed/评论/推荐 → A（旧一点没损失）。同一系统内逐功能选：电商下单走 C，商品页走 A——「按读写路径选」而不是给整个系统贴标签。
