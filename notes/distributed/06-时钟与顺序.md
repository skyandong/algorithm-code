# 时钟与顺序：为什么不能信时间戳

> **核心认知：** 分布式系统里**物理时钟是个渐近正确但随时会跳的公共设施**——NTP 校时让两台机器的「同一时刻」差几毫秒到几百毫秒，VM 迁移能跳几十秒。于是「用时间戳判定先后」（LWW 的 last write）会错判顺序：后写的因为本机时钟慢被旧的覆盖——**数据悄无声息地丢**。替代品是逻辑时钟：**Lamport 时钟**保证「有因果关系的操作计数递增」，**向量时钟**进一步能判定「并发还是因果」，**HLC（混合逻辑时钟）**把物理时间可读性和逻辑时钟正确性合体（CockroachDB 在用）。这条线串起前面所有篇章：Raft 的 term、Redlock 的失败假设、fencing 的单调性，全都是「不敢信物理时钟」的不同侧面。雪花 ID 是这条主线的工程伴生品：它信任时钟到什么程度、回拨了怎么办，是高频面试题。

前置知识：Redlock 时钟假设（本模块 `04`）、Raft 的 term 作为逻辑时钟（本模块 `02`）、MySQL MVCC 的时间版本（`notes/mysql/02`——它是单机版「时间即顺序」的成功案例）。

## 1. 物理时钟为什么不可信

三个信不过的来源：

1. **晶振漂移**：石英钟每天漂秒级（~1ppm 量级误差）——不校准必然越走越歪；
2. **NTP 校时是跳变**：校时会把时钟**直接拨快/拨慢**（不是平滑修正，slew 模式除外但速率有限）——上一毫秒是 10:00:00，这一毫秒跳回 09:59:58，**同一个时刻被观察两次或零次**。基于时间戳的逻辑（「10 秒内只执行一次」）瞬间错乱；
3. **虚拟化/闰秒**：VM 迁移时钟跳几十秒；闰秒导致 23:59:60 这个「不存在的时刻」（NTP 的 smear 技术缓解但不是所有设施都启用）。

Google 的 TrueTime（Spanner）是正面硬刚：硬件 GPS + 原子钟，**给出「当前时刻的置信区间」[earliest, latest]**——事务提交要等区间收窄（`Commit Wait`），用确定的不确定性换严格的外部一致性。代价：专属硬件 + 写延迟下限被时钟区间钉死。这是「我要物理时间且要严格」的唯一满血方案，也解释了为什么多数系统选择干脆不用物理时间判顺序。

## 2. happens-before：先有因果后有顺序

分布式顺序的正确地基不是时间，是**因果关系**（notes/golang/05 内存模型的分布式放大版）：

定义（a → b 读作「a happens-before b」）：

1. 同一进程内：a 先执行则 a → b（程序序）；
2. 跨进程：a 是发送方，b 是同一消息的接收，则 a → b（消息序）；
3. 传递性：a → b 且 b → c 则 a → c。

**既无 a → b 也无 b → a，则并发（concurrent）**。注意「并发 ≠ 同时」——并发只是「没有因果链」，可能物理上差了十分钟。

反例理解 LWW 为什么丢数据：

```text
10:00:01  机器X(时钟快1分钟)  写 name="新值"（本地时间戳 10:01:01）
10:00:05  机器Y(时钟准)       写 name="更新值"（本地时间戳 10:00:05）
存储按 LWW 取时间戳大者 → 保留 "新值"（10:01:01 > 10:00:05）
因果上更晚的 "更新值" 被更早的 "新值" 覆盖 —— 静默丢写
```

**所有基于物理时钟的 LWW 都是「在时钟漂移范围内允许丢写」的一致性**——Cassandra LWW 的官方文档对此有明示。工程上缓解：LWW 只用于真正幂等的字段（计数器用 CRDT 加法而不是覆盖）。

## 3. Lamport 时钟：计出全序

Lamport 逻辑时钟（1978，分布式系统的开山论文）——给每个进程一个计数器：

```go
// 发消息前：本地计数 +1，计数随消息带走
func send() {
    clock++
    msg := Message{payload: ..., lamport: clock}
    net.Send(msg)
}

// 收消息后：取「本地」和「消息携带」的最大值再 +1
func receive(msg Message) {
    clock = max(clock, msg.lamport) + 1
}
```

核心性质：**a → b（因果）则 L(a) < L(b)**。计数沿因果链单调传递——后发生的因果事件计数必然更大。

但**逆命题不成立**：L(a) < L(b) 不代表 a → b（并发事件的计数也可以一高一低）。所以 Lamport 时钟能「保因果有序」，不能「辨并发」。要全序，用 (计数, 进程ID) 二元组打破平局——但这个全序里并发事件的先后是**编出来的**（按进程 ID 强行排序），没有真实含义。

## 4. 向量时钟：判出并发

向量时钟（vector clock）把单个计数扩成 **N 维向量**（每个进程一格）：

```go
// 每个进程维护 vec[N]；事件发生：自己的格子 +1
func localEvent() { vec[me]++ }

// 发消息：整个向量随消息走
func send() { vec[me]++; msg.vec = vec.Copy() }

// 收消息：逐维取 max，再自己的格子 +1
func receive(m Msg) {
    for i := range vec { vec[i] = max(vec[i], m.vec[i]) }
    vec[me]++
}
```

判定规则（对两个事件 的向量 Va、Vb）：

- Va ≤ Vb（逐维）且 Va ≠ Vb → a → b（因果）；
- Vb ≤ Va → b → a；
- **两个方向都不满足 → 并发**——向量时钟唯一的价值就是能明确说「这两个写是并发的」。

价值定位（Dynamo 的用法）：**并发不是错误，是需要裁决的状态**。检测到并发写 → 触发冲突处理（业务合并/人工介入/展示两个版本让用户选）——而不是像 LWW 那样装作没看见、悄悄丢一个。代价：向量 O(N) 随进程数膨胀（大集群用版本截断或 Dotted version vectors）。

## 5. HLC：混合逻辑时钟

HLC（Hybrid Logical Clock，2014）= 物理时间的可读性 + 逻辑时钟的因果安全：

```text
时间戳 = (physical, logical)
- 正常:  physical 跟随墙上时钟（单调不减）, logical=0
- 墙钟落后（收到的消息更"新"）: physical 钉在已见最大值, logical 递增
- 墙钟追上来: logical 归零
```

性质：**因果保持**（a → b 则 hlc(a) < hlc(b)，Lamport 的保证）+ **物理接近**（时间戳前半部分就是墙钟，日志/调试直接可读）+ **有界偏差**（logical 部分受物理时钟漂移界约束，不会无限涨）。

CockroachDB 用 HLC 判断事务新鲜度（读时「不确定窗口」回查，模拟 TrueTime 的廉价版）；MongoDB causal consistency 也有 HLC 影子。工程价值：**「故障排查时能看懂」是被低估的时钟需求**——纯 Lamport 计数在日志里是天书。

## 6. 雪花 ID：工程妥协的艺术

雪花（Snowflake）算法：**64 位 = 1 符号 + 41 时间戳 + 10 机器 + 12 序列**，单机每毫秒 4096 个——趋势递增（利于 B+ 树插入）、分布式不冲突、生成零网络往返（对照 06 篇分布式 ID 的其他方案）。

每一段都是一个工程决策：

- **41 bit 毫秒时间戳**：69 年寿命。**趋势递增但不保证严格递增**（时钟回拨会破）——「递增」只是高概率性质，不能当 fencing 用（对照 04 篇 fencing 要的是严格单调）；
- **10 bit 机器 ID**：1024 台——谁来分配？手动配（会重复）、ZK/etcd 领号（又依赖一个服务）、数据库自增（够用）。美团 Leaf 的 worker 分配走 ZK；
- **12 bit 序列**：同毫秒内递增，压满 4096 才等下一毫秒。

**时钟回拨（高频考点）**：机器 NTP 校时回退 50ms——同一时间戳被复用，序列从 0 重数，**和回拨前的 ID 撞车**。处理三档：

1. **拒绝**：回拨小于阈值（如 5ms）自旋等待墙钟追上（Leaf 的策略）；回拨大直接报错拒服务（宁可不可用不重复发号）；
2. **兜底扩展位**：预留几位「回拨位」，回拨时用掉一位保证不撞（用寿命换可用）；
3. **不依赖本地钟**：Leaf-snowflake 用 ZK 时间戳做对账校准；或干脆换号段模式（Leaf-segment：数据库一次发一千个号在内存里慢慢分，时钟完全无关）。

选型注脚：UUIDv4（随机）做 MySQL 主键是灾难（页分裂 + 索引膨胀，对照 notes/mysql/01 的聚簇索引顺序性）；UUIDv7（时间前缀）修复了递增性；雪花系仍是国内主流（不长、可读、带时间）。对比 03 篇消息 id 的「全局唯一」需求：那是幂等去重用途，雪花完全够格。

## 7. 面试高频

**Q1：为什么分布式系统不能直接用时间戳判先后？**
物理时钟不可信：晶振漂移（天级秒差）、NTP 校时跳变（同一时刻被观察两次）、VM 迁移/闰秒。LWW 用时间戳会「后写被先写覆盖」——时钟慢的机器的旧数据赢，静默丢写。唯一严格方案是 Google TrueTime（GPS+原子钟给置信区间）。

**Q2：Lamport 时钟和向量时钟的区别？**
Lamport：单计数器，因果有序（a→b 则 L(a)<L(b)），但**不能辨并发**（计数小不代表先发生）。向量：N 维向量，能判定**并发还是因果**（逐维比较，两方向都不满足即并发）。工程用法：Dynamo 用向量时钟检测并发写触发冲突裁决，而不是 LWW 悄悄丢一个。

**Q3：HLC 是什么，解决什么？**
混合逻辑时钟 (physical, logical)：正常跟随墙钟（日志可读），墙钟落后时 logical 递增保因果单调。兼得「物理时间的可读性 + 逻辑时钟的因果安全」。CockroachDB 用它做读的新鲜度判断——TrueTime 的廉价替代。

**Q4：雪花 ID 的结构？时钟回拨怎么办？**
64 位 = 1+41 时间戳+10 机器+12 序列，趋势递增利于 B+ 树。回拨处理：小回拨自旋等待、大回拨拒绝发号（保唯一性）、或预留回拨扩展位、或 Leaf-snowflake 用 ZK 对账。选型：不做 fencing（只趋势递增不严格单调）。

**Q5：UUID 和雪花怎么选？**
UUIDv4 随机——MySQL 主键灾难（页分裂/索引膨胀）；UUIDv7 时间前缀修复递增。雪花：64bit 短、带时间戳可读、本地生成零网络。国内主流雪花/Leaf（号段模式时钟无关）。要严格单调序的场景用数据库号段或 etcd revision（04 篇的现成 fencing）。

**Q6：Raft 的 term 和逻辑时钟什么关系？**
term 就是 Lamport 时钟的特例：竞选（事件）时 +1，消息携带、收到更大值就更新——「因果上更晚的领导」必然 term 更大。Raft 从头到尾没碰物理时钟（超时只做触发器不做排序依据）——共识协议对物理时钟零信任的典范。
