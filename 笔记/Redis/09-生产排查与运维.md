# 9. 生产排查与运维

## bigkey
- `redis-cli --bigkeys`:采样分析各类型最大 Key
- `MEMORY USAGE key`:精确查单 Key 内存
- 危害:阻塞主线程、网络拥塞、集群迁移卡顿、删除阻塞
- 处理:拆分、`UNLINK` 删除、`lazyfree`

## hotkey
- `redis-cli --hotkeys`(需开启 LFU 淘汰策略)
- `OBJECT FREQ key` 查访问频率
- 处理:本地缓存、拆分热点、读写分离

## KEYS vs SCAN
- **`KEYS pattern` 阻塞主线程**,生产严禁
- **`SCAN cursor`** 渐进式遍历,不阻塞,但可能返回重复/遗漏(遍历期间 rehash)

## slowlog
- `SLOWLOG GET`:慢查询日志(`slowlog-log-slower-than` 阈值,默认 10ms)
- 常见慢:`KEYS *`、大 Key 操作、`LRANGE 0 -1`、复杂 Lua

## 内存碎片
- `INFO memory`:`used_memory` vs `used_memory_rss`,比值过低有碎片
- `activedefrag yes`:主动碎片整理(jemalloc)

## CPU 飙升毛刺排查

Redis 命令单线程执行,**毛刺 = 主线程被某个耗时操作占住**。按出现频率排:

### 最常见原因

1. **bgsave / AOF 重写的 `fork()`** —— 周期性毛刺头号嫌疑人
   - fork 是主线程同步操作,要复制页表;实例内存越大 fork 越慢(几十 GB 实例可达数百 ms)
   - 特征:毛刺和 RDB/AOF 保存周期高度相关(定时触发)
   - 排查:`LATENCY HISTORY fork`;`INFO persistence` 看最近 bgsave 耗时

2. **大 key 的 O(N) 操作或同步删除**
   - `DEL`/`EXPIRE` 大 key、`HGETALL`/`LRANGE 0 -1`/`SMEMBERS`/`ZRANGE` 大集合
   - 特征:与某类业务流量相关,非周期性
   - 排查:`redis-cli --bigkeys`、`MEMORY USAGE`、`SLOWLOG GET`
   - 解决:拆 key、`UNLINK` 异步删、避免全量遍历

3. **慢命令**
   - `KEYS *`(O(N) 扫全库)、`SORT` 大集合、复杂 `SINTER`/`ZUNIONSTORE`、重 Lua 脚本
   - 排查:`SLOWLOG GET`;`INFO commandstats` 看哪类命令累计耗时高

4. **过期 key 集中淘汰**
   - 大量 key 同一时刻过期 → 定期删除循环忙;`hz` 越高扫描越激进越吃 CPU
   - 特征:与过期时间点对齐的周期性毛刺
   - 解决:过期时间加随机值打散

5. **`MONITOR` 没关**
   - 开了 MONITOR,每条命令都同步发给 monitor 客户端 → CPU 与 QPS 正比
   - 排查:`CLIENT LIST` 看有没有 monitor 客户端
   - 解决:关掉 MONITOR,生产别用

6. **内存淘汰触发**
   - 内存满 → eviction 采样 + 删除;`maxmemory-samples` 越高越吃 CPU
   - 排查:`INFO stats` 的 `evicted_keys`;`INFO memory` 看 used/max

7. **active defrag(主动碎片整理)**
   - `activedefrag yes` 在主线程跑,有 cycle 上限,可控但可能产生毛刺

### OS 层面(看着像 Redis 毛刺,其实是宿主)

- **THP(透明大页)**:fork/COW 期间卡顿,Redis 官方建议关闭
- **swap**:内存换页到磁盘 → 延迟和 CPU 双飙升,`free -m` 查 swap
- **CPU 没隔离**:同机其他进程抢 CPU
- **NUMA**:大实例跨节点访问

### 杀手锏:Latency Monitor(2.8.13+)

**是什么**:Redis 内置的延迟监控框架。把**超过阈值**的操作记成"延迟事件"(时间戳+耗时),专门抓毛刺。

- **默认关闭** —— 先 `CONFIG SET latency-monitor-threshold 100`(ms)才开始记录;建议写进配置常驻
- **只存内存**,重启丢失
- 阈值权衡:太低噪音大,太高漏毛刺,100ms 常见起点

**命令**:
- `LATENCY DOCTOR` —— 分析事件,直接给文字诊断(如"fork 耗时过长,建议关 THP")
- `LATENCY HISTORY event` —— 某类事件历史时序;类型:`fork`/`expire-cycle`/`aof-write`/`unlink`/`eviction-cycle`/`command` 等
- `LATENCY LATEST`(每类最近一次)、`LATENCY GRAPH event`(ASCII 图)、`LATENCY RESET`(清空)

**实战流程**:
1. `CONFIG SET latency-monitor-threshold 100`(开监控,建议常驻)
2. 等毛刺出现或复现
3. `LATENCY DOCTOR` 看初步结论 → `LATENCY HISTORY <event>` 对时间点确认

### Latency Monitor vs SLOWLOG(关键区别)

| | SLOWLOG | Latency Monitor |
|--|--------|-----------------|
| 记什么 | **慢命令**(命令执行耗时) | **延迟事件**(含内部非命令操作) |
| 能抓 fork/expire/aof-write | **不能**(不是命令) | **能** |
| 默认 | 开(阈值 10ms) | **关**(阈值 0) |

毛刺若由 fork、过期淘汰、AOF 写这类**内部操作**引起,`SLOWLOG GET` 是空的,只有 Latency Monitor 抓得到。两者互补,生产都开。

### 其他排查命令

- `SLOWLOG GET` —— 慢命令
- `INFO commandstats` —— 哪类命令累计吃 CPU
- `INFO persistence` —— `rdb_last_bgsave_time_sec`、`latest_fork_usec` 看 bgsave/fork 耗时
- `INFO stats` / `INFO memory` —— 淘汰数、内存
- `redis-cli --bigkeys` / `--hotkeys` —— 大/热 key
- `CLIENT LIST` —— 查 MONITOR 客户端

### 定位示例:怀疑是 fork 的问题

1. `CONFIG SET latency-monitor-threshold 100`(先开监控)
2. 等毛刺出现后查:
   - `LATENCY HISTORY fork` —— 看 fork 每次耗时,毛刺时间点对不对得上
   - `INFO persistence` —— `rdb_last_bgsave_time_sec`、`latest_fork_usec`
   - `LATENCY DOCTOR` —— 直接给结论

fork 慢的根因:实例内存大(页表复制久)、THP 开着(COW 卡顿)、写量大(COW 复制页多)。解决:缩内存/分片、关 THP、错峰触发 bgsave。

### 一句话排查顺序

`SLOWLOG` → `LATENCY`(fork/expire)→ `--bigkeys` → 查 `MONITOR` → 查 OS(THP/swap)
