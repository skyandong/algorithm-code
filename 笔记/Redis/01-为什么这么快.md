# 1. 为什么 Redis 这么快

> **核心观点(antirez)**:Redis 快**不是"因为单线程所以快"**,而是 **"瓶颈不在 CPU,所以单线程就够了"**。数据在内存,CPU 不是瓶颈,瓶颈在网络。单线程的好处是避免锁竞争和上下文切换,让单核跑接近极限。
>
> 这是最容易被问倒的点 —— 别把"单线程"说成快的原因,要说成"刚好够用、且避免了多线程开销"的设计选择。

## 四个支柱

- **基于内存**:数据读写直接操作内存,避免磁盘 I/O 瓶颈
- **高效数据结构**:跳表、listpack、哈希表等,时间复杂度低
  - SDS:O(1) 取长度、二进制安全
  - 字典:**渐进式 rehash**,扩容时分摊到后续操作,不阻塞
- **单线程命令执行**:无锁、无上下文切换,单核跑满
- **I/O 多路复用**:epoll 事件循环(`ae.c`),单线程高效处理海量并发连接

## 单线程:为什么"够用"反而最优

- 瓶颈是**网络和内存带宽**,不是 CPU —— 单线程已能逼近硬件极限
- 多线程要加锁,锁竞争 + 上下文切换可能反而拖慢
- **代价**:单条命令慢会**放大**阻塞所有后续命令 → 这就是官方强调"避免大 key(>10KB)"的原因

## Redis 6.0 多线程 I/O:补网络,不是推翻单线程

- 6.0 把**网络读写**(socket 读、协议解析、回包写)分摊到 I/O 线程池(`io-threads`,建议 2-4)
- **命令执行仍是单线程** —— 数据结构操作不加锁,线程安全
- 为什么只动 I/O:网络成了新瓶颈,这一环节可并行且无共享数据,性价比最高

## 真正的瓶颈在哪(官方观点)

- 网络 / 内存带宽,而非 CPU
- **pipelining** 能把吞吐拉到数倍(官方基准实测)
- 大 key、慢命令(`KEYS *`)会拖垮单线程 → 生产用 `SCAN`、拆 key
